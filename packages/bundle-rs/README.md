# doric-bundle

The Rust SDK of Doric bundles: the crate `doric-bundle`, the Nx project
`doric-bundle`. It is the bundle side of the control stream of
[`docs/designs/grpc-processes.md`](../../docs/designs/grpc-processes.md)
(section 10, "The Rust SDK"), server side only. A bundle built on it serves the
methods it registers and calls no other bundle. See
[`docs/features/bundle-processes.md`](../../docs/features/bundle-processes.md),
"Phase 4".

## API

- `run(bundle) -> ExitCode`: runs the bundle process until the host stops it.
  It reads `DORIC_ROUTER_URL`, `DORIC_INSTANCE_TOKEN`, `DORIC_BUNDLE_ID`,
  `DORIC_GENERATION` and `DORIC_INCARNATION`, opens
  `doric.platform.v1.BundleHostService/Connect` over cleartext HTTP/2 with
  `authorization: Bearer <token>`, and answers the exit code `main` returns.
- `Bundle`: `services()` (called once, before the `Hello`), `activate()`
  (on `Activate`; an error fails the activation) and `stop()` (on `Stop`; the
  process exits 0 once it returns).
- `Services`: `new()`, then `unary`, `server_stream` and `client_stream`, each
  with a gRPC method path such as `"/doric.storage.kv.v1.KvService/Get"` and a
  handler that receives a `Call` first. Requests and responses are `prost`
  messages.
- `Requests<Req>`: the request stream of a client-streaming call.
- `Call`: the `Caller` (`bundle_id`, `version`, `generation`, `incarnation`),
  `scope`, `traceparent`, `deadline` and `cancelled`, a `CancellationToken`.
- `ContractError { code, message, details }`, sent as a `google.rpc.Status`
  with a `google.rpc.ErrorInfo` (reason `code`, domain `doric`) and, when
  `details` is set, a `doric.platform.v1.ErrorDetails`; the gRPC code
  comes from the error table of `packages/bundle/src/contracts/status.ts`,
  `FAILED_PRECONDITION` for a code it does not hold.
- `log(level, message)` with `Level` (`Debug`, `Info`, `Warn`, `Error`):
  writes one JSON line on stdout, the same line the SDK writes for its own
  events (`level`, the lowercase name such as `warn`, `msg` and the
  instance's `bundleId`, `generation` and `incarnation`). A line written
  before `run` has read the environment, or when the environment is
  malformed, has no instance fields. It may be called from any thread and
  never fails.
- Re-exports `Stream` (`tokio-stream`) and `CancellationToken` (`tokio-util`).

In the example, `GetRequest` and `GetResponse` are the bundle's own messages,
generated by its `build.rs` (see "Generating a bundle's messages" below).

```rust
use std::process::ExitCode;

use doric_bundle::{Bundle, Call, ContractError, Services};

// The bundle's own generated messages, from its `build.rs`.
mod proto {
    tonic::include_proto!("doric.example.v1");
}
use proto::{GetRequest, GetResponse};

struct Kv;

impl Bundle for Kv {
    fn services(&self) -> Services {
        Services::new().unary("/doric.example.v1.KvService/Get", get)
    }

    async fn activate(&self) -> Result<(), ContractError> {
        Ok(())
    }

    async fn stop(&self) {}
}

async fn get(_call: Call, request: GetRequest) -> Result<GetResponse, ContractError> {
    Err(ContractError::new("not_found", format!("No key {}.", request.key)))
}

fn main() -> ExitCode {
    doric_bundle::run(Kv)
}
```

## Generating a bundle's messages

The SDK does not generate a bundle's messages. A bundle crate has its own
`build.rs` that compiles its `.proto` files from `dist/proto` with `protox` and
generates the `prost` messages with `tonic-prost-build`, as this crate's
`build.rs` does for the conformance messages. `dist/proto` is written by
`npx nx run @org/source:proto-export`, which must run first; this crate's own
`build.rs` needs it too, so every target of `doric-bundle` depends on it.

## Rules for handlers

- A handler must not block before its first `.await`. The SDK polls a handler
  once before it reads the next frame, so a blocking handler holds back
  `HealthCheck`, `CallCancel`, `CallCredit` and `Stop`, and the host can
  quarantine the instance after its `health_timeout`. Run blocking work with
  `tokio::task::spawn_blocking`.
- The 4 MiB limit applies to the encoded frame: a response whose frame would
  pass it is not sent, and the call ends `limit_exceeded`.

## Protocol behaviour

- Response messages never exceed credit: the `CallStart`'s `initial_credit`,
  then one per message a `CallCredit` counts. Each request a client-streaming
  handler takes grants the host one more (`CallCredit { messages: 1 }`).
- A call ends with `CallEnd`: `OK`, the status of a `ContractError`,
  `limit_exceeded` instead of a response frame over 4 MiB, `internal` when the
  handler panics, `invalid_input` when a request does not decode, and
  `CANCELLED` once the call is cancelled (`CallCancel` or
  its deadline), whatever the handler answers after.
- A cancelled call waits for its handler instead of aborting it; a long
  handler should watch `Call::cancelled`.
- A handler is polled once before the reader takes the next frame, as the
  TypeScript SDK runs a handler synchronously.
- A method the bundle did not register answers `unknown_contract`
  (`UNIMPLEMENTED`).
- In a client-streaming call, a request that does not decode is the last item
  of `Requests`, an `Err` with `invalid_input`.
- A `deadline_unix_ms` of 0 or NaN means the call has no deadline.
- A panic in `activate` answers `internal`. A panic in `stop` is logged, and
  `StopResult` and exit 0 follow.
- After `StopResult` has left the outbound queue, the SDK waits up to 250 ms
  (`FLUSH_GRACE`) for the host to end the stream. A stream that ends during the
  stop still exits 0.
- Handlers still running when the process exits are abandoned.
- The process exits 70 (the host is gone) when the environment is missing or
  malformed (an empty variable counts as missing), when the runtime fails to
  start, when the connection fails, on `Rejected`, when the first host frame is
  neither `Accepted` nor `Rejected`, when the stream ends after `Accepted`, or
  when no answer to the `Hello` arrives within 10 s of process start.
- Logs are JSON lines on stdout with `level`, `msg`, `bundleId`, `generation`
  and `incarnation`; lines logged before the environment is read have no
  instance fields.
- Requests are not checked against protovalidate rules (section 10, "No
  protovalidate"): a handler checks its own rules. A request that does not
  decode ends the call `invalid_input`.

## Build and test

```sh
npx nx run doric-bundle:build
npx nx run doric-bundle:test
npx nx run doric-bundle:lint
npx nx run doric-bundle:format-check
npx nx run doric-bundle:compile-example
npx nx run bundle:conformance
```

`build` is `cargo check` and produces no binary. `compile-example` builds `examples/conformance.rs`, a fixture that serves
`doric.conformance.v1.ConformanceService` and mirrors the TypeScript fixture;
`DORIC_CONFORMANCE_ACTIVATE=fail` makes its activation fail.
`bundle:conformance` depends on it and runs the conformance suite against it
through `packages/bundle/tests/conformance/rust.test.ts`.

## Limits

Server side only (spec A28): there is no client of the router, so a Rust bundle
calls no other bundle, and no registration, replay, `log/v1` facade, asset or
HTTP prefix.
