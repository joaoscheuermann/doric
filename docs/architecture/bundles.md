# Doric's architecture

- Status: living document. It describes the architecture as implemented on 2026-11-21, and indexes the architecture documents under `docs/architecture/bundles/`.

## Summary

Doric is a TypeScript-first agent core. Its product work is the agent runtime and the surfaces that support it directly: prompt, message and context handling; the abstraction over models and providers; the definition, invocation and results of tools; the control of the agent loop and its structured events; and errors, cancellation, retries and the minimal state those need ([`packages/agent`](../../packages/agent/README.md), [`packages/llms`](../../packages/llms/README.md), [`packages/tool`](../../packages/tool/README.md), [`packages/messages`](../../packages/messages/README.md)).

Around that core, every feature of the app is a **bundle**: model providers, the executor that runs a prompt, sandboxes, tools and skills, the Project and Thread model, durable events, hooks, storage, and the whole desktop UI, from the frame of the workspace window to each screen in it. The platform, the code of `packages/bundle`, `packages/desktop`, the host app and the desktop app ([The parts of the repository](#the-parts-of-the-repository)), knows no bundle's features: it reads manifests, activates the parts of the bundles a composition enables, carries calls between them and serves their files ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts), [`activation.ts`](../../packages/bundle/src/runtime/activation.ts), [Bundle boundaries](bundles/boundaries.md)). One bundle of the composition is the **core**, which provides the basic services every other bundle builds on; any of those services may come from another bundle the composition chooses instead ([`core/manifest.json`](../../bundles/foundation/core/manifest.json), [The core bundle](bundles/core.md)).

This document is the overview: what the parts are, how they fit, and where each mechanism is described in full. Each mechanism has one home among the documents of the [index](#index-of-the-architecture-documents); a bundle's own contracts, routes and data are in its README, and a flow across bundles in its feature doc under `docs/features/`, such as [Local history](../features/local-history.md) or [UI redesign](../features/ui-redesign.md).

## The parts of the repository

| --------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host      | `app/backend/doric-host`                                                        | The agent host: long-lived, sandbox-backed Projects and their Threads behind REST and Socket.IO, and the source of truth for the installed bundles and the composition ([host README](../../app/backend/doric-host/README.md), [`composition.json`](../../app/backend/doric-host/composition.json))                                                                                     |
| Desktop   | `app/desktop/doric`, `app/desktop/doric-renderer`, `app/desktop/doric-platform` | The Electron app: its main process downloads and verifies the bundles, runs their `desktopMain` parts and creates the windows; every window loads one shell and runs the `client` parts ([`app.ts`](../../app/desktop/doric/src/platform/app.ts), [`build.mjs`](../../app/desktop/doric-platform/build.mjs))                                                                            |

## What bundles supply

A bundle reaches another only through the contracts that bundle publishes, and imports no module of it but `<id>/contracts` ([Contracts](bundles/contracts.md), [`boundaries.test.mjs`](../../tests/boundaries.test.mjs)). The shipped composition is made of these kinds of bundle ([`composition.json`](../../app/backend/doric-host/composition.json)):

- **The core and the foundation.** `core` provides the basic services on the host, in the desktop's main process and in each window. `postgres` provides `storage.backend/v1` and `secrets.backend/v1` over PostgreSQL, chosen under `providers` ([`core/manifest.json`](../../bundles/foundation/core/manifest.json), [`postgres/manifest.json`](../../bundles/foundation/postgres/manifest.json)).
- **The domain and its execution.** `runtime` owns the Project and Thread model, the prompt queue and the leases (`runtime/v2` and the other `runtime.*` contracts); `default` provides the executor, `executor/v1`, which runs the agent loop of `packages/agent` ([`runtime/manifest.json`](../../bundles/runtime/runtime/manifest.json), [`default/manifest.json`](../../bundles/runtime/default/manifest.json), [`executor.ts`](../../bundles/runtime/default/src/host/executor.ts)).
- **Model providers and sandboxes.** `openai`, `openrouter`, `codex` and `claude` each register a provider kind in `models.provider/v1`, a contract of cardinality `many` that the core's `models/v1` aggregates. `docker` and `firecracker` provide `sandbox/v1`; the composition's `alternatives` picks one by `DORIC_SANDBOX_PROVIDER`, `docker` by default ([`openai/manifest.json`](../../bundles/providers/openai/manifest.json), [`models/index.ts`](../../bundles/foundation/core/src/host/models/index.ts), [`composition.json`](../../app/backend/doric-host/composition.json)).
- **Features.** Files, Git, the terminal, the web, resources, the screen, usage, MCP, comments, generated UI and the others register tools, skills, services, hooks and event types on the host, and the elements that show them in the windows ([bundle map](bundles/feature-split.md)).
- **The host's transport.** `transport` registers the REST routes and the Socket.IO namespaces over the services of the other bundles; their reference is in the [host README](../../app/backend/doric-host/README.md#rest-api) ([transport README](../../bundles/foundation/transport/README.md)).
- **The desktop UI.** `layout` draws the frame of the workspace window and declares its slots; `workspace`, `chat`, `account`, `settings` and the client parts of the feature bundles draw everything inside it. The renderer itself holds no product UI ([`bootstrap.ts`](../../packages/desktop/src/client/bootstrap.ts), [The layout bundle](bundles/layout.md), [UI composition](bundles/ui-composition.md)).
- **Features of the desktop's main process.** A bundle may own a `desktopMain` part. The local history cache is one: `history` keeps a snapshot of each Thread's event log on disk, under its directory of the platform contract `doric.cache/v1`, keyed by the host's storage identity, so a conversation renders at once when it opens ([`history/src/desktop/index.ts`](../../bundles/desktop/history/src/desktop/index.ts), [Storage](bundles/storage.md#the-local-snapshot), [Local history](../features/local-history.md)). `chat`, `notifications`, `papercraft` and `screen` have `desktopMain` parts as well ([bundle map](bundles/feature-split.md)).

## Three environments and their processes

A bundle has up to three parts, one per environment, each built from its own entry point: `host` (`src/host/index.ts`), `desktopMain` (`src/desktop/index.ts`) and `client` (`src/client/index.ts`) ([Manifest](bundles/manifest.md#package-layout-and-build-output)). Each part exports `activate(ctx)`, and the context has one member, `services`, in every environment; the core receives the same context as any bundle ([`context.ts`](../../packages/bundle/src/contracts/context.ts), [Contexts](bundles/contexts.md#the-context)).

| Environment   | Process                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host`        | The host process is the **kernel**: it runs the foundation, the core and the bundles the composition lists under `resident` (`host-config`, `transport`, `screen-relay`). Every other host part runs in a **generation process**, one Node process per bundle generation, which the kernel forks and restarts when it is lost ([`kernel.ts`](../../packages/bundle/src/process/kernel.ts), [`partition.ts`](../../packages/bundle/src/process/partition.ts), [`manager.ts`](../../packages/bundle/src/process/manager.ts)) |
| `desktopMain` | One Electron `utilityProcess` per desktop generation; the Electron main process plays the kernel and provides the native platform contracts, such as windows, menus and the cache directory ([`process.ts`](../../app/desktop/doric/src/platform/generation/process.ts), [`broker.ts`](../../app/desktop/doric/src/platform/generation/broker.ts))                                                                                                                                                                         |
| `client`      | Each app window. A window stays on the generation it loaded with ([`activate.ts`](../../packages/desktop/src/client/activate.ts), [`app.ts`](../../app/desktop/doric/src/platform/app.ts))                                                                                                                                                                                                                                                                                                                                 |

A new generation is a new process, so bundle code changes without restarting the host or the app. The kernel and a generation call each other's services through one RPC envelope, and a bundle does not see the boundary ([`link.ts`](../../packages/bundle/src/runtime/envelope/link.ts), [Process isolation](bundles/process-isolation.md)).

## Composition, activation and the core

The host keeps the **composition**, one JSON file: the core bundle, the enabled bundles, the provider chosen for a contract under `providers`, and the `resident`, `required` and `alternatives` fields ([`composition.json`](../../app/backend/doric-host/composition.json), [Composition and distribution](bundles/composition-and-distribution.md#the-composition-file)). From it and the manifests, the catalog decides, without running bundle code, which bundles activate and in what order. In each environment it activates three phases: the **foundation** (the providers chosen for contracts the core provides or requires), then the **core**, then the other bundles in the dependency order of their `requires` ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts), [Composition and distribution](bundles/composition-and-distribution.md#foundation-and-activation-order)).

Any contract without the `doric.` prefix may be provided by another bundle. A contract of cardinality `one` has one active provider; a second one the composition does not choose is quarantined. A contract of cardinality `many` aggregates its providers ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts), [Composition and distribution](bundles/composition-and-distribution.md#providers-and-cardinality)).

A bundle that fails to validate, resolve or activate is **quarantined** with a reason, together with the bundles that require what it provides; the others keep running. When the core or a chosen foundation provider cannot activate, the environment enters **recovery mode** ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts), [The core bundle](bundles/core.md#quarantine)). What must work without the core stays in the platform: the catalog, diagnostics, the splash and recovery surface, the `doric://app` origin, the IPC bridge, the generation processes, the native window and menu APIs and the platform's own log ([The core bundle](bundles/core.md#what-the-platform-keeps)).

On the desktop, the main process reads the host's distribution through `doric.catalog/v1` during the splash, downloads the files it lacks, checks each one's SHA-256 and activates the `desktopMain` and `client` parts against its own platform version ([`distribution.ts`](../../app/desktop/doric/src/platform/catalog/distribution.ts), [Composition and distribution](bundles/composition-and-distribution.md#the-splash-on-the-desktop)). The splash is one technical surface outside any bundle; when loading fails, it becomes the recovery surface and offers the actions that correct the composition ([`splash.ts`](../../app/desktop/doric/src/splash-page/splash.ts), [Splash and recovery](bundles/splash-and-recovery.md)).

## How bundles talk to one another

Every capability is a service contract reached through `services` ([`services.ts`](../../packages/bundle/src/runtime/services.ts), [Contexts](bundles/contexts.md)):

- **Basic contracts** carry no bundle name: `hooks/v1`, `log/v1`, `settings/v1`, `secrets/v1`, `secrets.backend/v1`, `tools/v1`, `skills/v1`, `storage/v1`, `storage.backend/v1`, `events/v1`, `models/v1`, `models.provider/v1`, `commands/v1`, `ui/v1`, `navigation/v1`, `regions/v1`, `windows/v1` and `menus/v1`. The platform declares them in `bundle/contracts`, with their cardinality and environments in a fixed table. The core provides them by default, except `storage.backend/v1` and `secrets.backend/v1`, which `postgres` provides, and `models.provider/v1`, which the model-provider bundles provide ([`basic/index.ts`](../../packages/bundle/src/contracts/basic/index.ts)).
- **Platform contracts** (`doric.*`) are the platform's own capabilities, such as `doric.catalog/v1`, `doric.diagnostics/v1`, `doric.windows/v1`, `doric.menus/v1`, `doric.cache/v1` and `doric.log/v1`; they always exist and no bundle provides them ([`platform.ts`](../../packages/bundle/src/contracts/platform.ts)). Their full shapes are in [Contexts](bundles/contexts.md#shapes-of-the-platform-contracts).
- **Bundle contracts** are named `<bundle>.<name>/vN`, or `<bundle>/vN` for a bundle's main contract, such as `runtime.threads/v1`, `layout.tabs/v2` or `runtime/v2`, and are described in the README of the bundle that provides them. A bundle may also declare a contract for others to provide: `runtime` declares `executor/v1`, which `default` provides, and `sandbox/v1`, which `docker` and `firecracker` provide ([`ids.ts`](../../packages/bundle/src/contracts/ids.ts), [`executor.ts`](../../bundles/runtime/runtime/src/contracts/executor.ts), [`sandbox.ts`](../../bundles/runtime/runtime/src/contracts/sandbox.ts), [Contracts](bundles/contracts.md#contract-ids)).

A contract is written in zod with the `define*` family, and its id carries its major version; the build generates its JSON Schema ([`define.ts`](../../packages/bundle/src/contracts/define.ts), [Contracts](bundles/contracts.md), [Versioning](bundles/versioning.md)). A bundle lists in its manifest every contract it provides, requires or may use, except a `doric.*` contract ([`manifest.ts`](../../packages/bundle/src/runtime/manifest.ts), [Manifest](bundles/manifest.md)).

Bundles exchange four kinds of message, each with a delivery contract of its own ([Services and channels](bundles/services-and-channels.md#the-message-channels)):

- **Service calls.** `services.use(ref)` returns a typed stub that reaches the provider wherever it runs. Each method receives `(input, call, services)`; the platform fills `call.caller` with the bundle that made the hop, inherits the scope, the signal and the trace from a parent call, and fills `scope.windowKey` for a call that leaves a window ([`call.ts`](../../packages/bundle/src/runtime/call.ts), [`dispatch.ts`](../../packages/bundle/src/runtime/dispatch.ts)). A window reaches every service it does not provide itself through the desktop process, which alone talks to the host, and only the methods a contract exposes to the desktop ([`dispatcher.ts`](../../app/desktop/doric/src/platform/bridge/dispatcher.ts), [`exposure.ts`](../../packages/bundle/src/runtime/exposure.ts)).
- **Hooks.** The owner of an operation declares its hooks, and any bundle may observe them through `hooks/v1`. The app's lifecycle is a set of hooks the platform declares, `doric.app.hooks/v1` and `doric.window.hooks/v1`, and defines in each environment's provider of `hooks/v1`; the core opens the primary window and sets the menu skeleton from `onAppReadyHook` ([`core/src/shared/hooks.ts`](../../bundles/foundation/core/src/shared/hooks.ts), [`core/src/desktop/index.ts`](../../bundles/foundation/core/src/desktop/index.ts), [`activation.ts`](../../packages/bundle/src/runtime/activation.ts), [Hooks](bundles/hooks.md)).
- **Durable events.** A bundle declares an event type with `defineEvent` and appends it through `events/v1`; every event lands in the log of one Thread, which the conversation projects into what the reader sees ([`core/src/host/events/facade.ts`](../../bundles/foundation/core/src/host/events/facade.ts), [Events and nodes](bundles/events-and-nodes.md)).
- **DOM events** between the elements of one window ([UI composition](bundles/ui-composition.md#elements-are-the-boundary)).

## Windows and the UI

The Electron main process creates every window and keeps the preload and the IPC boundary, and no window is fixed in it: the core opens windows through the platform contract `doric.windows/v1`, and other bundles through the core's `windows/v1` or `doric.windows/v1` itself. A window is a key plus a path; the core opens the `workspace` window at `/`, or at the last path it showed ([`native-windows.ts`](../../app/desktop/doric/src/platform/windows/native-windows.ts), [Windows](bundles/windows.md)). Every app window loads the same shell from the origin `doric://app`, which also serves the platform packages and the bundles' files ([`handler.ts`](../../app/desktop/doric/src/platform/protocol/handler.ts), [The `doric://app` protocol](bundles/doric-protocol.md)).

In a window, the bootstrap activates the client parts and puts the core's `<core-outlet>` in the `body`; the path of the window's URL chooses the route the outlet shows, and the outlet shows `<core-not-found>` when no active bundle registered that path ([`bootstrap.ts`](../../packages/desktop/src/client/bootstrap.ts), [`outlet.ts`](../../bundles/foundation/core/src/client/elements/outlet.ts), [Navigation](bundles/navigation.md)). The boundary between bundles in a window is the custom element: a bundle defines elements whose tag starts with its own id and shows another bundle's elements by tag, through `ui/v1`, without importing their code ([`core/src/client/ui.ts`](../../bundles/foundation/core/src/client/ui.ts), [UI composition](bundles/ui-composition.md)). An element may be written in React ([React inside Web Components](bundles/react-web-components.md)).

Every window gets one copy of the shared client packages: React and ReactDOM, Lexical, Base UI, `zod`, `desktop/ui` with the shadcn/ui components it ships and the theme, and `bundle/contracts`. A bundle's client part imports them and leaves them out of its build ([`packages.config.mjs`](../../app/desktop/doric-platform/packages.config.mjs), [`parts.ts`](../../packages/bundle/src/build/parts.ts), [Platform packages](bundles/platform-packages.md#the-shared-packages)).

## Data

Durable storage is two contracts: `storage.backend/v1`, the backend, which `postgres` provides over PostgreSQL, and `storage/v1`, the core's facade, which lets each bundle reach only its own data and validates every value it writes ([`storage/facade.ts`](../../bundles/foundation/core/src/host/storage/facade.ts), [Storage](bundles/storage.md#the-two-contracts)). A Thread's history is the `runtime` bundle's, in the same backend ([Storage](bundles/storage.md#a-threads-history)). Secrets are kept by `secrets.backend/v1`, which `postgres` also provides, behind the core's `secrets/v1` ([`postgres/manifest.json`](../../bundles/foundation/postgres/manifest.json), [The core bundle](bundles/core.md#host)).

## Logs and diagnostics

A bundle writes logs through `log/v1`, whose provider writes each record to the platform contract `doric.log/v1` ([`core/src/shared/log.ts`](../../bundles/foundation/core/src/shared/log.ts)). A record written by a bundle part on the host or in a desktop generation process carries the identity of the calling bundle from `call.caller` (bundle, version, generation), the environment, the call's scope and its trace id; the host kernel and the desktop's main process write it with that identity ([`core/src/shared/log.ts`](../../bundles/foundation/core/src/shared/log.ts), [`platform.ts`](../../packages/bundle/src/contracts/platform.ts), [`platform-providers.ts`](../../packages/bundle/src/runtime/platform-providers.ts), [`boot.ts`](../../app/backend/doric-host/src/lib/bundles/boot.ts), [`broker.ts`](../../app/desktop/doric/src/platform/generation/broker.ts)). A window's record does not: the main process keeps only its level (`info`, `warn` or `error`), message and fields, adds the window's key as `windowKey`, which a field of that name replaces, and does not write a `debug` record ([`dispatcher.ts`](../../app/desktop/doric/src/platform/bridge/dispatcher.ts)). Where each process's records go is in [Contexts](bundles/contexts.md#shapes-of-the-platform-contracts) and [Observability](bundles/observability.md#where-records-go).

The platform also keeps a log of its own, independent of any bundle, and `doric.diagnostics/v1`, which holds the bundle states, quarantine reasons and recent errors of a generation and works without the core. The platform measures no metrics; the one timing it keeps is the duration of each bundle's activation ([Observability](bundles/observability.md)).
