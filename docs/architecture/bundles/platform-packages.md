# Platform packages and theme tokens

- Status: living document. It describes the client packages the app provides and the theme tokens as implemented on 2026-11-20.

## Summary

The desktop app gives every window one copy of a fixed set of client packages: React and ReactDOM, Lexical, Base UI, `zod`, the shared UI of `packages/desktop` (`desktop/ui` and its subpaths) and the browser-safe contracts of `packages/bundle` (`bundle/contracts`). `app/desktop/doric-platform` builds them as browser ESM into folders under `assets/platform/` and writes `importmap.platform.json`, the map from each import specifier to its file ([`build.mjs`](../../../app/desktop/doric-platform/build.mjs), [`packages.config.mjs`](../../../app/desktop/doric-platform/packages.config.mjs)). The main process injects that map, plus one `<id>/contracts` entry for each bundle of the window's generation that has a contracts module, into the shell document before any module loads ([`import-map.ts`](../../../app/desktop/doric/src/platform/protocol/import-map.ts), [`shell.ts`](../../../app/desktop/doric/src/platform/protocol/shell.ts)). A bundle's client part leaves the same specifiers external, so the window keeps one instance of each ([`externals.ts`](../../../packages/bundle/src/build/externals.ts)).

CSS follows the same rule. The theme, `desktop/ui/theme.css`, carries the preflight, the fonts, the tokens and the utilities of most shared components (the rest come from the bundle sheets, [below](#styles-and-the-tailwind-rule)) once per window; a bundle's stylesheet references the theme's Tailwind entry and emits utilities and its own rules, never a theme token ([`theme.css`](../../../packages/desktop/src/styles/theme.css), [`parts.ts`](../../../packages/bundle/src/build/parts.ts)). The theme tokens are stated once, in [`tokens.ts`](../../../packages/desktop/src/tokens/tokens.ts); a build step writes them as CSS variables for the windows and as `tokens.json` for the main process, and the platform contract `doric.tokens/v1` answers them to any bundle.

`packages/desktop` also exports `desktop/reads` (generic read helpers and the error value), `desktop/protocol` (the window–main protocol) and `desktop/client` (the window's loader runtime). Bundles use `desktop/ui` and `desktop/reads`; they never import `desktop/client`.

The table is what [`packages.config.mjs`](../../../app/desktop/doric-platform/packages.config.mjs) lists, with the Lexical packages expanded as [below](#how-the-platform-files-are-built), and what the build's test asserts ([`import-map.test.mjs`](../../../app/desktop/doric-platform/tests/import-map.test.mjs)). A third-party folder is named by the npm version installed in the workspace; a platform-owned folder (`desktop@…`, `bundle@…`) by `PLATFORM_ASSETS_VERSION`, `1.0.0`, which does not follow `PLATFORM_VERSION` ([`version.ts`](../../../packages/bundle/src/runtime/version.ts)).

Base UI is shared like React because its contexts and stores must be one instance per window: a bundle's component inside a `desktop/ui` component reads the same context. Every other dependency of the shared components (`lucide-react`, `cmdk`, `cn`, `sonner`, `@dnd-kit/*`, `react-resizable-panels`, `monaco-editor`, `class-variance-authority`) is bundled into the `desktop/ui` files and reached only through them ([`package.json`](../../../packages/desktop/package.json)). The data layer (`@tanstack/react-query`) and `xterm` are each bundle's own dependencies (for example [`chat/package.json`](../../../bundles/desktop/chat/package.json), [`terminal/package.json`](../../../bundles/features/terminal/package.json)).

A bundle may use none of these packages, for example by writing its custom elements without React: the theme stylesheet is always loaded, and each module only when something imports it.

## How the platform files are built

The Nx target `doric-platform:build` runs `node app/desktop/doric-platform/build.mjs --out dist/app/desktop/doric/assets` after `desktop:build` and `bundle:build` ([`project.json`](../../../app/desktop/doric-platform/project.json)). The mode is `--mode production|development`, else `development` when `NODE_ENV` is `development` and `production` otherwise; any other value throws. Production minifies; both modes define `process.env.NODE_ENV` and resolve the mode's export condition ([`build.mjs`](../../../app/desktop/doric-platform/build.mjs)).

The build makes one esbuild pass per group, each into its own folder ([`build.mjs`](../../../app/desktop/doric-platform/build.mjs)):

- **React and ReactDOM** ship CommonJS. Each listed specifier becomes one ESM file that re-exports the module's export names, read by evaluating the module in the build's mode. A `require('react')` inside ReactDOM becomes a static import of `react`, so ReactDOM never carries its own React.
- **Lexical**: the packages the renderer lists, and every `lexical` or `@lexical/*` package they depend on, transitively, each with every subpath it exports.
- **ESM packages** (`zod`, `@base-ui/react`): every subpath the package exports, wildcards expanded.
- **`bundle/contracts`**: `packages/bundle/src/contracts/index.ts`, built for a neutral platform as `bundle@<assets version>/contracts.js`, in one split build with `bundle/contracts/gen/<path>_pb.js` (each generated file of `packages/bundle`) so each generated module loads once; the build fails when those generated files are missing.
- **`@bufbuild/protobuf`**: every exported subpath, served under `@bufbuild/protobuf@<npm version>/`.
- **`desktop/ui`**: every `./ui` and `./ui/<name>` entry of the export map of [`packages/desktop/package.json`](../../../packages/desktop/package.json) that names a source, CSS and JSON excluded. The wildcard `./ui/*` expands to one entry per `src/components/*.tsx`. The folder also gets the prefix entry `desktop/ui/` → `desktop@<assets version>/`.

Every specifier of the map stays an external import wherever it is imported, inside its own group too, so each module exists once. A group's subpath whose code imports a package the workspace does not install cannot load in a window: the build drops that subpath, rebuilds the group without it, stops treating it as external in the groups after it, and prints which subpaths it left out and which packages they import. In this workspace that is Base UI's `internals/temporal-adapter-luxon`, because `luxon` is not installed. Any other import of a missing package fails the build, as do two entries of a group emitting the same file and an entry whose file was not emitted.

Each folder carries its package's `LICENSE` and, under `licenses/`, the license of every package bundled into its files, named `<name>@<version>.txt`, with the `/` of a scoped name written `__`; a package that ships no license file is recorded by the `license` field of its manifest. The `desktop/ui` folder also gets:

- the module worker `workers/editor.worker.js` (Monaco's editor worker, bundled with nothing external), which `desktop/ui/code` starts by URL ([`editor.worker.ts`](../../../packages/desktop/src/code/editor.worker.ts));
- `theme.css`: Tailwind compiled from [`theme.css`](../../../packages/desktop/src/styles/theme.css), with the CSS the `desktop/ui` modules import (Monaco's stylesheets) appended once, in import order, and the fonts and Monaco's codicon face written beside it;
- `fonts/`, the vendored faces, and `tokens.json`, copied from `packages/desktop/dist/tokens.json`.

Last, the build writes `importmap.platform.json` (`{ "imports": { … } }`, sorted by specifier) from the files actually emitted, and copies `packages/bundle/dist/schemas` to `assets/schemas/`. It cleans only the folders it owns, so the `splash@…` folder other steps write there stays.

## The import map of a window

A generation is one resolved set of enabled bundles that the desktop starts together; each window loads the client parts of one generation, and the bundles a generation retains are the ones it serves ([Composition and distribution](composition-and-distribution.md)). The main process reads `importmap.platform.json` once, at start; a file without an `imports` object throws ([`import-map.ts`](../../../app/desktop/doric/src/platform/protocol/import-map.ts), [`app.ts`](../../../app/desktop/doric/src/platform/app.ts)). For a window of a generation, it adds `"<id>/contracts"` → `doric://app/bundles/<id>@<version>/<entry>` for each retained bundle of that generation that ships a contracts module, and `"<id>/contracts/gen/"` → `doric://app/bundles/<id>@<version>/contracts/gen/` for each one with generated code, a contracts module or not (such as `transport`); before the first generation the map is the platform map alone. The map of each generation is computed once and cached ([`shell.ts`](../../../app/desktop/doric/src/platform/protocol/shell.ts)).

The shell document is rendered per request: the renderer's `shell.html` with three elements inserted as the first children of `<head>`, in order — `<meta name="doric-generation">` (when there is a generation), `<script type="importmap">` and `<link rel="stylesheet">` to `/platform/desktop@<assets version>/theme.css` ([`shell.ts`](../../../app/desktop/doric/src/platform/protocol/shell.ts), [`app.ts`](../../../app/desktop/doric/src/platform/app.ts)). In the map's JSON every `<` is escaped as `\u003c`, and the policy of the response allows that one inline script by its SHA-256 hash. A template without `<head>` throws.

```html
<script type="importmap">
  {
    "imports": {
      "react": "doric://app/platform/react@19.2.8/index.js",
      "lexical": "doric://app/platform/lexical@0.51.0/index.js",
      "@base-ui/react/popover": "doric://app/platform/@base-ui/react@1.8.0/popover.js",
      "desktop/ui/": "doric://app/platform/desktop@1.0.0/",
      "desktop/ui/sidebar": "doric://app/platform/desktop@1.0.0/sidebar.js",
      "bundle/contracts": "doric://app/platform/bundle@1.0.0/contracts.js",
      "git/contracts": "doric://app/bundles/git@1.3.0/contracts/index.js"
    }
  }
</script>
```

An import map cannot change once loaded, so a window keeps its generation's packages until it reloads ([Composition and distribution](composition-and-distribution.md)). The `doric://app/platform/…` addresses are served by the app's one origin ([The `doric://` protocol](doric-protocol.md)).

Two other maps derive from the same file:

- **The desktopMain process** of a generation, the Node process that runs the `desktop` parts of its bundles, resolves only `file:` URLs: each `doric://app/platform/…` target becomes the matching file under the platform folder (every other target is dropped), `bundle/contracts` points at the generation's own contracts module, one instance shared with its runner, and each `<id>/contracts` points at the cached `file:` copy of that bundle's contracts module ([`import-map.ts`](../../../app/desktop/doric/src/platform/protocol/import-map.ts), [`app.ts`](../../../app/desktop/doric/src/platform/app.ts)).
- **The preview frame**, the sandboxed `<iframe>` document in which a bundle's frame module draws a preview, carries only React, ReactDOM and every Base UI specifier of the platform map: no `desktop/ui`, no contracts, no `zod` ([`frame.ts`](../../../app/desktop/doric/src/platform/protocol/frame.ts)).

## How a bundle uses them

A client part's build leaves `react`, `react-dom`, `@base-ui/react`, `lexical`, `@lexical/*`, `desktop/ui`, `zod`, `@bufbuild/protobuf` (each with its subpaths), `bundle/contracts`, every `*/contracts` and every `<package>/contracts/gen/<path>` external; a frame (`src/client/frames/<name>.ts`) leaves only React, ReactDOM and Base UI external; its build refuses `bundle/*`, `desktop/*`, Lexical, `@bufbuild/protobuf` and every `*/contracts`, and bundles `zod`, other npm packages and the sources of its own `src/contracts` ([`externals.ts`](../../../packages/bundle/src/build/externals.ts), [`parts.ts`](../../../packages/bundle/src/build/parts.ts)). Anything else a client part imports, `desktop/reads` included, is bundled into the part. The build refuses `bundle`, `bundle/runtime`, `desktop` and `desktop/client` in a client part; the full list of refused imports per part is in [Boundaries](boundaries.md#what-a-client-part-may-import-and-slot-names).

Because the platform takes a major whenever one of these packages takes a major, a bundle's `engines.doric` range is enough to state its compatibility with them; a client part whose range the platform does not satisfy is quarantined before it is imported ([Versioning](versioning.md), [Core and quarantine](core.md)). Adding a `desktop/ui` subpath or a prop to a shared component is an addition to the platform and raises `PLATFORM_VERSION` by a minor; the folders and URLs keep `PLATFORM_ASSETS_VERSION` ([`version.ts`](../../../packages/bundle/src/runtime/version.ts)).

### Generic primitives only

A read or a piece of UI that names a bundle's concept (files, Git, changes) belongs to that bundle, not to `packages/desktop`: the reads of files and of Git are in [`files/src/client/reads`](../../../bundles/features/files/src/client/reads) and [`git/src/client/reads`](../../../bundles/features/git/src/client/reads). `desktop/reads` and `desktop/ui` hold only generic primitives: refresh queues, path utilities, tree and panel components, tokens, the viewport helpers and the error notice. A bundle passes its own rows, labels and colours to them ([`panels/index.ts`](../../../packages/desktop/src/panels/index.ts)), and its own error codes in its own catalog ([below](#the-error-notice)). A production import of a bundle's package from a platform package fails the `core` boundary check ([Boundaries](boundaries.md)).

### The shadcn components

The components are shadcn/ui files in the `base-nova` style, built on Base UI primitives (`@base-ui/react`), with Tailwind CSS and `lucide` icons ([`components.json`](../../../packages/desktop/components.json)). Each file has one of two recorded origins in [`provenance.json`](../../../packages/desktop/tests/fixtures/provenance.json): `registry`, the shadcn CLI's output, or `renderer`, a copy read from Git at a recorded commit; [`PROVENANCE.md`](../../../packages/desktop/PROVENANCE.md) lists each file's origin and local patches, and `desktop:test` runs [`verify-provenance.mjs`](../../../packages/desktop/scripts/verify-provenance.mjs), which undoes the patches, compares each file with the SHA-256 recorded for its origin, and fails on any other difference or on a component file the record does not list.

The overlays — `AlertDialog`, `Combobox`, `ContextMenu`, `Dialog`, `DropdownMenu`, `Popover`, `Select`, `Sheet`, `Tooltip` and the components built on them — portal their content into the container the nearest `PortalContainerProvider` names, or into `document.body` outside one; a `container` passed directly to an overlay's `*Portal` wins ([`portal-container.tsx`](../../../packages/desktop/src/portal-container.tsx), for example [`dialog.tsx`](../../../packages/desktop/src/components/dialog.tsx)). An element that must keep its overlays inside itself, such as a React root in a shadow root, names itself as the container.

`desktop/ui/sidebar` also exports `SidebarScope`, the sidebar context alone, with no wrapper element and no keyboard shortcut. An element that draws sidebar rows from its own React root cannot see the sidebar's provider; inside `SidebarScope` it reads the outer context when there is one, and otherwise an expanded, non-mobile state whose setters do nothing ([`sidebar.tsx`](../../../packages/desktop/src/components/sidebar.tsx)).

### Custom elements drawn with React

`defineReactElement({ render, props, wrap?, display? })` returns a custom element class whose content is a React component, rendered in the element's light DOM with the services of the bundle that owns the element. Setting `services` or a listed property re-renders. The element's `display` is `contents` unless given. All elements of one class render through portals of one React root that the class creates on first connection, each inside its own error boundary, so content that throws empties only its own element. The content unmounts when the element stays disconnected after one microtask, and `dispose()` unmounts it at once (`flushSync`). `portalHosts(properties)` makes host elements with no root of their own, whose content another React root renders through `useHosts()` ([`react-element.ts`](../../../packages/desktop/src/react-element.ts)). How bundles build their custom elements on these classes is in [React inside Web Components](react-web-components.md).

### The error notice

`ErrorNotice` shows one `ErrorInfo` the same way on every surface, in a `block`, `compact` or `inline` variant, with the title of the catalog entry, Retry when the entry allows it and the caller passes `onRetry`, Copy details, and collapsible details. Each bundle passes its own `catalog`, merged over the shared entries the module holds (generic codes such as `unknown`, `not_found`, `network_error`, `credential_missing`). `toastError({ id, error, catalog?, fallbackCode?, context? })` shows a compact notice as a toast that a later call with the same `id` replaces; it needs the window's `Toaster` (`desktop/ui/sonner`) mounted ([`error-notice.tsx`](../../../packages/desktop/src/error-notice.tsx), [`error-copy.ts`](../../../packages/desktop/src/error-copy.ts)).

The shared entries are the codes that `packages/bundle`, `packages/llms`, `packages/agent` and `packages/tool` define, in words that name no bundle; `error-copy.ts` is not in the export map, so they exist once per window, inside `desktop/ui/error-notice`. A bundle's own codes stay in its own catalog, for example `chatErrorCatalog` ([`chat/src/client/domain/error-catalog.ts`](../../../bundles/desktop/chat/src/client/domain/error-catalog.ts)) or `filesToolCatalog` ([`files/src/client/chat/edit-call.tsx`](../../../bundles/features/files/src/client/chat/edit-call.tsx)); for a code both list, the bundle's entry wins ([`error-copy.ts`](../../../packages/desktop/src/error-copy.ts)). The client parts of `chat` ([`failure-turn-node.tsx`](../../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/failure-turn-node.tsx)), `layout` ([`bundle-health-notice.tsx`](../../../bundles/desktop/layout/src/client/components/molecules/bundle-health-notice.tsx)), `workspace` ([`workspace-error-notice.tsx`](../../../bundles/desktop/workspace/src/client/components/molecules/workspace-error-notice.tsx)), `settings` ([`settings-credentials.tsx`](../../../bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx)), `claude-login` ([`use-claude-login.ts`](../../../bundles/features/claude-login/src/client/use-claude-login.ts)), `default` ([`skill-call.tsx`](../../../bundles/runtime/default/src/client/skill-call.tsx)), `files` ([`edit-call.tsx`](../../../bundles/features/files/src/client/chat/edit-call.tsx)), `terminal` ([`terminal-call.tsx`](../../../bundles/features/terminal/src/client/chat/terminal-call.tsx)) and `threads` ([`spawn-call.tsx`](../../../bundles/features/threads/src/client/spawn-call.tsx)) import `desktop/ui/error-notice`.

## Styles and the Tailwind rule

Tailwind generates CSS from the classes it finds in source files, and each bundle is built apart. The rule is:

- `desktop/ui/theme.css` emits once, in the layers `theme, base, components, utilities`: Tailwind's preflight, the font faces, the tokens and the utilities of the files its `@source` lines name: `src/components/`, `chrome-bar.tsx`, `element-host.tsx`, `error-notice.tsx`, `model-icon.tsx`, `choice-list.tsx` and `collapsible-block.tsx`. The classes of `desktop/ui/panels`, `desktop/ui/code`, `desktop/ui/comment-pin` and `desktop/ui/reader-avatar` come from the bundle sheets that scan `packages/desktop/src`. Its base layer gives borders and outlines the theme's colours, sets running text to weight 300 and headings to `--font-weight-normal`, and the `.chrome-bar` class takes `--doric-titlebar-height` ([`theme.css`](../../../packages/desktop/src/styles/theme.css)).
- `desktop/ui/tailwind.css` is the reference entry: Tailwind's theme, `tw-animate-css`, shadcn's Tailwind CSS, the `dark` variant (`&:is(.dark *)`), the colour, font and shadow tokens as Tailwind theme variables, and the radius scale. A stylesheet that `@reference`s it gets those names and emits none of them ([`tailwind.css`](../../../packages/desktop/src/styles/tailwind.css)).
- The radius scale (`--radius-sm`, `--radius-md`, `--radius-lg`, `--radius-xl`, from `--radius`) is in `@theme static`, so it is always emitted: the components read it through `var()` in arbitrary values such as `rounded-[min(var(--radius-md),12px)]`, which Tailwind does not count as a use of the variable.
- A bundle's `src/client/styles.css` references `desktop/ui/tailwind.css` and imports `tailwindcss/utilities.css` into the `utilities` layer. Its build fails when the sheet contains `@theme`, so a bundle adds no token to the platform theme; it may declare its own custom properties, as `git` declares its `--git-*` colours ([`parts.ts`](../../../packages/bundle/src/build/parts.ts), [`git/src/client/styles.css`](../../../bundles/features/git/src/client/styles.css)). All sheets share one `utilities` layer, so between two sheets the later one wins: a sheet that re-emits a plain utility (`inline-flex`) after another sheet's variant (`md:hidden`) overrides it. To keep one order, 10 of the 13 bundle sheets also `@source` `packages/desktop/src`, and seven of them (`files`, `git`, `openui`, `resources`, `terminal`, `threads`, `usage`) also `@source` the client folders of `layout`, `chat`, `settings`, `account` and `workspace` ([`files/src/client/styles.css`](../../../bundles/features/files/src/client/styles.css)); `mcp` and `screen` name their classes with `@source inline(…)`. A sheet may state `@layer theme, base, components, utilities;` itself, as `chat` does, for a document that loads it before the theme, and may carry its own `base` or unlayered rules. The build appends the CSS the part's modules import to the compiled sheet ([`parts.ts`](../../../packages/bundle/src/build/parts.ts)).
- The window links each scheduled client part's stylesheet in `<head>`, in activation order, after the theme ([`styles.ts`](../../../packages/desktop/src/client/styles.ts)).

```css
/* bundles/<group>/<name>/src/client/styles.css */
@import 'tailwindcss/utilities.css' layer(utilities);
@reference 'desktop/ui/tailwind.css';
@source './';
@source '../../../../../packages/desktop/src';
```

## Fonts

The faces are vendored, because the packaged app's content security policy allows fonts from `'self'` only, and each is a variable font with one `woff2` file per subset that carries every weight ([`fonts.css`](../../../packages/desktop/src/styles/fonts.css), [`assets/fonts`](../../../packages/desktop/assets/fonts)):

- **Noto Sans** (weights 100–900, normal and italic) is the face of the app's surfaces, `--font-sans` and `--font-serif`, with `-apple-system`, `BlinkMacSystemFont` and `sans-serif` as fallback. It ships its Latin and Latin Extended subsets only. Its license is `NotoSans-OFL.txt`.
- **IBM Plex Mono** (weights 100–700, normal and italic) is the face of the conversation, `--font-conversation`, and of code, `--font-mono`, with `monospace` as fallback. It ships its Latin1, Latin2, Latin3 and Pi subsets. Its license is `IBMPlexMono-OFL.txt`.

The platform build rewrites the faces' URLs to the `fonts/` folder beside `theme.css` and copies the files there ([`build.mjs`](../../../app/desktop/doric-platform/build.mjs)).

## Theme tokens

The tokens are stated once, in [`tokens.ts`](../../../packages/desktop/src/tokens/tokens.ts), as a `Tokens` value:

| Field            | Contents                                                                                                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`        | `1.0.0`, the assets version the tokens ship with                                                                                                                                                                                                                    |
| `defaultVariant` | `light`, the CSS fallback before the system preference is evaluated                                                                                                                                                                                                 |
| `variants`       | `light` and `dark`, each a `TokenSet` (CSS variable → value): the shadcn colours (`--background`, `--foreground`, `--primary`, `--muted`, `--border`, `--ring`, `--sidebar-*`, `--chart-*` and others), `--warning`, the `--paper-*` palette and the shadows        |
| `shared`         | Tokens both variants state alike: `--font-sans`, `--font-serif`, `--font-mono`, `--font-conversation`, `--font-weight-normal`, `--font-weight-medium`, `--radius`, `--paper-radius-*`, `--paper-text-*`, `--tracking-normal`, `--spacing` and the shadow parameters |
| `window`         | `titlebarHeight` (40), `trafficLight` (`size`, `insetX`, `reservedWidth`) and the native window `backgrounds` (`window.light`, `window.dark`)                                                                                                                       |

`desktop:build` compiles the module and runs [`build-tokens.mjs`](../../../packages/desktop/scripts/build-tokens.mjs), which writes two outputs; neither is edited by hand ([`project.json`](../../../packages/desktop/project.json)):

- `src/styles/tokens.css`, from `tokensCss`: `:root` with the light variant and the shared tokens, the dark variant under `@media (prefers-color-scheme: dark)` and under `.dark`, and a second `:root` with the window variables `--doric-titlebar-height` (from `titlebarHeight`), `--doric-window-background` (`var(--background)`), `--doric-safe-top`, `--doric-safe-left` and `--doric-safe-right` (`0px`) ([`css.ts`](../../../packages/desktop/src/tokens/css.ts)).
- `dist/tokens.json`, the `Tokens` value as JSON, which the platform build copies to `desktop@<assets version>/tokens.json`. The main process reads it at start, for the chrome bar's measures, the window buttons and the native window background, which it needs without reading CSS; an unknown window colour name throws ([`tokens.ts`](../../../app/desktop/doric/src/platform/tokens.ts)). How the main process and the window use these values is in [Window appearance](window-appearance.md).

### `doric.tokens/v1`

The platform contract `doric.tokens/v1` answers the resolved token values to any bundle. Its ref is `DoricTokensV1` from `bundle/contracts`; like every `doric.*` contract, a bundle does not list it in its manifest and reaches it with `services.use(DoricTokensV1)` ([`platform.ts`](../../../packages/bundle/src/contracts/platform.ts)).

| Property     | Value                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Environments | `client` and `desktopMain`                                                                                                                 |
| Provider     | The platform, under principal `doric` (the identity a provider registers under), version `PLATFORM_VERSION`, cardinality `one`             |
| Method       | `get(call?)`: no input; resolves to `Readonly<Record<string, string>>`, CSS variable name → value                                          |
| Value        | The shared tokens, the default (light) variant and the window variables, as `resolvedVariables(tokens)` states them; a fresh copy per call |

The main process builds the value from `tokens.json` ([`tokens.ts`](../../../app/desktop/doric/src/platform/tokens.ts)). In a desktopMain process the generation's broker provides it ([`broker.ts`](../../../app/desktop/doric/src/platform/generation/broker.ts)); in a window the main process sends it in the window description, and the window's platform providers answer it unchanged ([`protocol.ts`](../../../packages/desktop/src/client/protocol.ts), [`platform.ts`](../../../packages/desktop/src/client/platform.ts)). The value does not follow the dark variant or the system preference.
