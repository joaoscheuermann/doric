# Migration in verifiable deliveries

**Status:** proposal. Part of the [bundle architecture](../bundles.md); nothing here describes behavior already implemented, and the documentation remains the contract of the current implementation.

## Summary

The migration of the current Doric to the bundle architecture happens in eleven steps. Each step describes a change and the parity evidence required before the old path is removed. The steps are review cuts, not an obligation to create all the interfaces at once. The proof of each step observes public contracts and usage scenarios, without pinning private details of the implementation.

## Overview

| Step                     | Focus of the change                                                                                                                                                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Contract              | Manifest v1, the `define*` contracts API and the references of the basic contracts in `bundle/contracts`, loader with foundation, context with services only, `hooks/v1`, `log/v1`, `tools/v1` and `skills/v1` of the core in the host, the app's hooks and quarantine. |
| 2. Storage               | `postgres` in the foundation with the current Prisma behind `storage.backend/v1` and `secrets.backend/v1`; `settings/v1`, `secrets/v1`, `storage/v1` and `events/v1` of the core.                                                                                       |
| 3. Generic protocol      | Generic storage primitives in PostgreSQL and conformance kit.                                                                                                                                                                                                           |
| 4. Generation processes  | Kernel, child process per generation and RPC envelope.                                                                                                                                                                                                                  |
| 5. Domain runtime        | Project, Thread, queue, delegation, lease and resumption in the `runtime` bundle.                                                                                                                                                                                       |
| 6. Executor              | `direct` extracted with opaque and versioned history/checkpoint state; `models/v1` of the core aggregating `models.provider/v1`.                                                                                                                                        |
| 7. Data migration        | Current data converted to objects and streams defined by the bundles.                                                                                                                                                                                                   |
| 8. Desktop platform      | `doric://app`, splash with verified download, import map, windows, menus, keybindings, cache, core services in `desktopMain`, client runtime in `desktop/client` and a single IPC.                                                                                      |
| 9. UI in bundles         | Path router, `<core-outlet>` and regions in the core client; `layout`, `settings` and `chat` extracted.                                                                                                                                                                 |
| 10. Features and sandbox | Providers, features and sandboxes extracted with host/client contributions.                                                                                                                                                                                             |
| 11. Full extension       | External bundles and complete extension, conditioned on the deferred decision about trust.                                                                                                                                                                              |

## Steps

### 1. Contract

**Change:** manifest v1 in JSON Schema with reading of v0, semver check, loader, local typed services, registrations and disposal; the contracts API in the browser-safe subpath `bundle/contracts` of `packages/bundle`, with `defineHook`/`defineHooks`, `defineService`/`defineMethod`, `defineEvent`, `defineCommand`, `defineSettings` and `defineStorageType` written in zod, the function `ref` for typed references, the generation of the canonical JSON Schema in the build and the public entrypoint `<bundle>/contracts` of each bundle (`core/contracts`, `files/contracts`, `git/contracts`). The options of `defineService` only declare the cardinality of the contract when it is `many` (several providers without conflict, aggregated by the consumer); without an option, the contract is `one` (one active provider, chosen by the composition).

`bundle/contracts` exports the `define*` functions; the types `HostContext`, `DesktopContext`, `ClientContext`, `Services` and `Call`; the constants of the platform's contracts (`AppHooksV1` as `doric.app.hooks/v1`, `WindowHooksV1` as `doric.window.hooks/v1`, `DoricWindowsV1`, `DoricMenusV1`, `DoricCatalogV1`, `DoricDiagnosticsV1`, `DoricBundleV1`, `DoricCacheV1`, `DoricTokensV1`); and the typed references (`ref`) of the basic contracts (`HooksV1`, `LogV1`, `SettingsV1`, `SecretsV1`, `SecretsBackendV1`, `ToolsV1`, `SkillsV1`, `StorageV1`, `StorageBackendV1`, `EventsV1`, `ModelsV1`, `ModelsProviderV1`, `CommandsV1`, `UiV1`, `NavigationV1`, `RegionsV1`, `WindowsV1`, `MenusV1`), with the types of those contracts. The references and the types stay in the platform because any bundle can provide those contracts; the core provides the definitions with `execute`, written with `defineService(WindowsV1, { ... })`, which makes the compiler check the methods. `core/contracts` exports only what belongs to the core (`CoreHooksV1` and `OpenSettingsCommandV1`, the reference of the command `core.open-settings/v1`), contracts of other bundles come from `<bundle>/contracts`, and each bundle imports its own contracts by relative path (`../contracts/index.js`). No code imports the `bundle` entrypoint, which is the Node loader.

The context now delivers only services: `host` parts receive `HostContext`, `desktopMain` parts receive `DesktopContext` and `client` parts receive `ClientContext`, all three in the shape `{ readonly services: Services }`, with `provide(definição)`, `use(contract, scope?)` and `whenAvailable(contract, callback)`. The loader tracks everything a bundle registers through services and disposes of it in reverse order on deactivation; `activate` can return a cleanup function, which replaces `onDispose` and `signal` of the old context. Every `execute` of a service method, of a command and of a tool receives `(input, call, services)`, with the services of the bundle that provided or registered it, and every hook handler receives `call` (`caller`, `scope`, `signal`, `trace`). Every stub accepts as an optional last argument a parent `call` (the `call` received) or `{ signal, deadline }`; the dispatcher inherits `scope`, `signal` and `trace` from the parent, but never `caller`. `call.caller` (`{ bundleId: string; version: string; generation: number }`) is always the bundle that makes the call of that hop, filled in by the dispatcher: when git passes the `call` received in the `execute` of `switchBranch` on to `events/v1`, the `caller` of that new hop is `git`. See [contexts](./contexts.md) and [services](./services-and-channels.md).

The `core` bundle now provides in the host the basic services `hooks/v1`, `log/v1`, `tools/v1` and `skills/v1`, with validation by the schemas of the contracts. `settings/v1`, `secrets/v1`, `storage/v1` and `events/v1` of the core only come in at step 2. The manifests declare in `requires` every contract that their own code uses with `use`, including the basic ones of the core; `doric.*` contracts belong to the platform, always exist and never go in `requires`, and optional contracts use `whenAvailable` without going in `requires`.

In each environment the loader first activates the foundation: the bundles chosen in `providers` for contracts that the core provides or consumes, such as a `myhooks` chosen for `hooks/v1`. Foundation bundles only declare `doric.*` contracts in `requires`. Then it activates the core and, last, the other bundles, in dependency order. When the composition chooses another provider for a contract that the core also provides, the loader does not register the core's definition for that contract in that environment, and the core's own `services.use` returns the chosen provider. The choice in `providers` holds in each environment in which the chosen bundle provides the contract; in the others, the default provider remains. Without a choice in `providers`, a second provider of a `one` contract goes to quarantine with a reason; since the foundation and the core activate first, the one that goes to quarantine is the substitute bundle that the composition did not choose.

After the host's `hooks/v1` provider activates (the core, by default, or the one chosen in `providers`), the platform calls `define(AppHooksV1)` and from then on fires `execute` of the app's hooks through the contract. Any bundle, not only the core, registers handlers of those hooks. The platform reads tools and skills only through the contracts. Catalog, quarantine, diagnosis and the platform's own log remain in the platform, independent of the core, because they need to work without it; a minimal test core proves that loading does not depend on the default core.

`bundles/foundation/core` is renamed to `files`, preserving the public names of the tools and skills; `files`, `git` and `threads` are loaded through the new contract and register tools with `services.use(ToolsV1).register(tool, options)`. As a proposed change of the `tool` package, the `execute` of `defineTool` stops receiving `(sandbox, host, payload, config)` and receives `(payload, call, services)` instead, with the bundle's services bound in the `register` of `tools/v1`. The `threads`, `workspace` and `terminals` controls of the current `Host` of `packages/host` become the contracts `runtime.threads/v1`, `runtime.workspace/v1` and `terminal/v1`, obtained with `services.use(contrato, call.scope)`. Since `runtime` is only extracted in step 5 and `terminal` in step 10, in this step those three contracts are provided in the host by a provisional adapter over the current `Host`, mounted in `agents/doric`; the adapter delivers `runtime.threads/v1` and `runtime.workspace/v1` until step 5 and `terminal/v1` until step 10, and leaves when the extracted bundle takes over the contract. Structured log, tracing and the catalog's diagnosis come in with it: `bundleId`, `version` and `generation` of each record come from `call.caller`, and `environment` comes from the process of the `log/v1` provider.

The semver check of this step, suspended until publication (step 11), would compare the JSON Schemas generated from zod; no bundle writes JSON Schema by hand. The details are in [contracts](./contracts.md), [manifest](./manifest.md), [core bundle and quarantine](./core.md), [versioning](./versioning.md) and [hooks](./hooks.md).

**Parity evidence:** catalog, order, collisions, dependencies, quarantine, tools and skills keep their public behavior; the diagnosis shows each bundle active or in quarantine with a reason; a bundle that provides `hooks/v1`, chosen in `providers`, activates in the foundation before the core, receives the definition of the app's hooks in place of the core, and the core's `services.use(HooksV1)` returns that provider; a second provider of `hooks/v1` that was not chosen goes to quarantine with a reason, and the core does not; a failure of a bundle's `activate` leads to quarantine, while a failure of an `onActivateHook` handler only appears in the diagnosis; a failure of the core leads to recovery mode; the `call.caller` of each hop is the bundle that called, even when the parent `call` is passed on.

### 2. Storage

**Change:** select `postgres` in the composition as the default provider of `storage.backend/v1` and `secrets.backend/v1` (`"providers": { "storage.backend/v1": "postgres", "secrets.backend/v1": "postgres" }`), which places it in the foundation, activated before the core. `postgres` encapsulates the current Prisma behind those contracts, provided with `services.provide(postgresStorage)` and `services.provide(postgresSecrets)`, definitions written with `defineService(StorageBackendV1, { ... })` and `defineService(SecretsBackendV1, { ... })`, and exposes health/write admission. The default `secrets.backend/v1` stores each secret as an AES-256-GCM envelope under `DORIC_CREDENTIAL_KEY`, like the host's current credential store. Both are `one` contracts.

The core now provides in the host `settings/v1`, `secrets/v1`, `storage/v1` and `events/v1` and declares in `requires` only `storage.backend/v1` and `secrets.backend/v1`, the only contracts it can require, because the foundation provides them. `storage/v1` is the core's facade over `storage.backend/v1`, and the persisted `settings/v1` relies on it; `secrets/v1` is the facade over `secrets.backend/v1` and applies redaction before the log, as today. The switch to these facades over the backends happens without changing the behavior for the callers. `events/v1` receives `events.append(definição, payload, call)`. From here on the platform reads settings, secrets and storage only through the contracts. See [storage](./storage.md).

**Parity evidence:** ProjectStore/ThreadStore, indexes, transactions, rewind, replay, recovery, usage and disk pressure keep parity; credentials written by the current credential store remain readable by `secrets.backend/v1`; no log shows a resolved secret.

### 3. Generic protocol

**Change:** implement versioned documents, declared indexes, streams, declarative commit, commit feed and blobs in the PostgreSQL backend, and the conformance kit in `packages/storage`; verify the contract without migrating the current data yet. The declared indexes come from the `defineStorageType` definitions described in [storage](./storage.md).

**Parity evidence:** concurrency, revision conflicts, paginated queries, sequence with gaps, snapshot+cursor, feed after a crash and commit failure pass the conformance kit.

### 4. Generation processes

**Change:** kernel with transport, storage, catalog, foundation and core; child process per generation for the other bundles of the host; RPC envelope with JSON Schema (generated from the zod of the contracts), cancellation and `traceparent`; `utilityProcess` per generation for `desktopMain`. See [process isolation](./process-isolation.md).

**Parity evidence:** generation switch without restarting the host; executions in progress finish in the old generation; a crash of the process of a generation pauses the Threads and resumes them from the checkpoint; no external API changes.

### 5. Domain runtime

**Change:** extract Project, Thread, queue, delegation, lease and resumption to the `runtime` bundle, chosen provider of `runtime/v1` (`one` contract), preserving external APIs. `runtime` now provides `runtime.threads/v1` (`RuntimeThreadsV1`: prompt sending, reading of Threads and the child-Thread controls of the current `Host`), `runtime.workspace/v1`, `runtime.lease/v1` and `runtime.hooks/v1`, and writes Threads with the storage type `runtime.thread/v1` and the stream `runtime.thread.events/<threadId>`. `runtime` takes over `runtime.threads/v1` and `runtime.workspace/v1` in place of the provisional adapter of step 1, which stops providing them; `terminal/v1` stays in the adapter until step 10.

**Parity evidence:** creation, tree, serial execution per Thread, parallelism between Threads, restart and deletion have the same semantics; the tools of `files`, `git` and `threads` receive from `runtime.threads/v1` and `runtime.workspace/v1` the same result they received from the adapter.

### 6. Executor

**Change:** extract the `direct` bundle, chosen provider of `executor/v1` (`one` contract), with opaque and versioned history/checkpoint state; allow participation in the rewind transaction. The core now provides in the host `models/v1`, which aggregates the providers of `models.provider/v1` (`many` contract, whose reference has been in `bundle/contracts` since step 1); `resolve(ref)` uses the `call.scope`. Until step 10, the current providers of `packages/llms` (OpenAI, OpenRouter and Codex) are registered in `models.provider/v1` by a provisional adapter in the host. `direct` resolves models with `services.use(ModelsV1, call.scope).resolve(ref)` and emits events with `services.use(EventsV1).append(definição, payload, call)`.

**Parity evidence:** prompt, streaming, cancellation, pause and resumption preserve the model's context without duplicating effects; the configurable types, fields and model catalogs seen through `models/v1` are the same ones the current host exposes.

### 7. Data migration

**Change:** convert Project, Thread, events and the state of `direct` to objects and streams defined by the bundles, with offline migration and a verification read before the switch.

**Parity evidence:** IDs, events, sequences/gaps, messages, checkpoints, usage, queue state and references remain readable; no record disappears.

### 8. Desktop platform

**Change:** `doric://app` protocol with generated CSP; catalog and artifacts downloaded from the host in the splash, with the hash checked to guarantee the integrity of the cache; import map with React, Lexical, `desktop/ui` (full shadcn) and tokens; splash and recovery surface; `packages/desktop` becomes the loader's client runtime used by `app/doric-renderer`, without being imported by bundles, and `desktop/ui` keeps components, tokens and Tailwind; per-bundle cache directory in `doric.cache/v1`, a platform contract in `desktopMain`; native window and menu APIs in `doric.windows/v1` and `doric.menus/v1`, used by the core; native appearance by tokens (`doric.tokens/v1`); single IPC dispatcher. In `desktopMain`, the core provides `hooks/v1`, `log/v1`, `settings/v1` (local desktop preferences), `windows/v1`, `menus/v1`, `commands/v1` and `core.hooks/v1`; `windows/v1` (opening and focusing windows by the core's policies) and `menus/v1` (items, keybindings and `setContext`) are reached through the bridge by the `client` parts that declare them in `requires`. `commands/v1` exists in `desktopMain` and in the client, not in the host. After the `hooks/v1` provider of `desktopMain` activates, the platform calls `define(AppHooksV1)` in it and fires the lifecycle hooks through it; `WindowHooksV1` is defined in the client, in step 9. A window is a key plus a path: the core opens the main window with `windows.open({ key: 'workspace', path: '/' })` in `onAppReadyHook`, reopens it in `onAppActivateHook`, builds the menu skeleton (App, Editar, Visualizar, Janela, Ajuda) and the basic keybindings in `onAppReadyHook`, not directly in `activate`, and opens the settings window with `{ key: 'settings', path: path ?? '/settings' }` through the command `core.open-settings/v1`. The main process keeps the last path of each key and reopens the window at it. The protocol handler answers with the shell for any path that is not a file of `/platform/` or `/bundles/`, and the window loads `doric://app/<path>`. See [`doric://` protocol](./doric-protocol.md), [composition and distribution](./composition-and-distribution.md), [shared packages](./platform-packages.md), [splash and recovery](./splash-and-recovery.md), [windows](./windows.md), [menus and keybindings](./menus-and-keybindings.md) and [native appearance](./window-appearance.md).

**Parity evidence:** the packaged app opens only through `doric://app`; reloading a window keeps the path; missing files in `/platform/` and `/bundles/` answer `404`; Electron keeps what it already does today; the splash closes after the first window is ready; an incompatible client part goes to quarantine without blocking the rest; the other bundles, including through their client parts, open windows and contribute menus through `windows/v1` and `menus/v1`.

### 9. UI in bundles

**Change:** the core now provides in the client `hooks/v1`, `log/v1`, `ui/v1`, `navigation/v1`, `regions/v1` and `commands/v1` and defines the elements `<core-outlet>`, `<core-region>`, `<core-not-found>` and `<core-unavailable>` ([UI in the client](./core.md#ui-no-client)). The bootstrap of each window puts a `<core-outlet>` in the `body`, defines `WindowHooksV1` (`onCloseHook`, `onFlushHook`) in the client's `hooks/v1` and executes it when the main process asks to close the window; the dispatcher fills in `scope.windowKey` in every call that leaves a client window. Routes are paths registered with `services.use(NavigationV1).register({ path, create, parent? })`, and the core's router navigates through the History API, changing `location.pathname` ([navigation and routes](./navigation.md)). Extract `layout`, `settings` and `chat`. `layout` registers the route `/` with `<layout-workspace>`, which has a `<core-outlet>` for the child routes and the regions `layout.sidebar`, `layout.header`, `layout.panel` and `layout.footer`, and provides `layout.tabs/v1` ([the layout bundle](./layout.md)). `settings` registers `/settings` with `<settings-page>`, which has the region `settings.sections` and a `<core-outlet>` for the sections, and `/settings/providers` with parent `/settings`. `chat` defines `chat-view`, registers `/projects/:projectId/threads/:threadId` with parent `/` and exposes `chat.views/v1`, where renderers come in with `registerRenderer({ blockType, elementTag })`; whoever wants the conversation outside the route uses `ui.create('chat-view', { projectId, threadId })`, which creates the element with the services of `chat` ([`ui.create` step by step](./core.md#uicreate-passo-a-passo)). The selection of Project and Thread becomes the active route, and the old persisted selection is converted into a path once. UI and menu commands are defined and registered in the client parts (or `desktopMain`). Move `history` to `desktopMain`, writing to `<hostId>/<storageGeneration>/<threadId>` inside the cache directory that `doric.cache/v1` gives it. `ui/v1` refuses a tag that does not start with `<id do bundle chamador>-`. See [UI composed by bundles](./ui-composition.md), [navigation and routes](./navigation.md), [the layout bundle](./layout.md) and [the chat bundle](./chat.md).

**Parity evidence:** the core opens the windows at `/` and `/settings`; the minimal test core opens a window without bundles of the default UI; the window at `/projects/p1/threads/t1` shows `<chat-view>` inside the outlet of `<layout-workspace>`; back, forward and reload keep the route; a path without a route shows `<core-not-found>`; two bundles with the same path lead the second to quarantine; the old selection reappears as a path; subscriptions and the handlers of `onCloseHook` and `onFlushHook` of `WindowHooksV1`, registered with `hooks.use(WindowHooksV1)`, hold only for the client window that called (`call.scope.windowKey`) and run when the main process asks to close it; routes, conversation, cache and replay keep parity.

### 10. Features and sandbox

**Change:** extract the providers `openai`, `openrouter` and `codex`, which register configurable type, fields and model catalog through `models.provider/v1` (`many` contract, aggregated by the core's `models/v1` since step 6), which replace the provisional adapter of `models.provider/v1`, `files`, `web`, `git`, `threads`, `terminal`, `usage`, `resources` and the sandboxes `docker` and `firecracker`, providers of `sandbox/v1` (`one` contract), with host/client contributions. `terminal` now provides `terminal/v1` in place of the provisional adapter of step 1, which then leaves; `threads` keeps the delegation tools and the cards, while prompt sending and reading of Threads stay in `runtime.threads/v1`; `git.open-comparison/v1` is a command defined with `defineCommand` in the client part, dispatched by the conversation, which opens `/git/diff/:threadId/:repository` in a window of its own; `git` also registers `/settings/git` with parent `/settings`. See [split of the current features](./feature-split.md).

**Parity evidence:** configuration, credentials, models, costs, routes, IPC, lease and the remaining components preserve results and privacy.

### 11. Full extension

**Change:** installation of external bundles, replacement by another bundle of `settings/v1`, `secrets/v1` or of the backends `storage.backend/v1` and `secrets.backend/v1`, chosen in `providers` and activated in the foundation (without separate configuration and credentials bundles, which stay covered by the core), `notifications` (which reacts to `runtime.prompt-finished/v1`), `transport`, events/nodes/hooks and workflow executor when needed; depends on the deferred decision about trust.

**Parity evidence:** an example bundle goes through host service → durable event → Web Component → command; another composition swaps runtime and UI only through `providers` and the list of bundles, without changing the bootstrap.

## Rules of the steps

- The steps are review cuts, not an obligation to create all the interfaces at once.
- The old path is only removed after the parity evidence of the step.
- The proof must observe public contracts and usage scenarios, including replay, interruption, missing bundles, provider conflicts and the activation order of the foundation, without pinning private details of the implementation.
- Each step delivers the observability of what it extracts: the first brings structured log, tracing in the dispatcher and the catalog's diagnosis, and the following ones add the metrics of the extracted parts. See [observability](./observability.md).

## Boundary refactoring (BWP-0 to BWP-14)

After step 10, the boundary between platform and bundles was refactored in steps named BWP. Each one is described in [implementation decisions](./implementation-decisions.md), with the part that remains pending:

- **Completed in code:** removal of the semver baseline (BWP-0); opaque call scope (BWP-1); primary window, without the platform's `openSettings()` (BWP-2); `packages/host` removed (BWP-3); `required` and `alternatives` in the composition (BWP-4); opaque generation retentions (BWP-5); start, stop, generation and signal hooks (BWP-6); the owner's event sink (BWP-7); client reads and panels in the bundles, with Git leftovers to check in `packages/desktop` (BWP-11).
- **In progress in drafting:** credential kinds registered per bundle (BWP-8, with the `GIT` of `git`); `host-config` bundle with manifest (BWP-9); exposure declared per method and the generic bridge (BWP-10).
- **Still planned:** bundle folders grouped by role (BWP-13), and sandbox reattachment after restart, which is the only approved behavior change (BWP-14).

The rule that guides the steps is that of the platform without bundle concepts, described in `docs/architecture/bundles/boundaries.md`.
