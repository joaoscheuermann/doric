# Decisões de implementação da migração para bundles

**Estado:** registro das decisões tomadas durante a implementação da [arquitetura de bundles](../bundles.md). Resolve os pontos que os documentos de conceito deixam em aberto ou contraditórios. Quando um documento de conceito e este registro divergirem, este registro vale para o código; `GROUNDING.md` continua sendo o contrato do comportamento implementado e é atualizado à medida que cada fase entra.

## Princípios

- **Paridade 1:1.** A migração preserva o comportamento atual observável, inclusive peculiaridades documentadas no inventário (por exemplo `POST /threads/:id/interrupt` ignora `promptId`, a seção Tools das settings não chega ao host, só a seleção de Thread persiste no renderer, o app só tem tema escuro, `alwaysAvailable` não filtra tools nem skills, a mensagem `resume_exhausted` em português). Nenhuma funcionalidade nova de produto entra; correções de bugs ficam fora desta migração.
- **API mínima.** Quando os documentos não nomeiam um método necessário para preservar uma funcionalidade atual, o método entra com o menor formato que cobre essa funcionalidade e é marcado aqui.
- **Etapas combinadas.** As etapas da [migração](./migration.md) são cortes de revisão. As etapas 5, 6 e 7 são implementadas juntas: `runtime` e `direct` nascem sobre os tipos e streams genéricos de `storage/v1`, e a migração de dados converte as tabelas atuais. A etapa 2 entrega diretamente as primitivas genéricas da etapa 3 no `postgres`.
- **Etapa 11.** Instalação externa de bundles, assinatura e consentimento continuam adiados. `notifications` e `transport` entram porque correspondem a funcionalidades atuais.

## Estrutura de pastas e pacotes

| Decisão                         | Valor                                                                                                                                                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Pastas das partes               | `host/`, `desktop/` (ambiente `desktopMain`), `client/`, `contracts/`, `skills/` dentro de `bundles/<id>/src` (fonte) e `dist` (artefato), seguindo a convenção do manifesto. Os exemplos com `desktopMain/` são ilustrativos.                         |
| Nome do pacote npm de um bundle | Igual ao ID do bundle (`core`, `files`, `git`, `chat`...). Os pacotes de biblioteca `packages/docker` e `packages/firecracker` passam a se chamar `docker-sandbox` e `firecracker-sandbox` para liberar os nomes dos bundles `docker` e `firecracker`. |
| `<bundle>/contracts`            | Subpath `./contracts` no `exports` do pacote do bundle; no navegador, entrada do import map `"<id>/contracts"` para o artefato da geração.                                                                                                             |
| `bundle/contracts`              | Subpath browser-safe de `packages/bundle`; nenhum import de Node alcançável a partir dele. Contém também os schemas zod dos contratos básicos (janelas, menus, ui, navegação, regiões), para que provedores substitutos validem igual.                 |
| Runtime de serviços             | O diretório de serviços, o dispatcher e a propagação de `call` ficam num subpath browser-safe interno de `packages/bundle` (`bundle/runtime`), usado pelo loader do host, pelo `desktopMain` e por `packages/desktop-client`. Bundles não o importam.  |
| Pacotes novos                   | `packages/storage` (tipos do protocolo e kit de conformidade), `packages/desktop-client` (runtime client do loader) e `packages/desktop-ui` (componentes shadcn, tokens, Tailwind, tema e o helper de elemento React).                                 |
| Build das partes                | `host/` com `tsc` como hoje; `client/` e `desktop/` com esbuild em ESM, deixando externos os pacotes compartilhados e os `<id>/contracts`. CSS de cada bundle client gerado com Tailwind v4 e servido como `client/styles.css`.                        |

## Contratos e serviços

- **Ambiente e cardinalidade antes do código.** O build gera, junto com os JSON Schemas, um descritor por bundle (`dist/contracts.json`) com cada contrato fornecido, seu ambiente, cardinalidade e tipo (serviço, hooks, evento, comando, settings, storage). O loader usa o descritor antes da ativação e confere em `provide`/`register`.
- **`requires` por ambiente.** Uma entrada de `requires` restringe a parte de um ambiente quando algum bundle habilitado fornece o contrato nesse ambiente. Partes `client` também são satisfeitas por provedores do `host` e do `desktopMain` pela ponte. Entradas sem provedor alcançável são dependência ausente.
- **Cardinalidade.** Tabela fixa em `bundle/contracts` para os básicos (`many` só para `models.provider/v1`); para os demais, o descritor do bundle dono. `use` de um contrato `many` lança `ContractError` com código `many_contract_use`.
- **`whenAvailable`.** Callback `(api, provider: { bundleId, version }) => void | Cleanup`. O que o callback registra é descartado quando aquele provedor desativa.
- **`use` fora de `requires`.** Lança `ContractError` `undeclared_requirement`, exceto contratos `doric.*`, contratos que o próprio bundle fornece e o core usando contratos básicos.
- **Escopo.** Escopo efetivo = `call.scope` do pai mesclado com o escopo de `use` (chaves de `use` prevalecem); o dispatcher sobrescreve `windowKey` nas chamadas que saem de uma janela.
- **`deadline` e `trace`.** `deadline` em milissegundos de época, `0` significa sem prazo. `trace` é `{ traceparent: string }` no formato W3C; cada salto cria um span filho com o mesmo trace ID.
- **Erros.** `bundle/contracts` exporta `ContractError` (`code`, `message`, `details?`). Valores lançados sem `code` viram `internal`; falhas de validação viram `invalid_input` e `invalid_output`.
- **Métodos síncronos.** Serviços só locais (com entradas `z.custom` ou funções) devolvem o resultado do `execute` diretamente, síncrono ou não; o dispatcher se recusa a levá-los pela ponte.
- **Hooks.** Tipos `observe`, `transform` e `decide`. `execute` aguarda os handlers `observe` em sequência, cada um com o prazo padrão; falha de `observe` vai ao diagnóstico. Só o bundle que lista o contrato de hooks em `provides` (ou a plataforma, para `doric.*`) pode chamar `define`; `define` é idempotente por dono.
- **Ordem entre bundles não relacionados.** Ordem topológica por dependência com desempate lexical pelo `id`; a mesma ordem vale para handlers de hooks.
- **Entradas dos hooks do app.** `onActivateHook`/`onDeactivateHook`: `{ bundleId, version, generation, environment }`; `onHostReadyHook`, `onAppReadyHook`, `onAppActivateHook`, `onBeforeQuitHook`: `{}`; `onGenerationReadyHook`: `{ generation }`; `onConnectionChangedHook`: `{ connected }`. Todos `.strict()`.
- **`log/v1`.** `debug | info | warn | error(message, fields?)`, sem lançar e sem esperar resposta.
- **`provide` seguido de `use` no mesmo `activate`.** `provide` registra de forma síncrona; a plataforma chama `define(AppHooksV1)` depois que o `activate` do provedor de `hooks/v1` termina.
- **Comandos.** Comandos são contratos versionados e entram em `provides`. Tipos de bloco de projeção não entram.
- **S-1 Refinamentos das etapas 2 e 3.** Antes de qualquer baseline publicada, as etapas 2 e 3 refinam, sem evento de semver, os formatos básicos de `storage`, `secrets`, `settings`, `events` e do catálogo (`CatalogSnapshot.storage`, `HostPlatform.storageIdentity()`) e acrescentam os códigos `revision_conflict`, `sequence_conflict`, `unique_conflict`, `limit_exceeded`, `unknown_type`, `invalid_index_value`, `invalid_stream`, `unknown_settings`, `settings_missing`, `settings_conflict`, `unknown_event`, `invalid_scope` e `credential_*`. Core e `postgres` usam esses schemas exatos (D-12).
- **S-6 Regras dos campos de credencial.** `credentialFields`, `credentialFieldsSatisfied`, `credentialFieldsMessage` e os tipos dos campos ficam em `bundle/contracts`; o kernel (schemas das rotas) e o core (validação) importam de lá, então a regra continua uma só.
- **S-7 `secrets/v1.view()`.** Visão local e síncrona do cache do provedor (`list`, `redactions`, `addRedaction`), que nunca atravessa a ponte. `secrets/v1.redactions(call)` (API mínima, serializável) devolve a mesma lista de redação a quem está fora do processo (revisão cruzada X-4).
- **S-8 Referências no lugar da FK.** `secrets/v1.registerReferences(fonte)` (API mínima, local): `delete` responde `referenced` enquanto uma fonte registrada nomeia a credencial, e é conferido primeiro. `settings/v1.set` e as escritas de `secrets/v1` passam por uma única fila de escrita do core, então uma configuração nunca nomeia uma credencial removida por um delete concorrente. A fila em processo substitui a transação Serializable da configuração; vale a suposição existente de um processo de host por banco, da qual o cache de credenciais já dependia.
- **S-10 `events/v1`.** Grava em `runtime.thread.events/<threadId>` (`threadEventsStream`) o envelope atual, `threadEventEnvelopeSchema` (`projectId`, `threadId`, `promptId`, `type`, `event`); `sequence` e `createdAt` são os da entrada do protocolo, e esse é o único formato desse stream também para o `runtime` (X-5). O corpo leva `type`, a redação roda antes de gravar, o escopo da chamada precisa nomear project, Thread e prompt (`invalid_scope`) e só o dono do evento registrado faz append (`not_owner`). Nenhum bundle publicado registra evento até a etapa 7 (teste E-6), porque um append direto contorna o agregado do `runtime`.
- **S-12 `postgres.database/v1` provisório.** `connect()` e `client()` (local) e o subpath `postgres/prisma` (cliente gerado e `createDatabase`) existem só para o kernel, cujas tabelas de Project, Thread, eventos e uso continuam no SQL atual até a etapa 7.

## Composição e boot

- **Arquivo de composição.** O host lê a composição de `DORIC_COMPOSITION` (caminho de um JSON) e, sem a variável, da composição padrão distribuída com o host (`agents/doric/composition.json`). Formato: `{ "core": "core", "enabled": [...], "providers": { ... } }`, validado por zod em `packages/bundle`. Os bundles instalados são lidos de `DORIC_BUNDLES_PATH` (padrão: o diretório `dist/bundles` do host).
- **Fundação por ambiente.** Um bundle escolhido em `providers` é fundação só nos ambientes em que fornece o contrato escolhido; nos outros, ativa com os demais. Bundles da fundação que substituem uma fachada do core (`events/v1`, `settings/v1`, `models/v1`) podem exigir `storage.backend/v1` e `secrets.backend/v1`, que ativam antes dentro da fundação.
- **Gerações.** Contador monótono por catálogo publicado. Bundles do kernel informam a geração em que o kernel os ativou.
- **`hostId` e `storageGeneration`.** O backend `postgres` guarda um registro de metadados reservado com os dois valores; o catálogo os publica (S-5).
- **S-15 Ordem do boot.** `bootstrap → sandbox_pool → bundle_load → database_client → credential_activation → configuration_activation → workspace_reconciliation → network_binding → ready`: só `database_client` muda de lugar, para depois de `bundle_load`. Nenhum `activate` da fundação ou do core faz I/O (cliente, cifra e `declareType` são preguiçosos); o kernel força cada um no estágio que já falhava por ele: em `database_client` só a falta de `DORIC_DATABASE_URL` (o `connect()` do adaptador `pg` não abre conexão, como o `$connect()` de antes); a identidade do storage é lida logo após a carga das credenciais, em `credential_activation`, onde um banco inacessível ou sem migração já falhava, leitura da configuração em `configuration_activation`. Nomes de estágio, textos das mensagens de log e o caminho fatal não mudam; só a ordem das linhas de inicialização segue a dos estágios. `Bundles loaded` passa a contar 5 bundles (entra `postgres`; os embutidos `host-adapter` e `host-config` não contam). No encerramento, o `$disconnect` acontece na desativação do `postgres`, dentro de `platform.stop()`.

## Armazenamento e dados

- **`storage.backend/v1`.** Primitivas genéricas: documentos versionados por tipo e chave com revisão, índices declarados (igualdade, inclusive `null`, e ordenação), streams com sequência e lacunas, `commit` declarativo atômico (puts, deletes, appends, verificação de revisão esperada), feed de commits com cursor, blobs, truncamento de stream e saúde/admissão de escrita. `packages/storage` define os tipos e o kit de conformidade que qualquer backend precisa passar.
- **Dados atuais.** Uma migração offline e idempotente converte Project, Thread, eventos, fila, estado do executor, uso, configuração e providers para tipos e streams dos bundles donos, com leitura de verificação antes da troca. Credenciais continuam no envelope AES-256-GCM sob `DORIC_CREDENTIAL_KEY` e são lidas sem reescrever o segredo.
- **Eventos.** Eventos gravados nunca são reescritos; a etapa 7 copia os eventos para o stream novo com o mesmo tipo e payload. O tipo `prompt.finished` passa a ser lido também como `runtime.prompt-finished/v1`.
- **`settings/v1`.** `register(definição)`, `get(definição)`, `entry(definição)` (S-9), `set(definição, valor, { expectedRevision? })` e `subscribe`. Cada definição é um espaço com `{ value, revision, version, updatedAt, generation }`. Um contador global de geração de configuração preserva a proveniência que os Projects guardam hoje.
- **`secrets/v1`.** `resolve(ref)`, `list`, `describe(ref)` (nunca devolve o segredo), `create`, `update` (ausente mantém, `''` limpa, valor define), `delete` (recusado quando referenciado), `resolveByKind(kind, { exclude? })` e `redactions()`, mais os locais `registerReferences` (S-8) e `view` (S-7). Redação nos logs como hoje.
- **`usage`.** Fica no agregado do `runtime` enquanto não houver participação transacional de outro bundle; o bundle `usage` lê a projeção e fornece a UI.
- **Pressão de disco.** O `postgres` informa medidas e admissão (S-4); quem chama mantém a política atual (limiar de 10%, verificação a cada 3 s, mapeamento de `53100` e `ENOSPC`): o runner do kernel nas etapas 2 a 4 e o `runtime` a partir da etapa 5.
- **S-2 `commit.dropStreams`.** API mínima: remove streams inteiros, para a paridade da exclusão de Thread e Project a partir da etapa 5. Ordem de aplicação num lote atômico, verificada pelo kit: expect → delete → put → dropStreams → truncate → append. O resultado continua `{ position }`; quem escreve com `expect` deriva a revisão nova como esperada + 1 (uma criação com `revision` 0 recebe 1; X-2).
- **S-3 Entradas e truncamento.** O protocolo é dono do `createdAt` de cada entrada de stream (ISO-8601 em ms, UTC, fixado pelo backend no commit) e das marcas de truncamento `{ afterSequence, atSequence }`, que `read` devolve aos leitores afetados (`afterSequence < pedido <= atSequence`). `lastSequence` nunca diminui. Cada commit do feed separa `streams` (appends), `truncated` e `dropped`.
- **S-4 Saúde.** `health` informa medidas: `{ status: 'ok' | 'unavailable', writable, reason?, disk?: { blocks, availableBlocks } }`. `'pressure'` sai do enum, e um disco que não se mede é `unavailable` sem `disk`. `storage/v1.health` entra (API mínima). A saúde do `postgres` mede `DORIC_STORAGE_PATH` sem ida ao banco. Não existe código `storage_full`: erros do banco propagam sem mudança, então `53100` continua reconhecível. A fachada não tem `capabilities()`: recusa com `limit_exceeded` antes de enviar, e `maxBatch` padrão é 10000, para que a exclusão atômica de um Project grande caiba num lote (X-3).
- **S-5 Identidade.** `storage.backend/v1.identity()` cria na primeira chamada o registro reservado com `hostId` (UUID aleatório) e `storageGeneration` 1 e devolve os mesmos valores depois, em qualquer instância. `HostPlatform.storageIdentity()` memoriza a promessa (rejeição não memorizada) e põe a identidade em `catalog().storage`; o kernel a resolve em `database_client`. O contador de gerações de bundle continua por processo; persisti-lo fica para a etapa que precisar dele (a revisão cruzada G-6 o entrega ao desenho da etapa 8).
- **S-9 Espaços de settings.** `settings/v1.entry` (API mínima), porque `GET`/`PUT /config` precisam de revisão e horário. `SettingsEntry` ganha `updatedAt` e `generation`. Cada espaço é um documento `core.settings/v1` com o ID do espaço, e o contador global é o documento `global` de `core.settings-generation/v1`; cada `set` incrementa a revisão do espaço e o contador. Os assinantes rodam de forma síncrona depois do commit, antes de a fila de escrita liberar. Códigos: `unknown_settings`, `settings_missing`, `settings_conflict` e `invalid_input`.
- **S-11 Chaves de índice.** Codificação ordenável em bytes: `null` < `false` < `true` < número < string; números em ordem numérica, strings por bytes UTF-8; empate pelo ID do documento, também em bytes UTF-8 (como `COLLATE "C"`).
- **S-13 Configuração em `settings/v1`.** A configuração passa ao espaço `host-config.configuration/v1`, do bundle provisório embutido `host-config` (kernel). A migração SQL `20261009000000_generic_storage` converte `doric_configuration`, `provider_configuration` e `model_configuration` sem perda, mantendo `revision` e `updated_at` (ms, UTC `Z`) e iniciando o contador global na revisão; verifica a conversão antes de remover essas tabelas e o enum `ModelRole`. Um kind de provider fora de `openai`, `openrouter` e `codex` interrompe a migração (`RAISE`), sem descartar nem converter nada. O UUID `generation` de cada substituição, que ninguém lia, sai; os Projects continuam guardando a revisão. Sem FK, a tabela `credential` fica sozinha: as referências são garantidas pelo S-8 e pela refinação do `host-config`. A migração não se desfaz (política pré-1.0): o operador faz backup antes de `prisma migrate deploy`. A divisão do espaço entre os donos fica para a etapa 10 (X-6).
- **S-14 Posições do feed.** Alocadas sob um lock consultivo de transação, tomado por último no commit, então o feed não tem lacunas e segue a ordem de commit. `NOTIFY` espera um publicador (etapa 5 em diante).
- **S-16 Prisma no `postgres`.** O schema, as migrações (as 17 anteriores sem mudança mais `generic_storage`) e o cliente gerado ficam em `bundles/postgres`. `agents/doric/prisma.config.ts` continua como ponto de entrada compatível (Compose, imagem, `nx run doric:migrate`). O que o Prisma não expressa (índice único parcial, `COLLATE "C"`) é do SQL da migração, como o trigger e o CHECK de antes; o fluxo é só `migrate deploy`.

## Execução e domínio

- **Acesso ao sandbox pelas tools.** `runtime.lease/v1` expõe as operações do sandbox adquirido para `call.scope.projectId` (exec, arquivos, Git, diff, métricas), respondendo os estados atuais do lease sem adquirir. `files/v1`, `git`, `terminal/v1` e `resources` usam esse contrato.
- **Métodos de `runtime.*`, `terminal/v1` e `files/v1`.** Derivados um a um dos controles atuais de `packages/host` e das rotas atuais de Project, Thread e terminal.
- **Configuração de tools.** Vai para o `defineSettings` do bundle dono e é lida com `services.use(SettingsV1).get(...)` dentro do `execute`.
- **Skills.** O loader descobre `skills/*/SKILL.md` e registra pelo `skills/v1` em nome do bundle; `skills/v1.register(skill)` existe para registro por código; `skills/v1.list()` preserva a ordem dos bundles e a resolução de `allowed-tools` por bundle; `direct` lê skills e tools por `skills/v1` e `tools/v1`.
- **`models.provider/v1`.** `{ kind(): KindDescriptor; listModels(config, call); create(config, secrets, call): LlmProvider }`, espelhando `providerKinds` e `createProviderForKind` de `packages/llms`. `models/v1.resolve({ providerId, model, effort }, call)`.
- **Transporte.** O bundle `transport` monta as rotas REST e os namespaces Socket.IO atuais sobre as operações semânticas dos bundles, preservando caminhos, formatos, códigos de erro e cabeçalhos (inclusive o `Cache-Control: no-store` global). Além disso, o host expõe um endpoint técnico de ponte (`/doric/bridge`, Socket.IO) com mensagens `call`, `result`, `cancel`, `subscribe`, `event` e `unsubscribe`, usado pelo desktop para chamadas a serviços do host, catálogo e download de artefatos por hash.
- **Processos.** No host, o kernel (`agents/doric`) roda transporte técnico, catálogo, fundação e core; os demais bundles rodam num processo filho por geração (`child_process.fork`) com o envelope RPC. No desktop, todas as partes `desktopMain` de uma geração (fundação, core e demais) rodam no `utilityProcess` daquela geração.

## Desktop e UI

- **Preload.** Um único namespace `window.doric.desktop`: `describeWindow()`, `ready()`, `reportFailure(info)`, `onCloseRequested(cb)` com canal de resposta, `onChromeChanged(cb)`, `catalog()`, `call(envelope)`, `cancel(id)` e assinatura de streams. Os canais semânticos atuais saem quando a UI em bundles assume.
- **Import map.** React, ReactDOM, Lexical e `@lexical/*`, `desktop-ui`, `zod`, `bundle/contracts` e os `<id>/contracts` da geração. O handler do protocolo renderiza a shell por requisição com o import map da geração e calcula o hash da CSP na mesma resposta.
- **Dev.** Em desenvolvimento as janelas também abrem por `doric://app`; o handler encaminha a shell e os assets ao servidor de desenvolvimento.
- **Privilégios do esquema.** `standard`, `secure`, `supportFetchAPI`, `corsEnabled` e `codeCache`, confirmados no primeiro teste da etapa 8.
- **Janelas.** `open({ key, path })` sempre respeita `path`. O main guarda o último path e os limites de cada chave. No `onAppReadyHook`, o core reabre `workspace` no último path guardado (ou `/`), o que preserva a seleção de Thread entre reinícios; a seleção antiga em `localStorage` (`doric.selection`) é convertida em path uma vez.
- **Gerações no desktop.** Na troca, o novo `utilityProcess` sobe, define `AppHooksV1` e dispara `onGenerationReadyHook` (não `onAppReadyHook`); janelas abertas continuam na geração em que nasceram e recarregam para trocar.
- **Comandos.** O `commands/v1` do client procura primeiro no registro da janela e depois encaminha ao `desktopMain` pela ponte. O main resolve menu e atalho no registro do `desktopMain` e depois na janela em foco. Comandos ligados a menu ou atalho aceitam entrada vazia.
- **Atalhos.** Papéis do menu Editar mantêm aceleradores nativos; os demais atalhos são tratados por um único listener na shell, que recebe do main a tabela efetiva filtrada por `when`. Como hoje o app usa o menu padrão do Electron, o esqueleto do core reproduz esse menu padrão e os atalhos atuais.
- **Lexical.** O `chat` congela o próprio registro de nodes na criação do primeiro editor da janela.
- **Renderizadores.** `registerRenderer({ blockType, elementTag })` estrito; ações de bloco são IDs de comando, despachadas pelo `chat` por um único evento de intenção `{ command, input }`.
- **Notificações.** Capacidade de plataforma `doric.notifications/v1` no `desktopMain` (`show({ title, body })`, com o mesmo relato de recusa do sistema que existe hoje); o bundle `notifications` decide quando avisar a partir de `runtime.prompt-finished/v1`.
- **Histórico local.** O bundle `history` fornece no `desktopMain` `history.snapshots/v1` (`read(threadId)`, `write`), gravando em `<hostId>/<storageGeneration>/<threadId>` dentro do diretório de `doric.cache/v1`; o `chat` o usa por `whenAvailable`.
- **Rotas.** Casamento só por `pathname`; barra final normalizada, exceto em `/`; segmentos estáticos antes de parâmetros; padrões de mesma especificidade que casam os mesmos paths são conflito.
- **Elementos React.** `dispose()` idempotente; o helper `defineReactElement` fica em `desktop-ui`, não em `desktop-client`.
- **Abas do layout.** Estado das abas indexado pelo `threadId` da rota ativa.
- **Seções de settings.** Os contratos de configuração e credenciais são serviços do host (`settings/v1`, `secrets/v1`, `models/v1`) alcançados pela ponte.

## Validação

- Toda fase passa `npx nx run-many -t typecheck test build`, `npm run format:check` e `npm run lint`.
- A paridade é verificada por uma suíte end-to-end que roda os mesmos cenários de API (REST e Socket.IO) e de UI (Electron por CDP) contra o baseline e contra a implementação nova, com um servidor de modelo falso compatível com OpenAI Responses.
- A imagem Docker do host (`agents/doric/.Dockerfile`, alvos `agent-runtime`, `docker-runtime` e `runtime`) compila todos os bundles, inclusive os artefatos `client` e `desktop` que o desktop baixa durante o splash.

## Etapa 1 (Contrato)

Decisões tomadas ao implementar a etapa 1. Os identificadores **D-n** são citados no código e nos testes.

### Contratos e runtime de serviços

- **D-1 Ordem das skills.** O loader descobre `skills/*/SKILL.md` em ordem lexical de pasta. As pastas do `files` levam prefixos de dois dígitos que reproduzem a ordem do antigo manifesto, então o system prompt é idêntico byte a byte.
- **D-2 Marcas e erros entre instâncias.** Definições, `Call` e o protocolo de registro usam `Symbol.for`; erros são reconhecidos por `name`/`code`, nunca por `instanceof`; os mapas do runtime usam o ID do contrato como chave.
- **D-3 Argumento de chamada no fim.** Um `Call` no fim é sempre o argumento de chamada. Opções `{ signal, deadline }` só contam como argumento de chamada além do comprimento da tupla ou quando o item da tupla naquela posição as recusa; assim `log.info('x', { deadline: 5 })` mantém `deadline` como campo.
- **D-4 Registros.** Toda API de registro devolve `Disposable` (`{ dispose() }`), inclusive `navigation.subscribe`.
- **D-7 Saída original.** Dentro do processo a saída é validada e o valor original é devolvido, nunca a cópia do zod; schemas de saída são descritivos.
- **D-8 Erro original.** Dentro do processo o valor lançado por `execute` propaga sem mudança; `toContractError` só onde um código é exigido.
- **D-10 Protocolo de registro.** `bindRegistrant` liga um argumento registrável (tool, comando) aos serviços do bundle que chamou antes da validação.
- **D-11 `invalid_input` síncrono.** A validação dos argumentos lança de forma síncrona no processo; os wrappers das tools são `async`, então quem chama vê uma rejeição.
- **D-12 Provedores de contratos básicos.** `provide` confere nomes de métodos e JSON Schema de cada método contra a especificação da plataforma (`contract_mismatch`).
- **D-13 `whenAvailable`.** Cada callback roda num escopo filho ligado à vida daquele provedor.
- **D-14 Chamador da plataforma.** `{ bundleId: 'doric', version: PLATFORM_VERSION, generation }`.
- **D-16 Fachada de `hooks/v1`.** O provedor implementa métodos planos (`define`, `register`, `whenDefined`, `execute`); o runtime monta a API de consumo.
- **D-17 Entradas de `WindowHooksV1`.** `{}` estrito.
- **D-18 `doric.log/v1`.** Contrato de plataforma novo (API mínima), `write(record)`, por onde um provedor de `log/v1` chega aos arquivos de log do host.
- **D-29 Segurança no navegador.** Além do teste do grafo de imports, `tsconfig.browser.json` (só typecheck, `lib` es2022+dom, `types: []`) compila `bundle/contracts` e `bundle/runtime`.
- **D-30 Partes puras no runtime.** Schemas de manifesto, composição e descritor, o resolvedor por ambiente `resolveEnvironment` e o laço genérico de ativação ficam em `bundle/runtime`; `loader/` guarda só leitura de arquivos, descoberta, skills e o `startHost` de Node.
- **D-31 `skills/v1.list`.** Assíncrono (método não local).
- **D-32 `define` de hooks.** O `define` do provedor devolve um `Disposable` registrado no escopo do dono; ao descartá-lo, os registros feitos dentro de callbacks `whenDefined` caem. A fachada devolve um handle por contrato.
- **D-33 Sem corrida de sinal.** O dispatcher no processo não confere nem corre contra `call.signal`/prazo; o cancelamento chega aos provedores só por `call.signal`.
- **D-34 JSON Schema por direção.** `io: 'input'` para entradas e `io: 'output'` para saídas.
- **Plataforma reservada.** `defineService` recusa IDs `doric.*`, como `defineHooks`; a plataforma usa uma variante interna.
- **Saídas somente leitura.** `defineMethod` aceita formas readonly do tipo de saída.
- **Chamada a método inexistente.** Um método que o provedor não tem responde `unavailable`.
- **Schemas frouxos tipados.** Os schemas de registros de `runtime/contracts` e `terminal/contracts` são `z.looseObject` anotados com a interface correspondente (`z.ZodType<T, T>`), para que o provedor devolva o tipo que já tem.

### Manifesto, composição, catálogo e ativação

- **D-19 Tools v0.** Uma tool de manifesto v0 precisa exportar por padrão uma definição atual de `tool`; uma fábrica antiga coloca o bundle em quarentena (`invalid_part`).
- **D-20 Backends na composição.** A regra de `storage.backend/v1`/`secrets.backend/v1` sempre em `providers` começa na etapa 2.
- **D-21 Fundação em quarentena.** Um provedor de fundação escolhido em quarentena leva o host à recuperação, sem cair para o core. Um provedor escolhido que não é de fundação, em quarentena, deixa o contrato sem provedor ativo, e seus dependentes recebem `dependency_quarantined`.
- **D-22 Ambiente pelo build.** O ambiente e a cardinalidade de cada contrato no descritor vêm de uma ativação a seco no build, não de declaração.
- **D-35 Manifesto.** O `id` não pode ser `doric`; manifestos v0 convertidos recebem um descritor vazio. Um bundle cujo manifesto não pode ser lido não tem ID conhecido e fica sempre em quarentena (`invalid_manifest`).
- **Raiz ausente.** Uma raiz de bundles ilegível vira um problema da composição e recuperação (core ausente), não uma exceção.
- **Contadores.** A geração é um contador por processo; os provedores de contrato no snapshot do catálogo também trazem `bundleVersion`.
- **Isenção do core no build.** O gravador do build não isenta o core de declarar contratos básicos (no build não existe composição); na etapa 1 o core só usa contratos que fornece e `doric.*`.

### Core, bundles e adaptador

- **D-5 `runtime.lease/v1`.** Entra na etapa 1 no adaptador com `describe`, `exec`, `readFile` e `writeFile`; `exec` não repassa sinal de cancelamento ao sandbox e não devolve bytes.
- **D-6 Terminal opcional.** O `files` consome `terminal/v1` por `whenAvailable` (fora de `requires`) e mantém o fallback da tool `terminal` para um comando simples no sandbox, recusando `background` e `pty` com `This host does not support live terminals.`. O adaptador responde `unavailable` para um prompt cujo `Host` não tem terminais, o que leva ao mesmo fallback.
- **D-9 Configuração de tools.** Os valores deixam de chegar ao `execute`; os metadados `settings`, `requireToolConfigs`, `resolveToolConfigs` (ainda chamado em cada prompt, que continua recusando settings não satisfeitas) e `GET /tools` mantêm o comportamento até `settings/v1`.
- **D-15 Recuperação no host.** Na etapa 1 o modo de recuperação termina no caminho fatal de inicialização existente (`Doric failed to start`, estágio `bundle_load`) depois de registrar no log `Bundle recovery mode` com o estado e os motivos de cada bundle.
- **D-23 Contratos do core no desktop.** `core.hooks/v1` e `core.open-settings/v1` entram nos `provides` do core na etapa 8; `core/contracts` já publica as referências.
- **D-24 Prazo dos hooks.** 10 000 ms por handler no core; `doric.window.hooks/v1` segue as regras próprias (`onCloseHook` sem prazo, `onFlushHook` com o prazo da chamada).
- **D-25 Nomes.** Projetos Nx `bundle-<id>`; pacotes npm `<id>`.
- **D-26 Pacotes só de contratos.** `bundles/runtime` e `bundles/terminal` existem desde a etapa 1 apenas como `runtime/contracts` e `terminal/contracts`, sem manifesto e sem staging.
- **D-27 Adaptador embutido.** O bundle embutido `host-adapter` (sempre habilitado pelo host, fora da composição) fornece `runtime.threads/v1`, `runtime.workspace/v1`, `runtime.lease/v1` e `terminal/v1` sobre o `Host` e o sandbox de cada prompt, ligados ao escopo do prompt durante a execução (`attach`/`release`, com a liberação protegida pela identidade da ligação). Sai quando os bundles extraídos assumirem esses contratos.
- **D-28 Diagnóstico sem rota.** Nenhuma rota HTTP de diagnóstico na etapa 1; o diagnóstico fica em `doric.diagnostics/v1`, `HostPlatform.diagnostics()` e nas linhas de log `Bundle quarantined`.
- **Executor obrigatório.** O serviço de workspace recebe o executor do Direct do composition root (`createDirectExecutor({ call, attach })`); não existe mais executor padrão.
- **Caminhos.** `DORIC_BUNDLES_PATH` (padrão: `dist/bundles` ao lado do entrypoint compilado) e `DORIC_COMPOSITION` (padrão: `agents/doric/composition.json`).
- **Mudanças observáveis aceitas.** `Bundles loaded` conta 4 bundles em vez de 3 (o core novo); um bundle não-core que falha fica em quarentena em vez de impedir a inicialização; os quadros de pilha de erros persistidos em `tool.failed`/`agent.failed` mudam de caminho, mantendo `name`, `message` e `cause`.

### Pontos abertos

- Etapa 4: invocação de tools e handlers de hooks entre processos (referências de handler no envelope); o erro do envelope precisa manter `name`, `message` e a cadeia `cause` para a paridade dos eventos `tool.failed`/`agent.failed`; métodos só locais (`tools/v1.register/list`, `hooks/v1.register`) precisam de handles do lado do envelope; limpeza no provedor por `caller.generation` quando uma geração sai.
- Etapa 2: valores das settings de tools por `settings/v1`; saída de `events/v1.append`; a regra dos backends em `providers`; contador de geração persistido e `hostId`.
- Etapas 8/9: gravador de descritor com DOM para partes `client`; registros que devolvem `Promise<void>` pela ponte (`menus/v1`) descartados do lado do provedor no `onDeactivateHook`; promover o core mínimo de teste a `bundle/testing`.
- Rotação de arquivos de log não entra na etapa 1; `doric.log/v1` escreve nos destinos pino existentes.
- Acesso por escopo (HC-007): qualquer bundle que exija `runtime.lease/v1`, `runtime.threads/v1` ou `terminal/v1` e monte um escopo com os IDs de um prompt em execução alcança os controles desse prompt. Todos os bundles da etapa 1 são de primeira parte e bundles externos continuam adiados; a etapa 5 precisa manter esses formatos (extensão minor) ou registrar uma mudança major.

## Etapas 2 e 3 (Storage e protocolo genérico)

Decisões tomadas ao implementar as etapas 2 e 3 juntas. As decisões de desenho **S-1** a **S-16** ficam nas seções gerais acima (Contratos e serviços, Composição e boot, Armazenamento e dados); as subseções abaixo registram os detalhes de cada pacote.

### Pacotes

- **Nome `postgres`.** O pacote npm do bundle é `postgres` (Nx `bundle-postgres`), como os demais bundles. A dependência `postgres@3.4.7` do `prisma` fica aninhada em `node_modules/prisma/node_modules/postgres`, e `prisma --version` funciona; não há exceção de nome. O pacote de protocolo é `storage` (Nx `storage`).

### Contratos (`packages/bundle`)

- **Tipos de credencial exportados.** Além das regras de campos (S-6), `bundle/contracts` exporta `credentialKinds`, de onde sai `credentialKindSchema`, para o kernel derivar o `z.enum` das rotas da mesma lista.
- **Regra de atualização documentada.** O comentário de `credentialUpdateSchema` passa a dizer a regra real do serviço atual: ausente ou `null` mantém o campo; qualquer string, inclusive `''`, grava. O formato não muda.
- **`storageIdentity()` sem backend.** Sem provedor ativo de `storage.backend/v1`, `HostPlatform.storageIdentity()` responde `undefined` sem memorizar. A identidade resolvida aparece em `catalog().storage` e em `doric.catalog/v1.get()`.
- **Nomes de schema.** A declaração do backend é exportada como `storageDeclarationSchema`/`StorageDeclaration`; `hostId` usa `z.uuid()` (equivalente zod 4 de `z.string().uuid()`). `feedRequestSchema.after` não muda.

### Protocolo (`packages/storage`)

- **Auxiliares além do desenho.** A raiz de `storage` também exporta `decodeIndexKey` (inverso da codificação), `compareBytes`, `compareIds` (desempate por ID em bytes UTF-8, como `COLLATE "C"`), `defaultStorageCapabilities` e `checkBatchLimits`, para que memória, `postgres` e a fachada do core apliquem os mesmos limites.
- **Valores indexáveis.** Número não finito, string com surrogate isolado, objeto ou array é `invalid_index_value`; `-0` e `0` têm a mesma chave. Um intervalo com `gt` e `gte` (ou `lt` e `lte`) juntos é `invalid_input`.
- **`parseStreamId`.** `family` é o nome qualificado antes da barra, com o dono (`runtime.thread.events`); `owner` é o primeiro segmento. O backend aceita qualquer nome de stream; validar o formato é papel da fachada.
- **Lote e limites.** Lote vazio é o de `batchSize` 0 (`invalid_input`); um lote só com `expect` é válido e ocupa uma posição no feed. Os limites são inclusivos, e `maxAppendBytes` vale para cada evento anexado. A unicidade é verificada a cada `put`, como um índice único não adiado do PostgreSQL.
- **Marca de truncamento.** `atSequence` é o `lastSequence` ao fim do lote, contando os appends do mesmo lote, para que um leitor que já tinha a cauda removida sempre veja a marca.
- **Consulta e feed.** Consultar um índice não declarado (ou um tipo sem declaração), igualdade com mais campos que o índice ou intervalo sem campo seguinte é `invalid_input`. `documents` no feed são as chaves de `delete` e `put`, sem repetição.
- **Blobs.** `putBlob` exige base64 padrão (senão `invalid_input`); `getBlob` de um hash mal formado responde `undefined`.
- **Backends em memória.** `secrets.backend/v1` em memória ordena `list` por nome em unidades de código (como `COLLATE "C"`), mantém o `kind` gravado numa atualização e preenche `createdAt`/`updatedAt`. `memoryFoundation` aceita também `storage` (limites e `health` do backend de storage).
- **Kit de conformidade.** `storage/conformance` exporta `conformanceCases` (49 casos, IDs D1–D7, C1–C4, R1–R3, Q1–Q10, S1–S6, P1–P2, F1–F4, X1–X5, B1–B3, L1–L3, H1–H2), `runConformanceCase(harness, caso)` e `runStorageConformance(harness, { skip, timeout })`, que registra uma suíte `node:test` por grupo (limite de 120 s por caso). Cada caso roda depois de `reset()`, e as instâncias que ele abre e não fecha nem derruba são fechadas no fim. O harness é genérico no tipo da instância.
- **Casos independentes do backend.** O kit não supõe que as posições do feed comecem em 1 nem que sejam contíguas (storage.md diz só "monotônica"): exige posições estritamente crescentes, cada commit bem-sucedido uma vez e na ordem, e que um leitor que acompanha commits concorrentes não perca nenhum. A ordem das chaves dentro de um commit do feed não é verificada. A contiguidade do `postgres` (S-14) continua no teste próprio do bundle.
- **Itens do desenho agrupados.** As consultas inválidas entram em Q1, Q2 e Q5; criações concorrentes com `revision` 0 em C1; reivindicações concorrentes de uma chave única em C4; `invalid_index_value` no meio do lote em X2; `createdAt` ISO em S1. O kit não fixa se uma chave única admite vários documentos sem o campo: hoje memória e `postgres` tratam `null` como valor, e um índice único aceita só um documento com o campo ausente.
- **Autoteste do kit.** `tests/kit-self.test.ts` envolve o backend em memória em três variantes quebradas (sem atomicidade, com sequência reutilizada após truncamento, com lacuna no feed) e exige que X1–X4, S3–S4 e F1–F4 falhem; qualquer erro conta como falha. Um invólucro que só repassa as chamadas passa nos mesmos casos.

### Backend `postgres` (`bundles/postgres`)

- **Bloqueios.** Em vez de `SELECT … FOR UPDATE`, cada `commit` toma de uma vez, numa ordem global (pela chave `hashtextextended`), locks consultivos de transação: exclusivo por documento de `expect`/`put`/`delete` e por stream escrito, compartilhado por tipo de `put`/`delete`; `declareType` toma o exclusivo do tipo. Assim uma criação com `revision` 0, uma verificação de ausência sem `put` e um stream removido também se serializam, sem ciclo de espera. O lock da posição (S-14) vem por último.
- **Puts um a um.** Os `put` aplicam-se em ordem, cada um com sua revisão e suas entradas de índice; a unicidade é conferida a cada `put`, com um `INSERT` por índice único, de modo que o `23505` em `storage_index_entry_unique_key` vira `unique_conflict` com o nome do índice. Os outros erros do banco propagam sem mudança (`53100` continua reconhecível).
- **Declarações sem cache.** `commit` e `query` leem `storage_type` a cada chamada, então uma declaração feita por outro processo vale na hora.
- **Feed.** `storage_commit` ganha as colunas `truncated` e `dropped` (padrão `'[]'`) em vez de guardar esses nomes dentro de `streams`. Um banco recém-migrado começa com a posição 1, o commit da conversão da configuração.
- **Horário.** Um `clock_timestamp()` por commit, truncado em milissegundos e lido depois dos locks, vale para `updated_at` e para o `createdAt` das entradas, no formato de `toISOString()`.
- **JSON.** Valores ficam em JSONB: a ordem das chaves é a do JSONB, e `\u0000` em valores, IDs ou nomes de stream é recusado pelo PostgreSQL (erro propagado), ao contrário do backend em memória; a fachada aplica `storable` antes.
- **Transações.** As transações interativas do Prisma usam `maxWait` de 30 s e `timeout` de 120 s, porque um lote pode ter até `maxBatch` itens e esperar locks.
- **Cliente e ambiente.** `client()` cria o cliente no primeiro uso a partir de `DORIC_DATABASE_URL` (falha não memorizada); `connect()` e os métodos de storage rejeitam, sem lançar de forma síncrona, quando o cliente não pode ser criado. A limpeza da desativação desconecta só o cliente criado pela URL; um cliente injetado (testes) fica com quem o criou. `createDatabase` é o de antes, então as consultas por modelo usam o schema `public`.
- **Segredos.** A cifra é criada na primeira chamada de `list`, `get` ou `put` (uma chave mal formada recusa toda chamada com a mesma mensagem, antes do banco); falha de decifração é `credential_unreadable` com a mensagem da cifra; `list`/`get` devolvem `createdAt`/`updatedAt`. IDs que não são UUID chegam ao Prisma como no store anterior.
- **Migração da configuração.** Os providers do documento migrado ficam em `ORDER BY id` na collation do banco; o carregamento antigo ordenava por `localeCompare` na leitura, e o leitor novo precisa continuar ordenando. `jsonb_typeof(models) = 'array'` reproduz o `Array.isArray`; a verificação também exige o documento do contador global. Nomes de FK e `ON UPDATE CASCADE` seguem o Prisma, e `prisma migrate diff` não acusa diferença.
- **Cliente gerado.** `bundles/postgres/src/generated/prisma` fica fora do git (`src/generated/.gitignore`), como o cliente do kernel antes.
- **Kit de conformidade.** `tests/conformance.test.ts` roda `runStorageConformance` com o harness de `tests/support/harness.ts` sobre um schema migrado por arquivo; fechar uma instância também desconecta o cliente dela, para não esgotar as conexões. `tests/storage-*.test.ts` continuam como evidência direta sobre PostgreSQL.

### Fachadas do core (`bundles/core`)

- **Versão do core.** O core passa a `1.1.0`: os contratos novos em `provides` são uma mudança minor contra a baseline publicada na etapa 1, e a baseline é regenerada.
- **Dependência de `storage`.** A parte host do core importa `parseStreamId` e `checkBatchLimits` de `storage`, para aplicar as mesmas regras de stream e limites dos backends. O pacote entra nas dependências do core e precisa estar no staging e na imagem do host.
- **Registros.** `storage/v1.defineType` repetido pelo mesmo dono com o mesmo JSON Schema e os mesmos índices devolve outro handle, e o tipo sai quando o último é descartado. `settings/v1.register` e `events/v1.register` recusam a segunda definição do mesmo ID com `registration_conflict`.
- **Plataforma.** `doric` passa nas verificações de dono e lê sem validação documentos de tipos que ninguém define. Toda escrita exige o tipo definido, também para `doric`, porque o `put` é validado pelo schema do tipo.
- **Campos de índice.** Um campo com pontos precisa existir no schema zod, atravessando `optional`, `nullable`, `default`, `lazy`, `pipe` (pela saída), união, interseção, `record` e posições numéricas de `array`/`tuple`; `unknown`, `any` e `custom` aceitam qualquer caminho.
- **Streams.** Só o dono do stream (primeiro segmento) ou `doric` lê. O provedor ativo de `events/v1` só ganha a escrita.
- **Espaço nunca gravado.** `entry` responde os defaults do schema com `revision` 0, `generation` 0, `updatedAt` na época (`1970-01-01T00:00:00.000Z`) e a versão de `provides`.
- **Definição registrada.** `get`, `entry` e `set` usam o schema da definição registrada com aquele ID, não o do objeto recebido. Um valor gravado que o schema recusa na leitura é `invalid_output`. Leitura, escrita e assinatura não verificam dono, porque `settings/v1` não define `not_owner`.
- **Assinantes.** A falha de um assinante vai a `doric.diagnostics/v1` como `settings_listener_failed`, no bundle que assinou.
- **Redação em `events/v1`.** O append usa `secrets/v1.redactions(call)`, que carrega as credenciais se preciso, em vez de `view()`: um evento nunca é gravado sem redação, e uma falha de carga falha o append. O corpo passa por `eventJson` e depois pelo `storable` de cada string, como `json()` do kernel; nomes de propriedade são redigidos e, como no kernel, não passam por `storable`.
- **Redação no log.** Strings de registros simples, arrays, `Error` (com `name`, `message`, `stack` e `cause`) e instâncias com propriedades enumeráveis são redigidas numa cópia simples; instâncias sem propriedade enumerável (`Date`, `Map`) ficam como estão, porque o destino não escreve seu conteúdo. `addRedaction('')` é ignorado também na `view()`.

- **Tipos de storage em `core/contracts`.** Além de `CoreHooksV1` e `OpenSettingsCommandV1`, `core/contracts` exporta os tipos de storage do próprio core, `core.settings/v1` e `core.settings-generation/v1` (com `settingsGenerationId`), para que as migrações de dados e seus testes usem as mesmas definições. Isto amplia a regra "`core/contracts` exporta só ..." dos documentos de conceito.
- **Dono das definições.** `settings/v1.register` e `events/v1.register` conferem o namespace, a presença do ID em `provides` e o tipo do objeto recebido (`defineSettings`/`defineEvent`), mas não o tipo do descritor declarado: o catálogo ainda não carrega o tipo de cada contrato de `dist/contracts.json`. A conferência entra quando o loader publicar esse tipo no catálogo (etapa da instalação externa, quando descritores deixam de ser confiáveis por construção).

### Kernel `agents/doric` (etapas 2 a 4)

- **`host-config` por instância.** `createHostConfig()` devolve o bundle, a definição do espaço e `track`; a refinação que exige credenciais armazenadas lê a `view()` daquele host, sem estado de módulo, para que vários hosts no mesmo processo (testes) não se misturem.
- **Refinação também na leitura.** Como a fachada aplica o schema registrado ao ler, o kernel carrega as credenciais antes da configuração (a ordem do boot). Uma configuração gravada que nomeie credencial ausente seria `invalid_output` em `configuration_activation`; isso não ocorre, porque o documento migrado vem de linhas com FK e toda escrita passa pela refinação.
- **Referências protegidas.** `referencedCredentialIds` devolve os campos `secret` dos providers, `gitCredentialId` e `githubCredentialId`, exatamente o que as FKs protegiam; um `secret` em `tools` continua sem proteção, como antes.
- **`track` na carga.** `ConfigStore.load()` informa a configuração carregada ao `host-config`; depois, a assinatura de `settings/v1` mantém a referência atual.
- **Adaptador de credenciais.** `credential_invalid` vira `invalid` com a mensagem, `credential_missing` vira `missing`, `credential_name_taken` vira `conflict`, `credential_kind_immutable` vira `immutable` e `credential_storage_unavailable` vira `MissingKeyError` (a classe fica em `credentials/service.ts`); outros erros propagam.
- **Boot.** `startBundles` aceita `embedded` além do adaptador; `bundleCount` exclui todos os embutidos e passa a 5. No encerramento, o `$disconnect` acontece em `platform.stop()`, antes de `pool.dispose()`.
- **Dependências.** O kernel depende de `postgres`; `@prisma/client` sai; `@prisma/adapter-pg` fica só como devDependency das fixtures de teste, e `storage` como devDependency. O `.gitignore` da raiz passa a ignorar `bundles/postgres/src/generated/prisma/`.
- **Testes do kernel.** `tests/helpers/platform.ts` sobe o core instalado de `dist/bundles` com a fundação embutida `postgres-test` (ID diferente do `postgres` instalado, para não gerar `duplicate_id`). K-1 compara a leitura inteira como string e a resposta de `replace` como string com `updatedAt` substituído, porque o relógio difere entre as duas escritas. Os testes de cifra de `credentials.test.ts` viram testes do adaptador sobre PostgreSQL (envelope `v1:`, nonce novo a cada escrita, chave em branco igual a nenhuma, chave mal formada recusada na carga).

### Revisões cruzadas e notas para as próximas etapas

- **Registros por geração (X-10).** `storage/v1.defineType`, `settings/v1.register`/`subscribe` e `events/v1.register` passam a ser chaveados por `(id, geração da chamada)` na etapa 4 (D4-11): o mesmo dono registra o mesmo ID uma vez por geração, e descartar a geração N não remove o registro de N+1. Em processo único toda chave tem geração 0, que é o comportamento desta etapa.
- **Dono da configuração (X-6).** O `host-config` continua no kernel e, na etapa 6, ganha o contrato `host-config/v1` (`current`, `replace`), com a referência em `runtime/contracts`; o core não recebe configuração de produto. A divisão do espaço `host-config.configuration/v1` entre os donos (providers, `direct`, `git`, tools) passa da etapa 6/7 para a etapa 10.
- **Etapa 4.** Métodos só locais (`settings/v1.get`/`set`/`entry` com objeto de definição, `secrets/v1.view` e `registerReferences`, `postgres.database/v1.client`) não atravessam o envelope: as definições passam a IDs registrados por RPC, e os métodos só do kernel ficam no processo do kernel, onde rodam fundação e core.
- **Etapa 5.** O `runtime` adota `runtime.thread.events/<id>`, acompanha o feed e acrescenta `NOTIFY`; usa `secrets/v1.redactions()` em vez de `view()`, porque roda no processo filho; leva a política de disco; e deixa de usar `postgres.database/v1` para Thread e Project.
- **Etapas 6/7.** Exportação e importação offline em NDJSON; a importação incrementa `storageGeneration`.

### Pontos abertos

- Do item "Etapa 2" da etapa 1: a saída de `events/v1.append` está em S-10; a regra dos backends em `providers` (D-20) decorre da verificação existente de que o core exige um contrato que nenhuma fundação ativa fornece (teste A-4); `hostId` está em S-5.

## Etapa 4 — validação de tools (4-WP4-C)

- `BoundTool.check(payload)` é síncrono (`input.safeParse` + mapeamento de issues existente) e `toTool` o propaga; `Tool.check?` é opcional e pode devolver uma promise (tools remotas). O `ToolPayloadCheck` do pacote `tool` é estruturalmente igual ao de `bundle/contracts` e usa `ToolIssue`.
- `ToolStorage.validate` devolve `ToolCall | Promise<ToolCall>`: só é assíncrono quando o `check` da tool devolve uma promise. Tools sem `check` ou com `check` síncrono continuam no caminho síncrono; `execute` delas continua validando duas vezes como hoje, e o de tools assíncronas valida uma vez e executa com `check.data`. Falhas assíncronas geram o mesmo `invalid_payload` (mensagem `Tool call payload failed validation: <nome>`, issues do `check`).
- No `agent`, `validatedCalls` é assíncrono: todas as calls são parseadas primeiro (como hoje) e validadas em ordem, parando na primeira falha, dentro do mesmo `try`; eventos, mensagens e contador de reparos não mudam.

## Etapa 4 — costuras do runtime (4-WP4-A2)

- `callGeneration`/`generationOf` são exportados por `bundle/contracts` (ajuste aditivo em `contracts/index.ts`). Toda call criada pelo runtime recebe a propriedade não enumerável; sem call pai vale `generation ?? defaultGeneration ?? 0`, e `dispatch` passa `runtime.operationGeneration ?? 0`.
- `LayeredDirectory.register` grava na camada base: os bundles do kernel registram pela `activeView` e seus providers precisam estar no `kernelDirectory`. `active` devolve o provider da base antes do overlay; `setOverlay` emite `removed` dos records do overlay antigo e `added` dos novos para cada assinante.
- O marcador `x-doric-local` passa a ser posto no lugar de cada valor local que tem codec: `disposable` para o `disposableSchema` básico (por identidade) e `callback`/`object` quando o autor declara `.meta({ 'x-doric-local': '<tipo>' })` no schema. Se algum valor local de um membro não tem codec, o membro inteiro continua `{ "x-doric-local": true }`. `functionSchema()` continua sem codec declarado, então os inputs de hooks e tools continuam `true`; as saídas `disposableSchema` passam a `disposable`.
- Tuplas geradas levam `minItems` (itens iniciais não opcionais na direção do membro, então um item com `default` é opcional no input e obrigatório no output) e `maxItems` quando não têm rest. Os baselines `contracts.published.json` de `core` e `postgres` foram regenerados pelo comando `baseline` da build. Os outros baselines não mudaram.
- `contractDocument`, `RecordedContract`, `ContractDocument`, `JSON_SCHEMA_DIALECT` e `schemaPath` foram movidos para `runtime/json-schema.ts`. `build/schemas.ts` os reexporta.
- Opções de `activateEnvironment`: `preActive` entra no conjunto de ativos da checagem de dependências. `hooksProvider: 'remote'` define `AppHooksV1` antes do laço, e cada bundle do laço é observado. `settle` roda depois de `activate` (a rejeição recebe o código que a mesma recusa teria em processo: uma recusa de registro vira `registration_failed`/`cardinality_mismatch`, qualquer outro erro vira `activate_failed`) e de novo depois de `afterActivate` (`registration_failed`). `isRegistrationConflict` é exportado por `runtime`.

## Etapa 4 — core ciente de geração (4-WP4-D)

- A partição segue D4-11 com `g = generationOf(call)`; o helper `bundles/core/src/host/partition.ts` concentra a regra: uma leitura vê a partição do kernel e a geração `g` (ou a ativa, lida de `doric.catalog/v1.get(call)`, quando `g === 0`); um registro com `g === 0` colide com toda entrada viva, e um com `g > 0` colide com o kernel e com a própria geração. O catálogo só é lido quando há entrada de geração diferente de 0, então o modo de um processo não faz leitura nova.
- `RegisteredTool`/`RegisteredSkill` devolvidos por `list` não ganham o campo `generation`: ele fica numa entrada interna, para que a forma pública (e `GET /tools`) não mude.
- `tools/v1.list` passa a aceitar `call?: CallArg` no tipo (`contracts/basic/tools.ts`, mudança só de tipo, sem efeito no schema publicado), para que `skills/v1.register` resolva `allowed-tools` com `list(call)` na geração de quem registra.
- `hooks/v1`: a definição de um contrato de bundle fica por `(id, g)`; contratos `doric.*` têm um estado único. Os handlers ficam numa lista por ID com a geração de quem registrou, e `execute` filtra pela visão da chamada antes de ordenar por `catalog.order` e `seq`. `whenDefined` observa a definição da própria geração do chamador; um bundle do kernel (`g === 0`) observa só definições do kernel, o que é coerente com a regra de residência (o kernel não chama contratos de geração durante `activate`).
- Fachadas X-10 (`storage/v1.defineType`, `settings/v1.register`/`subscribe`, `events/v1.register`): entradas por `(id, g)`. Em `settings/v1`, a assinatura pertence à entrada da sua geração (o `dispose` de uma geração nunca remove a de outra), mas uma escrita notifica os assinantes de todas as entradas vivas do mesmo ID, porque um único documento `core.settings/v1` guarda o espaço para todas as gerações.
- Os testes de visão chamam os métodos dos serviços do core diretamente, com chamadas fixadas por `createHopCall({ generation })` e um `Services` falso (catálogo, diagnósticos e backend em memória), porque o runner de geração (WP4-B) ainda não existe. A evidência de ponta a ponta fica com WP4-E.

## Etapa 4 — envelope (4-WP4-A1)

- O código do envelope fica em `packages/bundle/src/runtime/envelope/` e não é reexportado por `runtime/index.ts` (arquivo da A2): o processo (4-WP4-B) o importa pelo caminho relativo do pacote. O teste de segurança para browser cobre `runtime/envelope/index.js` (só `zod`).
- Tabela de codecs por `(contrato, método)` em `envelope/values.ts`, não por identidade de schema em `contracts/basic/common.ts`: `functionSchema()` cria um schema novo a cada uso. Métodos básicos e de plataforma sem entrada na tabela seguem uma regra fixa: sem valor local, atravessam; entrada serializável e saída `disposableSchema`, registro otimista; qualquer outro valor local, `local_only`. Contratos de bundle usam os marcadores `x-doric-local` dos schemas (`true` recusa o método). Um teste enumera todos os métodos básicos e de plataforma.
- Recusados com `local_only` na etapa 4: `tools/v1.list`, `secrets/v1.registerReferences` e `view`, `models/v1.resolve`, `models.provider/v1.create`, `commands/v1.register`, `ui/v1.*` e `navigation/v1.register`/`subscribe` (callbacks síncronos do cliente, etapa 8).
- Callbacks atravessam em três modos: `async` (handlers de hooks e callbacks de contratos de bundle; devolve a promise do `invoke`), `listener` (`settings/v1.subscribe`; dispara sem esperar, falha vai para o diagnóstico como `listener_failed`) e `scoped` (`hooks/v1.whenDefined`). No `scoped`, o proxy do kernel é síncrono: abre uma execução com um handle próprio e devolve uma limpeza que libera esse handle. A geração roda o callback em um escopo filho do escopo atual do principal; ao liberar, descarta esse escopo (soltando os registros feitos no callback) e então chama a limpeza do callback.
- Exatidão nas bordas: o lado que tem a definição real (o remetente) envia o resultado do `safeParse` quando ele passa e o valor original quando falha, para que a recusa e a mensagem continuem sendo as do core. Na volta, refaz o parse quando ele passa. Vale para entradas de hooks (`execute` e o handler registrado), saídas `transform`, valores de `settings/v1` (`get`, `entry`, `set`, entradas de `subscribe`) e payloads de `events/v1.append`.
- Espelhos no kernel: contratos de hooks `doric.*` conhecidos viram o objeto real; os demais são `defineHooks` com validadores JSON Schema, guardados em cache por forma no link. Eventos e tipos de storage viram `z.looseObject({})` com o validador; settings viram só o validador. Risco: a introspecção do core sobre o schema de um tipo de storage (campos de índice, `fingerprintOf`) vê o espelho, então um índice com campo inexistente definido na geração não é recusado no kernel. Nenhum bundle de geração define tipos de storage hoje.
- Invariante de geração no kernel: uma `call`/`invoke` que chega pelo link da geração N deve trazer N ou uma geração que o próprio kernel já enviou por esse link (por exemplo 0, quando um callback chamado a partir de uma chamada não fixada do kernel chama o kernel de volta). Qualquer outra recebe `protocol_error`.
- Um `cancel` que chega depois do prazo da chamada aborta o sinal do provider com `TimeoutError`, como em processo, porque o sinal do remetente abortou pelo prazo.
- Registros otimistas: `ProcessLink.activating(bundleId)` marca a ativação. Enquanto ela dura, as recusas ficam guardadas para `settle(bundleId)`; fora dela, viram `registration_failed` no diagnóstico do processo. Os handles exportados para a operação (tool, callback) são liberados quando o registro é descartado ou recusado.
- No fechamento do link, os ouvintes de `onClose` rodam antes da rejeição das chamadas pendentes (`generation_lost`, detalhes `{ generation, incarnation }`). Depois disso, o lado que fica descarta tudo o que o outro lado registrou nele. `registerRemote` remove o record remoto do diretório quando o link fecha.
- Objetos `object`: o handle importado é um proxy que só responde ao próprio handle (`then` e `dispose` leem `undefined`, para não ser tomado por thenable ou Disposable). Qualquer outra leitura lança `local_only`, e ao voltar ao processo de origem o handle vira de novo o objeto original.
- `ControlMessage.init` é tipado como `unknown`, e quem o valida é o runner (4-WP4-B), dono de `GenerationInit`.

## Etapa 4 — camada de processo Node (4-WP4-B)

- Residência (D4-1, revisada por X-8): `process/partition.ts` põe no kernel `foundation`, `core` e todo bundle embutido; `others` instalados vão para a geração. A ordem publicada é a do kernel seguida da da geração (D4-2). O kernel ativa sua partição com `preActive` = bundles agendados da geração, então a dependência de um bundle do kernel em um provider da geração é satisfeita pelo catálogo. `kernel_requires_generation` não é emitido: com a revisão, ele só valeria quando nenhum bundle habilitado fornece o contrato, caso que o resolvedor já trata com seus próprios códigos.
- Pendente (G-11): a espera dos stubs do kernel por uma geração ativa (`onActive`) não foi implementada; com nenhuma geração ativa, `dispatch` responde `unavailable` como hoje. Não há consumidor no kernel na etapa 4.
- O contador de gerações é por kernel (boot = 1, cada `publish` aceito = +1), não o contador global do processo de `startHost`. Um `publish` recusado (`kernel_restart_required`) não consome número.
- `kernel_restart_required` compara uma assinatura da partição do kernel: ID, versão, fase, estado e origem das entradas do kernel, os providers do kernel por contrato e o motivo de recuperação.
- `doric.generation/v1` (API mínima, `describe()`/`hold(execution)`) é um contrato de plataforma em `contracts/platform.ts`, fornecido pelo kernel e anunciado à geração como provider remoto (sem novas mensagens de controle). `describe` e `hold` respondem pela geração da operação (`generationOf(call)`, ou a ativa quando 0). `acquire` do gerenciador e `hold` usam a mesma contagem (`holds` por geração, `ExecutionRef | { window }`). A drenagem para quando não há holds; chamadas pendentes não entram no critério (o `ProcessLink` não as expõe), e toda execução em curso já tem um hold.
- `doric.catalog/v1`, `doric.diagnostics/v1` e `doric.bundle/v1` são locais no processo da geração. O catálogo vem de `init` e é trocado pelas mensagens `catalog`: o kernel envia a cada processo vivo o snapshot da própria geração dele sempre que uma geração fica ativa. O diagnóstico local junta o store do processo com os estados do catálogo para os bundles do kernel; `report` grava no store local e o processo envia o snapshot (`diagnostics`) ao kernel, que o mescla na visão daquela geração. O diagnóstico de uma geração no kernel tem os bundles do kernel, os da geração pelo último snapshot recebido e os erros dos dois em ordem de horário.
- O runner registra os providers locais da plataforma direto no diretório interno; `AnnouncingDirectory` anuncia (`provide`/`unprovide`) só records locais que não são `doric.*`. Os providers do kernel chegam em `init.kernelProviders`, exceto os três locais acima.
- Barreira de ativação: `activateEnvironment` ganhou a opção `onPrincipal(entry, principal)` (arquivo da A2, mudança aditiva), chamada logo após criar o principal. O runner a usa para abrir `link.activating(id)` (fechado quando o próximo bundle começa ou quando o laço termina) e para que callbacks `scoped` encontrem o principal já durante `activate`. Um teste confirma que a recusa de uma tool duplicada na geração quarentena o bundle com o mesmo motivo do modo de um processo.
- O runner Node relê o manifesto do bundle (`readInstalledBundle`) no `afterActivate` para obter as tools e skills de manifestos v0, em vez de carregar isso no `init`.
- Falha de início: após `startAttempts` processos que saem antes de `ready`, a geração fica `failed`, seus bundles aparecem `quarantined` com `generation_failed` (`Generation N could not start: its process exited before it was ready (code X, signal Y; ...).`), o kernel registra `Bundle quarantined` para cada um e ativa uma visão vazia (só a partição do kernel), disparando `onActive(N)` para que `acquire` resolva. Em `publish`, a falha deixa a geração ativa como está e devolve `failed`.
- Queda de uma geração pronta: os ouvintes `onLost` rodam dentro do fechamento do link, antes das rejeições `generation_lost`; os holds da incarnação perdida são descartados (o `release` posterior não faz nada). Uma geração ativa é recriada com `incarnation + 1` e, ao ficar pronta, dispara `onActive` e `onGenerationReadyHook`; uma geração drenando apenas para. O kernel registra no diagnóstico `generation_lost` (e `generation_failed` quando desiste).
- Em modo de recuperação o kernel não inicia gerações (como hoje, os bundles restantes ficam inativos); `acquire` então espera, abortável pelo sinal.
- `ajv@8.20.0` (já no lockfile) virou dependência direta de `bundle` (`package.json` e a entrada `packages/bundle` do `package-lock.json`); a implementação é `process/ajv.ts`, com cache por JSON canônico.
- A tabela de `tests/values.test.ts` (A1) ganhou `doric.generation/v1` (`describe` atravessa; `hold` é otimista com `Disposable`).

## Etapa 4 — integração do host (4-WP4-E)

- `startBundles` passa a usar `startKernel` (com `errorClasses: [ToolErrorObject]`) e devolve `catalog()` (tools e skills da geração ativa) e `acquire(execution, signal)`, que fixa o prompt na geração ativa e devolve um `BundleLease` (`call`, `tools(call)`, `skills(call)`, `release`). As tools são lidas a cada chamada de `ToolsV1.list`; as skills, que são assíncronas, ficam em cache por geração e são relidas em `onActive`, porque `GET /tools` e `requireToolConfigs` precisam de leitura síncrona.
- O `Generation` da configuração perdeu `catalog`. `ConfigService` ganhou `catalog()`, e `GET /tools` e a validação de `replace` leem a geração ativa por ele. O executor Direct adquire o lease antes de `attach` e o libera depois do `release` do adapter; as tools e skills do prompt vêm do lease.
- Supressão de perda de geração: um `tool.failed` cujo erro é `handler_failed` com causa `generation_lost`, com o sinal já abortado, não é gravado. O executor grava o histórico nesse instante e não grava de novo no `finally`, porque o `release()` do agente responderia à chamada com "Tool call did not complete…". Assim o histórico fica como numa queda do host: a chamada sem resultado, que o run retomado responde com o resultado de chamada interrompida (Q10). O desenho supunha que o `finally` já guardaria a chamada pendente; não guarda.
- `pauseForGenerationLoss` é síncrono e não pega a trava do projeto: o `onLost` roda antes da rejeição das chamadas pendentes, e esperar a trava deixaria a rejeição chegar com o sinal ainda não abortado. `held` também é verificado no laço de `run`, não só em `start()`, para que o mesmo laço não pegue o próximo prompt da fila depois da pausa.
- Esgotamento em `resumeHeld`: usa `ThreadStore.failPrompt` (os mesmos eventos, resultado e resultado delegado ao pai que o boot grava), depois publica os eventos novos do Thread e do pai e põe na fila do pai, em memória, a entrada que `failPrompt` aceitou para ele.
- A fiação `onLost`/`onActive` fica em `recoverGenerationLoss` (`bundles/boot.ts`), usada por `index.ts` e pelos testes. Quando a geração perdida não era a ativa (estava drenando), a retomada começa logo, sem esperar `onActive`. As operações de recuperação (`suspendForGenerationLoss`, `resumeAfterGenerationLoss`) são expostas pelo tipo `GenerationRecovery` de `workspace/service.ts`, sem alterar `WorkspaceService` em `types.ts`.
- Paridade E4: o teste "a Host control failure fails the tool call with that same error as its cause" passou a comparar classe, nome e mensagem da causa, não a identidade do objeto. A tool roda na geração, então a causa atravessa duas fronteiras de processo e chega reconstruída. O que é observável (o `ToolErrorObject` `handler_failed` com a causa da recusa do Host) não muda.
- Fixtures: `tests/fixtures/generation-bundles/{probe,crash-on-activate}` são JS puro (manifesto v1, `contracts.json`, `package.json` com `type: module`). Os testes copiam `dist/bundles` e as fixtures para raízes temporárias em `agents/doric/dist-tests`, para que `bundle`, `tool` e `zod` resolvam pelo `node_modules` do repositório, como nos bundles preparados. O gate da tool `probe` usa arquivos com caminho absoluto (`<gate>.started` com o pid, `<gate>.release`).

## Etapa 4 — decisões de desenho (D4-1 a D4-18)

As seções 4-WP4-\* acima detalham a implementação; esta lista registra as decisões do desenho da etapa e onde a implementação as ajustou.

- **D4-1 Residência.** Fundação, core e bundles embutidos ficam no kernel; `others` instalados vão para o processo da geração. Ajuste (X-8, 4-WP4-B): `kernel_requires_generation` nunca é lançado; o kernel ativa com `preActive` = bundles da geração, e a falta de provider continua com o resolvedor.
- **D4-2 Ordem publicada.** Ordem do kernel seguida da ordem da geração.
- **D4-3 Respawn.** Mantém o número da geração; `incarnation` conta os processos.
- **D4-4 Geração da operação.** Herdada ao longo da cadeia de chamadas (`generationOf`, `callGeneration`, campo `generation` do envelope); 0 = kernel ou não fixada.
- **D4-5 Envelope.** Acrescenta `generation`, `provider`, `oneway`, `invoke` e `release`; tipos de stream reservados; plano de controle separado.
- **D4-6 Semântica de chamada.** `cancel` é consultivo (sem rejeição local); `invoke` não é um hop; o kernel sobrescreve `caller.generation` pelo link.
- **D4-7 Erros.** Codec com ordem das propriedades próprias, classes registradas, protótipos sintéticos por nome e `stack` copiado; `code: 'internal'` é só metadado.
- **D4-8 Valores locais.** Só atravessam em contratos básicos e de plataforma, por tabela fixa de codecs; métodos locais definidos por bundles são `local_only`.
- **D4-9 Registros síncronos.** Otimistas, com barreira de ativação (`settle`) que preserva os códigos de quarentena.
- **D4-10 Schemas.** Validação JSON Schema com ajv 2020 atrás de `SchemaValidators`; tuplas com `minItems`/`maxItems`; baselines regenerados.
- **D4-11 Core por geração.** Tools, skills e hooks particionados pela geração da operação; leituras de catálogo e diagnóstico recebem a call.
- **D4-12 Troca.** Ativa N+1, troca, dispara `onGenerationReadyHook`, drena N pelos leases sem prazo; mudança no kernel exige reinício (`kernel_restart_required`). A drenagem espera holds zerados e nenhuma chamada em voo (`ProcessLink.inFlight`: saídas pendentes + entradas não respondidas); `onIdle` reavalia a parada.
- **D4-13 Gatilho.** Nenhum gatilho externo de geração na etapa 4; `publish()` é interno ao kernel.
- **D4-14 Queda.** `onLost` antes das rejeições; só a geração ativa é recriada; 3 tentativas de início; depois, quarentena `generation_failed` e visão vazia.
- **D4-15 Execução de tools.** Cada tool roda no processo do seu bundle; o kernel usa `RemoteTool` com `check` exato assíncrono; `tool`/`agent` aceitam validação assíncrona.
- **D4-16 Perda com prompts fixados.** Os prompts pausam com `host_restarted`, os Threads ficam retidos e retomam com o orçamento e a ordem do boot. Ajuste (4-WP4-E): retomada imediata quando a geração perdida estava drenando.
- **D4-17 Desktop.** Reusa `runGeneration`/`ProcessLink` com `hooksProvider: 'local'`; o main faz o papel de kernel só com providers de plataforma (etapa 8).
- **D4-18 Prisma.** Nenhuma mudança de schema ou migração SQL na etapa 4.
- **Gate E2E.** A imagem `docker build -f agents/doric/.Dockerfile --target docker-runtime` sobe sem mudança no `.Dockerfile` (o kernel continua PID 1 e recebe o SIGTERM sozinho). Três execuções do harness (21/21 API, 18/18 UI na primeira): a UI é idêntica ao baseline; na API resta só a diferença de `stack` em `17-failures-and-http`, que já existia nas etapas 1 e 2/3. Em uma das três execuções, `14-delegation` mostrou a corrida entre o fim do prompt do pai e o resultado do filho (o resultado chegou com o pai ainda ocupado: `prompt.accepted{queued: true}` e `prompt.queued`, e por isso `lastSequence` + 1 em `15` e `18`). Os dois desfechos são comportamento atual; a latência do IPC (R8) torna o segundo possível, e nada foi alterado para escondê-lo.
