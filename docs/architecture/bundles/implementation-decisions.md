# Decisões de implementação da migração para bundles

**Estado:** registro das decisões tomadas durante a implementação da [arquitetura de bundles](../bundles.md). Resolve os pontos que os documentos de conceito deixam em aberto ou contraditórios. Quando um documento de conceito e este registro divergirem, este registro vale para o código; `GROUNDING.md` continua sendo o contrato do comportamento implementado e é atualizado à medida que cada fase entra.

## Princípios

- **Paridade 1:1.** A migração preserva o comportamento atual observável, inclusive peculiaridades documentadas no inventário (por exemplo `POST /threads/:id/interrupt` ignora `promptId`, a seção Tools das settings não chega ao host, só a seleção de Thread persiste no renderer, o app só tem tema escuro, `alwaysAvailable` não filtra tools nem skills, a mensagem `resume_exhausted` em português). Nenhuma funcionalidade nova de produto entra; correções de bugs ficam fora desta migração.
- **API mínima.** Quando os documentos não nomeiam um método necessário para preservar uma funcionalidade atual, o método entra com o menor formato que cobre essa funcionalidade e é marcado aqui.
- **Etapas combinadas.** As etapas da [migração](./migration.md) são cortes de revisão. As etapas 5, 6 e 7 são implementadas juntas: `runtime` e `direct` nascem sobre os tipos e streams genéricos de `storage/v1`, e a migração de dados converte as tabelas atuais. A etapa 2 entrega diretamente as primitivas genéricas da etapa 3 no `postgres`.
- **Etapa 11.** Instalação externa de bundles, assinatura e consentimento continuam adiados. `notifications` e `transport` entram porque correspondem a funcionalidades atuais.

## Estrutura de pastas e pacotes

| Decisão                         | Valor                                                                                                                                                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Pastas das partes               | `host/`, `desktop/` (ambiente `desktopMain`), `client/`, `contracts/`, `skills/` dentro de `bundles/<id>/src` (fonte) e `dist` (artefato), seguindo a convenção do manifesto. Os exemplos com `desktopMain/` são ilustrativos.                         |
| Nome do pacote npm de um bundle | Igual ao ID do bundle (`core`, `files`, `git`, `chat`...). Os pacotes de biblioteca `packages/docker` e `packages/firecracker` passam a se chamar `docker-sandbox` e `firecracker-sandbox` para liberar os nomes dos bundles `docker` e `firecracker`. |
| `<bundle>/contracts`            | Subpath `./contracts` no `exports` do pacote do bundle; no navegador, entrada do import map `"<id>/contracts"` para o artefato da geração.                                                                                                             |
| `bundle/contracts`              | Subpath browser-safe de `packages/bundle`; nenhum import de Node alcançável a partir dele. Contém também os schemas zod dos contratos básicos (janelas, menus, ui, navegação, regiões), para que provedores substitutos validem igual.                 |
| Runtime de serviços             | O diretório de serviços, o dispatcher e a propagação de `call` ficam num subpath browser-safe interno de `packages/bundle` (`bundle/runtime`), usado pelo loader do host, pelo `desktopMain` e por `packages/desktop`. Bundles não o importam.         |
| Pacotes novos                   | `packages/storage` (tipos do protocolo e kit de conformidade) e, após a consolidação, `packages/desktop` (runtime client do loader, helpers de leitura, componentes shadcn, tokens, Tailwind e tema).                                                  |
| Build das partes                | `host/` com `tsc` como hoje; `client/` e `desktop/` com esbuild em ESM, deixando externos os pacotes compartilhados e os `<id>/contracts`. CSS de cada bundle client gerado com Tailwind v4 e servido como `client/styles.css`.                        |

## Contratos e serviços

- **Ambiente e cardinalidade antes do código.** O build gera, junto com os JSON Schemas, um descritor por bundle (`dist/contracts.json`) com cada contrato fornecido, seu ambiente, cardinalidade e tipo (serviço, hooks, evento, comando, settings, storage). O loader usa o descritor antes da ativação e confere em `provide`/`register`.
- **`requires` por ambiente.** Uma entrada de `requires` restringe a parte de um ambiente quando algum bundle habilitado fornece o contrato nesse ambiente. Partes `client` também são satisfeitas por provedores do `host` e do `desktopMain` pela ponte. Entradas sem provedor alcançável são dependência ausente.
- **Cardinalidade.** Tabela fixa em `bundle/contracts` para os básicos (`many` só para `models.provider/v1`); para os demais, o descritor do bundle dono. `use` de um contrato `many` lança `ContractError` com código `many_contract_use`.
- **`whenAvailable`.** Callback `(api, provider: { bundleId, version }) => void | Cleanup`. O que o callback registra é descartado quando aquele provedor desativa.
- **`use` fora de `requires`.** Lança `ContractError` `undeclared_requirement`, exceto contratos `doric.*`, contratos que o próprio bundle fornece e o core usando contratos básicos.
- **Escopo.** Escopo efetivo = `call.scope` do pai mesclado com o escopo de `use` (chaves de `use` prevalecem); o dispatcher sobrescreve `windowKey` nas chamadas que saem de uma janela.
- **`deadline` e `trace`.** `deadline` em milissegundos de época, `0` significa sem prazo. `trace` é `{ traceparent: string }` no formato W3C; cada salto cria um span filho com o mesmo trace ID.
- **Erros.** `bundle/contracts` exporta `ContractError` (`code`, `message`, `details?`). Valores lançados sem `code` viram `internal`; falhas de validação viram `invalid_input` e `invalid_output`.
- **Métodos síncronos.** Serviços só locais (com entradas `z.custom` ou funções) devolvem o resultado do `execute` diretamente, síncrono ou não; o dispatcher se recusa a levá-los pela ponte.
- **Hooks.** Tipos `observe`, `transform` e `decide`. `execute` aguarda os handlers `observe` em sequência, cada um com o prazo padrão; falha de `observe` vai ao diagnóstico. Só o bundle que lista o contrato de hooks em `provides` (ou a plataforma, para `doric.*`) pode chamar `define`; `define` é idempotente por dono.
- **Ordem entre bundles não relacionados.** Ordem topológica por dependência com desempate lexical pelo `id`; a mesma ordem vale para handlers de hooks.
- **Entradas dos hooks do app.** `onActivateHook`/`onDeactivateHook`: `{ bundleId, version, generation, environment }`; `onHostReadyHook`, `onAppReadyHook`, `onAppActivateHook`, `onBeforeQuitHook`: `{}`; `onGenerationReadyHook`: `{ generation }`; `onConnectionChangedHook`: `{ connected }`. Todos `.strict()`.
- **`log/v1`.** `debug | info | warn | error(message, fields?)`, sem lançar e sem esperar resposta.
- **`provide` seguido de `use` no mesmo `activate`.** `provide` registra de forma síncrona; a plataforma chama `define(AppHooksV1)` depois que o `activate` do provedor de `hooks/v1` termina.
- **Comandos.** Comandos são contratos versionados e entram em `provides`. Tipos de bloco de projeção não entram.
- **S-1 Refinamentos das etapas 2 e 3.** Antes de qualquer baseline publicada, as etapas 2 e 3 refinam, sem evento de semver, os formatos básicos de `storage`, `secrets`, `settings`, `events` e do catálogo (`CatalogSnapshot.storage`, `HostPlatform.storageIdentity()`) e acrescentam os códigos `revision_conflict`, `sequence_conflict`, `unique_conflict`, `limit_exceeded`, `unknown_type`, `invalid_index_value`, `invalid_stream`, `unknown_settings`, `settings_missing`, `settings_conflict`, `unknown_event`, `invalid_scope` e `credential_*`. Core e `postgres` usam esses schemas exatos (D-12).
- **S-6 Regras dos campos de credencial.** `credentialFields`, `credentialFieldsSatisfied`, `credentialFieldsMessage` e os tipos dos campos ficam em `bundle/contracts`; o kernel (schemas das rotas) e o core (validação) importam de lá, então a regra continua uma só.
- **S-7 `secrets/v1.view()`.** Visão local e síncrona do cache do provedor (`list`, `redactions`, `addRedaction`), que nunca atravessa a ponte. `secrets/v1.redactions(call)` (API mínima, serializável) devolve a mesma lista de redação a quem está fora do processo (revisão cruzada X-4).
- **S-8 Referências no lugar da FK.** `secrets/v1.registerReferences(fonte)` (API mínima, local): `delete` responde `referenced` enquanto uma fonte registrada nomeia a credencial, e é conferido primeiro. `settings/v1.set` e as escritas de `secrets/v1` passam por uma única fila de escrita do core, então uma configuração nunca nomeia uma credencial removida por um delete concorrente. A fila em processo substitui a transação Serializable da configuração; vale a suposição existente de um processo de host por banco, da qual o cache de credenciais já dependia.
- **S-10 `events/v1`.** Grava em `runtime.thread.events/<threadId>` (`threadEventsStream`) o envelope atual, `threadEventEnvelopeSchema` (`projectId`, `threadId`, `promptId`, `type`, `event`); `sequence` e `createdAt` são os da entrada do protocolo, e esse é o único formato desse stream também para o `runtime` (X-5). O corpo leva `type`, a redação roda antes de gravar, o escopo da chamada precisa nomear project, Thread e prompt (`invalid_scope`) e só o dono do evento registrado faz append (`not_owner`). Nenhum bundle publicado registra evento até a etapa 7 (teste E-6), porque um append direto contorna o agregado do `runtime`.
- **S-12 `postgres.database/v1` provisório.** `connect()` e `client()` (local) e o subpath `postgres/prisma` (cliente gerado e `createDatabase`) existem só para o kernel, cujas tabelas de Project, Thread, eventos e uso continuam no SQL atual até a etapa 7.

## Composição e boot

- **Arquivo de composição.** O host lê a composição de `DORIC_COMPOSITION` (caminho de um JSON) e, sem a variável, da composição padrão distribuída com o host (`agents/doric/composition.json`). Formato: `{ "core": "core", "enabled": [...], "providers": { ... } }`, validado por zod em `packages/bundle`. Os bundles instalados são lidos de `DORIC_BUNDLES_PATH` (padrão: o diretório `dist/bundles` do host).
- **Fundação por ambiente.** Um bundle escolhido em `providers` é fundação só nos ambientes em que fornece o contrato escolhido; nos outros, ativa com os demais. Bundles da fundação que substituem uma fachada do core (`events/v1`, `settings/v1`, `models/v1`) podem exigir `storage.backend/v1` e `secrets.backend/v1`, que ativam antes dentro da fundação.
- **Gerações.** Contador monótono por catálogo publicado. Bundles do kernel informam a geração em que o kernel os ativou.
- **`hostId` e `storageGeneration`.** O backend `postgres` guarda um registro de metadados reservado com os dois valores; o catálogo os publica (S-5).
- **S-15 Ordem do boot.** `bootstrap → sandbox_pool → bundle_load → database_client → credential_activation → configuration_activation → workspace_reconciliation → network_binding → ready`: só `database_client` muda de lugar, para depois de `bundle_load`. Nenhum `activate` da fundação ou do core faz I/O (cliente, cifra e `declareType` são preguiçosos); o kernel força cada um no estágio que já falhava por ele: em `database_client` só a falta de `DORIC_DATABASE_URL` (o `connect()` do adaptador `pg` não abre conexão, como o `$connect()` de antes); a identidade do storage é lida logo após a carga das credenciais, em `credential_activation`, onde um banco inacessível ou sem migração já falhava, leitura da configuração em `configuration_activation`. Nomes de estágio, textos das mensagens de log e o caminho fatal não mudam; só a ordem das linhas de inicialização segue a dos estágios. `Bundles loaded` passa a contar 5 bundles (entra `postgres`; os embutidos `host-adapter` e `host-config` não contam). No encerramento, o `$disconnect` acontece na desativação do `postgres`, dentro de `platform.stop()`.

## Armazenamento e dados

- **`storage.backend/v1`.** Primitivas genéricas: documentos versionados por tipo e chave com revisão, índices declarados (igualdade, inclusive `null`, e ordenação), streams com sequência e lacunas, `commit` declarativo atômico (puts, deletes, appends, verificação de revisão esperada), feed de commits com cursor, blobs, truncamento de stream e saúde/admissão de escrita. `packages/storage` define os tipos e o kit de conformidade que qualquer backend precisa passar.
- **Dados atuais.** Uma migração offline e idempotente converte Project, Thread, eventos, fila, estado do executor, uso, configuração e providers para tipos e streams dos bundles donos, com leitura de verificação antes da troca. Credenciais continuam no envelope AES-256-GCM sob `DORIC_CREDENTIAL_KEY` e são lidas sem reescrever o segredo.
- **Eventos.** Eventos gravados nunca são reescritos; a etapa 7 copia os eventos para o stream novo com o mesmo tipo e payload. O tipo `prompt.finished` passa a ser lido também como `runtime.prompt-finished/v1`.
- **`settings/v1`.** `register(definição)`, `get(definição)`, `entry(definição)` (S-9), `set(definição, valor, { expectedRevision? })` e `subscribe`. Cada definição é um espaço com `{ value, revision, version, updatedAt, generation }`. Um contador global de geração de configuração preserva a proveniência que os Projects guardam hoje.
- **`secrets/v1`.** `resolve(ref)`, `list`, `describe(ref)` (nunca devolve o segredo), `create`, `update` (ausente mantém, `''` limpa, valor define), `delete` (recusado quando referenciado), `resolveByKind(kind, { exclude? })` e `redactions()`, mais os locais `registerReferences` (S-8) e `view` (S-7). Redação nos logs como hoje.
- **`usage`.** Fica no agregado do `runtime` enquanto não houver participação transacional de outro bundle; o bundle `usage` lê a projeção e fornece a UI.
- **Pressão de disco.** O `postgres` informa medidas e admissão (S-4); quem chama mantém a política atual (limiar de 10%, verificação a cada 3 s, mapeamento de `53100` e `ENOSPC`): o runner do kernel nas etapas 2 a 4 e o `runtime` a partir da etapa 5.
- **S-2 `commit.dropStreams`.** API mínima: remove streams inteiros, para a paridade da exclusão de Thread e Project a partir da etapa 5. Ordem de aplicação num lote atômico, verificada pelo kit: expect → delete → put → dropStreams → truncate → append. O resultado continua `{ position }`; quem escreve com `expect` deriva a revisão nova como esperada + 1 (uma criação com `revision` 0 recebe 1; X-2).
- **S-3 Entradas e truncamento.** O protocolo é dono do `createdAt` de cada entrada de stream (ISO-8601 em ms, UTC, fixado pelo backend no commit) e das marcas de truncamento `{ afterSequence, atSequence }`, que `read` devolve aos leitores afetados (`afterSequence < pedido <= atSequence`). `lastSequence` nunca diminui. Cada commit do feed separa `streams` (appends), `truncated` e `dropped`.
- **S-4 Saúde.** `health` informa medidas: `{ status: 'ok' | 'unavailable', writable, reason?, disk?: { blocks, availableBlocks } }`. `'pressure'` sai do enum, e um disco que não se mede é `unavailable` sem `disk`. `storage/v1.health` entra (API mínima). A saúde do `postgres` mede `DORIC_STORAGE_PATH` sem ida ao banco. Não existe código `storage_full`: erros do banco propagam sem mudança, então `53100` continua reconhecível. A fachada não tem `capabilities()`: recusa com `limit_exceeded` antes de enviar, e `maxBatch` padrão é 10000, para que a exclusão atômica de um Project grande caiba num lote (X-3).
- **S-5 Identidade.** `storage.backend/v1.identity()` cria na primeira chamada o registro reservado com `hostId` (UUID aleatório) e `storageGeneration` 1 e devolve os mesmos valores depois, em qualquer instância. `HostPlatform.storageIdentity()` memoriza a promessa (rejeição não memorizada) e põe a identidade em `catalog().storage`; o kernel a resolve em `database_client`. O contador de gerações de bundle continua por processo; persisti-lo fica para a etapa que precisar dele (a revisão cruzada G-6 o entrega ao desenho da etapa 8).
- **S-9 Espaços de settings.** `settings/v1.entry` (API mínima), porque `GET`/`PUT /config` precisam de revisão e horário. `SettingsEntry` ganha `updatedAt` e `generation`. Cada espaço é um documento `core.settings/v1` com o ID do espaço, e o contador global é o documento `global` de `core.settings-generation/v1`; cada `set` incrementa a revisão do espaço e o contador. Os assinantes rodam de forma síncrona depois do commit, antes de a fila de escrita liberar. Códigos: `unknown_settings`, `settings_missing`, `settings_conflict` e `invalid_input`.
- **S-11 Chaves de índice.** Codificação ordenável em bytes: `null` < `false` < `true` < número < string; números em ordem numérica, strings por bytes UTF-8; empate pelo ID do documento, também em bytes UTF-8 (como `COLLATE "C"`).
- **S-13 Configuração em `settings/v1`.** A configuração passa ao espaço `host-config.configuration/v1`, do bundle provisório embutido `host-config` (kernel). A migração SQL `20261009000000_generic_storage` converte `doric_configuration`, `provider_configuration` e `model_configuration` sem perda, mantendo `revision` e `updated_at` (ms, UTC `Z`) e iniciando o contador global na revisão; verifica a conversão antes de remover essas tabelas e o enum `ModelRole`. Um kind de provider fora de `openai`, `openrouter` e `codex` interrompe a migração (`RAISE`), sem descartar nem converter nada. O UUID `generation` de cada substituição, que ninguém lia, sai; os Projects continuam guardando a revisão. Sem FK, a tabela `credential` fica sozinha: as referências são garantidas pelo S-8 e pela refinação do `host-config`. A migração não se desfaz (política pré-1.0): o operador faz backup antes de `prisma migrate deploy`. A divisão do espaço entre os donos fica para a etapa 10 (X-6).
- **S-14 Posições do feed.** Alocadas sob um lock consultivo de transação, tomado por último no commit, então o feed não tem lacunas e segue a ordem de commit. `NOTIFY` espera um publicador (etapa 5 em diante).
- **S-16 Prisma no `postgres`.** O schema, as migrações (as 17 anteriores sem mudança mais `generic_storage`) e o cliente gerado ficam em `bundles/foundation/postgres`. `agents/doric/prisma.config.ts` continua como ponto de entrada compatível (Compose, imagem, `nx run doric:migrate`). O que o Prisma não expressa (índice único parcial, `COLLATE "C"`) é do SQL da migração, como o trigger e o CHECK de antes; o fluxo é só `migrate deploy`.

## Execução e domínio

- **Acesso ao sandbox pelas tools.** `runtime.lease/v1` expõe as operações do sandbox adquirido para `call.scope.projectId` (exec, arquivos, Git, diff, métricas), respondendo os estados atuais do lease sem adquirir. `files/v1`, `git`, `terminal/v1` e `resources` usam esse contrato.
- **Métodos de `runtime.*`, `terminal/v1` e `files/v1`.** Derivados um a um dos controles atuais de `packages/host` e das rotas atuais de Project, Thread e terminal.
- **Configuração de tools.** Vai para o `defineSettings` do bundle dono e é lida com `services.use(SettingsV1).get(...)` dentro do `execute`.
- **Skills.** O loader descobre `skills/*/SKILL.md` e registra pelo `skills/v1` em nome do bundle; `skills/v1.register(skill)` existe para registro por código; `skills/v1.list()` preserva a ordem dos bundles e a resolução de `allowed-tools` por bundle; `direct` lê skills e tools por `skills/v1` e `tools/v1`.
- **`models.provider/v1`.** `{ kind(): KindDescriptor; listModels(config, call); create(config, secrets, call): LlmProvider }`, espelhando `providerKinds` e `createProviderForKind` de `packages/llms`. `models/v1.resolve({ providerId, model, effort }, call)`.
- **Transporte.** O bundle `transport` monta as rotas REST e os namespaces Socket.IO atuais sobre as operações semânticas dos bundles, preservando caminhos, formatos, códigos de erro e cabeçalhos (inclusive o `Cache-Control: no-store` global). Além disso, o host expõe um endpoint técnico de ponte (`/doric/bridge`, Socket.IO) com mensagens `call`, `result`, `cancel`, `subscribe`, `event` e `unsubscribe`, usado pelo desktop para chamadas a serviços do host, catálogo e download de artefatos por hash.
- **Processos.** No host, o kernel (`agents/doric`) roda transporte técnico, catálogo, fundação e core; os demais bundles rodam num processo filho por geração (`child_process.fork`) com o envelope RPC. No desktop, todas as partes `desktopMain` de uma geração (fundação, core e demais) rodam no `utilityProcess` daquela geração.

## Desktop e UI

- **Preload.** Um único namespace `window.doric.desktop`: `describeWindow()`, `ready()`, `reportFailure(info)`, `onCloseRequested(cb)` com canal de resposta, `onChromeChanged(cb)`, `catalog()`, `call(envelope)`, `cancel(id)` e assinatura de streams. Os canais semânticos atuais saem quando a UI em bundles assume.
- **Import map.** React, ReactDOM, Lexical e `@lexical/*`, Base UI (`@base-ui/react` e suas subpaths, desde 2026-10-17), `desktop/ui`, `zod`, `bundle/contracts` e os `<id>/contracts` da geração. O handler do protocolo renderiza a shell por requisição com o import map da geração e calcula o hash da CSP na mesma resposta.
- **Dev.** Em desenvolvimento as janelas também abrem por `doric://app`; o handler encaminha a shell e os assets ao servidor de desenvolvimento.
- **Privilégios do esquema.** `standard`, `secure`, `supportFetchAPI`, `corsEnabled` e `codeCache`, confirmados no primeiro teste da etapa 8.
- **Janelas.** `open({ key, path })` sempre respeita `path`. O main guarda o último path e os limites de cada chave. No `onAppReadyHook`, o core reabre `workspace` no último path guardado (ou `/`), o que preserva a seleção de Thread entre reinícios; a seleção antiga em `localStorage` (`doric.selection`) é convertida em path uma vez.
- **Gerações no desktop.** Na troca, o novo `utilityProcess` sobe, define `AppHooksV1` e dispara `onGenerationReadyHook` (não `onAppReadyHook`); janelas abertas continuam na geração em que nasceram e recarregam para trocar.
- **Comandos.** O `commands/v1` do client procura primeiro no registro da janela e depois encaminha ao `desktopMain` pela ponte. O main resolve menu e atalho no registro do `desktopMain` e depois na janela em foco. Comandos ligados a menu ou atalho aceitam entrada vazia.
- **Atalhos.** Papéis do menu Editar mantêm aceleradores nativos; os demais atalhos são tratados por um único listener na shell, que recebe do main a tabela efetiva filtrada por `when`. Como hoje o app usa o menu padrão do Electron, o esqueleto do core reproduz esse menu padrão e os atalhos atuais.
- **Lexical.** O `chat` congela o próprio registro de nodes na criação do primeiro editor da janela.
- **Renderizadores.** `registerRenderer({ blockType, elementTag })` estrito; ações de bloco são IDs de comando, despachadas pelo `chat` por um único evento de intenção `{ command, input }`.
- **Notificações.** Capacidade de plataforma `doric.notifications/v1` no `desktopMain` (`show({ title, body })`, com o mesmo relato de recusa do sistema que existe hoje); o bundle `notifications` decide quando avisar a partir de `runtime.prompt-finished/v1`.
- **Histórico local.** O bundle `history` fornece no `desktopMain` `history.snapshots/v1` (`read(threadId)`, `write`), gravando em `<hostId>/<storageGeneration>/<threadId>` dentro do diretório de `doric.cache/v1`; o `chat` o usa por `whenAvailable`.
- **Rotas.** Casamento só por `pathname`; barra final normalizada, exceto em `/`; segmentos estáticos antes de parâmetros; padrões de mesma especificidade que casam os mesmos paths são conflito.
- **Elementos React.** `dispose()` idempotente; o helper `defineReactElement` fica em `desktop/ui`, não em `desktop/client`.
- **Abas do layout.** Estado das abas indexado pelo `threadId` da rota ativa.
- **Seções de settings.** Os contratos de configuração e credenciais são serviços do host (`settings/v1`, `secrets/v1`, `models/v1`) alcançados pela ponte.

## Validação

- Toda fase passa `npx nx run-many -t typecheck test build`, `npm run format:check` e `npm run lint`.
- A paridade é verificada por uma suíte end-to-end que roda os mesmos cenários de API (REST e Socket.IO) e de UI (Electron por CDP) contra o baseline e contra a implementação nova, com um servidor de modelo falso compatível com OpenAI Responses.
- A imagem Docker do host (`agents/doric/.Dockerfile`, alvos `agent-runtime`, `docker-runtime` e `runtime`) compila todos os bundles, inclusive os artefatos `client` e `desktop` que o desktop baixa durante o splash.

## Etapa 1 (Contrato)

Decisões tomadas ao implementar a etapa 1. Os identificadores **D-n** são citados no código e nos testes.

### Contratos e runtime de serviços

- **D-1 Ordem das skills.** O loader descobre `skills/*/SKILL.md` em ordem lexical de pasta. As pastas do `files` levam prefixos de dois dígitos que reproduzem a ordem do antigo manifesto, então o system prompt é idêntico byte a byte.
- **D-2 Marcas e erros entre instâncias.** Definições, `Call` e o protocolo de registro usam `Symbol.for`; erros são reconhecidos por `name`/`code`, nunca por `instanceof`; os mapas do runtime usam o ID do contrato como chave.
- **D-3 Argumento de chamada no fim.** Um `Call` no fim é sempre o argumento de chamada. Opções `{ signal, deadline }` só contam como argumento de chamada além do comprimento da tupla ou quando o item da tupla naquela posição as recusa; assim `log.info('x', { deadline: 5 })` mantém `deadline` como campo.
- **D-4 Registros.** Toda API de registro devolve `Disposable` (`{ dispose() }`), inclusive `navigation.subscribe`.
- **D-7 Saída original.** Dentro do processo a saída é validada e o valor original é devolvido, nunca a cópia do zod; schemas de saída são descritivos.
- **D-8 Erro original.** Dentro do processo o valor lançado por `execute` propaga sem mudança; `toContractError` só onde um código é exigido.
- **D-10 Protocolo de registro.** `bindRegistrant` liga um argumento registrável (tool, comando) aos serviços do bundle que chamou antes da validação.
- **D-11 `invalid_input` síncrono.** A validação dos argumentos lança de forma síncrona no processo; os wrappers das tools são `async`, então quem chama vê uma rejeição.
- **D-12 Provedores de contratos básicos.** `provide` confere nomes de métodos e JSON Schema de cada método contra a especificação da plataforma (`contract_mismatch`).
- **D-13 `whenAvailable`.** Cada callback roda num escopo filho ligado à vida daquele provedor.
- **D-14 Chamador da plataforma.** `{ bundleId: 'doric', version: PLATFORM_VERSION, generation }`.
- **D-16 Fachada de `hooks/v1`.** O provedor implementa métodos planos (`define`, `register`, `whenDefined`, `execute`); o runtime monta a API de consumo.
- **D-17 Entradas de `WindowHooksV1`.** `{}` estrito.
- **D-18 `doric.log/v1`.** Contrato de plataforma novo (API mínima), `write(record)`, por onde um provedor de `log/v1` chega aos arquivos de log do host.
- **D-29 Segurança no navegador.** Além do teste do grafo de imports, `tsconfig.browser.json` (só typecheck, `lib` es2022+dom, `types: []`) compila `bundle/contracts` e `bundle/runtime`.
- **D-30 Partes puras no runtime.** Schemas de manifesto, composição e descritor, o resolvedor por ambiente `resolveEnvironment` e o laço genérico de ativação ficam em `bundle/runtime`; `loader/` guarda só leitura de arquivos, descoberta, skills e o `startHost` de Node.
- **D-31 `skills/v1.list`.** Assíncrono (método não local).
- **D-32 `define` de hooks.** O `define` do provedor devolve um `Disposable` registrado no escopo do dono; ao descartá-lo, os registros feitos dentro de callbacks `whenDefined` caem. A fachada devolve um handle por contrato.
- **D-33 Sem corrida de sinal.** O dispatcher no processo não confere nem corre contra `call.signal`/prazo; o cancelamento chega aos provedores só por `call.signal`.
- **D-34 JSON Schema por direção.** `io: 'input'` para entradas e `io: 'output'` para saídas.
- **Plataforma reservada.** `defineService` recusa IDs `doric.*`, como `defineHooks`; a plataforma usa uma variante interna.
- **Saídas somente leitura.** `defineMethod` aceita formas readonly do tipo de saída.
- **Chamada a método inexistente.** Um método que o provedor não tem responde `unavailable`.
- **Schemas frouxos tipados.** Os schemas de registros de `runtime/contracts` e `terminal/contracts` são `z.looseObject` anotados com a interface correspondente (`z.ZodType<T, T>`), para que o provedor devolva o tipo que já tem.

### Manifesto, composição, catálogo e ativação

- **D-19 Tools v0.** Uma tool de manifesto v0 precisa exportar por padrão uma definição atual de `tool`; uma fábrica antiga coloca o bundle em quarentena (`invalid_part`).
- **D-20 Backends na composição.** A regra de `storage.backend/v1`/`secrets.backend/v1` sempre em `providers` começa na etapa 2.
- **D-21 Fundação em quarentena.** Um provedor de fundação escolhido em quarentena leva o host à recuperação, sem cair para o core. Um provedor escolhido que não é de fundação, em quarentena, deixa o contrato sem provedor ativo, e seus dependentes recebem `dependency_quarantined`.
- **D-22 Ambiente pelo build.** O ambiente e a cardinalidade de cada contrato no descritor vêm de uma ativação a seco no build, não de declaração.
- **D-35 Manifesto.** O `id` não pode ser `doric`; manifestos v0 convertidos recebem um descritor vazio. Um bundle cujo manifesto não pode ser lido não tem ID conhecido e fica sempre em quarentena (`invalid_manifest`).
- **Raiz ausente.** Uma raiz de bundles ilegível vira um problema da composição e recuperação (core ausente), não uma exceção.
- **Contadores.** A geração é um contador por processo; os provedores de contrato no snapshot do catálogo também trazem `bundleVersion`.
- **Isenção do core no build.** O gravador do build não isenta o core de declarar contratos básicos (no build não existe composição); na etapa 1 o core só usa contratos que fornece e `doric.*`.

### Core, bundles e adaptador

- **D-5 `runtime.lease/v1`.** Entra na etapa 1 no adaptador com `describe`, `exec`, `readFile` e `writeFile`; `exec` não repassa sinal de cancelamento ao sandbox e não devolve bytes.
- **D-6 Terminal opcional.** O `files` consome `terminal/v1` por `whenAvailable` (fora de `requires`) e mantém o fallback da tool `terminal` para um comando simples no sandbox, recusando `background` e `pty` com `This host does not support live terminals.`. O adaptador responde `unavailable` para um prompt cujo `Host` não tem terminais, o que leva ao mesmo fallback.
- **D-9 Configuração de tools.** Os valores deixam de chegar ao `execute`; os metadados `settings`, `requireToolConfigs`, `resolveToolConfigs` (ainda chamado em cada prompt, que continua recusando settings não satisfeitas) e `GET /tools` mantêm o comportamento até `settings/v1`.
- **D-15 Recuperação no host.** Na etapa 1 o modo de recuperação termina no caminho fatal de inicialização existente (`Doric failed to start`, estágio `bundle_load`) depois de registrar no log `Bundle recovery mode` com o estado e os motivos de cada bundle.
- **D-23 Contratos do core no desktop.** `core.hooks/v1` e `core.open-settings/v1` entram nos `provides` do core na etapa 8; `core/contracts` já publica as referências.
- **D-24 Prazo dos hooks.** 10 000 ms por handler no core; `doric.window.hooks/v1` segue as regras próprias (`onCloseHook` sem prazo, `onFlushHook` com o prazo da chamada).
- **D-25 Nomes.** Projetos Nx `bundle-<id>`; pacotes npm `<id>`.
- **D-26 Pacotes só de contratos.** `bundles/runtime/runtime` e `bundles/features/terminal` existem desde a etapa 1 apenas como `runtime/contracts` e `terminal/contracts`, sem manifesto e sem staging.
- **D-27 Adaptador embutido.** O bundle embutido `host-adapter` (sempre habilitado pelo host, fora da composição) fornece `runtime.threads/v1`, `runtime.workspace/v1`, `runtime.lease/v1` e `terminal/v1` sobre o `Host` e o sandbox de cada prompt, ligados ao escopo do prompt durante a execução (`attach`/`release`, com a liberação protegida pela identidade da ligação). Sai quando os bundles extraídos assumirem esses contratos.
- **D-28 Diagnóstico sem rota.** Nenhuma rota HTTP de diagnóstico na etapa 1; o diagnóstico fica em `doric.diagnostics/v1`, `HostPlatform.diagnostics()` e nas linhas de log `Bundle quarantined`.
- **Executor obrigatório.** O serviço de workspace recebe o executor do Direct do composition root (`createDirectExecutor({ call, attach })`); não existe mais executor padrão.
- **Caminhos.** `DORIC_BUNDLES_PATH` (padrão: `dist/bundles` ao lado do entrypoint compilado) e `DORIC_COMPOSITION` (padrão: `agents/doric/composition.json`).
- **Mudanças observáveis aceitas.** `Bundles loaded` conta 4 bundles em vez de 3 (o core novo); um bundle não-core que falha fica em quarentena em vez de impedir a inicialização; os quadros de pilha de erros persistidos em `tool.failed`/`agent.failed` mudam de caminho, mantendo `name`, `message` e `cause`.

### Pontos abertos

- Etapa 4: invocação de tools e handlers de hooks entre processos (referências de handler no envelope); o erro do envelope precisa manter `name`, `message` e a cadeia `cause` para a paridade dos eventos `tool.failed`/`agent.failed`; métodos só locais (`tools/v1.register/list`, `hooks/v1.register`) precisam de handles do lado do envelope; limpeza no provedor por `caller.generation` quando uma geração sai.
- Etapa 2: valores das settings de tools por `settings/v1`; saída de `events/v1.append`; a regra dos backends em `providers`; contador de geração persistido e `hostId`.
- Etapas 8/9: gravador de descritor com DOM para partes `client`; registros que devolvem `Promise<void>` pela ponte (`menus/v1`) descartados do lado do provedor no `onDeactivateHook`; promover o core mínimo de teste a `bundle/testing`.
- Rotação de arquivos de log não entra na etapa 1; `doric.log/v1` escreve nos destinos pino existentes.
- Acesso por escopo (HC-007): qualquer bundle que exija `runtime.lease/v1`, `runtime.threads/v1` ou `terminal/v1` e monte um escopo com os IDs de um prompt em execução alcança os controles desse prompt. Todos os bundles da etapa 1 são de primeira parte e bundles externos continuam adiados; a etapa 5 precisa manter esses formatos (extensão minor) ou registrar uma mudança major.

## Etapas 2 e 3 (Storage e protocolo genérico)

Decisões tomadas ao implementar as etapas 2 e 3 juntas. As decisões de desenho **S-1** a **S-16** ficam nas seções gerais acima (Contratos e serviços, Composição e boot, Armazenamento e dados); as subseções abaixo registram os detalhes de cada pacote.

### Pacotes

- **Nome `postgres`.** O pacote npm do bundle é `postgres` (Nx `bundle-postgres`), como os demais bundles. A dependência `postgres@3.4.7` do `prisma` fica aninhada em `node_modules/prisma/node_modules/postgres`, e `prisma --version` funciona; não há exceção de nome. O pacote de protocolo é `storage` (Nx `storage`).

### Contratos (`packages/bundle`)

- **Tipos de credencial exportados.** Além das regras de campos (S-6), `bundle/contracts` exporta `credentialKinds`, de onde sai `credentialKindSchema`, para o kernel derivar o `z.enum` das rotas da mesma lista.
- **Regra de atualização documentada.** O comentário de `credentialUpdateSchema` passa a dizer a regra real do serviço atual: ausente ou `null` mantém o campo; qualquer string, inclusive `''`, grava. O formato não muda.
- **`storageIdentity()` sem backend.** Sem provedor ativo de `storage.backend/v1`, `HostPlatform.storageIdentity()` responde `undefined` sem memorizar. A identidade resolvida aparece em `catalog().storage` e em `doric.catalog/v1.get()`.
- **Nomes de schema.** A declaração do backend é exportada como `storageDeclarationSchema`/`StorageDeclaration`; `hostId` usa `z.uuid()` (equivalente zod 4 de `z.string().uuid()`). `feedRequestSchema.after` não muda.

### Protocolo (`packages/storage`)

- **Auxiliares além do desenho.** A raiz de `storage` também exporta `decodeIndexKey` (inverso da codificação), `compareBytes`, `compareIds` (desempate por ID em bytes UTF-8, como `COLLATE "C"`), `defaultStorageCapabilities` e `checkBatchLimits`, para que memória, `postgres` e a fachada do core apliquem os mesmos limites.
- **Valores indexáveis.** Número não finito, string com surrogate isolado, objeto ou array é `invalid_index_value`; `-0` e `0` têm a mesma chave. Um intervalo com `gt` e `gte` (ou `lt` e `lte`) juntos é `invalid_input`.
- **`parseStreamId`.** `family` é o nome qualificado antes da barra, com o dono (`runtime.thread.events`); `owner` é o primeiro segmento. O backend aceita qualquer nome de stream; validar o formato é papel da fachada.
- **Lote e limites.** Lote vazio é o de `batchSize` 0 (`invalid_input`); um lote só com `expect` é válido e ocupa uma posição no feed. Os limites são inclusivos, e `maxAppendBytes` vale para cada evento anexado. A unicidade é verificada a cada `put`, como um índice único não adiado do PostgreSQL.
- **Marca de truncamento.** `atSequence` é o `lastSequence` ao fim do lote, contando os appends do mesmo lote, para que um leitor que já tinha a cauda removida sempre veja a marca.
- **Consulta e feed.** Consultar um índice não declarado (ou um tipo sem declaração), igualdade com mais campos que o índice ou intervalo sem campo seguinte é `invalid_input`. `documents` no feed são as chaves de `delete` e `put`, sem repetição.
- **Blobs.** `putBlob` exige base64 padrão (senão `invalid_input`); `getBlob` de um hash mal formado responde `undefined`.
- **Backends em memória.** `secrets.backend/v1` em memória ordena `list` por nome em unidades de código (como `COLLATE "C"`), mantém o `kind` gravado numa atualização e preenche `createdAt`/`updatedAt`. `memoryFoundation` aceita também `storage` (limites e `health` do backend de storage).
- **Kit de conformidade.** `storage/conformance` exporta `conformanceCases` (49 casos, IDs D1–D7, C1–C4, R1–R3, Q1–Q10, S1–S6, P1–P2, F1–F4, X1–X5, B1–B3, L1–L3, H1–H2), `runConformanceCase(harness, caso)` e `runStorageConformance(harness, { skip, timeout })`, que registra uma suíte `node:test` por grupo (limite de 120 s por caso). Cada caso roda depois de `reset()`, e as instâncias que ele abre e não fecha nem derruba são fechadas no fim. O harness é genérico no tipo da instância.
- **Casos independentes do backend.** O kit não supõe que as posições do feed comecem em 1 nem que sejam contíguas (storage.md diz só "monotônica"): exige posições estritamente crescentes, cada commit bem-sucedido uma vez e na ordem, e que um leitor que acompanha commits concorrentes não perca nenhum. A ordem das chaves dentro de um commit do feed não é verificada. A contiguidade do `postgres` (S-14) continua no teste próprio do bundle.
- **Itens do desenho agrupados.** As consultas inválidas entram em Q1, Q2 e Q5; criações concorrentes com `revision` 0 em C1; reivindicações concorrentes de uma chave única em C4; `invalid_index_value` no meio do lote em X2; `createdAt` ISO em S1. O kit não fixa se uma chave única admite vários documentos sem o campo: hoje memória e `postgres` tratam `null` como valor, e um índice único aceita só um documento com o campo ausente.
- **Autoteste do kit.** `tests/kit-self.test.ts` envolve o backend em memória em três variantes quebradas (sem atomicidade, com sequência reutilizada após truncamento, com lacuna no feed) e exige que X1–X4, S3–S4 e F1–F4 falhem; qualquer erro conta como falha. Um invólucro que só repassa as chamadas passa nos mesmos casos.

### Backend `postgres` (`bundles/foundation/postgres`)

- **Bloqueios.** Em vez de `SELECT … FOR UPDATE`, cada `commit` toma de uma vez, numa ordem global (pela chave `hashtextextended`), locks consultivos de transação: exclusivo por documento de `expect`/`put`/`delete` e por stream escrito, compartilhado por tipo de `put`/`delete`; `declareType` toma o exclusivo do tipo. Assim uma criação com `revision` 0, uma verificação de ausência sem `put` e um stream removido também se serializam, sem ciclo de espera. O lock da posição (S-14) vem por último.
- **Puts um a um.** Os `put` aplicam-se em ordem, cada um com sua revisão e suas entradas de índice; a unicidade é conferida a cada `put`, com um `INSERT` por índice único, de modo que o `23505` em `storage_index_entry_unique_key` vira `unique_conflict` com o nome do índice. Os outros erros do banco propagam sem mudança (`53100` continua reconhecível).
- **Declarações sem cache.** `commit` e `query` leem `storage_type` a cada chamada, então uma declaração feita por outro processo vale na hora.
- **Feed.** `storage_commit` ganha as colunas `truncated` e `dropped` (padrão `'[]'`) em vez de guardar esses nomes dentro de `streams`. Um banco recém-migrado começa com a posição 1, o commit da conversão da configuração.
- **Horário.** Um `clock_timestamp()` por commit, truncado em milissegundos e lido depois dos locks, vale para `updated_at` e para o `createdAt` das entradas, no formato de `toISOString()`.
- **JSON.** Valores ficam em JSONB: a ordem das chaves é a do JSONB, e `\u0000` em valores, IDs ou nomes de stream é recusado pelo PostgreSQL (erro propagado), ao contrário do backend em memória; a fachada aplica `storable` antes.
- **Transações.** As transações interativas do Prisma usam `maxWait` de 30 s e `timeout` de 120 s, porque um lote pode ter até `maxBatch` itens e esperar locks.
- **Cliente e ambiente.** `client()` cria o cliente no primeiro uso a partir de `DORIC_DATABASE_URL` (falha não memorizada); `connect()` e os métodos de storage rejeitam, sem lançar de forma síncrona, quando o cliente não pode ser criado. A limpeza da desativação desconecta só o cliente criado pela URL; um cliente injetado (testes) fica com quem o criou. `createDatabase` é o de antes, então as consultas por modelo usam o schema `public`.
- **Segredos.** A cifra é criada na primeira chamada de `list`, `get` ou `put` (uma chave mal formada recusa toda chamada com a mesma mensagem, antes do banco); falha de decifração é `credential_unreadable` com a mensagem da cifra; `list`/`get` devolvem `createdAt`/`updatedAt`. IDs que não são UUID chegam ao Prisma como no store anterior.
- **Migração da configuração.** Os providers do documento migrado ficam em `ORDER BY id` na collation do banco; o carregamento antigo ordenava por `localeCompare` na leitura, e o leitor novo precisa continuar ordenando. `jsonb_typeof(models) = 'array'` reproduz o `Array.isArray`; a verificação também exige o documento do contador global. Nomes de FK e `ON UPDATE CASCADE` seguem o Prisma, e `prisma migrate diff` não acusa diferença.
- **Cliente gerado.** `bundles/foundation/postgres/src/generated/prisma` fica fora do git (`src/generated/.gitignore`), como o cliente do kernel antes.
- **Kit de conformidade.** `tests/conformance.test.ts` roda `runStorageConformance` com o harness de `tests/support/harness.ts` sobre um schema migrado por arquivo; fechar uma instância também desconecta o cliente dela, para não esgotar as conexões. `tests/storage-*.test.ts` continuam como evidência direta sobre PostgreSQL.

### Fachadas do core (`bundles/foundation/core`)

- **Versão do core.** O core passa a `1.1.0`: os contratos novos em `provides` são uma mudança minor contra a baseline publicada na etapa 1, e a baseline é regenerada.
- **Dependência de `storage`.** A parte host do core importa `parseStreamId` e `checkBatchLimits` de `storage`, para aplicar as mesmas regras de stream e limites dos backends. O pacote entra nas dependências do core e precisa estar no staging e na imagem do host.
- **Registros.** `storage/v1.defineType` repetido pelo mesmo dono com o mesmo JSON Schema e os mesmos índices devolve outro handle, e o tipo sai quando o último é descartado. `settings/v1.register` e `events/v1.register` recusam a segunda definição do mesmo ID com `registration_conflict`.
- **Plataforma.** `doric` passa nas verificações de dono e lê sem validação documentos de tipos que ninguém define. Toda escrita exige o tipo definido, também para `doric`, porque o `put` é validado pelo schema do tipo.
- **Campos de índice.** Um campo com pontos precisa existir no schema zod, atravessando `optional`, `nullable`, `default`, `lazy`, `pipe` (pela saída), união, interseção, `record` e posições numéricas de `array`/`tuple`; `unknown`, `any` e `custom` aceitam qualquer caminho.
- **Streams.** Só o dono do stream (primeiro segmento) ou `doric` lê. O provedor ativo de `events/v1` só ganha a escrita.
- **Espaço nunca gravado.** `entry` responde os defaults do schema com `revision` 0, `generation` 0, `updatedAt` na época (`1970-01-01T00:00:00.000Z`) e a versão de `provides`.
- **Definição registrada.** `get`, `entry` e `set` usam o schema da definição registrada com aquele ID, não o do objeto recebido. Um valor gravado que o schema recusa na leitura é `invalid_output`. Leitura, escrita e assinatura não verificam dono, porque `settings/v1` não define `not_owner`.
- **Assinantes.** A falha de um assinante vai a `doric.diagnostics/v1` como `settings_listener_failed`, no bundle que assinou.
- **Redação em `events/v1`.** O append usa `secrets/v1.redactions(call)`, que carrega as credenciais se preciso, em vez de `view()`: um evento nunca é gravado sem redação, e uma falha de carga falha o append. O corpo passa por `eventJson` e depois pelo `storable` de cada string, como `json()` do kernel; nomes de propriedade são redigidos e, como no kernel, não passam por `storable`.
- **Redação no log.** Strings de registros simples, arrays, `Error` (com `name`, `message`, `stack` e `cause`) e instâncias com propriedades enumeráveis são redigidas numa cópia simples; instâncias sem propriedade enumerável (`Date`, `Map`) ficam como estão, porque o destino não escreve seu conteúdo. `addRedaction('')` é ignorado também na `view()`.

- **Tipos de storage em `core/contracts`.** Além de `CoreHooksV1` e `OpenSettingsCommandV1`, `core/contracts` exporta os tipos de storage do próprio core, `core.settings/v1` e `core.settings-generation/v1` (com `settingsGenerationId`), para que as migrações de dados e seus testes usem as mesmas definições. Isto amplia a regra "`core/contracts` exporta só ..." dos documentos de conceito.
- **Dono das definições.** `settings/v1.register` e `events/v1.register` conferem o namespace, a presença do ID em `provides` e o tipo do objeto recebido (`defineSettings`/`defineEvent`), mas não o tipo do descritor declarado: o catálogo ainda não carrega o tipo de cada contrato de `dist/contracts.json`. A conferência entra quando o loader publicar esse tipo no catálogo (etapa da instalação externa, quando descritores deixam de ser confiáveis por construção).

### Kernel `agents/doric` (etapas 2 a 4)

- **`host-config` por instância.** `createHostConfig()` devolve o bundle, a definição do espaço e `track`; a refinação que exige credenciais armazenadas lê a `view()` daquele host, sem estado de módulo, para que vários hosts no mesmo processo (testes) não se misturem.
- **Refinação também na leitura.** Como a fachada aplica o schema registrado ao ler, o kernel carrega as credenciais antes da configuração (a ordem do boot). Uma configuração gravada que nomeie credencial ausente seria `invalid_output` em `configuration_activation`; isso não ocorre, porque o documento migrado vem de linhas com FK e toda escrita passa pela refinação.
- **Referências protegidas.** `referencedCredentialIds` devolve os campos `secret` dos providers, `gitCredentialId` e `githubCredentialId`, exatamente o que as FKs protegiam; um `secret` em `tools` continua sem proteção, como antes.
- **`track` na carga.** `ConfigStore.load()` informa a configuração carregada ao `host-config`; depois, a assinatura de `settings/v1` mantém a referência atual.
- **Adaptador de credenciais.** `credential_invalid` vira `invalid` com a mensagem, `credential_missing` vira `missing`, `credential_name_taken` vira `conflict`, `credential_kind_immutable` vira `immutable` e `credential_storage_unavailable` vira `MissingKeyError` (a classe fica em `credentials/service.ts`); outros erros propagam.
- **Boot.** `startBundles` aceita `embedded` além do adaptador; `bundleCount` exclui todos os embutidos e passa a 5. No encerramento, o `$disconnect` acontece em `platform.stop()`, antes de `pool.dispose()`.
- **Dependências.** O kernel depende de `postgres`; `@prisma/client` sai; `@prisma/adapter-pg` fica só como devDependency das fixtures de teste, e `storage` como devDependency. O `.gitignore` da raiz passa a ignorar `bundles/foundation/postgres/src/generated/prisma/`.
- **Testes do kernel.** `tests/helpers/platform.ts` sobe o core instalado de `dist/bundles` com a fundação embutida `postgres-test` (ID diferente do `postgres` instalado, para não gerar `duplicate_id`). K-1 compara a leitura inteira como string e a resposta de `replace` como string com `updatedAt` substituído, porque o relógio difere entre as duas escritas. Os testes de cifra de `credentials.test.ts` viram testes do adaptador sobre PostgreSQL (envelope `v1:`, nonce novo a cada escrita, chave em branco igual a nenhuma, chave mal formada recusada na carga).

### Revisões cruzadas e notas para as próximas etapas

- **Registros por geração (X-10).** `storage/v1.defineType`, `settings/v1.register`/`subscribe` e `events/v1.register` passam a ser chaveados por `(id, geração da chamada)` na etapa 4 (D4-11): o mesmo dono registra o mesmo ID uma vez por geração, e descartar a geração N não remove o registro de N+1. ## Etapa 4 — validação de tools (4-WP4-C)

- `BoundTool.check(payload)` é síncrono (`input.safeParse` + mapeamento de issues existente) e `toTool` o propaga; `Tool.check?` é opcional e pode devolver uma promise (tools remotas). O `ToolPayloadCheck` do pacote `tool` é estruturalmente igual ao de `bundle/contracts` e usa `ToolIssue`.
- `ToolStorage.validate` devolve `ToolCall | Promise<ToolCall>`: só é assíncrono quando o `check` da tool devolve uma promise. Tools sem `check` ou com `check` síncrono continuam no caminho síncrono; `execute` delas continua validando duas vezes como hoje, e o de tools assíncronas valida uma vez e executa com `check.data`. Falhas assíncronas geram o mesmo `invalid_payload` (mensagem `Tool call payload failed validation: <nome>`, issues do `check`).
- No `agent`, `validatedCalls` é assíncrono: todas as calls são parseadas primeiro (como hoje) e validadas em ordem, parando na primeira falha, dentro do mesmo `try`; eventos, mensagens e contador de reparos não mudam.

## Etapa 4 — costuras do runtime (4-WP4-A2)

- `callGeneration`/`generationOf` são exportados por `bundle/contracts` (ajuste aditivo em `contracts/index.ts`). Toda call criada pelo runtime recebe a propriedade não enumerável; sem call pai vale `generation ?? defaultGeneration ?? 0`, e `dispatch` passa `runtime.operationGeneration ?? 0`.
- `LayeredDirectory.register` grava na camada base: os bundles do kernel registram pela `activeView` e seus providers precisam estar no `kernelDirectory`. `active` devolve o provider da base antes do overlay; `setOverlay` emite `removed` dos records do overlay antigo e `added` dos novos para cada assinante.
- O marcador `x-doric-local` passa a ser posto no lugar de cada valor local que tem codec: `disposable` para o `disposableSchema` básico (por identidade) e `callback`/`object` quando o autor declara `.meta({ 'x-doric-local': '<tipo>' })` no schema. Se algum valor local de um membro não tem codec, o membro inteiro continua `{ "x-doric-local": true }`. `functionSchema()` continua sem codec declarado, então os inputs de hooks e tools continuam `true`; as saídas `disposableSchema` passam a `disposable`.
- Tuplas geradas levam `minItems` (itens iniciais não opcionais na direção do membro, então um item com `default` é opcional no input e obrigatório no output) e `maxItems` quando não têm rest. Os baselines `contracts.published.json` de `core` e `postgres` foram regenerados pelo comando `baseline` da build. Os outros baselines não mudaram.
- `contractDocument`, `RecordedContract`, `ContractDocument`, `JSON_SCHEMA_DIALECT` e `schemaPath` foram movidos para `runtime/json-schema.ts`. `build/schemas.ts` os reexporta.
- Opções de `activateEnvironment`: `preActive` entra no conjunto de ativos da checagem de dependências. `hooksProvider: 'remote'` define `AppHooksV1` antes do laço, e cada bundle do laço é observado. `settle` roda depois de `activate` (a rejeição recebe o código que a mesma recusa teria em processo: uma recusa de registro vira `registration_failed`/`cardinality_mismatch`, qualquer outro erro vira `activate_failed`) e de novo depois de `afterActivate` (`registration_failed`). `isRegistrationConflict` é exportado por `runtime`.

## Etapa 4 — core ciente de geração (4-WP4-D)

- A partição segue D4-11 com `g = generationOf(call)`; o helper `bundles/foundation/core/src/host/partition.ts` concentra a regra: uma leitura vê a partição do kernel e a geração `g` (ou a ativa, lida de `doric.catalog/v1.get(call)`, quando `g === 0`); um registro com `g === 0` colide com toda entrada viva, e um com `g > 0` colide com o kernel e com a própria geração. O catálogo só é lido quando há entrada de geração diferente de 0, então o modo de um processo não faz leitura nova.
- `RegisteredTool`/`RegisteredSkill` devolvidos por `list` não ganham o campo `generation`: ele fica numa entrada interna, para que a forma pública (e `GET /tools`) não mude.
- `tools/v1.list` passa a aceitar `call?: CallArg` no tipo (`contracts/basic/tools.ts`, mudança só de tipo, sem efeito no schema publicado), para que `skills/v1.register` resolva `allowed-tools` com `list(call)` na geração de quem registra.
- `hooks/v1`: a definição de um contrato de bundle fica por `(id, g)`; contratos `doric.*` têm um estado único. Os handlers ficam numa lista por ID com a geração de quem registrou, e `execute` filtra pela visão da chamada antes de ordenar por `catalog.order` e `seq`. `whenDefined` observa a definição da própria geração do chamador; um bundle do kernel (`g === 0`) observa só definições do kernel, o que é coerente com a regra de residência (o kernel não chama contratos de geração durante `activate`).
- Fachadas X-10 (`storage/v1.defineType`, `settings/v1.register`/`subscribe`, `events/v1.register`): entradas por `(id, g)`. Em `settings/v1`, a assinatura pertence à entrada da sua geração (o `dispose` de uma geração nunca remove a de outra), mas uma escrita notifica os assinantes de todas as entradas vivas do mesmo ID, porque um único documento `core.settings/v1` guarda o espaço para todas as gerações.
- Os testes de visão chamam os métodos dos serviços do core diretamente, com chamadas fixadas por `createHopCall({ generation })` e um `Services` falso (catálogo, diagnósticos e backend em memória), porque o runner de geração (WP4-B) ainda não existe. A evidência de ponta a ponta fica com WP4-E.

## Etapa 4 — envelope (4-WP4-A1)

- O código do envelope fica em `packages/bundle/src/runtime/envelope/` e não é reexportado por `runtime/index.ts` (arquivo da A2): o processo (4-WP4-B) o importa pelo caminho relativo do pacote. O teste de segurança para browser cobre `runtime/envelope/index.js` (só `zod`).
- Tabela de codecs por `(contrato, método)` em `envelope/values.ts`, não por identidade de schema em `contracts/basic/common.ts`: `functionSchema()` cria um schema novo a cada uso. Métodos básicos e de plataforma sem entrada na tabela seguem uma regra fixa: sem valor local, atravessam; entrada serializável e saída `disposableSchema`, registro otimista; qualquer outro valor local, `local_only`. Contratos de bundle usam os marcadores `x-doric-local` dos schemas (`true` recusa o método). Um teste enumera todos os métodos básicos e de plataforma.
- Recusados com `local_only` na etapa 4: `tools/v1.list`, `secrets/v1.registerReferences` e `view`, `models/v1.resolve`, `models.provider/v1.create`, `commands/v1.register`, `ui/v1.*` e `navigation/v1.register`/`subscribe` (callbacks síncronos do cliente, etapa 8).
- Callbacks atravessam em três modos: `async` (handlers de hooks e callbacks de contratos de bundle; devolve a promise do `invoke`), `listener` (`settings/v1.subscribe`; dispara sem esperar, falha vai para o diagnóstico como `listener_failed`) e `scoped` (`hooks/v1.whenDefined`). No `scoped`, o proxy do kernel é síncrono: abre uma execução com um handle próprio e devolve uma limpeza que libera esse handle. A geração roda o callback em um escopo filho do escopo atual do principal; ao liberar, descarta esse escopo (soltando os registros feitos no callback) e então chama a limpeza do callback.
- Exatidão nas bordas: o lado que tem a definição real (o remetente) envia o resultado do `safeParse` quando ele passa e o valor original quando falha, para que a recusa e a mensagem continuem sendo as do core. Na volta, refaz o parse quando ele passa. Vale para entradas de hooks (`execute` e o handler registrado), saídas `transform`, valores de `settings/v1` (`get`, `entry`, `set`, entradas de `subscribe`) e payloads de `events/v1.append`.
- Espelhos no kernel: contratos de hooks `doric.*` conhecidos viram o objeto real; os demais são `defineHooks` com validadores JSON Schema, guardados em cache por forma no link. Eventos e tipos de storage viram `z.looseObject({})` com o validador; settings viram só o validador. Risco: a introspecção do core sobre o schema de um tipo de storage (campos de índice, `fingerprintOf`) vê o espelho, então um índice com campo inexistente definido na geração não é recusado no kernel. Nenhum bundle de geração define tipos de storage hoje.
- Invariante de geração no kernel: uma `call`/`invoke` que chega pelo link da geração N deve trazer N ou uma geração que o próprio kernel já enviou por esse link (por exemplo 0, quando um callback chamado a partir de uma chamada não fixada do kernel chama o kernel de volta). Qualquer outra recebe `protocol_error`.
- Um `cancel` que chega depois do prazo da chamada aborta o sinal do provider com `TimeoutError`, como em processo, porque o sinal do remetente abortou pelo prazo.
- Registros otimistas: `ProcessLink.activating(bundleId)` marca a ativação. Enquanto ela dura, as recusas ficam guardadas para `settle(bundleId)`; fora dela, viram `registration_failed` no diagnóstico do processo. Os handles exportados para a operação (tool, callback) são liberados quando o registro é descartado ou recusado.
- No fechamento do link, os ouvintes de `onClose` rodam antes da rejeição das chamadas pendentes (`generation_lost`, detalhes `{ generation, incarnation }`). Depois disso, o lado que fica descarta tudo o que o outro lado registrou nele. `registerRemote` remove o record remoto do diretório quando o link fecha.
- Objetos `object`: o handle importado é um proxy que só responde ao próprio handle (`then` e `dispose` leem `undefined`, para não ser tomado por thenable ou Disposable). Qualquer outra leitura lança `local_only`, e ao voltar ao processo de origem o handle vira de novo o objeto original.
- `ControlMessage.init` é tipado como `unknown`, e quem o valida é o runner (4-WP4-B), dono de `GenerationInit`.

## Etapa 4 — camada de processo Node (4-WP4-B)

- Residência (D4-1, revisada por X-8): `process/partition.ts` põe no kernel `foundation`, `core` e todo bundle embutido; `others` instalados vão para a geração. A ordem publicada é a do kernel seguida da da geração (D4-2). O kernel ativa sua partição com `preActive` = bundles agendados da geração, então a dependência de um bundle do kernel em um provider da geração é satisfeita pelo catálogo. `kernel_requires_generation` não é emitido: com a revisão, ele só valeria quando nenhum bundle habilitado fornece o contrato, caso que o resolvedor já trata com seus próprios códigos.
- Pendente (G-11): a espera dos stubs do kernel por uma geração ativa (`onActive`) não foi implementada; com nenhuma geração ativa, `dispatch` responde `unavailable` como hoje. Não há consumidor no kernel na etapa 4.
- O contador de gerações é por kernel (boot = 1, cada `publish` aceito = +1), não o contador global do processo de `startHost`. Um `publish` recusado (`kernel_restart_required`) não consome número.
- `kernel_restart_required` compara uma assinatura da partição do kernel: ID, versão, fase, estado e origem das entradas do kernel, os providers do kernel por contrato e o motivo de recuperação.
- `doric.generation/v1` (API mínima, `describe()`/`hold(execution)`) é um contrato de plataforma em `contracts/platform.ts`, fornecido pelo kernel e anunciado à geração como provider remoto (sem novas mensagens de controle). `describe` e `hold` respondem pela geração da operação (`generationOf(call)`, ou a ativa quando 0). `acquire` do gerenciador e `hold` usam a mesma contagem (`holds` por geração, `ExecutionRef | { window }`). A drenagem para quando não há holds; chamadas pendentes não entram no critério (o `ProcessLink` não as expõe), e toda execução em curso já tem um hold.
- `doric.catalog/v1`, `doric.diagnostics/v1` e `doric.bundle/v1` são locais no processo da geração. O catálogo vem de `init` e é trocado pelas mensagens `catalog`: o kernel envia a cada processo vivo o snapshot da própria geração dele sempre que uma geração fica ativa. O diagnóstico local junta o store do processo com os estados do catálogo para os bundles do kernel; `report` grava no store local e o processo envia o snapshot (`diagnostics`) ao kernel, que o mescla na visão daquela geração. O diagnóstico de uma geração no kernel tem os bundles do kernel, os da geração pelo último snapshot recebido e os erros dos dois em ordem de horário.
- O runner registra os providers locais da plataforma direto no diretório interno; `AnnouncingDirectory` anuncia (`provide`/`unprovide`) só records locais que não são `doric.*`. Os providers do kernel chegam em `init.kernelProviders`, exceto os três locais acima.
- Barreira de ativação: `activateEnvironment` ganhou a opção `onPrincipal(entry, principal)` (arquivo da A2, mudança aditiva), chamada logo após criar o principal. O runner a usa para abrir `link.activating(id)` (fechado quando o próximo bundle começa ou quando o laço termina) e para que callbacks `scoped` encontrem o principal já durante `activate`. Um teste confirma que a recusa de uma tool duplicada na geração quarentena o bundle com o mesmo motivo do modo de um processo.
- O runner Node relê o manifesto do bundle (`readInstalledBundle`) no `afterActivate` para obter as tools e skills de manifestos v0, em vez de carregar isso no `init`.
- Falha de início: após `startAttempts` processos que saem antes de `ready`, a geração fica `failed`, seus bundles aparecem `quarantined` com `generation_failed` (`Generation N could not start: its process exited before it was ready (code X, signal Y; ...).`), o kernel registra `Bundle quarantined` para cada um e ativa uma visão vazia (só a partição do kernel), disparando `onActive(N)` para que `acquire` resolva. Em `publish`, a falha deixa a geração ativa como está e devolve `failed`.
- Queda de uma geração pronta: os ouvintes `onLost` rodam dentro do fechamento do link, antes das rejeições `generation_lost`; os holds da incarnação perdida são descartados (o `release` posterior não faz nada). Uma geração ativa é recriada com `incarnation + 1` e, ao ficar pronta, dispara `onActive` e `onGenerationReadyHook`; uma geração drenando apenas para. O kernel registra no diagnóstico `generation_lost` (e `generation_failed` quando desiste).
- Em modo de recuperação o kernel não inicia gerações (como hoje, os bundles restantes ficam inativos); `acquire` então espera, abortável pelo sinal.
- `ajv@8.20.0` (já no lockfile) virou dependência direta de `bundle` (`package.json` e a entrada `packages/bundle` do `package-lock.json`); a implementação é `process/ajv.ts`, com cache por JSON canônico.
- A tabela de `tests/values.test.ts` (A1) ganhou `doric.generation/v1` (`describe` atravessa; `hold` é otimista com `Disposable`).

## Etapa 4 — integração do host (4-WP4-E)

- `startBundles` passa a usar `startKernel` (com `errorClasses: [ToolErrorObject]`) e devolve `catalog()` (tools e skills da geração ativa) e `acquire(execution, signal)`, que fixa o prompt na geração ativa e devolve um `BundleLease` (`call`, `tools(call)`, `skills(call)`, `release`). As tools são lidas a cada chamada de `ToolsV1.list`; as skills, que são assíncronas, ficam em cache por geração e são relidas em `onActive`, porque `GET /tools` e `requireToolConfigs` precisam de leitura síncrona.
- O `Generation` da configuração perdeu `catalog`. `ConfigService` ganhou `catalog()`, e `GET /tools` e a validação de `replace` leem a geração ativa por ele. O executor Direct adquire o lease antes de `attach` e o libera depois do `release` do adapter; as tools e skills do prompt vêm do lease.
- Supressão de perda de geração: um `tool.failed` cujo erro é `handler_failed` com causa `generation_lost`, com o sinal já abortado, não é gravado. O executor grava o histórico nesse instante e não grava de novo no `finally`, porque o `release()` do agente responderia à chamada com "Tool call did not complete…". Assim o histórico fica como numa queda do host: a chamada sem resultado, que o run retomado responde com o resultado de chamada interrompida (Q10). O desenho supunha que o `finally` já guardaria a chamada pendente; não guarda.
- `pauseForGenerationLoss` é síncrono e não pega a trava do projeto: o `onLost` roda antes da rejeição das chamadas pendentes, e esperar a trava deixaria a rejeição chegar com o sinal ainda não abortado. `held` também é verificado no laço de `run`, não só em `start()`, para que o mesmo laço não pegue o próximo prompt da fila depois da pausa.
- Esgotamento em `resumeHeld`: usa `ThreadStore.failPrompt` (os mesmos eventos, resultado e resultado delegado ao pai que o boot grava), depois publica os eventos novos do Thread e do pai e põe na fila do pai, em memória, a entrada que `failPrompt` aceitou para ele.
- A fiação `onLost`/`onActive` fica em `recoverGenerationLoss` (`bundles/boot.ts`), usada por `index.ts` e pelos testes. Quando a geração perdida não era a ativa (estava drenando), a retomada começa logo, sem esperar `onActive`. As operações de recuperação (`suspendForGenerationLoss`, `resumeAfterGenerationLoss`) são expostas pelo tipo `GenerationRecovery` de `workspace/service.ts`, sem alterar `WorkspaceService` em `types.ts`.
- Paridade E4: o teste "a Host control failure fails the tool call with that same error as its cause" passou a comparar classe, nome e mensagem da causa, não a identidade do objeto. A tool roda na geração, então a causa atravessa duas fronteiras de processo e chega reconstruída. O que é observável (o `ToolErrorObject` `handler_failed` com a causa da recusa do Host) não muda.
- Fixtures: `tests/fixtures/generation-bundles/{probe,crash-on-activate}` são JS puro (manifesto v1, `contracts.json`, `package.json` com `type: module`). Os testes copiam `dist/bundles` e as fixtures para raízes temporárias em `agents/doric/dist-tests`, para que `bundle`, `tool` e `zod` resolvam pelo `node_modules` do repositório, como nos bundles preparados. O gate da tool `probe` usa arquivos com caminho absoluto (`<gate>.started` com o pid, `<gate>.release`).

## Etapa 4 — decisões de desenho (D4-1 a D4-18)

As seções 4-WP4-\* acima detalham a implementação; esta lista registra as decisões do desenho da etapa e onde a implementação as ajustou.

- **D4-1 Residência.** Fundação, core e bundles embutidos ficam no kernel; `others` instalados vão para o processo da geração. Ajuste (X-8, 4-WP4-B): `kernel_requires_generation` nunca é lançado; o kernel ativa com `preActive` = bundles da geração, e a falta de provider continua com o resolvedor.
- **D4-2 Ordem publicada.** Ordem do kernel seguida da ordem da geração.
- **D4-3 Respawn.** Mantém o número da geração; `incarnation` conta os processos.
- **D4-4 Geração da operação.** Herdada ao longo da cadeia de chamadas (`generationOf`, `callGeneration`, campo `generation` do envelope); 0 = kernel ou não fixada.
- **D4-5 Envelope.** Acrescenta `generation`, `provider`, `oneway`, `invoke` e `release`; tipos de stream reservados; plano de controle separado.
- **D4-6 Semântica de chamada.** `cancel` é consultivo (sem rejeição local); `invoke` não é um hop; o kernel sobrescreve `caller.generation` pelo link.
- **D4-7 Erros.** Codec com ordem das propriedades próprias, classes registradas, protótipos sintéticos por nome e `stack` copiado; `code: 'internal'` é só metadado.
- **D4-8 Valores locais.** Só atravessam em contratos básicos e de plataforma, por tabela fixa de codecs; métodos locais definidos por bundles são `local_only`.
- **D4-9 Registros síncronos.** Otimistas, com barreira de ativação (`settle`) que preserva os códigos de quarentena.
- **D4-10 Schemas.** Validação JSON Schema com ajv 2020 atrás de `SchemaValidators`; tuplas com `minItems`/`maxItems`; baselines regenerados.
- **D4-11 Core por geração.** Tools, skills e hooks particionados pela geração da operação; leituras de catálogo e diagnóstico recebem a call.
- **D4-12 Troca.** Ativa N+1, troca, dispara `onGenerationReadyHook`, drena N pelos leases sem prazo; mudança no kernel exige reinício (`kernel_restart_required`). A drenagem espera holds zerados e nenhuma chamada em voo (`ProcessLink.inFlight`: saídas pendentes + entradas não respondidas); `onIdle` reavalia a parada.
- **D4-13 Gatilho.** Nenhum gatilho externo de geração na etapa 4; `publish()` é interno ao kernel.
- **D4-14 Queda.** `onLost` antes das rejeições; só a geração ativa é recriada; 3 tentativas de início; depois, quarentena `generation_failed` e visão vazia.
- **D4-15 Execução de tools.** Cada tool roda no processo do seu bundle; o kernel usa `RemoteTool` com `check` exato assíncrono; `tool`/`agent` aceitam validação assíncrona.
- **D4-16 Perda com prompts fixados.** Os prompts pausam com `host_restarted`, os Threads ficam retidos e retomam com o orçamento e a ordem do boot. Ajuste (4-WP4-E): retomada imediata quando a geração perdida estava drenando.
- **D4-17 Desktop.** Reusa `runGeneration`/`ProcessLink` com `hooksProvider: 'local'`; o main faz o papel de kernel só com providers de plataforma (etapa 8).
- **D4-18 Prisma.** Nenhuma mudança de schema ou migração SQL na etapa 4.
- **Gate E2E.** A imagem `docker build -f agents/doric/.Dockerfile --target docker-runtime` sobe sem mudança no `.Dockerfile` (o kernel continua PID 1 e recebe o SIGTERM sozinho). Três execuções do harness (21/21 API, 18/18 UI na primeira): a UI é idêntica ao baseline; na API resta só a diferença de `stack` em `17-failures-and-http`, que já existia nas etapas 1 e 2/3. Em uma das três execuções, `14-delegation` mostrou a corrida entre o fim do prompt do pai e o resultado do filho (o resultado chegou com o pai ainda ocupado: `prompt.accepted{queued: true}` e `prompt.queued`, e por isso `lastSequence` + 1 em `15` e `18`). Os dois desfechos são comportamento atual; a latência do IPC (R8) torna o segundo possível, e nada foi alterado para escondê-lo.

## Etapas 5 a 7 — emendas de contrato (57-WP-C)

- **`models/v1` e `models.provider/v1` refinados (57 §2.10).** O provider tem `kind`, `advertised` e `catalog` assíncronos e `create({ providerId, values, secret? })`; `models/v1` ganha `kinds`, `kind`, `catalog` e `prepare`. `ModelEntry`/`listModels` saem e dão lugar a `CatalogModel`/`catalog` (`{ status: 'read', models } | { status: 'absent' | 'failed' }`). `prepare` recebe a configuração como registro solto, porque `packages/bundle` não depende de `DoricConfig`.
- **Travessia por marcador nos contratos básicos.** Um método básico sem entrada fixa no envelope atravessa pelos marcadores `x-doric-local` dos seus schemas (mesma regra dos contratos de bundle); sem codec continua recusado. O `LanguageModel` é marcado `object` (volta ao processo que o criou como o objeto original; em outro processo qualquer uso é `local_only`) e o `secret` de `create` é marcado `callback`, lido antes de cada requisição.

## Etapas 5 a 7 — store do `runtime` sobre `storage/v1` (57-WP-R1)

- **`bundles/runtime/runtime/src/host/store/`.** `createRuntimeStores(storage, { executor })` devolve `ProjectStore` e `ThreadStore` (`types.ts` da 57-WP-0) sobre um conjunto de documentos compartilhado; `runtimeStorageTypes` lista os quatro tipos para o `defineType` da ativação (57-WP-R2). Os mapeadores, as regras de estado (`excludedStates`, `startedAt`, `finishedAt`, `open`), a página por `createdKey` com cursor exclusivo, o `reconcile` e o fold de `unfinishedPrompts` vieram de `projects.ts`, `threads.ts`, `usage-store.ts` e `storage.ts` sem mudança de regra.
- **Protocolo de escrita.** Cada escrita é um `commit` com `expect` da revisão lida, fila por documento no processo e cache `{ value, revision }` (revisão `expected + 1` depois do commit). `revision_conflict` e `sequence_conflict` descartam o cache, releem e recalculam, até 8 vezes. O append usa `expectedSequence = lastSequence` do documento, então documento e contador do stream não divergem.
- **Horário do protocolo.** O `createdAt` de um evento é o da entrada do stream; o store relê as entradas que acabou de gravar (um `read` por commit) para responder o `ThreadEvent`. O fold no mesmo commit usa um horário provisório; quando o do backend difere, uma segunda escrita do documento (sem mover `updatedAt`) grava o do backend em `pending[].acceptedAt` e `lastStarted.at`, e só para `prompt.accepted` e `prompt.started`. Se o processo cair entre as duas escritas, fica o horário provisório (diferença de milissegundos).
- **Participação do executor no rewind.** `types.ts` não recebe o executor; a fábrica recebe `executor.rewind({ projectId, threadId, history, promptId, removedPromptIds })`. O store calcula `from`, os prompts removidos e os sobreviventes pelo stream, pede o patch e grava tudo num commit (truncate, marcador, documento, partes). Sem eventos do prompt ou sem patch → `undefined`.
- **Helpers puros no store.** `queueSnapshot` (com `storageQueueError`), a projeção de uso (`projectUsage`, `usageTotals`, …) e `delegatedResult` ficam em `store/` e saem por `store/index.ts`, porque o store os usa e é a camada de baixo. O domínio (57-WP-R2) deve importá-los daqui em vez de manter cópias.
- **Sanitização onde era `json()`/`storable()`.** Corpo dos eventos, `usage`, `configSnapshot`, texto do resultado e partes de histórico. Nome e `cwd` não são alterados.
- **Diferenças inalcançáveis pelo domínio.** `promptId` de um append é validado como UUID antes do commit (a coluna `uuid` recusava); uma leitura de eventos depois do contador responde `[]` (o protocolo recusa com `invalid_input`); `create` num Project ausente lança `Inactive project.` (antes um erro do Prisma); `saveHistory` numa Thread ausente rejeita; no `pending`, `text` que não é string vira `''` e uma `source` inválida vira `{ kind: 'user' }`, porque o schema do documento as exige; um campo ausente é omitido em vez de `paused: undefined` depois de um `prompt.resumed`.
- **Ordem de `usage().threads`.** A Thread pedida e depois os descendentes nível a nível, em ordem de `createdKey`. A CTE recursiva de hoje não define ordem dentro de um nível.
- **Exclusão acima de `maxBatch` (R12).** A exclusão de Project ou de subárvore é um commit só; acima do limite o backend recusa com `limit_exceeded` antes de escrever. O log dessa recusa fica com o domínio.
- **Testes.** `tests/store/store.conformance.test.ts` porta os casos de store de `persistence.test.ts` e roda na memória e, com `DORIC_TEST_DATABASE_URL`, no PostgreSQL com as migrações do `postgres`. `tests/store/support.ts` serve `storage/v1` sobre o backend (declaração adiada do tipo e validação do schema em cada `put`, como a fachada do core); como embrulha o backend de memória já conformante, o kit de conformidade não roda de novo. `progress.property.test.ts` compara o fold incremental e o fold preguiçoso (`pending: null`) com o fold antigo, sobre 60 logs gerados com semente e sobre o único log completo do baseline E2E (`13-replay`, a partir da sequência 5, em `tests/store/fixtures/baseline-logs.json`). `append-cost.test.ts` mede 10k `text.delta`: um commit e um read por evento, nenhum `get` ou `query` (G-12, parte do store; o custo de `secrets/v1.redactions()` é da 57-WP-R2).

## Etapas 5 a 7 — domínio e serviços do `runtime` (57-WP-R2)

- **Host part do `runtime` (`bundles/runtime/runtime/src/host/`).** `activate` define os quatro tipos de storage, registra `runtime.prompt-finished/v1`, monta as portas (57 §4.3) e chama `provideRuntime`, que provê `runtime/v1`, `runtime.threads/v1`, `runtime.workspace/v1`, `runtime.lease/v1`, `runtime.terminals/v1` e `terminal/v1` e define `runtime.hooks/v1`. A ativação não faz trabalho de dados; `recover` faz. `runtimeStores(storage, ports)` liga a participação do executor no rewind ao `executor/v1` com escopo no prompt reescrito. O build roda `cli.js build`, há `contracts-baseline` (`contracts.published.json`) e o teste roda `tests/**`.
- **Storage types em `provides`.** O CLI de build exige que todo tipo definido no `activate` esteja em `provides`; o manifesto ganhou `runtime.project/v1`, `runtime.thread/v1`, `runtime.history/v1` e `runtime.migration/v1` `@1.0.0` (o teste de manifesto da 57-WP-0 foi ajustado).
- **Domínio movido sem mudança de regra.** `service.ts`, `runner.ts`, `runtime.ts`, `prompts.ts`, `storage-pause.ts`, `cwd.ts`, `git.ts` (→ `git-credentials.ts`, com a resolução de credenciais), `usage-context.ts`, `colors.ts` e `events/serialization.ts` + `credentials/redact.ts` (→ `serialization.ts`) estão em `domain/`; `files`, `file-changes`, `git-status`, `branches`, a metade de sandbox de `resources` e `terminals` estão em `provisional/`. Fila, uso e `delegatedResult` vêm do `store/` (57-WP-R1), sem cópia no domínio. Mensagens de log e campos são os de hoje, agora por `log/v1` (`log.warn(mensagem, campos)`).
- **Sem retenção por perda de geração.** `held`, `pauseForGenerationLoss`, `resumeHeld`, `suspendForGenerationLoss` e `resumeAfterGenerationLoss` (D4-16) foram apagados, não movidos (X-12): o runner morre com a sua geração e a geração nova retoma por `recover`. O handover entre gerações vivas é da 57-WP-H.
- **Execução pelo `executor/v1`.** No despacho, sob o lock: `checkStorage`, `state(running)`, `executor.checkpoint({ history, promptId })` gravado por `saveCheckpoint` e `prompt.started`. A execução cria a `PromptSession` (história e evento redigidos com `eventJson`, história antes do evento, retry da última história e do evento pendente), liga o Host do prompt ao escopo (`bindings.attach`) e chama `run` com `{ signal }`; o vínculo é solto quando a execução assenta. O erro lido é `session.failure ?? erro`, porque a classe `ThreadPersistenceError` não atravessa o despachante. A guarda de 3 s de storage embrulha essa chamada.
- **Formato de história.** Um formato que o executor não lê faz o prompt falhar antes de qualquer execução (`agent.failed` e `prompt.finished` `failed`); `doric.diagnostics/v1` não tem método de relato, então o código `history_format_unsupported` vai num `log.error` com `threadId`.
- **Redação.** `redactor.current()` é `[...secrets/v1.redactions(), ...registrados]`; o token Git aplicado a um sandbox é registrado no runtime (não mais no cache do core). O stream de terminal é síncrono: usa a última lista lida (`latest()`), que dispara uma releitura em segundo plano, e cada início de terminal lê `current()` antes. Uma rotação chega ao terminal no pedaço seguinte à releitura, não no mesmo instante como hoje.
- **Credenciais Git por `secrets/v1`.** `byId` → `resolve`, `byKind` → `resolveByKind`, `byUnclaimedKind` → `resolveByKind(kind, { exclude })`, com as mesmas mensagens no `warn`. As credenciais reivindicadas são os campos `secret` da kind de cada provider, lidos em `models/v1.kind`, e só são lidas quando o token não tem escolha configurada.
- **`recover` uma vez por processo.** A segunda chamada devolve o primeiro resumo sem trabalho; `dispose` é idempotente.
- **Leituras de lease.** As leituras de Project usam `call.scope.projectId` e as de Thread (`git`, `branches`) usam `call.scope.threadId`; sem o id exigido, `ContractError('invalid_input', leaseScopeMessage)`. Como no adaptador da etapa 1, as recusas dos métodos de prompt (`inactive`) e de escopo são lançadas de forma síncrona pelo `execute`.
- **Hooks e exclusão grande.** `onProjectReadyHook` e `onProjectClosingHook` disparam sem espera depois dos commits `ready` e `cancelling`; uma falha do hook é ignorada. Uma exclusão recusada com `limit_exceeded` (R12) é logada (`Deletion exceeds the storage batch limit`) e propagada; nada é apagado.
- **Testes.** Os casos de `workspace-service`, `workspace-queue`, `coordination`, `workspace-lifecycle`, `storage-pressure`, `rewind`, `prompt-events`, `event-json`, `usage-context`, `workspace-cwd`, `workspace-github`, `workspace-resume`, `workspace-restart` (PostgreSQL), a metade de runner de `workspace-direct`, a metade de serviço de `workspace-files`, `workspace-git`, `branches`, `file-changes`, `terminals` e a metade de sandbox de `resources` foram portados e rodam pelos contratos do runtime, a partir de um bundle consumidor, sobre o store real (memória; `workspace-restart` em PostgreSQL), com fakes só nos contratos exigidos e um `executor/v1` roteirizado. `tests/contracts/adapter-parity.test.ts` repete a transcrição dourada da 57-WP-0 contra os provedores do runtime e é igual depois da normalização. Ajustes: o caso de entrada de máquina usa uma `source` `result` completa (o store da 57-WP-R1 normaliza uma incompleta para `user`), e uma segunda recuperação no mesmo processo devolve o primeiro resumo.

## Etapas 5 a 7 — handover de gerações (57-WP-H)

- **Plataforma, espera por geração ativa (G-11).** `ServiceRuntime.awaitProvider` é preenchido só no kernel. Um stub sem provider (não fixado por `whenAvailable`) de um contrato que bundles da geração fornecem, chamado enquanto nenhuma geração está ativa (janela de respawn), espera o próximo `onActive` e então despacha de novo. O sinal da chamada aborta a espera. Com o host parando, ou com uma geração `failed` (visão vazia), responde `unavailable` como antes. Nesse caso um método síncrono devolve uma promessa, o que só acontece para contratos remotos.
- **Plataforma, providers do kernel tardios.** `ServiceDirectory.observe` vê todo registro e remoção. Depois de um registro ou de uma remoção local no kernel, o gerenciador compara `kernelProviders()` com o que cada processo pronto já conhece (por microtask) e manda `provide`/`unprovide`. Um processo que ainda está iniciando é sincronizado no `ready`. O runner registra e retira esses providers remotos.
- **Plataforma, geração em drenagem (G-1, item 5).** `LayeredDirectory.setOverlay(next, { retain: true })` mantém o overlay anterior: seus registros saem da leitura (`providers`, `active`), mas continuam ativos para quem já os segura (`isActive`). A remoção chega aos inscritos só quando o próprio overlay remove o registro ou com `release`. O gerenciador retém na troca e solta quando a geração para ou morre. Assim, o `watch` do transporte sobre N vive até N parar, e o transporte não precisou mudar. Na queda da geração ativa não há retenção.
- **Plataforma, ordem na troca.** Em `#activate`, os listeners de `onActive` rodam antes da checagem de parada da geração substituída, e esta já está `draining`. Uma chamada iniciada no listener (o `drain`) conta como em voo e mantém N viva.
- **Dono do Project.** `runtime.project/v1` ganhou `owner: { generation, incarnation } | null`, opcional, interno e ignorado pelo mapeador. Nem a gravação do dono nem a sua limpeza movem `updatedAt`. É gravado na criação e no `claim` de `resumeProject`: o `claim` falha se o dono atual é outro processo vivo, e o Project fica em standby. A limpeza (`release`) acontece na parada do host, no término e no drain. O processo se identifica por `doric.generation/v1.describe()`; sem esse contrato (host de processo único) nenhum dono é gravado e tudo funciona como hoje. Os contratos foram para `runtime/v1@1.1.0` e `runtime.project/v1@1.1.0`, com o bundle em `1.1.0` (mudança menor; a baseline publicada continua em 1.0.0).
- **`recover` intacto e `recoverWith` novo.** Trocar a entrada de `recover` para uma tupla com `handover` opcional é mudança maior pela regra de semver do build. Por isso `recover()` ficou igual e entrou `recoverWith({ live })`, com o mesmo resultado em cache por processo. Os Projects cujo dono está em `live` ficam de fora de `threads.reconcile`, `projects.reconcile`, `resumeInterrupted` e `recoverProjects`: os dois `reconcile` do store aceitam um predicado de Project e o serviço aceita um `include`. Um dono que não está em `live` está morto e recebe a semântica de `host_restarted`.
- **`drain(released)` (API mínima).** O desenho dizia "N não inicia prompt novo". Ficou assim: N não traz Project nenhum de volta (`resumeProject` recusa), e entrada nova não chega a N, porque os stubs resolvem a geração ativa. Os prompts já enfileirados em N e os disparados por um prompt em execução (delegação) continuam rodando. Sem isso, um prompt pai que espera um filho travaria o drain. Quando um Project fica ocioso (sem tarefa e sem aquisição), N fecha os terminais (desvio já previsto em (6), só alcançável pelo `publish()` interno, D4-13), solta o lease, limpa o dono e chama `released(projectId)`. Estado de Project e Threads fica como está, sem `queued`. Um resultado de terminal em segundo plano que chegue depois é descartado com os terminais.
- **`adopt({ live })`.** Serializado depois da recuperação. Cada Project em standby cujo dono ficou nulo, ou não está mais em `live`, é adotado: com dono morto, primeiro o `reconcile` só daquele Project (com o log de hoje); depois `resumeInterrupted` só dele e `resumeProject` (`claim`, aquisição pelo nome, G-3).
- **Espera em standby, desvio registrado.** Toda operação que precisa do runtime local de um Project em standby espera a adoção: `exclusive` do Project, `projectFor` e as leituras de lease. Um prompt, uma pausa, um término ou `ssh` enviados a N+1 durante o drain esperam N terminar o prompt em execução, em vez de responderem `inactive` ou `unavailable`. Isso só acontece no `publish()` interno, e as rotas continuam sem timeout. As leituras de storage (`find`, `list`, eventos) não esperam. A lista de terminais de N+1 não mostra os terminais de N.
- **Kernel, `installHandover` em `agents/doric/src/lib/bundles/handover.ts`.** Em `onActive(g)`, de forma síncrona: `drain` em cada geração `draining` ainda não drenada, com `released → adopt` na geração ativa e outro `adopt` quando o drain termina; depois `recoverWith({ live: draining })` em g, que também cobre o respawn. Em `onLost` de uma geração em drenagem: `adopt` sem ela. A ligação ao boot (o boot continua chamando `recover()`) fica com a 57-WP-K.
- **Retenção por execução não adotada.** O runtime não toma `doric.generation/v1.hold` por prompt. O que mantém N viva é a chamada `drain` em voo, então `onLost` de N chega com `executions: []`.
- **Testes.** `packages/bundle/tests/handover.test.ts` usa processos reais e cobre: chamada esperando o respawn e abortada pelo sinal; provider do kernel registrado e removido depois do boot chegando à geração; o `whenAvailable` de um bundle do kernel mantendo o provider de N até N parar; e uma chamada iniciada em `onActive` mantendo N viva. `bundles/runtime/runtime/tests/domain/handover.test.ts` usa dois runtimes sobre o mesmo storage (memória e PostgreSQL) e cobre: E2 (N termina o prompt no seu lease, M espera e adota, um lease por vez, sem pausa), E3c (N morre drenando, M reconcilia com `host_restarted` e retoma) e donos órfãos de um host que caiu. `agents/doric/tests/handover.test.ts` cobre a orquestração do kernel.

## Etapas 5 a 7 — integração do kernel (57-WP-K)

- **Boot.** `bootstrap` → `sandbox_pool` (só as duas linhas de log, lidas do mesmo ambiente que o `sandbox-adapter` lê na geração; `src/lib/bundles/sandbox.ts` repete a leitura porque o pacote do adaptador não exporta `sandboxSettings`) → `bundle_load` (`startBundles` com `host-config` e `transport` embutidos, `assertStructural`, `Bundles loaded` com `bundleCount` 9, que exclui os embutidos) → `database_client` (`postgres.database/v1.connect()`; o kernel não lê mais `client()`, G-13) → `credential_activation` (carga das credenciais e `storageIdentity`) → `configuration_activation` (`host-config/v1.current()` e `models/v1.prepare(snapshot)`, G-16) → `workspace_reconciliation` (`runtime/v1.recover()` pela envelope; as três linhas de recuperação agora vêm do runtime por `log/v1`) → `installHandover` e `watchStructural` → `platform.ready()` → `network_binding`. A parada é `server.close`, `io.close`, `runtime/v1.dispose()`, remoção dos listeners e `platform.stop()` (o `postgres` desconecta por último).
- **`assertStructural`.** `runtime/v1`, `executor/v1`, `sandbox/v1`, `models/v1` e `host-config/v1` precisam de um provider cujo bundle esteja `active`, e o `transport` precisa estar ativo. Senão o kernel loga `Bundle recovery mode` com `reason` (`structural providers unavailable: …`), para a plataforma e o boot termina no caminho fatal de sempre, no estágio `bundle_load`. Uma geração que não sobe (bundles `quarantined` com `generation_failed`) cai no mesmo caminho.
- **G-5, perda estrutural depois do boot.** `watchStructural` reavalia o catálogo em cada `onActive`; se uma geração esgotou os respawns e a visão ativa ficou sem provider estrutural, o kernel loga `Bundle recovery mode` e sai com código 1, como o processo morria antes. Decisão recomendada pela revisão cruzada; ainda pede aprovação explícita (§5 do cross-review).
- **`host-config/v1` (X-6).** O `host-config` embutido continua em `src/lib/bundles/configuration.ts` (não em `configuration/**`, para não mudar os imports dos testes) e passa a fornecer `host-config/v1`, exigindo também `models/v1` e `tools/v1`. `current()` carrega o espaço de settings uma vez (uma carga que falha é tentada de novo na próxima chamada) e depois responde o snapshot ativo em memória, como o `ConfigService` antigo. `replace(body)` faz o pipeline do `PUT /config` na mesma ordem, numa fila serial: schema (`invalid`, `The Doric configuration is invalid.`), regra de credenciais (`invalid` com a mensagem de hoje), preenchimento pelo catálogo (`readModelProperties` de `core/contracts` lendo `models/v1.catalog` por provider), regra dos campos de tool sobre `tools/v1.list()` (`invalid`), `models/v1.prepare` da configuração candidata, gravação, e `models/v1.prepare` do snapshot gravado, que ativa essa revisão. Qualquer outra falha mantém a configuração ativa e responde `rejected` (503). O `warn` `Model catalog could not be read` agora é o do core, com `{ kind }` em vez de `{ providerId }`; logs não entram na comparação E2E.
- **Recusa de dados legados.** O kernel não loga o motivo da recusa do `connect()`: o caminho fatal continua logando só o estágio (`database_client`), como em toda falha de boot.
- **Plataforma, registros de contrato `many` pela envelope.** O kernel identificava um provider remoto por `(contrato, bundle)`. Os três registros `models.provider/v1` do `models-adapter` viravam um só no kernel, e `prepare` falhava com `Unknown provider kind: openrouter` no boot. Agora cada registro anunciado leva uma `key` estável do processo que o anuncia (`RemoteProviderDescriptor.key`), a chamada leva `record` e o `unprovide` leva a `key`; um descritor sem `key` funciona como antes. Teste em `packages/bundle/tests/envelope-records.test.ts`.
- **Plataforma, saída opcional pela envelope.** Uma saída `.optional()` de contrato definido por bundle publica só o schema interno, então o kernel recusava `undefined` (`project(id)` de um Project inexistente respondia 500 em vez de 404). A saída de um provider remoto agora aceita `undefined`: o processo que fornece já validou o resultado contra o seu próprio schema zod. Mesmo arquivo de teste.
- **Chamada em voo na perda da geração.** Uma requisição cujo despacho já estava no processo que morreu falha com ele (500 `internal_error`); as chamadas feitas depois da perda esperam o respawn (G-11). Antes da etapa 4 a mesma queda derrubava o host inteiro.
- **Composição e build.** `composition.json` habilita `runtime`, `direct`, `models-adapter` e `sandbox-adapter`; `build-bundles` e o `.Dockerfile` compilam e encenam esses bundles e o `transport` (embutido, sem encenação). `agents/doric` depende de `core` (contracts) e `transport`.
- **Testes.** Saíram os testes movidos (§13.2), `generations.test.ts` (sua premissa era o workspace no kernel) e `postgres-client.test.ts` (o kernel não usa mais o cliente Prisma). Sem port anterior, foram portados para `bundles/runtime/runtime/tests`: `usage`, `storage-persistence` e `storage-health`. `config.test.ts` cobre o novo serviço; `reference-race.test.ts` roda o pipeline e as credenciais diretamente (o mapeamento HTTP é do transporte); `secret-logs.test.ts`, `boot.test.ts` e `integration.test.ts` sobem o host compilado como processo, com PostgreSQL, sandbox Docker real e um endpoint OpenRouter roteirizado. `integration.test.ts` também mata o processo da geração durante um prompt e verifica a pausa `host_restarted` e a retomada pela geração respawnada (evidência E3 de ponta a ponta). O oráculo da etapa 7 foi congelado em `tests/helpers/legacy` (stores Prisma e dependências, com os tipos de sandbox vindos de `runtime/contracts`).
- **Configurações do sandbox sem deriva.** O kernel mantém a cópia de `sandboxSettings` (um bundle não tem entrada pública e o kernel não importa código de bundle); `tests/sandbox-settings.test.ts` compara a cópia com a do `sandbox-adapter` encenado em `dist/bundles` para vários ambientes, então uma mudança em só uma delas falha o teste.

## Etapas 5 a 7 — gate E2E (57-WP-E)

- **Normalização de frames (G-8).** O `compare.mjs` do harness normaliza só strings `stack`, dos dois lados: frames em `agents/doric/dist/` (kernel e bundles staged, como o `direct`, que saiu de `src/lib/agents/direct/`) viram `at <host-frame>`, com frames seguidos colapsados em um; frames em `/workspace/packages/` mantêm função e arquivo e perdem `:linha:coluna` (o pacote `agent` mudou na etapa 1). ## Etapa 8 — `packages/desktop` (8D)

- **Pacote escrito à mão no formato dos pacotes `tsc` existentes** (`storage`): `project.json` com `build`/`typecheck`/`test` por `nx:run-commands`, exports com a condição `@org/source`, `lib: ["es2022", "dom"]`, testes em `node --test`. Além de `.`, o subpath `desktop/protocol` expõe só os tipos e schemas zod do protocolo, para o main importar sem o código de DOM. O link em `node_modules` veio de `npm install`; as referências do `tsconfig.json` raiz ficam para o `nx sync` da 8I.
- **`WireError`/`WireScope` não são importados.** O envelope da etapa 4 não é exportado por `bundle/runtime`, e a 8D não altera o `bundle`. Por isso `protocol.ts` define `BridgeError { code, message, details? }` e `BridgeScope = Omit<CallScope, 'windowKey'>`, que têm a mesma forma.
- **`RemoteMethodSpec = { tuple, local, stream }`.** Junta a forma de 13.5 com o `stream` de 11.3a. `remoteMethodSpecFromSchema(input, output)` lê os JSON Schemas publicados. Uma tupla dá o tamanho [S8-12]. `x-doric-stream` no último item marca um stream. Qualquer outro `x-doric-local` (ou um output local de método que não é stream) torna o método `local`, porque pela ponte do desktop só cruzam JSON e streams. Uma tupla cujo membro inteiro vira marcador local publica `tuple: null`, o que não importa, porque o método é `local`.
- **Registros remotos próprios, sem `remoteRecord`.** O `remoteRecord` da etapa 4 depende de um `ProcessLink`. O registro da janela chama `desktop.call`/`subscribe`. A entrada é `z.tuple` de `z.unknown().optional()` com o tamanho publicado, ou `z.unknown()`, e a saída é `z.unknown()`. A validação real fica no main (ajv) e no provedor. Sem ajv no renderer: o CSP empacotado não tem `unsafe-eval`. Um abort envia `cancel(id)` e espera a resposta do main (aviso, como no envelope). Um método de stream envia `subscribe` com a tupla sem o listener e devolve um `Disposable` síncrono. O primeiro `end` encerra o observer, e eventos depois dele são descartados.
- **`scope.windowKey` local por um `Directory` da janela.** O `dispatch` da etapa 1 chama `createHopCall` sem `windowKey`, e mudar isso exigiria editar o `bundle`. Em vez disso, `WindowDirectory` embrulha os registros locais (não os remotos), e cada `invoke` recebe uma call filha com `windowKey` = chave da janela, criada por `createHopCall({ arg: call, windowKey })`. A call herda sinal, deadline e geração; o trace ganha um span filho. O splash (`key: null`) usa o diretório simples. Chamadas que saem da janela continuam sem `windowKey`, que o main preenche.
- **`doric.tokens/v1` local como registro direto no diretório.** `definePlatformService` não é público em `bundle/contracts`. O registro usa principal `doric`, versão `PLATFORM_VERSION` e o mesmo schema da especificação de plataforma. Os demais (`catalog`, `bundle`, `log`, `diagnostics`) vêm de `providePlatformServices`, sem os membros de distribuição.
- **Diagnóstico encaminhado por `WindowDiagnostics`**, uma subclasse de `DiagnosticsStore`. Ela envia, fire-and-forget, em `doric.shell/v1.diagnostic`, os itens `{ kind: 'quarantine', bundleId, reason }`, `{ kind: 'report', entry }` e `{ kind: 'recovery', reason }`. `doric.shell/v1.log` recebe o `LogRecord` sem alteração. Falhas dessas chamadas são descartadas.
- **Comandos vindos do main (18.3 revisado) já na 8D.** `serveShellCommands` assina o stream `doric.shell/v1.commands` e executa `services.use(CommandsV1).execute(command, input)` com o principal `doric`. Em seguida responde `commandResult` com `{ id, ok: true }` ou com `{ id, ok: false, error }`. Sem um provedor `commands/v1` no cliente, o que vale para a etapa 8 com o legado, a resposta é `unavailable`.
- **Teclas.** A tabela de `doric.shell/v1.keybindings` é `{ key, command }[]`, com `key` no formato de acelerador do Electron. `CmdOrCtrl` é Meta no macOS e Control nos outros sistemas, e os modificadores precisam bater exatamente. Uma tecla que casa chama `keybinding({ key })` sem esperar a resposta e chama `preventDefault()`. Com a tabela vazia da etapa 8, nada é interceptado (R9).
- **Bootstrap.** O `bootstrapWindow` aceita `importPart` e `keyTarget` injetáveis, além de `desktop` e `document`, para os testes. Um erro em qualquer passo até o `mount` gera `reportFailure({ kind: 'bootstrap' })`. Com o core em quarentena na janela `workspace`, gera `reportFailure({ kind: 'core', bundleId, message })`, em que `message` junta as razões com `; `. O flush passa `request.deadline` para o `onFlushHook` quando o deadline é maior que zero (revisão da etapa 9). Os `<link>` de CSS recebem `data-bundle` com o ID do bundle.

## Etapa 8 — plataforma Electron (8F)

- **O main faz o papel de kernel pelos tipos públicos.** `bundle/runtime` passa a exportar o envelope da etapa 4, o runner (`runGeneration`), `definePlatformService` e `platformContracts`: o main fornece serviços `doric.*`, que bundles não podem, e por isso eles continuam fora de `bundle/contracts`. - **Hooks de ciclo de vida por `hooks/v1.execute(AppHooksV1, …)`.** `runGeneration` não trata as mensagens de controle `lifecycle`, e o runner é do `packages/bundle`. O main chama então o `hooks/v1` anunciado pela geração com o caller `doric`, o dono de `AppHooksV1` (o codec cruza `AppHooksV1` por identidade). Sem provedor, `onBeforeQuitHook` permite e os demais não fazem nada, como em 13.3.
- **Uma instância de `bundle/contracts` por geração.** O runner é um build esbuild com `splitting` de três entradas: `generation-runner.mjs` (registra `module.registerHooks` antes de qualquer módulo com `zod`), `generation-runner-main.mjs` e `generation-contracts.mjs`. No processo, `bundle/contracts` resolve para `generation-contracts.mjs`, que divide os chunks com o runtime do runner. O `bundle@1.0.0/contracts.js` da plataforma não serve aqui, porque o runtime importa nomes internos que `contracts/index.ts` não exporta. `zod` fica externo e resolve para os arquivos da plataforma, e `<id>/contracts` para o cache. O hook também marca como ESM os `.js` da plataforma e do cache, que não têm `package.json` com `type`.
- **Canal do utility process.** `child.postMessage` e `process.parentPort` (clone estruturado) em vez de um par `MessageChannelMain`. `stdio: 'inherit'`, e os argumentos do runner (mapa de imports e partes) seguem em argv, em JSON base64. Uma saída depois do `ready` larga os itens e atalhos da geração e reinicia o processo uma vez, sem novo `onAppReadyHook`.
- **Ponte do host `/doric/bridge` (contrato com a 8H).** Cada mensagem do envelope é emitida sob o nome do seu `kind`, levando a mensagem inteira: `call`, `cancel`, `subscribe` e `unsubscribe` do desktop, e `result`, `event` e `end` do host. Sem conexão, ou com o deadline vencido, a chamada responde `unavailable` / `Doric backend is unavailable.`, e uma perda de conexão encerra os streams com `disconnected`. Uma recusa do servidor (middleware do namespace), que o Socket.IO não repete, também é tentada de novo a cada 1 s (P4).
- **Artefatos.** O cache baixa todos os arquivos distribuídos de todo bundle não desabilitado, e não só as partes desktopMain e client, porque `<id>/contracts` e os schemas de qualquer bundle podem ser necessários (o desktop do core importa `core/contracts`). Cada arquivo passa por staging, `fsync` e `rename`. Na falha de verificação, o bundle fica em quarentena com `invalid_part` e a mensagem `artifact hash mismatch: <path>`.
- **`distributionFiles` inclui o fecho de imports relativos de `contracts/**.js`** (`packages/bundle/src/loader/distribution.ts`). O `core/contracts`reexporta`host/models/catalog.js`, e sem esse arquivo o desktop não carregava `core/contracts`. O teste fica em `distribution.test.ts`.
- **Menu: o padrão do Electron 44 não tem Help.** A comparação no próprio Electron (`Menu.getApplicationMenu()` no `ready`, sem empacotar) mostrou App, File, Edit, View e Window. Por isso o papel `help` só aparece com itens contribuídos, e os quatro links de S8-15 não são reproduzidos (S8-15 revisado). Uma geração que não definiu esqueleto usa o último definido com os itens dela, porque o core só define o esqueleto em `onAppReadyHook`, que uma geração em segundo plano não recebe.
- **`ready()` antes do `onAppReadyHook`** (uma janela aberta na ativação, como o núcleo mínimo de teste) conta como o primeiro `ready()` assim que o hook dispara.
- **Evidências de quarentena da parte client (22.1).** Um contrato que nenhum bundle fornece dá `missing_dependency` na resolução, não `dependency_quarantined`. Esse código aparece quando o provedor da dependência falha. Por isso o caso fica em `desktop/client/tests/bootstrap.test.ts` (provedor que falha na ativação, dependente em quarentena, demais ativos e `ready()` chamado), e não em `activate.test.ts`, que não chega ao `ready()`. Uma quarentena do desktop para o splash em `bundle-failure` até "Continue without them". Por isso o relatório `doric.diagnostics/v1.report` ao host falso é conferido em `tests-electron/splash.test.ts`, e não junto dos bundles de `bridge.test.ts`.
- **Quit (17.3).** Um close retido pelo protocolo cancela o quit do Electron. Quando a janela fecha de fato durante um quit já decidido, o main chama `app.quit()` de novo.
- **Migração da seleção.** A página estática de `doric://app` é `splash@<v>/blank.html` (da 8F), e não `shell@<v>/blank.html` (do renderer). O `localStorage` de `file://` é lido de `assets/legacy-origin.html`.
- **Migração de origem com dono no core [fechamento de vazamento de plataforma].** O código de migração de `doric.selection` e o nome do marcador `selectionOrigin` saíram da plataforma. A plataforma oferece `doric.migrations/v1.storage({ key, marker })`, só para `desktopMain`, e devolve `migrated`, `none`, `skipped` ou `failed`. O chamador escolhe só a chave e o marcador; a página de origem `file://`, a página `doric://app`, o modo empacotado e o registro de falhas são da plataforma, e o contrato não aceita nenhum campo de origem. O marcador é um registro do estado (`migrations`), com nomes limitados por padrão e no máximo 32 entradas; o arquivo de perfis existentes continua com `selectionOrigin: true`. O core (`bundles/foundation/core/src/desktop/migrations.ts`) envia `{ key: 'doric.selection', marker: 'selectionOrigin' }` e aguarda a resposta no `onAppReadyHook`, antes de abrir a janela primária; uma falha de chamada é registrada pelo core e não impede a janela. A chamada `DesktopPlatform.start(callback)` saiu: `main.ts` não passa mais migração. Mantido: copia só para perfis empacotados, nunca sobrescreve um valor de destino, roda uma vez, falha registra e marca como feita, e as janelas ocultas são fechadas. Diferença de log de diagnóstico: a linha de falha agora é `Storage origin migration failed` (antes `Selection origin migration failed`) e traz o marcador. Consequência de ordem: a migração roda quando o core chega ao `onAppReadyHook`; no modo de recuperação, sem core ativo, ela só roda quando um core ativar. O layout mantém a própria constante `doric.selection` para o `localStorage` da renderização; as duas copias devem coincidir.
- **Canais legados.** `senderIsAllowed(url)` aceita a origem `doric://app` em qualquer caminho [S8-1], e `registerWorkspaceHandlers` e `registerTerminalHandlers` deixam de receber `allowedUrls` e ganham `available()`. No modo `last-good-core`, todos respondem `Doric backend is unavailable.`. `doric:settings:flushed` e o push `doric:settings:flush` saem, e o `settings.onFlush` do preload roda na fase de flush do protocolo de fechamento. `doric:settings:open` executa `core.open-settings/v1` no desktopMain com o caller `doric`.
- **Preload.** Uma janela sem handler de fechamento, ou cujo handler de veto falha, responde `{ allow: true }`, para nunca prender a janela. Os nomes dos canais são literais no preload sandboxed, e um teste os compara com os de `desktop/client`.
- **Dispatcher.** Um bundle sem parte cliente ativa na geração da janela recebe `unavailable`. Um contrato `doric.*`, ou fora de `requires` ∪ `provides`, recebe `undeclared_requirement`. Uma janela cujo shell é de uma geração que o main não retém mais é recarregada, e a chamada responde `unavailable`. Num stream desktopMain, o listener cruza o link como função (codec de callback), então o `end` do provedor não atravessa; o fim chega com a saída do processo. O `scope.windowKey` vindo da janela já é recusado pelo schema estrito, e o main o preenche.
- **Tokens e chrome.** `doric.tokens/v1` replica o `resolvedVariables` do `desktop/ui` (`--doric-window-background: var(--background)`), e um teste fixa a igualdade. `titleBar: 'none'` tem área segura zero. O `WindowCatalog` sem `storage` publica `hostId: ''` e `storageGeneration: 0`.
- **Build do main.** `app/doric/webpack.config.js` restringe o `ts-loader` a `src/`, porque os pacotes do workspace vêm do `dist` ESM e recompilá-los como CommonJS trocava imports por `require`. `externalDependencies: ['socket.io-client']` embute `bundle`, `desktop/client`, `zod` e `ajv` no main e no preload sandboxed. As saídas do `build` são listadas por arquivo, porque `assets/platform` e o runner são de outros alvos. `build-runner` (esbuild) emite o runner e o splash em `dist/app/doric/assets`.
- **Testes Electron.** `doric-app:test-electron` roda `node:test` com `isolation: 'none'` dentro do main do Electron, num perfil temporário. Uma execução em processo só termina no `beforeExit`, que o Electron nunca alcança, então o runner o emite quando todos os testes de topo terminaram. O relógio do harness pula os 5 s do splash (o tempo mínimo é coberto pelo teste unitário com relógio falso). O host falso é um servidor Socket.IO no mesmo processo.
- **Perguntas Q1–Q5 conforme a revisão cruzada §6.** Q1: o main grava só o último caminho por chave, em `doric/windows.json`, sem bounds. Q2: o prazo de 30 s e a espera por "Continue without them". Q3: perfis de desenvolvimento não migram. Q4: os botões de recuperação aparecem e chamam `doric.catalog/v1.disable({ bundleId })` e `resetComposition()` no host (HR-6). Se a chamada falha, a falha fica no log e o mesmo estado volta. Q5: o isolamento continua igual ao de hoje.

## Etapa 8 — ponte e catálogo do host (8H)

- **Seam no kernel em vez de provedor próprio no host.** `startKernel` ganha a opção `distribution(source)`, e o kernel a repassa a `providePlatformServices`, porque `doric.catalog/v1` é um único provedor da plataforma e o host não pode registrar outro. A `KernelDistributionSource` expõe o catálogo publicado e os estados vivos da geração que a chamada vê (0 = a ativa), as gerações retidas, a identidade de armazenamento e `onActive`. A lógica (HR-2..HR-4) fica em `agents/doric/src/lib/bridge/catalog.ts`.
- **`KernelPlatform.methodSpec(contract, method)`.** A ponte precisa do spec do provedor ativo para espalhar a tupla de entrada e distinguir um método stream (`x-doric-stream`). Sem provedor, a chamada segue para o stub, que responde `unavailable` (ou espera a geração em respawn, G-11).
- **Chamadas da ponte rodam como principal `doric` na visão ativa.** O stub valida a entrada com zod, aplica `scope` e `deadline` da mensagem, e o `cancel` aborta a chamada. O `caller` e o `trace` da mensagem não são propagados (a chamada abre um trace novo). Na etapa 8 o desktop só faz saltos de plataforma (`caller` `doric`, D-14); a allowlist por caller é a HR-10 (etapa 9).
- **`call` num stream e `subscribe` num método comum respondem `invalid_input`**, como no dispatcher do desktop. Uma mensagem malformada recebe `invalid_input` (`result` ou `end`) quando tem `id`.
- **Arquivos por geração, estados ao vivo.** Os hashes são calculados uma vez por catálogo publicado (`distributionFor`). A cada `distribution()` o host recalcula o snapshot, os estados, os motivos e o `storage` (HR-8). `artifact` procura o hash nas gerações retidas e na ativa, relê o arquivo e confere o SHA-256 antes de servir. Um hash desconhecido, ou cujo arquivo mudou no disco, responde `not_found`.
- **`watch` emite só quando o número da geração ativa muda.** Um respawn reativa a mesma geração e não publicou nada.
- **`hostBoot`.** `randomUUID()` por processo do host, criado em `startBundles` (opção `hostBoot` para testes).
- **Log de startup inalterado.** A linha `Network interfaces configured` continua com `['/status', '/projects', '/threads']`, por paridade. `/doric/bridge` não entra nessa lista.
- **HR-7.** O Dockerfile não muda de comandos: o `cli.js build` de cada bundle já constrói as partes com esbuild (devDependency da raiz), e o `stage` copia o `dist` inteiro. Só o comentário foi atualizado. O teste confere que o core em `dist/bundles` tem `desktop/index.js` distribuído.

## Etapa 8 — ações de recuperação da composição (HR-6)

- **Arquivo de overrides ao lado da composição (Q4).** O host guarda as ações de recuperação em `composition.overrides.json`, no diretório da composição ativa (`compositionOverridesPath(DORIC_COMPOSITION)`), nunca no banco do produto. O formato é `{ "disabled": string[] }`, estrito. A gravação é atômica: um arquivo temporário renomeado por cima. O arquivo da composição nunca é reescrito. O `.gitignore` ignora `composition.overrides.json`, porque o padrão de desenvolvimento cai em `agents/doric/`.
- **Aplicação em toda leitura do catálogo.** `readHostCatalog` lê os overrides depois da composição (opção `compositionOverrides` de `StartHostOptions`) e tira de `enabled` cada bundle desativado. Isso vale no boot e em cada `publish()`. O catálogo então mostra o bundle com o estado `disabled` que a resolução já usa para bundles fora de `enabled`, e o desktop o tira de `enabled` [S8-8]. Um arquivo ilegível vira um problema do catálogo (`issues`) e é ignorado: a composição como escrita vale, para que um arquivo ruim não prenda o host.
- **Servidas pelo kernel.** `doric.catalog/v1` ganha `disable({ bundleId }): void` e `resetComposition(): void` (contrato e schemas em `contracts/platform.ts`). O kernel só os registra com `compositionOverrides`; `startBundles` sempre passa o caminho (opção `compositionOverridesPath` para testes). A lógica fica em `process/composition-actions.ts`: as ações rodam uma por vez, gravam ou apagam o arquivo e chamam `generations.publish()`.
- **Recusas.** `disable` de um bundle fora do `enabled` da composição escrita responde `not_found`. `disable` do core responde `invalid_input`, porque sem core o host não sobe e não pode mais receber "Return to default composition". Nos dois casos nada é gravado.
- **Mudança no kernel.** Quando a publicação responde `kernel_restart_required` ou `failed`, o override continua gravado e vale no próximo boot. A chamada responde `unavailable` com o motivo, e o desktop registra `Recovery action failed` e volta ao mesmo estado.
- **Linhas de log** (log da plataforma): `Bundle disabled` `{ bundleId, path }`, `Composition reset` `{ path }`, `Composition published` `{ generation, path }`, `Composition change applies at the next host start` (warn, `{ status, reason, path }`) e `Composition overrides replaced` (warn, quando `disable` substitui um arquivo ilegível). Os documentos não definem linhas de log para a HR-6; estas são as mínimas para auditar as ações.
- **Desktop sem mudança.** A 8F já chamava os dois métodos. Os testes Electron do splash usam um host falso que serve os métodos e publica uma nova distribuição; os dois botões chegam à janela `workspace`.

As fixtures dos testes portados ganharam `lastSequence` e `configRevision`. `projectColors` é uma cópia local com `satisfies`, e as `ref` de `runtime/v1` e `runtime.threads/v1` são montadas pelo ID em `api/host.ts`, porque o import map da janela não garante o módulo de contratos de um bundle do host.

Falhas da ponte (`unavailable`, `disconnected`, `generation_lost`) dão `Doric backend is unavailable.`; `invalid_output` e um cursor repetido dão `Doric returned an invalid response.`; qualquer outra dá `The request could not be completed.`. `threads.get` de um Thread que não existe dá `undefined`. Um delete repete a cada 500 ms enquanto o host responde `active` (porte de `retryWhileActive`).
- **Watch do Project.** `api/project-watch.ts` porta `project-events.ts` sobre `runtime/v1.watchProject({ projectId })`: um watch por janela, snapshot inteiro a cada assinatura, notícias de outro Project descartadas. Um fim com `disconnected` ou `unavailable` não mostra nada e reassina no próximo `connected` de `doric.connection/v1`, ou depois de 1 s se a conexão não caiu (o atraso de reconexão do Socket.IO). Um fim com outro erro mostra `The Project event stream failed.` uma vez e não reassina, como o `disconnect()` do servidor depois de `workspace:error`. Os `terminals` do snapshot ficam para a parte provisória.
- **Seleção na rota (§5.5).** `stores/route-selection.ts` porta o store de seleção: mesma regra `shouldWriteSelection`, mas grava `pathFor(seleção)` com `navigation.navigate`. É push quando o caminho é o da última seleção marcada pelo usuário (linhas, breadcrumb, criação, `beginThread` em outro Project) e replace nos demais casos. O restore de partida (`startRestore`) lê o Thread da rota, ou em `/` o registro legado. Um Thread restaurado entra na seleção da rota antes do settle, então o caminho não pisca para `/`.
- **Desvio: falha do restore.** O desenho manda manter o caminho e a chave legada quando a leitura falha. O código atual não fazia isso: o efeito de montagem já marcava `changed`, então o settle `failed` gravava a seleção da tela e apagava o valor guardado. Por paridade, o settle `failed` grava o caminho da seleção da tela (em geral `/`), e a chave legada é apagada em qualquer settle.
- **Navegação de fora (regra 5).** `routeIntent` é puro. Um Thread descrito é selecionado com a semântica de `selectThread`. Um Thread não descrito é buscado como no restore; se sumiu ou a leitura falhou, `rewriteRoute` devolve o caminho da seleção com replace. `/` com Thread selecionado deixa só o Project. As navegações do próprio store são ignoradas pelo ouvinte.
- **`layout.tabs/v1`.** O dono é `tabOwnerOf(rota, Project selecionado)`. A aba `element` guarda `element: object` no domínio, para os testes sem DOM. `open` de um id aberto só foca. `close` remove a aba e chama `ui.dispose`. Id desconhecido em `close`/`focus` não faz nada. Sem dono, `open` dá `ContractError('unavailable', 'No thread or project is selected.')`. As operações são síncronas e respondem promessas; uma recusa é rejeição.
- **`layout.workspace/v1`.** É local, com `thread(id)` em todos os Projects descritos, `selectedThread()` só quando a árvore descreve a seleção, e `subscribe` sobre o `workspaceStore` (qualquer mudança notifica).
- **Refresh.** `projectActivity` lê um terminal estrutural (`id`, `state`, `command`, `cwd`). O gatilho 1 (`onSandboxActivityHook` do chat) chama `refreshProject` na ativação do layout. Os casos de `changedSandboxProjects` foram para o chat.
- **Ativação.** O `index.ts` liga os adaptadores, o espelho de conexão, o watch do Project e os dois contratos, define `<layout-workspace>` e os hosts de portal, registra `/` e adiciona os itens de região (cwd, uso, novo terminal). A ligação final está em "Etapa 9 — integração e paridade".

Git: `missing` → `The thread was not found.`, `pending`/`inactive` → `{ repo: false, status }`. Branches sem sandbox dão a lista vazia com `Preparing environment…`/`Environment unavailable.`. Na troca, `refused` mostra a mensagem do host e `inactive` dá `The thread cannot perform this operation.`. Usage `undefined` → `The thread was not found.`. As validações de resposta do cliente REST foram portadas (`Doric returned an invalid response.`).
- **Terminais.** Toda falha de terminal mostra `Doric could not complete the terminal request.`, como o cliente REST de terminais (inclusive `create` sem sandbox, `input`/`resize` de terminal sumido). Desvio: uma ponte perdida (`unavailable`, `disconnected`, `generation_lost`) mostra `Doric backend is unavailable.`, como as demais chamadas ao host (etapa 8 §14.3). A entrada é serializada por terminal no adaptador (porte de `terminal-ipc.ts`).
- **Streams de terminal.** `terminals/api/terminal-watch.ts` porta `terminal-events.ts` e os ouvintes do preload sobre `runtime.terminals/v1.watchProject`: um ouvinte por Project ou terminal (o mais novo substitui), o snapshot do terminal lido só para achar o Project, o snapshot do stream relê e envia a saída, buffer de 2 097 152 caracteres, reconciliação por offset e geração incrementada na queda. Uma queda (`disconnected`/`unavailable`) é silenciosa e reassina no próximo `connected`, ou depois de 1 s, como no watch do Project (WP2a). Qualquer outro fim mostra `The terminal connection failed.` (o `connect_error` do socket) e não reassina.
- **Monaco e xterm.** São carregados com `import()` quando o editor ou o terminal monta (`files/components/monaco.ts`, `terminals/components/xterm.ts`), então nenhum módulo toca o DOM na importação. O worker do editor é `src/client/workers/editor.worker.ts` (fora de `provisional/`, porque o build só compila workers dessa pasta), criado com `new Worker(new URL('./workers/editor.worker.js', import.meta.url), { type: 'module' })`. Como o Monaco chega depois do primeiro render, os editores são criados com o texto do render corrente e reaplicam idioma, texto e layout quando ficam prontos. O CSS do Monaco e do xterm é extraído pelo esbuild e anexado ao CSS do layout.
- **`desktop/ui/cmdk`.** O `BranchPicker` usa `Command.Input asChild` do cmdk. Uma cópia do cmdk dentro do bundle não enxergaria o store do `Command` do `desktop/ui`, então o `desktop/ui` ganhou a entrada `./cmdk` (`src/cmdk.ts`, só `export { Command as CommandPrimitive } from 'cmdk'`), servida pelo import map como as demais.
- **Itens de região.** `layout-cwd` (rodapé, 10), `layout-thread-usage` (rodapé, 30) e `layout-new-terminal` (cabeçalho, 10) são hosts de portal (`portalHosts` do `desktop/ui/react-element`) definidos e registrados na ativação. `ProvisionalPortals` (recebe Thread, `changes`, `onShowChanges` e `onNewTerminal`) renderiza o conteúdo neles e deve ficar na view do workspace. O botão "New terminal" sai do `WorkspaceHeader` quando o cabeçalho ganhar a região `layout.header`; até lá os dois coexistem só no código, porque nada monta a moldura.
- **Testes.** As 10 suítes do renderer (`change-tree`, `cwd`, `file-diff`, `files`, `oklch`, `resources`, `sandbox-reads`, `terminals`, `thread-git`, `usage`) vieram para `bundles/desktop/layout/tests`. Novas: `terminal-watch.test.ts` (os 3 casos de `terminal-events` e as regras do stream) e `provisional-adapter.test.ts` (estados, guardas e mensagens por desfecho).

## Etapa 9 — bundle `settings` (WP3)

- **Pacote.** `bundles/desktop/settings` (projeto `bundle-settings`) só tem parte client; não há `src/contracts` nem `contracts.published.json`. O `tsconfig.json` é o typecheck do client (`noEmit`); os testes sem DOM usam `tsconfig.spec.json` e os de janela (happy-dom, core e settings construídos) `tsconfig.client-spec.json`. O alvo de teste usa `--test-force-exit`, porque os timers do React Query mantêm o processo vivo depois do último teste.
- **Manifesto.** `requires` usa `host-config/v1` no lugar de `core.configuration/v1`, como a revisão cruzada fixou. O ref é declarado no adaptador por id (`ref('host-config/v1')`) e só os tipos vêm de `runtime/contracts`, que não está no import map da janela. `tools/v1.catalog()` é o de WP-H.
- **Adaptador (`api/settings-api.ts`).** Junta as três camadas que a chamada antiga atravessava, com as mesmas mensagens: os guardas de `validation.ts` (`desktopConfiguration` descarta Tools e `execution.maxToolResultChars`, e omite referência vazia ou `null`), as validações das rotas REST (`/providers/models` valida a draft contra `models/v1.kind` antes do catálogo; `/credentials` valida campos e UUID) e os leitores de resposta de `api.ts`. Falha de ponte `unavailable`/`disconnected`/`generation_lost`/`protocol_error` vira 'Doric backend is unavailable.'; `invalid_output` vira 'Doric returned an invalid response.'; o resto vira a mensagem do handler final, 'The request could not be completed.'. No `replace`, qualquer outra exceção vira 'The Doric configuration could not be activated.', como a rota.

As linhas da nav são portais nos hosts `settings-link` que a `<core-region name="settings.sections">` cria, filtradas pela busca por label e descrição. O `SidebarMenu` fica montado com `hidden` quando nada casa, ao lado de "No sections match", para a região não descartar os itens. A seção ativa é um portal no host que o `<core-outlet>` da página segura, com `key` da seção, de modo que o estado local se perde na troca, como antes. Trocar de seção, por clique ou por histórico, fecha a página de provider.
- **Flush no fechamento.** `onFlushHook` é registrado com os serviços do elemento enquanto a página está montada, e vale o prazo de 1,5 s da plataforma.
- **Picker de execução.** `<settings-execution-picker>` tem raiz própria com `StrictMode`, `QueryClientProvider` (um cliente por bundle e janela) e `TooltipProvider`. Não tem flush nem toast. Os toasts da página usam `desktop/ui/sonner`, a mesma loja do `Toaster` que a página monta.
- **CSS.** `src/client/styles.css` gera as utilities que os componentes do settings usam, sobre o tema da plataforma, sem regras próprias. Risco aceito: as utilities ficam numa segunda folha depois de `theme.css`, e a ordem entre duas classes conflitantes de folhas diferentes pode divergir da folha única do renderer. A conferência fica para o CDP.

## Etapa 10 — contratos do host (10R)

- **Runtime `1.3.0`.** `runtime.lease/v1@1.1.0` ganha `withLease(task)` (R-5.1), `runtime.workspace/v1@1.1.0` ganha `withThread(threadId, options, task)` (R-5.2), `runtime.threads/v1@1.2.0` ganha `enqueueTerminalResult`/`failTerminalResult` (R-5.3), `runtime.hooks/v1@1.1.0` ganha `onThreadsClosingHook` (R-5.4) e o contrato novo `runtime.usage/v1@1.0.0` tem `read(threadId)` (R-5.5). `withLease` e `withThread` são só locais: a tarefa é `callback` e a resposta é `object` (`LeaseOutcome`, `ThreadTaskOutcome`; o nome `ThreadOutcome` já existia em `model.ts`).

- **Redação.** O registro redige por chunk com o último `secrets/v1.watchRedactions` e relê `secrets/v1.redactions()` antes de cada início (o `redactor.current()` do runner). Os segredos que o `runtime` só registra no próprio `redactor` (token Git aplicado ao sandbox) não chegam ao bundle; o `runtime` precisa também chamar `secrets/v1.view().addRedaction` antes da 10L ligar o bundle.
- **`run`.** Sem `threadId`/`promptId` no escopo, ou com `withThread` diferente de `ready`, ou com a Thread fechando, lança `Thread is inactive.`. O resultado em segundo plano vai a `enqueueTerminalResult` sem `call` (o prompt de origem já acabou); a rejeição do resultado ou da entrega chama `failTerminalResult`.
- **Limpeza.** O handler de `onThreadsClosingHook` registra `Terminal cleanup failed` com `{ projectId }` (o runner usava `{ threadId }` na suspensão de uma Thread e `{ projectId }` no fechamento) e nunca rejeita. Requer `log/v1@^1.0.0`, `secrets/v1@^1.1.0`, `runtime.threads/v1@^1.2.0` e `runtime.hooks/v1@^1.1.0` (as versões que trazem o que é chamado).
- **Ferramenta.** `src/host/tool.ts` é a cópia literal de `files/src/host/tools/terminal.ts` sem o fallback de comando simples [D10-12]; sempre chama `terminal/v1` do próprio bundle no escopo do prompt. A 10L remove a do `files`.
- **Cliente.** Entrada `index.ts` (o builder só reconhece esse nome). Ordem do botão no `layout.header` é 10, a do provisório (o desenho dizia 100; o `files-toggle` é 200). O estado manual (`manualId`/`manualIds` por Thread) passa ao store do bundle; a seção inferior é mostrada pela ativação (`setBottomVisible('terminal-manual', …)`), não pelo elemento, porque os itens de `layout.main.bottom` só montam com a seção visível. As linhas seguem o Projeto de cada Thread na primeira chamada de `count` (o renderer seguia todos os Projetos carregados) e calculam a profundidade pelos `parentThreadId`. O clique navega para `/projects/<p>/threads/<t>` antes de mostrar o terminal manual ou abrir a aba `terminal:<id>`. Uma mudança da atividade (id, estado, comando, cwd) da lista de um Projeto chama `files.refresh/v1.request(projectId)`.
- **Regiões só na 10N.** Os quatro elementos são definidos na ativação; `registerTerminalSurfaces` (itens `terminal-new` e `terminal-manual` e as linhas `terminals`) é chamado pela 10N ao remover os terminais provisórios do layout; juntos, apareceriam dois botões e duas listas de linhas.
- **Ponte.** A allowlist (`agents/doric/src/lib/bridge/allowlist.ts`) ainda lista `runtime.terminals/v1`; a 10L/10N precisa acrescentar `terminal/v1` (`list`, `create`, `snapshot`, `input`, `resize`, `stop`, `watchProject`, nunca `run`).

## Etapa 10 — bundle `git` (10G)

- **Esquemas próprios em `git/contracts`.** Os tipos vêm de `runtime/contracts` (só `import type`), mas os esquemas zod são escritos no módulo: a parte cliente carrega `git/contracts`, e o mapa de imports da janela não garante o módulo de contratos de um bundle de host (mesma escolha de `files`).
- **`git.changes/v1` com `{ projectId, cwd? }`.** O escopo é o diretório de trabalho cru, não `root`: é a forma que o consumidor (`files`, árvore decorada) já usa e a mesma de `files.sandbox/v1`; a chave `['files', p, 'changes', cwd]` não muda.
- **Busca de ocupado por `runtime.terminals/v1`.** O `terminal/v1@1.0.0` ainda não tem `list`; o host usa `runtime.terminals/v1.list(projectId)` por `whenAvailable` (o mesmo registro que o runtime consultava), com o filtro de hoje (`state !== 'exited'` e `origin === 'agent' || command !== 'bash'`). Quando o `terminal` dono do registro entrar (10L), a fonte troca para `terminal/v1.list` sem mudar o serviço (função `TerminalList`).
- **`fileDiff` inválido antes do lease.** Repositório ou caminho absoluto, com `..`, com NUL ou caminho vazio respondem `{ status: 'ready', value: { status: 'invalid_path' } }` sem chamar `withLease`, como a rota respondia 422 em qualquer estado do lease.
- **Leituras de Thread por `withThread`.** `status` usa `{ exclusive: false, refreshHint: true }`; `branches` e `switchBranch` usam `{ exclusive: true }`. O `withThread` também responde `inactive` para um registro terminal, que o `git`/`branches` do runtime não checavam explicitamente (uma Thread terminal não tem runtime vivo, então a resposta é a mesma).
- **Troca de branch espera o refresh.** Como o `refreshProject` que o `onSuccess` aguardava, o sucesso pede `files.refresh/v1.request(projectId)` (os outros leitores da janela) e aguarda o refresh do próprio cliente; sem `files.refresh/v1`, o retry e o refresh caem no cliente do `git`.
- **Versioning.** O elemento lê `settings.config/v1` (`draft`, `setDraft(update)`, `subscribe`) por ref estrutural local, porque `settings` não publica módulo de contratos; a lista de credenciais é `secrets/v1.list` na query `['credentials']` do cliente do `git` (uma leitura a mais que o cache do settings, invisível). Uma falha da lista deixa a seção sem opções, como antes.
- **Elementos com raiz própria.** Cada elemento envolve `StrictMode`, o `QueryClientProvider` do bundle e um `TooltipProvider` (a raiz React do elemento não herda os do layout); a aba de comparação tem a raiz `flex h-full min-h-0 flex-col`, como a aba de arquivo do `files`.
- **Superfícies só na 10N.** Os cinco elementos, o serviço `git.changes/v1` e o comando são registrados na ativação; os itens `layout.panel` (`changes`, 200), `layout.footer` (`git-cwd`, 10), `settings.sections` (`versioning`, 40) e a rota `/settings/git` saem em `registerGitSurfaces`, que a 10N chama ao remover o Changes e o `layout-cwd` provisórios do layout e a seção Versioning do `settings` (juntos, apareceriam dois de cada).
- **Ponte.** A allowlist (`agents/doric/src/lib/bridge/allowlist.ts`) ainda não lista `git.commands/v1`; a 10L/10N precisa acrescentar `status`, `branches`, `switchBranch`, `changes` e `fileDiff`. As rotas de transporte continuam nas leituras de `runtime.lease/v1` até a 10L.

## Etapa 10 — troca do host (10L)

- **Composição.** `agents/doric/composition.json` habilita `openai`, `openrouter`, `codex`, `docker`, `terminal`, `usage` e `resources` no lugar de `models-adapter` e `sandbox-adapter`. `build-bundles`/`stage` e o `.Dockerfile` constroem e preparam também `firecracker` (preparado, não habilitado), `web` e `notifications`. `notifications` fica fora da composição até a 10N (decisão da 10K: com o `announce` do chat ainda ativo, cada aviso apareceria duas vezes). `core/tests/models.test.ts` passa a usar os três bundles de provedor.
- **`DORIC_SANDBOX_PROVIDER` [D10-9].** Sem `DORIC_COMPOSITION`, `firecracker` faz o kernel bootar a composição enviada com `firecracker` no lugar de `docker` (objeto passado a `startKernel`; os overrides continuam ao lado do arquivo). Com `DORIC_COMPOSITION`, a composição do operador decide, e a linha `sandboxProvider` dos logs reflete o bundle habilitado. Motivo: o `transport` é estrutural, e com `requires` um bundle de recurso desabilitado pela ação de recuperação "Desabilitar bundle" ou em quarentena derrubaria o host (`kernel_restart_required`); um stub de `whenAvailable` não liga escopo, e as leituras de Projeto precisam de `call.scope.projectId`. O `transport` não fornece mais contrato (`resources/v1` é do bundle `resources`) e não declara os contratos de recurso.
- **Socket `/projects`.** Os avisos de terminal vêm de `terminal/v1.watchProject`: um stream por Projeto assinado, aberto antes da leitura do snapshot e fechado com o último socket; um novo provedor (troca de geração) é assinado de novo para cada Projeto. O snapshot do próprio stream é ignorado (o socket lê o seu com `terminal/v1.list`); `terminal:removed` mantém a forma `{ projectId, threadId, terminalId }`.
- **Terminais.** O `runtime` deixa de fornecer `terminal/v1` (versão do bundle 2.0.0, `contracts.published.json` regravado); a ferramenta `terminal` é a do bundle `terminal` (ordem 500) e sai do `files`. `runtime.terminals/v1` e o snapshot `terminals` dos watches do runtime delegam a `terminal/v1` enquanto houver provedor (G-9), então as janelas que ainda leem o contrato provisório veem as mesmas sessões das rotas; sem provedor (testes do próprio runtime) responde o registro provisório. As duas refs (`TerminalV1`/`TerminalServiceV1`) continuam até o registro provisório ser apagado. A leitura deprecada `runtime.lease/v1.branches` ainda consulta o registro provisório (vazio em produção) para terminais ocupados; `git.commands/v1` usa `runtime.terminals/v1.list`, que delega.
- **Leituras deprecadas mantidas (R-5.1 revisada).** `runtime.lease/v1` (`files`, `tree`, `file`, `diff`, `changes`, `fileDiff`, `resources`, `git`, `branches`) e `runtime.threads/v1.usage` (com o preenchimento de capacidade do runtime) continuam para os elementos provisórios do layout até a 10N; as rotas não as chamam mais.
- **`web` habilitado sem exclusão.** A composição habilita `web` logo depois de `files`; a ferramenta `web` (700) e a skill `web-research` (1200) passam a vir do bundle `web`, com o mesmo corpo de requisição ao modelo (ordem global D10-5). Os originais de `files` (`tools/web.ts`, `tests/web.test.ts` e `skills/12-web-research`) foram removidos, e o `host/index.ts` não registra mais `web`; nenhuma skill duplicada põe `web` em quarentena.
- **Catálogo de tipos do `llms` mantido.** `packages/llms/src/lib/providers/kinds.ts` continua exportado: a validação síncrona do documento de configuração em `agents/doric/src/lib/config/{schema,store}.ts` (bundle embutido `host-config`) e os testes de rotas do `transport` ainda leem `providerKind`; trocá-los por `models/v1.kind` (assíncrono, no processo de geração) é trabalho à parte.
- **Ponte.** A allowlist ganha `files/v1` (`directory`, `tree`, `content`), `git.commands/v1` (`status`, `branches`, `switchBranch`, `changes`, `diff`, `fileDiff`), `usage/v1.thread`, `resources/v1.project` e `terminal/v1` (`list`, `create`, `snapshot`, `input`, `resize`, `stop`, `watchProject`; nunca `run`).
- **Teste de quarentena.** `bundles.test.ts` mantém o caso "um bundle de ferramenta quebrado" com `git`: como o `transport` não exige `git.commands/v1`, o host continua servindo.

## Refatoração de fronteira — BWP-1 (escopo de chamada opaco, M1)

- **Decisão do usuário.** A plataforma transporta o escopo de chamada sem conhecer as suas chaves. `CallScope` vira um registro de texto limitado (`Readonly<Record<string, string>>`): cada chave casa com `scopeKeyPattern` (`^[A-Za-z][A-Za-z0-9_.-]{0,63}$`), há no máximo `SCOPE_MAX_KEYS` = 16 chaves e cada valor tem no máximo `SCOPE_MAX_VALUE` = 512 caracteres. `windowKey` é a única chave reservada: a plataforma a preenche para as chamadas que saem de uma janela.
- **Um esquema para todos.** `callScopeSchema` (`packages/bundle/src/contracts/call.ts`) é usado pelo envelope (`runtime/envelope/messages.ts`), pelo registro de log (`contracts/platform.ts`) e pela ponte (`packages/desktop/src/client/protocol.ts`). O `.strict()` com as quatro chaves nomeadas sai; a restrição passa a ser o limite de chaves, o tamanho e o padrão.
- **Ponte [revisado na revisão cruzada].** A janela envia só as três chaves que a linha de base admitia, `projectId`, `threadId` e `promptId`, por `bridgeScopeSchema`, um `.strict()` como no HEAD. Qualquer outra chave recusa a chamada, e `windowKey` é recusada em qualquer grafia. Os valores continuam cadeias sem limite, como antes. A ponte não usa `callScopeSchema`: uma janela poderia enviar até 16 chaves arbitrárias de até 512 caracteres, e cada uma chegaria às chamadas de todos os bundles e aos registros de log. A plataforma continua preenchendo `windowKey` com a janela de origem.
- **Ajudantes do runtime.** `bundles/runtime/runtime/src/contracts/scope.ts` define `RuntimeScope`, `runtimeScope` (monta o escopo de `projectId`/`threadId`/`promptId`, omitindo as chaves ausentes) e `readRuntimeScope` (lê essas três chaves de uma chamada). O runtime (`host/domain/bindings.ts`, `host/services/lease.ts`) e os testes de apoio do runtime e do git leem por eles; o dono das chaves é o runtime.
- **Desvios do desenho.** (1) `bundles/features/terminal/src/host/provider.ts` continua lendo `threadId` e `promptId` diretamente: o `runtime` depende do `terminal`, e importar `runtime/contracts` fecharia um ciclo entre os projetos (o mesmo motivo registrado em `bundles/features/terminal/src/host/peers.ts`). (2) `bundles/foundation/core/src/host/events/facade.ts` continua lendo as três chaves até a BWP-7, que troca a escrita por um sink registrado pelo dono; o `core` não depende do `runtime`, e uma dependência nova só para uma leitura que sai na BWP-7 não se justifica.
- **Desvios revisados e aceitos.** (1) `terminal`: `runtime` depende de `terminal`, então `terminal` não pode importar `runtime/contracts` sem ciclo; o bundle conhece o próprio conceito de Thread, como já conhece no `peers.ts`, e a leitura direta das chaves fica como está. (2) `core`: a leitura das três chaves no `events/facade.ts` sai com o sink da BWP-7 (M5), não nesta fase.
- **Exceções de paridade.** (a) Envelope: `wireScopeSchema` (`runtime/envelope/messages.ts`) descarta, antes dos limites, as chaves que não casam com `scopeKeyPattern` e as de valor que não é cadeia, como o HEAD descartava chaves desconhecidas. Chaves extras válidas, que o HEAD removia, agora atravessam o envelope, e um escopo com mais de 16 chaves ou valor acima de 512 caracteres é recusado por inteiro. Nenhum chamador atual monta esse escopo; o único literal é `{ projectId }` em `bundles/features/files/src/client/api/reads.ts`. (b) Registro de log: `logRecordSchema.scope` aceita qualquer chave limitada, sem o `.strict()` das quatro chaves do HEAD, porque `core/shared/log.ts` copia o escopo da chamada. (c) Fio, linhas de log e cargas da ponte mantêm as mesmas chaves e o mesmo formato. Estas exceções são diagnósticas ou restritivas apenas para escopos que nenhum chamador atual monta; a confirmação do usuário fica pendente.

## Refatoração de fronteira — BWP-4 (composição: `required` e `alternatives`, M4 e M8)

- **`required` na composição [M4].** O esquema da composição aceita `required: { contracts, bundles }`. `agents/doric/composition.json` declara os cinco contratos estruturais (`runtime/v1`, `executor/v1`, `sandbox/v1`, `models/v1`, `host-config/v1`) e o bundle `transport`, que antes eram constantes em `boot.ts`. `structuralFault(catalog, required)`, `assertStructural` e `watchStructural` recebem a exigência; a mensagem de recusa não muda.
- **Ausente mantém a exigência da linha de base [revisado na revisão cruzada].** Uma composição sem `required` exige o conjunto que o host sempre exigiu: `defaultRequirement` em `boot.ts`, com os cinco contratos estruturais e o bundle `transport`. Vale nos caminhos de `DORIC_COMPOSITION`, da composição padrão e da composição ilegível. Assim uma composição de operador sem `required` continua recusando um host sem roteamento, como no HEAD. O desenho (M4) previa "nada exigido", mas essa mudança de comportamento não foi aprovada pelo usuário e por isso não foi aplicada. Sem a mudança, a composição enviada declara o mesmo conjunto e o caso padrão não muda. O teste `an operator composition without required refuses a host without transport, as HEAD did` confirma a recusa com a mensagem do HEAD.
- **`alternatives` na composição [M8].** `sandbox` declara `env: DORIC_SANDBOX_PROVIDER`, `default: docker` e `options: [docker, firecracker]`. A variável escolhe uma opção; um valor fora das opções escolhe o padrão, como a linha de base fazia com qualquer valor diferente de `firecracker`. O desenho previa recusa fatal para valor desconhecido, mas a linha de base não recusa; mantive o comportamento de antes.
- **Escolha pelo host, não pelo kernel.** `packages/bundle` oferece `selectAlternatives`, `enableAlternatives` e `enabledAlternatives` (`runtime/composition.ts`). ## Refatoração de fronteira — BWP-7 (sumidouro de eventos, M5)

- **Desenho (M5).** `events/v1` ganha `sink(spec)`: o dono dos eventos registra uma vez onde suas linhas vão, com `scopeKeys` ordenadas e obrigatórias, um `stream` com marcadores `{chave}` (cada um nomeia uma chave do sumidouro) e `scopeDescription`, usada na mensagem de `invalid_scope`. Saem de `packages/bundle` o `threadEventsStream` e o `threadEventEnvelopeSchema`: a plataforma não conhece mais o fluxo de threads.
- **Dono do sumidouro.** `bundles/runtime/runtime/src/contracts/events.ts` exporta `threadEventSink`, com `scopeKeys` `projectId`, `threadId`, `promptId` e o stream `runtime.thread.events/{threadId}`. O `activate` do runtime o registra e o libera no cleanup. O envelope (`threadEventEnvelopeSchema`) e o tipo `ThreadEventEnvelope` passam a viver em `runtime/contracts/storage.ts`; os leitores do runtime importam daí.
- **Facade do core.** Uma linha de evento tem as chaves do sumidouro na ordem dele, depois `type` e `event`, a mesma ordem de antes. Falta uma chave do sumidouro, ou nenhum sumidouro está registrado, dá `invalid_scope`. A propriedade de `append` (só o dono anexa) e a validação do payload não mudaram.
- **Guarda de dono (não é funcionalidade).** Um sumidouro só pode escrever em stream cuja família seja do próprio bundle que o registra, a mesma regra de propriedade do `storage/v1`, verificada no registro com um valor de amostra. Caso contrário, `not_owner`. Assim um bundle não redireciona eventos para streams alheios. O sumidouro é um por provedor: um segundo registro vivo dá `registration_conflict`, com a mesma regra de geração do registro de eventos.
- **Paridade.** O nome do stream e a linha armazenada não mudam. A fixture da linha foi capturada do código anterior ao sumidouro (`{"projectId":"p-1","threadId":"t-1","promptId":"q-1","type":"notify.sent/v1","event":{...}}`) e é comparada byte a byte no teste do core; trocar a ordem de `type` e `event` faz esse teste falhar. Nenhum caminho de produção chama `events/v1.append` (o runtime só registra `runtime.prompt-finished/v1`, como antes, e grava as threads direto pelo `storage/v1`), então não há exceção de paridade para o usuário.
- **Desvios de posse.** Além dos arquivos da BWP-7, o trabalho tocou `bundles/foundation/core/tests/events.test.ts` (novo sumidouro de teste e fixture), `packages/bundle/tests/basic-contracts.test.ts` (o teste de envelope foi para o runtime; o de esquema do sumidouro entrou no lugar), `packages/bundle/tests/values.test.ts` (a entrada `sink` do `events/v1` em "stated way across the envelope"), `bundles/runtime/runtime/tests/contracts/event-sink.test.ts` (novo: sumidouro do runtime, envelope e registro na ativação com liberação no cleanup) e os READMEs `packages/bundle/README.md` e `bundles/foundation/core/README.md`, que descreviam o stream e a API removidos.
- **Pendências.** `GROUNDING.md` e os documentos de conceito (`events-and-nodes.md`, `storage.md`, `core.md`, `contracts.md`) ainda descrevem o stream do runtime escrito pelo core; ficam para a BWP-12.
- **Validação.** Árvore isolada em HEAD com a aplicação desta BWP (`git worktree` temporário, `node_modules` clonado). `typecheck` de 46 projetos, `test` de 47 projetos com PostgreSQL descartável (2944 passam, 0 falham, 5 pulam: testes de sandbox Docker sem `DORIC_TEST_SANDBOX`), `build` de 47 projetos. `biome format` e `biome check` limpos nos arquivos alterados. O gate E2E `gatef2.sh` não foi executado: recria a stack `doric`, que é proibida nesta tarefa.

## Revisão cruzada — BWP-5 e BWP-7

- **Guarda de dono por linha (sumidouro, achado 1).** Corrigido na raiz. A checagem do registro usa um valor de amostra (`x` em cada chave). Com um marcador na posição do dono (`{projectId}.x/{threadId}`), ela só passava para um bundle chamado `x`, e a linha podia então escrever no stream de qualquer dono, como `runtime`. Agora `events/v1.append` calcula o stream da linha com os valores da chamada e exige que o dono desse stream seja o bundle que registrou o sumidouro; senão responde `not_owner` antes de qualquer escrita. O registro continua recusando cedo. Teste: `bundles/foundation/core/tests/events.test.ts`, "a sink whose owner segment is a placeholder writes only the streams of its owner, row by row". Sem a correção, esse teste falha.
- **Retenção de janela (achado 2).** Testes novos em `packages/bundle/tests/process.test.ts`, com o gerenciador real (`HostGenerations`, obtido de `platform.generations` e conferido com `instanceof`): (a) uma retenção de janela sozinha não aparece em `describe()` como trabalho e não impede o término de uma geração em dreno; (b) uma geração em dreno termina quando acaba a retenção de trabalho, mesmo com a de janela ainda presente. Nenhum caminho de produção toma retenção de janela; os testes chamam `holdFor` diretamente. Com a regra antiga (`holds.size === 0`), os dois falham.
- **Perda por bundle (achado 3).** O teste de perda com retenções de trabalho usa dois bundles (`probe` e `other`) na mesma geração. O fixture de sonda aceita `id` (padrão `probe`). O teste confere `holds` com uma entrada por bundle, cada uma com sua chave, e `work` igual a 2. A retenção de janela da mesma geração não entra na perda.
- **Sumidouro do runtime comparado byte a byte (achado 4) [não alterado; desvio do desenho registrado].** O desenho (M5) pede um teste do runtime que compare a linha armazenada com a fixture. A fixture byte a byte fica em `bundles/foundation/core/tests/events.test.ts`, porque é o core que escreve a linha. O teste do runtime (`bundles/runtime/runtime/tests/contracts/event-sink.test.ts`) fixa `scopeKeys`, em ordem, e o stream, e com esses dois valores o escritor do core define a forma da linha. Ligar os dois num só teste exigiria um pacote de teste dependendo do outro (`core` ou `runtime`), o que a fronteira não permite. Achado à parte: nenhum caminho de produção chama `events/v1.append` com `runtime.prompt-finished/v1` (a busca em `bundles/*/src`, `agents`, `packages` e `app` não acha esse uso). O runtime grava as linhas das threads direto no `storage/v1` (`bundles/runtime/runtime/src/host/store/threads.ts`, com `threadEventsStream`). Assim `threadEventSink` está registrado mas sem escrita em produção. Manter o registro ou rotear as escritas por ele fica como pendência para a BWP-12.

## Refatoração de fronteira — BWP-6 (ciclo de vida do host, M3)

- **Decisão do desenho.** O kernel deixa de conhecer o ciclo de vida dos bundles. `AppHooksV1` ganha `onHostStartHook` e `onHostStopHook`, do tipo novo `sequence` (handlers aguardados um a um, sem prazo, com a falha de um handler rejeitando a execução; a parada usa `order: 'reverse'`). Ganha também `onGenerationChangedHook` (`activated`, `draining`, `lost`, `stopped`), entregue a cada geração viva, e `onPeerSignalHook`. `doric.generation/v1.signal` leva um sinal às outras gerações vivas do mesmo bundle. `doric.startup/v1` (só host) tem `stage(name)` e `log(record)`, e grava as linhas de startup com o mesmo formato de antes.
- **Kernel.** `platform.start()` roda os start hooks em ordem de ativação e, depois deles, lê a identidade do storage. `platform.shutdown()` roda os stop hooks em ordem reversa, antes de `platform.stop()`. Uma geração que entra em dreno recebe `draining` e só então o gerenciador verifica se pode parar: o runtime toma nesse hook a retenção `runtime.drain`, e a parada espera por ela. A troca não é anunciada no boot (o boot não é uma troca) nem durante `stop()`.
- **Runtime.** `bundles/runtime/runtime/src/host/lifecycle.ts` tem o start step (estágio `workspace_reconciliation`; 'Reconciling persisted projects and threads' e, ao final, 'Workspace reconciled' com `interruptedThreads` e `interruptedProjects`) e o stop step (`dispose`). `bundles/runtime/runtime/src/host/handover.ts` faz a troca que o kernel fazia com `drain`, `recoverWith` e `adopt`: reage a `onGenerationChangedHook` e a `onPeerSignalHook` com o tópico `runtime.released`. A retenção `runtime.drain` é tomada antes do dreno e liberada no fim; a geração para depois. Os métodos `recover`, `recoverWith`, `adopt`, `drain` e `dispose` de `runtime/v1` continuam no contrato por uma versão, sem chamador no host.
- **Core.** `bundles/foundation/core/src/host/secrets/activation.ts` registra o start step de credenciais: conecta o storage pelo `storage.backend/v1.connect`, marca `credential_activation`, registra 'Activating stored credentials' e lê os segredos uma vez, para que uma chave ausente ou inutilizável falhe o host ali.
- **Postgres [desvio do desenho].** O `postgres` não registra o próprio start hook. O `hooks/v1` é provido pelo `core`, que exige `storage.backend/v1` do `postgres`; o registro criaria um ciclo de ativação. Por isso `connect()` virou método de `storage.backend/v1` (sem argumentos, `void`): o `postgres` o implementa em `bundles/foundation/postgres/src/host/start.ts`, que marca `database_client`, registra 'Initializing PostgreSQL client', conecta com a checagem de tabelas legadas e registra 'PostgreSQL client initialized'. O `memory` é um no-op. A mudança é aditiva; os dados não mudam.
- **Configuração, sandbox e transporte.** O start step de configuração ('Activating Doric configuration', estágio `configuration_activation`) fica no host-config provisório (`agents/doric/src/lib/bundles/configuration.ts`), até a BWP-9. Os de `bundles/sandboxes/docker/src/host/start.ts` e `bundles/sandboxes/firecracker/src/host/start.ts` usam o estágio `sandbox_pool`. O transporte (`bundles/foundation/transport/src/kernel.ts`) registra 'Network interfaces configured' com `socketNamespaces` no próprio start step. `docker`, `firecracker` e o transporte (`transportRequires`) passam a listar `hooks/v1@^1.0.0`.
- **Removidos.** `agents/doric/src/lib/bundles/handover.ts` e `agents/doric/src/lib/bundles/database.ts`, e o teste `agents/doric/tests/handover.test.ts`, cujos casos foram para `bundles/runtime/runtime/tests/host/handover-hooks.test.ts`. `agents/doric/src/index.ts` ficou com o composition root: sobe os bundles, roda `platform.start()`, instala a ponte, espera `ready`, escuta, e no encerramento roda `platform.shutdown()` e `platform.stop()`.
- **Mantido por dependência [desvio do desenho].** `agents/doric/src/lib/credentials/*` não foi removido. `CredentialService` ainda é consumido pelo host-config provisório (`configuration.ts` e `config/*`), que sai nas BWP-8 e BWP-9. A ativação saiu para o core; a remoção do diretório fica para essas fases.
- **Entrega de eventos [corrigido na revisão do BWP-6; sem desvio].** (a) Um hook `observe` é executado uma vez por geração viva, e só os handlers daquela geração o recebem. `live` lista as gerações ativas ou em dreno depois da mudança, sem a geração que caiu ou parou. (b) Em `lost`, `holds` chega a cada handler só com as retenções do próprio bundle dele, como o desenho (M2 e revisão (c) do M3) exige. `defineHook` aceita `forOwner` em hooks `observe`; o `hooks/v1` do core e o de teste aplicam o filtro por handler antes de chamá-lo, e pulam o handler quando `forOwner` devolve `undefined`. (c) `onPeerSignalHook` usa o mesmo mecanismo: o sinal de par só chega aos handlers do bundle que o emitiu, nas outras gerações vivas, como o M3 define. Nenhum nome de bundle entra no kernel. Teste: `packages/bundle/tests/lifecycle.test.ts`, 'a lost generation hands each bundle only its own holds, and a peer signal stays with its bundle' (dois bundles na mesma geração; antes do filtro, o segundo bundle recebia as retenções e o sinal do primeiro).
- **Identidade do storage.** `storageIdentity` é lida depois de toda a sequência de start hooks. Antes era lida no estágio de credenciais. Uma falha de identidade fica atribuída ao último estágio informado. Em produção, a identidade só falha quando a conexão já falhou em `database_client`, então o efeito é diagnóstico.
- **Exceções de paridade (logs de startup, diagnósticas).** (1) `Doric listening` perde `interrupted`; o valor sai em `Workspace reconciled`, do runtime, antes de `Binding HTTP listener`. (2) `Network interfaces configured` sai do kernel e vem do transporte, antes do bloco do sandbox. (3) `Configuring sandbox pool` e `Sandbox pool configured` vêm do bundle do sandbox, com os campos da linha de base (`sandboxProviderName`, `sandboxImage`, `sandboxResources`, limites, `networkMode`, `sshEnabled`). A BWP-4 tinha colocado `alternatives` nelas, e essa chave sai. (4) A ordem das linhas de startup mudou; a ordem nova é a de ativação. `Doric starting` e `Doric listening` mantêm `alternatives`. Conferido nos scripts do harness E2E (`gatef2.sh`, e os de api, ui, lib e stack do `e2e-stage10`): nenhum lê `interrupted`, `sshEnabled`, `socketNamespaces` nem essas linhas.
- **Testes-duplos.** `createMinimalHooks` (`bundle/testing`) passa a executar `sequence` e a filtrar os handlers pela geração, como o `core` faz. Os harnesses de docker, firecracker e transporte passam a prover `hooks/v1` com esse duplo, pois o host sempre o tem por meio do core. Os duplos de `storage.backend/v1` ganham `connect`.
- **Testes.** Novos: `packages/bundle/tests/lifecycle.test.ts` (ordem de start e de stop com a ordem de ativação; falha de start com o estágio nomeado pelo bundle; falha de stop reportada, com o host ainda parando; `order` só em `sequence`; `activated`, `draining`, `stopped` e o sinal de par entre processos reais; `lost` com retenções reportadas). `bundles/runtime/runtime/tests/host/handover-hooks.test.ts` (troca, perda, respawn, sinal de outro bundle, start e stop do runtime). Quatro casos de `sequence` em `bundles/foundation/core/tests/hooks.test.ts`. Atualizados: `packages/bundle/tests/values.test.ts` (tabela de cruzamento: `connect`, `signal`, `doric.startup/v1`) e `agents/doric/tests/boot.test.ts` (ordem e campos novos, contra um host real com PostgreSQL).
- **Pendências.** (1) O gate E2E (`gatef2.sh`) não foi executado nesta fase. O harness usa o projeto de compose `doric-e2e-stage10`, separado da pilha `doric`, mas exige a imagem do host e a pilha completa, então fica para a fase de gate. (2) `GROUNDING.md` e os documentos de conceito (`process-isolation.md`, `hooks.md`, `core.md`, `storage.md`, `contexts.md`) ficam para a BWP-12. (3) O sandbox firecracker não tem teste dedicado para as linhas de startup; o do docker está coberto pelo teste de boot. (4) `lib/credentials/*` fica até as BWP-8 e BWP-9.

- **Logs da troca [exceção de paridade, diagnóstica].** As falhas `Generation drain failed` e `Generation recovery failed` voltam a levar o campo `generation` (a geração afetada), como no HEAD. `Project adoption failed` continua só com `err`, como no HEAD. As linhas agora saem do log do runtime (componente `bundles`), e não do `startup` do HEAD, que o kernel passava a `installHandover`. Confirmado: nenhum script do harness E2E lê essas linhas.
- **Testes da troca.** Acrescentado em `bundles/runtime/runtime/tests/host/handover-hooks.test.ts`: 'a failed generation activates no runtime: it recovers nothing' (geração em estado `failed` não chama `recoverWith`), caso que estava no HEAD em `agents/doric/tests/handover.test.ts` e não tinha sido portado.

## Integração final da fronteira (2026-10-12)

- `host-config` e `transport` são bundles instalados com manifesto e descritor próprios. A composição os inclui em `enabled` e `resident`. `resident` seleciona partes host que precisam compartilhar recursos nativos; não identifica funcionalidades no kernel. A alteração dessa seleção requer reinício do kernel.
- `doric.network/v1.register` entrega os listeners HTTP e Socket.IO a uma função local do bundle, com liberação no encerramento. O host cria os listeners; `transport` registra as rotas e namespaces. O manifesto pode declarar contratos opcionais em `optional`, permitindo indisponibilidade de funcionalidades sem adicionar dependências obrigatórias à ativação.
- A ponte recusa métodos sem `expose: 'desktop'`. Contratos básicos têm como limite as declarações do protocolo; outros contratos declaram a exposição no próprio bundle. `desktopScope` restringe chaves aceitas por contrato e `windowKey` continua vindo apenas da plataforma. Snapshots separados cobrem os métodos do host e os serviços desktop de janelas, menus e comandos já usados pelo cliente.
- `GIT` é registrado por `git`, com username e email obrigatórios e sem secret. Os tipos genéricos de autenticação continuam disponíveis no core. A migração `20261012000000_registered_credential_kinds` converte a coluna de tipo de credencial de enum para texto, preservando IDs e bytes cifrados. Isso permite persistir tipos declarados por outros bundles sem nova versão do backend. Os 110 testes do PostgreSQL, incluindo essa conversão, passaram em banco real.
- A conversão de manifesto v0 preserva o ID escrito pelo autor; foi retirada a exceção de produto que renomeava `core` para `files`. Os bundles distribuídos já usam v1. A instalação externa continua adiada.
- A conexão do desktop observa `/doric/bridge`, pertencente à plataforma. `/status` continua disponível no bundle `transport` para consumidores existentes.
- As pastas dos bundles são agrupadas em `foundation`, `runtime`, `providers`, `sandboxes`, `features` e `desktop`; IDs, pacotes npm, contratos e diretórios dos artefatos distribuídos continuam iguais. `transport` fica em `foundation`.
- A recuperação do sandbox verifica também a configuração do contêiner encontrado. Uma alteração incompatível de imagem, limites, rede, DNS ou SSH substitui o contêiner e preserva o volume. A aquisição falha se não puder remover duplicatas. Testes concorrentes verificam liberação idempotente; 60 testes passaram com Docker real.
- O gate E2E completo foi executado uma vez após a integração, com repetição apenas dos cenários afetados pelas correções. As evidências e diferenças classificadas estão em [Validação da integração](./validation-2026-10-12.md); resultados históricos abaixo não validam esta revisão.

## Refatoração de fronteira — BWP-12 (documentação da fronteira)

- **Regra vinculante.** A plataforma instala bundles, compõe provedores, roteia chamadas e mantém processos, janelas e IPC. Ela não conhece conceitos de bundle (Project, Thread, prompt, fila, Git, settings) nem seus métodos ou formatos de armazenamento. Um campo nomeado de schema genérico também é vazamento, então `projectId`, `threadId` e `promptId` não aparecem em código de plataforma. A regra foi confirmada pelo usuário.
- **Escopo desta fase.** `GROUNDING.md` (nova seção _Platform Boundary_, e as seções de runtime atual, configuração, credenciais, sandbox, transporte e startup reescritas para o estado do código), `agents/AGENTS.md`, `packages/AGENTS.md` e os documentos de conceito de `docs/architecture/bundles/` citados no fim desta seção. Nenhuma cláusula de Hard Constraint foi alterada. As afirmações históricas (pacote `packages/host`, transporte e host-config embutidos, `workspace` como literal, dependências fixas de boot, `allowed-tools` restrito ao próprio bundle, sumidouro de eventos no core) foram substituídas, não acrescidas de um parágrafo "agora".
- **Mecanismos da plataforma (M1 a M12).** Escopo de chamada opaco e limitado (`callScopeSchema`, com `windowKey` reservado à plataforma); `WorkHold` atribuído pelo bundle chamador; hooks `onHostStartHook`, `onHostStopHook`, `onGenerationChangedHook` e `onPeerSignalHook`; `doric.startup/v1` para estágios e logs de startup; `required` e `alternatives` na composição; `sink` de eventos com um sumidouro por provedor; `registerKind` em `secrets/v1`; exposição de método por declaração (`expose`, `x-doric-expose`) e `desktopScope` por provedor; `primary` na janela; `packages/host` removido, com os tipos do `Host` em `bundles/runtime/runtime/src/contracts/tool-host`.
- **Adições genéricas pedidas no pai.** `composition.resident` lista bundles instalados que rodam no processo nativo do host, não num processo de geração; a composição distribuída usa `host-config` e `transport`. `manifest.optional` lista IDs de contrato que um bundle pode chamar em melhor esforço, sem dependência de ativação; sem provedor ativo, a chamada mantém o comportamento indisponível do chamador (as leituras de funcionalidades do transporte são o exemplo). `doric.network/v1.register(listener)` dá um callback local sobre os handles nativos HTTP e Socket.IO, que nunca são serializados: o host é dono do listener e da ponte genérica (`/doric/bridge`), e o transporte registra todas as rotas por esse callback. Nenhuma mudança nas fases de fundação e core.
- **Exposição (BWP-10).** O padrão é negar. Um método só chega à janela desktop quando declara `expose: 'desktop'`, e cada provedor declara as chaves de escopo que uma janela pode enviar em `desktopScope`; `windowKey` é só da plataforma. O snapshot `agents/doric/tests/bridge-exposure.snapshot.json` é uma porta permanente de CI: mudar o conjunto exposto exige atualizar o snapshot na revisão. Nenhum `contracts.published.json` é mantido (BWP-0).
- **Credenciais.** Os kinds básicos (`API_TOKEN`, `USERNAME_PASSWORD`) continuam no contrato genérico. O kind `GIT` é registrado pelo bundle `git` com `username` e `email` apenas, nunca com segredo. O ID armazenado não muda.
- **Correção aprovada no sandbox (BWP-14) [desvio intencional do 1:1].** Esta é a única mudança de comportamento observável aprovada nesta refatoração. Ao adquirir um Project depois de reiniciar o host, o provedor Docker reanexa o contêiner em execução do workspace (ou remove os obsoletos), de modo que exista um sandbox por Project, com o volume e os arquivos preservados. A linha de base (eda9171) criava um contêiner novo a cada reinício, acumulando duplicatas. Na validação final, o probe `sandboxAfterRestart` observou 1 sandbox, com o mesmo contêiner e arquivo preservado, tanto no reinício normal quanto no abrupto; o terminal SSH também permaneceu operacional. A correção está registrada como correção, não como paridade. Evidências em `validation-2026-10-12.md`.
- **Diferenças de log de diagnóstico [não são paridade 1:1 de conteúdo].** Além das exceções já registradas na BWP-6 (`interrupted`, `socketNamespaces`, `sshEnabled` e a ordem das linhas), a chave `sandboxProvider` de `Doric starting` e `Doric listening` é substituída por `alternatives: {sandbox: ...}`, gerado a partir de dados da composição. O nome da variável de ambiente fica só em `composition.json`. Nenhum script do harness E2E lê essas linhas (conferido na BWP-6).
- **Caminhos.** A BWP-13 agrupou os bundles em `foundation`, `runtime`, `providers`, `sandboxes`, `features` e `desktop`, incluindo os caminhos da documentação, Docker, Nx e TypeScript. IDs, nomes npm e nomes de projeto Nx não mudam. A pasta de origem não determina a fase de ativação.
- **Reconciliação da implementação.** O manifesto de `host-config` está instalado; a allowlist de produto foi removida; os kinds de credenciais são registrados pelos bundles; os widgets e leituras de domínio saíram dos pacotes genéricos. A busca final em código de produção da plataforma não encontrou os IDs e campos de Project/Thread/Prompt apontados na revisão.

## Correções encontradas na validação integrada (2026-10-12)

- O catálogo distribuído deve preservar `optional` e `desktopScope`. Descartá-los fazia a ponte recusar chamadas que o provedor havia declarado.
- Além dos contratos do host, os serviços desktop de janelas, menus, comandos, notificações e cache de histórico precisam declarar a exposição de seus métodos. A verificação de exposição inclui esses serviços. O chat declara `history.snapshots/v1` como dependência opcional, mantendo seu funcionamento sem cache.
- `doric.migrations/v1` precisa ser anunciado ao processo desktop da geração. Um teste com Electron real reproduziu a ausência do marcador persistido antes da correção e passou depois dela.
- A saída autorizada do app aguarda as gravações de rotas e estado da plataforma. Antes, a gravação iniciada no fechamento da janela podia perder a corrida com a saída do processo e restaurar a rota anterior. A segunda solicitação de saída continua forçando o encerramento, como antes.
- O probe de terminal com SSH habilitado verificou interrupção, término de Thread, reinício normal e queda abrupta do host. Após ambos os reinícios, havia um único sandbox, com o mesmo contêiner e o arquivo preservado. Um novo terminal também funcionou após a queda. A stack e os sandboxes desse probe foram removidos ao terminar.

## Base UI compartilhado pelo import map (2026-10-17)

- **Base UI no lugar do Radix.** Os componentes de `desktop/ui` passam a usar o Base UI (`@base-ui/react`), e a plataforma o serve uma vez por janela, como o React, porque seus contextos e stores precisam de uma instância só: o Base UI de um bundle e o de `desktop/ui` são o mesmo. Isso substitui a parte da S8-21 em que o Radix era empacotado dentro de `desktop/ui`.
- **Pasta e subpaths.** `@base-ui/react` entra em `esmPackages` e sai de um único esbuild com `splitting` na pasta `@base-ui/react@<versão>/`, com uma entrada por subpath do `exports` (menos `./package.json`), então as subpaths compartilham os chunks. As dependências (`@base-ui/utils`, `@floating-ui/*`, `reselect`, `use-sync-external-store`) entram nos chunks, com as licenças em `licenses/`, e o `require('react')` CommonJS de `use-sync-external-store` passa pelo módulo de interop, ficando a instância do mapa. `desktop/ui` mantém os especificadores do Base UI externos, como todo especificador da plataforma, sem cópia nos chunks de `desktop@`.
- **Subpath que não roda numa janela.** Regra geral do build: uma subpath de um pacote ESM cujo código importa um pacote que o workspace não instala fica fora do mapa, e o build a nomeia; o grupo é construído de novo sem ela. No Base UI 1.8.0 são `internals/temporal-adapter-date-fns` e `internals/temporal-adapter-luxon`, que pedem `date-fns`, `@date-fns/tz` e `luxon`: o mapa serve 77 dos 79 especificadores.
- **Externos.** `clientExternals` ganha `@base-ui/react` e `@base-ui/react/*`, e uma parte desktopMain não pode importar o Base UI. O preview do Papercraft deixa externos, além do React, os especificadores do Base UI que o mapa serve: o host pergunta à própria cópia, uma vez por especificador, se ela empacota a subpath com o React externo, a mesma pergunta que o build da plataforma faz. `radix-ui` sai de `HOST_PACKAGES` e passa a ser pacote do Project como qualquer outro.
