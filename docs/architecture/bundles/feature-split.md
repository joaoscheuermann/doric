# The bundle map

- Status: living document. It lists the bundles of the repository as implemented on 2026-11-21.

## Summary

A bundle is a directory `bundles/<group>/<id>` that holds a `manifest.json`. The repository has 33 of them. This map says, for each one, which parts it has, which contracts it provides, what else it owns (tools, skills, routes, elements, slots and slot items), where its README is and which feature docs describe the features it implements. Use it to find the home of a capability; the detail is always in the README it links.

What a bundle owns starts from its manifest: a bundle provides exactly the contracts its manifest lists under `provides`, and the bundle build fails when the code of a part provides, defines or registers a contract the manifest does not list ([Manifest](manifest.md#provides-and-the-descriptor)). The tools, skills, routes, elements and region items a bundle registers are named by its README. A bundle's README is the complete description of the bundle: its contracts, behavior, data, configuration, limits and errors. A feature doc describes one feature across the bundles that implement it and links their READMEs.

## How to read the tables

- **Bundle** links the bundle's README; the directory is under it.
- **Parts** links each part's entry file: `host` (the host process), `desktop` (the desktop app's main process, `desktopMain`) and `client` (each app window). A bundle has only the parts it has a source entry for ([Manifest](manifest.md#package-layout-and-build-output)). The cell also links `contracts`, the bundle's contracts module, when it has one; the bundle exports it as `<id>/contracts` ([Contracts](contracts.md)). 24 bundles have one; `postgres`, `transport`, `threads`, the four model providers, `docker` and `firecracker` do not.
- **Provides** is the `provides` list of the bundle's `manifest.json`, with each contract's version.
- **Owns** names what the bundle's parts register besides those contracts, in the words of its README.
- **Feature docs** are the feature docs that name the bundle as one of the units that implement the feature. [Feature docs by bundle](#feature-docs-by-bundle) lists the same links the other way round.

The folders under `bundles/` group the source and set nothing at run time: in particular they do not set the activation phase ([Composition and distribution](composition-and-distribution.md#foundation-and-activation-order)).

## The shipped composition

The host's composition file, [`app/backend/doric-host/composition.json`](../../../app/backend/doric-host/composition.json), enables 32 of the 33 bundles: every bundle but `firecracker`. Its alternative `sandbox` enables `docker` by default and `firecracker` in its place when `DORIC_SANDBOX_PROVIDER=firecracker` ([Composition and distribution](composition-and-distribution.md#alternatives)). It chooses `postgres` under `providers` for `storage.backend/v1` and `secrets.backend/v1`, which makes `postgres` the foundation that activates before `core` ([Composition and distribution](composition-and-distribution.md#providers-and-cardinality)). It lists `host-config`, `transport` and `screen-relay` under `resident`, so they run in the host's kernel process, where `doric.network/v1` reaches the host's network listeners ([Composition and distribution](composition-and-distribution.md#resident)). It requires an active provider of `runtime/v2`, `executor/v1`, `sandbox/v1`, `models/v1` and `host-config/v1`, and an active `transport`, or the host's start fails ([Composition and distribution](composition-and-distribution.md#required)).
