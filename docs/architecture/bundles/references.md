# Prior art

- Status: living document. It describes the outside systems the bundle architecture takes decisions from, and what Doric does in their place, as implemented on 2026-11-20.

## Summary

The bundle architecture takes decisions from existing systems without copying any of them whole. From the DeepSeek Harness it takes composition through services scoped by context, and the split between generic stored state and the log of a session; Doric's storage, though, holds a stronger contract than the Harness's key-value store. VS Code, Discord, gRPC, Web Components and Lexical are the models for the manifest, stable contract ids, typed stubs with propagated cancellation, custom elements as the boundary between client parts, and the nodes of the conversation. Inside the repository, `defineTool` of the `tool` package and `defineMethod` and `defineCommand` of `bundle/contracts` put the logic in the definition, as `execute(input, call, services)` over a zod `input`; a tool and a method also declare a zod `output` ([`tools.ts`](../../../packages/tool/src/lib/tools.ts), [`define.ts`](../../../packages/bundle/src/contracts/define.ts)).

## The DeepSeek Harness

### How the Harness keeps state

The Harness keeps a generic key-value store, `ctx.storageDomain`, for the domains of its plugins, apart from the log of a Session and from `ctx.sessionPersistence`. Its key-value store validates schemas and writes each operation before it notifies, and lists as known limitations that it has no transactions across tables, no secondary indexes and no automatic migration. The log of a Session is append-only and kept in memory; `deriveMessages()` rebuilds the model's context from it, and a backend may write in batches until a policy asks for a `flush` ([Storage](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/storage.md), [limitations of the store](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/storage/storage-domain/README.md#known-limitations-and-deferred-work), [Sessions](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md), [persistence](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)).

### What Doric's storage holds beyond it

Doric follows the Harness's composition model and keeps the split between generic state and a session's log, but its storage contract is stronger than the Harness's store:

- **One commit spans documents and streams.** A `storage/v1` commit carries, in one batch, the expected revisions, the documents to put and delete, the stream entries to append at an expected sequence, the truncations and the streams to drop ([`basic/storage.ts`](../../../packages/bundle/src/contracts/basic/storage.ts), [core README](../../../bundles/foundation/core/README.md)). The `runtime` writes the events of a prompt in the same commit as the Thread document that folds them, and publishes them only after that commit lands ([`runtime/src/host/store/threads.ts`](../../../bundles/runtime/runtime/src/host/store/threads.ts)). The backend in the shipped host composition is the `postgres` bundle, the provider of `storage.backend/v1` ([`composition.json`](../../../app/backend/doric-host/composition.json), [postgres README](../../../bundles/foundation/postgres/README.md)).
- **Storage types have indexes.** `defineStorageType` declares a zod schema and indexes, each with a `name`, its `fields` and an optional `unique` ([`define.ts`](../../../packages/bundle/src/contracts/define.ts)).
- **What the model receives is a separate record.** The executor's history, which it sends to the model, is kept per Thread as the storage type `runtime.history/v1`, one opaque document per named part, beside the Thread's event log and not derived from it ([`runtime/src/contracts/storage.ts`](../../../bundles/runtime/runtime/src/contracts/storage.ts), [`runtime/src/host/store/history.ts`](../../../bundles/runtime/runtime/src/host/store/history.ts), [runtime README](../../../bundles/runtime/runtime/README.md)).
- **A rewind truncates the log and keeps its sequence.** A rewind removes the entries from the rewound prompt on, appends a `history.truncated` marker after the last sequence ever assigned, so the sequences of the removed entries are not reused, and keeps the usage of the calls that already ran ([`runtime/src/host/store/threads.ts`](../../../bundles/runtime/runtime/src/host/store/threads.ts), [`runtime/src/host/store/usage.ts`](../../../bundles/runtime/runtime/src/host/store/usage.ts)).

State outside the database has its own owner. A Project has one sandbox, shared by its Threads; the sandbox bundles provide `sandbox/v1`, and the `runtime` leases each Project's sandbox through it and coordinates the acquisition, the release and the recovery after a restart, so that storing a Project's id is not taken as storing its process or its files ([runtime README](../../../bundles/runtime/runtime/README.md), [`runtime/src/host/domain/service.ts`](../../../bundles/runtime/runtime/src/host/domain/service.ts)). [Storage](storage.md) describes the storage contract, and [Events and nodes](events-and-nodes.md) the Thread log.

## `defineTool` and the `define*` family

A tool is written like a service method. `defineTool` of `packages/tool` ([`tools.ts`](../../../packages/tool/src/lib/tools.ts), [`types/tool.ts`](../../../packages/tool/src/lib/types/tool.ts)):

- takes `name`, an optional `description`, `input` (a `z.object`), `output` (a zod schema) and `execute(payload, call, services)`, and optionally `strict` (default `true`), `inputSchema`, `settings` and `resultModalities`;
- refuses an `input` that is not a `z.ZodObject`, an `inputSchema` whose `type` is not `object`, and a schema `z.toJSONSchema` cannot represent, each with the error `invalid_schema`;
- keeps an inspectable `definition` with the name, the description, the input JSON Schema (the given `inputSchema`, or the one generated from `input`), the output JSON Schema and `strict`;
- validates what `execute` returns against `output` with `safeParse`, and throws `invalid_output` with the zod issues when it does not match.

A bundle registers a tool with `services.use(ToolsV1).register(tool, options)`. The registration binds the tool to the registering bundle's services, so its `execute` receives them as `services`. The bound tool that `tools/v1` stores has `execute(payload, call)`, the shape of the contract's `ContractTool`, and runs the defined `execute` with the bound services; `toTool(call)` then gives the tool the agent loop runs for one prompt, whose `execute(payload)` runs under that prompt's `call` ([`tools.ts`](../../../packages/tool/src/lib/tools.ts), [`registrable.ts`](../../../packages/bundle/src/contracts/registrable.ts), [`basic/tools.ts`](../../../packages/bundle/src/contracts/basic/tools.ts), [core README](../../../bundles/foundation/core/README.md)). A tool reaches the Project's workspace, its Threads and its terminals as services in the call's scope, such as `services.use(RuntimeWorkspaceV1, call.scope)`, and passes its `call` on as the last argument of the stub methods it calls ([`files/src/host/tools/cwd.ts`](../../../bundles/features/files/src/host/tools/cwd.ts)). The `runtime` provides `runtime.workspace/v1` and `runtime.threads/v1`, and the `terminal` bundle `terminal/v1`; their shapes are in the [runtime README](../../../bundles/runtime/runtime/README.md) and the [terminal README](../../../bundles/features/terminal/README.md).

The `define*` family shares the use of zod. `defineHook` and `defineHooks`, `defineService` and `defineMethod`, `defineEvent`, `defineCommand`, `defineSettings` and `defineStorageType` are exported by the browser-safe entry point `bundle/contracts` of `packages/bundle` and declare every payload with a zod schema (`defineHooks` and `defineService` group hook and method definitions under an id) ([`index.ts`](../../../packages/bundle/src/contracts/index.ts), [`define.ts`](../../../packages/bundle/src/contracts/define.ts)). The logic of a service method and of a command lives in the definition, in an `execute(input, call, services)`, and a consumer holds a `ref`, which carries only the contract id. Where there is execution, the input is validated: the dispatcher validates a method's input and output ([`dispatch.ts`](../../../packages/bundle/src/runtime/dispatch.ts)), the provider of `hooks/v1` a hook's input and the result of a `transform` or `decide` handler ([`core/src/shared/hooks.ts`](../../../bundles/foundation/core/src/shared/hooks.ts)), and the provider of `commands/v1` a command's input ([`core/src/client/commands.ts`](../../../bundles/foundation/core/src/client/commands.ts), [`core/src/desktop/commands.ts`](../../../bundles/foundation/core/src/desktop/commands.ts), [core README](../../../bundles/foundation/core/README.md)). The build generates each contract's JSON Schema from its zod definition ([`json-schema.ts`](../../../packages/bundle/src/runtime/json-schema.ts), [`cli.ts`](../../../packages/bundle/src/build/cli.ts)). `defineService` takes one option, `{ cardinality: 'many' }`; without it, the contract has cardinality `one` ([`define.ts`](../../../packages/bundle/src/contracts/define.ts)). [Contracts](contracts.md) describes the family in full.

The one place a JSON Schema comes from outside zod is a tool's `inputSchema`: the `mcp` bundle passes each MCP server's input schema there, with a permissive `input` and `strict: false`, since the server validates the payload ([`mcp/src/host/tools.ts`](../../../bundles/features/mcp/src/host/tools.ts)).

## Outside references

- [DeepSeek Harness: architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) and [Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md): services scoped by context, events with explicit semantics, and registrations that are undone. In Doric, `services.use(contract, scope)` binds a scope to the stub it returns, and a `Disposable` a call returns is tracked in the calling bundle's scope and disposed when the bundle deactivates ([`context.ts`](../../../packages/bundle/src/contracts/context.ts), [`dispatch.ts`](../../../packages/bundle/src/runtime/dispatch.ts), [`activation.ts`](../../../packages/bundle/src/runtime/activation.ts)). Its [conversation subsystem](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/conversation.md) keeps the reading of events apart from their display; in Doric the `chat` bundle projects the Thread log into turns and blocks, and other bundles project and draw their part through `chat.views/v1` ([chat README](../../../bundles/desktop/chat/README.md)).
- [DeepSeek Harness: storage](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/storage.md), [sessions](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md) and [persistence](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md): the versioned store of plugins and the durable log of a session are separate contracts. Doric keeps that split and adds commits that span a Thread's document, its events and its usage, as [What Doric's storage holds beyond it](#what-dorics-storage-holds-beyond-it) says.
- [VS Code: extension anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy), [contribution points](https://code.visualstudio.com/api/references/contribution-points), [activation events](https://code.visualstudio.com/api/references/activation-events) and [commands](https://code.visualstudio.com/api/extension-guides/command): a manifest the host reads before running code, and registrations disposed with the extension. Doric's catalog decides from the manifests and the `contracts.json` descriptors which bundles activate and in what order, without running bundle code; it activates every scheduled bundle at start, not on first use: the foundation first, then the core, then the others, each group in dependency order ([`catalog.ts`](../../../packages/bundle/src/runtime/catalog.ts), [`activation.ts`](../../../packages/bundle/src/runtime/activation.ts)). Doric's client has no fixed workbench to contribute to: the window's whole frame is the element of the route `/`, which the `layout` bundle registers ([`layout/src/client/index.ts`](../../../bundles/desktop/layout/src/client/index.ts), [layout README](../../../bundles/desktop/layout/README.md)); in a composition without `layout`, another shell takes its place by registering `/` itself, since a second registration of a path fails with `route_conflict` ([`navigation.ts`](../../../bundles/foundation/core/src/client/navigation.ts), [Layout](layout.md)).
- [VS Code: extension hosts](https://code.visualstudio.com/api/advanced-topics/extension-host) and [webviews](https://code.visualstudio.com/api/extension-guides/webview): one entry point per environment, and code run apart from the main process. A Doric bundle has one part per environment (`host`, `desktopMain`, `client`). The host kernel runs the foundation, the core, the embedded bundles and the bundles the composition lists under `resident`, and every other scheduled host part runs in a generation process apart from it ([`partition.ts`](../../../packages/bundle/src/process/partition.ts), [`composition.json`](../../../app/backend/doric-host/composition.json)). The desktop app runs every scheduled `desktopMain` part of a generation, the core's included, in one Electron `utilityProcess` apart from the main process ([`app.ts`](../../../app/desktop/doric/src/platform/app.ts), [`generation/process.ts`](../../../app/desktop/doric/src/platform/generation/process.ts), [Process isolation](process-isolation.md), [Manifest](manifest.md)).
- [Discord: Gateway](https://docs.discord.com/developers/events/gateway), [interactions](https://docs.discord.com/developers/interactions/receiving-and-responding) and [components](https://docs.discord.com/developers/components/reference): stable ids for events and commands, declared interests and asynchronous answers. Doric names every contract, event type and command by an id that carries its major version, such as `comments.added/v1`, a bundle declares what it uses under `requires` and `optional`, and the Thread log gives each event its own durable sequence ([`ids.ts`](../../../packages/bundle/src/contracts/ids.ts), [`manifest.ts`](../../../packages/bundle/src/runtime/manifest.ts), [`runtime/src/host/store/threads.ts`](../../../bundles/runtime/runtime/src/host/store/threads.ts), [Events and nodes](events-and-nodes.md)).
- [gRPC: core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/): service contracts, methods, stubs, deadlines and cancellation. Every Doric stub method takes, as its last optional argument, the parent `call` or `{ signal, deadline }`; from a parent call the new hop inherits the scope, the signal and the deadline and continues the parent's trace with a new span, and a scope bound with `services.use(contract, scope)` wins over the parent's keys. Unlike metadata passed along, `call.caller` is always the bundle that makes the hop: the dispatcher fills it and never inherits it ([`call.ts`](../../../packages/bundle/src/contracts/call.ts), [`runtime/call.ts`](../../../packages/bundle/src/runtime/call.ts), [`dispatch.ts`](../../../packages/bundle/src/runtime/dispatch.ts)). The calls between processes travel in Doric's own RPC envelope, not in the gRPC protocol ([`link.ts`](../../../packages/bundle/src/runtime/envelope/link.ts)).
- [MDN: Web Components](https://developer.mozilla.org/en-US/docs/Web/API/Web_components), [composed events](https://developer.mozilla.org/en-US/docs/Web/API/Event/composed) and [the custom element registry](https://developer.mozilla.org/en-US/docs/Web/API/CustomElementRegistry/define): elements and DOM events as the boundary between client parts, and a tag that, once defined, cannot be replaced in the same registry. In Doric a bundle defines and creates elements through `ui/v1`, which refuses a tag that does not start with the bundle's id followed by `-` ([`ui.ts`](../../../bundles/foundation/core/src/client/ui.ts), [core README](../../../bundles/foundation/core/README.md)); the window's record of tags refuses a second definition of a tag with `registration_conflict` ([`elements.ts`](../../../packages/desktop/src/client/elements.ts)); and a bundle element that tells the page something dispatches a bubbling, composed DOM event ([`comment-thread.ts`](../../../bundles/desktop/chat/src/client/utility/comment-thread.ts)). [UI composition](ui-composition.md) describes the mechanism.
- [Lexical: extensions](https://lexical.dev/docs/extensions/intro) and [nodes](https://lexical.dev/docs/concepts/nodes): nodes enter the configuration before the editor is created, and `DecoratorNode` hosts arbitrary views. In Doric, Lexical belongs to the `chat` bundle: `chat.lexical/v1` adds node classes and extensions to the conversation editor until the window's first editor is created, and refuses a later registration with `frozen` ([`chat/src/client/services/lexical.ts`](../../../bundles/desktop/chat/src/client/services/lexical.ts), [chat README](../../../bundles/desktop/chat/README.md)). The core's `ui/v1` does not use Lexical; the desktop app gives each window one copy of `lexical` and `@lexical/*` through its import map, for the bundles that import it ([`packages.config.mjs`](../../../app/desktop/doric-platform/packages.config.mjs), [Platform packages](platform-packages.md)).
