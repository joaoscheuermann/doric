# Feature: coding workflow

- Status: `implemented`

## Problem

A coding task in a Git repository goes better when one Thread coordinates it and hands each step (triage, search, spec, review, plan, contracts, tests, implementation, cleanup, docs) to a separate agent Thread. The Thread that receives the task needs those instructions when it works at a repository's root, and only then. A Thread that runs as an agent, or that does one delegated step, must not run the workflow: its own instructions are its work.

## Decisions

- The workflow is a built-in skill of the `default` bundle, `coding-workflow`, loaded on demand with `load_skill`; it is not always-available. Its description says when to load it, and no other logic routes to it.
- The host does not push the workflow into a Thread and does not check that the model loaded it. Delivery relies on the model: the skill's row in the catalog says when to load it, and the system prompt tells the model to load the skills that match its work when a `cwd` result it receives reports a repository root. The accepted risks: the model may work on code without loading the workflow; reaching it costs a `load_skill` call, and a `cwd` call when the model makes one; and a rewind past the `load_skill` result removes the workflow, after which only the catalog row and a later `cwd` result at a root remind the model.
- Whether the working directory is a repository root reaches the model only in the result of a `cwd` call, never in the system prompt, so a move leaves the system prompt (and the provider's prompt cache) unchanged. At a root that result carries the reminder `Remember to load the skills that match your task when working in a repository.`
- A Thread that runs as an agent (a Thread with `agent`) is not offered the skill: it is not listed for it, and `load_skill` refuses it.
- The skill has `order: 50`, so it sorts ahead of every bundle skill with a higher order and is the first built-in row unless always-available skills overflow their budget.
- The "Loaded skills" message that a compaction writes never leaves the `coding-workflow` entry out for its size cap.
- The coordinator chooses the route itself, from what triage reports.
- The coordinator gives each step an effort (low for triage, search, cleanup and docs; medium for plan, contracts, tests and implementation; high for spec and review) and no model, so each step runs on the coordinator's model.
- A Thread whose input is a `<parent-instruction>` does that instruction and returns its result; it does not run the workflow.

## Current behavior and contracts

### The skill

- The workflow's text is [bundles/runtime/default/src/skills/coding-workflow/SKILL.md](../../bundles/runtime/default/src/skills/coding-workflow/SKILL.md), a bundle skill of [`default`](../../bundles/runtime/default/README.md) (2.8.0). Its frontmatter is `name: coding-workflow`, `order: 50`, no `alwaysAvailable`, and the description "Coordinates a coding task in a Git repository through the built-in triage, search, spec, review, plan, contracts, tests, implementation, cleanup and docs agents. Use when you receive a coding task as a <user-request> and your working directory is a Git repository's root; not when you are a delegated step." The bundle loader reads `skills/<dir>/SKILL.md` and its `order` key ([packages/bundle/src/loader/skills.ts](../../packages/bundle/src/loader/skills.ts)). `skills/v1` 1.1.0 carries `order` ([packages/bundle/src/contracts/basic/skills.ts](../../packages/bundle/src/contracts/basic/skills.ts)), and its provider lists skills by `order` ascending, unordered last, then bundle order, then registration order (`byOrder`, [bundles/foundation/core/src/host/skills.ts](../../bundles/foundation/core/src/host/skills.ts); see the [`core` README](../../bundles/foundation/core/README.md)).
- The executor lists the skill as a row of "Built-in skills" under "Skills to load" in the system prompt's `# Skills` section, with its description as the row's text. It is the first row of that list except when always-available skills pass their 16 000-character budget: those become rows ahead of it ([bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts), [bundles/runtime/default/src/host/prompts/skills-catalog.md](../../bundles/runtime/default/src/host/prompts/skills-catalog.md)). The model loads it with `load_skill({ name: 'coding-workflow' })`, which answers the skill's text ([bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)). The full catalog, its budgets and `load_skill` are described in the [`default` README](../../bundles/runtime/default/README.md#skills).
- For a Thread with `agent`, the executor removes the skill whose name is `CODING_WORKFLOW_SKILL` (`'coding-workflow'`, exported by [bundles/runtime/default/src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts)) from the run's built-in skills right after reading them, before it builds the catalog and its live updates ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)). The skill is then absent from `# Skills`, and `load_skill({ name: 'coding-workflow' })` fails with the unknown-id error: `Unknown skill id "coding-workflow". Call load_skill with one of: ` followed by the ids the run can load, each in backticks, or `Unknown skill id "coding-workflow". No skill can be loaded now.` when the run lists none ([bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)). A Thread without `agent`, a plain child included, is offered the skill.

### Reaching the workflow

- The system prompt's `# Working Directory` section tells the model to work from the directory the task concerns, moving there with `cwd` before the commands that depend on it; for code in a Git repository that directory is the repository root, reached before any other tool touches the code. It tells the model not to reach into a repository from elsewhere with `working_directory` or absolute paths, because the repository's skills and agents are listed only from the working directory. It tells it to load the skills that match its work when `cwd` reports a repository root, before starting that work. For code outside any repository, it tells it to initialize a repository at the folder's root for a deliverable meant to be kept and extended, then move there, and to ask the user and wait for the answer for an experiment ([bundles/runtime/default/src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)).
- The system prompt's `# Inputs` section names the five envelopes an input arrives in (`<user-request>`, `<parent-instruction>`, `<child-result>`, `<terminal-output>`, `<bundle-instruction>`) and tells the model to follow a `<bundle-instruction>` from its next step ([bundles/runtime/default/src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)). The executor wraps each prompt in the envelope of its source: a prompt from the reader is a `<user-request>`, and one from a parent Thread a `<parent-instruction thread="…" prompt="…">` ([bundles/runtime/default/src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).
- Every `cwd` result carries `repositoryRoot`, true only when the working directory after the call is a Git repository's root, and at a root `note` with the reminder text above, on a report, a move and a refusal alike ([bundles/features/files/src/host/tools/cwd.ts](../../bundles/features/files/src/host/tools/cwd.ts); the tool is described in [cwd tool](cwd-tool.md) and the [`files` README](../../bundles/features/files/README.md)).
- A Thread whose run starts at a repository root, such as a child, which starts in its parent's working directory ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)), learns that it is at a root only if it calls `cwd`. A Thread an earlier prompt moved to a root has no `cwd` result in this run until it calls the tool; an earlier prompt's result stays in its history unless a compaction or a rewind removed it. The system prompt does not tell it to call `cwd` before working on code ([bundles/runtime/default/src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)); without that call, only the skill's catalog row routes it to the workflow.

### The workflow's flow

What the skill tells the model, as written in [SKILL.md](../../bundles/runtime/default/src/skills/coding-workflow/SKILL.md):

- **Roles.** The coordinator is the Thread that receives the task as a `<user-request>`, a message from the reader. It runs the workflow, does none of its steps and is the only one that asks the user. Each step is done by the built-in agent of that name. A Thread whose input is a `<parent-instruction>` is a delegated step: it does that instruction and returns its result.
- **Trivial changes.** A change confined to one place that needs no design decision, such as a typo or a one-line fix, skips the workflow, triage included: the coordinator makes it, verifies it, and ends without the route line.
- **Routes.** Every other task starts with triage, given the request as written. The small route is triage, search (skipped when triage already answers what plan needs), plan, contracts, tests, implementation, cleanup and docs. The large route is triage, search, spec, the review stages and the user's explicit approval, then plan through docs. Any large-change signal from triage makes the change large; when plan returns "large change" the task switches to the large route, and a change never moves from large to small. An unclear idea goes through brainstorm first: questions to the user, a concept written by spec, reviews with the Scope, Critique and Comprehension lenses, and the user's choice to implement it or not.
- **Review stages** (large route): Scope; then Comprehension, Critique, Structural and Style in parallel; Scope again on what changed; then Readiness and Codebase in parallel. Each lens runs in a new review agent given only the repository path, the document's path and the lens. After each stage the coordinator gives the user the findings and asks how to continue; a stage repeats at most once.
- **Docs.** Every route ends with docs, followed by a review with the Docs lens: always on the large route, and on the small route only when docs changed files. The review's documentation findings go to a new docs agent, and its drift to a new implementation agent.
- **Coordination.** The coordinator starts each step with `thread-spawn`, `agent: <name>`, the effort of its row (low for triage, search, cleanup and docs; medium for plan, contracts, tests and implementation; high for spec and review) and the title `<Type>: <subject>`. Each instruction stands alone. When tests do not fail, or implementation or cleanup reports a failure, a new agent of the same name gets the concrete finding; the coordinator does not fix it itself. When an agent reports that the plan is wrong, the workflow goes back to plan. The answer ends with `Route: small|large — <reason>`. Git stays inspection-only.
- The ten step agents ship with the bundle as `bundles/runtime/default/src/host/agents/<name>.md` and are served by `default.agents/v1`; none names a model ([bundles/runtime/default/src/host/agents/built-in.ts](../../bundles/runtime/default/src/host/agents/built-in.ts), [bundles/runtime/default/manifest.json](../../bundles/runtime/default/manifest.json); the agent definitions are described in the [`default` README](../../bundles/runtime/default/README.md#agents)). `thread-spawn` belongs to [`threads`](../../bundles/features/threads/README.md); the runtime creates the child Thread (`RuntimeThreadControls.spawn`, [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts); see the [`runtime` README](../../bundles/runtime/runtime/README.md)).

Each step runs on the coordinator's provider and model, with the effort the coordinator gives it, when the coordinator's `thread-spawn` call names no model. SKILL.md asks only for `agent`, the effort and the title, and no built-in agent definition names a model, so `thread-spawn` passes none (`input.model ?? agent.model`, [bundles/features/threads/src/host/tools/thread-spawn.ts](../../bundles/features/threads/src/host/tools/thread-spawn.ts)), and the spawn starts from the parent's execution and applies only the effort it names ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), `spawnExecution`).

### After a compaction

- A compaction writes one retained "Loaded skills" message (`<bundle-instruction bundle="default" reason="loaded-skills">`) holding the skills loaded in the summarized span and not loaded again in the kept tail, within a size cap. The `coding-workflow` entry is placed first and never left out for that cap; the other entries fill the rest of it ([bundles/runtime/default/src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts), `loadedSkillsReplacement`). The message's caps are described in the [`default` README](../../bundles/runtime/default/README.md#compaction). Compaction itself is described in [context-compaction.md](context-compaction.md). The message itself is described in [skills.md](skills.md#loaded-skills-across-a-compaction).
