# Feature: Screen

- Status: `implemented`

## Problem

A GUI program that the agent or the reader starts in a Project's sandbox has nowhere to draw. The reader needs to watch and drive that sandbox's graphical display from the app, in a window of its own, whether the host runs on the reader's machine or on a remote server behind a tunnel or a reverse proxy. The screen must survive a host restart and a host that moves it, and it must not give the page it shows any access to the app.

## Decisions

- `screen` lists `workspace.selection/v1` and `runtime.records/v1` under `requires`, not `optional`: in a composition without the [`workspace`](../../bundles/desktop/workspace/README.md) bundle, or with a [runtime](../../bundles/runtime/runtime/README.md) that does not serve records, the bundle is quarantined with `missing_dependency` ([manifest rules](../architecture/bundles/manifest.md)).
- A new view's label is the selected Project's name, read from `runtime.records/v1`, and only while the selected Project is the Project the view watches; otherwise the label is the Project's id.
- The Screens pane keeps its header and collapse control, has no resize handle, and sits at the bottom of the sidebar column; open, it is as tall as its rows, up to 40% of the column, and scrolls past that.
- Screens rows align their icons with the pane header's chevron. A row's actions (Retry and Remove) show only while the row is hovered or holds keyboard focus (`:focus-visible`), laid over the row's right edge with no space reserved, and the row's status fades out while they show; a row clicked with the mouse returns to rest when the pointer leaves. The header's add action shows only while the header is hovered or focused. An open pane with no rows says so.
- Screens rows take the hover, pressed and keyboard-focus states of the sidebar's rows on their wrapper and have no selection; a disabled row takes none of these states. The bundle ships its own utility sheet listing the classes its rows use.

## Current behavior and contracts

### The bundles

- The feature is two bundles. `screen` 2.0.4 provides `screen.sessions/v2@2.0.0` (host) and `screen.views/v1@1.0.0` (desktop), and has a host part (the sessions), a desktop part (the reader's views and their windows) and a client part (the sidebar's Screens pane) ([bundles/features/screen/manifest.json](../../bundles/features/screen/manifest.json), [src/host/index.ts](../../bundles/features/screen/src/host/index.ts), [src/desktop/index.ts](../../bundles/features/screen/src/desktop/index.ts), [src/client/index.ts](../../bundles/features/screen/src/client/index.ts), [README](../../bundles/features/screen/README.md)).
- `screen-relay` 1.0.0 provides `screen.relay/v1@1.0.0` and has a host part only. The host's composition enables it and runs it resident in the host process ([bundles/features/screen-relay/manifest.json](../../bundles/features/screen-relay/manifest.json), [src/host/index.ts](../../bundles/features/screen-relay/src/host/index.ts), [app/backend/doric-host/composition.json](../../app/backend/doric-host/composition.json), [README](../../bundles/features/screen-relay/README.md)).
- The work is split because of where each half runs. The relay mounts on the host's shared request router and `http.Server`, which `doric.network/v1` hands only to a resident bundle. The sessions need the Project's sandbox, which `runtime.lease/v1.withLease` hands only to a bundle running in a host generation. So `screen` starts the sessions and publishes them on `screen.relay/v1`, and `screen-relay` serves them ([bundles/features/screen-relay/src/host/index.ts](../../bundles/features/screen-relay/src/host/index.ts), [bundles/features/screen/src/host/index.ts](../../bundles/features/screen/src/host/index.ts)).
- `screen` requires `log/v1`, `runtime.lease/v1@^1.1.0`, `ui/v1`, `workspace.selection/v1`, `runtime.records/v1`, `layout.stack/v2@^2.0.0` and `screen.relay/v1`. A window may send the scope keys `projectId`, `threadId` and `promptId` to `screen.sessions/v2` ([bundles/features/screen/manifest.json](../../bundles/features/screen/manifest.json)).
- The sandbox image must provide `xpra` with its HTML5 client; the host's sandbox image installs it ([app/backend/doric-host/.sandbox.Dockerfile](../../app/backend/doric-host/.sandbox.Dockerfile)).

### The flow

1. The reader adds a view for the selected Project from the Screens pane; the desktop part stores it ([bundles/features/screen/src/client/elements.tsx](../../bundles/features/screen/src/client/elements.tsx), [bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
2. The desktop part cannot call a host contract: a desktop generation reaches only the providers of its own environment and the kernel's `doric.*` services. It lists each attach it wants as a dial in the `screen.views/v1.watch` stream ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
3. Every app window that runs the client part watches that stream, calls `screen.sessions/v2.attach(projectId)` scoped to the dial's Project, and hands the answer back through `screen.views/v1.deliver` ([bundles/features/screen/src/client/index.ts](../../bundles/features/screen/src/client/index.ts), [bundles/features/screen/src/client/dial.ts](../../bundles/features/screen/src/client/dial.ts)).
4. On the host, `attach` ensures the Project's xpra session in its sandbox, publishes the session's upstream on `screen.relay/v1` under the session's token, and answers the host-relative path `/screen/<token>/` ([bundles/features/screen/src/host/provider.ts](../../bundles/features/screen/src/host/provider.ts)).
5. The desktop part turns the answer into the view's status and, when the reader asked for the window, opens it through `doric.windows/v1` at that path; the app resolves the path against the origin it reaches the host on ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts), [app/desktop/doric/src/platform/windows/view.ts](../../app/desktop/doric/src/platform/windows/view.ts)).
6. The window loads the page; the relay forwards it, and the live WebSocket, to the xpra server inside the sandbox ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).

### Sessions on the host

`screen.sessions/v2` 2.0.0 has one method, `attach(projectId)`. It answers `ready` with the host-relative path `/screen/<token>/` and the X display, such as `:100`; `pending` while the Project has no sandbox lease yet; or `unavailable` with the reason `sandbox`, `missing-xpra` or `start-failed`. Its full shape is in the [`screen` README](../../bundles/features/screen/README.md#contract-screensessionsv2-host) ([bundles/features/screen/src/contracts/index.ts](../../bundles/features/screen/src/contracts/index.ts)).

- `attach` is an idempotent ensure. It runs on the runtime lease of the call's scope through `runtime.lease/v1.withLease` (see the [runtime](../../bundles/runtime/runtime/README.md) for leases) and never acquires a lease: a lease that is pending answers `pending`, and any other lease that is not ready answers `unavailable` with `sandbox`. Concurrent calls for the same Project share one attempt ([bundles/features/screen/src/host/provider.ts](../../bundles/features/screen/src/host/provider.ts)).
- One Project has one screen. Every Thread of a Project shares the Project's sandbox and so its one session ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- Inside the sandbox the session manager first runs `command -v xpra`; when it fails, `attach` answers `unavailable` with `missing-xpra`. It then reads the marker `/tmp/doric-screen.json` (`{ display, port, token }`), lists the live displays with `xpra list`, and finds the sandbox's address as the first IPv4 address of `hostname -I` outside `127.*` ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- A marker whose display is live and whose port accepts a TCP connection within 1 second is reused as it is. A marker whose display is live but whose port does not answer has that display stopped with `xpra stop` first. Otherwise a session is started ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- A start uses the marker's display, or else the lowest display from `:100` up that `xpra list` does not report. It tries the ports `14500`, `14501` and `14502` in order, the marker's port first, each with `xpra start :<display> --html=on --bind-tcp=0.0.0.0:<port> --daemon=yes --log-file=/tmp/doric-screen.log`. Each `xpra start` may take 30 seconds. A start succeeds when `xpra list` reports the display live within 10 seconds and then the port accepts a connection within another 10 seconds. A failed start moves on to the next port, logging `Screen port is taken`, only when the log's last 4,096 characters contain `Address already in use` or `failed to setup tcp socket`; anything else, or the last port failing, answers `unavailable` with `start-failed`. A sandbox with no routable address also answers `start-failed` ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- A started session keeps the marker's token, or gets a new random UUID, and the marker is written again. So a restarted host, or a restarted session, reuses the same display, port and token. A marker that cannot be written logs `The screen marker could not be written` and the session is still served ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- The marker and the log live in the sandbox's `/tmp`, so they are read and written through the sandbox shell, the content passed as an argument ([bundles/features/screen/src/host/session.ts](../../bundles/features/screen/src/host/session.ts)).
- A ready session is published with `screen.relay/v1.expose({ token, host, port })`, after `forget` of the Project's previous token when it changed; `attach` answers only once the relay has accepted it. A session that cannot be served logs `The screen session is unavailable` with the Project's id and the reason ([bundles/features/screen/src/host/provider.ts](../../bundles/features/screen/src/host/provider.ts)).
- When the host part deactivates, it forgets every token it published; a relay that is gone is ignored ([bundles/features/screen/src/host/provider.ts](../../bundles/features/screen/src/host/provider.ts)).

### The relay

`screen.relay/v1` 1.0.0 lets the `screen` bundle register or replace the upstream of one token with `expose` and drop it with `forget`; its full shape is in the [`screen-relay` README](../../bundles/features/screen-relay/README.md#contract-provided-screenrelayv1) ([bundles/features/screen-relay/src/contracts/index.ts](../../bundles/features/screen-relay/src/contracts/index.ts), [bundles/features/screen-relay/src/host/service.ts](../../bundles/features/screen-relay/src/host/service.ts)).

- The relay binds no server of its own. On activation it registers with `doric.network/v1`, adds a middleware to the host's router and an `upgrade` listener to the host's `http.Server`, so the screen is served on whatever origin the host is reached on ([bundles/features/screen-relay/src/host/index.ts](../../bundles/features/screen-relay/src/host/index.ts), [bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- HTTP: a request under `/screen/<token>/` of a known token is forwarded to the upstream with the prefix removed and the query kept, `Host` rewritten to the upstream and hop-by-hop headers dropped both ways. An upstream error answers 502 `The screen upstream is unavailable.`, and an upstream request times out after 30 seconds ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- WebSocket: the relay opens a TCP connection to the upstream, sends a `GET` of the upstream path carrying every header of the browser's upgrade request, `Sec-WebSocket-Key` included, with the names lower-cased and `Host` rewritten to the upstream, returns xpra's handshake unchanged and then pipes raw bytes both ways. Subprotocols, extensions and frames reach xpra as the browser sent them. An upstream that fails before the handshake answers 502 ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- A request or upgrade under `/screen` with an unknown token answers 404. Every other request passes on to the host's other routes, and every other upgrade, such as Socket.IO, is left alone ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- On deactivation the relay passes every request through and destroys the sockets of every relayed WebSocket still open, the browser's and the upstream's; HTTP requests in flight are not ended ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- A process entry (S49a, not yet the one the host runs until S62) serves the relay as the only handler of its own loopback listener behind the gateway's `/screen/` prefix; there anything but a known token answers 404 ([bundles/features/screen-relay/README.md](../../bundles/features/screen-relay/README.md#process-entry-s49a)).
- The token is the capability: whoever reaches the host's origin and holds a token can watch and drive that screen, and the operator's network boundary is the access control ([bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).

### Views on the desktop

`screen.views/v1` 1.0.0 is provided by the desktop part and exposed to app windows; its full shape is in the [`screen` README](../../bundles/features/screen/README.md#contract-screenviewsv1-desktop) ([bundles/features/screen/src/contracts/index.ts](../../bundles/features/screen/src/contracts/index.ts), [bundles/features/screen/src/desktop/index.ts](../../bundles/features/screen/src/desktop/index.ts)).

- A view has an id, a label, the Project it watches and a status. Its status is `waiting`, `ready` with `path` and `display`, `unavailable` with its reason, or `failed`. An answer `pending` reads as `waiting`, and a dial with no answer (the window could not reach the host, or the answer was not a valid status) reads as `failed` ([bundles/features/screen/src/desktop/status.ts](../../bundles/features/screen/src/desktop/status.ts), [bundles/features/screen/src/client/api.ts](../../bundles/features/screen/src/client/api.ts)).
- `add({ projectId, label? })` creates a view in the state `waiting`, named after `label` or else the Project's id. `add` makes at most one view per Project: adding a Project already watched answers that view and opens or focuses its window, at once when the view is ready and otherwise once it is ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts), [bundles/features/screen/src/desktop/status.ts](../../bundles/features/screen/src/desktop/status.ts)).
- The views persist across restarts in `views.json` in the bundle's `doric.cache/v1` directory (its shape is in the [`screen` README](../../bundles/features/screen/README.md#data-and-persistence)), replaced atomically whenever `add` creates a view and whenever `remove` drops one. The status is never stored; a loaded view starts `waiting`. A missing or unreadable file, a file that is not that shape, or one with a single invalid entry reads as no views at all; a failed write keeps the list in memory. Every stored view loads, so a file with two views of one Project shows both ([bundles/features/screen/src/desktop/store.ts](../../bundles/features/screen/src/desktop/store.ts), [bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
- A loop runs every second and dials each view whose attach is due: a `waiting`, `failed` or `unavailable` view every 2 seconds, a `ready` view with an open window every 15 seconds, and a view whose image has no `xpra` never. A dial unanswered after 5 seconds is dialed again. The loop starts on the first `list`, `add`, `open` or `retry`, never on `watch` or `deliver`; the window only watches, so after an app restart the loaded views stay `waiting` (`Starting…`) until the reader clicks a row, presses Retry or adds a view ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts), [bundles/features/screen/src/desktop/status.ts](../../bundles/features/screen/src/desktop/status.ts)).
- Each dial carries a sequence number. `deliver` applies only the answer to the view's current dial, so a stale answer, or a second window's answer to the same dial, is ignored ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
- `watch(revision, listener)` pushes `{ revision, views, dials }` once the views are loaded, unless the caller already holds that revision, and after every change ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
- `open(viewId)` opens the window of a ready view, or focuses it when it is open; for a view that is not ready it remembers the request and makes it due, so the loop dials on its next pass unless a dial is already in flight, and the window opens when the view becomes ready. `retry(viewId)` makes a view that is not ready due, dropping any dial in flight, and focuses the open window of a ready one. `remove(viewId)` drops the view from the list and the file; it does not close the view's window ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).
- The desktop follows a screen that moved: when a ready answer carries another path than the one the open window shows, the window is navigated to it with `doric.windows/v1.navigate`. A focus that finds the window closed opens it again ([bundles/features/screen/src/desktop/status.ts](../../bundles/features/screen/src/desktop/status.ts), [bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts), [bundles/features/screen/src/desktop/windows.ts](../../bundles/features/screen/src/desktop/windows.ts)).
- The desktop part learns that the reader closed a window only when a focus finds it gone. Until then the view counts its window as open, so a ready view keeps being dialed every 15 seconds. If its screen then moves, `navigate` on the closed key fails with `not_found`: `deliver` stores the new status but fails before announcing it, so the pane shows it only with the next dial's change, and every later answer, and every click on the row, fails the same way, so the window cannot be reopened from the pane until the view is removed and added again or the app restarts ([bundles/features/screen/src/desktop/status.ts](../../bundles/features/screen/src/desktop/status.ts), [bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts), [bundles/features/screen/src/desktop/windows.ts](../../bundles/features/screen/src/desktop/windows.ts)).

### The screen window

- Each view has one window, opened through `doric.windows/v1.open` with the key `screen:<viewId>`, a view of the host-relative path in the session partition `screen:<viewId>`, the view's label as the native window title, and the native title bar ([bundles/features/screen/src/desktop/windows.ts](../../bundles/features/screen/src/desktop/windows.ts)).
- The app opens it as a view window: an Electron `BaseWindow` whose whole content is one `WebContentsView` in that partition, sandboxed, with context isolation and no Node integration. It carries no preload and no bundle contracts and no app chrome; it loads the path resolved against the origin the app reaches the host on (`DORIC_HOST_URL`, else `http://127.0.0.1:3000`), which is the host's page the relay serves ([app/desktop/doric/src/platform/windows/native-windows.ts](../../app/desktop/doric/src/platform/windows/native-windows.ts), [app/desktop/doric/src/platform/windows/view.ts](../../app/desktop/doric/src/platform/windows/view.ts), [app/desktop/doric/src/main.ts](../../app/desktop/doric/src/main.ts), [app/desktop/doric/src/platform/bridge/host-bridge.ts](../../app/desktop/doric/src/platform/bridge/host-bridge.ts)).
- The page may navigate within that origin, as the xpra client does to `connect.html`, and nowhere else; it may open no new window ([app/desktop/doric/src/platform/windows/navigation-guard.ts](../../app/desktop/doric/src/platform/windows/navigation-guard.ts), [app/desktop/doric/src/platform/windows/view.ts](../../app/desktop/doric/src/platform/windows/view.ts)).
- Opening an open key restores and focuses its window, and loads the new path when it differs ([app/desktop/doric/src/platform/windows/native-windows.ts](../../app/desktop/doric/src/platform/windows/native-windows.ts)).
- `add` never creates a second view of a Project, so a Project whose views all came from `add` has one view, and so one window onto its one screen ([bundles/features/screen/src/desktop/views.ts](../../bundles/features/screen/src/desktop/views.ts)).

### The Screens pane

- The client part registers the pane `screen-sidebar` in `layout.stack/v2`, titled "Screens", with the order 10, collapsible and initially collapsed. The [layout](../../bundles/desktop/layout/README.md) draws it below the Threads tree with its header and collapse control ([bundles/features/screen/src/client/index.ts](../../bundles/features/screen/src/client/index.ts), [bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx](../../bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx)).
- The header's **+** (`<screen-group-action>`, "New screen view") adds a view for the Project selected in `workspace.selection/v1`; it is disabled with no selected Project and while `screen.views/v1` is not served ([bundles/features/screen/src/client/elements.tsx](../../bundles/features/screen/src/client/elements.tsx)).
- The pane (`<screen-sidebar>`) lists only the views of the selected Project. With a Project selected and no view it shows `No screens open`; with no Project it shows nothing ([bundles/features/screen/src/client/elements.tsx](../../bundles/features/screen/src/client/elements.tsx)).
- Clicking a row calls `open`. Each row shows the view's label and one state ([bundles/features/screen/src/client/elements.tsx](../../bundles/features/screen/src/client/elements.tsx)):

| Status                        | Row text                 | Retry |
| ----------------------------- | ------------------------ | ----- |
| `waiting`                     | `Starting…`              | No    |
| `ready`                       | the display, e.g. `:100` | No    |
| `unavailable`, `sandbox`      | `Sandbox unavailable`    | Yes   |
| `unavailable`, `start-failed` | `Screen failed to start` | Yes   |
| `unavailable`, `missing-xpra` | `No xpra in the image`   | No    |
| `failed`                      | `Backend unavailable`    | Yes   |

- Every row has a Remove action, and a row that can be retried has a Retry action to its left. While `screen.views/v1` is not served, the row and its actions are disabled ([bundles/features/screen/src/client/elements.tsx](../../bundles/features/screen/src/client/elements.tsx)).
