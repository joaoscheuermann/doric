# Feature: Sandboxes

- Status: `implemented`

## Problem

The agent runs commands, installs packages and changes files, and none of that may touch the machine Doric runs on. Each Project needs a machine of its own, with bounded CPU, memory and disk, a network it cannot use to reach the host or private addresses, and files that survive the end of one sandbox so that a Project that comes back finds its work again. Sandboxes take time to provision and a host can hold only a few, so their number must be bounded and their creation retried when a provider fails. One deployment wants a container on a developer machine, another a virtual machine on a prepared Linux host, and the code that uses a sandbox must not change between the two.

## Decisions

- `sandbox/v1.acquire` is the only local method: the lease it returns and the abort signal it takes are live objects of the process. `describe`, `discard`, `machines` and `machine` are asynchronous and serializable, so the `transport` bundle, which runs in the kernel (the host process), reaches the provider, which runs in the generation process (the Node process the kernel forks for the current generation of bundles). [Process isolation](../architecture/bundles/process-isolation.md) describes the two kinds of process.
- `sandbox/v1.machines()` and `machine(id)` answer for the provider of the active generation only.
- The `docker` and `firecracker` bundles do not read `DORIC_SANDBOX_PROVIDER`: the composition decides which of them is enabled. The kernel reads no environment variable for this; the host makes the choice. Without `DORIC_COMPOSITION`, the host boots the shipped composition with the chosen option enabled in place of `docker`; with `DORIC_COMPOSITION`, the operator's composition is booted as written and its enabled bundle is the provider.
- A value of `DORIC_SANDBOX_PROVIDER` outside the options selects the default, `docker`; it is not refused.
- The shipped composition lists `sandbox/v1` under `required`, so it is a structural contract of the shipped host: when no active bundle provides it, the host logs `Bundle recovery mode` with the reason `structural providers unavailable: …` and stops on its fatal path, at boot and whenever a generation becomes active.
- Each sandbox bundle requires `log/v1`, because the pool's records go to `log/v1`. Each bundle has its own copy of the logger that turns the pool's Pino records into `log/v1` calls.

## Current behavior and contracts

### The units

- Four packages and two bundles make the feature. [`sandbox`](../../packages/sandbox/README.md) is the provider-neutral boundary: the `SandboxProvider` and `SandboxRuntime` a provider implements, and `createSandbox`, which adds the workspace, Git, file, diff, SSH and lifecycle operations on top ([packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts), [packages/sandbox/src/lib/types/sandbox.ts](../../packages/sandbox/src/lib/types/sandbox.ts)). [`sandpool`](../../packages/sandpool/README.md) bounds and leases the sandboxes ([packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)). The npm packages [`docker-sandbox`](../../packages/docker-sandbox/README.md) (`packages/docker-sandbox`) and [`firecracker-sandbox`](../../packages/firecracker-sandbox/README.md) (`packages/firecracker-sandbox`) depend on `sandbox` and each exposes one provider ([packages/docker-sandbox/package.json](../../packages/docker-sandbox/package.json), [packages/firecracker-sandbox/package.json](../../packages/firecracker-sandbox/package.json)).
- The [`docker`](../../bundles/sandboxes/docker/README.md) and [`firecracker`](../../bundles/sandboxes/firecracker/README.md) bundles, version 1.0.0, each provide `sandbox/v1@1.0.0` and require `hooks/v1` and `log/v1` ([bundles/sandboxes/docker/manifest.json](../../bundles/sandboxes/docker/manifest.json), [bundles/sandboxes/firecracker/manifest.json](../../bundles/sandboxes/firecracker/manifest.json)). At activation each builds its provider, wraps it in a VM registry (`createVmRegistry`), builds a pool over it, and provides `sandbox/v1`; nothing is contacted until the first acquisition, and deactivation disposes the pool ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- The [`runtime`](../../bundles/runtime/runtime/README.md) bundle requires `sandbox/v1@^1.0.0` and is the only caller that acquires a sandbox; [Projects and Threads](projects-and-threads.md) describes how a Project holds its lease ([bundles/runtime/runtime/manifest.json](../../bundles/runtime/runtime/manifest.json), [bundles/runtime/runtime/src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts)).
- The [`transport`](../../bundles/foundation/transport/README.md) bundle also requires `sandbox/v1@^1.0.0`, to answer the VM routes below; it never acquires ([bundles/foundation/transport/manifest.json](../../bundles/foundation/transport/manifest.json), [bundles/foundation/transport/src/host/routes/vms.ts](../../bundles/foundation/transport/src/host/routes/vms.ts)).

### Choosing the provider

- The shipped composition enables `docker`, requires `sandbox/v1` among its structural contracts, and declares the alternative `sandbox` with the variable `DORIC_SANDBOX_PROVIDER`, the default `docker` and the options `docker` and `firecracker` ([app/backend/doric-host/composition.json](../../app/backend/doric-host/composition.json)).
- Without `DORIC_COMPOSITION`, the host reads the variable: a value among the options is chosen, any other value or none chooses `docker`, and a chosen `firecracker` replaces `docker` in the enabled bundles. With `DORIC_COMPOSITION`, the composition is booted as written; the option the host reports is the one of its enabled bundles, or the default when none or several are enabled. The chosen option appears only in the host's `Doric starting` and `Doric listening` log lines, as `alternatives` ([app/backend/doric-host/src/index.ts](../../app/backend/doric-host/src/index.ts), [app/backend/doric-host/src/lib/bundles/boot.ts](../../app/backend/doric-host/src/lib/bundles/boot.ts), [packages/bundle/src/runtime/composition.ts](../../packages/bundle/src/runtime/composition.ts)). The [composition document](../architecture/bundles/composition-and-distribution.md) describes alternatives in general.

### The `sandbox/v1` contract

`sandbox/v1` 1.0.0 is `SandboxProviderApi`, exported as `SandboxV1` from the runtime's contracts module ([bundles/runtime/runtime/src/contracts/sandbox.ts](../../bundles/runtime/runtime/src/contracts/sandbox.ts)).

| Method                           | Behavior                                                                                                                                                |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acquire({ identity, signal? })` | A named acquisition from the pool: resolves a `SandboxLease` (`{ sandbox, release }`) for the sandbox made for `identity`. The signal cancels the wait. |
| `describe()`                     | `{ provider, durableWorkspace }`: `{ provider: 'docker', durableWorkspace: true }` or `{ provider: 'firecracker', durableWorkspace: false }`.           |
| `discard(identity)`              | Removes a deleted Project's durable workspace. On Docker it removes the workspace's containers, then its volume; on Firecracker it does nothing.        |
| `machines()`                     | The `{ id, provider }` of every runtime this provider provisioned and has not yet disposed.                                                             |
| `machine(id)`                    | One of those, or `undefined`.                                                                                                                           |

The VM registry records a runtime once it is provisioned and removes it once its disposal completes; a runtime whose disposal fails stays listed ([packages/sandbox/src/lib/vms.ts](../../packages/sandbox/src/lib/vms.ts)).

### The VM routes

The `transport` bundle exposes the provider's machines over HTTP; its [README](../../bundles/foundation/transport/README.md) holds the full routes ([bundles/foundation/transport/src/host/routes/vms.ts](../../bundles/foundation/transport/src/host/routes/vms.ts)).

- `GET /vms` answers `sandbox/v1.machines()`.
- `GET /vms/:id/ssh` reads the machine with `sandbox/v1.machine(id)` and answers 404 `vm_not_found` when there is none. It then asks `runtime/v2.vmSsh(id)`, which answers only while a Project that is not closing holds that machine's lease and its sandbox has SSH; otherwise the route answers 409 `vm_ssh_unavailable`. On success it answers the machine with the Project's id and its SSH access. Every answer of this route, the 404 and the 409 included, carries `Cache-Control: no-store`. This is how a user reaches the SSH that `DORIC_SANDBOX_SSH` enables ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/runtime/runtime/src/host/services/runtime.ts](../../bundles/runtime/runtime/src/host/services/runtime.ts)).

### Settings

Both bundles read their settings from the environment at activation ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).

| Variable                      | Read by                 | Default            | Meaning                                                                                                                                                |
| ----------------------------- | ----------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DORIC_SANDBOX_IMAGE`         | `docker`, `firecracker` | `node:22-bookworm` | The image every sandbox runs, pulled only when it is not present locally (on Firecracker: when the ext4 cache holds no disk for that image reference). |
| `DORIC_SANDBOX_SSH`           | `docker`, `firecracker` | off                | Exactly `true` adds user SSH access to each sandbox.                                                                                                   |
| `DORIC_SANDBOX_DOCKER_SOCKET` | `docker`                | off                | Exactly `true` mounts the host daemon's socket into every sandbox.                                                                                     |
| `DORIC_SANDBOX_CPUS`          | `docker`                | `4`                | The CPU ceiling of each sandbox.                                                                                                                       |
| `DORIC_SANDBOX_MEMORY_MIB`    | `docker`                | `2048`             | The memory ceiling of each sandbox, in MiB.                                                                                                            |

- `DORIC_SANDBOX_CPUS` and `DORIC_SANDBOX_MEMORY_MIB` take a whole positive number. An unset or empty value keeps the default; any other value fails activation with `<name> must be a whole positive number, got "<value>"` ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts)).
- Every Docker sandbox has a 4096 MiB writable layer. Every Firecracker sandbox has 1 CPU, 512 MiB of memory and a 4096 MiB disk ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- Both bundles provision with outbound networking (`mode: 'egress'`) and the DNS server `1.1.1.1` ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- The Compose profile `firecracker` sets `DORIC_SANDBOX_PROVIDER=firecracker` and defaults `DORIC_SANDBOX_SSH` to `true`. The profile `docker` sets `DORIC_SANDBOX_PROVIDER=docker`, defaults `DORIC_SANDBOX_IMAGE` to `doric-sandbox:local`, `DORIC_SANDBOX_SSH` to `true` and `DORIC_SANDBOX_DOCKER_SOCKET` to `false`, and passes `DORIC_SANDBOX_CPUS` and `DORIC_SANDBOX_MEMORY_MIB` empty unless set. The Doric runtime images set `DORIC_SANDBOX_SSH=true` ([app/backend/doric-host/compose.yaml](../../app/backend/doric-host/compose.yaml), [app/backend/doric-host/.Dockerfile](../../app/backend/doric-host/.Dockerfile)). The [host README](../../app/backend/doric-host/README.md) lists the host's variables.
- At host start, each bundle reports the stage `sandbox_pool`, then logs `Configuring sandbox pool` and `Sandbox pool configured` with its provider, image, resources, pool limits, network mode and SSH setting; the `docker` bundle also logs whether the socket is shared ([bundles/sandboxes/docker/src/host/start.ts](../../bundles/sandboxes/docker/src/host/start.ts), [bundles/sandboxes/firecracker/src/host/start.ts](../../bundles/sandboxes/firecracker/src/host/start.ts)).

### The pool

- Both bundles build the pool with `minIdle: 0`, `maxSandboxes: 10` and `maxCreateAttempts: 3`. Every acquisition names its Project as the identity, and the pool provisions a new session for a named acquisition instead of leasing a warmed one, so the pool warms nothing ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts), [packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)).
- At most `maxSandboxes` sessions exist at once. Acquisitions wait in arrival order; a warmed idle session is offered only to an acquisition without an identity. A session whose named caller cancelled or gave up while it was being created is disposed, never leased to another caller ([packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)).
- A failed factory call is retried with exponential backoff: 250 ms, doubling up to 5 s. After `maxCreateAttempts` consecutive failures, every pending acquisition rejects with `Sandpool could not create a sandbox after 3 attempts`; later demand starts a fresh batch, so a provider that recovers serves new work ([packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)).
- Releasing a lease disposes its session: a released session is never reused, and `release` is idempotent. A disposal that fails is retried with the same backoff until it succeeds, and `release` resolves only then; until then the session keeps its place under `maxSandboxes`, and `dispose()` of the pool waits for it too. Once a lease is released, every operation on its sandbox, SSH included, fails with `Sandbox lease is no longer active` ([packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)).
- The pool logs through the bundle's logger to `log/v1`, at the level `debug` and above ([bundles/sandboxes/docker/src/host/logger.ts](../../bundles/sandboxes/docker/src/host/logger.ts), [bundles/sandboxes/firecracker/src/host/logger.ts](../../bundles/sandboxes/firecracker/src/host/logger.ts)).

### The sandbox boundary

- `createSandbox` requires each of `cpuCount`, `memoryMiB` and `diskMiB` to be a positive integer, and confines every file path and working directory below the root, `/workspace` by default ([packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts)).
- The network policy defaults to `disabled`. Effective egress needs at least one DNS server, and each DNS server must be an IPv4 literal. Private addresses are reached only through exceptions by IPv4 CIDR, protocol and ports. Enabling SSH turns on egress. SSH binds to `127.0.0.1` unless a bind address is given, and a non-loopback bind address requires an advertised host ([packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts)).
- A named `workspace` is passed to the provider unchanged; the provider decides whether the files outlive the sandbox ([packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts)). The [`sandbox` README](../../packages/sandbox/README.md) gives the session's methods and the workspace listing helpers.

### Docker

- **Durable workspace.** A sandbox provisioned with a workspace keeps its files in the Docker volume `doric-workspace-<identity>`, bound at the sandbox root, and labels its container `doric.sandbox.workspace=<identity>`. The identity must start with a letter or digit and hold only letters, digits, `_`, `.` and `-` ([packages/docker-sandbox/src/lib/workspace.ts](../../packages/docker-sandbox/src/lib/workspace.ts), [packages/docker-sandbox/src/lib/provider.ts](../../packages/docker-sandbox/src/lib/provider.ts)).
- **Reattachment.** Provisioning one identity is serialized. While this process already serves the identity, a new lease shares that container, and the container is removed with the last lease. Otherwise the provider lists the containers labelled with the identity, running ones first, then the newest, and keeps the first whose image, working directory, labels, exposed ports, network mode, memory, CPUs, writable-layer size, DNS, binds and SSH port bindings match the request; it removes every other one and creates a container when none matches. The volume is kept in every case, so a Project finds its files again after a container is replaced or the host restarts. A removal that fails fails the acquisition ([packages/docker-sandbox/src/lib/provider.ts](../../packages/docker-sandbox/src/lib/provider.ts), [packages/docker-sandbox/src/lib/reuse.ts](../../packages/docker-sandbox/src/lib/reuse.ts)).
- **Discard.** `discardWorkspace` removes the workspace's containers, then its volume; removing what is already gone succeeds ([packages/docker-sandbox/src/lib/workspace.ts](../../packages/docker-sandbox/src/lib/workspace.ts)).
- **Limits.** CPU and memory become the daemon's `NanoCpus` and `Memory` ceilings, and the disk becomes the writable-layer limit `StorageOpt.size`. When the daemon rejects that option, the provider creates the container once more without it: the writable layer is then unmetered, and CPU and memory stay enforced. A container made that way never matches a request on reattachment, so it is replaced at the next acquisition, its volume kept. The volume holds its files on the host's own storage, so the disk limit bounds only the writable layer ([packages/docker-sandbox/src/lib/provider.ts](../../packages/docker-sandbox/src/lib/provider.ts), [packages/docker-sandbox/src/lib/reuse.ts](../../packages/docker-sandbox/src/lib/reuse.ts)).
- **Docker socket.** With `exposeDockerSocket`, which the bundle sets from `DORIC_SANDBOX_DOCKER_SOCKET`, every sandbox gets the host daemon's Unix socket at `/var/run/docker.sock`, so its Docker CLI can build and run the images a Project describes. That socket carries the daemon's authority on the host. A connection that is not a Unix socket shares nothing ([packages/docker-sandbox/src/lib/docker.ts](../../packages/docker-sandbox/src/lib/docker.ts), [packages/docker-sandbox/src/lib/provider.ts](../../packages/docker-sandbox/src/lib/provider.ts)).
- **Networking on Linux.** Egress requires a local Unix daemon, access to the host network namespace and nftables with `CAP_NET_ADMIN`. The provider installs one nftables table per container, keyed to its inspected address: it drops new traffic from the sandbox to the host, drops traffic to the protected ranges (`0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`) except the private exceptions, and then accepts DNS to the configured servers, so a DNS server inside a protected range stays blocked (the bundles use `1.1.1.1`) ([packages/docker-sandbox/src/lib/host.ts](../../packages/docker-sandbox/src/lib/host.ts)).
- **Networking elsewhere.** On macOS and Windows the provider installs no firewall and uses Docker Desktop's bridge and NAT, so the ranges Linux blocks stay reachable. On any other platform it refuses to provision ([packages/docker-sandbox/src/lib/host.ts](../../packages/docker-sandbox/src/lib/host.ts)).
- **SSH.** SSH runs the pinned Dropbear inside the container with password logins disabled, with Ed25519 user and host keys generated for each sandbox, and publishes port 22 on the policy's bind address, on a host port Docker allocates unless the policy names one. A reattached container with SSH is restarted, so no daemon with stale keys keeps running ([packages/docker-sandbox/src/lib/host.ts](../../packages/docker-sandbox/src/lib/host.ts), [packages/docker-sandbox/src/lib/provider.ts](../../packages/docker-sandbox/src/lib/provider.ts)).

### Firecracker

- The [`firecracker-sandbox`](../../packages/firecracker-sandbox/README.md) provider runs on Linux x86_64 only. Before each provisioning it checks the host (KVM, TUN, cgroup v2, IPv4 forwarding, nftables, Firecracker and jailer 1.16.1, the guest kernel and initramfs, the Dropbear key tool, writable state and cache directories, and the tools it calls) and refuses one that lacks any of them; it has no Docker dependency and no socket access ([packages/firecracker-sandbox/src/lib/preflight.ts](../../packages/firecracker-sandbox/src/lib/preflight.ts), [packages/firecracker-sandbox/src/lib/firecracker.ts](../../packages/firecracker-sandbox/src/lib/firecracker.ts)).
- It resolves `linux/amd64` OCI registry images with `skopeo`, which uses its default registry auth file, and `umoci`, converts each root filesystem into an immutable ext4 base disk, and keeps those disks in a cache bounded to 20 GiB that evicts the least recently used. Eviction skips disks in use; when only in-use disks remain over the limit, provisioning fails with `Firecracker rootfs cache is full with in-use images` ([packages/firecracker-sandbox/src/lib/image.ts](../../packages/firecracker-sandbox/src/lib/image.ts)).
- Each sandbox gets a sparse ext4 writable overlay disk, a jailed Firecracker process, a private `/30` network on its own TAP device from the pool `10.231.0.0/16`, a management SSH channel for the provider, and, when SSH is on, a proxied user SSH access with Ed25519 keys ([packages/firecracker-sandbox/src/lib/disk.ts](../../packages/firecracker-sandbox/src/lib/disk.ts), [packages/firecracker-sandbox/src/lib/runtime.ts](../../packages/firecracker-sandbox/src/lib/runtime.ts), [packages/firecracker-sandbox/src/lib/network.ts](../../packages/firecracker-sandbox/src/lib/network.ts), [packages/firecracker-sandbox/src/lib/ssh.ts](../../packages/firecracker-sandbox/src/lib/ssh.ts)).
- Its nftables rules drop new traffic from the sandbox to the host and to the protected ranges, except the private exceptions, and then accept DNS to the configured servers, so a DNS server inside a protected range stays blocked ([packages/firecracker-sandbox/src/lib/network.ts](../../packages/firecracker-sandbox/src/lib/network.ts)).
- The first provisioning through a client removes every sandbox recorded under the state directory's `sandboxes`, whether or not its process still runs: it sends `SIGKILL` to every process whose command line names the sandbox's id and `firecracker` or `jailer`, unmounts its base disk, deletes its nftables tables and TAP device, its network record and its cache-use markers, and removes its jail and state directories. It also deletes `.network-lock` under the state directory, `.lru-lock` under the cache directory and every lock under the cache's `locks`. So two provider processes cannot share these directories: the second one to provision removes the first one's sandboxes. Disposal releases the same resources of one sandbox ([packages/firecracker-sandbox/src/lib/firecracker.ts](../../packages/firecracker-sandbox/src/lib/firecracker.ts), [packages/firecracker-sandbox/src/lib/reconcile.ts](../../packages/firecracker-sandbox/src/lib/reconcile.ts), [packages/firecracker-sandbox/src/lib/runtime.ts](../../packages/firecracker-sandbox/src/lib/runtime.ts)).
- Nothing outlives a Firecracker sandbox: the bundle passes the Project's id as the workspace name, the provider keeps no durable workspace, and every sandbox starts from its image ([bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts), [packages/firecracker-sandbox/src/lib/runtime.ts](../../packages/firecracker-sandbox/src/lib/runtime.ts)).

### In the runtime

- The runtime's workspace service holds the association between a Project and its lease in process memory. It acquires with the Project's id as the identity and the Project's abort signal ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The runtime itself applies remote credentials inside the sandbox, through sandbox commands, not through any tool's arguments: it sets the Git identity with `git config --global user.name` and `user.email`, and for a GitHub token sets `credential.helper store`, stores `https://<user>:<token>@github.com` as the credential and writes the GitHub CLI's hosts file, passing the token in each command's environment. A failure there only logs `Git credentials could not be applied` and never fails the Project ([bundles/runtime/runtime/src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts), [bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- When the acquisition, the read of the configuration in force, the reset of a working directory missing from the sandbox, or the write of the `ready` state of the Project or its Threads fails, the Project ends `failed` with `sandbox_acquisition_failed`. A directory probe that cannot run keeps the stored directories and fails nothing ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The runtime waits for `release` before it records how a Project ends. Both bundles hand the runtime the pool's lease unchanged, whose `release` never rejects, so a Project whose disposal keeps failing waits until the disposal succeeds, and a terminated one stays `cancelling` meanwhile ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts), [packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)). Only a lease whose `release` rejects, which no shipped provider produces, gives a failed release, whose outcome depends on why the lease ends. On termination the Project ends `failed` with `sandbox_release_failed`. On a host stop it is written back `queued` with the error code `sandbox_release_failed`, so it stays resumable. When a Project drains from the host to another generation, the runtime logs `Project sandbox release failed` and the Project keeps its state ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- When a Project is deleted, the runtime calls `sandbox/v1.discard` with its id; a failed discard logs `Project workspace discard failed` and never fails the deletion ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
