# Feature: generative UI in the conversation

- Status: `implemented`

## Problem

An agent that can answer only in text describes a form, a table or a choice in words, and the reader has to translate it back. The agent also needs a reliable way to ask the reader to decide something, and to learn when the UI it wrote is broken. So the agent's answer itself carries UI: the agent writes an OpenUI Lang program in a fence, the conversation draws it while the answer streams, a click on a control goes back to the agent as the reader's next message, a question to the reader is a form drawn the same way, and errors in a drawn program reach both the reader and the agent.

## Decisions

- The fence tag decides where a program is drawn. A conversation fence (` ```openui-lang `) is drawn in the app's own DOM, with react-ui's library and Doric's tokens. Only a papercraft fence (` ```papercraft `) is drawn in the isolated frame, because it runs repository code; it is described in [papercraft.md](papercraft.md).
- A fence names its program in its info string, for example ` ```openui-lang settings `. A later fence with the same identity is a patch of that program, merged by statement name; a fence with a new identity starts a new program. A fence without an identity always starts a new program and never patches the Thread's last one.
- The agent asks the reader to decide through the question form: a fence whose first line is `root = AskForm(…)`. Only a main Thread asks the reader, and the answers arrive as the next user request. A question fence is always a whole program and never a patch, and a question is identified by the prompt that wrote it and the digest of its parsed questions.
- The first recorded answer to a question is final. The answer is recorded under the prompt that took it, so a rewind of that prompt makes the question pending again.
- A click on a control sends at once, with no review step: the action's message becomes the reader's next message by the composer's route, a steer while a prompt runs and a new prompt otherwise. The message is marked as coming from the UI, and one action per fence is in flight at a time. The risk is accepted knowingly: after one click, text the model wrote becomes the reader's message, which is prompt injection through model-written button text.
- Actions work only on the latest closed revision of a program, in a main Thread. A click on an older revision, on a fence still streaming or in a subagent's Thread sends nothing.
- `Modal` is drawn inside its fence: no model-written dialog covers the window. `@OpenUrl` is disabled and shows its URL as text.
- A fence's errors reach the agent only when a window drew it, from the renderer's `onError` and the conversation's own check; no host parses fences to find errors.
- A closed fence's errors are sent within 200 ms of their report, for both fence tags: as a steer of the Thread's latest prompt while it runs, or as a new prompt when none runs, within the limits under [Errors](#errors). The rest wait for the Thread's next prompt start.
- The reader sees a program's errors in one card under its fence: a header with an alert icon and "1 error" or "N errors", one plain line per error with the statement name before it when there is one, no code badges, and the footer "Sent to the agent." once reported. The card lists the program half of the conversation's own check; the question form shows its own problems itself.
- The instructions are a static skill, `openui`, loaded on demand. It holds the language and the built-in components; its text is generated from OpenUI's own prompt builder and committed to Git.
- The skill's rules: a fence with the same name as an earlier one is a patch merged into it; a new program is written whole, starting with `root`; a fragment is never sent as a new program; an `AskForm` holds at most 5 questions, each `AskQuestion` 2 to 6 options, and every `AskOption` is given a description of at least one character, although the form's schema accepts an option without one. When the text of a program is gone from the conversation, for example after a compaction, the agent writes it whole again; no other instruction restores it.
- No local state is durable: form values and `$variables` reset when a fence remounts.
- The OpenUI packages are used directly, with no reimplementation: `@openuidev/lang-core` 1.0.2, `@openuidev/react-lang` 1.0.2 and `@openuidev/react-ui` 0.18.1, each pinned to an exact version ([bundles/features/openui/package.json](../../bundles/features/openui/package.json); see the README's [Dependencies](../../bundles/features/openui/README.md#dependencies)).
- In the `openui` bundle, the `zustand` peer of react-ui and of `@openuidev/react-headless` resolves to the root zustand 5 (`^5.0.15`) through root `overrides` entries, and `@openuidev/react-headless` is an installed peer of react-ui that no Doric module imports ([package.json](../../package.json)).
- OpenUI's runtime telemetry is opt-in through `OPENUI_RUNTIME_TELEMETRY_ENABLED`, and Doric never sets it: no Doric module names the variable, the bundle's own code reads no environment variable at run time, and only its client part, which runs in a browser window where lang-core sends no runtime telemetry, imports an OpenUI package (see the README's [Configuration](../../bundles/features/openui/README.md#configuration)).

## Current behavior and contracts

The feature is the `openui` bundle (2.3.4), which draws the fences and keeps the questions and the errors, over the conversation of the `chat` bundle (2.0.0), which finds the fences in the agent's answer and sends the reader's clicks. Both rely on contracts of the `runtime` bundle (`runtime.threads/v1`, `runtime.hooks/v1` and the fence helpers of its contracts module). Each README gives the full shape of its contracts: [bundles/features/openui/README.md](../../bundles/features/openui/README.md), [bundles/desktop/chat/README.md](../../bundles/desktop/chat/README.md) and [bundles/runtime/runtime/README.md](../../bundles/runtime/runtime/README.md). The diagram components of the same library are described in [openui-diagrams.md](openui-diagrams.md), and how the conversation draws everything else in [conversation.md](conversation.md).

### Fences and programs

- At activation the `openui` client defines `<openui-fence>` and registers it as the chat's renderer of `openui-lang` fences through `chat.views/v1` 1.2.0 `registerFenceRenderer`; no setting governs it ([bundles/features/openui/src/client/index.ts](../../bundles/features/openui/src/client/index.ts)). From then on the chat draws every `openui-lang` fence of an agent turn as one such element per fence key and sets its `view` ([bundles/desktop/chat/src/client/services/views.ts](../../bundles/desktop/chat/src/client/services/views.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/markdown-blocks.ts](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/markdown-blocks.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/fence-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/fence-node.tsx)).
- The view (`ChatFenceView`, [bundles/desktop/chat/src/contracts/index.ts](../../bundles/desktop/chat/src/contracts/index.ts)), built by the conversation ([bundles/desktop/chat/src/client/components/organisms/conversation/index.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/index.tsx)), carries the fence, the Thread's `origin` (`agent` for a subagent's Thread, `user` otherwise) and every fence of the same tag in the Thread. A fence has the key `<promptId>/<turnSequence>/<index>`, where `<index>` counts the turn's fences of the same tag, its info string, its body and a state: `closed` when its closer line exists, `streaming` while its turn is the last one and its prompt has not settled, `unterminated` otherwise ([bundles/desktop/chat/src/client/domain/fences.ts](../../bundles/desktop/chat/src/client/domain/fences.ts)).
- A fence's identity is the second word of its info string when it matches `^[a-z][a-z0-9-]{0,63}$`; otherwise, and always for a question fence, it is `_<n>`, the fence's ordinal among the Thread's fences of its tag ([bundles/features/openui/src/contracts/identity.ts](../../bundles/features/openui/src/contracts/identity.ts)).
- The fold of a Thread turns its fences into revisions: each fence with a completed line that is not blank is the next revision of its identity, and a fence whose identity already has a program is merged into it statement by statement with OpenUI's `mergeStatements`. A merge that throws keeps the earlier program and is reported as an error. The folds of one window are shared by its elements, one per Thread and tag ([bundles/features/openui/src/contracts/fold.ts](../../bundles/features/openui/src/contracts/fold.ts)).
- The element starts importing the renderer chunk `client/chunks/renderer.js` at its first render, once per window, and appends the chunk's stylesheet link without waiting for it; a failed import is not retried ([bundles/features/openui/src/client/folds.ts](../../bundles/features/openui/src/client/folds.ts)). Until it can draw, it shows the fence's source with a line under it ([bundles/features/openui/src/client/fence-element.tsx](../../bundles/features/openui/src/client/fence-element.tsx)):
  - a fence with no completed line that is not blank: "Writing…", or "Incomplete: the answer ended before the fence closed" when the fence is unterminated, whether or not the chunk has loaded;
  - a failed import: "The UI renderer did not load: <message>";
  - while the chunk loads, or while the fold has no revision for the fence: "Drawing…".
- Then the chunk draws the revision: the raw body while a first revision streams, the folded program after. A drawn unterminated fence has the footer "Incomplete: the answer ended before the fence closed". A crash of the renderer outside OpenUI's own handling draws "This UI failed to draw: <message>" in place of the program; it is reported as a `render-error` when the fence is closed or cut off, unless the renderer has already passed that revision's errors, even an empty list; a crash after that reaches only the reader ([bundles/features/openui/src/client/chunks/renderer.ts](../../bundles/features/openui/src/client/chunks/renderer.ts)).
- The library is react-ui's, with `Modal` drawn as a bordered block inside the fence, the question built-ins and the diagram components ([bundles/features/openui/src/client/library.ts](../../bundles/features/openui/src/client/library.ts)). Doric's tokens map 42 `--openui-*` variables ([bundles/features/openui/src/client/tokens.css](../../bundles/features/openui/src/client/tokens.css)).

### Actions

- A click on a control of a drawn program builds its text: the action's message, then the action's parameters, then the values of the form the control belongs to or the program's `$variables`, each as `<key>: <value>`. A text over 16,000 UTF-16 code units, an action with no message or an action type other than continuing the conversation sends nothing and shows a line under the fence; `@OpenUrl` shows its URL there ([bundles/features/openui/src/client/actions.ts](../../bundles/features/openui/src/client/actions.ts)).
- The fence sends the text through `chat.send/v1` 1.1.0 `sendAction` with the program's identity. While a click is sent the fence is inert for at least 500 ms, and a failed send shows "Not sent: …" under it. A click is refused, and the line under the fence says why, in a subagent's Thread, on a fence still streaming or cut off, and on an older revision ([bundles/features/openui/src/client/chunks/renderer.ts](../../bundles/features/openui/src/client/chunks/renderer.ts)).
- `sendAction` wraps the text in `<ui-action program="…">` and sends it by the composer's route: a steer of the running prompt, else a new prompt, resuming a paused, empty queue first. It answers `refused` for a missing Thread, one of another Project or an agent's, and never touches the composer's draft ([bundles/desktop/chat/src/client/services/send.ts](../../bundles/desktop/chat/src/client/services/send.ts), [bundles/desktop/chat/src/client/domain/send-route.ts](../../bundles/desktop/chat/src/client/domain/send-route.ts), [bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).
- The transcript shows such a prompt as the reader's message with the caption "Sent from the UI · <program>" ([bundles/desktop/chat/src/client/components/organisms/conversation/nodes/user-turn-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/user-turn-node.tsx), [bundles/desktop/chat/src/client/styles.css](../../bundles/desktop/chat/src/client/styles.css)).

### The question form

- A fence whose first completed line that is not blank matches `^root\s*=\s*AskForm\(` is a question fence (`isQuestionLine`, [bundles/runtime/runtime/src/contracts/fences.ts](../../bundles/runtime/runtime/src/contracts/fences.ts)). Its questions follow `askInputSchema`: an optional context and one to five questions, each with two to six options whose description is optional ([bundles/features/openui/src/contracts/questions.ts](../../bundles/features/openui/src/contracts/questions.ts); the full shape and limits are in the README's [`openui.questions/v1`](../../bundles/features/openui/README.md#openuiquestionsv1-100--the-question-service)).
- A Thread whose result text holds a question form counts as waiting for input, and the runtime does not archive it on its own (`hasQuestionForm`, [bundles/runtime/runtime/src/contracts/fences.ts](../../bundles/runtime/runtime/src/contracts/fences.ts); [bundles/runtime/runtime/src/host/domain/archiver.ts](../../bundles/runtime/runtime/src/host/domain/archiver.ts); see [thread-archive.md](thread-archive.md)).
- The form draws, in order of precedence: a notice when `AskForm` is not the root of its fence; "Not asked: only the main thread can ask the reader." in a subagent's Thread; the questions disabled with "Writing the question…" while the fence streams; "Not asked: the question was cut off" when it is unterminated; the schema's issue when the questions are invalid; else the answers when answered, "Replaced by a later question" when a later closed question fence of the Thread is valid, or the form to answer. A failed `status` read draws the form as pending ([bundles/features/openui/src/client/question/ask-form.tsx](../../bundles/features/openui/src/client/question/ask-form.tsx)); a failed `answer` shows "Could not send. Try again." under the form ([bundles/features/openui/src/client/question/ask.tsx](../../bundles/features/openui/src/client/question/ask.tsx)).
- `openui.questions/v1` 1.0.0 (host, exposed to the desktop with the scope `projectId`, `threadId`) keys a question by its `promptId` and the SHA-256 of its parsed questions, and reads the Thread's log again on every call ([bundles/features/openui/src/host/questions.ts](../../bundles/features/openui/src/host/questions.ts)):
  - `status` answers `answered` with the answers of the first matching `openui.answered/v1` row, else `pending`;
  - `answer` first reads the question's state, then checks the answers against the questions (`invalid_input` otherwise, whatever the Thread), then sends them formatted under "Answers to your questions:" as the reader's next message by the composer's route, then appends `openui.answered/v1` (`questionPromptId`, `digest`, `answers`) under the prompt that took them. An already answered question is returned unchanged, without sending. The answers are sent before the row is appended: when the append fails, the call rejects, the answers have reached the Thread and the question stays pending, so a second answer is sent again. For valid answers, a Thread that is an agent's, unknown or of another Project, or a route not taken, is `unavailable` ("The Thread did not take the answers.") with nothing sent. Calls for one question run one at a time.
- The window's open forms read their status again on each live `openui.answered/v1` row for their question and on each `history.truncated` row of their Thread, through `chat.hooks/v2` `onThreadUpdateHook`, which the bundle uses only when it is available; without it an open form reads its status only when it mounts or its question changes. A rewind that removes the answered row makes the question pending again ([bundles/features/openui/src/client/answer-changes.ts](../../bundles/features/openui/src/client/answer-changes.ts)). A projector claims `openui.answered/v1` rows so they draw no block ([bundles/features/openui/src/client/answers-projector.ts](../../bundles/features/openui/src/client/answers-projector.ts)).

### Errors

- Each drawn revision has one reporter. At the first `onError` of the renderer once the fence is `closed` or `unterminated`, it sends one report through `openui.programs/v1` 1.0.0 `reportErrors` (host, exposed to the desktop with the scope `projectId`, `threadId`): a merge failure, then the conversation's own check, then OpenUI's errors without warnings, at most 50, each message cut to 300 characters. A closed fence with no error sends nothing; an unterminated one always sends ([bundles/features/openui/src/contracts/report.ts](../../bundles/features/openui/src/contracts/report.ts), [bundles/features/openui/src/contracts/programs.ts](../../bundles/features/openui/src/contracts/programs.ts)).
- The conversation's own check reports `Query` and `Mutation` statements, `@OpenUrl`, an `AskForm` off the root of a fence that is not a question, a question in a subagent's Thread, an invalid closed question and the diagram findings; an `unknown-component` message gains the hint that repository components and `Export` exist only in papercraft fences ([bundles/features/openui/src/client/check.ts](../../bundles/features/openui/src/client/check.ts)).
- The card under a fence that is not streaming lists, in order, a merge failure, the program half of the check (`programCheck`: everything above except the two question lines, which the form shows), then the renderer's errors without warnings, with the renderer's own message (no hint) and with codes outside the reported set kept. Of two lines with the same code and statement the first is kept, then the first 50; each message is cut to 300 characters. Each line shows its statement name before its message and no code ([bundles/features/openui/src/contracts/report.ts](../../bundles/features/openui/src/contracts/report.ts), `shownErrors`; [bundles/features/openui/src/client/chunks/renderer.ts](../../bundles/features/openui/src/client/chunks/renderer.ts)). Its footer says "Sent to the agent." once the reporter has sent ([bundles/features/openui/src/client/chunks/errors-card.ts](../../bundles/features/openui/src/client/chunks/errors-card.ts)).
- The host keeps the reports per Thread, for both tags, from the Thread's first prompt start it sees: a report for a Thread with no prompt started since the host started, or whose prompt is neither the Thread's current nor its previous started prompt, is dropped. Each error (by tag, key, code and statement) is listed at most once ([bundles/features/openui/src/host/validation.ts](../../bundles/features/openui/src/host/validation.ts)):
  - errors of a closed fence go out 200 ms after the report, gathered into one `validation` instruct through `runtime.threads/v1` `instruct` on the Thread's latest prompt: a steer while it runs, a queued new prompt once it has finished;
  - at most 3 such immediate instructs go out per prompt that a validation instruct did not start; errors past that budget, errors that arrive while a validation prompt is queued, errors of an unterminated fence and errors of a failed instruct wait for the Thread's next prompt start (`runtime.hooks/v1` `onPromptStartedHook`), which gives them all in one instruct;
  - an instruct opens with a fixed text that explains the line format and how to fix a program, then lists at most 50 lines, each `<tag> <identity> r<revision> <statement>: <code> <text>`, and counts the ones left out. A line without a statement shows `-`, an error without a message shows its code's fixed text, and an unterminated fence adds the line `<tag> <identity> r<revision>: cut off before the fence closed`;
  - the host keeps entries for at most 1,000 Threads; past that it removes the Thread whose prompt started longest ago.

### The skill

- The host registers the skill `openui` at activation, at order 3400, listed in the skills index and loaded on demand ([bundles/features/openui/src/host/service.ts](../../bundles/features/openui/src/host/service.ts), [bundles/features/openui/src/host/skill.ts](../../bundles/features/openui/src/host/skill.ts)); the process reads it through `context.assets` from the `host.assets` the build stages (`dist/host/skills/openui.md`). It holds the language, the built-in components with the question built-ins and the diagram components, how to read a `<ui-action>`, and the rules of the decisions above; it also tells the agent to close every fence before calling a tool, to write no `Query`, `Mutation` or `@Run`, and to keep repository components and `Export` out of `openui-lang` fences ([bundles/features/openui/src/host/skills/openui.md](../../bundles/features/openui/src/host/skills/openui.md)).
- Its body is generated with OpenUI's prompt builder over the library and Doric's own rules, which the test holds (`doricRules`, `diagramRules`), and compared with the committed file by that test, which rewrites the file when run with `OPENUI_SKILL_UPDATE=1`; changing a rule means editing the test and regenerating the file ([bundles/features/openui/tests/client/skill-text.test.ts](../../bundles/features/openui/tests/client/skill-text.test.ts); see the README's [Development](../../bundles/features/openui/README.md#development)).
