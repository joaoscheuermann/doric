# Feature: Comments

- Status: `implemented`

## Problem

A note such as "make this bigger" forces the agent to guess what the reader means. The reader needs to point at the exact thing (an element of a live preview, a passage of the agent's answer) and leave a note there that the agent reads as an instruction. The agent needs to answer each note where it was left, say what it changed or ask what is unclear, and mark it attended. Every window, a restarted host and a replayed Thread must show the same comments and the same state, and a note the reader is still writing must not reach the agent before the reader sends it.

## Decisions

- A comment always has an anchor. Without an anchor it is not a comment but a message, and the message is the prompt.
- A comment is durable and can be rebuilt: it becomes an event of the Thread log, and a replay rebuilds it like any other node.
- A comment opens a thread. The agent answers the comment, saying what it changed or asking what it did not understand, and the thread ends resolved. The answer is another comment linked to the first, not a loose message.
- A comment never authorizes. It guides: the decision to act is the agent's, the agent does not wait for a comment before acting, and a comment that arrives after the work counts as a request for an adjustment, not as a veto. There is no approval state.
- The registry never interprets a target: it stores it, validates its schema and forwards it. The bundle that owns a target's `kind` decides what its `id`, `revision` and anchor mean.
- A comment has one gesture, the send, and two records: the durable event and the prompt that wakes the agent. A comment that is never sent never becomes an event: while it is a draft, it is not in the log.
- The owner of a comment kind is the owner of its target: it draws the target, resolves the anchor and registers the flush that turns its drafts into events. The stack's line is the chat's for every kind, and its note is edited in the line itself, with no popover or buttons.
- The prompt's text and the stack of comments are one state, held in the desktop's main process by a service of the chat's desktop part (`chat.composer/v1`), shared by every window.
- Reading a stored prompt back follows one rule: every place of the chat that shows a stored prompt as the reader's words reads the body of `<message>`.
- "Attended" is a state of the thread, that is of its root comment. It is set by `comments/v1.resolve`, by the reader from a pin's thread popover or by the agent with `resolve` on `comment_reply`, and drawn as `done`; reopening is another `resolve` with `resolved: false`.
- Pressing the pin of an agent's reply in the conversation does not jump to the target: it opens a popover with the thread, and the popover's header holds the button that goes to the comment on the target.
- A comment on a papercraft program targets `{ kind: 'papercraft-program', id: <the program's identity>, revision }` and anchors with the `selector` form, the statement's name as `selector` and its component as `label`; where no statement wraps the click, it anchors with the `point` form.

## Current behavior and contracts

Three bundles carry the feature. [`comments`](../../bundles/features/comments/README.md) is the registry: `comments/v1`, the events `comments.added/v1` and `comments.resolved/v1`, and the tool `comment_reply`; it has no UI. [`chat`](../../bundles/desktop/chat/README.md) holds the drafts on its composer's stack, builds the prompt that carries them, owns the comment kind `message` (a comment on a passage of the agent's answer) and draws every comment in the conversation. [`papercraft`](../../bundles/features/papercraft/README.md) owns the kind `papercraft-program`, a comment on an element of a live preview; its canvas is described in [papercraft.md](papercraft.md). Each README holds the full shape of its contracts; the composer, the send and the prompt envelope as the conversation uses them are in [conversation.md](conversation.md).

### The flow

1. The reader opens a comment on a target. The target's owner puts a draft item on the Thread's stack of `chat.composer/v1`, under the comment's id `comment-<uuid>` ([bundles/desktop/chat/src/shared/composer-state.ts](../../bundles/desktop/chat/src/shared/composer-state.ts)).
2. The reader sends. The chat builds one prompt: the drafts in `<comments>`, the reader's words in `<message>` ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).
3. Once the host accepts the prompt, the stack flushes: each draft's owner answers the write its draft becomes, and the sending window writes it through `comments/v1.add` in the accepted prompt's scope ([bundles/desktop/chat/src/client/api/composer.ts](../../bundles/desktop/chat/src/client/api/composer.ts)).
4. The agent reads the comments and answers each with `comment_reply`, which writes a reply comment and may resolve the root ([bundles/features/comments/src/host/tools/comment-reply.ts](../../bundles/features/comments/src/host/tools/comment-reply.ts)).
5. The chat folds the log's comment events into threads, each `open`, `await` or `done`, and draws them in the conversation; the target's owner draws them on the target ([bundles/desktop/chat/src/client/domain/comment-threads.ts](../../bundles/desktop/chat/src/client/domain/comment-threads.ts)).

### The registry: `comments/v1`

`comments/v1` 1.0.0 is a host service of cardinality `one`, provided by the `comments` bundle (manifest 1.0.0), which requires `events/v1`, `runtime.threads/v1` (`^1.2.0`) and `tools/v1` ([bundles/features/comments/manifest.json](../../bundles/features/comments/manifest.json), [bundles/features/comments/src/contracts/index.ts](../../bundles/features/comments/src/contracts/index.ts), [bundles/features/comments/src/host/index.ts](../../bundles/features/comments/src/host/index.ts)).

- A comment is `{ commentId, target, text, author?, resolved, createdAt, inReplyTo? }`; a target is `{ kind, id, revision?, anchor }` ([bundles/features/comments/src/contracts/index.ts](../../bundles/features/comments/src/contracts/index.ts)).
- An anchor has one of four forms, each requiring its own field: `source` a `path` (with an optional positive whole `line`), `selector` a `selector`, `point` both `x` and `y`, `range` the selected `text`. Every form may carry any of the other fields as optional: `path`, `line`, `selector`, `x`, `y`, `text`, `label`, `pseudo` (`::before` or `::after`), and the seat fields `turn`, `block`, `at` and `item`. The target and anchor schemas are loose objects: the registry keeps any key a caller adds ([bundles/features/comments/src/contracts/index.ts](../../bundles/features/comments/src/contracts/index.ts)).
- The registry holds no state. The Thread log is the only record: `add` and `resolve` append the two events to the call's Thread, and `list` and `resolve` fold them back out of the log through `runtime.threads/v1.threadEvents` (and `projectThreads` for a Project-wide read), so a restarted host, a replay or a rewind answers what the log holds. A log row that breaks the event's schema is skipped, and of two `comments.added/v1` rows with the same `commentId` the first one counts ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).
- `add(input)` writes `comments.added/v1` and answers the comment. It needs a scope with `projectId`, `threadId` and `promptId` (else `invalid_scope`). The text is trimmed and must not be empty. A caller may choose `commentId` (`/^[A-Za-z0-9_-]{1,128}$/`); a `commentId` the Thread already holds answers that comment and appends nothing, and without one the registry generates `comment-<uuid>`. `inReplyTo` must name a comment of the same Thread (else `invalid_input`) and is normalized to that comment's root, so threads are flat ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).
- An anchor may name a seat: `turn` (a non-empty string) and `block` (a non-negative whole number) only together, and `at` and `item` (non-negative whole numbers) only with them. `add` refuses a half or malformed seat with `invalid_input`; it does not interpret the seat ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).
- `list({ target?, kind? })` needs `projectId`. It reads the call's Thread when the scope names one, else every Thread of the Project, and answers the comments in log order, filtered by `kind` and by the target's `kind`, `id` and `revision`, never by its anchor ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).
- `resolve({ commentId, resolved })` needs the same scope as `add` and sees only the call's own Thread: a comment that Thread does not hold answers `undefined` and writes nothing. It writes `comments.resolved/v1` only when the state changes, and `resolved: false` reopens ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).
- The three methods are exposed to the desktop, with `desktopScope` `projectId`, `threadId` and `promptId` ([bundles/features/comments/manifest.json](../../bundles/features/comments/manifest.json), [bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).

| Event                  | Payload                                                        |
| ---------------------- | -------------------------------------------------------------- |
| `comments.added/v1`    | `{ commentId, target, text, author?, createdAt?, inReplyTo? }` |
| `comments.resolved/v1` | `{ commentId, resolved }`                                      |

The bundle registers both events with `events/v1` on activation ([bundles/features/comments/src/host/index.ts](../../bundles/features/comments/src/host/index.ts)). A folded comment's `createdAt` is the payload's, else the log entry's time ([bundles/features/comments/src/host/comments.ts](../../bundles/features/comments/src/host/comments.ts)).

### How comments reach the agent

- Every send of the composer (the editor's, the send command's and `chat.send/v1.send`) carries one text: `<comments>` with the stack's items whose note is not blank, grouped by target (`kind`, `id`, `revision`) in order of first appearance, then the reader's trimmed words in `<message>`. Either part is left out when empty, and an empty text sends nothing. A click on a control of a UI the agent drew sends `<ui-action>` instead, with no comments ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).

  ```text
  <comments>
  <target kind="papercraft-program" id="checkout" revision="2" title="checkout">
  <comment id="comment-…" pin="1" anchor="header" element="CardHeader">more room</comment>
  <comment id="comment-…" in-reply-to="comment-…" pin="1" anchor="header" element="CardHeader">and the button</comment>
  </target>
  </comments>
  <message>
  the reader's words
  </message>
  ```

- A `<target>` takes `title` and `source` from the first item's `refs`; an item that names no target stands outside any `<target>`. A `<comment>` carries `id`, `in-reply-to` for a reply, `pin`, and attributes by anchor form: `source` gives `anchor="path:line"` and `element`, `selector` gives the selector and `element`, `point` gives `anchor="point x,y"` and `near` (the nearest element), and `range` gives `anchor="range"` and `quote`, the selected text cut to 200 characters. The note is the body ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).
- Attribute values are escaped, and in a body every closing tag of an envelope element is neutralized (`<\/message>`), so the reader's text never closes the structure; reading back restores it ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).
- Every surface of the chat that shows a stored prompt reads back the body of `<message>`; a prompt that is not exactly an envelope is shown as written. Editing a queued prompt keeps its `<comments>` as sent and replaces only `<message>` (`withPromptMessage`) ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).
- The [`default`](../../bundles/runtime/default/README.md) executor wraps the whole prompt in `<user-request>`. Its system prompt explains `<comments>` and tells the agent to answer every comment with `comment_reply` and to set `resolve` once it is done ([bundles/runtime/default/src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts), [bundles/runtime/default/src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)).
- A papercraft program's comments arrive under a target of kind `papercraft-program` whose id is the program's identity, with `title` the identity; the papercraft skill tells the agent to answer each with `comment_reply` and resolve it when done ([bundles/features/papercraft/src/client/surface/preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx), [bundles/features/papercraft/src/host/skills/papercraft.md](../../bundles/features/papercraft/src/host/skills/papercraft.md)).

### The `comment_reply` tool

- The `comments` bundle registers `comment_reply` as always available, at the model-visible order 1800, with no skill ([bundles/features/comments/src/host/index.ts](../../bundles/features/comments/src/host/index.ts), [bundles/features/comments/src/host/tools/comment-reply.ts](../../bundles/features/comments/src/host/tools/comment-reply.ts)).
- Input `{ comment_id, text, resolve? }`; output `{ commentId, inReplyTo, resolved }`: the reply's id, the root it answers and whether the root is resolved now ([bundles/features/comments/src/host/tools/comment-reply.ts](../../bundles/features/comments/src/host/tools/comment-reply.ts)).
- The tool looks `comment_id` up in the calling prompt's Thread; an unknown id is `invalid_input`. It writes the answer through `add` with `author: "agent"`, the root's target and `inReplyTo` the root, even when `comment_id` names a reply. With `resolve: true` it also resolves the root ([bundles/features/comments/src/host/tools/comment-reply.ts](../../bundles/features/comments/src/host/tools/comment-reply.ts)).

### Drafts on the composer's stack

- A draft is an item of `chat.composer/v1`'s stack: `{ id, kind, elementTag, data, author?, note }`. The id is `comment-<uuid>` and becomes the comment's id; `addItem` keeps an `id` with that prefix the stack does not hold. By convention `data` is `{ target, pin?, inReplyTo?, refs?: { title?, source? } }`, and the chat's `message` kind adds `seat` ([bundles/desktop/chat/src/contracts/index.ts](../../bundles/desktop/chat/src/contracts/index.ts), [bundles/desktop/chat/src/shared/composer-state.ts](../../bundles/desktop/chat/src/shared/composer-state.ts), [bundles/desktop/chat/src/client/domain/composer-stack.ts](../../bundles/desktop/chat/src/client/domain/composer-stack.ts)).
- Each kind's owner registers the flush of its kind from its desktop part (`registerFlush`); a second flush for a kind is a `registration_conflict`. The chat registers the `message` flush; the `papercraft` bundle registers the `papercraft-program` flush. Each answers one write `{ target, text: <the trimmed note>, commentId: <the item's id>, inReplyTo?, author? }` for an item with a non-blank note and a target, and none otherwise. The `message` flush takes any target with a string `kind` and `id` and an object `anchor`; the `papercraft-program` flush takes only a target of kind `papercraft-program` with a non-empty `id` ([bundles/desktop/chat/src/desktop/index.ts](../../bundles/desktop/chat/src/desktop/index.ts), [bundles/desktop/chat/src/shared/message-flush.ts](../../bundles/desktop/chat/src/shared/message-flush.ts), [bundles/features/papercraft/src/desktop/index.ts](../../bundles/features/papercraft/src/desktop/index.ts), [bundles/features/papercraft/src/desktop/comment-flush.ts](../../bundles/features/papercraft/src/desktop/comment-flush.ts)).
- The flush runs only after the host accepts the prompt; a refused send flushes nothing. It walks the stack in order, so a root is written before its replies, and a reply whose root stays on the stack stays with it. An item leaves the stack only when its flush answers a write. One flush runs per Thread at a time; a second waits and runs after it, in call order. Each flush removes only the ids it flushed, from the stack as it stands when the flush ends, and announces `removed` only for those still there; an item added or removed meanwhile keeps that change, and a flush that rejects changes nothing ([bundles/desktop/chat/src/shared/composer-state.ts](../../bundles/desktop/chat/src/shared/composer-state.ts)).
- The sending window performs the writes through `comments/v1.add` in the scope of the accepted prompt, so the events land in that prompt's log. A write that fails is logged and its item goes back on the stack under the same id; the write is idempotent on that id ([bundles/desktop/chat/src/client/api/composer.ts](../../bundles/desktop/chat/src/client/api/composer.ts)).
- Before a send reads the stack, the window dispatches `doric:prompt-send` on the document with `{ threadId, waitUntil }`. A surface holding an unconfirmed note confirms it, and a note whose item is still being added hands that add to `waitUntil`; the send waits for every promise and reads the stack back ([bundles/desktop/chat/src/client/services/send-command.ts](../../bundles/desktop/chat/src/client/services/send-command.ts), [bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx)).
- A window hands a note's edits to `chat.composer/v1` 150 ms after the last one. An edit still waiting goes at once when the note loses the focus, when a send reads the stack and when the window stops showing the Thread; removing the comment drops it. An echo of an older write never overwrites a note written after it ([bundles/desktop/chat/src/client/stores/composer-stack.ts](../../bundles/desktop/chat/src/client/stores/composer-stack.ts), [bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx](../../bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx)).

### Comments on the agent's answers: the `message` kind

- Selecting words of an agent's answer draws nothing new. Typing over a selection whose two ends lie in the same answer opens a new comment holding what was typed, and the answer's text is never edited: the first printable key without Cmd, Ctrl or Alt, a paste, or a text input. Navigation keys, Escape, Tab and chords keep their meaning, and a selection that runs into the prompt or over several turns is the prompt's ([bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx)).
- An input method's composition is moved, not prevented: the key that starts it (`Dead`, `Process`, or key code 229) opens the comment and puts the caret in its note first. A composition no key announced is kept from the answer; its committed text opens the comment, and the answer's block is drawn again from the chat's Markdown ([bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx)).
- The comment stands right after the innermost block that holds the end of the selected words, or, when that block is a list, at the end of the list item that holds it. From its first character to the send it is one element: the reader's avatar and the note, written in place inside a frame of the theme's primary colour, with no author name, quote or buttons ([bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx)).
- The note's first words add its stack item under the comment's id, chosen when it opens, with the target `{ kind: 'message', id: <the answer's promptId>, anchor: { form: 'range', text, turn, block, at, item? } }`: the answer's turn key, the 0-based block the words start in, `at` (how far into that block they start, counted in characters that are not whitespace, which picks the selected occurrence of repeated words) and `item` (the list item they start in). The item's data carries the `seat`: `turn`, `block`, `at`, and `after` and `item` for where the comment stands ([bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-selection.tsx)).
- Enter commits a note that holds words and hands the caret to the prompt; Shift+Enter writes a newline. Escape, and Backspace or Delete on an empty note (whitespace alone is empty), remove the item, the highlight and the seat. Leaving the note keeps a comment with words and removes an empty one. These are the only gestures that take a comment off the stack: a stack the window stops holding, because the view unmounts or the part deactivates, removes nothing ([bundles/desktop/chat/src/client/domain/comment-entry.ts](../../bundles/desktop/chat/src/client/domain/comment-entry.ts), [bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx)).
- Once the flush takes its item, the comment is sent and stays where it was written, its passage highlighted and its note read-only. Every root comment the reader sent on a `message` target whose anchor names its `turn` and `block`, from the log or still on its way, is seated so, in a remounted conversation too, after the block or at the end of the list item that holds the end of its words ([bundles/desktop/chat/src/client/domain/comment-seats.ts](../../bundles/desktop/chat/src/client/domain/comment-seats.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-seats.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-seats.tsx)).
- Each comment is a seat, a decorator inside the agent turn or its list item named by the comment's id, so a block or item holds any number of comments, in the order of their passages (`at`). A turn rebuilt from a streamed delta builds again only the tail the new text outgrew, so a comment being written in an earlier block is not moved. A redraw that does move a focused note gives it back its focus and caret: while the note holds the focus its caret is recorded, and when an update of the editor leaves the focus nowhere, the note takes it back with the caret where it stood, else at its end. Leaving the note is read one tick after the blur, so focus lost to such a redraw does not count as leaving ([bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-seat-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-seat-node.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/agent-turn-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/agent-turn-node.tsx), [bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx)).
- The seats are a view of the stack: every item whose data names a `seat` stands at it while its turn is in the transcript, beside the comments the reader opened and still holds and the comments sent. A remounted conversation or an undo gets its comments back, an undo never revives a removed one, and the seats' own edits stay out of the undo history ([bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-seats.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-seats.tsx), [bundles/desktop/chat/src/client/domain/comment-seats.ts](../../bundles/desktop/chat/src/client/domain/comment-seats.ts)).
- Every comment's words stay highlighted while it stands, through the CSS Custom Highlight API (`::highlight(chat-comment)`), with one range per text run, so a quote over several blocks or in a list item never paints a comment. A seat's ranges are found again only when the seat changed, its turn was redrawn or its text left the document; the answer's text is never touched ([bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-highlights.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-highlights.tsx), [bundles/desktop/chat/src/client/domain/comment-highlight.ts](../../bundles/desktop/chat/src/client/domain/comment-highlight.ts)).
- The passage under the pointer, found once per animation frame, wears `::highlight(chat-comment-hover)`, and the element under the pointer (never the editor's root) gets `data-comment-hover`, the pointer cursor. The passage of the comment whose note holds the focus wears the same highlight, without the cursor. A click strictly inside a highlight, outside any comment, puts the caret at the end of its comment, the newest one where passages overlap; a sent comment's passage answers neither the click nor the pointer ([bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-highlights.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/comment-highlights.tsx)).

### Comments in the conversation

- The stack is drawn inside the prompt's block, above the reader's words, as a comment group: the block's mark moves beside an `N comment`/`N comments` header with a chevron, the group's only control, which a press, Enter or Space folds and unfolds. An empty stack draws nothing ([bundles/desktop/chat/src/client/components/organisms/comment-group.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-group.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/composer-stack-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/composer-stack-node.tsx)).
- The stack lists every item that is not being sent, seated or not; an edit made on a card shows in the inline comment, and the other way round ([bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx](../../bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx), [bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx](../../bundles/desktop/chat/src/client/components/organisms/comment-entry.tsx)).
- Each comment is the chat's `chat-comment-line` card for every target kind, with no popover. A context line comes first: the anchor's quote read in the paragraph the transcript draws for the anchor's `turn` and `block`, on one line truncated with an ellipsis and the quoted words highlighted (among repeated words, the occurrence nearest the seat's or the anchor's `at`, else the first); the quote alone when that paragraph is not drawn; else the anchor's label. Nested in it is the comment: avatar, `↩` for a reply, and the note, framed in the theme's primary colour (1px, 3px on the left, square). An item whose `elementTag` another bundle defines draws that element in the group instead ([bundles/desktop/chat/src/client/components/molecules/comment-line.tsx](../../bundles/desktop/chat/src/client/components/molecules/comment-line.tsx), [bundles/desktop/chat/src/client/domain/comment-excerpt.ts](../../bundles/desktop/chat/src/client/domain/comment-excerpt.ts), [bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx](../../bundles/desktop/chat/src/client/components/organisms/composer-stack.tsx)).
- While a card is hovered or holds the keyboard's focus, a small arrow ("Go to the commented passage") closes its context line. It puts the caret in a `message` comment's inline note while that note stands in the answer; else it scrolls to the answer's paragraph the anchor names and flashes it; for any other target, or a paragraph the transcript does not draw, it opens the comment's thread on its target (below). A press on a sent card does the same ([bundles/desktop/chat/src/client/hooks/use-go-to-comment.ts](../../bundles/desktop/chat/src/client/hooks/use-go-to-comment.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx)).
- Keys in the stack: the arrows walk between the header, the notes and the prompt by visual line (ArrowUp on the prompt's first line goes to the last note, or to the header of a folded stack); Enter goes to the next note, or from the last to the prompt's end; Escape goes to the prompt's end; Cmd/Ctrl+Backspace removes the comment, as do Backspace and Delete on an empty note; Cmd/Ctrl+Enter sends ([bundles/desktop/chat/src/client/domain/composer-stack.ts](../../bundles/desktop/chat/src/client/domain/composer-stack.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/plugins/stack-caret.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/stack-caret.tsx)).
- Every comment group, the stack's and a sent turn's, and every inline comment is isolated from the conversation's Lexical editor: each event that starts there is marked handled for the editor, so its keys never write into the prompt ([bundles/desktop/chat/src/client/utility/isolate.ts](../../bundles/desktop/chat/src/client/utility/isolate.ts)).
- A user turn opens with its comments, the `comments.added/v1` of its prompt, drawn as the same group and cards; nothing on them is editable ([bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx)).
- A send draws its comments from its first moment: the pending turn wears the stack items its envelope names, in stack order, and after acceptance the turn wears each one until the log holds it; a comment whose write fails returns to the stack and leaves the turn. Meanwhile the stack leaves out the comments being sent, so no comment is drawn twice ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts), [bundles/desktop/chat/src/client/stores/thread-chats.ts](../../bundles/desktop/chat/src/client/stores/thread-chats.ts), [bundles/desktop/chat/src/client/domain/pending-turns.ts](../../bundles/desktop/chat/src/client/domain/pending-turns.ts), [bundles/desktop/chat/src/client/hooks/use-sending-comments.ts](../../bundles/desktop/chat/src/client/hooks/use-sending-comments.ts)).
- A card draws no thread state; the state (`resolved`, `waiting on you` or `open`) and the number of the agent's replies are read out to screen readers only, from visually hidden text ([bundles/desktop/chat/src/client/components/molecules/comment-marker.tsx](../../bundles/desktop/chat/src/client/components/molecules/comment-marker.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/comment-lines-node.tsx)).

### Threads, states and the agent's replies

- The chat's built-in projection folds `comments.added/v1` and `comments.resolved/v1` into threads: the root, then its replies in log order, and whether the root is resolved. A thread is `done` when its root is resolved, `await` when the agent wrote its last message, and `open` otherwise ([bundles/desktop/chat/src/client/domain/comment-threads.ts](../../bundles/desktop/chat/src/client/domain/comment-threads.ts), [bundles/desktop/chat/src/client/domain/projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts)).
- A `comment_reply` call that did not fail draws no tool row; a failed one keeps its row. The agent's answers are drawn where they happened in its turn, grouped in a block of collapsible rows: `Replied to:` with the note it answers, and the agent's words as Markdown. A row is folded while its thread is `done` and open otherwise, until the reader opens or closes it ([bundles/desktop/chat/src/client/domain/projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/nodes/replies-turn-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/replies-turn-node.tsx), [bundles/desktop/chat/src/client/domain/collapsible.ts](../../bundles/desktop/chat/src/client/domain/collapsible.ts)).
- A reply row ends with the comment's pin: the teardrop of `desktop/ui/comment-pin`, numbered by the comment's position among its prompt's comments (1 for the first) and coloured by the thread's state, with a 2px `outline-ring` outline under keyboard focus. Pressing it opens a popover with the thread's messages (avatar, author and text) and, in its header, the anchor's label and a button, "Show comment in the preview", that opens the thread on its target ([bundles/desktop/chat/src/client/components/molecules/comment-thread-pin.tsx](../../bundles/desktop/chat/src/client/components/molecules/comment-thread-pin.tsx), [packages/desktop/src/comment-pin.tsx](../../packages/desktop/src/comment-pin.tsx), [bundles/desktop/chat/src/client/domain/projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts)). The `pin` attribute of the envelope is the item's own `data.pin` ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts)).

### Opening a thread on its target

- That button, and a card's "go to" that opens a thread, scroll to and flash the conversation's latest block that draws the target, then dispatch the DOM event `doric:comment-thread-open`, bubbling and composed, with `detail: { commentId, target }`: the root's id and its target without `revision`, so the latest drawing of the target answers ([bundles/desktop/chat/src/client/utility/comment-thread.ts](../../bundles/desktop/chat/src/client/utility/comment-thread.ts)).
- Blocks another bundle draws in the conversation carry `data-chat-block-id`, which is how the latest block of a target is found ([bundles/desktop/chat/src/client/components/organisms/conversation/nodes/chat-block-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/chat-block-node.tsx), [bundles/desktop/chat/src/client/utility/comment-thread.ts](../../bundles/desktop/chat/src/client/utility/comment-thread.ts)).
- The bundle that draws the target listens for the event and opens the thread there; how a papercraft canvas answers is in [papercraft.md](papercraft.md) ([bundles/features/papercraft/src/client/surface/preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx)).

### Papercraft targets

- A comment on a papercraft program is drafted with the item kind and target kind `papercraft-program`, the target `{ kind: 'papercraft-program', id: <identity>, revision, anchor }` and `refs: { title: <identity> }`. A click on an element wrapped by a statement anchors with `selector` (the statement's name), `label` (its component, else its tag) and the click's `x` and `y`; otherwise the anchor is `{ form: 'point', x, y }`, with no label, so the envelope gives it no `near` attribute ([bundles/features/papercraft/src/client/anchor.ts](../../bundles/features/papercraft/src/client/anchor.ts), [bundles/features/papercraft/src/client/surface/gestures.ts](../../bundles/features/papercraft/src/client/surface/gestures.ts), [bundles/features/papercraft/src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts), [bundles/features/papercraft/src/client/surface/preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx)).
- The canvas window, which has no prompt, sends the stack through `chat.send/v1` ([bundles/features/papercraft/src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts)).
- Resolving or reopening a thread from the canvas's thread popover calls `comments/v1.resolve` on the root, in the scope of the prompt the root was written under ([bundles/features/papercraft/src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts)).
