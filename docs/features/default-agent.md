# Feature: Default agent

- Status: `implemented`

## Problem

Every Doric conversation needs an agent loop: something that turns one prompt of a Thread into model requests and tool calls. The model must be told where it works, what it can do and who it works for, it must run on the provider and model the Thread chose, and what it does must be kept as a history the Thread can resume, rewind and compact. Other bundles need a way to adjust the system prompt at each turn, and a workspace needs a way to define the agents a Thread can be spawned as, in files, without a change to Doric.

## Decisions

- Every text the model receives whole is one Markdown file under `src/host/prompts`, rendered with `mustache`; tool descriptions stay in each tool's `defineTool`. Templates are used rather than TypeScript template literals because the texts need named variables and workspace templates read at run time.
- The code supplies only data: which skills and rows fit, each cell already on one line, capped and pipe-escaped, the locators, the dropped counts, the fences, the cut flags and the omitted ids. The templates do all the formatting, with mustache sections whose tags each stand alone on their line. A budget is measured by rendering the section it fills (`renderSection`), so a row's format exists only in its template.
- Each module reads the templates it uses once, when it loads, not at activation, because their consumers are synchronous and are called without activation in tests. A missing template fails the import, and the bundle is quarantined with `invalid_part`.
- A template may cite only the names declared for it, at any section depth; partials are refused. Rendering does no HTML escaping, through a per-call option that leaves mustache's global `escape` unchanged.
- The build copies the `.md` files of `src/host` into `dist/host`, and the bundle's test target copies them next to the compiled tests. `.prettierignore` leaves `bundles/*/*/src/host/**/*.md` alone, so the bytes the model reads stay as written.
- `system.md` ends with an `# Environment` section rendered from the prompt variables; the lines of `os` and of the user's name sit in mustache sections, so an absent value leaves no blank line.
- `date` is the calendar day only (`YYYY-MM-DD`), never the time of day: providers cache the system prompt, and the day changes it at most once a day.
- The prompt variables are read once at the start of each run and do not change until it ends, so every request of a run carries the same prompt, even across midnight.
- The user's name and time zone come from the optional `profile` block of the host configuration, filled in by the user. They are never taken from the host's operating-system user or the Git identity, because the host can be remote and neither describes who uses Doric. Without a `timezone`, the host's zone applies; without a `name`, the line is left out.
- `os` is read with one exec in the sandbox through `runtime.lease/v1`, with a 5-second timeout, and cached in memory per Project and lease id. A missing provider, a failed, timed-out or empty probe leaves the line out and is not cached, so the next run tries again.
- Built-in and workspace agents share one format and one parser: the name is the file's, `description` (required), `model` and `effort` (optional, blank counts as absent) come from the frontmatter, `name:` and unknown keys are ignored, and the instructions are the text after the frontmatter. An invalid built-in file, a built-in file name outside the pattern or two built-in files of one name make activation throw before anything is provided.
- The ten built-in agents repeat the same common block word for word: each definition is a self-contained file, with no partial or include.
- An agent's instructions are always a mustache template that may cite only the prompt variables (`os`, `date`, `timezone`, `user`, `user.name`); citing another name makes the definition invalid, and the reason names the name and suggests `{{=<% %>=}}` for literal tags. `resolve` answers the raw template; the run renders it, so the date follows each run.
- The scan of `.agents/agents` is an exec of its own, run in parallel with the skills scan, so each read keeps its own failure (missing provider, non-zero exit or timeout gives an empty list) and its own record format.
- The listing reads each file's size and first 4096 bytes, and checks the template only when that head is the whole file; `resolve` reads the file whole and checks it again. A file longer than 4096 bytes whose instructions cite another name is therefore listed and then fails to resolve with `invalid_definition`. This is accepted, because reading every file whole would cost up to 64 × 64,000 bytes per run.
- A workspace file with a built-in's name replaces the built-in even when it is invalid: it is left out of `list`, and `resolve` fails with `invalid_definition` rather than answering the built-in, so what the workspace's author wrote is never silently swapped for another definition.
- The "Agents changed" message compares agents by name: an agent is added or changed when it is new or its `description` or `source` differs, and removed when its name is gone. A change of `model` or `effort` alone is not told, because the catalog does not show them. The message comes before the "Skills changed" one, and after a compaction the next comparison is made with the system prompt's agents again.
- A Thread that runs as an agent gets a `# Agent: <name>` section after `system.md` and before `# Agents` and `# Skills`, holding the agent's instructions rendered with the run's prompt variables. The default system prompt stays whole, and the agent's instructions take precedence over its general guidance on how to do the task, so the agent keeps the envelope, the tools and the environment `system.md` describes.
- Instructions that cite a name outside the prompt variables, use a partial or do not parse make the run reject before its first model request.
- A Thread that runs as an agent is not offered the `coding-workflow` skill: the agent's instructions are its workflow.
- The runner reads an agent Thread's instructions from the stored Thread on every run and every compaction and hands them to the executor as `thread.agent.instructions`; the public Thread never carries them. When none are stored, the runner drops the agent and the Thread runs as the default agent instead of failing the validation of `executor/v1`.
- A Thread whose stored provider or model is not available fails each run with the code `thread_execution_unavailable` and a message that tells the reader to choose another model in the conversation footer; a manual compaction of it fails as `summarizer_failed`.
- When a tool call fails because its generation process was lost, the run saves the history at that moment and not again when it ends, so the call stays unanswered, as a host crash leaves it, and the resumed run answers it with the interrupted-call result.
- `executor/v1` is local, and `run` receives the `PromptSession` of the [`runtime`](../../bundles/runtime/runtime/README.md) bundle, through which every history and event write goes; `checkpoint` and `rewind` are the executor's part in a rewind.
- The executor writes its streamed deltas coalesced: consecutive deltas of one kind (`reasoning.delta`, `text.delta`, `refusal.delta`), or of one tool call (`tool_call.delta` with the same `index` and `id`), become one event holding their concatenation. The event is written 250 ms after its first delta, once it holds 64 KiB of text (UTF-8 bytes), before any other event or history save, and when the run ends, aborts, throws or loses its generation process. Empty deltas are dropped without breaking the run of deltas. Every write, a window's included, goes through one queue; a window's failure, which no caller awaits, reaches the next write, so the run ends with the runtime's own persistence error. A live channel or a new storage primitive is rejected in favor of this.
- `mergeDeltas`, `isEmptyDelta` and `streamDelta` live in `runtime/contracts` as pure functions, so the executor and the tests of the [`chat`](../../bundles/desktop/chat/README.md) bundle apply the same rule: answer text that is still blank is not merged with the first words after it, reasoning is merged, and a tool-call piece is empty only with no arguments, no `id` and no `name` ([bundles/runtime/runtime/src/contracts/deltas.ts](../../bundles/runtime/runtime/src/contracts/deltas.ts), [bundles/runtime/default/src/host/deltas.ts](../../bundles/runtime/default/src/host/deltas.ts), [bundles/desktop/chat/tests/projector-coalesced.property.test.ts](../../bundles/desktop/chat/tests/projector-coalesced.property.test.ts)).

## Current behavior and contracts

### The bundle

- The [`default`](../../bundles/runtime/default/README.md) bundle, version 2.8.0, provides `executor/v1@1.5.0`, `default.hooks/v1@1.0.0` and `default.agents/v1@1.0.0`. It requires `tools/v1`, `skills/v1`, `models/v1`, `host-config/v1` (^1.1.0), `hooks/v1`, `log/v1` and `ui/v1`; `runtime.lease/v1`, `runtime.workspace/v1`, `chat.views/v1` and `default.skill-sources/v1` are optional ([manifest.json](../../bundles/runtime/default/manifest.json)).
- `executor/v1` is one of the contracts the host's composition requires, and the `runtime` bundle requires it at `^1.4.0` to run every prompt ([app/backend/doric-host/composition.json](../../app/backend/doric-host/composition.json), [bundles/runtime/runtime/manifest.json](../../bundles/runtime/runtime/manifest.json), [bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

It then provides `default.agents/v1` over them, defines `default.hooks/v1` through `hooks/v1` and provides the executor ([src/host/index.ts](../../bundles/runtime/default/src/host/index.ts), [src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- The bundle also declares `default.skill-sources/v1`, which it does not provide, and its client part draws each `load_skill` call in the conversation through `chat.views/v1`. Both belong to the skills, described in [skills.md](skills.md) ([src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts), [src/client/index.ts](../../bundles/runtime/default/src/client/index.ts)).

### The `executor/v1` contract

`executor/v1` 1.5.0 is `Executor`, defined in [bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts). The provider is [src/host/index.ts](../../bundles/runtime/default/src/host/index.ts), defined by the id `ExecutorV1.id` because the loose output schema of `run` does not match the typed overload's exact result type. Its full shape is in the default README's [`executor/v1`](../../bundles/runtime/default/README.md#executorv1-150).

| Method                                            | Behavior                                                                                                                                                                                                                                  |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `run({ thread, job, session })`                   | Runs one prompt of the Thread. `thread` is an `ExecutorThread`: the public `Thread`, whose `agent`, when present, also carries the agent's `instructions`. `job` is `{ id, prompt, source }`. Resolves with `{ text }`, the final answer. |
| `checkpoint({ history, promptId })`               | The history patch that records the prompt's turn boundary: the current message count, recorded once; a boundary the prompt already has wins.                                                                                              |
| `rewind({ history, promptId, removedPromptIds })` | The history a rewind to `promptId` leaves (see [Provider history](#provider-history)), or `undefined` when the prompt has no boundary.                                                                                                    |
| `formats()`                                       | The history formats the executor reads: `default.history/v1` and `direct.history/v1`.                                                                                                                                                     |
| `compact({ thread, session, policy })`            | Condenses an idle Thread's history on demand; answers `compacted`, `refused` or `failed`. See [context-compaction.md](context-compaction.md).                                                                                             |

`run` is called with `call.scope` naming `{ projectId, threadId, promptId }`, and `call.signal` aborts it ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)).

### One run

Each prompt run builds everything afresh ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)):

- It reads the stored `messages` and `meta`. When the prompt already has a turn boundary and the stored history is longer than it, the run resumes: the agent continues the stored history without appending the input again, so repeated resumptions keep the original order of the messages.
- When the last assistant turn holds tool calls without results, as a restart in the middle of a tool batch leaves it, the run answers each such call with the result `The host was restarted while this tool call was running, so its result was lost. Call it again if you still need it.`, marked incomplete. A call is answered rather than run again, because a tool that already ran may have changed the sandbox.
- It reads the configuration from `host-config/v1`, resolves the Thread's execution ([Model resolution](#model-resolution)), reads the prompt variables, lists the tools of `tools/v1`, and reads the skills and the workspace agents of the Thread's working directory in parallel.
- It creates a fresh agent of [`packages/agent`](../../packages/agent/README.md) with a fresh tool-call store, the run's tools, a message store initialized from the Thread's stored provider-ready history, the model and effort, and the system prompt ([packages/agent/src/lib/types/agent.ts](../../packages/agent/src/lib/types/agent.ts)).
- Before the first provider call it measures the context pressure of the stored history plus the input, and between turns it measures it again; see [context-compaction.md](context-compaction.md).
- The run streams the agent and records every event through its session. It saves the history with the events `response.finished`, `tool.finished` and `agent.steered`, and once more when the run ends, whether it completes, aborts or fails, unless its generation process was lost (see below). After each event it records, it checks the prompt's abort signal. A `response.started` event carries the run's `providerId`.
- When a tool call fails because the generation process that ran it exited and the prompt was aborted, the run saves the history as it stands and not again when the run ends, with the call left unanswered, records no failure, and rejects with the abort's reason, so the prompt pauses and its next run repairs the call.
- Inputs that arrive while the run works are taken as steers, each wrapped in the envelope of its source ([Input envelope](#input-envelope)); see [prompt-control.md](prompt-control.md). A steer from a bundle marked to be retained is recorded in `meta.retained` under `<bundleId>:<reason>` once the run stores it.
- `run` resolves with the text of the agent's final answer.
- Every history and event write goes through the runtime's `PromptSession`, which redacts, persists, publishes and keeps the retry, wrapped first by the coalescing writer ([src/host/deltas.ts](../../bundles/runtime/default/src/host/deltas.ts)): one event per run of same-kind deltas, written after 250 ms, at 64 KiB, before any other write and when the run ends; empty deltas are dropped. The merge rule is `mergeDeltas` of `runtime/contracts` ([bundles/runtime/runtime/src/contracts/deltas.ts](../../bundles/runtime/runtime/src/contracts/deltas.ts)).

### The system prompt

- The system prompt is `system.md` rendered with the run's prompt variables, followed, after a blank line, by the `# Agent: <name>` section of a Thread that runs as an agent, the `# Agents` section and the `# Skills` section, each only when it has content, separated by blank lines. It is the same for human Threads and child Threads. The text the run builds stays the same for the whole run; what each request carries is that text as `onBeforeModelRequestHook` answers it ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Before every model request, the run passes the system prompt through `default.hooks/v1.onBeforeModelRequestHook` under the prompt's call, and the model receives what the hook answers. `packages/agent` takes the system prompt as a function, which it calls before every provider request ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [packages/agent/src/lib/types/agent.ts](../../packages/agent/src/lib/types/agent.ts)).
- `system.md` has the sections `# Role & Objective`, `# Sandbox`, `# Working Directory`, `# Inputs`, `# Review Comments`, `# Final Response` and `# Environment` ([src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)). In them it tells the agent:
  - to complete the user's request in the Project's sandbox, continuing from the persisted history and the sandbox's current state; that other Threads share the sandbox, so it checks a file's current state before editing it and never reverts changes it did not make; and to use tools for evidence rather than guess;
  - that each Thread has its own working directory, starting at `/workspace`, which the `cwd` tool reports and changes; to work from a repository's root and move there with `cwd` before any other tool touches the code; not to reach into a repository from elsewhere, since the repository's skills and agents are listed only from the working directory; to load the matching skills when `cwd` reports a repository root; and, for code outside a repository, to initialize one for a deliverable meant to be kept and to ask the user first for an experiment (see [cwd-tool.md](cwd-tool.md) and [coding-workflow.md](coding-workflow.md));
  - how inputs arrive: the five envelopes, the request inside `<message>` or the `<ui-action>` a click on a control of a UI the agent drew sends, and that an input arriving mid-task applies from the next step;
  - how the chat's review comments arrive (`<comments>`, `<target>`, `<comment>`) and that each is answered with the `comment_reply` tool;
  - to keep the final response concise, stating the outcome and the verification run, or why none was run.

### Prompt templates

- The texts the model receives whole are seven templates in `src/host/prompts`: `system.md` (the system prompt), `agent.md` (the `# Agent: <name>` section), `agents.md` (the `# Agents` section), `agents-changed.md` (the "Agents changed" message), `skills-catalog.md` (the `# Skills` section), `skills-changed.md` (the "Skills changed" message) and `loaded-skills.md` (the "Loaded skills" message). The modules that use them load them when they are imported: `executor.ts` (`system.md`, `agent.md`), `agents/catalog.ts`, `skills/catalog.ts` and `skills/loaded.ts` ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [src/host/agents/catalog.ts](../../bundles/runtime/default/src/host/agents/catalog.ts), [src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts), [src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts)).
- `loadTemplate` reads a template synchronously and checks it against the names it may cite: `system.md` the prompt variables, `agent.md` `name` and `instructions`, the others their own lists. It removes exactly one trailing newline. Every `name`, `&`, `#` and `^` tag at any depth must cite a declared name, compared whole (`user.name` included); comments and delimiter changes are allowed. It fails with `Template "<file>" cites undeclared name "<name>".`, `Template "<file>" includes partial "<name>"; partials are not supported.` or `Template "<file>": <parse error>`, so a module that loads a missing or invalid template fails to import ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts)).
- `render` renders with mustache 4.2, every value as written, with no HTML escaping and no partials; a name the view lacks renders empty. `renderBlock` renders a template without one leading and one trailing newline. `renderSection` renders the first `#name` section for given items exactly as the whole template would, which is how the catalogs measure their budgets ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts)).
- The build copies the templates into `dist/host`, and the test target copies them into `dist-tests/src/host` ([packages/bundle/src/build/cli.ts](../../packages/bundle/src/build/cli.ts), [project.json](../../bundles/runtime/default/project.json)). `.prettierignore` excludes `bundles/*/*/src/host/**/*.md` ([.prettierignore](../../.prettierignore)).

### The `# Environment` section

- `system.md` ends with `# Environment`, rendered from the prompt variables ([src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md), [src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)):
  - `Operating system of the sandbox: <os>`, only when `os` is known;
  - `Today's date: <date> (<timezone>)`;
  - `User's name: <user.name>`, only when the profile names the user.
- `os` is `<PRETTY_NAME> (<uname -srm>)`, from one `sh -c` exec through `runtime.lease/v1` that prints `uname -srm` and sources `/etc/os-release`, with a 5,000 ms timeout. It is cached in memory per Project and lease id (`describe().id`), so each run asks `describe` and probes again only when the lease changed. A missing provider, a rejection, a non-zero or null exit, or an empty line leaves `os` out and is not cached ([src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)).
- `timezone` is the configuration profile's `timezone`, else the host's zone; `date` is today in that zone, as `YYYY-MM-DD`. `user` is present only when the profile has a `name`. The variables are read once at the start of each run; a time zone `Intl` does not know makes the run reject with a `RangeError` ([src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Agents

An agent is a definition a Thread can be spawned as; the tools that spawn and steer child Threads ship in the [`threads`](../../bundles/features/threads/README.md) bundle and are described in [delegation.md](delegation.md).

- **Definition.** One Markdown file `<name>.md`, its name matching `^[a-z0-9][a-z0-9_-]{0,63}$` (`agentNamePattern`), with a frontmatter holding `description` (required), and `model` and `effort` (optional; `effort` one of `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`; blank counts as absent). The text after the frontmatter, trimmed, is the agent's instructions: a raw mustache template that may cite only `os`, `date`, `timezone`, `user` and `user.name` ([src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts), [src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts), [bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- **Invalid.** A file larger than 64,000 bytes (`spawnInstructionsMaxLength`, [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts)), without a description, with an unknown effort, or whose instructions cite another name or do not parse. The reasons read `the file is larger than 64000 bytes`, `the frontmatter has no description`, `effort "<value>" is not one of none, minimal, low, medium, high, xhigh, max`, `the instructions cite "<name>", which is not a prompt variable (os, date, timezone, user, user.name); to write literal mustache tags, switch delimiters with {{=<% %>=}}` and `the instructions are not a valid template: <cause>` ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- **Built-in agents.** The bundle ships ten, in this order: `triage`, `search`, `spec`, `review`, `plan`, `contracts`, `tests`, `implementation`, `cleanup` and `docs`, the steps of the [coding workflow](coding-workflow.md). Each holds the same common block on its input, limits and tools (`## Workflow step`, `## Tools`) followed by its step, and none names a model or an effort. Four of them (`triage`, `spec`, `review`, `docs`) open with an attribution comment that is not rendered ([src/host/agents/built-in.ts](../../bundles/runtime/default/src/host/agents/built-in.ts), [src/host/agents/triage.md](../../bundles/runtime/default/src/host/agents/triage.md)).
- **Workspace agents.** The `.agents/agents/*.md` files of the Thread's current working directory, read with one `runtime.lease/v1` exec of at most 64 regular files in sorted order, with a 5,000 ms timeout, which prints each file's size and first 4096 bytes. A file whose base name does not match the pattern defines no agent. The template is checked only when the head is the whole file. A missing provider, a rejection, a non-zero exit or a timeout gives no workspace agent ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- **The agents in effect.** A workspace file, valid or not, hides the built-in of its name. The agents in effect are the built-ins not hidden, in shipped order, then the valid workspace agents in file-name order ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).

`default.agents/v1` 1.0.0 is `DefaultAgents`, defined in [src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts) and provided by [src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts). It is host-only: no method is exposed to a window. Its full shape is in the default README's [`default.agents/v1`](../../bundles/runtime/default/README.md#defaultagentsv1-100). The working directory is the one `runtime.workspace/v1.cwd` answers under `call.scope`.

| Method              | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list()`            | The agents in effect, each `{ name, description, source, model?, effort? }` without instructions; `source` is `built-in` or `workspace`. With no known working directory, the built-ins only. Never rejects because of the workspace.                                                                                                                                                                                                                                                                                                                |
| `resolve({ name })` | One agent with its raw instructions, chosen by the same rule. A workspace agent is read whole with `runtime.lease/v1.readFile` and checked again. Fails with a `ContractError`: `invalid_input` (a name outside the pattern, or another key), `not_found` (`Agent "<name>" is not defined. Defined agents: <a>, <b>.` or `… No agent is defined.`, details `{ name, agents }`) or `invalid_definition` (`Agent "<name>" is invalid: <reason>.`, details `{ name, path, reason }`; a file it cannot read gives the reason `the file cannot be read`). |

In a run ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)):

- The run reads the workspace agents of `thread.cwd` at its start, in parallel with the skills. Its `# Agents` section is a table `| Agent | Description |` with one row per agent in effect, each description cut at 500 characters, trailing rows dropped (and counted) while the rows pass 8,000 characters; at least one row always fits, and no agent means no section ([src/host/agents/catalog.ts](../../bundles/runtime/default/src/host/agents/catalog.ts), [src/host/prompts/agents.md](../../bundles/runtime/default/src/host/prompts/agents.md)).
- Before every model request after the first, the run reads the Thread's working directory through `runtime.workspace/v1` and scans `.agents/agents` again only when it moved. When the agents changed by name, description or source, the model reads one `<bundle-instruction bundle="default" reason="agents-changed">` message, before any "Skills changed" one, with the added or changed agents as a table and, under the heading `No longer available`, the names that are gone; a `model` or `effort` change alone is not told. After a compaction, the next check compares with the system prompt's agents ([src/host/agents/live.ts](../../bundles/runtime/default/src/host/agents/live.ts), [src/host/agents/catalog.ts](../../bundles/runtime/default/src/host/agents/catalog.ts), [src/host/prompts/agents-changed.md](../../bundles/runtime/default/src/host/prompts/agents-changed.md)).
- A Thread whose `thread.agent` is set gets the `# Agent: <name>` section: `You run as the <name> agent. Follow these instructions; they take precedence over general guidance for how to do your task.`, then the instructions rendered with the run's prompt variables. Instructions that cite another name, use a partial or do not parse make the run reject with the error of `checkTemplate`, named `agent <name>`, before its first model request ([src/host/prompts/agent.md](../../bundles/runtime/default/src/host/prompts/agent.md), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Such a Thread is not offered the built-in `coding-workflow` skill ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The runner reads the instructions from the stored Thread on every run and every compaction; when an agent Thread has none stored, it hands the executor the Thread without its agent, which runs as the default agent ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Tools

- The run offers every tool `tools/v1` lists for the prompt, in bundle order, each bound to the prompt's call, so a tool runs in the prompt's scope. A listed tool that was not made with `defineTool` fails the run with `Tool "<name>" was not defined with defineTool.` A tool whose declared result modalities the run's model does not read is left out; a model whose catalog does not say keeps every tool ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Before the model is called, the run resolves every tool's settings from the configuration: each declared field takes its stored value or its default, and a required field with neither refuses the prompt with `Tool <name> requires a <key> value.` ([src/host/tool-config.ts](../../bundles/runtime/default/src/host/tool-config.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- After the registered tools comes the run's own `load_skill`, which is never registered with `tools/v1` and is offered from the first request at which the run lists a skill to load, and from then on. It is described in [skills.md](skills.md) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).
- Each tool answer the model reads is capped at the configuration's `execution.maxToolResultChars`, or at `defaultMaxToolResultChars` (50,000 characters) when it names none, so one oversized answer cannot fill the context. `load_skill` is exempt: its answer reaches the model whole. An answer over the cap keeps its first characters up to the cap, followed by `\n… [truncated <omitted> of <total> characters]`; the full output stays on the tool-call record ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/foundation/host-config/src/contracts/index.ts](../../bundles/foundation/host-config/src/contracts/index.ts), [packages/agent/src/lib/utils/run.ts](../../packages/agent/src/lib/utils/run.ts)).
- The run's turn budget is the configuration's `execution.maxTurns` ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Model resolution

- Each run resolves the Thread's provider, model and effort once, with `resolveThreadExecution` on the configuration `host-config/v1` answers, and uses them for its agent loop, its input modalities, its `response.started` events and its automatic compaction. A Thread with a `providerId` runs on its own provider, model and effort; a Thread without one runs on the workspace default's provider, with its own `model` and `effort` over the default's when it stores them. The rules and how a Thread's execution is chosen are described in [per-thread-model.md](per-thread-model.md) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/runtime/runtime/src/contracts/execution.ts](../../bundles/runtime/runtime/src/contracts/execution.ts)).
- When the Thread's provider or model is not available, the run logs one `LogV1` warning `Thread execution unavailable` with `threadId`, `providerId`, `model` and `issue`, and rejects before any model request with an error whose `code` is `thread_execution_unavailable` and whose message is `The model "<model>" on provider "<providerId>" is not available for this thread. Choose another model in the conversation footer.` ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The run asks `models/v1.resolve` for the language model of that provider, model and effort (no effort when none is resolved), and `models/v1.inputModalities` for what the model reads. Images attached to a prompt or answered by a tool reach the model only when it reads images; see [attachments.md](attachments.md) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).
- A manual compaction (`compact`) uses the Thread's resolved provider and model, without effort; when that execution is unavailable or `models/v1` cannot resolve it, the compaction fails as `summarizer_failed` ([src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts)).

### Provider history

- The executor keeps a Thread's history as the opaque state `default.history/v1`, in two parts: `messages`, the provider-ready messages, and `meta`, holding `checkpoints` (each prompt's turn boundary, by prompt id), `messageCount` and `retained` (the index of each standing instruction, by `<bundleId>:<reason>`) ([src/host/history.ts](../../bundles/runtime/default/src/host/history.ts)).
- It also reads state stored as `direct.history/v1`, which holds the same parts, as it is; every save writes `default.history/v1`. A Thread with no `meta` part has no boundary and no retained message, and its message count is the length of its `messages` ([src/host/history.ts](../../bundles/runtime/default/src/host/history.ts)).
- `checkpoint` records the prompt's boundary once; `rewind` keeps the messages before the prompt's boundary, drops the boundaries of the removed prompts and forgets every retained message past the boundary, so its instruction can be given again ([src/host/history.ts](../../bundles/runtime/default/src/host/history.ts)).
- The runtime checks the stored format against `formats()` before a run; a history in a format the executor does not read logs `Thread history format is unsupported` and fails with `The Thread history format is unsupported.` before any model call ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- What the runtime stores is redacted and sanitized by its session on write ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)).

### Input envelope

- The executor frames every input in an XML envelope that names its source: `<user-request>`, `<parent-instruction thread="" prompt="">`, `<terminal-output terminal="" prompt="">`, `<child-result thread="" prompt="">` or `<bundle-instruction bundle="" reason="">`, as `<tag attributes>`, a newline, the body, a newline and the closing tag. Attribute values escape `&`, `"` and `<`. In the body, a closing tag of any of the five names becomes `<\/…`; nothing else changes ([src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).
- The bundle's own messages use `<bundle-instruction bundle="default">` with the reason `skills-changed`, `agents-changed` or `loaded-skills` ([src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).

### The `default.hooks/v1` contract

- `default.hooks/v1` 1.0.0 has one hook, `onBeforeModelRequestHook`, of the kind `transform`, whose input is `{ system }` (strict). It runs before every model request of a prompt, under the prompt's call: `call.scope` names the prompt (`projectId`, `threadId`, `promptId`) and `call.signal` aborts with it ([src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)); its full shape is in the default README's [`default.hooks/v1`](../../bundles/runtime/default/README.md#defaulthooksv1-100).
- The `default` bundle registers no handler of its own. A bundle registers one through `hooks/v1`, with `default.hooks/v1` under `requires` or `optional` ([src/host/index.ts](../../bundles/runtime/default/src/host/index.ts), [bundles/foundation/core/src/shared/hooks.ts](../../bundles/foundation/core/src/shared/hooks.ts)):

  ```ts
  services
    .use(HooksV1)
    .use(DefaultHooksV1)
    .onBeforeModelRequestHook(({ system }) => ({
      system: `${system}\n\n# Project rules\n\nUse tabs.`,
    }));
  ```

- Handlers run in turn, each receiving the previous one's output. A handler that throws, times out or answers a value outside the input schema is reported and skipped, and the value goes on unchanged ([bundles/foundation/core/src/shared/hooks.ts](../../bundles/foundation/core/src/shared/hooks.ts)). Hooks in general are described in [docs/architecture/bundles/hooks.md](../architecture/bundles/hooks.md).

### What a run reaches through the runtime

- For every prompt, the runtime's runner builds a `Host` facade and binds it, with the Project's sandbox, to the prompt's scope while the executor runs, and releases the binding once the run settles ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/domain/bindings.ts](../../bundles/runtime/runtime/src/host/domain/bindings.ts)).
- `Host` is the `runtime` bundle's own type, in `runtime/contracts` (`src/contracts/tool-host`). It has two namespaces: `threads`, control over the direct child Threads of the prompt, and `workspace`, the working directory of the prompt's own Thread. Its definition states that a namespace is added only for a concrete need, never as a dumping ground ([bundles/runtime/runtime/src/contracts/tool-host/host.ts](../../bundles/runtime/runtime/src/contracts/tool-host/host.ts)).
- Tools reach these capabilities through contracts the `runtime` provides, never as an argument: the child controls of `runtime.threads/v1` (`spawn`, `list`, `get`, `events`, `send`, `restart`, `interrupt`, `terminate`) and `cwd`, `setCwd` and `location` of `runtime.workspace/v1` forward to the `Host` of the prompt named by the call's scope; the other methods of the two contracts ignore the scope. `runtime.lease/v1` forwards a call whose scope names a prompt to that prompt's sandbox. A forwarded call fails with `Thread control is no longer active.` when its scope names no prompt that is running; a Host failure reaches the caller unchanged. `runtime.lease/v1.exec` passes no abort signal to the sandbox ([bundles/runtime/runtime/src/host/services/threads.ts](../../bundles/runtime/runtime/src/host/services/threads.ts), [bundles/runtime/runtime/src/host/services/workspace.ts](../../bundles/runtime/runtime/src/host/services/workspace.ts), [bundles/runtime/runtime/src/host/services/lease.ts](../../bundles/runtime/runtime/src/host/services/lease.ts), [bundles/runtime/runtime/src/host/domain/bindings.ts](../../bundles/runtime/runtime/src/host/domain/bindings.ts)).
- The agent's shell commands (the `terminal` tool) go through `terminal/v1`, which the [`terminal`](../../bundles/features/terminal/README.md) bundle provides; see [terminal.md](terminal.md) ([bundles/features/terminal/manifest.json](../../bundles/features/terminal/manifest.json)).
