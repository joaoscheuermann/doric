# Feature: Default agent

- Status: `implemented`

## Problem

Every Doric conversation needs an agent loop: something that turns one prompt of a Thread into model requests and tool calls. The model must be told where it works, what it can do and who it works for, it must run on the provider and model the Thread chose, and what it does must be kept as a history the Thread can resume, rewind and compact. Other bundles need a way to adjust the system prompt at each turn, and a workspace needs a way to define the agents a Thread can be spawned as, in files, without a change to Doric.

## Decisions

- The long texts the model receives whole (the system prompt, the agent, agents and skills sections, and the "changed" and "Loaded skills" messages) are Markdown templates under `src/host/prompts`, rendered with `mustache`, because they need named variables and workspace agents are templates read at run time. Tool descriptions stay in each tool's `defineTool`. Compaction's texts (the summarizer's system prompt and the `[Context summary]` header) and short tool results and notes, such as the interrupted-call result, are built in TypeScript ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts), [src/host/compaction/summarize.ts](../../bundles/runtime/default/src/host/compaction/summarize.ts), [src/host/compaction/markers.ts](../../bundles/runtime/default/src/host/compaction/markers.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The code supplies only data to the templates, and the templates do all the formatting; a budget is measured by rendering the section it fills, so a row's format exists only in its template ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts)).
- Each module reads its templates once, when it is imported, not at activation, because their consumers are synchronous and tests call them without activation ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts)).
- A template may cite only the names declared for it; partials are refused, and rendering does no HTML escaping ([src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts)).
- The bytes the model reads stay as written: the build copies the `.md` files of `src/host` into `dist/host`, and `.prettierignore` leaves `bundles/*/*/src/host/**/*.md` alone ([packages/bundle/src/build/cli.ts](../../packages/bundle/src/build/cli.ts), [`packages/bundle`](../../packages/bundle/README.md#sources-and-outputs), [.prettierignore](../../.prettierignore)).
- The system prompt ends with an `# Environment` section. Its `date` is the calendar day only, never the time of day, because providers cache the system prompt and the day changes it at most once a day. The prompt variables are read once at the start of each run, so every request of a run carries the same prompt, even across midnight ([src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The user's name and time zone come from the `profile` the user fills in the host configuration, never from the host's operating-system user or the Git identity, because the host can be remote and neither describes who uses Doric ([src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)).
- The sandbox's operating system is probed through the sandbox and cached per Project and lease; a failed probe is not cached, so the next run tries again ([src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)).
- Built-in and workspace agents share one file format and one parser. Each built-in agent is a self-contained file that repeats the common block word for word, with no partial or include ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts), [src/host/agents/built-in.ts](../../bundles/runtime/default/src/host/agents/built-in.ts)).
- An agent's instructions are a template that may cite only the prompt variables, rendered by the run, so the date follows each run ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The workspace agents are scanned with an exec of their own, in parallel with the skills scan, so each read keeps its own failure and record format ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- The listing checks a workspace agent's template only when the file fits in the head the scan reads; `resolve` reads the file whole and checks it again. A long file whose instructions cite another name is therefore listed and then fails to resolve. This is accepted, because reading every file whole would cost up to 64 × 64,000 bytes per run (the scan reads at most 64 files, and a definition may hold up to 64,000 bytes) ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- A workspace file with a built-in's name replaces the built-in even when it is invalid, so what the workspace's author wrote is never silently swapped for another definition ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- A Thread that runs as an agent keeps the whole default system prompt and gets the agent's instructions in a section of their own, which take precedence over its general guidance; it keeps the envelope, the tools and the environment the system prompt describes. It is not offered the `coding-workflow` skill, because the agent's instructions are its workflow ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [src/host/prompts/agent.md](../../bundles/runtime/default/src/host/prompts/agent.md)).
- An agent Thread's instructions live only in the stored Thread, never in the public Thread; the runtime hands them to the executor on every run and compaction ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- When a tool call fails because its generation process was lost, the run saves the history at that moment and leaves the call unanswered, as a host crash leaves it, so the resumed run answers it with the interrupted-call result rather than running it again ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- `executor/v1` is local: `run` receives the runtime's `PromptSession`, through which every history and event write goes, so the runtime keeps redaction, persistence and its retry ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)).
- Streamed deltas are written coalesced, one event per run of same-kind deltas, rather than through a live channel or a new storage primitive. The merge rule is one set of pure functions in `runtime/contracts`, so the executor and the chat's projector apply the same rule ([bundles/runtime/runtime/src/contracts/deltas.ts](../../bundles/runtime/runtime/src/contracts/deltas.ts), [src/host/deltas.ts](../../bundles/runtime/default/src/host/deltas.ts), [bundles/desktop/chat/tests/projector-coalesced.property.test.ts](../../bundles/desktop/chat/tests/projector-coalesced.property.test.ts)).

### Activation and what a failure does to the host

- The process entry serves `executor/v1` and `default.agents/v1` over the router ([src/host/main.ts](../../bundles/runtime/default/src/host/main.ts)). Activation installs the asset texts read through `context.assets.read`, loads the built-in agents, then defines `default.hooks/v1` through `hooks/v1`; each failure rejects `activate` before anything is served ([src/host/service.ts](../../bundles/runtime/default/src/host/service.ts)). `assetText` answers only the installed texts: with nothing installed, or a path they lack, it throws an `Error` naming the path, and reads no file ([src/host/assets.ts](../../bundles/runtime/default/src/host/assets.ts)).
- A missing or invalid built-in agent file fails `activate`, naming the file by its bundle-relative path: the process entry's `activate` rejects, and the supervisor quarantines `default` with `activate_failed` and stops its process ([packages/bundle/src/platform/supervisor/boot.ts](../../packages/bundle/src/platform/supervisor/boot.ts)). A missing or invalid prompt template is read and checked at its first render, so it fails the run that renders it; no module reads a file at import (phase 3, slice S51c of [grpc-processes.md](../designs/grpc-processes.md); [src/host/prompts/templates.ts](../../bundles/runtime/default/src/host/prompts/templates.ts), [src/host/agents/built-in.ts](../../bundles/runtime/default/src/host/agents/built-in.ts)).
- `executor/v1` is one of the contracts the host's composition requires. With `default` quarantined, `runtime`, which requires it, is quarantined with `dependency_quarantined`, and the host logs `Bundle recovery mode` and exits with code 1 ([app/backend/doric-host/composition.json](../../app/backend/doric-host/composition.json), [bundles/runtime/runtime/manifest.json](../../bundles/runtime/runtime/manifest.json), [`required`](../architecture/bundles/composition-and-distribution.md#required)).

### The path of one prompt

The runtime's side of each step is in its README's [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue) and in [projects-and-threads.md](projects-and-threads.md#the-queue); the executor's in the default README's [One prompt run](../../bundles/runtime/default/README.md#one-prompt-run).

1. **Checkpoint.** When a Thread dispatches a prompt, the runtime marks it `running`, then calls `executor/v1.checkpoint` with the stored history and the prompt's id, saves the patch it answers with `saveCheckpoint`, and appends `prompt.started`. The checkpoint is the prompt's turn boundary, the history's message count at that moment, recorded once: a boundary the prompt already has wins ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/history.ts](../../bundles/runtime/default/src/host/history.ts)).
2. **Format check.** Before `run`, the runtime compares the stored history's format with `executor/v1.formats()` (`default.history/v1` and `direct.history/v1`). A stored format outside that list logs `Thread history format is unsupported` with the code `history_format_unsupported` and fails the prompt with `The Thread history format is unsupported.`; a Thread with no stored format passes ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
3. **Run.** The runtime calls `executor/v1.run` with the Thread, the job and the session, under a call whose scope names `{ projectId, threadId, promptId }` and whose signal aborts with the prompt; for an agent Thread it adds the stored instructions, and when none are stored it drops the agent, so the Thread runs as the default agent ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
4. **Resume or start.** The run reads the stored history. When the prompt's boundary is shorter than the stored history, the run resumes: it continues the stored history without appending the input again. A last assistant turn whose tool calls have no results is answered with the interrupted-call result ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
5. **Read what the run needs.** The configuration from `host-config/v1`, the Thread's execution ([Model](#model)), the prompt variables, the tools of `tools/v1`, and, in parallel, the skills and the workspace agents of the Thread's working directory ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
6. **Loop.** The run creates a fresh agent of `packages/agent` over the stored history, the tools, the model and the system prompt, and streams it. Before the first request and after each finished response it checks the context pressure ([context-compaction.md](context-compaction.md)). Inputs that arrive meanwhile are taken as steers, each in its source's envelope ([prompt-control.md](prompt-control.md)) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
7. **Record.** Every event the agent streams is recorded through the session, and the history is saved with `response.finished`, `tool.finished` and `agent.steered`, the events after which the agent has stored new messages, and once more when the run ends ([Events and who reads them](#events-and-who-reads-them)).
8. **End.** `run` resolves with the text of the agent's final answer. When `run` rejects, the runtime decides what follows: a steer that aborted only the current step makes it call `run` again for the same prompt; a storage-full error appends no `agent.failed` and pauses the Thread's queue for storage, and a persistence error appends none and closes the Thread with `persistence_failed` ([Storage pressure](../../bundles/runtime/runtime/README.md#storage-pressure)); a pause, which a run whose generation process was lost also leads to, appends `prompt.paused`, so the next run repairs the call; an interruption or an abort appends `agent.cancelled`; any other error appends `agent.failed` with the error. The rules are in the runtime README's [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue) ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Events and who reads them

- The run records each event of `packages/agent`'s stream: the provider's stream events (among them `response.started`, the `reasoning.delta`, `text.delta`, `refusal.delta` and `tool_call.delta` deltas, `tool_call.done`, `usage`, `response.finished` and `error`) and the agent's own (`agent.started`, `agent.steered`, `tool.started`, `tool.finished`, `tool.failed`, `agent.finished`). It adds the run's `providerId` to every `response.started` ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [`AgentEvent`](../../packages/agent/README.md#agentevent), [Stream events](../../packages/llms/README.md#stream-events)).
- Deltas are coalesced before they are written; the window and size are in the default README's [Writes](../../bundles/runtime/default/README.md#writes) ([src/host/deltas.ts](../../bundles/runtime/default/src/host/deltas.ts)).
- The session redacts and persists each event in the Thread's log and publishes it ([bundles/runtime/runtime/src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts)). The runtime folds `response.started`, `usage` and `response.finished` into the Thread's usage state, which [usage.md](usage.md) describes ([bundles/runtime/runtime/src/host/store/usage.ts](../../bundles/runtime/runtime/src/host/store/usage.ts)).
- The `chat` projector turns the log into the conversation's turns and reads the `providerId` of `response.started` to know which provider answered; see [conversation.md](conversation.md#from-the-log-to-turns) ([bundles/desktop/chat/src/client/domain/projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts)).

### The system prompt

- The system prompt is `system.md` rendered with the run's prompt variables, then, each only when it has content, the `# Agent: <name>` section of an agent Thread, the `# Agents` section and the `# Skills` section. It is the same for human and child Threads and stays the same for the whole run ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md)).
- `system.md` tells the agent how to work in the shared sandbox, how its working directory and repositories work ([cwd-tool.md](cwd-tool.md), [coding-workflow.md](coding-workflow.md)), how inputs and review comments arrive, and how to write its final response; it ends with `# Environment`: the sandbox's operating system when known, today's date in the profile's time zone (else the host's), and the user's name when the profile has one. The sections, variables and templates are in the default README's [The system prompt](../../bundles/runtime/default/README.md#the-system-prompt) ([src/host/prompts/system.md](../../bundles/runtime/default/src/host/prompts/system.md), [src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)).
- Before each request of the agent loop, the run passes the system prompt through `default.hooks/v1.onBeforeModelRequestHook` under the prompt's call, and the model receives what the hook answers ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)). The summarizer's requests, automatic and manual, do not pass through the hook ([src/host/compaction/summarize.ts](../../bundles/runtime/default/src/host/compaction/summarize.ts), [src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts)).

### The `default.hooks/v1` hook

- `default.hooks/v1` has one hook, `onBeforeModelRequestHook`, a `transform` whose input is `{ system }`; `call.scope` names the prompt and `call.signal` aborts with it. Its shape is in the default README's [`default.hooks/v1`](../../bundles/runtime/default/README.md#defaulthooksv1-100) ([src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts)).
- No bundle registers a handler: `default` registers none, and no other bundle names the hook ([src/host/service.ts](../../bundles/runtime/default/src/host/service.ts)). A bundle registers one through `hooks/v1`, with `default.hooks/v1` under `requires` or `optional`:

  ```ts
  services
    .use(HooksV1)
    .use(DefaultHooksV1)
    .onBeforeModelRequestHook(({ system }) => ({
      system: `${system}\n\n# Project rules\n\nUse tabs.`,
    }));
  ```

- Handlers run in turn, ordered by their bundle's rank in the catalog and then by registration, each receiving the previous one's output, with a deadline of 10,000 ms each. A handler that throws, times out or answers outside the input schema is reported to `doric.diagnostics/v1` and skipped, and the value goes on unchanged ([bundles/foundation/core/src/shared/hooks.ts](../../bundles/foundation/core/src/shared/hooks.ts), [Firing a hook](../architecture/bundles/hooks.md#firing-a-hook), [`hooks/v1`](../../bundles/foundation/core/README.md#hooksv1)).

### Agents

An agent is a definition a Thread can be spawned as. The format, the limits and the reasons a definition is invalid are in the default README's [Agents](../../bundles/runtime/default/README.md#agents), and `default.agents/v1`'s shape in [`default.agents/v1`](../../bundles/runtime/default/README.md#defaultagentsv1-100).

- **Definition.** One Markdown file `<name>.md` with a frontmatter holding `description` (required), `model` and `effort` (optional), and the instructions after it ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- **Built-in agents.** Ten, the steps of the [coding workflow](coding-workflow.md): `triage`, `search`, `spec`, `review`, `plan`, `contracts`, `tests`, `implementation`, `cleanup` and `docs`; none names a model or an effort ([src/host/agents/built-in.ts](../../bundles/runtime/default/src/host/agents/built-in.ts)).
- **Workspace agents.** The `.agents/agents/*.md` files of the Thread's working directory, read through `runtime.lease/v1`; a failed read gives no workspace agent. A workspace file hides the built-in of its name; the agents in effect are the built-ins not hidden, then the valid workspace agents ([src/host/agents/definitions.ts](../../bundles/runtime/default/src/host/agents/definitions.ts)).
- **In a run.** The run lists the agents in effect in its `# Agents` section. Before each later request it checks whether the working directory moved and, when the agents changed by name, description or source, tells the model in one `agents-changed` bundle instruction, before any "Skills changed" one ([src/host/agents/live.ts](../../bundles/runtime/default/src/host/agents/live.ts), [src/host/agents/catalog.ts](../../bundles/runtime/default/src/host/agents/catalog.ts)).
- **Spawning.** `thread-spawn` resolves the named agent through `default.agents/v1.resolve` under the calling prompt's scope and spawns the child with the agent's name, source and instructions. The call's own `model` and `effort` win, else the agent's; the runtime completes the parent's execution with what is given, always on the parent's provider, and refuses an execution the configuration does not allow with `invalid_execution`. The rules, among them the start effort of a model named without an effort, are in [per-thread-model.md](per-thread-model.md#creation-and-spawn) ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts),[bundles/features/threads/src/host/tools/thread-spawn.ts](../../bundles/features/threads/src/host/tools/thread-spawn.ts), [delegation.md](delegation.md#spawning-a-child)).
- **Running as an agent.** The child's runs get the `# Agent: <name>` section with the instructions rendered with the run's prompt variables; instructions that cite a name outside the prompt variables, include a partial or do not parse make the run reject before its first model request ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Tools

The details are in the default README's [Tools](../../bundles/runtime/default/README.md#tools).

- The run offers the tools `tools/v1.list` answers for the prompt's call: the unscoped tools and those of the call's Project, ordered by their `order` key, unordered ones last, then by registration ([bundles/foundation/core/src/host/tools/service.ts](../../bundles/foundation/core/src/host/tools/service.ts), [`tools/v1`](../../bundles/foundation/core/README.md#toolsv1)). Each is bound to the prompt's call; one not made with `defineTool` fails the run, and one whose result modalities the model does not read is left out ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Before the model is called, the run checks every tool's settings against the configuration: each field takes its stored value, even a blank one, and its default only when nothing is stored; a required field whose value is missing or blank refuses the prompt with `Tool <name> requires a <key> value.` The run passes the resolved values to no tool: the check only decides whether the prompt runs ([src/host/tool-config.ts](../../bundles/runtime/default/src/host/tool-config.ts), [src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [Settings fields](../../packages/tool/README.md#settings-fields)).
- After the registered tools comes the run's own `load_skill`, offered once a skill can be loaded; see [skills.md](skills.md) ([src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).
- Each tool answer the model reads is capped at the configuration's `execution.maxToolResultChars`, else 50,000 characters, except `load_skill`'s ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- The agent loop runs at most `execution.maxTurns` turns, 32 by default. A run that needs another turn fails with `turn_limit_exceeded` and the message `Agent exceeded its <n>-turn limit.` ([bundles/foundation/host-config/src/host/config/schema.ts](../../bundles/foundation/host-config/src/host/config/schema.ts), [packages/agent/src/lib/utils/run.ts](../../packages/agent/src/lib/utils/run.ts), [Turn limit](../../packages/agent/README.md#turn-limit)).
- The agent's shell commands go through the `terminal` tool of the [`terminal`](../../bundles/features/terminal/README.md) bundle; see [terminal.md](terminal.md).

### What a tool reaches through the runtime

- While the run executes, the runtime binds a `Host` facade and the Project's sandbox to the prompt's scope, and releases the binding once the run settles ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/domain/bindings.ts](../../bundles/runtime/runtime/src/host/domain/bindings.ts)).
- A tool reaches it through the runtime's contracts, under its call's scope: the child-Thread controls of [`runtime.threads/v1`](../../bundles/runtime/runtime/README.md#runtimethreadsv1), the working directory of [`runtime.workspace/v1`](../../bundles/runtime/runtime/README.md#runtimeworkspacev1) and the sandbox of [`runtime.lease/v1`](../../bundles/runtime/runtime/README.md#runtimeleasev1). A forwarded call whose scope names no running prompt fails with `Thread control is no longer active.` ([bundles/runtime/runtime/src/host/rpc/threads.ts](../../bundles/runtime/runtime/src/host/rpc/threads.ts), [bundles/runtime/runtime/src/host/rpc/workspace.ts](../../bundles/runtime/runtime/src/host/rpc/workspace.ts)).

### Model

- Each run resolves the Thread's provider, model and effort once and uses them for its agent loop, its input modalities, its `response.started` events and its automatic compaction; the rules are in [per-thread-model.md](per-thread-model.md) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/runtime/runtime/src/contracts/execution.ts](../../bundles/runtime/runtime/src/contracts/execution.ts)).
- The run asks `models/v1` for the language model and what it reads; images reach the model only when it reads them ([attachments.md](attachments.md)) ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [`models/v1`](../../bundles/foundation/core/README.md#modelsv1)).
- When the Thread's provider or model is not available, the run logs `Thread execution unavailable` and rejects before any model request with the code `thread_execution_unavailable` and the message `The model "<model>" on provider "<providerId>" is not available for this thread. Choose another model in the conversation footer.` ([src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)). The chat shows the failed prompt as `Model unavailable` with that message, without Retry ([bundles/desktop/chat/src/client/domain/error-catalog.ts](../../bundles/desktop/chat/src/client/domain/error-catalog.ts), [error-messages.md](error-messages.md#conversation)). A manual compaction of such a Thread fails as `summarizer_failed` ([src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts)).

### Provider history and rewind

- The executor keeps a Thread's history as the opaque state `default.history/v1`: the provider-ready `ProviderMessage`s of `packages/llms` and a `meta` part with each prompt's boundary and the retained standing instructions. It also reads `direct.history/v1` and writes `default.history/v1` on every save. The shape is in the default README's [Provider history](../../bundles/runtime/default/README.md#provider-history) ([src/host/history.ts](../../bundles/runtime/default/src/host/history.ts)).
- A rewind runs in the runtime's store: it finds the first event of the target prompt in the log and calls `executor/v1.rewind` with the stored history, the prompt's id and `removedPromptIds`, every prompt with an event at or after that one, the target included. The executor keeps the messages before the target's boundary, drops the removed prompts' boundaries and forgets the retained instructions past it; it answers `undefined` when the prompt has no boundary. The runtime answers `busy` while a prompt runs or waits, and `unknown_prompt` when the log holds no event of the prompt or the executor answers `undefined`; the REST route maps `unknown_prompt` to a 404. Otherwise, in one write, the store truncates the log from that event, appends `history.truncated` and stores the executor's patch as the history, and the runtime queues the rewind's edited text as a new input of the reader ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/history.ts](../../bundles/runtime/default/src/host/history.ts), [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue), [projects-and-threads.md](projects-and-threads.md#the-queue), [`executor/v1`](../../bundles/runtime/runtime/README.md#executorv1)).
- What the runtime stores is redacted by its session on write ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)). Compaction rewrites the history; see [context-compaction.md](context-compaction.md).

### Input envelope

- The executor frames every input in an XML envelope that names its source: `<user-request>`, `<parent-instruction>`, `<terminal-output>`, `<child-result>` or `<bundle-instruction>`, with the source's ids as attributes. A closing tag of any of the five names in the body, in any case, is escaped, so a body cannot close its envelope. The escaping is in the default README's [Input envelope](../../bundles/runtime/default/README.md#input-envelope) ([src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).
- The body of a `<user-request>` is written by the `chat`: the reader's words in `<message>`, after the composer's review comments in `<comments>` ([conversation.md](conversation.md), [comments.md](comments.md)), or a `<ui-action>` when the reader clicks a control of a UI the agent drew, which the [`openui`](../../bundles/features/openui/README.md) bundle sends through `chat.send/v1.sendAction` ([generative-ui.md](generative-ui.md)) ([bundles/desktop/chat/src/client/domain/prompt-envelope.ts](../../bundles/desktop/chat/src/client/domain/prompt-envelope.ts), [bundles/desktop/chat/src/client/services/send.ts](../../bundles/desktop/chat/src/client/services/send.ts)).
- The bundle's own messages are `<bundle-instruction bundle="default">` with the reason `skills-changed`, `agents-changed` or `loaded-skills` ([src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).
