# Feature: Attachments

- Status: `implemented`

## Problem

A reader wants to show the agent a screenshot, and a tool wants to hand the model an image it found. The model must receive the image itself, while prompts, queued inputs, edits, events, tool results and the stored history stay text that every part of the system already stores, redacts, compacts and draws. An image must be readable only in the Project that holds it, must go when the Thread or Project that holds it is deleted, and must not reach a model whose provider's catalog says it reads no images.

## Decisions

- The host's Socket.IO message limit is a constant of the host's own, `SOCKET_MAX_HTTP_BUFFER_BYTES`, 8,039,084 bytes: the base64 size of the largest attachment (6,990,508 bytes for 5 MiB) plus 1,048,576 bytes for the envelope around it. The host imports no bundle to size it; a host test imports the runtime's `ATTACHMENT_MAX_BYTES` and fails when the constant is smaller than that attachment as base64 plus 1,048,576 bytes ([app/backend/doric-host/src/lib/socket-buffer.ts](../../app/backend/doric-host/src/lib/socket-buffer.ts), [app/backend/doric-host/tests/socket-buffer.test.ts](../../app/backend/doric-host/tests/socket-buffer.test.ts)).

## Current behavior and contracts

- The `default` bundle's executor turns reference lines into images in the requests a model reads ([src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts), [README](../../bundles/runtime/default/README.md)). The `llms` package sends the images in each provider's format ([README](../../packages/llms/README.md)).

- The tools `view-image` of the `files` bundle and the MCP tools of the `mcp` bundle attach the images they return ([bundles/features/files/src/host/tools/view-image.ts](../../bundles/features/files/src/host/tools/view-image.ts), [bundles/features/mcp/src/host/tools.ts](../../bundles/features/mcp/src/host/tools.ts); READMEs of [`files`](../../bundles/features/files/README.md) and [`mcp`](../../bundles/features/mcp/README.md)).
- The host sizes its Socket.IO messages for one attachment ([app/backend/doric-host/src/lib/socket-buffer.ts](../../app/backend/doric-host/src/lib/socket-buffer.ts), [README](../../app/backend/doric-host/README.md)).

### One image, end to end

1. The reader pastes or drops an image in the conversation; the `chat` composer sends its bytes, base64, to `runtime.attachments/v1.attach` in the conversation's Thread ([attach-images.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx), [attachments-api.ts](../../bundles/desktop/chat/src/client/api/attachments-api.ts)).
2. The call crosses the host's `/doric/bridge` Socket.IO namespace whole, within the host's message limit ([socket-buffer.ts](../../app/backend/doric-host/src/lib/socket-buffer.ts)).
3. The `runtime` checks the bytes, keeps them as a `storage/v1` blob, commits the Thread's `runtime.attachment/v1` record and answers the id and the cleaned name ([src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).
4. The composer writes the reference line into the prompt from that answer, and the prompt sends the line as text ([attach-images.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx)).
5. The runner starts the prompt and hands its session `attachment(id)` for the Thread's Project ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
6. The `default` executor finds the line in each request, reads the attachment through the session and, when the model reads images, puts an image part in the line's place ([bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).
7. The `llms` provider sends the image part in its own format ([packages/llms/README.md](../../packages/llms/README.md)).
8. The window draws the line as the image, read through `runtime.attachments/v1.read` ([attachment-image.tsx](../../bundles/desktop/chat/src/client/components/molecules/attachment-image.tsx)).

A tool's image enters the same flow at step 3: `view-image` or an MCP tool attaches it in the calling Thread and answers the line as its result.

### The reference line

- Text names an attachment with the Markdown image line `![<name>](doric-attachment:sha256-<64 hex>)`. The id `sha256-<hex>` is the blob's hash `sha256:<hex>` spelled for a URL ([src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- `attachmentReference(name, id)` writes the line. Its name is `attachmentLabel(name)`: the name has line breaks turned into spaces, brackets removed, is trimmed and cut to 200 characters, and is `image` when nothing is left ([src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- `attachmentReferences(text)` finds every reference in a text, wherever it stands; `attachmentLine(line)` answers the reference only when the trimmed line holds nothing else; `withAttachmentPlaceholders(text)` writes each reference as `[<name>]` ([src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- Because an image is a line of text, prompts, queued inputs, edits, steers, events, tool results and the stored history carry no image bytes ([src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts), [bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).

### Keeping an image

- An attachment is one content-addressed `storage/v1` blob plus one `runtime.attachment/v1` record per Thread that attached it. The record holds `{ projectId, threadId, id, name, mediaType, size, createdAt }` under the key `<threadId>:<id>`, with the indexes `byProject` (`projectId`, `id`), `byThread` (`threadId`) and `byBlob` (`id`) ([src/contracts/storage.ts](../../bundles/runtime/runtime/src/contracts/storage.ts), [src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).
- `runtime.attachments/v1` has two methods, both reachable from the desktop. Its scope keys are `projectId`, `threadId` and `promptId` ([src/host/services/attachments.ts](../../bundles/runtime/runtime/src/host/services/attachments.ts), [manifest.json](../../bundles/runtime/runtime/manifest.json)).

| Method                    | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `attach({ name, bytes })` | Keeps base64 `bytes` for the Thread of `call.scope.threadId` and answers `{ id, name, mediaType, size }`, where `name` is `attachmentLabel(name)`, 1–200 characters, which the record keeps. Without a Thread scope it refuses with `invalid_input` (`runtime.attachments/v1.attach needs a Thread scope.`); an unknown Thread is `not_found`. Attaching the same bytes again answers the same id; in the same Thread it rewrites that Thread's one record for the bytes, with the new cleaned name and `createdAt`. |
| `read({ id })`            | Answers `{ id, name, mediaType, size, bytes }` for the Project of `call.scope.threadId`, else `call.scope.projectId`, or `undefined` when the id is not `sha256-<64 hex>`, when that Project holds no record of the id, or when the blob is gone. An unknown Thread is `not_found`. With neither scope it refuses with `invalid_input` (`runtime.attachments/v1 needs a Project or Thread scope.`).                                                                                                                  |

- An attach refuses with `invalid_input` bytes that are empty (`The attachment is empty.`), larger than 5 MiB (`ATTACHMENT_MAX_BYTES`; `The attachment is larger than 5 MiB.`), or not a PNG, JPEG, WebP or GIF (`The attachment is not a PNG, JPEG, WebP or GIF image.`). The media type is read from the bytes' signature, never from the name ([src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts), [src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- Every Thread of a Project reads the images any of its Threads attached, so a reader's image and an image a tool attached in a delegated Thread are read alike. A reference line written in another Project reads as nothing ([src/host/services/attachments.ts](../../bundles/runtime/runtime/src/host/services/attachments.ts), [src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).
- The cleaned name is what every later step writes: the window's reference line, the executor's `[Image: <name>]` and the answer's schema, which requires 1–200 characters ([attach-images.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx), [bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts), [src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- An attach first writes the blob through `storage/v1.putBlob` and then commits the record. When the commit fails, the blob stays behind with no record naming it, and nothing collects it ([src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).

### Deleting

- Deleting a Thread with its subtree, or a Project, deletes its attachment records in the same commit that deletes its documents, histories and event streams ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)).
- After that commit, each blob those records named and no record in any Project names any more is deleted through `storage/v1.deleteBlob`. A failure there leaves the blob behind, unreadable since no record names it, and does not fail the delete ([src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).
- Records belong to the Thread that attached, so deleting a delegated Thread deletes the records of the images its tools attached. A reference to such an image in its parent then reads as nothing, unless another Thread of the Project attached the same bytes ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).
- An attach checks that its Thread exists and then commits the record with no condition on the Thread, outside the per-Project lock a Thread delete holds, so an attach racing a delete can write its record after the delete's commit ([src/host/services/attachments.ts](../../bundles/runtime/runtime/src/host/services/attachments.ts), [src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The runtime runs an attach and a collection of the same blob one at a time in its process, so a collection never deletes the bytes of a record being written ([src/host/store/attachments.ts](../../bundles/runtime/runtime/src/host/store/attachments.ts)).

### Sending images to the model

- The runner hands each prompt's session `attachment(id)`, which reads through the attachment store for the Thread's Project (`PromptSession.attachment`, `executor/v1`) ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)).
- Each run of the default executor (`executor/v1` 1.5.0, provided by `default`) asks `models/v1.inputModalities` (`models/v1` 1.2.0, defined in [`packages/bundle`](../../packages/bundle/README.md); `core` provides 1.4.0) what its model reads ([bundles/runtime/default/manifest.json](../../bundles/runtime/default/manifest.json), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [packages/bundle/src/contracts/basic/models.ts](../../packages/bundle/src/contracts/basic/models.ts), [bundles/foundation/core/manifest.json](../../bundles/foundation/core/manifest.json)).
- `core` answers from the model's entry in the cached catalog of exactly one candidate provider: a configured provider whose kind reports `catalogCapacity`, and that is the requested provider or, without one, has the model in its configured `models` list. It answers `undefined` when no such provider or more than one exists, when its catalog does not list the model, when the entry has no `inputModalities` array, or when the lookup fails. An entry whose `inputModalities` is `[]` answers `[]`, so that model reads no images ([bundles/foundation/core/src/host/models/capacity.ts](../../bundles/foundation/core/src/host/models/capacity.ts), [README](../../bundles/foundation/core/README.md)).
- The [`claude`](../../bundles/providers/claude/README.md) and [`openrouter`](../../bundles/providers/openrouter/README.md) kinds report `catalogCapacity`; the [`openai`](../../bundles/providers/openai/README.md) and [`codex`](../../bundles/providers/codex/README.md) kinds do not, so their models always answer `undefined` ([bundles/providers/claude/src/host/kind.ts](../../bundles/providers/claude/src/host/kind.ts), [bundles/providers/openrouter/src/host/kind.ts](../../bundles/providers/openrouter/src/host/kind.ts), [bundles/providers/openai/src/host/kind.ts](../../bundles/providers/openai/src/host/kind.ts), [bundles/providers/codex/src/host/kind.ts](../../bundles/providers/codex/src/host/kind.ts)).
- A model whose answer is `undefined` is treated as reading everything: it is offered every tool and sent every image ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- A tool declares what its results hand the model besides text in `resultModalities` (`tools/v1` 1.4.0, defined in [`packages/bundle`](../../packages/bundle/README.md)), such as `image` for `view-image`. The field is carried across processes, so a tool registered from another process declares it too ([packages/bundle/src/contracts/basic/tools.ts](../../packages/bundle/src/contracts/basic/tools.ts), [packages/bundle/src/runtime/envelope/values.ts](../../packages/bundle/src/runtime/envelope/values.ts), [bundles/features/files/src/host/tools/view-image.ts](../../bundles/features/files/src/host/tools/view-image.ts)).
- The executor leaves out every tool whose declared result modalities the model does not read. A tool that declares none stays offered ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Only the request a model reads changes; the stored history stays text. In each user or tool message whose content is text, every reference the Project holds becomes a text part ending in `[Image: <name>]`, where `<name>` is the name the attachment's record keeps, followed by an image part `data:<mediaType>;base64,<bytes>`, in the reference's place among the words. A reference the Project does not hold stays text ([bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).
- For a model that reads no images, nothing is read and every reference becomes `[Image: <name> (not shown: this model does not read images)]`, where `<name>` is the reference's alt text ([bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).
- A run reads each attachment once, however many requests carry it, and keeps the read's outcome for the whole run. When `session.attachment(id)` rejects, the request that carries the reference rejects, and so does every later request of the run that carries it, with no new read ([bundles/runtime/default/src/host/attachments.ts](../../bundles/runtime/default/src/host/attachments.ts)).
- Automatic and manual compaction (`compactThread`) read the history through the unwrapped language model, so a summary is written from the reference lines as text and never carries image bytes ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/runtime/default/src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts)).
- Each provider sends the image parts in its own format ([packages/llms/src/lib/providers/openai/body.ts](../../packages/llms/src/lib/providers/openai/body.ts), [packages/llms/src/lib/providers/codex.ts](../../packages/llms/src/lib/providers/codex.ts), [packages/llms/src/lib/providers/openrouter/body.ts](../../packages/llms/src/lib/providers/openrouter/body.ts), [packages/llms/src/lib/providers/claude/body.ts](../../packages/llms/src/lib/providers/claude/body.ts)):
  - OpenAI and Codex send `input_image` parts beside `input_text` parts, in a user turn and in a `function_call_output`; a tool result without images stays a plain string.
  - OpenRouter sends a user turn's images as `image_url` parts. Tool messages stay text; after a run of tool messages it sends one user message with the images those calls returned, each set introduced by ``The tool call `<id>` returned these images:``.
  - Claude sends `image` blocks with a base64 source, in a user turn and inside a `tool_result`.

### Tools that return images

- `view-image` of the [`files`](../../bundles/features/files/README.md) bundle reads a file from the sandbox, attaches it in the calling Thread, and answers the reference line; a file that is not an accepted image is refused by the attach, and that refusal is what the model reads ([bundles/features/files/src/host/tools/view-image.ts](../../bundles/features/files/src/host/tools/view-image.ts)).
- An image block of an MCP tool result of the [`mcp`](../../bundles/features/mcp/README.md) bundle, of an accepted type, is attached as `image.<subtype>` and becomes its reference line. A block of another type becomes `[An image (<type>) the conversation cannot show.]`, and a block whose attach refuses with `invalid_input` becomes `[An image (<type>) the Project refused to keep.]`. Any other attach rejection fails the whole tool call with that error. A result flagged `isError` still attaches its images, and the tool call fails with `mcp_tool_failed` whose message is the result's text, reference lines included. MCP tools declare no `resultModalities`, so they stay offered to a model that reads no images, and their images reach it as the not-shown note ([bundles/features/mcp/src/host/tools.ts](../../bundles/features/mcp/src/host/tools.ts)).

### In the window

- The composer takes the files whose MIME type starts with `image/` that the reader pastes into the prompt or drops anywhere in the conversation's editor, which holds the turns and the prompt; a paste outside the prompt is left to the editor. It attaches them in order, a file with an empty name as `image`, through `runtime.attachments/v1.attach` in the conversation's Thread, and only then writes its reference line from the name the attach answers, on a line of its own at the caret, or at the end of the prompt when the caret is not in the prompt, so an image dropped on a turn lands in the prompt ([src/client/components/organisms/conversation/plugins/attach-images.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx), [src/client/components/organisms/conversation/index.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/index.tsx)).
- A file larger than 5 MiB is refused in the window before it is sent, with `invalid_input` and `The image is larger than 5 MiB.`; a host `invalid_input` refusal keeps its code and the host's sentence; any other host failure keeps its code, except `internal`, with the generic host-failure message ([src/client/api/attachments-api.ts](../../bundles/desktop/chat/src/client/api/attachments-api.ts), [src/client/api/threads-api.ts](../../bundles/desktop/chat/src/client/api/threads-api.ts)).
- A failed attach shows a toast for that file, one per Thread and file name. Its title comes from the first error level whose code has a catalog entry: an `invalid_input` refusal, the window's or the host's, is titled "Request refused" with the refusal's sentence as its explanation, and an unknown Thread (`not_found`) "Not found". A failure with no such code, such as `internal`, is titled "Image not attached" (`attach_failed`) ([src/client/components/organisms/conversation/plugins/attach-images.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx), [packages/desktop/src/error-copy.ts](../../packages/desktop/src/error-copy.ts) ([README](../../packages/desktop/README.md)), [src/client/domain/error-catalog.ts](../../bundles/desktop/chat/src/client/domain/error-catalog.ts)).
- The prompt holds the image as a node whose text is the reference line, so the prompt sends, drafts and edits the line as text; text loaded back into the prompt turns each line that is only a reference into the image again ([src/client/components/organisms/conversation/nodes/attachment-image-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/attachment-image-node.tsx)).
- The prompt, every turn and a tool result that is only a reference line draw it as the image, as wide as the column at most. The image is read through `runtime.attachments/v1.read` in the conversation's Thread and kept once per attachment as a `data:` URL; a read that fails is not kept, and the next draw asks again. One the Project does not hold, or that cannot be read, shows `[<name>]`, where `<name>` is the reference's alt text. A reference with words around it on its line is drawn as text, and one inside a code fence as code ([src/client/components/molecules/attachment-image.tsx](../../bundles/desktop/chat/src/client/components/molecules/attachment-image.tsx), [src/client/domain/markdown.ts](../../bundles/desktop/chat/src/client/domain/markdown.ts), [src/client/components/organisms/conversation/nodes/markdown-blocks.ts](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/markdown-blocks.ts), [src/client/components/molecules/tool-item.tsx](../../bundles/desktop/chat/src/client/components/molecules/tool-item.tsx)).
- Queue rows show each reference of a reader's prompt as `[<name>]` and other sources' text as is; the queued-prompt block shows every item's references as `[<name>]`; the queue edit header shows the edited prompt's references as `[<name>]` ([src/client/domain/queue.ts](../../bundles/desktop/chat/src/client/domain/queue.ts), [src/client/components/organisms/conversation/nodes/queued-turn-node.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/nodes/queued-turn-node.tsx), [src/client/components/organisms/conversation/plugins/edit-queue-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/edit-queue-prompt.tsx)).

### Message size

- A desktop call carries an attachment whole, base64 in its envelope, over the host's `/doric/bridge` Socket.IO namespace. The host's Socket.IO server accepts messages of up to `SOCKET_MAX_HTTP_BUFFER_BYTES`, 8,039,084 bytes; a larger message drops the connection ([app/backend/doric-host/src/lib/socket-buffer.ts](../../app/backend/doric-host/src/lib/socket-buffer.ts), [app/backend/doric-host/tests/socket-buffer.test.ts](../../app/backend/doric-host/tests/socket-buffer.test.ts), [app/backend/doric-host/src/index.ts](../../app/backend/doric-host/src/index.ts), [app/backend/doric-host/src/lib/bridge/socket.ts](../../app/backend/doric-host/src/lib/bridge/socket.ts)).
