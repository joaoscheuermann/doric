# Feature: Host API

- Status: `implemented`

> **Branch `feat/grpc-processes`, from slice S62c3.** The host no longer
> serves an Express app, Socket.IO or the desktop bridge `/doric/bridge`; the
> public API is `doric.api.*` on the platform's gateway
> ([grpc-processes.md](../designs/grpc-processes.md), section 12). This doc
> still describes the REST and Socket.IO API the branch replaces; its rewrite
> belongs to phase 8 and group F of that spec.

## Problem

Clients other than the desktop need to drive a Doric host over the network: create Projects and Threads, send prompts, read a Project's workspace, open terminals, edit the configuration and the credentials, and follow a Thread's events live. They need one stable surface for that, which the host serves on its own listener and which keeps answering the same way when the bundles behind it change. The full route and event reference is in the host's README, under [REST API](../../app/backend/doric-host/README.md#rest-api) and [Socket.IO](../../app/backend/doric-host/README.md#socketio); this document describes how the API works across the bundles that serve it.

## Decisions

- The host's REST routes and Socket.IO namespaces are a public API: clients outside the desktop call them. Their reference, every path, status, request rule and payload, lives in the host's README.
- The API carries no version: no path and no namespace names one, and no payload carries one of its own; only the `type` of an event a bundle appends to a Thread's log, such as `comments.added/v1`, names that event's version. An answer or an event payload may gain optional fields, and a Thread's log may gain event types; a client ignores the fields and the types it does not know. No answer field is removed or renamed, and none changes its type or meaning, without a notice in the release notes of an earlier release. The rule covers what the host sends, not what it accepts: a request body with a key its route does not know is refused.
- The host owns the listener: its address, the bind, the close, and the generic desktop namespace `/doric/bridge`. It registers no product route. The `transport` bundle registers the REST routes and the namespaces `/status`, `/projects` and `/threads` through `doric.network/v1.register`, which hands it the native Express app, HTTP server and Socket.IO server, in process and never serialized. `transport` runs resident in the host's own process, the only one where those handles exist.
- The contracts of the feature bundles that `transport` calls (`files/v1`, `git.commands/v1`, `usage/v1`, `resources/v1`, `terminal/v1`) are optional for it: `transport` activates without them. A route that calls an absent one answers `500 internal_error`, and without `terminal/v1` every `/projects` subscription fails its snapshot and is disconnected; the other routes and `/threads` keep serving.
- `/projects` owns environments and `/threads` owns conversations; no other path serves a Project or a Thread. `POST /projects` takes a name only, never a prompt; a conversation starts with a Thread created under its Project.
- SSH private keys are sandbox state held by the sandbox provider and returned only in an HTTP answer. They are never stored in Doric's database, logged, included in a list, or sent through Socket.IO, and an SSH answer is never cached.
- PostgreSQL is the source of truth for Thread events: an event and the Thread's last sequence are committed before the event is sent live. There is no ordering of events across Threads.
- No route authenticates its caller, and provider URLs and credential references are set through the open `PUT /config`. A deployment keeps the listener on an isolated, trusted network.

## Current behavior and contracts

### The listener and who serves it

- The host builds one Express app, one HTTP server and one Socket.IO server on it, and binds them to `DORIC_HOST` and `DORIC_PORT`, by default `0.0.0.0:3000` ([app/backend/doric-host/src/index.ts](../../app/backend/doric-host/src/index.ts)). It offers the three handles to bundles through the platform contract `doric.network/v1`, described in the [`packages/bundle`](../../packages/bundle/README.md) README; a bundle never calls `listen` itself ([packages/bundle/src/contracts/network.ts](../../packages/bundle/src/contracts/network.ts), [packages/bundle/src/process/network.ts](../../packages/bundle/src/process/network.ts)).
- The [`transport`](../../bundles/foundation/transport/README.md) bundle's host part calls `doric.network/v1.register`, and its listener mounts the routers and opens the namespaces on the handles it receives ([bundles/foundation/transport/src/host/index.ts](../../bundles/foundation/transport/src/host/index.ts), [bundles/foundation/transport/src/kernel.ts](../../bundles/foundation/transport/src/kernel.ts)). The [`screen-relay`](../../bundles/features/screen-relay/README.md) bundle registers through the same contract, adds its own relayed path tree to the app and attaches an `upgrade` listener to the HTTP server ([bundles/features/screen-relay/src/host/index.ts](../../bundles/features/screen-relay/src/host/index.ts), [bundles/features/screen-relay/src/host/relay.ts](../../bundles/features/screen-relay/src/host/relay.ts)).
- `transport` stores nothing. Every answer is the answer of a contract call to the bundle that owns the data, resolved when the request arrives, so a request reaches the generation active at that moment: the [`runtime`](../../bundles/runtime/runtime/README.md) for Projects, Threads, prompts and events; [`files`](../../bundles/features/files/README.md) and [`git`](../../bundles/features/git/README.md) for workspace reads; [`terminal`](../../bundles/features/terminal/README.md), [`resources`](../../bundles/features/resources/README.md), [`usage`](../../bundles/features/usage/README.md) and [`host-config`](../../bundles/foundation/host-config/README.md); and [`core`](../../bundles/foundation/core/README.md) for `secrets/v1`, `models/v1` and `tools/v1` ([bundles/foundation/transport/src/host/services.ts](../../bundles/foundation/transport/src/host/services.ts), [bundles/foundation/transport/src/kernel.ts](../../bundles/foundation/transport/src/kernel.ts)).
- A call to a feature contract with no active provider rejects, so its route answers `500 internal_error` (`PUT /config` answers `503 configuration_rejected`). Every `/projects` snapshot reads `terminal/v1.list`, so without `terminal/v1` each `/projects` subscription receives `workspace:error` `replay_failed` and is disconnected ([bundles/foundation/transport/src/kernel.ts](../../bundles/foundation/transport/src/kernel.ts), [bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)).
- The desktop does not call this API: it reaches the host's contracts through the kernel's `/doric/bridge` namespace ([app/desktop/doric/src/connection/status.ts](../../app/desktop/doric/src/connection/status.ts), [app/desktop/doric/src/platform/bridge/host-bridge.ts](../../app/desktop/doric/src/platform/bridge/host-bridge.ts)).

### REST

- The routers are mounted in this order: the JSON body parser, the terminal routes at the root, then `/vms`, `/config`, `/credentials`, `/resources`, `/providers`, `/projects`, `/threads` and `/tools`, and last the error handler ([bundles/foundation/transport/src/host/app.ts](../../bundles/foundation/transport/src/host/app.ts)). The full list of paths and statuses is the host's [Routes](../../app/backend/doric-host/README.md#routes) table.
- A refusal answers `{ error: { code, message } }`. An unexpected failure answers `500 internal_error` with `The request could not be completed.` and never carries its cause ([bundles/foundation/transport/src/host/errors.ts](../../bundles/foundation/transport/src/host/errors.ts)). A Project, Thread or credential id that is not a UUID answers `400 invalid_<kind>_id`, except on `GET /projects/:id/terminals` and `POST /threads/:id/terminals`, which the terminal routes serve before the Project and Thread routers check the id ([bundles/foundation/transport/src/host/routes/input.ts](../../bundles/foundation/transport/src/host/routes/input.ts), [bundles/foundation/transport/src/host/app.ts](../../bundles/foundation/transport/src/host/app.ts)). Lists page by `limit` and `cursor`, and a page answers its items and, while more follow, the cursor of the next page. Every route that takes a body checks it against a strict schema, so a key the route does not know answers `422`; a route that takes no body ignores one ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts), [bundles/foundation/transport/src/host/routes/terminals.ts](../../bundles/foundation/transport/src/host/routes/terminals.ts), [bundles/foundation/transport/src/host/routes/providers.ts](../../bundles/foundation/transport/src/host/routes/providers.ts), [bundles/foundation/transport/src/host/routes/credentials.ts](../../bundles/foundation/transport/src/host/routes/credentials.ts), [bundles/foundation/transport/src/host/routes/config.ts](../../bundles/foundation/transport/src/host/routes/config.ts), [bundles/foundation/host-config/src/host/config/schema.ts](../../bundles/foundation/host-config/src/host/config/schema.ts)). The host's [Conventions](../../app/backend/doric-host/README.md#conventions) give the codes, the page rules and the record shapes.
- A JSON body over 100 KB, or one that is not valid JSON, is refused by the body parser and answers `500 internal_error` without `Cache-Control`. Every other answer carries `Cache-Control: no-store`: the terminal routes, mounted first at the root, set it on every request that passes through them ([bundles/foundation/transport/src/host/app.ts](../../bundles/foundation/transport/src/host/app.ts), [bundles/foundation/transport/src/host/routes/terminals.ts](../../bundles/foundation/transport/src/host/routes/terminals.ts)).
- **Configuration and credentials.** `GET /config` and `PUT /config` read and replace the configuration through `host-config/v1` ([bundles/foundation/transport/src/host/routes/config.ts](../../bundles/foundation/transport/src/host/routes/config.ts)). `/credentials` lists, creates, updates and deletes credentials through `secrets/v1`, and answers descriptions that never hold a secret ([bundles/foundation/transport/src/host/routes/credentials.ts](../../bundles/foundation/transport/src/host/routes/credentials.ts)).
- **Providers.** `GET /providers/kinds` answers the provider kinds `models/v1.kinds()` lists, each with its fields and, in `site`, an optional `https:` page a client may link to with the link's label. `POST /providers/models` answers the models of a kind's catalog for a provider not yet saved; the shapes are in the host's [Configuration and providers](../../app/backend/doric-host/README.md#configuration-and-providers) ([bundles/foundation/transport/src/host/routes/providers.ts](../../bundles/foundation/transport/src/host/routes/providers.ts), [packages/bundle/src/contracts/basic/models.ts](../../packages/bundle/src/contracts/basic/models.ts)).
- **Tools.** `GET /tools` answers each tool that `tools/v1.list()` lists for the active generation, with its name, optional description and settings; the shape is in the host's [Tools, resources and VMs](../../app/backend/doric-host/README.md#tools-resources-and-vms). The call carries no Project scope, so it lists the unscoped tools only and never a Project's own; listing runs no tool ([bundles/foundation/transport/src/host/routes/tools.ts](../../bundles/foundation/transport/src/host/routes/tools.ts), [packages/bundle/src/contracts/basic/tools.ts](../../packages/bundle/src/contracts/basic/tools.ts)).
- **Machines.** `GET /resources` reports the machine the host runs on, through `resources/v1` ([bundles/foundation/transport/src/host/routes/resources.ts](../../bundles/foundation/transport/src/host/routes/resources.ts)). `GET /vms` answers the sandbox provider's machines from `sandbox/v1.machines()`. `GET /vms/:id/ssh` answers the machine and its SSH access only while it is leased to a live Project: an unknown machine answers `404 vm_not_found` and a machine without access `409 vm_ssh_unavailable` ([bundles/foundation/transport/src/host/routes/vms.ts](../../bundles/foundation/transport/src/host/routes/vms.ts)).
- **Projects.** `POST /projects` takes `{ name }`, creates the Project through `runtime/v2`, and answers `202` with the Project and the link `ssh: { href: '/projects/<id>/ssh' }`. The Project routes also list, read, rename, color, terminate and delete Projects, and create and list a Project's Threads. Terminating a Project that has already ended answers its record again; deleting one that has not ended answers `409 project_active` ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts)).
- **SSH.** `GET /projects/:id/ssh` asks `runtime.lease/v1.ssh` for the Project's sandbox: `202 { status: 'pending' }` with `Retry-After: 1` while the sandbox is being acquired, `404 project_not_found` for an unknown Project, `410 project_ssh_expired` once the Project is terminated or failed, `409 project_ssh_unavailable` while it holds no sandbox (released, closing, or a sandbox without SSH), and otherwise the access, with its private key, and the link to `/vms/<vmId>/ssh`. The runtime reads the access from the live sandbox on each request ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- **Workspace reads.** `GET /projects/:id/files` lists one directory, `/tree` the whole workspace, or the directory its optional `path` names, as one nested tree, `/files/content` one file up to a byte cap with `truncated` and `binary` flags, and `/diff` one entry per Git repository of the workspace, with its root, its diff and its changes, untracked files included; `/changes`, `/files/diff` and `/resources`, the Project sandbox's own CPU and memory, read the same way. Each read answers the Project's lease state instead of acquiring a sandbox, so observing a Project never brings it up: `404 project_not_found`, `202 { status: 'pending' }` with `Retry-After: 1`, `410 project_files_expired` once the Project is terminated or failed, or `409 project_files_unavailable` while it holds no sandbox; `/resources` answers any other refusal with `409 project_resources_unavailable` ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). Workspace reads never log file content or diff bodies. A query `path` has at most 4096 characters and no NUL; a path that escapes the workspace root is refused with `422 invalid_project_path` ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [bundles/features/files/src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [bundles/features/git/src/host/changes.ts](../../bundles/features/git/src/host/changes.ts), [bundles/features/git/src/host/service.ts](../../bundles/features/git/src/host/service.ts)). The shapes are in the host's [Workspace reads](../../app/backend/doric-host/README.md#workspace-reads).
- **Threads.** The Thread routes read, change (name, working directory, and `providerId`, `model` and `effort`), terminate and delete a Thread; terminating an ended Thread answers its record again, deleting one that, or any of whose descendants, has not ended answers `409 thread_active`; deleting an ended Thread removes it and every descendant, and sends `thread:deleted` for each. A Thread an agent opened is deleted only once it is archived: before that, `DELETE /threads/:id` answers `204` and deletes nothing ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). `GET /threads/:id/usage` reads its usage through `usage/v1`; `GET /threads/:id/git` and `GET /threads/:id/branches` read its Git status and branches, and `POST /threads/:id/branches` switches its branch, through `git.commands/v1`. The routes also drive its prompts through `runtime.threads/v1`: `POST /threads/:id/prompt` queues a prompt and answers `202 { promptId }`; `steer` and `resume` act on a prompt of the Thread; `interrupt` stops the running prompt and pauses the Thread's queue until it is resumed; `rewind` takes `{ promptId, prompt }`, removes that prompt and every later one, and sends the new text, and answers `409 thread_busy` while the Thread runs or has queued input; `compact` condenses the history; the `/queue` routes read, edit, remove and resume the queued prompts ([bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts), [bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/contracts/rest-errors.ts](../../bundles/runtime/runtime/src/contracts/rest-errors.ts)). The rules behind each outcome are in the [`runtime`](../../bundles/runtime/runtime/README.md) README.
- **Replay.** `GET /threads/:id/events` answers the Thread's stored events after an optional exclusive `afterSequence` (default `0`; `400 invalid_event_cursor` otherwise) ([bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts)).
- **Records.** A Project record holds, among its fields, its identity, name, color, state and timestamps; a Thread record holds, among its fields, its place in the tree, its state and last sequence, its working directory and model choice, and in `result` the status and final answer text of its latest finished prompt. Beyond that answer, neither record holds message history, prompt text, events, a credential or an SSH key ([bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)). The full shapes are under the host's [Conventions](../../app/backend/doric-host/README.md#conventions).
- **Terminals.** `GET /projects/:id/terminals`, `POST /threads/:id/terminals` and the `/terminals/:id` routes list, open, read, write to, resize and stop terminal sessions through `terminal/v1` ([bundles/foundation/transport/src/host/routes/terminals.ts](../../bundles/foundation/transport/src/host/routes/terminals.ts)). The sessions themselves are described in the [terminal](terminal.md) feature doc.

### Socket.IO

- `transport` opens three namespaces on the host's Socket.IO server; every event flows from the host to the client ([bundles/foundation/transport/src/host/sockets/status.ts](../../bundles/foundation/transport/src/host/sockets/status.ts), [bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)):
  - `/status` takes no input and sends no event: a connection confirms that the host is reachable.
  - `/projects` takes `auth: { projectId }` and sends the Project, its Thread tree and its terminal sessions, then their updates; the terminal items come from one `terminal/v1.watchProject` stream per subscribed Project ([bundles/foundation/transport/src/host/sockets/terminal-feed.ts](../../bundles/foundation/transport/src/host/sockets/terminal-feed.ts)).
  - `/threads` takes `auth: { threadId, afterSequence? }` and sends the Thread's stored events after `afterSequence`, then its live events and updates.
- Subscription parameters travel in the handshake's `auth` only, never in the query. A handshake that fails is refused with `Invalid project subscription.` or `Invalid thread subscription.`. The check covers the parameters' shape; it authenticates no one ([bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)).
- A subscription receives only the updates that name its own Project or Thread. `thread:updated` and `thread:deleted` reach both the Thread's and its Project's subscribers ([bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)).
- A Thread subscription registers the socket before it reads anything, keeps what is published meanwhile, sends `thread:snapshot` with the stored events after `afterSequence`, and then sends each event as `agent:event` once and in sequence order, from the snapshot's last sequence on: an event at or below it is dropped, and an event after a gap waits for the missing one. Playback and live events therefore leave no gap and no repeat ([bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)).
- An event names its Project, Thread and prompt, its sequence, its type, its body and when it was created; the shape is in the host's [Replay](../../app/backend/doric-host/README.md#replay) ([bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)). The runtime commits each event to its storage, which the [`postgres`](../../bundles/foundation/postgres/README.md) bundle backs, before it publishes it, so a watcher sees an event only after its commit. Events other bundles append to a Thread reach `/threads` the same way, after the commit that takes them in ([bundles/runtime/runtime/src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts), [bundles/runtime/runtime/src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [bundles/runtime/runtime/src/host/appends.ts](../../bundles/runtime/runtime/src/host/appends.ts)).
- Live events have the stored log's granularity: a streamed answer arrives as the coalesced deltas its executor wrote, never token by token. The [`default`](../../bundles/runtime/default/README.md) executor holds a run of same-kind deltas for at most 250 ms, and writes it sooner when it reaches 64 KiB or anything else is written ([bundles/runtime/default/src/host/deltas.ts](../../bundles/runtime/default/src/host/deltas.ts)).
- A Socket.IO `Manager` holds one socket per namespace, so a client opens each watched Thread on a `Manager` of its own; `/status` and one `/projects` subscription can share one `Manager`. Closing a socket ends its subscription and drops what it kept ([bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)). A Thread reconnects with the last sequence it received as `afterSequence`; a Project reconnection receives its whole snapshot and tree again.
- A snapshot read that fails sends `workspace:error` with `replay_failed` and disconnects the socket ([bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)). The events and payloads of each namespace are listed in the host's [Socket.IO](../../app/backend/doric-host/README.md#socketio) and [Subscriptions](../../app/backend/doric-host/README.md#subscriptions) sections.

### Exposure

- No route and no namespace authenticates its caller; who can reach the port is the only control ([bundles/foundation/transport/src/host/app.ts](../../bundles/foundation/transport/src/host/app.ts), [bundles/foundation/transport/src/host/routes/credentials.ts](../../bundles/foundation/transport/src/host/routes/credentials.ts)). The host's [Network exposure](../../app/backend/doric-host/README.md#network-exposure) section says how to deploy it.
