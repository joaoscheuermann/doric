- Version 2 (2026-11-06): revised after the Scope, Critique and Comprehension reviews ([Evolution](#evolution)).

## Summary

The agent can answer with forms, tables and charts in an `openui-lang` fence, but it cannot draw a diagram. This concept adds four diagram components to the conversation library: `Flowchart` (flowcharts, and architecture with grouped regions), `SequenceDiagram`, `EntityDiagram` (ER or class) and `MindMap` (mind maps and trees). The agent writes them as ordinary OpenUI Lang components. While the fence streams, the diagram shows a text outline of its parts; when the fence closes, the app lays the diagram out once, draws it with Doric's theme, and lets the reader pan and zoom it.

The user would like Mermaid support, and also chose native components for how the model writes diagrams. The user chose native components as the only path in this version, laid out by ELK, with Mermaid decided again later against a measured baseline ([UD6](#decisions), [UD7](#decisions)). [Native components and Mermaid](#native-components-and-mermaid) compares the options.

## Problem

- **The library has no diagram.** The conversation library is react-ui's `openuiLibrary` plus the three question built-ins and an inline `Modal` (`bundles/features/openui/src/client/library.ts:58-61`). Its 82 components (measured) include nine charts and no graph, sequence, entity or tree component; the skill lists charts under "Charts (2D)", "Charts (1D)" and "Charts (Scatter)" (`bundles/features/openui/src/host/skills/openui.md:70-92`).
- **The agent has no other way to draw one.** No source under `bundles/` or `packages/` mentions Mermaid (search on 2026-11-06; only `docs/architecture/bundles.md:70` and `docs/architecture/bundles/process-isolation.md:30` use Mermaid fences in documentation). The only fence renderers registered with the chat are `openui-lang`'s and `papercraft`'s (`bundles/features/openui/src/client/index.ts:49`, `bundles/features/papercraft/src/client/index.ts:89`), so a `mermaid` fence in an answer is not drawn. An agent that explains an architecture, a request flow or a schema writes prose, ASCII art or Mermaid source the reader must render elsewhere.
- **draw.io is excluded.** A draw.io feature exists only on the unmerged branch `feature/doric-88-threads-drawio-diagrams` (commit `9c4a4629`, "draw.io diagrams in Threads with review, edit and export"). The user excluded draw.io and stated no reason in this request; this concept reuses nothing from that branch.

## Users

- **The reader**, a developer or designer in a Doric conversation, who asks how a system is built, how a request flows, how tables relate or how a topic breaks down, and reads the answer as a picture they can pan and zoom.
- **The agent**, which writes the diagram as OpenUI Lang in its answer and revises it with patches, as it does other UI.

## Scope

In this version:

- Four diagram components with their parts, added to the conversation library and to the `openui` skill (UD1, UD2). `SequenceDiagram` has `Participant`, `Message`, `Note`, `Fragment` and `Section` ([UD9](#decisions)). Phase 1 is `Flowchart`; the other three come in phase 2 ([UD13](#decisions)).
- Diagram components at the root of a program or in a `Stack` (P5).
- Automatic layout and the app's theme (UD2). While the fence streams, the outline grows part by part (P9).
- Pan and zoom inside the drawn diagram (UD4).
- Checks of diagram programs, shown in the fence's error card and sent to the agent through the existing validation feedback ([Errors in diagrams](#errors-in-diagrams)).
- `openui-lang` fences only (UD3).

## Non-goals

- Papercraft fences (UD3). Diagram components are not in papercraft's library; a `papercraft` fence that uses one gets `unknown-component`, as an `openui-lang` fence that uses a repository component does today (`bundles/features/openui/src/client/check.ts:20-22`).
- Clicks on nodes, links or actions from a diagram (UD4).
- Export to SVG, PNG, Mermaid, draw.io or any file (UD5).
- draw.io in any form (user).
- Positions, sizes, colors or routes written by the agent: the app always lays out.
- Editing a diagram by dragging. A diagram changes only through a new fence.
- Icons or images inside nodes ([UD11](#decisions)).
- Diagram components inside `Card`, `TabItem`, `AccordionItem`, `Carousel` or `Modal` (P5).
- Diagram types outside UD1: Gantt, state charts with nested states, C4, timelines. A simple state machine is a `Flowchart`.
- Durable view state: pan and zoom reset when a fence remounts, as papercraft's viewport does (`bundles/features/papercraft/src/client/surface/viewport.ts:9-10`) and as [U38](papercraft.md#decisions) rules for form values.

## Decisions

Made by the user on 2026-11-06, binding for the spec:

- **UD1 Diagram types.** Flowchart, sequence, architecture (grouped boxes or regions with connections), ER or class, mind map or tree. No draw.io; Mermaid support is desirable.
- **UD2 Native components.** The model describes a diagram with native OpenUI components in OpenUI Lang (diagram, node and edge style components), drawn with automatic layout and the app's theme.
- **UD3 Scope.** `openui-lang` fences only, not papercraft.
- **UD4 Interaction.** Pan and zoom; no click actions on nodes.
- **UD5 Export.** None for now.

Made by the user on 2026-11-06 when accepting the concept, in answer to Q1–Q8:

- **UD6 Mermaid (Q1).** No Mermaid for now. It is decided again later, with A1's Mermaid baseline ([Riskiest assumptions](#riskiest-assumptions)).
- **UD7 ELK (Q2).** ELK's license is accepted, and ELK is the layout engine. dagre and d3-hierarchy do not ship.
- **UD8 Blocked fences (Q3).** A fence whose wrapper is `inert` shows a static, fitted diagram. The renderer's `inert` does not change (P14).
- **UD9 Sequence parts (Q4).** `Note`, `Fragment` and `Section` are in this version, in phase 2.
- **UD10 Class diagrams (Q5).** Methods are plain strings.
- **UD11 Icons (Q6).** No icons in nodes.
- **UD12 Limits (Q7).** P6's limits: 100 nodes, 200 edges, 25 groups and 4 levels per `Flowchart`; 20 participants and 200 steps per `SequenceDiagram`; 60 entities and 120 relations per `EntityDiagram`; 300 topics and 8 levels per `MindMap`; labels cut at 120 characters.
- **UD13 Phases (Q8).** Phase 1: `Flowchart` with groups, the layout chunk, the shared pan and zoom helpers, drawing, the checks and the skill. Phase 2: `SequenceDiagram` (with `Note`, `Fragment`, `Section`), `EntityDiagram` and `MindMap`. Diagrams inside closed-union containers (slots) and Mermaid come only if the user asks later. Each phase ships when the user accepts it, as U48 rules for OpenUI's stages.

## Native components and Mermaid

UD1 calls Mermaid desirable and UD2 chooses native components. The two meet in four ways:

| Option                                            | What the agent writes                                     | What draws it                                                     |
| ------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| **N. Native only** (Mermaid deferred)             | `Flowchart(nodes, edges, …)` and the other components     | Doric's SVG drawing and a layout engine                           |
| **E. Mermaid as engine behind native components** | The same native components                                | Doric translates them to Mermaid text; Mermaid lays out and draws |
| **C. Native plus a `Mermaid(code)` component**    | Native components, or Mermaid source as a string argument | Native: as N. `Mermaid`: Mermaid                                  |
| **F. A separate ` ```mermaid ` fence**            | Mermaid source in its own fence                           | Mermaid                                                           |

F is outside UD3 and is listed only because it is where Mermaid fits best if the user wants it later ([UD6](#decisions)).

### Trade-offs

- **Weight.** Mermaid 12.3.0 is 10,369,898 bytes (2,016,618 gz) as one browser build and installs 116 packages, among them cytoscape, katex, chevrotain, d3 and elkjs (measured). The renderer chunk today is 5,594,179 bytes (1,080,638 gz) (`bundles/features/openui/dist/client/chunks/renderer.js`, built 2026-11-06), so Mermaid alone is almost twice the renderer. Doric builds each `src/client/chunks/*.ts` as one file (`packages/bundle/src/build/parts.ts:413-431`), and the conversation spec rejected esbuild's code splitting for the client ([conversation-openui.md](../designs/conversation-openui.md), D29 "Alternatives", line 703), so Mermaid would load as one file, not one diagram type at a time. The native path adds elkjs, 2,669,066 bytes (514,626 gz), and the diagram components' own code.
- **Lazy loading.** Every option can load its engine at a window's first diagram, as the renderer chunk loads at the first fence (`bundles/features/openui/src/client/folds.ts:48-55`). E loads Mermaid for every diagram; C and F load it only for a `Mermaid` component or fence.
- **Theming.** Native components draw SVG whose fills and strokes are CSS variables, so a theme switch repaints without layout. Mermaid writes colors into the SVG it returns, so every theme switch draws it again, and its theming engine "will only recognize hex colors and not color names" (https://mermaid.js.org/config/theming.html). Doric's base colors are hex (`packages/desktop/src/styles/tokens.css:5-23,101-118`), but its chart colors are `oklch(…)` (`:26-30,121-125`) and react-ui's surface tokens are `color-mix(…)` expressions (`bundles/features/openui/src/client/tokens.css:15-60`); E, C and F must convert those to hex.
- **Streaming.** OpenUI re-parses the fence on every chunk, closes pending strings and brackets, and drops references not yet defined ([openui.md](../designs/openui.md#d5-progressive-merge-of-patches-p4), D5). A native diagram therefore has a list of complete parts at every chunk, which the outline shows (P9). A Mermaid source string is cut at an arbitrary character while it streams and does not parse; E, C and F can show only the source until the fence closes.
- **Writing Mermaid inside OpenUI Lang (C).** OpenUI's parser accepts a literal line break inside a string (measured with lang-core 1.0.2). Doric does not: the conversation's check names statements line by line (`bundles/features/openui/src/client/check.ts:3-4,27-36`), and the progressive merge assumes one statement per line ([openui.md](../designs/openui.md#d5-progressive-merge-of-patches-p4), line 427). The Mermaid source must therefore be one line with `\n` escapes and every `"` escaped, which Mermaid labels use often (`A["label"]`). This removes much of the advantage of the model's familiarity with Mermaid.
- **Skill growth.** The 16 native components below add 2,164 characters to the generated prompt, 636 for phase 1's four (measured). A `Mermaid(code)` component adds one signature and a few rules, but the skill would then teach two ways to draw the same diagram, and the agent must choose.
- **Errors.** Native parts are checked by OpenUI's schema and by Doric's own check, and each error names its statement. Mermaid's parse errors name a line inside the Mermaid source; under C that is a line inside one string argument.
- **Coverage.** Mermaid draws many more types than UD1 asks for (state, Gantt, C4, …), and models know its syntax well. Native components cover exactly UD1.
- **CSP.** The packaged shell policy has no `'unsafe-eval'` (`app/desktop/doric/src/platform/protocol/csp.ts:13-26`). The Mermaid build contains one `new Function(` (d3-dsv's row converter) and `Function("return this")` fallbacks after `global`/`self` checks (measured). They may never run for UD1's diagram types, but only a packaged build proves it. The elkjs and dagre builds contain neither (measured).
- **Security.** Native components draw labels as React text nodes, so a label cannot inject markup. Mermaid returns an SVG string inserted as markup; it needs `securityLevel: 'strict'` and its DOMPurify pass. Its `sandbox` level renders in an iframe, which the shell's `frame-src` forbids except for the papercraft frame (`csp.ts:10-11`).
- **License.** Mermaid 12.3.0 declares `elkjs ^0.12.0` as a dependency (`npm view mermaid dependencies`), so options C and F install elkjs too; the license question UD7 settled was not specific to N.

### Recommendation

- **P1. Option N in this version.** Native components are the only way to write a diagram. They meet UD2, show their parts while streaming, follow the theme without a second draw, and add one layout file loaded only at a window's first laid-out diagram.
- **P2. E is rejected** ([Alternatives considered](#alternatives-considered)).
- **P3. Mermaid is a later decision, not a later default** (UD6). If the user brings Mermaid in later, the author recommends F, a `mermaid` fence with its own renderer, over C: F avoids the escaping problem and keeps Mermaid's own line numbers in errors. F needs UD3 revised; C fits UD3 as it stands. [A1](#riskiest-assumptions)'s test gives that later decision a Mermaid baseline.

## Proposed component vocabulary

At concept level: names, arguments and their meaning. The spec fixes schemas, defaults and limits.

### Common rules

- **P4 Parts name each other by string id.** `Edge("api", "db")` names nodes by their `id`, as Mermaid does. Ids are unique within one diagram. The alternative, edges that reference node statements (`Edge(api, db)`), is listed under [Alternatives](#alternatives-considered).
- **P4 Lists are arrays of inline calls, provisionally**, for example `nodes = [Node("api", "API"), Node("db", "Postgres", "cylinder")]`, so a diagram is a few statements. A patch rewrites the whole list statement, and a patch's list appears only once its line is complete, because a patch merges completed lines only ([openui.md](../designs/openui.md#d5-progressive-merge-of-patches-p4), D5). The spec measures output tokens of this form against one statement per part, for a first write and for a patch, and keeps the cheaper.
- **No coordinates, sizes or colors** in any part. `height?: number` on each diagram component sets the drawing's height in pixels, as react-ui's charts do (`src/host/skills/openui.md:71-73`); the width is the fence's.
- **P5 Where a diagram goes.** At the root, or as a child of a `Stack`, whose children are `any[]` (`src/host/skills/openui.md:21`). The five containers with a closed union do not list diagram components in this version, so the skill does not offer them there. Without a slot the parser still accepts a diagram inside a `Card` (measured: no error, the child is the diagram element); only the prompt's signatures change. Slots wait for a later phase ([UD13](#decisions)).
- **Parts belong to their diagram.** A part draws nothing on its own, as `AskOption` draws nothing (`library.ts:18-24`). A part outside its diagram parses without error (measured: a `Topic` in a `Stack`), so the check reports it ([P12](#errors-in-diagrams)).
- **P6 Limits.** 100 nodes, 200 edges, 25 groups and 4 levels of group nesting per `Flowchart`; 20 participants and 200 steps per `SequenceDiagram`; 60 entities and 120 relations per `EntityDiagram`; 300 topics and 8 levels per `MindMap`; labels cut at 120 characters. At each limit the measured layout takes at most 244 ms ([Layout engines](#layout-engines-and-dependencies)).

Recursive zod schemas work with the prompt builder, which printed the signatures above, and with the parser, which drops children not yet written and lists them in `meta.unresolved` (both measured); drawing them is not measured ([A5](#riskiest-assumptions)).

### Where and when layout runs (P10)

- **Once per revision**, when the fence is `closed` or `unterminated`, after the document's fonts have loaded, never while it streams (P9). A long conversation lays out each diagram fence once when it mounts, one at a time.
- **In a second client chunk on the window's main thread.** `packages/bundle` already builds every `src/client/chunks/*.ts` into its own file a client can import on demand (`packages/bundle/src/build/parts.ts:407-438`). The renderer chunk imports the layout chunk at the first `Flowchart`, `EntityDiagram` or `MindMap` it draws, as the entry imports the renderer chunk (`folds.ts:48-55`); a `SequenceDiagram` never loads it (G5).
- **Interface.** The layout chunk takes one graph — boxes with their measured sizes, their nesting, the connections, the direction and the algorithm — and returns box positions, group bounds and edge routes. It keeps ELK behind that one function, so ELK's options stay inside it and the drawing code does not import ELK.
- **Main-thread cost.** At P6's limits a layout took at most 244 ms in Node, once per revision. A browser window is not measured ([A2](#riskiest-assumptions)); a worker is the fallback ([Alternatives](#alternatives-considered)).
- **Same picture.** ELK runs with a fixed seed on labels measured with the fonts already loaded, so the same program draws the same picture again on the same machine and font set ([A4](#riskiest-assumptions)). Positions are never stored, so a picture that differs on another machine changes nothing.

## Drawing, theme and pan and zoom

- **P11 SVG drawn by React.** Boxes, edges and labels are SVG elements whose fills and strokes are CSS variables of Doric's theme, so a theme switch repaints without a new layout. Box sizes come from the labels, measured with the font the diagram is drawn in.
- **Colors.** Regions are told apart by their border and label, not by hue: the theme's five chart colors are one hue (about 277°) at five lightness steps (`packages/desktop/src/styles/tokens.css:26-30,121-125`), too close to separate four nesting levels, and the darker steps sit near the light theme's text color (`--foreground: #333333`, `:6`). Regions use the theme's neutral surface tints with increasing strength per level, labels use the theme's text colors on them, and G3 (a)'s contrast test checks every label on every fill in both themes. Chart colors are used only for lines and markers.
- **Initial view.** The drawing fits the box: scaled down to fit the width and `height`, never scaled above 100 %.
- **P13 Gestures**, as papercraft's canvas node in the conversation behaves (`bundles/features/papercraft/src/client/surface/gestures.ts:411-424`): the wheel scrolls the conversation until the reader clicks the diagram; after that click the wheel pans it; Ctrl or ⌘ with the wheel, and trackpad pinch, zoom at the pointer whether or not it was clicked; a drag pans; buttons zoom in, zoom out and fit; the scale stays between 25 % and 400 % (`viewport.ts:22-23`). The diagram gives the wheel back to the conversation when it loses focus or on Escape (`gestures.ts:511,623-627`).
- **P13 Shared code, not a copy.** The pure viewport helpers of `bundles/features/papercraft/src/client/surface/viewport.ts` — the viewport type, scale clamping, zoom at a point, fit to bounds, surface-to-content conversion and the CSS transform (`:13-104`, without the grid helpers `:106-154`) — and the wheel rule of `gestures.ts:411-424` move to `packages/desktop`, which both bundles already depend on (`bundles/features/openui/package.json:20`, `bundles/features/papercraft/package.json:21`), with their tests from `bundles/features/papercraft/tests/client/viewport.test.ts`. Papercraft imports them from there. `fit.ts` stays in papercraft: its `useFit` is tied to papercraft's frame scene (`fit.ts:31-40`). The canvas gesture machine (`useCanvasGestures`, `gestures.ts:444`) stays too; the diagram needs only click-to-focus, drag, wheel and buttons.
- **Blocked fences.** The renderer wraps every program in an element that is `inert` whenever actions are off: in an agent Thread, while streaming, when unterminated, in a revision that is not the latest, and while a click is being sent (`bundles/features/openui/src/client/chunks/renderer.ts:161-165,218-234,322`). `inert` blocks all pointer and keyboard input, so pan and zoom do not work in those fences. P14: keep `inert` and rely on the fitted initial view there; the latest closed revision in the main Thread pans and zooms ([UD8](#decisions)).
- **Accessibility.** The SVG has `role="img"` and an `aria-label` naming the diagram's type and its counts of boxes and connections; the outline follows it as visually hidden text.

## Streaming and partial programs

What OpenUI already does ([openui.md](../designs/openui.md#d5-progressive-merge-of-patches-p4), D5): revision 1 is re-parsed from the raw body on every chunk, with pending strings and brackets closed and references not yet defined dropped; a patch merges only its completed lines. A diagram component receives its parts as element nodes; each carries `partial`, true while "the parser hasn't received all tokens for this node yet" (`node_modules/@openuidev/lang-core/dist/index.d.mts:166-170`, and `SubComponentOf.partial`, `:535-540`). The parse result lists missing references in `meta.unresolved` (`:339-340`). A component reads whether its fence streams with `useIsStreaming()` (`bundles/features/openui/node_modules/@openuidev/react-lang/dist/index.d.mts:150-153`).

Options weighed for drawing while the fence streams:

| Option                                                        | Work                                                                                                                                      | What the reader sees                                 |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Lay out again on every new part                               | One layout per chunk with a change; one in flight, stale results discarded; order-preserving options and transitions against jumps; refit | The picture grows, and earlier boxes may move        |
| Lay out after each completed statement                        | A component sees `partial` per element, not when a statement's line completes; for a patch, D5 already holds back the incomplete line     | With P4's one-line lists, the same as the next row   |
| **The outline while streaming, one layout at close** (chosen) | One layout per revision                                                                                                                   | The outline grows part by part; the picture at close |

Drawing while the answer streams is the generative UI's existing behavior ([generative-ui.md](generative-ui.md#summary)); UD2 does not ask for a laid-out picture before the fence closes. The chosen option keeps the existing behavior for text, meets G4 with the outline, and removes the relayout machinery and its jumping boxes.

P9, in substance:

- **While streaming**, the diagram shows its outline: each complete part (not `partial`) in program order, with the counts so far. An edge, message or relation appears once both its ids are in the outline.
- **At close**, or when the fence is cut off, the diagram is laid out once and drawn; the outline stays as its accessible text.
- **A patch** shows the outline of the merged program while it streams; the earlier revision's fence keeps its picture.
- **Errors** are neither shown nor reported while the fence streams, as today (`renderer.ts:137-148`).

## Errors in diagrams

How errors flow today ([openui.md, D18](../designs/openui.md#d18-validation-feedback-u19)): every drawn fence revision has one error reporter (`src/contracts/report.ts:125-160`). At the first `onError` after the fence is `closed` or `unterminated`, the reporter sends once (`report.ts:133-135`): the conversation's own `check` (`check.ts:121-128`), which is `programCheck` plus the question checks, and OpenUI's errors turned into reported errors by `map` (`check.ts:130-144`). The host turns a report into a `validation` message to the agent, at most 3 per prompt not started by validation (`src/host/validation.ts:1-7`). The reader's card under the fence shows `programCheck`'s lines and OpenUI's own errors (`renderer.ts:137-148`), keeping the first line of each code and statement (`report.ts:92-98`).

- **P12 One reading per diagram type.** A function reads a diagram component's props into its diagram model: the parts that can be drawn and the findings. The drawing and the check both use it, as `questionOf` serves both the question form and the check (`question/ask-form.tsx:129`, `check.ts:110`). Findings:
  - a duplicate id (the first part with the id is drawn);
  - an edge, message, relation or note naming an id the diagram does not have (not drawn);
  - a node naming a group that does not exist (drawn outside any group); a group whose `parent` chain loops or nests deeper than the limit (drawn at the top level);
  - a diagram with no node, participant, entity or topic (the outline says so);
  - a diagram over its limits (the parts within the limits are drawn; the rest are counted in the outline);
  - a part outside its diagram, for example a `Node` in a `Stack` (draws nothing).

  The engine therefore only ever receives unique ids, existing endpoints and a tree of groups.

- **Reported through `programCheck`**, which parses the program with the conversation library (`library.ts:65-69`), finds each diagram component and reads it. So the findings reach both the card and the agent. Each is a `runtime-error`, the code the check already uses for its own findings (`check.ts:72-77`), on the statement whose line holds the call. Because the card keeps one line per code and statement, the findings of one statement form one line: their count and the first findings, each naming the ids, cut at 300 characters. `openui.programs/v1` and the host's texts (`validation.ts:26-43`) do not change.
- **Not reported: layout and load failures.** If ELK throws on a diagram model, or the layout chunk does not load, the diagram shows its outline with one line saying the diagram could not be drawn, and nothing goes to the agent. These failures depend on the reader's machine and Doric's code, not on the program; the agent could fix nothing, and a report would invite it to cut a correct diagram. The reporter could not carry them anyway: it has already sent at the first `onError` (`report.ts:133-135`). A failed renderer chunk load is likewise shown and not reported (`fence-element.tsx:36,140`).

- **E. Mermaid as the engine behind native components.** Rejected (P2): it pays Mermaid's 10.4 MB for every diagram, translates each component back into Mermaid text that must escape every label, draws nothing before the fence closes, draws again on every theme switch, and reports Mermaid's errors on text the agent never wrote.
- **C. A `Mermaid(code)` component beside the native ones.** Not in this version (UD6). Trade-offs in [Native components and Mermaid](#trade-offs): one-line escaped source, Mermaid's weight and CSP check, two ways to draw the same diagram.
- **Mermaid only**, through C or F, with no native components. Rejected by UD2.
- **F. A ` ```mermaid ` fence.** Outside UD3; the author's preferred carrier for Mermaid if the user brings it in later (P3, UD6).
- **draw.io.** Excluded by the user.
- **Edges that reference node statements** (`Edge(api, db)`). Not chosen (P4): each node must then be its own statement, which costs a name per node, and every edge carries its two nodes as values. Unresolved references would hide edges to unwritten nodes for free, but the outline does the same with string ids.
- **One generic `Diagram` component** for every type. Not chosen: sequence, entity and tree diagrams have parts a graph does not (steps in order, fields, recursion), and the model chooses better between named components with their own descriptions.
- **Relayout while streaming.** Not chosen ([Streaming](#streaming-and-partial-programs)): its machinery serves a picture before close that no decision asks for.
- **ELK in a client worker.** Not chosen for now: no bundle has a client worker yet, so it would be the first; it needs a lifetime, a timeout and a failure path of its own; and `elk.bundled.js`, evaluated in a worker, sets `self.onmessage` to its own dispatcher (elkjs 0.12.1 `lib/elk.bundled.js:6601`, in the copy installed for the measurement; the repository's 0.11.1 copy, `node_modules/elkjs/lib/elk.bundled.js:6430`, also skips its export there), so a worker would drive `elk-worker.min.js` through `elk-api.js`'s `workerFactory` (`node_modules/elkjs/lib/elk-api.js:31-50`, 0.11.1). It stays the fallback if A2's browser measurement exceeds its budget; `packages/bundle` builds `src/client/workers/*.ts` (`parts.ts:292,386-402`) and the packaged policy allows `worker-src 'self'` (`csp.ts:17`).
- **dagre for everything.** Not chosen (UD7): 40 times smaller than ELK, but with edges through boxes at every measured size.
- **React Flow (`@xyflow/react`)** as renderer and viewport. Not chosen: 347 KB for an editor whose dragging and selection would be turned off, still without a layout engine, and no fit for sequence diagrams. The shared viewport helpers (P13) cover pan and zoom.
- **Graphviz compiled to WebAssembly.** Not chosen: without `'wasm-unsafe-eval'` in `script-src`, "WebAssembly is blocked from loading and executing on the page" (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src). The shell policy has been extended before (`csp.ts:1-6`), so adding it is possible, but it would let any script in every window compile WebAssembly, and ELK needs no policy change. Its size was not measured.
- **Positions written by the model.** Rejected: models place boxes poorly, every edit moves everything, and coordinates cost tokens.

## Risks

- **R1 Weight per window.** The layout chunk adds 2.67 MB of JavaScript to a window at its first laid-out diagram. Mitigation: loaded only on demand (G5), never for sequence diagrams.
- **R2 Main-thread pauses.** A layout at the limits pauses the window for up to about 250 ms (measured in Node), once per revision, and once per mounted fence when a long conversation opens. Mitigation: P6's limits, one layout at a time, A2's test and the worker fallback.
- **R3 Unreadable large diagrams.** A fitted 100-node diagram may be small. Mitigation: P6's limits, a finding that asks the agent to split the diagram, zoom.
- **R4 Font metrics.** A label measured with one font and drawn with another overflows its box. Mitigation: layout after the fonts load, with the drawing's own font.
- **R5 Pan and zoom blocked in `inert` fences** (P14). Mitigation: the fitted view; the renderer's `inert` stays (UD8).
- **R6 Wheel capture.** A diagram that pans or zooms on a plain wheel event takes the conversation's scroll. Mitigation: papercraft's rule (P13).
- **R7 Medium confusion.** The agent may use `Steps` or a `Table` where a `Flowchart` fits, or a diagram for numbers. Mitigation: P7's rules; G1 measures it.
- **R8 Model-written text.** Labels are untrusted text. Mitigation: React text nodes only, no markup, no links (UD4).
- **R9 Engine churn.** elkjs is compiled from Java; its errors are hard to read. Mitigation: pin the version and keep ELK behind the layout chunk's one function.
- **R10 Skill text.** The diagram rules may collide with OpenUI's own rules or with a react-ui upgrade that regenerates the skill. Mitigation: the skill-text test fails until the skill is regenerated, as today.
- **R11 Late picture.** The picture appears only when the fence closes; a long diagram fence shows its outline for several seconds. Mitigation: the outline (G4); relayout while streaming stays an alternative if the user wants the picture earlier.
- **R12 Shared viewport code.** Moving papercraft's helpers into `packages/desktop` touches papercraft. Mitigation: the helpers are pure and move with their tests; papercraft's behavior does not change.

## Measurement method

All on 2026-11-06, in throwaway folders outside the repository, except the prompt and parser checks, which ran in `bundles/features/openui` against its installed packages and were deleted after.

- **Sizes.** Each package installed alone at the listed version (`npm i`), "packages installed" as npm reported; one entry file importing the package's main export (for elkjs, `elkjs/lib/elk.bundled.js`; for Mermaid, `mermaid` with `initialize({startOnLoad: false})`; for React Flow, `ReactFlow`, `Background`, `Controls` with React external), built with the repository's esbuild as stated under [How to read this document](#how-to-read-this-document). `new Function(` and `Function("` counted with `grep -F` in the outputs.
- **Layout.** Graph generator with a seeded Park–Miller generator (seeds 7919 × 1…5): groups created in order, each nested under a random earlier group of lower depth with probability 0.5; each node in a random group with probability 0.85; each edge from a random node to a node of its own group with probability 0.6, otherwise to any node, no self-loops or duplicates. ELK: `algorithm layered`, `direction DOWN`, `hierarchyHandling INCLUDE_CHILDREN`, `edgeRouting ORTHOGONAL`, `json.shapeCoords ROOT`, `json.edgeCoords ROOT`, `randomSeed 1`, group padding 24 top, 12 elsewhere. dagre: compound graph, `rankdir TB`, `nodesep 30`, `ranksep 40`, group `paddingTop 24`. One warm-up, then 5 timed runs. Defects: an edge segment crossing a box other than its ends shrunk by 2 px (Liang–Barsky clipping); a box intersecting a group it is not a member of; two groups, neither inside the other, intersecting; two boxes intersecting.
- **Skill growth.** `openuiLibrary.extend({components: {add: […]}})` with exactly the 16 signatures and descriptions of the [Components](#components) table, and `prompt` with `openuiPromptOptions`, `inlineMode`, `editMode` and `openuiAdditionalRules`, without Doric's rules; growth is the difference in characters from the same call without the components (38,211). Phase 1 is `Node`, `Edge`, `Group`, `Flowchart`.
- **Parser.** `createParser(library.toJSONSchema(), library.root).parse(…)` on programs with a literal line break inside a string, a `MindMap` with unwritten `Topic`s, a `MindMap` in a `Card` with and without a slot, and a `Topic` in a `Stack`; `meta.errors` and the resulting element tree read.

## Current behavior and contracts

Both phases are built in the `openui` bundle (manifest 2.2.0). Nothing in the app draws Mermaid (UD6).

- **Components** (`src/client/diagram/definitions.ts`). The conversation library adds four diagram types and their parts.
  - `Flowchart(nodes, edges?, groups?, direction?, height?)` with `direction` `down` or `right`; `Node(id, label, shape?, group?)` with `shape` `box` (default), `round`, `diamond`, `circle` or `cylinder`; `Edge(from, to, label?, line?, arrow?)` with `line` `solid` or `dashed` and `arrow` `end` or `none`; `Group(id, label, parent?)`. The skill orders the lists `nodes`, `groups`, `edges`.
  - `SequenceDiagram(participants, steps?, height?)` with `Participant(id, label)`, `Message(from, to, text, kind?)` (`call` by default, `reply` dashed, `async`), `Note(text, over)`, `Fragment(kind, sections)` (`loop`, `opt`, `alt`, `par`) and `Section(label, steps)`; `steps` hold `Message`, `Note` and `Fragment`.
  - `EntityDiagram(entities, relations?, notation?, direction?, height?)` with `notation` `er` (default) or `class` and `direction` `down` (default) or `right`; `Entity(id, name, fields?, methods?)` (methods as plain strings); `Field(name, type?, key?)` (`pk`, `fk`, `pk-fk`, `unique`); `Relation(from, to, kind?, label?, fromCount?, toCount?)` with `kind` `association` (default), `inherits`, `implements`, `composition`, `aggregation` or `dependency`, and counts `1`, `0..1`, `*`, `1..*`. Under `er`, every relation is drawn as an association and methods are dropped, both without a finding ([FR19](../designs/openui-diagrams-phase2.md#risks)). Under `class`, the drawing puts a kind's marker at `to`: `A inherits B` means A is a subtype of B, and the whole of a composition or aggregation is `to` (F15); the skill's fifth rule says so.
  - `MindMap(root, layout?, height?)` with `layout` `right` (default) or `down` and recursive `Topic(label, children?)`. Recursion is written with zod getters, so the skill prints `Topic[]` and `(Message | Note | Fragment)[]`.
- **Limits.** Flowcharts: 100 nodes, 200 edges, 25 groups, 4 levels of group nesting; a group nested deeper moves to the top level. Sequences: 20 participants and 200 steps (messages, notes and fragments, numbered depth-first). Entity diagrams: 60 entities and 120 relations; fields and methods are not limited. Mind maps: 300 topics, 8 levels. Every type: labels of 120 characters and ids of 1–64 characters. Each departure is a finding: parts beyond a count limit are not drawn, a label is cut to 120 characters, and a part whose id is outside 1–64 characters is not drawn. A sequence part in the wrong nested list (for example a `Section` straight in `steps`), a diagram inside another diagram, and a part outside its diagram type also get a finding; the check is driven by one table of the four types (`DIAGRAM_PARTS`).
- **Streaming and layout.** While a fence streams, the diagram shows a generic outline of its parts; once its revision closes it is laid out once. Every type shares the reading (`read.ts`), the drawn-state hook (`view.ts`, `useDrawn`) and `DiagramFrame`. Flowcharts and entity diagrams are laid out by ELK layered with orthogonal routing, and mind maps by ELK `mrtree`, in the layout chunk `client/chunks/layout.js`, loaded once per window on first use. An entity diagram's counts are ELK end labels with marker spacing; a `class` diagram's `right` layout is its `down` layout transposed, because ELK's own `RIGHT` overlaps end labels, while `er` keeps ELK's `RIGHT`. A `SequenceDiagram` is laid out by Doric's own `sequence-layout.ts` (`layoutSequence`), not by ELK, so it never loads the layout chunk. A failed layout or a chunk that did not load shows a failed state and is not reported to the agent.
- **Drawing.** Interactive fences pan and zoom with the shared helpers of `desktop/ui/viewport` (also used by papercraft's canvas); a diagram is static and fitted, with no controls, when `blockedReason(view, latest)` gives a reason (an agent Thread, a streaming or unterminated fence, a revision that is not the latest). While a click of the fence is sending, the wrapper is also `inert`, but the diagram stays interactive and keeps its viewport.
- **Errors.** Diagram findings (for example, parts cut at a limit) become one numbered `runtime-error` line per statement, in both `programCheck` (the error card) and `check` (the report to the agent). `mergeDiagramErrors` appends them to the first `runtime-error` of the same statement when one exists; otherwise, the usual case, they are a line of their own.
- **Skill.** The `openui` skill's diagram rules are five rules for the four types, replacing phase 1's four; compared with the last commit, the diagram components and rules grow the skill by 3,847 characters (Flowchart signatures 626, phase 2 signatures 1,624, rules 1,597). The rules: when to use each type; each type's statement order, with a mind map's first-level branches as statements; ids and references; a patch rewrites only the changed statements, each written whole; and a class relation's direction.
- **Contracts.** `openui.programs/v1`, `openui.questions/v1`, `openui.answered/v1` and `openui/contracts` are unchanged. The renderer's fence context gains `interactive` and `layout`; `ConversationFence` takes an optional `layout` prop for tests and stories.
- **Dependency.** `elkjs` 0.11.1, pinned, EPL-2.0. The layout chunk keeps ELK's notices and a source statement. The license texts are to ship from a separate `packages/bundle` change; phase 1 may ship before it ([FR12](../designs/openui-diagrams.md#risks), an accepted risk).
