# Feature: Projects and Threads

- Status: `implemented`

## Problem

The reader works in Projects. A Project needs one [sandbox](sandboxes.md), which is scarce: the pool holds a bounded number, and acquiring one takes time. Inside a Project, the reader and the agents hold several conversations at once, each with its own history, its own queue of inputs and its own working directory, and each must run without waiting for the others. Work must survive a host that stops, crashes or hands over to a new generation of bundles: an accepted prompt is neither lost nor run twice, and a Project or Thread the reader terminated never comes back.

## Decisions

- The runtime keeps a Project as a `runtime.project/v1` document, a Thread as a `runtime.thread/v1` document and its provider history as `runtime.history/v1` documents, on `storage/v1`, which the [`core`](../../bundles/foundation/core/README.md#storagev1) bundle provides ([bundles/foundation/core/manifest.json](../../bundles/foundation/core/manifest.json)); their shapes are in the runtime README's [Data and storage](../../bundles/runtime/runtime/README.md#data-and-storage). Each Thread's events go to the stream `runtime.thread.events/<threadId>`. The Thread's `pending` projection and its usage aggregate are folded into the same commit as the event that changes them ([src/contracts/storage.ts](../../bundles/runtime/runtime/src/contracts/storage.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- Every write of a runtime document is one `storage/v1` commit that expects the revision the change was computed from. Writes to one document run one at a time in the process. A revision conflict or a sequence conflict drops the cached document, reads it again and computes the change again. A write makes at most 8 commit attempts that end in a revision conflict and, separately, at most 64 that end in a sequence conflict before it fails, so that appends other bundles make to a Thread's stream never use up the budget of revision conflicts ([src/host/store/documents.ts](../../bundles/runtime/runtime/src/host/store/documents.ts)).
- Deleting a Project, or a Thread with its subtree, removes every record in one atomic commit; the attachment blobs no record names any more are collected after that commit. A deletion larger than the storage batch limit is refused with `limit_exceeded` before anything is written; the runtime logs `Deletion exceeds the storage batch limit` and passes the refusal on ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- `onProjectReadyHook` and `onProjectClosingHook` fire without being awaited, after the `ready` and the `cancelling` commit of a Project; a failing handler is ignored. `onThreadsClosingHook`, `onPromptStartedHook` and `onThreadCwdChangedHook` are awaited by the runtime, except that resetting a working directory missing from a reacquired sandbox fires `onThreadCwdChangedHook` without awaiting it, since the reset holds the Project's lock that a handler's own calls need. A handler's failure never fails the operation that fired it. The inputs and firing points are in the runtime README's [`runtime.hooks/v1`](../../bundles/runtime/runtime/README.md#runtimehooksv1) ([src/contracts/hooks.ts](../../bundles/runtime/runtime/src/contracts/hooks.ts), [src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The [`postgres`](../../bundles/foundation/postgres/README.md) bundle measures the filesystem at `DORIC_STORAGE_PATH` (the current directory by default) and makes no database round trip; the runtime applies the policy: execution pauses when 10 percent or less of the blocks are available, when the measurement reports no blocks, when it is missing or when it fails. An error carrying PostgreSQL's `53100` or `ENOSPC`, as a code or in its message, or a message with "no space left on device", is treated the same way ([bundles/foundation/postgres/src/host/storage/health.ts](../../bundles/foundation/postgres/src/host/storage/health.ts), [src/host/domain/storage-pressure.ts](../../bundles/runtime/runtime/src/host/domain/storage-pressure.ts)).
- A Git credential never fails a Project or a prompt: a credential that cannot be chosen, or a write into the sandbox that fails, is logged as a warning and the Project goes on, as [Git in the sandbox](credentials.md#git-in-the-sandbox) describes ([src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts)).
- Recovery runs once per runtime process: a second call answers the summary of the first without doing the work again. A host stop is idempotent ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts)).
- Each Project records the runtime process that holds it, as `{ generation, incarnation }`. A process claims a Project before it brings it back, and the claim fails while another live process holds it; the Project then waits in standby in this process. Every lifecycle change of a Project in standby (termination, deletion, rename, color, Thread creation, rename, termination, deletion and rewind, a Thread's execution, the queue read) runs only after this process adopts it, and so do the operations that need its live runtime (input, resume, `withLease`, `ssh`). Reads of stored records and events do not wait. Recording or clearing the owner never moves `updatedAt`. A host without generations records no owner ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)).
- A draining generation brings no Project back. The prompts it already holds, queued ones included, and the work they start (delegation) run to their end there; each Project, once idle, closes its terminals, releases its lease and clears its owner. The active generation then adopts it: a Project whose owner is gone without releasing it is first reconciled as after a host restart ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The runtime's live state belongs to its generation process: when that process dies, its runtime holds nothing back, and the process that takes over recovers from durable state ([src/host/domain/runtime.ts](../../bundles/runtime/runtime/src/host/domain/runtime.ts)).

## Current behavior and contracts

### How a window reaches the runtime

- A desktop window never opens HTTP or Socket.IO. A client part's call to a host contract crosses the window's preload to the desktop process, which forwards it over the host's desktop bridge, the kernel's Socket.IO namespace `/doric/bridge`, to the provider in the active generation. Only methods declared with `expose: 'desktop'` are served, and the scope keys a window may send for `runtime/v2` and `runtime.threads/v1` are `projectId`, `threadId` and `promptId`, the runtime's `desktopScope` ([manifest.json](../../bundles/runtime/runtime/manifest.json), [app/backend/doric-host/src/lib/bridge/socket.ts](../../app/backend/doric-host/src/lib/bridge/socket.ts)). The path is described in [Calls from a desktop window](../architecture/bundles/services-and-channels.md#calls-from-a-desktop-window) and [The desktop bridge](../../app/backend/doric-host/README.md#the-desktop-bridge); the methods marked _desktop_ are listed in the runtime README's [Contracts it provides](../../bundles/runtime/runtime/README.md#contracts-it-provides).
- The desktop does not use `transport`'s REST routes or its namespaces; those serve HTTP clients, under the routes and rules of the host's [REST API](../../app/backend/doric-host/README.md#rest-api) and [Socket.IO](../../app/backend/doric-host/README.md#socketio) reference ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts), [bundles/foundation/transport/src/host/sockets/workspace.ts](../../bundles/foundation/transport/src/host/sockets/workspace.ts)).
- In each window, the runtime's client part provides `runtime.records/v1`: a mirror of the host's Projects and Threads that reads from memory, loads and writes over `runtime/v2` and `runtime.threads/v1`, and follows each Project through `runtime/v2.watchProject`, subscribing again after a dropped connection. Its reads, writes and retries are in the runtime README's [Client part: the records mirror](../../bundles/runtime/runtime/README.md#client-part-the-records-mirror) ([src/client/index.ts](../../bundles/runtime/runtime/src/client/index.ts), [src/client/records.ts](../../bundles/runtime/runtime/src/client/records.ts)).

### The path of a prompt

1. The reader writes in a Thread's composer. The [`chat`](../../bundles/desktop/chat/README.md) bundle sends it as `runtime.threads/v1.prompt`, or as a steer of the running prompt, over the bridge ([bundles/desktop/chat/src/client/services/send.ts](../../bundles/desktop/chat/src/client/services/send.ts)). How the conversation is drawn and sent is described in [conversation.md](conversation.md).
2. The runtime takes the Project's live runtime, bringing it back first when needed ([The queue](#the-queue)), applies the current Git credentials when they changed, accepts the input into the Thread's queue and appends `prompt.accepted` to the Thread's stream on `storage/v1` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
3. When the Thread dispatches it, the runtime marks the Thread `running`, has `executor/v1.checkpoint` record the turn's rewind boundary, appends `prompt.started`, awaits `onPromptStartedHook` and calls `executor/v1.run` ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
4. The executor calls the model and the tools. Every tool is bound to the sandbox the Project leased through `sandbox/v1.acquire` when it became `ready`, and reaches it through `runtime.lease/v1`, or through `runtime.workspace/v1` for the Thread's working directory, as the terminal tool and the files `cwd` tool do ([src/host/domain/bindings.ts](../../bundles/runtime/runtime/src/host/domain/bindings.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/features/terminal/src/host/tool.ts](../../bundles/features/terminal/src/host/tool.ts), [bundles/features/files/src/host/tools/cwd.ts](../../bundles/features/files/src/host/tools/cwd.ts)).
5. The runtime stores each history update and then its event on `storage/v1`, and publishes each committed event as a `runtime/v2` notice ([src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts), [src/host/domain/notices.ts](../../bundles/runtime/runtime/src/host/domain/notices.ts)).
6. The notices reach `runtime/v2.watch` listeners, `transport`'s namespaces among them, and the watch streams: the chat's `runtime.threads/v1.watchThread` draws the events, and the mirror's `runtime/v2.watchProject` updates the Project and its Threads in the window ([src/host/services/watches.ts](../../bundles/runtime/runtime/src/host/services/watches.ts), [bundles/desktop/chat/src/client/api/thread-watch.ts](../../bundles/desktop/chat/src/client/api/thread-watch.ts), [src/client/api/project-watch.ts](../../bundles/runtime/runtime/src/client/api/project-watch.ts)).
7. The prompt ends with `prompt.finished` and the Thread goes back to `ready`.

### What the reader sees

- The Dashboard lists the Projects with their name, activity, creation time and state, shown as the Project's `state` word; a Project's context menu opens, colors or deletes it. The desktop creates a Project and then its first Thread, with an empty name ([Dashboard](../../bundles/desktop/workspace/README.md#dashboard), [bundles/desktop/workspace/src/client/components/molecules/project-item.tsx](../../bundles/desktop/workspace/src/client/components/molecules/project-item.tsx), [bundles/desktop/workspace/src/client/hooks/use-workspace.ts](../../bundles/desktop/workspace/src/client/hooks/use-workspace.ts)).
- A Project's sidebar draws its Threads as a tree by `parentThreadId`. A row is active, shimmering with an elapsed badge, while its Thread runs a prompt or any descendant is active ([Project sidebar](../../bundles/desktop/workspace/README.md#project-sidebar), [Activity](../../bundles/desktop/workspace/README.md#activity), [bundles/desktop/workspace/src/client/domain/thread-tree.ts](../../bundles/desktop/workspace/src/client/domain/thread-tree.ts)).
- A Thread has one of three kinds, decided from its record ([Thread kinds](../../bundles/desktop/workspace/README.md#thread-kinds), [bundles/desktop/workspace/src/client/domain/thread-kind.ts](../../bundles/desktop/workspace/src/client/domain/thread-kind.ts)):

  | Kind | Record | The reader may |
  | --- | --- | --- |
  | Main thread | no parent | prompt, rename, delete, open a sub-thread |
  | Sub-thread | a parent, `origin` not `agent` | prompt, rename, delete |
  | Agent thread | a parent, `origin: 'agent'` | pause, continue, retry; delete once archived |

- Deleting asks in a dialog ("Delete project?" or "Delete thread?") and, once confirmed, terminates and then deletes the Project or the Thread; the mirror retries a deletion answered `active` every 500 ms, with no limit, until it answers otherwise ([bundles/desktop/workspace/src/client/components/molecules/delete-dialog.tsx](../../bundles/desktop/workspace/src/client/components/molecules/delete-dialog.tsx), [bundles/desktop/workspace/src/client/hooks/use-workspace.ts](../../bundles/desktop/workspace/src/client/hooks/use-workspace.ts), [src/client/api/workspace-api.ts](../../bundles/runtime/runtime/src/client/api/workspace-api.ts)).
- Archiving is described in [thread-archive.md](thread-archive.md), and the conversation inside a Thread in [conversation.md](conversation.md).

### Projects and Threads

- A Project (`Project`) has an `id`, a `name`, an optional `color`, a `state`, the `configRevision` it was created under, an optional `errorCode`, and its timestamps; its shape is in the runtime README's [Project](../../bundles/runtime/runtime/README.md#project) ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- Creating a Project and creating a Thread are separate operations: a new Project has no Thread. A new Project is `queued`, gets a random color, and starts acquiring its sandbox at once ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)).
- A Project stores the configuration in force when it was created, with its revision, as a record of where it came from. The runtime never reads that snapshot to run anything: every prompt runs under the configuration in force when it runs, read through [`host-config/v1`](../../bundles/foundation/host-config/README.md#host-configv1-version-120) ([src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts)).
- A Thread (`Thread`) belongs to one Project and may have a parent Thread. It has its own conversation, history, queue and working directory (`cwd`, with the repository hint `cwdRepo`). Its `origin` is `user` for a Thread the reader opened and `agent` for one an agent spawned; a Thread without `origin` is the reader's. Its shape is in the runtime README's [Thread](../../bundles/runtime/runtime/README.md#thread) ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)). The agent, model and effort of a Thread are described in [per-thread-model.md](per-thread-model.md), archiving in [thread-archive.md](thread-archive.md), and the working directory in [cwd-tool.md](cwd-tool.md).
- `createThread` answers `missing` when the Project does not exist, `inactive` when the process holds no live runtime for it or it is closing, `invalid_parent` when the parent is not a live Thread of the Project or when a Thread the reader opens would hang below a non-root Thread (only an agent nests deeper), and `inactive` when the parent is closing. The store refuses the rest by rejecting, with no status: `Inactive project.` when the Project is neither `queued` nor `ready`, and `Invalid parent thread.` when an ancestor is missing, belongs to another Project, or is `cancelling`, `failed` or `cancelled` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)). Child Threads and the delegation between them are described in [delegation.md](delegation.md).
- A new Thread starts `queued`, in `/workspace`, or, for a child, in its parent's current directory with its parent's hint. It becomes `ready` at once when its Project holds a lease, and otherwise when the lease arrives ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Names: the REST routes and the mirror's writes trim a Project or Thread name and require 1 to 80 Unicode code points without NUL. The mirror's Thread creation exempts exactly the empty name; its Project creation and both renames always apply the rule. The runtime's contracts store the name they are given, so the desktop's first Thread of a Project has the empty name and reads as Untitled ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [src/client/api/workspace-api.ts](../../bundles/runtime/runtime/src/client/api/workspace-api.ts), [bundles/desktop/workspace/src/client/domain/workspace.ts](../../bundles/desktop/workspace/src/client/domain/workspace.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)).
- Projects list newest first, by creation time and then id ([src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).

### States

- A Project is `queued`, `ready`, `cancelling`, `cancelled` or `failed`. A Thread has the same states and `running`. `cancelled` and `failed` are terminal: no write moves a record out of them, and a write to `queued`, `ready` or `running` also leaves a `cancelling` record as it is ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts), [src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).
- A Project goes from `queued` to `ready` when its sandbox is acquired, and its Threads become `ready` with it. A Thread runs each input as `ready -> running -> ready`. Termination goes `cancelling -> cancelled` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- `failed` records why in `errorCode`. A Project fails with `sandbox_acquisition_failed` when `sandbox/v1.acquire` rejects, when reading the configuration in force to choose the Git credentials rejects, or when the setup after it fails to persist; choosing or applying a credential is not part of that failure. It fails with `sandbox_release_failed` when its termination cannot release the lease; the shipped providers retry a failed disposal until it succeeds and never reject the release, so with them a termination or a host stop waits until the disposal succeeds, and a terminated Project stays `cancelling` meanwhile ([sandboxes.md](sandboxes.md#in-the-runtime), [packages/sandpool/README.md](../../packages/sandpool/README.md#failures-and-retries)). A Thread fails with `persistence_failed` when its history or events cannot be written, and with `terminal_result_failed` when a background terminal's result cannot be delivered ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- `startedAt` is written the first time a record becomes `ready`, and `finishedAt` when it becomes terminal ([src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- A prompt that fails, through its provider or a tool that ends the run, finishes as `failed` and returns its Thread to `ready`; a tool handler's failure answers its call and the run goes on ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Leases and the sandbox pool

- A Project holds one sandbox lease for its whole life, across all its Threads and prompts. The runtime acquires it through `sandbox/v1.acquire` (declared in the runtime README's [`sandbox/v1`](../../bundles/runtime/runtime/README.md#sandboxv1)) with the Project's id as the identity, and passes an abort signal that terminating the Project fires. Under [`docker`](../../bundles/sandboxes/docker/README.md#durable-workspaces) the identity names a workspace volume, so a Project that comes back gets its own files again; under [`firecracker`](../../bundles/sandboxes/firecracker/README.md#data-and-side-effects) it gets a fresh microVM without its earlier files. The runtime's side of the pool is described under [In the runtime](sandboxes.md#in-the-runtime) ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/contracts/sandbox.ts](../../bundles/runtime/runtime/src/contracts/sandbox.ts)).
- The pool's capacity bounds Projects, not Threads: a Project waits in `queued` until the pool provisions its sandbox, in arrival order. The shipped providers hold at most 10 sandboxes, as [The pool](sandboxes.md#the-pool) and the `sandpool` README's [Acquisition and ordering](../../packages/sandpool/README.md#acquisition-and-ordering) describe ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- When the sandbox arrives, the runtime applies the Git identity and GitHub token in force, then probes, in one sandbox command, the working directory of every live Thread not at the workspace root; a probe that cannot run keeps every directory. Then, under the Project's lock, it records the lease, sets the Project `ready` (which fires `onProjectReadyHook`), resets each directory the sandbox does not hold to the root, and sets each live Thread `ready` and starts its queue ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts)).
- Before a prompt, a retry, a steer, a resume, a queue resume or a rewind, the runtime chooses the Git credentials again and applies them only when they differ from the pair it last applied ([credentials.md](credentials.md#git-in-the-sandbox), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Choosing the credentials first reads the configuration in force, and a failed read is not caught. At acquisition it ends the Project with `sandbox_acquisition_failed` ([States](#states)). In `prompt`, `retry`, `steer`, `resume`, `resumeQueue` and `rewind` it rejects the call before anything is queued or changed, for a Project that holds a lease and is not closing. `prompt`, `retry`, `steer`, `resume` and `resumeQueue` take the Project's live runtime first, so by then the call may already have brought the Project back and waited for its acquisition ([The queue](#the-queue)); `rewind` does not ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Projects have no expiry: a Project holds its sandbox until it is terminated, the host stops, or its generation lets it go. The lease is released exactly once, after the Project's work has settled ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Only the runtime acquires a sandbox. Other bundles reach a Project's sandbox through `runtime.lease/v1` and `runtime.workspace/v1`, which never acquire: `withLease` runs a task on the sandbox the Project holds now, `withThread` runs a task on one live Thread and its sandbox, and the sandbox operations (`exec`, `readFile` and the others) run inside a prompt on the sandbox bound to it, else on the Project the call's scope names. When the Project holds no ready lease they answer why (`pending`, `unavailable`, `expired`, `missing`, `inactive`) or reject, so a read that needs a lease never brings a Project back; a Project another live process holds is answered once this process adopts it. The outcomes, the scope rules and their messages are in the runtime README's [`runtime.lease/v1`](../../bundles/runtime/runtime/README.md#runtimeleasev1) and [`runtime.workspace/v1`](../../bundles/runtime/runtime/README.md#runtimeworkspacev1) ([src/host/services/lease.ts](../../bundles/runtime/runtime/src/host/services/lease.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). [`files`](../../bundles/features/files/README.md), [`git`](../../bundles/features/git/README.md), [`resources`](../../bundles/features/resources/README.md), [`papercraft`](../../bundles/features/papercraft/README.md), [`mcp`](../../bundles/features/mcp/README.md) and [`screen`](../../bundles/features/screen/README.md) read through `withLease`, and `git` and [`terminal`](../../bundles/features/terminal/README.md) run Thread work through `withThread` ([bundles/features/files/src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [bundles/features/git/src/host/service.ts](../../bundles/features/git/src/host/service.ts), [bundles/features/terminal/src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)). How `git` answers from these outcomes is described in [git.md](git.md).

### The queue

- Each Thread has its own FIFO queue and runs one input at a time. Distinct Threads run in parallel, with no cap on their number or on concurrent runs, in a Project or across Projects; the queue's full behavior is in the runtime README's [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue) ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- An accepted input appends `prompt.accepted` with its text, its source and whether it was queued, and also `prompt.queued` when it waits: behind a running or queued input, behind a closed gate, or for its Project's lease. Its text is redacted before it is stored. An empty or whitespace-only prompt is refused ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Input (`prompt`, `retry`, `steer`, `instruct`, `resume`) and the queue controls `resumeQueue`, `editQueued` and `removeQueued` go through the Project's live runtime, and how long they wait depends on where that runtime came from ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)):
  - A Project created by this process is used at once: input to it while it is still `queued` appends `prompt.queued` and runs when the lease arrives.
  - A Project this process built from storage, through recovery, adoption, or input to a Project with no live runtime yet, makes the caller wait for its whole acquisition before anything is queued, so inputs that race to bring a Project back keep their order. It answers `inactive` when the acquisition ended without a lease or the Project is closing, and so does a Project that cannot be brought back.
- Before a Thread dispatches its next input, under the Project's lock, the runtime checks storage, marks the Thread `running`, has `executor/v1.checkpoint` record the turn's rewind boundary and appends `prompt.started`. Then, outside the lock, it awaits `onPromptStartedHook` and runs the prompt through `executor/v1` with the Thread's persisted provider history ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- A Thread's queue does not dispatch while its gate is closed (`queuePaused`), while a storage pause is pending, while the Thread or its Project is closing, or while the Project has no lease ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Stopping, steering, resuming, editing and removing queued inputs, retry and compaction are described in [prompt-control.md](prompt-control.md). `runtime.threads/v1.instruct` gives a Thread an instruction from the calling bundle, with the source `{ kind: 'bundle', bundleId, reason }`; it reaches agent Threads too ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). A background terminal's result reaches its Thread as [terminal.md](terminal.md) describes.
- Rewind replaces an edited turn. It answers `inactive` for a closing or terminal Thread or Project, and `busy` while the Thread runs or holds queued input, so the queue never runs on truncated history; `unknown_prompt` when the log holds no event of that prompt or `executor/v1.rewind` gives no history patch. Otherwise it truncates the event log from the first event of that turn, drops the history of that turn and every later one at the turn's checkpoint, appends `history.truncated`, and accepts the edited text as a new input of the reader. `prompt` and `rewind` answer `forbidden` for an agent Thread ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).

### Events and history

- Every event of a Thread has a sequence in its stream. Sequences are never reused: `history.truncated` carries `afterSequence`, the sequence of the last event that survives (`0` when none survives), and takes the next sequence the stream ever assigned, so a rewind leaves a gap. Readers follow sequences in order and never assume they are contiguous. The event types are listed in the runtime README's [Event streams](../../bundles/runtime/runtime/README.md#event-streams) ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- `prompt.finished` carries the input source, the status (`completed`, `failed` or `cancelled`) and the response text, and is what clients read as a prompt's end; other bundles read it as `runtime.prompt-finished/v1`. A prompt finishes as completed only after its history is stored ([src/contracts/events.ts](../../bundles/runtime/runtime/src/contracts/events.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- During a run, each history update is stored before its event, and both are redacted. A run that ends, completed or failed, has stored the history it reached ([src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts)).
- Event values become JSON without losing reasoning, replay data, tool payloads and results, or errors with their stack, cause and own properties. Undefined object properties are left out; undefined array entries, cycles and other values JSON cannot hold become markers (`[Undefined]`, `[Circular: …]`, `[BigInt: …]` and so on), and every configured secret becomes `[REDACTED]`. U+0000 and unpaired surrogates, which PostgreSQL refuses, become U+FFFD in every stored text ([src/host/domain/serialization.ts](../../bundles/runtime/runtime/src/host/domain/serialization.ts), [src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).
- Other bundles append to a Thread's stream through [`events/v1`](../../bundles/foundation/core/README.md#eventsv1). When the core reports a committed append ([`core.event-hooks/v1`](../../bundles/foundation/core/README.md#coreevent-hooksv1)`.onEventAppendedHook`), the runtime folds the new entries into the Thread document (sequence counter, queue flag, usage, latest start, `pending`) in that document's write order, commits it, and then publishes the events to `runtime/v2.watch` listeners in sequence order. A runtime commit that meets such an append first folds it on its `sequence_conflict` retry. Either way each event is folded and published once ([src/host/appends.ts](../../bundles/runtime/runtime/src/host/appends.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/documents.ts](../../bundles/runtime/runtime/src/host/store/documents.ts)).
- A watch subscribes to the notices before it reads its snapshot and holds back what arrives in between, so nothing is lost; `watchThread` sends each event sequence once. The watch items are in the runtime README's [Watches](../../bundles/runtime/runtime/README.md#watches) ([src/host/services/watches.ts](../../bundles/runtime/runtime/src/host/services/watches.ts)).
- Each Thread's usage aggregate counts every model call of every provider, with its tokens and context; a call without a `credits` cost counts as unpriced ([src/host/store/usage.ts](../../bundles/runtime/runtime/src/host/store/usage.ts)). Usage is described in [usage.md](usage.md).
- The durable records and the event streams are the source of replay. The process holds only live state: the leases, the Threads' queues, abort controllers and subscribers. It takes work up on its own only through recovery at startup and adoption ([src/host/domain/runtime.ts](../../bundles/runtime/runtime/src/host/domain/runtime.ts), [src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts)). The host runs as one instance, and its Socket.IO server is created with no shared adapter ([app/backend/doric-host/src/index.ts](../../app/backend/doric-host/src/index.ts)).

### Host stop

- A host stop is not a termination. The runtime's step on `onHostStopHook` ([`doric.app.hooks/v1`](../architecture/bundles/hooks.md#host-start-and-stop)) suspends every live Project: running prompts are aborted and recorded as `prompt.paused { reason: 'host_stopped' }`, queued inputs stay accepted and unfinished, `onThreadsClosingHook` fires for each Thread, the lease is released, the Project's owner is cleared, and the Project is written back as `queued` with its non-terminal Threads `ready`. A lease that will not release leaves the Project `queued` with `sandbox_release_failed`. After the stop, `createProject` rejects with `Doric is shutting down.`, and terminating a Project the process does not hold answers its record unchanged ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Recovery at startup

- The runtime's step on `onHostStartHook` ([`doric.app.hooks/v1`](../architecture/bundles/hooks.md#host-start-and-stop)) names the startup stage `workspace_reconciliation` through `doric.startup/v1`, runs recovery before the host listens, and logs `Workspace reconciled` with the counts; the detail is in the runtime README's [Recovery, host stop and handover](../../bundles/runtime/runtime/README.md#recovery-host-stop-and-handover). Recovery runs four steps in order ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)):
  1. Threads are reconciled. A prompt whose run started and recorded no pause gets `prompt.paused { reason: 'host_restarted' }`. A non-terminal Thread becomes `ready`, with no active prompt and no error code other than `storage_low`; a Thread left `cancelling` becomes `cancelled`.
  2. Projects are reconciled. A non-terminal Project becomes `queued`, with no error code; a Project left `cancelling` becomes `cancelled`, so a restart never revives work the reader terminated.
  3. The prompts the host owes are taken up: every unfinished prompt that was not superseded, that the reader did not stop and that no storage pause holds, on a Thread whose gate is open. A prompt already taken up twice (counted from its `prompt.resumed` events) is closed as a failure with the code `resume_exhausted` instead. Each other prompt is queued again, Project by Project, in the order the log accepted them, appending `prompt.resumed { attempt }`, so it continues from the provider history stored as its run advanced. Prompts that closing an exhausted delegated prompt delivers to its parent are queued in the same pass.
  4. Every other non-terminal Project is brought back, newest first.
- Bringing a Project back loads it and its Threads and starts its acquisition in the background, so a full pool never holds up the listener. The Projects of step 3 are brought back first, so they acquire first. A finished prompt is never run again ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- A Thread whose gate is closed keeps it across the restart: neither its queued inputs nor its interrupted prompt run until the reader resumes it. A storage pause that was stored also survives the restart and never resumes on its own ([src/host/domain/prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- The `resume_exhausted` message reads `The run was interrupted three times by a host restart and was not resumed again. The work may be incomplete; send the prompt again to continue.` The budget bounds automatic recovery only: the reader can always take an unfinished prompt up ([src/host/domain/prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts)).

### Generations

- The kernel switches or respawns the generation of bundles as [Generations](../architecture/bundles/process-isolation.md#generations) describes, so two runtime processes share one storage for a while. The runtime builds its handover on two platform contracts: it observes `onGenerationChangedHook` and `onPeerSignalHook` of [`doric.app.hooks/v1`](../architecture/bundles/process-isolation.md#generation-hooks), and calls `hold` and `signal` of [`doric.generation/v1`](../architecture/bundles/process-isolation.md#doricgenerationv1) ([src/host/handover.ts](../../bundles/runtime/runtime/src/host/handover.ts)):
  - the generation that becomes active runs recovery in the background with the draining processes as the live owners (`recoverWith`), leaving their Projects in standby;
  - a generation that starts draining takes the work hold `runtime.drain`, drains its Projects (`drain`) and signals `runtime.released` with the id of each one it lets go, then drops the hold;
  - the active generation adopts (`adopt`) on each `runtime.released` signal from the `runtime` bundle and on each `lost` or `stopped` change. Adoptions run one at a time, after recovery.
- A process that cannot describe its generation records no owner and claims every Project ([src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). The handover across bundles is summarised in [How the runtime hands over](../architecture/bundles/process-isolation.md#how-the-runtime-hands-over).

### Terminating a Thread or a Project

- Terminating a Thread closes it and its whole subtree, and leaves the Project's lease and its other Threads alone. Terminating a Project closes all its Threads and then releases its lease. Neither undoes what the work did in the sandbox ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Closing Threads marks them closing before anything is awaited, aborts their running prompts, awaits `onThreadsClosingHook` and, for at most one second, the running prompts' own record of their end. Each Thread is then written `cancelling`. Each queued input gets `agent.cancelled` and finishes `cancelled` (`The prompt was cancelled.`), or, when the close carries a failure code (the Project's, or the Thread's own `persistence_failed` or `terminal_result_failed`), gets `agent.failed` and finishes `failed` (`The project is unavailable.`). Once its run has ended the Thread becomes `cancelled`, or `failed` with that code ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- A Project's termination aborts its acquisition, writes `cancelling`, closes its Threads, and, once its acquisition, runs and closings have settled, releases the lease, clears its owner and writes `cancelled`. It writes `failed` with `sandbox_release_failed` when the release fails, and, for a Project closed for a failure, `failed` with that failure's code even when the release succeeds. Terminating a terminal Project answers it as it is ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Termination needs no live runtime. A Project another live process holds is terminated once this process adopts it. A Project no process holds is loaded and terminated without acquiring a sandbox. A Thread whose Project no process holds takes itself and its non-terminal subtree through `cancelling -> cancelled` in the store, publishing each change, so a reader can terminate and then delete it without prompting it first ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Cancellation, suspension and lease release go on when a state write fails; the failure is logged, with the messages listed in the runtime README's [Errors and failure behavior](../../bundles/runtime/runtime/README.md#errors-and-failure-behavior) ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Deleting removes records for good. A Thread is deleted only with its whole subtree, and only when every Thread of the subtree is terminal (`active` otherwise); an agent Thread is deleted only once archived (`forbidden` otherwise). A Project is deleted only when it and every Thread are terminal; its deletion removes its Threads, their histories, event streams and attachments, and calls `sandbox/v1.discard` with the Project's id, which removes the Project's containers and then its workspace volume under [`docker`](../../bundles/sandboxes/docker/README.md#durable-workspaces) and does nothing under [`firecracker`](../../bundles/sandboxes/firecracker/README.md#sandboxv1); a failed discard is logged and the deletion stands. The answers are `deleted`, `active`, `missing` and `forbidden` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts)).

### Storage pressure and persistence failures

- The runtime checks storage before each dispatch and every three seconds during a run, as the runtime README's [Storage pressure](../../bundles/runtime/runtime/README.md#storage-pressure) describes. A failed check, or a disk-full error, pauses the Thread instead of closing it: the run is aborted, the Thread is `ready` with `queuePaused` and the error code `storage_low`, and `queue.paused { reason: 'storage_low' }` and, for a running prompt, `prompt.paused { reason: 'storage_low' }` are appended. Queued inputs stay accepted ([src/host/domain/storage-pressure.ts](../../bundles/runtime/runtime/src/host/domain/storage-pressure.ts), [src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Compose sets `DORIC_STORAGE_PATH=/var/lib/doric/postgresql` and mounts the PostgreSQL volume there read-only, so the check measures the database's filesystem; a native or remote-database deployment must point the variable at the filesystem that holds the database ([app/backend/doric-host/compose.yaml](../../app/backend/doric-host/compose.yaml), [Storage protection](../../app/backend/doric-host/README.md#storage-protection)).
- When even the pause cannot be written, the gate stays closed in memory, with the history and event the run could not store; resuming writes them before anything is dispatched, and they are lost if the host process dies first. While the pause is only in memory, Thread reads show it as `ready`, paused and `storage_low`, and the queue shows the storage error ([src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Only an explicit resume that passes a fresh storage check reopens a storage pause; otherwise it answers `storage_low`, with the message `Execution paused: storage is low or unavailable. Free disk space above 10% and resume the queue.` ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- Any other failure to store a Thread's history or events closes the Thread as `failed` with `persistence_failed` and logs `Thread persistence failed`, so its queue never runs on stale history ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
