# Feature: Projects and Threads

- Status: `implemented`

## Problem

The reader works in Projects. A Project needs one [sandbox](sandboxes.md), which is scarce: the pool holds a bounded number, and acquiring one takes time. Inside a Project, the reader and the agents hold several conversations at once, each with its own history, its own queue of inputs and its own working directory, and each must run without waiting for the others. Work must survive a host that stops, crashes or hands over to a new generation of bundles: an accepted prompt is neither lost nor run twice, and a Project or Thread the reader terminated never comes back.

## Decisions

- The runtime keeps a Project as a `runtime.project/v1` document, a Thread as a `runtime.thread/v1` document and its provider history as `runtime.history/v1` documents, on `storage/v1`; their shapes are in the runtime README's [Data and storage](../../bundles/runtime/runtime/README.md#data-and-storage). Each Thread's events go to the stream `runtime.thread.events/<threadId>`. The Thread's `pending` projection and its usage aggregate are folded into the same commit as the event that changes them.
- Every write of a runtime document is one `storage/v1` commit that expects the revision the change was computed from. Writes to one document run one at a time in the process. A revision conflict or a sequence conflict drops the cached document, reads it again and computes the change again. A write makes at most 8 commit attempts that end in a revision conflict and, separately, at most 64 that end in a sequence conflict before it fails, so that appends other bundles make to a Thread's stream never use up the budget of revision conflicts.
- Deleting a Project, or a Thread with its subtree, removes every record in one atomic commit; the attachment blobs no record names any more are collected after that commit. A deletion larger than the storage batch limit is refused with `limit_exceeded` before anything is written; the runtime logs `Deletion exceeds the storage batch limit` and passes the refusal on.
- `onProjectReadyHook` and `onProjectClosingHook` fire without being awaited, after the `ready` and the `cancelling` commit of a Project; a failing handler is ignored. `onThreadsClosingHook`, `onPromptStartedHook` and `onThreadCwdChangedHook` are awaited by the runtime, except that resetting a working directory missing from a reacquired sandbox fires `onThreadCwdChangedHook` without awaiting it, since the reset holds the Project's lock that a handler's own calls need.
- The [`postgres`](../../bundles/foundation/postgres/README.md) bundle measures the filesystem at `DORIC_STORAGE_PATH` (the current directory by default) and makes no database round trip; the runtime applies the policy: execution pauses when 10 percent or less of the blocks are available, when the measurement is missing or when it fails. PostgreSQL error `53100` and `ENOSPC` are treated the same way.
- Recovery runs once per runtime process: a second call answers the summary of the first without doing the work again. A host stop is idempotent.
- Each Project records the runtime process that holds it, as `{ generation, incarnation }`. A process claims a Project before it brings it back, and the claim fails while another live process holds it; the Project then waits in standby in this process. Every lifecycle change of a Project in standby (termination, deletion, rename, color, Thread creation, rename, termination, deletion and rewind, a Thread's execution, the queue read) runs only after this process adopts it, and so do the operations that need its live runtime (input, resume, `withLease`, `ssh`). Reads of stored records and events do not wait. Recording or clearing the owner never moves `updatedAt`. A host without generations records no owner.
- A draining generation brings no Project back. The prompts it already holds, queued ones included, and the work they start (delegation) run to their end there; each Project, once idle, closes its terminals, releases its lease and clears its owner. The active generation then adopts it: a Project whose owner is gone without releasing it is first reconciled as after a host restart.
- The runtime's live state belongs to its generation process: when that process dies, its runtime holds nothing back, and the process that takes over recovers from durable state.

### Projects and Threads

- A Project (`Project`) has an `id`, a `name`, an optional `color` (one of `red`, `orange`, `amber`, `green`, `teal`, `blue`, `violet`, `pink`), a `state`, the `configRevision` it was created under, an optional `errorCode`, and `createdAt`, `updatedAt`, `startedAt` and `finishedAt`; its shape is in the runtime README's [Project](../../bundles/runtime/runtime/README.md#project) ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- Creating a Project and creating a Thread are separate operations: a new Project has no Thread. A new Project is `queued`, gets a random color, and starts acquiring its sandbox at once ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)). The desktop's [`workspace`](../../bundles/desktop/workspace/README.md) bundle creates a Project and then its first Thread, with an empty name ([bundles/desktop/workspace/src/client/hooks/use-workspace.ts](../../bundles/desktop/workspace/src/client/hooks/use-workspace.ts)).
- A Project stores the configuration in force when it was created, with its revision, as a record of where it came from. The runtime never reads that snapshot to run anything: every prompt runs under the configuration in force when it runs, read through [`host-config/v1`](../../bundles/foundation/host-config/README.md#host-configv1-version-120) ([src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- A Thread (`Thread`) belongs to one Project and may have a parent Thread. It has its own conversation, history, queue and working directory (`cwd`, with the repository hint `cwdRepo`). Its `origin` is `user` for a Thread the reader opened and `agent` for one an agent spawned; a Thread without `origin` is the reader's. It also carries `lastSequence`, `queuePaused`, `activePromptId`, `errorCode`, the result of its last finished prompt, and the fields its execution, archiving and pinning use; its shape is in the runtime README's [Thread](../../bundles/runtime/runtime/README.md#thread) ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)). The agent, model and effort of a Thread are described in [per-thread-model.md](per-thread-model.md), archiving in [thread-archive.md](thread-archive.md), and the working directory in [cwd-tool.md](cwd-tool.md).
- `createThread` answers `missing` when the Project does not exist, `inactive` when the process holds no live runtime for it or it is closing, `invalid_parent` when the parent is not a live Thread of the Project or when a Thread the reader opens would hang below a non-root Thread (only an agent nests deeper), and `inactive` when the parent is closing. The store refuses the rest by rejecting, with no status: `Inactive project.` when the Project is neither `queued` nor `ready`, and `Invalid parent thread.` when an ancestor belongs to another Project or is `cancelling`, `failed` or `cancelled` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)). Child Threads and the delegation between them are described in [delegation.md](delegation.md).
- A new Thread starts `queued`, in `/workspace`, or, for a child, in its parent's current directory with its parent's hint. It becomes `ready` at once when its Project holds a lease, and otherwise when the lease arrives ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Names: the REST routes trim a Project or Thread name and require 1 to 80 Unicode code points without NUL, at creation and at rename; a missing or invalid name answers 422 `invalid_project` or `invalid_thread`. The desktop's name form applies the same rule. The runtime's contracts store the name they are given, so the desktop's first Thread of a Project has the empty name ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts), [bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts), [src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts), [bundles/desktop/workspace/src/client/domain/workspace.ts](../../bundles/desktop/workspace/src/client/domain/workspace.ts)).
- Projects list newest first, by creation time and then id, with the id of the last item as the cursor ([src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).

### States

- A Project is `queued`, `ready`, `cancelling`, `cancelled` or `failed`. A Thread has the same states and `running`. `cancelled` and `failed` are terminal: no write moves a record out of them, and a write to `queued`, `ready` or `running` also leaves a `cancelling` record as it is ([src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts), [src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).
- A Project goes from `queued` to `ready` when its sandbox is acquired, and its Threads become `ready` with it. A Thread runs each input as `ready -> running -> ready`. Termination goes `cancelling -> cancelled` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- `failed` records why in `errorCode`. A Project fails with `sandbox_acquisition_failed` when its sandbox cannot be acquired or set up (applying the Git credentials included), and with `sandbox_release_failed` when its termination cannot release the lease; the shipped providers retry a failed disposal until it succeeds and never reject the release, so only another provider gives that failure; with them, a termination or a host stop waits until the disposal succeeds, and a terminated Project stays `cancelling` meanwhile ([sandboxes.md](sandboxes.md#in-the-runtime), [packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts)). A Thread fails with `persistence_failed` when its history or events cannot be written, and with `terminal_result_failed` when a background terminal's result cannot be delivered ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- `startedAt` is written the first time a record becomes `ready`, and `finishedAt` when it becomes terminal ([src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- A prompt that fails, through its provider or a tool that ends the run, finishes as `failed` and returns its Thread to `ready`; a tool handler's failure answers its call and the run goes on ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Leases and the sandbox pool

- A Project holds one sandbox lease for its whole life, across all its Threads and prompts. The providers, the pool and the sandbox boundary are described in [sandboxes.md](sandboxes.md), and the runtime's side of them under [In the runtime](sandboxes.md#in-the-runtime). The runtime acquires the lease through `sandbox/v1.acquire` (declared in the runtime README's [`sandbox/v1`](../../bundles/runtime/runtime/README.md#sandboxv1)) with the Project's id as the identity, and passes an abort signal that terminating the Project fires ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/contracts/sandbox.ts](../../bundles/runtime/runtime/src/contracts/sandbox.ts)). What a Project that comes back finds depends on the provider, which `sandbox/v1.describe()` reports as `durableWorkspace`; the runtime does not read it. Under [`docker`](../../bundles/sandboxes/docker/README.md#durable-workspaces) (`durableWorkspace: true`) the identity names a workspace volume, so the Project gets its own files again; under [`firecracker`](../../bundles/sandboxes/firecracker/README.md#data-and-side-effects) (`durableWorkspace: false`) it gets a fresh microVM from the configured image (`DORIC_SANDBOX_IMAGE`), without its earlier files ([bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- The pool's capacity bounds Projects, not Threads: a Project waits in `queued` until the pool provisions its sandbox, in arrival order. The [`docker`](../../bundles/sandboxes/docker/README.md) and [`firecracker`](../../bundles/sandboxes/firecracker/README.md) providers hold at most 10 sandboxes, as [The pool](sandboxes.md#the-pool) describes ([packages/sandpool/src/lib/sandpool.ts](../../packages/sandpool/src/lib/sandpool.ts), [bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)).
- When the sandbox arrives, the runtime applies the Git identity and GitHub token in force, then probes, in one sandbox command, the working directory of every live Thread not at the workspace root, and resets each directory the sandbox does not hold to the root. A probe that cannot run keeps every directory. Then the Project becomes `ready` and its Threads `ready`, and their queues start ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Projects have no expiry: a Project holds its sandbox until it is terminated, the host stops, or its generation lets it go. The lease is released exactly once, after the Project's work has settled ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Only the runtime acquires a sandbox. Other bundles reach a Project's sandbox through `runtime.lease/v1.withLease`, which runs a task on the sandbox the Project holds now, or through `runtime.workspace/v1.withThread`, which runs a task on one live Thread and its sandbox. Neither acquires ([src/contracts/lease.ts](../../bundles/runtime/runtime/src/contracts/lease.ts), [src/contracts/workspace.ts](../../bundles/runtime/runtime/src/contracts/workspace.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). [`files`](../../bundles/features/files/README.md), [`git`](../../bundles/features/git/README.md), [`resources`](../../bundles/features/resources/README.md), [`papercraft`](../../bundles/features/papercraft/README.md), [`mcp`](../../bundles/features/mcp/README.md) and [`screen`](../../bundles/features/screen/README.md) read through `withLease`, and `git` and [`terminal`](../../bundles/features/terminal/README.md) run Thread work through `withThread` ([bundles/features/files/src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [bundles/features/git/src/host/service.ts](../../bundles/features/git/src/host/service.ts), [bundles/features/resources/src/host/index.ts](../../bundles/features/resources/src/host/index.ts), [bundles/features/papercraft/src/host/sandbox.ts](../../bundles/features/papercraft/src/host/sandbox.ts), [bundles/features/mcp/src/host/open.ts](../../bundles/features/mcp/src/host/open.ts), [bundles/features/screen/src/host/provider.ts](../../bundles/features/screen/src/host/provider.ts), [bundles/features/terminal/src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)). How `git` answers its Git and branch reads from these outcomes is described in [git.md](git.md).
- `runtime.lease/v1` also runs sandbox operations for other bundles: `describe`, `exec` (with no abort signal), `readFile`, `readFileBytes` and `writeFile`, whose shapes are in the runtime README's [`runtime.lease/v1`](../../bundles/runtime/runtime/README.md#runtimeleasev1). Inside a prompt they run on the sandbox bound to that prompt. Outside one they run through `withLease` on the scoped Project, else the Project of the scoped Thread, else the Project with the most recent activity, and reject with `ContractError('unavailable', 'Project lease is not ready (<status>).')` when that Project holds no ready lease; with no Project at all they reject with `invalid_input`. `files`, `git`, `mcp` and [`default`](../../bundles/runtime/default/README.md) call them ([src/contracts/lease.ts](../../bundles/runtime/runtime/src/contracts/lease.ts), [src/host/services/lease.ts](../../bundles/runtime/runtime/src/host/services/lease.ts), [bundles/features/files/src/host/sandbox.ts](../../bundles/features/files/src/host/sandbox.ts), [bundles/features/git/src/host/sandbox.ts](../../bundles/features/git/src/host/sandbox.ts), [bundles/features/mcp/src/host/manager.ts](../../bundles/features/mcp/src/host/manager.ts), [bundles/runtime/default/src/host/prompts/variables.ts](../../bundles/runtime/default/src/host/prompts/variables.ts)).
- `withLease` answers `{ status: 'ready', value }`, or why it could not run: `missing` (no such Project), `expired` (a terminal Project the process does not hold), `unavailable` (a non-terminal Project the process does not hold, a closing Project, or one that started closing or lost its lease while the task ran) and `pending` (the Project has no lease yet). For a Project another live process holds, `withLease` waits for this process to adopt it before it answers. `withLease` and `ssh` take the Project from the call's scope and reject with `invalid_input` without one. `runtime.lease/v1.ssh` answers the same states. A read that needs a lease therefore never brings a Project back; changing a sandbox needs a live lease ([src/contracts/lease.ts](../../bundles/runtime/runtime/src/contracts/lease.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- `withThread(threadId, { exclusive, resume?, refreshHint? }, task)` ([`runtime.workspace/v1`](../../bundles/runtime/runtime/README.md#runtimeworkspacev1)) answers `{ status: 'ready', value }`, `missing`, `inactive` (no live runtime, a closing Project or Thread, or a terminal Thread) or `pending` (no lease). `exclusive` runs the task under the Project's mutation lock; `resume` brings the Project back from durable state first; `refreshHint` probes the Thread's repository hint after the task. The task receives the Project and Thread ids, the Thread's `cwd`, the sandbox, `closing()` and `busyCwds()`, the directories of the Project's Threads that hold an active or queued prompt ([src/contracts/workspace.ts](../../bundles/runtime/runtime/src/contracts/workspace.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Every bundle tool a prompt calls is bound to that prompt's Project sandbox for the run, and released when the run settles ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/domain/bindings.ts](../../bundles/runtime/runtime/src/host/domain/bindings.ts)).

### The queue

- Each Thread has its own FIFO queue and runs one input at a time. Distinct Threads run in parallel, with no cap on their number or on concurrent runs, in a Project or across Projects; the queue's full behavior is in the runtime README's [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue) ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- An accepted input appends `prompt.accepted` with its text, its source and whether it was queued, and also `prompt.queued` when it waits: behind a running or queued input, behind a closed gate, or for its Project's lease. Its text is redacted before it is stored. An empty or whitespace-only prompt is refused ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Input to a non-terminal Project that has no live runtime in the process yet (one recovery has not reached) brings it back first: the Project acquires its sandbox, and the input is queued after that, so inputs that race to bring a Project back keep their order. A Project that cannot come back answers `inactive` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Before a Thread dispatches its next input, under the Project's lock, the runtime checks storage, marks the Thread `running`, records the turn's rewind checkpoint and appends `prompt.started`. Then, outside the lock, it awaits `onPromptStartedHook`, and runs the prompt through `executor/v1` with the Thread's persisted provider history ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- A Thread's queue does not dispatch while its gate is closed (`queuePaused`), while a storage pause is pending, while the Thread or its Project is closing, or while the Project has no lease ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Stopping, steering, resuming, editing and removing queued inputs, retry and compaction are described in [prompt-control.md](prompt-control.md). `runtime.threads/v1.instruct` gives a Thread an instruction from the calling bundle, with the source `{ kind: 'bundle', bundleId, reason }`; it reaches agent Threads too ([src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Rewind replaces an edited turn. It answers `inactive` for a closing or terminal Thread or Project, and `busy` while the Thread runs or holds queued input, so the queue never runs on truncated history; `unknown_prompt` when the log holds no event of that prompt or the executor gives no history patch. Otherwise it truncates the event log from the first event of that turn, drops the history of that turn and every later one at the turn's checkpoint, appends `history.truncated`, and accepts the edited text as a new input of the reader ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).

### Events and history

- Every event of a Thread has a sequence in its stream. Sequences are never reused: `history.truncated` carries `afterSequence`, the sequence of the last event that survives (`0` when none survives), and takes the next sequence the stream ever assigned, so a rewind leaves a gap. Readers follow sequences in order and never assume they are contiguous. The event types are listed in the runtime README's [Event streams](../../bundles/runtime/runtime/README.md#event-streams) ([src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- `prompt.finished` carries the input source, the status (`completed`, `failed` or `cancelled`) and the response text, and is what clients read as a prompt's end; other bundles read it as `runtime.prompt-finished/v1`. A prompt finishes as completed only after its history is stored ([src/contracts/events.ts](../../bundles/runtime/runtime/src/contracts/events.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- During a run, each history update is stored before its event, and both are redacted. A run that ends, completed or failed, has stored the history it reached ([src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts)).
- Event values become JSON without losing reasoning, replay data, tool payloads and results, or errors with their stack, cause and own properties. Undefined object properties are left out; undefined array entries, cycles and other values JSON cannot hold become markers (`[Undefined]`, `[Circular: …]`, `[BigInt: …]` and so on), and every configured secret becomes `[REDACTED]`. U+0000 and unpaired surrogates, which PostgreSQL refuses, become U+FFFD in every stored text ([src/host/domain/serialization.ts](../../bundles/runtime/runtime/src/host/domain/serialization.ts), [src/host/store/records.ts](../../bundles/runtime/runtime/src/host/store/records.ts)).
- Other bundles append to a Thread's stream through [`events/v1`](../../bundles/foundation/core/README.md#eventsv1). When the core reports a committed append ([`core.event-hooks/v1`](../../bundles/foundation/core/README.md#coreevent-hooksv1)`.onEventAppendedHook`), the runtime folds the new entries into the Thread document (sequence counter, queue flag, usage, latest start, `pending`) in that document's write order, commits it, and then publishes the events to `runtime/v2.watch` listeners in sequence order. A runtime commit that meets such an append first folds it on its `sequence_conflict` retry. Either way each event is folded and published once ([src/host/appends.ts](../../bundles/runtime/runtime/src/host/appends.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/documents.ts](../../bundles/runtime/runtime/src/host/store/documents.ts)).
- Each Thread's usage aggregate counts every model call of every provider, with its tokens and context; a call without a `credits` cost counts as unpriced ([src/host/store/usage.ts](../../bundles/runtime/runtime/src/host/store/usage.ts)). Usage is described in [usage.md](usage.md).
- [`runtime.usage/v1`](../../bundles/runtime/runtime/README.md#runtimeusagev1)`.read(threadId)` answers the Thread's stored usage projection, without the context capacity that `runtime.threads/v1.usage` adds ([src/contracts/usage.ts](../../bundles/runtime/runtime/src/contracts/usage.ts), [src/host/services/usage.ts](../../bundles/runtime/runtime/src/host/services/usage.ts)).
- The durable records and the event streams are the source of replay. The process holds only live state: the leases, the Threads' queues, abort controllers and subscribers. It takes work up on its own only through recovery at startup and adoption. The host runs as one instance, so its Socket.IO server needs no shared adapter ([src/host/domain/runtime.ts](../../bundles/runtime/runtime/src/host/domain/runtime.ts), [src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts)).

### Host stop

- A host stop is not a termination. The runtime's `onHostStopHook` step suspends every live Project: running prompts are aborted and recorded as `prompt.paused { reason: 'host_stopped' }`, queued inputs stay accepted and unfinished, `onThreadsClosingHook` fires for each Thread, the lease is released, the Project's owner is cleared, and the Project is written back as `queued` with its non-terminal Threads `ready`. A lease that will not release leaves the Project `queued` with `sandbox_release_failed`. After the stop, `createProject` rejects with `Doric is shutting down.` ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Recovery at startup

- The runtime's `onHostStartHook` step runs recovery at the startup stage `workspace_reconciliation`, before the host listens, and logs `Workspace reconciled` with the counts; recovery, host stop and handover are also described in the runtime README's [Recovery, host stop and handover](../../bundles/runtime/runtime/README.md#recovery-host-stop-and-handover) ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts)). Recovery runs four steps in order ([src/host/lifecycle.ts](../../bundles/runtime/runtime/src/host/lifecycle.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts)):
  1. Threads are reconciled. A prompt whose run started and recorded no pause gets `prompt.paused { reason: 'host_restarted' }`. A non-terminal Thread becomes `ready`, with no active prompt and no error code other than `storage_low`; a Thread left `cancelling` becomes `cancelled`.
  2. Projects are reconciled. A non-terminal Project becomes `queued`, with no error code; a Project left `cancelling` becomes `cancelled`, so a restart never revives work the reader terminated.
  3. The prompts the host owes are taken up: every unfinished prompt that was not superseded, that the reader did not stop and that no storage pause holds, on a Thread whose gate is open. A prompt already taken up twice (`attemptBudget`, counted from its `prompt.resumed` events) is closed as a failure with the code `resume_exhausted` instead. Each other prompt is queued again, Project by Project, in the order the log accepted them, appending `prompt.resumed { attempt }`, so it continues from the provider history stored as its run advanced. Prompts that closing an exhausted delegated prompt delivers to its parent are queued in the same pass.
  4. Every other non-terminal Project is brought back, newest first.
- Bringing a Project back loads it and its Threads and starts its acquisition in the background, so a full pool never holds up the listener. The Projects of step 3 are brought back first, so they acquire first. A finished prompt is never run again ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- A Thread whose gate is closed keeps it across the restart: neither its queued inputs nor its interrupted prompt run until the reader resumes it. A storage pause that was stored also survives the restart and never resumes on its own ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts)).
- `RecoverySummary` counts `interruptedThreads` and `interruptedProjects`, the records moved back to `ready` and `queued`, and `resumedPrompts` ([src/contracts/runtime.ts](../../bundles/runtime/runtime/src/contracts/runtime.ts)).
- The `resume_exhausted` message reads `The run was interrupted three times by a host restart and was not resumed again. The work may be incomplete; send the prompt again to continue.` The budget bounds automatic recovery only: the reader can always take an unfinished prompt up ([src/host/domain/prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts)).

### Generations

- When the kernel switches or respawns the generation of bundles, two runtime processes share one storage for a while. Each reacts to `onGenerationChangedHook` ([src/host/handover.ts](../../bundles/runtime/runtime/src/host/handover.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)):
  - the generation that becomes active runs recovery with the draining processes as the live owners (`recoverWith`), leaving their Projects in standby;
  - a generation that starts draining takes the work hold `runtime.drain`, drains its Projects (`drain`) and sends the peer signal `runtime.released` for each one it lets go, then drops the hold;
  - the active generation adopts (`adopt`) on each `runtime.released` from the `runtime` bundle and on each `lost` or `stopped` change. Adoptions run one at a time, after recovery.
- A process that cannot describe its generation records no owner and claims every Project ([src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).

### Terminating a Thread or a Project

- Terminating a Thread closes it and its whole subtree, and leaves the Project's lease and its other Threads alone. Terminating a Project closes all its Threads and then releases its lease. Neither undoes what the work did in the sandbox ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Closing Threads marks them closing before anything is awaited, aborts their running prompts, awaits `onThreadsClosingHook` and, for at most one second, the running prompts' own record of their end. Each Thread is then written `cancelling`; each queued input finishes `cancelled` (`The prompt was cancelled.`), or `failed` (`The project is unavailable.`) when the close carries a failure code: the Project's, or the Thread's own `persistence_failed` or `terminal_result_failed`; and once its run has ended the Thread becomes `cancelled`, or `failed` with that code ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- A Project's termination aborts its acquisition, writes `cancelling`, closes its Threads, and, once its acquisition, runs and closings have settled, releases the lease, clears its owner and writes `cancelled`, or `failed` with `sandbox_release_failed` when the release fails. Terminating a terminal Project answers it as it is ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Termination needs no live runtime. A Project another live process holds is terminated once this process adopts it. A Project no process holds is loaded and terminated without acquiring a sandbox. A Thread whose Project no process holds (a Project in standby waits for adoption first) takes itself and its non-terminal subtree through `cancelling -> cancelled` in the store, publishing each change, so a reader can terminate and then delete it without prompting it first ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Cancellation and lease release go on when a state write fails; the failure is logged (`Project cancellation persistence failed`, `Thread cancellation persistence failed`, `Project termination persistence failed`) ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Deleting removes records for good. A Thread is deleted only with its whole subtree, and only when every Thread of the subtree is terminal (`active` otherwise); an agent Thread is deleted only once archived (`forbidden` otherwise). A Project is deleted only when it and every Thread are terminal; its deletion removes its Threads, their histories, event streams and attachments, and calls `sandbox/v1.discard` with the Project's id, which removes the Project's containers and then its workspace volume under [`docker`](../../bundles/sandboxes/docker/README.md#durable-workspaces) and does nothing under [`firecracker`](../../bundles/sandboxes/firecracker/README.md#sandboxv1); a failed discard is logged and the deletion stands. The answers are `deleted`, `active`, `missing` and `forbidden`. The desktop terminates before it deletes ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts), [src/host/store/projects.ts](../../bundles/runtime/runtime/src/host/store/projects.ts), [src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [bundles/desktop/workspace/src/client/hooks/use-workspace.ts](../../bundles/desktop/workspace/src/client/hooks/use-workspace.ts)).

### Storage pressure and persistence failures

- The runtime checks storage before each dispatch and every three seconds during a run, as the runtime README's [Storage pressure](../../bundles/runtime/runtime/README.md#storage-pressure) also describes. A failed check, or a disk-full error from PostgreSQL (`53100`) or the OS (`ENOSPC`), pauses the Thread instead of closing it: the run is aborted, the Thread is `ready` with `queuePaused` and the error code `storage_low`, and `queue.paused { reason: 'storage_low' }` and, for a running prompt, `prompt.paused { reason: 'storage_low' }` are appended. Queued inputs stay accepted. Compose sets `DORIC_STORAGE_PATH=/var/lib/doric/postgresql` and mounts the PostgreSQL volume there read-only, so the check measures the database's filesystem; a native or remote-database deployment must point the variable at the filesystem that holds the database ([app/backend/doric-host/compose.yaml](../../app/backend/doric-host/compose.yaml), [README](../../app/backend/doric-host/README.md#storage-protection)) ([src/host/domain/storage-pressure.ts](../../bundles/runtime/runtime/src/host/domain/storage-pressure.ts), [src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- When even the pause cannot be written, the gate stays closed in memory, with the history and event the run could not store; resuming writes them before anything is dispatched, and they are lost if the host process dies first. While the pause is only in memory, Thread reads show it as `ready`, paused and `storage_low`, and the queue shows the storage error ([src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- Only an explicit resume that passes a fresh storage check reopens a storage pause; otherwise it answers `storage_low`, with the message `Execution paused: storage is low or unavailable. Free disk space above 10% and resume the queue.` ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- Any other failure to store a Thread's history or events closes the Thread as `failed` with `persistence_failed` and logs `Thread persistence failed`, so its queue never runs on stale history ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### The `runtime/v2` contract

`runtime/v2` 2.0.0 is `Runtime`, exported as `RuntimeV2`; the provider is [src/host/services/runtime.ts](../../bundles/runtime/runtime/src/host/services/runtime.ts) over [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts) ([src/contracts/runtime.ts](../../bundles/runtime/runtime/src/contracts/runtime.ts)). Its methods, with their inputs and outputs and the ones the window reaches, are listed in the runtime README's [`runtime/v2`](../../bundles/runtime/runtime/README.md#runtimev2). For this feature it serves:

- recovery, generation handover and host stop: `recover`, `recoverWith`, `adopt`, `drain` and `dispose`, as above; `drain` calls `released(projectId)` once per Project it lets go;
- the life of a Project: `createProject`, which creates a `queued` Project, starts its acquisition and rejects with `Doric is shutting down.` after the host stop; `project`, `projects` (a page, newest first), `projectActivity` (every Project with the latest `updatedAt` of it and its Threads and its most recently updated non-terminal Thread, newest first), `renameProject` and `setProjectColor` (`null` clears the color), which store the change and publish the Project, and `terminateProject` and `deleteProject`, as above; and `vmSsh(vmId)`, the SSH access of the live, non-closing Project whose sandbox has that id once its SSH access is ready;
- the notices: `watch` sends every notice (`event`, `threadUpdated`, `threadDeleted`, `projectUpdated`, `projectDeleted`) in publication order, after its commit; the notice type also names `terminalUpdated`, `terminalOutput` and `terminalRemoved`, which the runtime never publishes, since terminals stream through `terminal/v1`. `watchProject` sends one snapshot of a Project and its Threads (`project: null` for an unknown Project), then the changes of that Project and its Threads.

- A watch subscribes to the notices before it reads the snapshot and holds back what arrives in between, so nothing is lost. `watchThread` sends each event sequence once; `watchProject` sends every held-back notice, even one the snapshot already reflects. A snapshot that cannot be read ends the stream with `ContractError('replay_failed', 'The snapshot could not be loaded.')`. The watch items are in the runtime README's [Watches](../../bundles/runtime/runtime/README.md#watches) ([src/contracts/watches.ts](../../bundles/runtime/runtime/src/contracts/watches.ts), [src/host/services/watches.ts](../../bundles/runtime/runtime/src/host/services/watches.ts)).

### The `runtime.threads/v1` contract

`runtime.threads/v1` 1.8.0 is `RuntimeThreads`, exported from [src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts); the provider is [src/host/services/threads.ts](../../bundles/runtime/runtime/src/host/services/threads.ts) over [src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts). Its methods, with their inputs and outputs, are listed in the runtime README's [`runtime.threads/v1`](../../bundles/runtime/runtime/README.md#runtimethreadsv1); the ones below ignore the call's scope. The controls a prompt uses on its direct children (`spawn`, `list`, `get`, `events`, `send`, `restart`, `interrupt`, `terminate`) are described in [delegation.md](delegation.md); `setThreadCwd` in [cwd-tool.md](cwd-tool.md); `setThreadExecution` in [per-thread-model.md](per-thread-model.md); `archiveThread`, `restoreThread`, `setThreadPinned` and `viewThread` in [thread-archive.md](thread-archive.md); `retry`, `steer`, `resume`, `pause`, `resumeQueue`, `queuedPrompt`, `editQueued`, `removeQueued` and `compact` in [prompt-control.md](prompt-control.md); `usage` in [usage.md](usage.md).

- Threads: `createThread` answers as above; `thread` shows a storage pause held only in memory, and `storedThread` answers the stored record as it is; `threads` pages a Project's Threads, or one parent's children, newest first, and `projectThreads` lists every Thread of a Project oldest first; `renameThread` stores the name and publishes the Thread, and `terminateThread` and `deleteThread` work as above.
- Input: `prompt` accepts the reader's input and `rewind` replaces an edited turn, as above; both answer `forbidden` for an agent Thread. `prompt` rejects an empty prompt; `rewind` checks it only when it queues the edited text, so an empty one truncates the turn and then rejects ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)). `instruct({ id, prompt, reason, promptId?, interrupt?, retain? })` is a bundle's instruction to the Thread, agent Threads included, with the source `{ kind: 'bundle', bundleId, reason }`. It brings the Project back first, as input does, and is delivered as a steer of `promptId`, or of the running prompt when none is given; it is queued when nothing runs, when `promptId` names a prompt other than the running one, or when the Thread is paused, interrupting, stopping or waiting on storage. `interrupt` aborts the current step; `retain` asks the executor to keep it as a standing instruction. It answers `steered` or `queued` with the prompt id, or `missing` or `inactive`.
- Events and the queue: `threadEvents` answers the events after a cursor with the Thread's last sequence, and `storedEventsAfter` the stored events with no check of the Thread record; `queue` answers the queue, where a storage pause shows as paused with the storage error; `watchThread` sends one snapshot of the Thread with the events after the cursor, then its events, gap-free and each sequence once, and its updates and deletion.
- `enqueueTerminalResult` and `failTerminalResult` deliver a background terminal's result to its Thread, or record that it never arrived, as [terminal.md](terminal.md) describes.

- `enqueueTerminalResult` delivers the redacted text, with the source `terminal`, to a Thread the process holds live: as a steer of the running prompt, read at its next safe point, or into the queue when nothing runs or the Thread is paused, interrupting, stopping or waiting on storage. It does nothing for a closing Thread or Project; a failed delivery closes the Thread as `failed` with `terminal_result_failed`. For a Thread the process does not hold, `enqueueTerminalResult` does nothing and `failTerminalResult` logs `Terminal result delivery failed` ([src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).

### Hooks

`runtime.hooks/v1` 1.2.0 holds five observe hooks; their inputs are in the runtime README's [`runtime.hooks/v1`](../../bundles/runtime/runtime/README.md#runtimehooksv1) ([src/contracts/hooks.ts](../../bundles/runtime/runtime/src/contracts/hooks.ts), [src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts), [src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)). A handler's failure never fails the operation that fired it.

- `onProjectReadyHook` and `onProjectClosingHook` fire after a Project's `ready` and `cancelling` commit, without being awaited.
- `onThreadsClosingHook` is awaited where Threads close: termination, a close for a failure, host stop, and a draining Project. It is not fired for an empty list.
- `onPromptStartedHook` is awaited after `prompt.started`, outside the Project's lock, before the executor runs, so an instruction a handler gives is read before the first model request.
- `onThreadCwdChangedHook` is awaited after a change of a Thread's `cwd` or `cwdRepo`, before the change answers its caller ([cwd-tool.md](cwd-tool.md)). Resetting a directory missing from a reacquired sandbox fires it without awaiting it, because the reset holds the Project's lock that a handler's own calls need ([src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
