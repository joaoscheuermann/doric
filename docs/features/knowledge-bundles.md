# Feature: Knowledge bundles

- Status: `implemented`

## Problem

An agent that works in a repository needs to know what each file holds before it reads it. Reading every source file costs context and time. The repository needs a knowledge base that describes every file once, is regenerated cheaply when files change, and that an agent can search, without the code leaving the machine for any provider the caller did not choose.

The knowledge base is written in the Open Knowledge Format (OKF). An OKF bundle is a directory below `<root>/.agents/bundles` that holds one Markdown concept per source file and an `index.md`; it is not a Doric bundle. A concept is a Markdown file with YAML front matter that describes one source file.

## Decisions

- The feature has no bundle. It is two standalone units: the library [`okf`](../../packages/okf/README.md) (`packages/okf`), which generates Open Knowledge Format (OKF) bundles, and the tool package [`tool-okf`](../../tools/okf/README.md) (`tools/okf`), which searches them. No bundle or application registers the `okf_search` tool; a caller that wants it registers the definition itself.
- `generate` has no built-in provider: the caller injects an `LlmProvider` and a model.
- An OKF bundle is written only below `<root>/.agents/bundles`, also after existing symbolic links and junctions are resolved.
- Every readable source file is sent unchanged to the provider the caller configured. Content privacy belongs to OKF and its host, not to a flag in the [`llms`](../../packages/llms/README.md) package.
- Each file that is not cached costs exactly three sequential, tool-free, plain-text completions at temperature zero: an analysis, a description and tags. No call asks for structured output or injects a response schema. The prompts guide the form of the description and the tags; at runtime every non-empty trimmed answer is accepted.
- A known failure is an `OkfError` the package builds, with fixed and safe details. `isOkfError` is the only trust check before a host logs one; `instanceof`, the prototype and the shape of the fields are not.
- The host owns logging. Neither an error nor a host log holds an absolute path, provider or filesystem diagnostics, a source body, a prompt, a model response, provider or model identity, a credential, or a caught message, name, stack, code or cause.
- Search is lexical, deterministic and read-only: it writes nothing, uses no network and follows no symbolic link inside the bundle root. The unregistered `okf_search` tool is described in [`tools/okf/README.md`](../../tools/okf/README.md); its search steps are in [Behavior](../../tools/okf/README.md#behavior).

## Current behavior and contracts

The full contracts are in the READMEs of the two units: [`packages/okf/README.md`](../../packages/okf/README.md) for generation and [`tools/okf/README.md`](../../tools/okf/README.md) for search. This document describes the flow between them.

### The flow

1. A host calls `generate(config, root, output?)` of `okf` ([generate.ts](../../packages/okf/src/lib/generate.ts)). The repository runner, `npm run okf -- <model-id>`, is one such host ([scripts/okf.mjs](../../scripts/okf.mjs)).
2. `generate` discovers the repository's files, sends each new or changed one through three completions, and writes one concept per file and a project index into the bundle directory, by default `<root>/.agents/bundles/project` ([generate.ts](../../packages/okf/src/lib/generate.ts)).
3. An agent calls the `okf_search` tool of `tool-okf`, which lists and ranks the concepts under `<workspace>/.agents/bundles` through the `Sandbox` of [`sandbox`](../../packages/sandbox/README.md) ([okf.ts](../../tools/okf/src/lib/okf.ts)).

### Generation

- **Input.** `generate` takes an `OkfConfig` with the required `provider` and `model` and the optional `effort`, `promptTarget`, `batchSize`, `ignore` patterns, `signal` and `progress` observer ([types/okf.ts](../../packages/okf/src/lib/types/okf.ts), [constants.ts](../../packages/okf/src/lib/constants.ts)). The shapes and defaults are in [Entry point and exports](../../packages/okf/README.md#entry-point-and-exports).
- **Output.** A root that does not exist or is not a directory rejects with `OKF_ROOT_INVALID`. Without `output`, the bundle is `<root>/.agents/bundles/project` (`defaultOutput(root)`). Any output must be a child of `<root>/.agents/bundles`, and `<root>/.agents/bundles` must stay inside the root, before and after symbolic links and junctions are resolved; otherwise `generate` rejects with `OKF_OUTPUT_INVALID` ([generate.ts](../../packages/okf/src/lib/generate.ts)). The steps of a run are in [What `generate` does](../../packages/okf/README.md#what-generate-does).
- **Discovery.** Every regular file below the root is a source unless a name in its path starts with `.` (so nothing under `.agents`, `.doric`, `.git` or `.github` and no file such as `.env` is read), a `.gitignore` rule or the caller's `ignore` patterns remove it, it is a symbolic link, or its content is binary. `.gitignore` files are rules, not sources. Files are processed in sequential batches of `batchSize`, the files of a batch concurrently. A file that cannot be read rejects with `OKF_DISCOVERY_FAILED` ([walk.ts](../../packages/okf/src/lib/walk.ts), [git.ts](../../packages/okf/src/lib/git.ts)). The rules are in [Discovery](../../packages/okf/README.md#discovery).
- **Type and parsing.** A file's type is its lowercase final extension, or `no-extension` ([detect.ts](../../packages/okf/src/lib/detect.ts)). Tree-sitter strictly parses the TypeScript, JavaScript and JSON types on every run, cache hit or not, and extracts the module interface of the TypeScript and JavaScript types; every other type is plain text. A failure to size the parser's buffer or to parse rejects with `OKF_SOURCE_PARSE_FAILED`, and a syntax error with `OKF_SOURCE_SYNTAX_INVALID`, before the file reaches the provider ([interface.ts](../../packages/okf/src/lib/interface.ts)). The types, the buffer size and the interface are in [Parsing and the module interface](../../packages/okf/README.md#parsing-and-the-module-interface).
- **Cache.** Each concept's `hash` is a SHA-256 of the generation recipe: the source's hash, path, type and interface, the fixed versions of the parser, the extractor, YAML, the concept schema, the plain-text fields and the pipeline, the prompt target and the three prompts, and the provider id, model and effort ([recipe.ts](../../packages/okf/src/lib/recipe.ts)). When the existing concept's YAML holds that exact hash, the file is a cache hit and makes no provider call ([concept.ts](../../packages/okf/src/lib/concept.ts), [generate.ts](../../packages/okf/src/lib/generate.ts)). The recipe is in [Cache](../../packages/okf/README.md#cache).
- **Completions.** On a cache miss, three completions run in order, each with the system prompt of its stage for the `promptTarget` from the `okf` package. The prompts are loaded once per run; an invalid `promptTarget` or a missing or empty prompt rejects with `OKF_PROMPT_LOAD_FAILED`, with no fallback to `default` ([constants.ts](../../packages/okf/src/lib/constants.ts), [generate.ts](../../packages/okf/src/lib/generate.ts), [prompts.ts](../../packages/okf/src/lib/prompts.ts), [agent.ts](../../packages/okf/src/lib/agent.ts), [summarize.ts](../../packages/okf/src/lib/summarize.ts)). An empty answer rejects with `OKF_SUMMARY_FAILED`, `OKF_DESCRIPTION_FAILED` or `OKF_TAGS_FAILED`, and no later call or concept write happens:
  1. The analysis receives the file's path, type, module interface when there is one, and its exact content. Its answer must not begin with YAML front matter.
  2. The description receives only the analysis. Any non-empty trimmed answer is kept as it is.
  3. The tags receive the same analysis. A plain-text, JSON or fenced answer is split into tags that keep their case, punctuation, order and duplicates; an answer in none of these forms, or one that leaves no tag, becomes one tag holding the whole trimmed answer.

  The messages, the output-token cap and the tag forms are in [Model calls](../../packages/okf/README.md#model-calls), and the prompts in [Prompts](../../packages/okf/README.md#prompts).

- **Concepts and index.** Each source has one concept below the output, named so that no concept takes the reserved name `index.md` or `log.md`. Its YAML front matter holds the source's identity and type, `description`, `tags`, `timestamp`, `hash`, and `imports` and `exports` when extracted; its Markdown body is the analysis ([tree.ts](../../packages/okf/src/lib/tree.ts), [concept.ts](../../packages/okf/src/lib/concept.ts)). After all files, `generate` writes `<output>/index.md`, a deterministic tree of the represented files with their descriptions, and resolves with `GenerateResult`: the canonical `root`, `output` and `index`, the represented `files`, and the `generated` and `cached` counts ([generate.ts](../../packages/okf/src/lib/generate.ts)). The concept and index formats are in [Data written](../../packages/okf/README.md#data-written).
- **Progress.** The `progress` observer receives a `ProgressEvent` for the start and end of the run, of each file, a cache miss, each completion stage on a miss, and of the index. A file is named only by its normalized repository-relative path, and the events of concurrent files may interleave. An observer that throws stops generation with its own exception, and the observer receives no further event. When generation rejects, the other files of the same batch are not cancelled: they keep calling the provider, writing concepts and sending progress events ([walk.ts](../../packages/okf/src/lib/walk.ts), [types/okf.ts](../../packages/okf/src/lib/types/okf.ts), [generate.ts](../../packages/okf/src/lib/generate.ts)). The events are listed in [Progress events](../../packages/okf/README.md#progress-events).

### Failures

- Every known failure rejects with an `OkfError` whose closed `code` and `stage`, fixed `hint`, a fixed `message` that names the `source` for the source-scoped stages, and, for those stages, the normalized repository-relative `source` come from the package. It carries no cause. `OkfError` cannot be constructed outside the package, and `isOkfError(value)` recognizes only errors the package created ([okf-error.ts](../../packages/okf/src/lib/classes/okf-error.ts)). The codes with their stages, messages and hints are in [Errors](../../packages/okf/README.md#errors).
- The completion boundary discards provider diagnostics and causes: a failed or empty completion becomes the stage's `OkfError` ([agent.ts](../../packages/okf/src/lib/agent.ts), [generate.ts](../../packages/okf/src/lib/generate.ts)).
- A cancelled `signal` rejects generation: between files with the signal's `reason` (an `AbortError` when `abort()` is given none), and during a completion with a new `AbortError` that carries nothing from the provider ([walk.ts](../../packages/okf/src/lib/walk.ts), [agent.ts](../../packages/okf/src/lib/agent.ts)). Any other failure escapes unchanged, for example the plain `Error` for a `batchSize` that is not a positive integer, and the host replaces it with fixed output ([walk.ts](../../packages/okf/src/lib/walk.ts), [generate.ts](../../packages/okf/src/lib/generate.ts)).

### The repository runner

- `npm run okf -- <model-id>` generates this repository's bundle at `.agents/bundles/project`; without a model it logs `Usage: npm run okf -- <model-id>` and exits with code 1. It builds the OpenAI provider of [`llms`](../../packages/llms/README.md), which calls the Responses API at `OKF_BASE_URL` (default `http://localhost:1234/v1`) with the optional `OKF_API_KEY`, and gives that provider a disabled logger ([scripts/okf.mjs](../../scripts/okf.mjs), [openai.ts](../../packages/llms/src/lib/providers/openai.ts)).
- It logs each progress event to stderr with `pino` and `pino-pretty`. For an `OkfError` it logs only the error's fixed fields; for a cancellation (a `DOMException` named `AbortError`) it logs `OKF generation cancelled`, and for any other failure `OKF generation failed unexpectedly` with the fixed hint `Retry the operation or report the failure.`; neither message holds anything from the failure. A failure sets the exit code 1 ([scripts/okf.mjs](../../scripts/okf.mjs)). The log fields are in [Repository runner](../../packages/okf/README.md#repository-runner).

### Search

- `createTool({ workspaceRoot, sandbox })`, where `sandbox` is a `Sandbox` of [`sandbox`](../../packages/sandbox/README.md) that holds the workspace, returns the `okf_search` tool definition. Its input is `{ query, bundle?, limit? }`; without `bundle` it searches every bundle under `<workspaceRoot>/.agents/bundles` ([okf.ts](../../tools/okf/src/lib/okf.ts), [types/okf.ts](../../tools/okf/src/lib/types/okf.ts)). The input and output shapes are in [API](../../tools/okf/README.md#api).
- It lists the concepts with `find` through the sandbox, without following symbolic links and without any file named `index.md` or `log.md`, and parses each concept's YAML front matter, which must hold a `type`; a concept it cannot read or parse is skipped and counted ([okf.ts](../../tools/okf/src/lib/okf.ts)). The fields it reads are in [Bundle data](../../tools/okf/README.md#bundle-data).
- It scores each concept lexically by the query's terms and phrase in the metadata and the body, drops the concepts that score 0 from the results and from `total`, and returns the best first, with a stable tie-break, within a bound on the output. A search that cannot run returns an `error` message instead of results ([okf.ts](../../tools/okf/src/lib/okf.ts)). The weights are in [Ranking](../../tools/okf/README.md#ranking), the bounds in [Limits](../../tools/okf/README.md#limits) and the messages in [Errors](../../tools/okf/README.md#errors).
