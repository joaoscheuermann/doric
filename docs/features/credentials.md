# Feature: Credentials

- Status: `implemented`

## Problem

Doric authenticates to model providers, to GitHub and to MCP servers, and commits in a Project's sandbox under a Git identity. Each authentication needs a secret value that must never reach the model, a tool result, an event, a log line, a response of the host's API or a file of the repository; the Git identity is not a secret. The reader needs one place to store such values by name, to choose them in the configuration, and to rotate them without restarting a running Project. A bundle that brings an integration of its own needs to add its own kind of credential without changing the store.

## Decisions

- A credential is named and has one kind, and the kind fixes its fields: a field the kind requires must be present, and a field it does not list must be absent. One rule, `credentialFieldsSatisfied` in `bundle/contracts`, decides this for the core's validation and for the host's REST routes, so the two cannot disagree.
- The platform defines two kinds, `API_TOKEN` (one secret: a provider key or a token) and `USERNAME_PASSWORD` (a username and a secret). Every other kind is registered by a bundle with `secrets/v1.registerKind`. The `git` bundle registers `GIT`, a username and an email with no secret: it is the identity commits are made with, not authentication. A kind name matches `^[A-Z][A-Z0-9_]{1,31}$`, and a name another registration in the same view already holds is refused with `duplicate_credential_kind`.
- A secret is write-only. No answer of the host carries it: a credential is described by its fields and `hasSecret`, which says only whether a non-empty secret is stored. A form that edits a credential therefore starts with the secret field empty.
- A secret is stored only in the `credential` table, as an AES-256-GCM envelope that names its version, under the base64 32-byte key in the host process's environment variable `DORIC_CREDENTIAL_KEY`. The version leaves room for another key; the host writes and reads only the version `v1`. The host refuses to start when a stored credential holds a secret and the key is missing, and whenever the key is malformed; a secret it cannot decrypt is an error, never an empty secret.
- A reference resolves in one of two ways. A provider or a configuration names a credential by id. An integration that names none asks for the kind it needs: no match leaves it off, and more than one match is refused (`credential_ambiguous`) rather than answered with the first.
- The GitHub token asked for by kind is chosen only among the `API_TOKEN` credentials no configured provider names, so a provider's key is never written into a sandbox as the GitHub token.
- No table references the `credential` table. A credential is protected from deletion by reference sources registered with `secrets/v1.registerReferences`: `delete` answers `referenced` while a source names the credential, and checks this before it touches the store. The `host-config` bundle registers the credentials the stored configuration names: each provider's `secret` fields, `gitCredentialId` and `githubCredentialId`. A credential named only in the tool configuration stays deletable.
- `settings/v1.set` and the writes of `secrets/v1` run in one write queue of the core, so a configuration never names a credential that a concurrent delete removes. This, like the credential cache, assumes one host process per database.
- An update keeps a field that is absent or `null` and sets a field to any string it carries, `''` included. A credential's kind cannot change after it is created.
- A tool result goes to the model, so the contracts a tool handler reaches expose capabilities and never a credential read. Of the tool bundles, `git` uses `secrets/v1` only to register `GIT`, `terminal` only to read the redaction list, and `mcp` reads only the credentials its own server's entries name, when that server connects, into that server's headers or environment, and the `MCP_TOKEN` credentials of that server's own OAuth sign-in, never into a tool argument or result; it also registers, stores, replaces and deletes the `MCP_TOKEN` credentials of its servers' sign-ins.
- A window reaches `secrets/v1.list`, `create`, `update` and `delete` only; `resolve`, `resolveByKind` and `redactions` are refused to it.
- The Git identity and the GitHub token are applied to a Project's sandbox per lease and never built into its image. They are applied again when the pair the configuration names differs from the pair the runtime last tried to apply, so a rotated secret reaches a running Project; an empty pair or an absent token writes nothing. The token is passed to the sandbox only in the environment of the process that writes it, never in a command line or a tool argument, and the runtime does not log it. A failure to apply them is a warning that names the Project alone and never fails the prompt.
- The redaction list is every non-empty stored secret, followed by every secret added with `view().addRedaction`. `secrets/v1.watchRedactions` delivers the whole list on subscribe and after every create, update, effective delete and added redaction; a write resolves only after every listener received the list it produced, and a failing listener never fails the write.
- The runtime adds the GitHub token it applies again to a running sandbox to its own redaction list, so that token stays redacted in what the runtime stores whether or not the store still holds it.
- `events/v1` redacts an event with `secrets/v1.redactions()`, which loads the credentials when needed: an event is never written unredacted, and a failed load fails the append.
- The window's `log/v1` does not redact: a window never holds a resolved secret.

### Kinds and fields

- A credential has an `id` (a UUID the core assigns on create), a `kind`, a `name`, and the fields `username`, `email` and `secret`, each optional by type ([packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts), [bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts)).
- A kind definition is `{ id, required, optional, label? }` over those three fields; a field cannot be both required and optional ([packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts)).

| Kind                | Registered by | Required            | Optional |
| ------------------- | ------------- | ------------------- | -------- |
| `API_TOKEN`         | the platform  | `secret`            | none     |
| `USERNAME_PASSWORD` | the platform  | `username`,`secret` | none     |
| `GIT`               | `git`         | `username`,`email`  | none     |
| `MCP_TOKEN`         | `mcp`         | `secret`            | none     |

- The kinds of the table are defined in [packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts), [bundles/features/git/src/host/credentials.ts](../../bundles/features/git/src/host/credentials.ts) and [bundles/features/mcp/src/host/credentials.ts](../../bundles/features/mcp/src/host/credentials.ts).
- A field counts as present when its value is defined, so `''` is a present value. A refused write is `credential_invalid` with the message `A <KIND> credential requires <fields> and carries no other field.`, or `… and may also carry <fields>.` for a kind with optional fields ([packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts), [bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts)).
- Registrations are partitioned by generation: `kinds` answers the built-in kinds and the kinds the call's generation sees, disposing a registration releases its name, and a kind no visible registration names is refused with `unknown_kind` on `create`, `update`, `resolve` and `resolveByKind`. A stored row of such a kind is still listed ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts)).
- The `git` bundle registers `GIT` at activation, before any start step reads a credential ([bundles/features/git/src/host/index.ts](../../bundles/features/git/src/host/index.ts)).

### The store and its key

- The `credential` table holds `id`, `kind`, `name`, `username`, `email`, `secret`, `created_at` and `updated_at`, with `(kind, name)` unique. A second credential of one kind with one name is refused with `credential_name_taken` ([bundles/foundation/postgres/prisma/schema.prisma](../../bundles/foundation/postgres/prisma/schema.prisma), [bundles/foundation/postgres/src/host/secrets/backend.ts](../../bundles/foundation/postgres/src/host/secrets/backend.ts)).
- A non-empty secret is stored as `v1:<nonce>:<tag>:<ciphertext>`, each part base64, with a random 12-byte nonce. The empty secret is stored as `''`; an absent secret as `NULL` ([bundles/foundation/postgres/src/host/secrets/envelope.ts](../../bundles/foundation/postgres/src/host/secrets/envelope.ts), [bundles/foundation/postgres/src/host/secrets/backend.ts](../../bundles/foundation/postgres/src/host/secrets/backend.ts)).
- `DORIC_CREDENTIAL_KEY` is read from the host process's environment. It must be 43 base64 characters and one `=`, which decode to 32 bytes; a malformed key fails every `list`, `get` and `put` of the backend with `DORIC_CREDENTIAL_KEY must be 32 base64-encoded bytes.`, while `delete` works without the key. An unset or blank key is no key ([bundles/foundation/postgres/src/host/secrets/backend.ts](../../bundles/foundation/postgres/src/host/secrets/backend.ts), [bundles/foundation/postgres/src/host/secrets/envelope.ts](../../bundles/foundation/postgres/src/host/secrets/envelope.ts)).
- Without a key, reading fails with `credential_key_required` while any stored credential holds a non-empty secret, and writing any defined secret fails with `credential_storage_unavailable`. An envelope that is not `v1` or that the cipher rejects fails with `credential_unreadable` ([bundles/foundation/postgres/src/host/secrets/backend.ts](../../bundles/foundation/postgres/src/host/secrets/backend.ts)).
- At startup the core's start step connects the storage backend, enters the stage `credential_activation`, logs `Activating stored credentials` and lists the credentials, so a missing or unusable key stops the host there ([bundles/foundation/core/src/host/secrets/activation.ts](../../bundles/foundation/core/src/host/secrets/activation.ts)).

### `secrets/v1`

- The core reads the backend once, on the first call, and answers every read from its cache after that; a failed load is retried by the next call. The cache starts in the backend's order (by name), each save sorts it by `localeCompare` of the name, and a removal keeps the order ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts), [bundles/foundation/core/src/host/secrets/cache.ts](../../bundles/foundation/core/src/host/secrets/cache.ts)).
- `list` and `describe` answer the public view `{ id, kind, name, username?, email?, hasSecret }`, which omits an empty username or email and never carries the secret. `resolve({ id })` answers the credential with its secret, or fails with `credential_missing` (`Credential <id> is not stored.`) ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts), [bundles/foundation/core/src/host/secrets/cache.ts](../../bundles/foundation/core/src/host/secrets/cache.ts)).
- `resolveByKind(kind, { exclude? })` answers the one credential of the kind outside `exclude`, `undefined` when there is none, and fails with `credential_ambiguous` (`More than one <KIND> credential is stored; name the one to use.`) when there are several ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts)).
- `create`, `update` and `delete` run in the core's write queue. `create` checks the kind and the fields, then stores the row. `update` fails with `credential_missing` for an unknown id and with `credential_kind_immutable` when it names another kind, merges the fields, and checks the result against the kind. `delete` answers `referenced`, `missing` or `deleted`; a deleted credential stops resolving at once ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts), [bundles/foundation/core/src/shared/writes.ts](../../bundles/foundation/core/src/shared/writes.ts)).
- `view()` is the in-process, synchronous view of the cache (`list`, `redactions`, `addRedaction`); before the credentials are loaded it fails with `unavailable`. `view` and `registerReferences` are local to the host process ([packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts), [bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts)).
- `watchRedactions(listener)` sends the whole redaction list once the credentials are loaded; when the load fails, the listener waits for the next change. It sends the list again after every create, update, effective delete and added redaction. A create, update or delete resolves only after every listener received its list; the list sent after an added redaction is not awaited. A listener that throws or rejects fails nothing ([bundles/foundation/core/src/host/secrets/facade.ts](../../bundles/foundation/core/src/host/secrets/facade.ts), [bundles/foundation/core/src/host/secrets/cache.ts](../../bundles/foundation/core/src/host/secrets/cache.ts)).
- The full method list, inputs, outputs and error codes are in [packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts).

### Managing credentials

- The settings window's Credentials section reaches `secrets/v1.list`, `create`, `update` and `delete` through the desktop bridge. It manages `API_TOKEN`, `USERNAME_PASSWORD` and `GIT`, and leaves listed credentials of any other kind, such as `MCP_TOKEN`, out of its table ([bundles/desktop/settings/src/client/api/settings-api.ts](../../bundles/desktop/settings/src/client/api/settings-api.ts), [bundles/desktop/settings/src/client/domain/config.ts](../../bundles/desktop/settings/src/client/domain/config.ts)).
- The section is a table of the stored credentials, showing whether each holds a secret. "Add credential" and each row's edit open a dialog with the kind, the name and the fields the kind carries; the kind cannot change once the credential exists. The secret field, labelled Token for `API_TOKEN` and Password otherwise, opens empty; on an edit an empty field sends `null`, which keeps the stored secret, and a typed value replaces it. A field the kind does not carry is left out of the request ([bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx](../../bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx), [bundles/desktop/settings/src/client/domain/config.ts](../../bundles/desktop/settings/src/client/domain/config.ts)).
- "Add credential" or "Save credential" sends the write. A refused write is shown in the dialog, which stays open on what was typed; a success closes it and shows `Credential added.` or `Credential saved.`. A refused removal is an error toast, a success shows `Removed <name>.` ([bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx](../../bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx)).
- Before it calls the host, the window refuses with `invalid_input` a secret that is not 1 to 512 printable ASCII characters without whitespace (an update may also send `''` or `null`), and on create a blank username or one over 128 characters, with `The configuration is invalid.`; a malformed request, a kind it does not manage, a blank name or one over 128 characters, an email over 254 characters or not an address, and on update a blank username or one over 128 characters, with `The credential is invalid.`; and any other request that breaks the limits of the REST routes or does not fit its kind with `The credential does not match its kind.` It maps `credential_missing` to `The credential was not found.`, `credential_name_taken` and `credential_kind_immutable` to `The credential cannot perform this operation.` and `credential_storage_unavailable` to `The host cannot store credential secrets.` ([bundles/desktop/settings/src/client/api/settings-api.ts](../../bundles/desktop/settings/src/client/api/settings-api.ts)).
- Any other `secrets/v1` method called from a window is refused before resolution with `<contract> <method> is not available to the desktop.` ([packages/bundle/src/contracts/basic/secrets.ts](../../packages/bundle/src/contracts/basic/secrets.ts), [app/backend/doric-host/src/lib/bridge/socket.ts](../../app/backend/doric-host/src/lib/bridge/socket.ts)).
- The host's REST routes serve the same operations ([bundles/foundation/transport/src/host/routes/credentials.ts](../../bundles/foundation/transport/src/host/routes/credentials.ts), [bundles/foundation/transport/src/host/routes/input.ts](../../bundles/foundation/transport/src/host/routes/input.ts)):

| Route                     | Answer                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /credentials`        | 200 with the public view of every credential, of every kind.                                                                                                                                           |
| `POST /credentials`       | 201 with the public view of the new credential.                                                                                                                                                        |
| `PATCH /credentials/:id`  | 200 with the public view. For `username`, `email` and `secret`, an absent or `null` field keeps what is stored, `''` clears it, a value sets it; `name` may be absent, and `''` or `null` answers 422. |
| `DELETE /credentials/:id` | 204; 404 `credential_not_found`; 409 `credential_referenced`.                                                                                                                                          |

- A route body holds a trimmed `name` of 1 to 128 characters, a trimmed `username` of 1 to 128, an `email` of at most 256 that is an email address, and a `secret` of 1 to 512 characters with no line break. A body that breaks these limits, names a kind no registration holds, or does not fit its kind answers 422 `invalid_credential`; an id that is not a UUID answers 400 `invalid_credential_id`; an unknown id 404 `credential_not_found`; a kind change 409 `credential_kind_immutable`; a taken name 409 `credential_name_taken`; and a host without a key 503 `credential_storage_unavailable`. Any other failure, such as `credential_key_required` or `credential_unreadable`, answers 500 `internal_error` with `The request could not be completed.` Errors have the shape `{ error: { code, message } }` ([bundles/foundation/transport/src/host/routes/credentials.ts](../../bundles/foundation/transport/src/host/routes/credentials.ts), [bundles/foundation/transport/src/host/routes/input.ts](../../bundles/foundation/transport/src/host/routes/input.ts), [bundles/foundation/transport/src/host/errors.ts](../../bundles/foundation/transport/src/host/errors.ts)).

### References from the configuration

- The stored configuration holds no secret. A provider field of the kind `secret` holds the id of a stored `API_TOKEN` credential; `gitCredentialId` names a `GIT` credential and `githubCredentialId` an `API_TOKEN` credential ([bundles/foundation/host-config/src/host/config/schema.ts](../../bundles/foundation/host-config/src/host/config/schema.ts), [bundles/foundation/host-config/src/host/config/service.ts](../../bundles/foundation/host-config/src/host/config/service.ts)).
- `host-config/v1.replace` refuses a reference to a credential that is not stored with `<label> references a credential that is not stored.`, and one of the wrong kind with `<label> must reference a <KIND> credential, not a <kind> one.`; a direct `settings/v1.set` is refused by the settings space with `The configuration references a credential that is not stored.`, and so is every reference before the credentials are loaded ([bundles/foundation/host-config/src/host/configuration.ts](../../bundles/foundation/host-config/src/host/configuration.ts), [bundles/foundation/host-config/src/host/config/service.ts](../../bundles/foundation/host-config/src/host/config/service.ts)).
- `host-config` registers a reference source that answers the credentials the latest stored configuration names, so `delete` answers `referenced` for them ([bundles/foundation/host-config/src/host/configuration.ts](../../bundles/foundation/host-config/src/host/configuration.ts)).
- The provider page offers the stored `API_TOKEN` credentials for a `secret` field, and the Versioning section offers the `GIT` credentials for the Git identity and the `API_TOKEN` credentials for GitHub; choosing none removes the key from the configuration ([bundles/desktop/settings/src/client/domain/provider-fields.ts](../../bundles/desktop/settings/src/client/domain/provider-fields.ts), [bundles/features/git/src/client/settings/settings-versioning.tsx](../../bundles/features/git/src/client/settings/settings-versioning.tsx), [bundles/features/git/src/client/domain/credentials.ts](../../bundles/features/git/src/client/domain/credentials.ts)).
- A saved credential or configuration reaches the next request of any Project, running ones included. A provider's credential is the first of its `secret` fields that names one; the provider reads that secret through `secrets/v1.resolve` each time it calls the model, and a credential that cannot be resolved reads as `''` ([bundles/foundation/core/src/host/models/index.ts](../../bundles/foundation/core/src/host/models/index.ts), [bundles/foundation/core/src/host/models/providers.ts](../../bundles/foundation/core/src/host/models/providers.ts)).

### Git in the sandbox

- When a Project acquires its sandbox, the runtime resolves the Git identity and the GitHub token the configuration in force names and applies them. Before it takes new input for a running Project, it resolves them again and applies them only when they differ from the pair it last tried to apply, which it records even when the apply failed, and then adds the token to its redaction list. A pair that is empty, or a token that is absent, writes nothing, so a cleared choice or a deleted credential leaves the earlier identity and token in the sandbox until its lease ends. The token applied when the sandbox is acquired is not added to the runtime's list, and the terminal redacts only with the store's list ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The identity resolves by `gitCredentialId`, else by the kind `GIT`. The token resolves by `githubCredentialId`, else by the kind `API_TOKEN` among the credentials no configured provider's `secret` field names. A missing or ambiguous reference leaves its half off and logs the warning `A credential was not applied: <reason>` with the `projectId`. A resolved `GIT` credential without both a username and an email, or a token whose secret is empty, is left off with no warning ([bundles/runtime/runtime/src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts), [bundles/runtime/runtime/src/host/ports.ts](../../bundles/runtime/runtime/src/host/ports.ts)).
- The identity is applied as `git config --global user.name` and `user.email`. With a token, the runtime sets `credential.helper store`, writes `https://<user>:<token>@github.com` to `~/.git-credentials`, and writes `~/.config/gh/hosts.yml` for `github.com` with `git_protocol: https`, both under `umask 077`, so mode 0600. `<user>` is the identity's username, or `oauth2` without one. The token reaches each write only through an environment variable of that `sandbox.exec` call ([bundles/runtime/runtime/src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts)).
- Any failure logs `Git credentials could not be applied` with the `projectId` only ([bundles/runtime/runtime/src/host/domain/git-credentials.ts](../../bundles/runtime/runtime/src/host/domain/git-credentials.ts)).

### Other integrations

- Of the tool bundles, `git` calls `secrets/v1` only to register `GIT`, `terminal` only to read the redaction list (`redactions` and `watchRedactions`), and `mcp` resolves only the credentials its servers' entries name and the `MCP_TOKEN` credentials of their OAuth sign-ins, and registers, stores, replaces and deletes the `MCP_TOKEN` credentials of its servers' sign-ins ([bundles/features/mcp/src/host/index.ts](../../bundles/features/mcp/src/host/index.ts), [bundles/features/git/src/host/index.ts](../../bundles/features/git/src/host/index.ts), [bundles/features/terminal/src/host/redactions.ts](../../bundles/features/terminal/src/host/redactions.ts), [bundles/features/mcp/src/host/credentials.ts](../../bundles/features/mcp/src/host/credentials.ts)).
- An MCP server's header or environment entry may name a credential, whose secret the `mcp` bundle reads through `secrets/v1` when that server connects, into that server's headers or environment. An entry that names an `MCP_TOKEN` credential, or a credential with no `secret` field, is refused with `invalid_input`. `MCP_TOKEN` credentials hold a server's OAuth sign-in, are named `mcp:<serverId>:<part>`, and are read only by that server's sign-in. A credential an entry names is not protected from deletion ([bundles/features/mcp/src/host/credentials.ts](../../bundles/features/mcp/src/host/credentials.ts)).
- The `claude-login` bundle stores an authorization as the `API_TOKEN` credential named `Claude`, or replaces the secret of the one already stored ([bundles/features/claude-login/src/host/login.ts](../../bundles/features/claude-login/src/host/login.ts)).

### Redaction

- The host's `log/v1` replaces every entry of the redaction list with `[REDACTED]` in a record's message and in the string leaves of its fields; before the credentials are loaded it has nothing to redact ([bundles/foundation/core/src/shared/log.ts](../../bundles/foundation/core/src/shared/log.ts), [bundles/foundation/core/src/shared/redact.ts](../../bundles/foundation/core/src/shared/redact.ts)).
- `events/v1` redacts each event with `secrets/v1.redactions()` before it is stored ([bundles/foundation/core/src/host/events/facade.ts](../../bundles/foundation/core/src/host/events/facade.ts)).
- The runtime redacts what a conversation stores with the stored secrets followed by the tokens it applied again to running sandboxes ([bundles/runtime/runtime/src/host/domain/redactor.ts](../../bundles/runtime/runtime/src/host/domain/redactor.ts), [bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The terminal redacts its output with the list `secrets/v1.watchRedactions` delivers ([bundles/features/terminal/src/host/redactions.ts](../../bundles/features/terminal/src/host/redactions.ts), [Terminal](terminal.md)).
