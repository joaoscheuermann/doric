# Feature: Skills

- Status: `implemented`

## Problem

The agent works better when it follows written procedures for recurring kinds of work, but a system prompt that holds every procedure in full fills the context and the provider's prompt cache with text most prompts never use. Procedures come from three places: the bundles that ship them, the repository the agent works in, and the Project's MCP servers. The agent needs to know which procedures exist and when each applies, read one in full only when its work matches, see the list change when it moves to another directory or a server connects, and keep a procedure it loaded in effect after its history is summarized. The reader needs to see which procedure the agent loaded and from where.

## Decisions

- A bundle ships skills as files, `skills/<folder>/SKILL.md`, and the loader registers them through `skills/v1` on the bundle's behalf, once every bundle of the activation phase has activated, so a skill's `allowed-tools` resolves against every tool of that phase. A bundle that requires `skills/v1` may also register a skill from its host part's `activate`; such a skill's `allowed-tools` resolves only against the tools registered by then.
- `skills/v1`, provided by `core`, holds only bundle skills. The skills of the working directory and of other sources are read by `default` for each prompt run and never enter `skills/v1`.
- `alwaysAvailable` decides only where `default` puts a bundle skill: an always-available skill's body goes in the system prompt, every other skill is a row the model loads on demand. For tools the same option is recorded and never consulted.
- `load_skill` belongs to the prompt run, not to `tools/v1`. It is offered from the first request at which the run lists a skill to load, checks the name against the run's live list on every call, and its answer is exempt from the tool result cap.
- `default` reads skills from other bundles through `default.skill-sources/v1`, a contract it declares and does not provide, and that any number of bundles may provide at once (each provider provides it with `{ cardinality: 'many' }`). A bundle becomes a source by providing it; `default` imports nothing from a source and does not depend on it. `mcp` is such a source.
- The `# Skills` section of the system prompt the run builds is computed once per prompt run and stays the same for the whole run, so the provider's prompt cache holds. A change in the skills the run can load reaches the model as one "Skills changed" message instead.
- A skill the model loaded stays in effect after a compaction: the compaction writes one retained "Loaded skills" message with the skills it summarized away, and the `coding-workflow` entry is never left out of it for size.
- The skills of an MCP server are used without the per-skill approval or integrity (digest) checks that SEP-2640 describes: their instructions run only through the agent's tools, in the Project's sandbox.
- The `default` bundle draws each `load_skill` call in the conversation, through `chat.views/v1`. The chat holds no code of its own for skills.

## Current behavior and contracts

### Where skills come from

- **Bundle skill files.** A bundle's source keeps its skills at `src/skills/<folder>/SKILL.md`; the build checks each one and copies it to `skills/<folder>/SKILL.md` of the built bundle ([packages/bundle/src/build/cli.ts](../../packages/bundle/src/build/cli.ts)). [`default`](../../bundles/runtime/default/README.md) ships the `coding-workflow` skill, described in [coding-workflow.md](coding-workflow.md) ([bundles/runtime/default/src/skills/coding-workflow/SKILL.md](../../bundles/runtime/default/src/skills/coding-workflow/SKILL.md)). [`files`](../../bundles/features/files/README.md#skills), [`git`](../../bundles/features/git/README.md#skills), [`threads`](../../bundles/features/threads/README.md#skills) and [`web`](../../bundles/features/web/README.md#skill-files) ship skill files too; the always-available ones are `files`' `01-goal-directed-tool-use` and `threads`' `thread-delegation` ([bundles/features/files/src/skills/01-goal-directed-tool-use/SKILL.md](../../bundles/features/files/src/skills/01-goal-directed-tool-use/SKILL.md), [bundles/features/threads/src/skills/thread-delegation/SKILL.md](../../bundles/features/threads/src/skills/thread-delegation/SKILL.md)).
- **Skills a bundle registers itself.** [`openui`](../../bundles/features/openui/README.md#the-openui-skill) and [`papercraft`](../../bundles/features/papercraft/README.md#the-skill) require `skills/v1@^1.1.0` and register one skill each through `skills/v1` from their host part's `activate`, with `order` 3400 and 3410 and `alwaysAvailable` false. Such a registration happens while the bundle activates, before the phase ends, so its `allowed-tools` resolves only against the tools registered so far. `papercraft` leaves its skill out when `skills/v1` refuses it ([bundles/features/openui/src/host/index.ts](../../bundles/features/openui/src/host/index.ts), [bundles/features/papercraft/src/host/index.ts](../../bundles/features/papercraft/src/host/index.ts)).
- **Workspace skills.** The `.agents/skills/<folder>/SKILL.md` files of the Thread's working directory ([bundles/runtime/default/src/host/skills/sources.ts](../../bundles/runtime/default/src/host/skills/sources.ts)).
- **Source skills.** The skills each provider of `default.skill-sources/v1` lists. The [`mcp`](../../bundles/features/mcp/README.md#skills) bundle provides one over the Project's connected MCP servers ([bundles/features/mcp/src/host/index.ts](../../bundles/features/mcp/src/host/index.ts)).

### Registering bundle skills

- A `SKILL.md` is YAML frontmatter followed by a Markdown body, the skill's text. The frontmatter holds `name`, `description`, an optional `allowed-tools` (a list, or one string of names separated by spaces), an optional `alwaysAvailable`, an optional `order` and an optional `indexText`, which `skills/v1` recalculates. A frontmatter `allowedTools` or `body` key is overwritten with the values read from `allowed-tools` and the body, and any other key makes the file invalid ([packages/bundle/src/loader/skills.ts](../../packages/bundle/src/loader/skills.ts)).
- The loader finds a bundle's skills in lexical order of their folders, ignoring a folder without `SKILL.md`, and registers each through `skills/v1` with the bundle as caller, passing `alwaysAvailable` (false when the file does not say) and `order` ([packages/bundle/src/loader/skills.ts](../../packages/bundle/src/loader/skills.ts), [packages/bundle/src/loader/activate.ts](../../packages/bundle/src/loader/activate.ts)).
- Registration runs once every bundle of the activation phase has activated, in the kernel and in each host generation process alike, for each installed bundle still active, in activation order. It does not run when the host is in recovery ([packages/bundle/src/runtime/activation.ts](../../packages/bundle/src/runtime/activation.ts), [packages/bundle/src/loader/activate.ts](../../packages/bundle/src/loader/activate.ts), [packages/bundle/src/process/kernel.ts](../../packages/bundle/src/process/kernel.ts), [packages/bundle/src/process/runner-main.ts](../../packages/bundle/src/process/runner-main.ts)).
- A bundle whose skill cannot be read or parsed is quarantined with `skill_invalid`; one whose skill `skills/v1` refuses, with `registration_failed`; one that has skills while no `skills/v1` provider is active, with `missing_dependency`. Its registrations are undone and the active bundles that depend on it are quarantined with `dependency_quarantined` ([packages/bundle/src/loader/activate.ts](../../packages/bundle/src/loader/activate.ts), [packages/bundle/src/runtime/activation.ts](../../packages/bundle/src/runtime/activation.ts)).
- `skills/v1` (1.1.0, provided by [`core`](../../bundles/foundation/core/README.md#skillsv1)) decodes each skill with `SkillSchema` into a `SkillRecord`, which trims the text and refuses it empty, drops repeated `allowedTools` and recalculates `indexText`; the shapes are in the [`bundle` package README](../../packages/bundle/README.md#skills) ([packages/bundle/src/contracts/skill.ts](../../packages/bundle/src/contracts/skill.ts)).
- `register` refuses a name another visible skill holds with `duplicate_skill`, and an `allowedTools` entry that is not a tool the caller's `tools/v1` list holds with `unavailable_tool`. `list` answers every visible skill with its bundle, its `alwaysAvailable` and `order` options and its record, sorted by `order` with unordered skills last, then in registration order ([bundles/foundation/core/src/host/skills.ts](../../bundles/foundation/core/src/host/skills.ts), [packages/bundle/src/contracts/basic/skills.ts](../../packages/bundle/src/contracts/basic/skills.ts)).
- `tools/v1` records the `alwaysAvailable` option of a tool registration as well, and nothing reads it: the run offers every listed tool whatever the flag says ([bundles/foundation/core/src/host/tools.ts](../../bundles/foundation/core/src/host/tools.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### What a prompt run reads

- At the start of each prompt run, the executor of [`default`](../../bundles/runtime/default/README.md) reads, in parallel, the bundle skills from `skills/v1`, the workspace skills of the Thread's working directory and the skills of every source ([bundles/runtime/default/src/host/skills/sources.ts](../../bundles/runtime/default/src/host/skills/sources.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Bundle skills are split by `alwaysAvailable` and keep the `skills/v1` order. A failure of `skills/v1` fails the run ([bundles/runtime/default/src/host/skills/sources.ts](../../bundles/runtime/default/src/host/skills/sources.ts)).
- Workspace skills come from one command through `runtime.lease/v1`, given 5 seconds, that reads the first 4,096 bytes of at most 64 `SKILL.md` files in the shell's sorted order. A workspace skill's name is its folder's name and its description the frontmatter's `description`; a file without one is skipped. A missing provider, a failed command or a timeout gives no workspace skills ([bundles/runtime/default/src/host/skills/sources.ts](../../bundles/runtime/default/src/host/skills/sources.ts)).
- Each source's `list` is called with the working directory and given 5 seconds. A source that rejects, times out or answers what fails the contract's schema offers nothing this time and is logged once per prompt as `Skill source left out`. A provider whose bundle id is `cwd` is ignored ([bundles/runtime/default/src/host/skills/sources.ts](../../bundles/runtime/default/src/host/skills/sources.ts)).
- A Thread that runs as an agent is not offered the `coding-workflow` skill, as [coding-workflow.md](coding-workflow.md) describes ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### The `# Skills` section

- The section ends the system prompt the run builds; a `default.hooks/v1` `onBeforeModelRequestHook` handler may still change that prompt before each request ([default-agent.md](default-agent.md)). It holds the always-available skills under "Always-available skills", each as `### Skill: <name>` and its body, then "Skills to load" with up to three lists, each a table `| Skill | Description |`: "Built-in skills", "Workspace skills" and "MCP server skills", the last holding the skills of every source. An empty list is left out, and the section is empty when nothing is in it ([bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts), [bundles/runtime/default/src/host/prompts/skills-catalog.md](../../bundles/runtime/default/src/host/prompts/skills-catalog.md)).
- Always-available skills are taken in order while they fit in 16,000 characters; the first that does not fit and every one after it become rows at the front of the built-in list ([bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts)).
- A row's id, the locator, is the bundle skill's name, `cwd/<name>` for a workspace skill, and `<bundleId>/<group>/<name>` (or `<bundleId>/<name>` without a group) for a source's skill; a locator already taken gets the first free `~2`, `~3`, …. Rows of the built-in list fit in 8,000 characters, those of the workspace and source lists in 4,000 each: descriptions are cut to 500 characters, to 120 when the list still does not fit, and then trailing rows are dropped and counted ([bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts)).
- A dropped row keeps its locator and counts as offered, but `load_skill` does not accept it for the whole run, and a later "Skills changed" message never offers it, since the run treats it as already told ([bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts), [bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).

### `load_skill`

- The run adds `load_skill` after the other tools it offers, described in [default-agent.md](default-agent.md), and never registers it with `tools/v1`. It is offered from the first request at which the run lists a skill to load, and from then on ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Its input is `{ name }`, a locator. A name the run does not list now fails with `Unknown skill id "<name>".`, followed by the ids it accepts, or by `No skill can be loaded now.` when it lists none ([bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).
- A listed skill's text comes from its origin: a bundle skill's body as the run read it at its start; a workspace skill's file, read now through `runtime.lease/v1` (its body after the frontmatter, preceded by a line naming the file and the folder its paths are relative to); or a source's `read`, called now, whose text loses its frontmatter and is preceded by the origin sentence the source gives. The answer is `# Skill: <name>` followed by that text, cut to 64,000 characters. Every failed read fails with `The skill <name> could not be loaded: <reason>`; for a source that has no provider now, the `<reason>` is `The skill source <bundleId> is not available.` ([bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).
- When the history already holds that skill's latest load unchanged and not cut, the answer is `Skill <name> is already loaded above; follow it.` ([bundles/runtime/default/src/host/skills/load-skill.ts](../../bundles/runtime/default/src/host/skills/load-skill.ts)).
- Its answer reaches the model whole: it is exempt from the tool result cap that bounds every other tool ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Changes during a run

- Before every model request after the first, the run reads the Thread's working directory through `runtime.workspace/v1`, scans the workspace skills again only when the directory moved, and lists every source again; a source left out keeps its last list, and the skills of a source that has no provider now are dropped and count as gone. Bundle skills are not compared ([bundles/runtime/default/src/host/skills/live.ts](../../bundles/runtime/default/src/host/skills/live.ts)).
- When skills were added, or a skill shown as a row went away, the model receives one `<bundle-instruction bundle="default" reason="skills-changed">` message: the added skills as workspace and source tables fitted like the system prompt's, and, under `No longer available`, the ids of the shown rows that went away. The executor appends the message to the run's messages as a `user` message before the request, so it is stored in the Thread's history; it is not a steer, emits no event and uses no turn. `load_skill` accepts the added rows and refuses the removed ids from then on. A dropped row that goes away is not reported ([packages/agent/src/lib/agent.ts](../../packages/agent/src/lib/agent.ts), [bundles/runtime/default/src/host/skills/catalog.ts](../../bundles/runtime/default/src/host/skills/catalog.ts), [bundles/runtime/default/src/host/prompts/skills-changed.md](../../bundles/runtime/default/src/host/prompts/skills-changed.md), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- After a compaction during the run, the next check compares with the system prompt's lists again, so a change the summary replaced is told again; locators stay the same ([bundles/runtime/default/src/host/skills/live.ts](../../bundles/runtime/default/src/host/skills/live.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).

### Loaded skills across a compaction

- A compaction, automatic or manual, writes one `<bundle-instruction bundle="default" reason="loaded-skills">` message with the latest load of each skill loaded in the summarized span and not loaded again in the kept tail. It is a retained message, recorded in the history's `meta.retained` under `default:loaded-skills`: a compaction keeps retained messages verbatim after its summary and leaves them out of the summarizer's input, as the [`default` README](../../bundles/runtime/default/README.md#compaction) describes. The next compaction replaces this one rather than keeping it, and removes it when the span it summarizes holds no load ([bundles/runtime/default/src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts), [bundles/runtime/default/src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts)).
- Each entry is cut at 20,000 characters and marked as cut; the entries fit within min(100,000, `charBudget` / 4) characters, where `charBudget` is the configuration's `execution.contextCompaction.charBudget`, and an entry that does not fit is named in a list of skills to load again. The `coding-workflow` entry comes first and is never left out for the cap ([bundles/runtime/default/src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts), [bundles/runtime/default/src/host/prompts/loaded-skills.md](../../bundles/runtime/default/src/host/prompts/loaded-skills.md)).
- `load_skill` treats an entry of that message as a load already in the history, so a skill kept whole answers the "already loaded" note ([bundles/runtime/default/src/host/skills/loaded.ts](../../bundles/runtime/default/src/host/skills/loaded.ts)).

### Skill sources

- `default.skill-sources/v1` 1.0.0 has two methods: `list` answers, for a working directory, the skills the source offers, each with an optional group, a name, a description and a reference; `read` takes a reference and answers the skill's text and an optional origin, a sentence saying where the skill comes from. The source bounds the time a read takes. The shape is in the [`default` README](../../bundles/runtime/default/README.md#defaultskill-sourcesv1-100) ([bundles/runtime/default/src/contracts/index.ts](../../bundles/runtime/default/src/contracts/index.ts)).
- The [`mcp`](../../bundles/features/mcp/README.md#defaultskill-sourcesv1-100) source lists the skills of the call's Project's connected servers, each server's skills grouped by its slug, in the servers' order, so a server skill's locator is `mcp/<server slug>/<name>`. A server's skills are those it lists through the MCP Skills extension. `read` reads one through `resources/read`, given 30 seconds, only when it is loaded and only while the server lists it, and gives the origin ``From the MCP server "<name>" (`<uri>`). Its other files are not available.`` ([bundles/features/mcp/src/host/index.ts](../../bundles/features/mcp/src/host/index.ts), [bundles/features/mcp/src/host/skills.ts](../../bundles/features/mcp/src/host/skills.ts), [bundles/features/mcp/src/host/manager.ts](../../bundles/features/mcp/src/host/manager.ts)). The servers themselves are described in [mcp.md](mcp.md).

### In the conversation

- The client part of `default` registers the element `default-skill-call` with the [`chat`](../../bundles/desktop/chat/README.md#chatviewsv1-client-120)'s `chat.views/v1` for the tool `load_skill`, as a block of its own outside the activity group, while the chat serves that contract. Without that registration the chat draws a `load_skill` call as its generic row inside the activity group ([bundles/runtime/default/src/client/index.ts](../../bundles/runtime/default/src/client/index.ts), [bundles/desktop/chat/src/contracts/index.ts](../../bundles/desktop/chat/src/contracts/index.ts)).
- The block's header shows `Loading skill`, `Loaded skill` or `Failed to load skill`, the skill's name and its source: `workspace` for a locator `cwd/<name>`, `<source> · <group>` for a locator `<source>/<group>/<name>`, and `built-in` for any other locator, a source's `<bundleId>/<name>` without a group included. The block is folded while it loads and once loaded, and open when the load failed ([bundles/runtime/default/src/client/skill-call.tsx](../../bundles/runtime/default/src/client/skill-call.tsx), [bundles/runtime/default/src/client/skill-load.ts](../../bundles/runtime/default/src/client/skill-load.ts)).

The rest of the prompt run is described in [default-agent.md](default-agent.md).
