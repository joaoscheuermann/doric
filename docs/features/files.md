# Feature: Files

- Status: `implemented`

## Problem

The agent works on the code of its Project, which lives in the Project's sandbox. It needs to map that workspace, search it, read an image in it, and change files precisely, with every relative path resolved against the directory it works in. The reader needs to see the same workspace beside the conversation: browse its tree, open a file and read it, and make an empty file or folder, while what the panel shows follows what the agent changes without a watcher on the sandbox.

## Decisions

- The window refreshes a Project after a sandbox-writing tool because the owner of that tool asks for it: `files` and `git` observe `chat.hooks/v2.onThreadUpdateHook` and call `files.refresh/v1.request` after their own tools finish. `chat.hooks/v2.onSandboxActivityHook` does not fire after a finished tool call.
- `files.decorations/v1` is a many-contract with one method, `observe`. `files` declares it and does not provide it; `git` provides the marks of its changes.
- `files.sandbox/v1.observeTree` takes `{ projectId, cwd? }`, where `cwd` is the Thread's raw working directory. The tree's root is derived from it with `workspacePath(cwd)`, and the tree's query key is `['files', projectId, 'tree', cwd]`.
- Every `files/v1` method answers a `LeaseOutcome` through `runtime.lease/v1.withLease` and never acquires a lease. The window maps that outcome itself: `pending` with `retryAfterSeconds: 1`, `not_found` as not found, every other refusal as `invalid_path`, and a failed call as `Doric backend is unavailable.`, `The request could not be completed.` or `Doric returned an invalid response.`
- The refresh coordinator has no React. A change of what it watches (the selected Project and its state, the selected Thread and its working directory, the Project's Thread activity, whether something of the Project is shown, the connection) requests a refresh; window focus and the 15-second poll act only while a registrant of the selected Project is active and the window is connected. The chat's activity hook requests a refresh whatever the connection. Terminal activity arrives as `request`. "Shown" means that a registrant is active: the tree and each file tab register while they are mounted.
- The tools register at fixed global model-visible positions, so the order of the tool list does not depend on the order the bundles load in.
- `files/contracts` re-exports the sandbox vocabulary that `git` reads (`workspacePath`, `SANDBOX_ROOT`, `ROOT_PATH`, `sandboxNotice`, `ProjectLeaseState`, `SandboxStatus`) from `src/contracts/reads.ts`, a file that imports nothing. The `files` client rereads only its own `['files', projectId, …]` keys.
- The text the tree skeleton announces belongs to the bundle that shows the tree: `files` passes `Loading files`.
- The Files column is always shown: 328 px wide by default, resizable between 14rem and 30rem, and never collapsed. Reveal in Files selects the Files view with `select('files')`.
- New file and New folder are the only writes the bundle's window part makes to the workspace.

## Current behavior and contracts

- Its host part provides `files/v1` and registers the tools `edit`, `find`, `grep`, `tree`, `view-image` and `write`, with `cwd`, which [cwd-tool.md](cwd-tool.md) describes ([src/host/index.ts](../../bundles/features/files/src/host/index.ts)). Its client part provides `files.sandbox/v1` and `files.refresh/v1`, registers `files.open-file/v1`, defines the elements `files-tree`, `files-file-view`, `files-file-icon` and `files-edit-call`, and adds the Files view to the region `shell.panel` ([src/client/index.ts](../../bundles/features/files/src/client/index.ts)).
- `chat.hooks/v2`, `chat.views/v1` and `files.decorations/v1` are optional. Without the chat the bundle draws nothing in the conversation and refreshes nothing after a tool call; with no provider of `files.decorations/v1` no tree row is marked ([manifest.json](../../bundles/features/files/manifest.json), [src/client/index.ts](../../bundles/features/files/src/client/index.ts), [src/client/hooks/use-decorations.ts](../../bundles/features/files/src/client/hooks/use-decorations.ts)).
- The bundle also ships `goal-directed-tool-use`, always available, and skills on workspace discovery, content search, file inspection, dependency tracing, editing, writing, multi-file consistency, shell commands, failure diagnosis, change validation and synthesis, which [skills.md](skills.md) describes ([README.md](../../bundles/features/files/README.md)).

### The workspace's visibility rules

- One implementation in `packages/sandbox` decides what a listing of the workspace shows: a path must stay inside the workspace root; `.gitignore` files apply, with negation; `node_modules` and `__pycache__` are ignored as rules of the workspace root placed before every `.gitignore`, so a negation there shows them again; hidden entries are left out except `.agents`; `.git` is never listed; directories come first, then files, each sorted by name ([packages/sandbox/src/lib/files.ts](../../packages/sandbox/src/lib/files.ts)).
- The `tree` tool, every `files/v1` listing (the Files panel's tree among them) and the host's file routes, which call `files/v1`, read through those rules ([src/host/tools/tree.ts](../../bundles/features/files/src/host/tools/tree.ts), [src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts)).
- `find` and `grep` read with rules of their own: the `.gitignore` files inside the searched directory, with negation and the last matching rule winning, and `.git` and `node_modules` always pruned. Hidden files are searched ([src/host/tools/visible-files.ts](../../bundles/features/files/src/host/tools/visible-files.ts)).

### The file tools

All the tools are always available and run in the calling prompt's Project sandbox through `runtime.lease/v1`. A relative path resolves against the calling Thread's working directory, read from `runtime.workspace/v1` at call time; an absolute path is used as it is ([src/host/index.ts](../../bundles/features/files/src/host/index.ts), [src/host/sandbox.ts](../../bundles/features/files/src/host/sandbox.ts)).

| Order | Tool         | What it does                                                                  |
| ----- | ------------ | ----------------------------------------------------------------------------- |
| 100   | `cwd`        | Reports or moves the Thread's working directory ([cwd-tool.md](cwd-tool.md)). |
| 200   | `edit`       | Changes a file through exact-text replacements.                               |
| 300   | `find`       | Finds files by glob.                                                          |
| 400   | `grep`       | Searches file contents.                                                       |
| 600   | `tree`       | Shows the directory structure as an ASCII tree.                               |
| 800   | `write`      | Creates or overwrites a whole file.                                           |
| 850   | `view-image` | Hands the model an image of the workspace.                                    |

The positions 500 and 700 are the `terminal` tool's ([terminal.md](terminal.md)) and the `web` tool's ([web-research.md](web-research.md)) ([src/host/index.ts](../../bundles/features/files/src/host/index.ts)).

#### `edit`

- Input: `{ path, edits: [{ oldText, newText }] }`. Output: `{ success, diff, first_changed_line?, error? }` ([src/host/tools/edit.ts](../../bundles/features/files/src/host/tools/edit.ts)).
- Each `oldText` must match exactly one region of the original file, and the matched regions must not overlap; every edit applies to the original content. Line endings are compared as `\n`. Each line of `oldText` and `newText` loses its trailing whitespace, and each loses a final line break. When an `oldText` does not occur in the file as it is, the whole file is compared and rewritten with the trailing whitespace of each line stripped and without its final line break ([src/host/tools/edit.ts](../../bundles/features/files/src/host/tools/edit.ts)).
- The file keeps its byte order mark and its line endings: a file that holds `\r\n` is written back with `\r\n` ([src/host/tools/edit.ts](../../bundles/features/files/src/host/tools/edit.ts)).
- A failure writes nothing and answers `success: false` with the reason: the file is missing (`File not found: <path>`) or unreadable; `edits` is empty; an `oldText` is empty, not found or found more than once (with the count); two edits overlap; or the result equals the file ([src/host/tools/edit.ts](../../bundles/features/files/src/host/tools/edit.ts)).
- `diff` holds the changed lines, each numbered and marked `-` or `+`, with up to three lines of context on each side; `first_changed_line` is the first line that differs ([src/host/tools/edit.ts](../../bundles/features/files/src/host/tools/edit.ts)).

#### `write`

- Input: `{ path, content }`. Output: `{ success, bytes_written, diff?, error? }`. It creates the file, or overwrites it, creating its parent directories; an empty `path` is refused ([src/host/tools/write.ts](../../bundles/features/files/src/host/tools/write.ts), [src/host/sandbox.ts](../../bundles/features/files/src/host/sandbox.ts), [packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts)).
- `bytes_written` counts the content's UTF-8 bytes. `diff` starts with `Edited <path> (+<added> -<removed>)`, followed by the changed lines against the file's earlier content (empty for a new file), with up to three lines of context on each side ([src/host/tools/write.ts](../../bundles/features/files/src/host/tools/write.ts)).

#### `find`

- Input: `{ pattern, path?, limit? }`. Output: `{ results, total, truncated, error? }`. It lists the files under `path` (the working directory by default) whose path relative to `path`, or whose name, matches the glob, in sorted order ([src/host/tools/find.ts](../../bundles/features/files/src/host/tools/find.ts)).
- In the glob, `**` matches any characters, `*` any characters but `/`, and `?` one character but `/`; a character class (`[`) is refused ([src/host/tools/find.ts](../../bundles/features/files/src/host/tools/find.ts)).
- It stops at `limit` results (1,000 by default) or at 50 KiB of output and then sets `truncated`. A path outside the workspace root answers `Path escapes workspace: <path>`, a missing one `Path not found: <path>`; a path that is a file answers no results ([src/host/tools/find.ts](../../bundles/features/files/src/host/tools/find.ts)).

#### `grep`

- Input: `{ pattern, path?, glob?, ignoreCase?, literal?, context?, limit? }`. Output: `{ matches, total, truncated, lines_truncated, error? }`; each match is `{ file, line, text, context_before, context_after }` ([src/host/tools/grep.ts](../../bundles/features/files/src/host/tools/grep.ts)).
- `pattern` is a JavaScript regular expression, or literal text with `literal: true`. `glob` filters the files with the glob rules of `find`. `path` may name one file, which is then the only file searched ([src/host/tools/grep.ts](../../bundles/features/files/src/host/tools/grep.ts)).
- It stops at `limit` matches (100 by default) or at 50 KiB of output and then sets `truncated`. A line longer than 500 characters is cut, which sets `lines_truncated` ([src/host/tools/grep.ts](../../bundles/features/files/src/host/tools/grep.ts)).

#### `tree`

- Input: `{ path?, exclude?, depth? }`. The answer is text: the listed directory's absolute path, then its entries drawn with `|-- ` and `` `-- `` ([src/host/tools/tree.ts](../../bundles/features/files/src/host/tools/tree.ts)).
- It shows `depth` levels below the path, three by default. A directory at the last level shows `(<n> entries not shown)` instead of its children, and an empty directory shows `(empty)` ([src/host/tools/tree.ts](../../bundles/features/files/src/host/tools/tree.ts)).
- A path outside the workspace, missing, or not a directory, and an `exclude` pattern that is invalid or matches the root, answer an error line ([src/host/tools/tree.ts](../../bundles/features/files/src/host/tools/tree.ts)).

#### `view-image`

- Input: `{ path }`. It reads the file's bytes, keeps them as an attachment of the Project through `runtime.attachments/v1.attach`, and answers the attachment's reference line, `![<name>](doric-attachment:<id>)` ([src/host/tools/view-image.ts](../../bundles/features/files/src/host/tools/view-image.ts), [bundles/runtime/runtime/src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).
- The tool declares `resultModalities: ['image']`: the model receives the image itself with the result, and a run whose model's catalog names input modalities without `image` is not offered the tool; a model whose catalog names no modalities keeps it. The runtime refuses a file that is not a PNG, JPEG, WebP or GIF of at most 5 MiB, and that refusal is the tool's answer ([src/host/tools/view-image.ts](../../bundles/features/files/src/host/tools/view-image.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [bundles/runtime/runtime/src/contracts/attachments.ts](../../bundles/runtime/runtime/src/contracts/attachments.ts)).

### In the conversation

- While `chat.views/v1` is served, the bundle registers how the chat draws three tools, each in a registration of its own ([src/client/index.ts](../../bundles/features/files/src/client/index.ts), [src/client/chat/views.ts](../../bundles/features/files/src/client/chat/views.ts)).
- `edit` and `write` calls are drawn by `files-edit-call`, a block of its own, open until the reader closes it: `Editing`, `Edited` or `Failed to edit`, the file's name, the `+added / −removed` counts and the numbered diff. The first 16 diff lines show, then `⋯ Show <n> more lines`. A failed call shows the failure notice, with `tool_failed` as its fallback code ([src/client/chat/edit-call.tsx](../../bundles/features/files/src/client/chat/edit-call.tsx), [src/client/chat/edit-tool.ts](../../bundles/features/files/src/client/chat/edit-tool.ts)).
- `view-image` keeps the chat's generic row, open until the reader closes it, so the image stands beside the call ([src/client/chat/views.ts](../../bundles/features/files/src/client/chat/views.ts)).

### The `files/v1` contract

`files/v1` 1.3.0 is `Files`, exported as `FilesV1`. The Project is the call's `scope.projectId`. Each method runs on the Project's current lease through `runtime.lease/v1.withLease`: it answers `{ status: 'ready', value }`, or the lease state `pending`, `unavailable`, `expired` or `missing` without acquiring a lease. Every method is exposed to the desktop, scoped by `projectId`, `threadId` and `promptId`. Paths are workspace-relative, or absolute under the sandbox root ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [manifest.json](../../bundles/features/files/manifest.json)).

| Method                                 | Behavior                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `directory({ path? })`                 | One directory level, files with their sizes: `{ status: 'listed', path, entries }`, or `not_found`, `not_directory`, `invalid_path`. No `path` is the workspace root.                                                                                                                                                                                 |
| `tree({ path? })`                      | The whole tree below `path` in one read, each directory carrying `children`, with the same answers.                                                                                                                                                                                                                                                   |
| `directories({ paths, root? })`        | 1 to 1,000 directories (`DIRECTORIES_LIMIT`) listed one level each in one sandbox command, with no sizes: `{ status: 'listed', directories }`, one `{ path, status, entries? }` per asked path, in order. Each listing applies the rules the whole-tree read from `root` applies, so a directory lists exactly the children that read nests under it. |
| `content({ path, encoding? })`         | One file: `{ status: 'read', path, content, truncated, binary }`, or `not_found`, `not_file`, `invalid_path`. As text it keeps the first 262,144 bytes, and `content` is empty when the bytes hold a NUL (`binary`). With `encoding: 'base64'` it answers the first 4,194,304 bytes in base64.                                                        |
| `createFile({ directory, name })`      | Makes one empty file. See below.                                                                                                                                                                                                                                                                                                                      |
| `createDirectory({ directory, name })` | Makes one empty directory. See below.                                                                                                                                                                                                                                                                                                                 |

- `createFile` and `createDirectory` never overwrite. A `name` that is empty, `.`, `..`, holds `/`, `\` or NUL, or passes 255 UTF-8 bytes answers `{ status: 'refused', reason: 'invalid-name' }`; a `directory` outside the workspace answers `outside`, and one that is not an existing directory `no-directory`. One command makes the entry and fails when the name exists (`set -C; : >` for a file, `mkdir --` for a directory), so a name that exists answers `exists` and keeps its content. Success answers `{ status: 'created', path }` with the workspace-relative path; any other failure answers `{ status: 'failed', message }` with the first line of stderr ([src/host/writes.ts](../../bundles/features/files/src/host/writes.ts)).
- The window calls `files/v1` through the desktop bridge. It checks a Project id (1 to 200 characters, no NUL) and a path (relative, no `..`, no NUL, at most 4,096 characters) before the call, and turns a host failure into `Doric backend is unavailable.`, `Doric returned an invalid response.` or `The request could not be completed.` ([src/client/api/reads.ts](../../bundles/features/files/src/client/api/reads.ts)).

### The Files panel

- The Files column sits on the right of the workspace window and is always shown: 328 px wide by default, resizable between 14rem and 30rem, with a 40 px header and a 28 px footer row. [ui-redesign.md](ui-redesign.md) describes the window ([bundles/desktop/layout/src/client/components/templates/workspace-layout.tsx](../../bundles/desktop/layout/src/client/components/templates/workspace-layout.tsx)).
- The Files view is the region item `files` of `shell.panel`, with the order 100, the label `Files` and the `files-file-icon` element as its icon, chosen from the column header's tabs beside the Changes view of [git.md](git.md). The client selects it when it activates ([src/client/index.ts](../../bundles/features/files/src/client/index.ts)).
- The footer row is the region `shell.panel.footer`, where `git` draws the working directory and the branch ([bundles/desktop/layout/src/client/views/workspace-view.tsx](../../bundles/desktop/layout/src/client/views/workspace-view.tsx), [bundles/features/git/src/client/index.ts](../../bundles/features/git/src/client/index.ts)).

#### The tree

- The view reads the selected Project's sandbox and roots its tree at the selected Thread's working directory, so selecting another Thread of the Project roots the tree elsewhere. It reads the selection through `workspace.selection/v1` and the records through `runtime.records/v1` ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [src/client/api/selection.ts](../../bundles/features/files/src/client/api/selection.ts)).
- With no Project selected the view shows `No project selected`. During the first read it shows skeleton rows that match the tree's row height, indentation and icons, announced as `Loading files`. When the first read fails, the panel body stays empty and only the read toast shows. When the sandbox cannot be read it shows `No files to show` with the sentence of `sandboxNotice` for the state, as [projects-and-threads.md](projects-and-threads.md) describes the lease states; a lease the host has not prepared yet reads `The sandbox is still being prepared; the host suggests trying again in 1 seconds.` An empty root shows `No files` and `This directory is empty.` ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [src/contracts/reads.ts](../../bundles/features/files/src/contracts/reads.ts), [src/client/api/reads.ts](../../bundles/features/files/src/client/api/reads.ts), [packages/desktop/src/panels/tree-skeleton.tsx](../../packages/desktop/src/panels/tree-skeleton.tsx)).
- The tree is read per directory through `files/v1.directories`: one call reads the root and every open folder. A folder opened later is read on its own, with the folders opened with it, and merged in; until its children arrive it shows the line `Loading…`. A folder whose read fails closes again, and its failure is the panel's read toast. An open folder that its parent's listing does not hold as a directory is not shown, and a folder whose own read answers that it is gone makes the tree read its parent again ([src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts), [src/client/reads/directory-tree.ts](../../bundles/features/files/src/client/reads/directory-tree.ts), [packages/desktop/src/panels/file-tree.tsx](../../packages/desktop/src/panels/file-tree.tsx)).
- Which folders are open is kept per Project and root, apart from the read, so leaving a Thread and coming back keeps them open ([src/client/stores/expansion.ts](../../bundles/features/files/src/client/stores/expansion.ts)).
- A row shows a file, folder or open-folder icon and the entry's name, and its tooltip is the path. Click, Enter or Space opens a file or toggles a folder; Right opens a closed folder and Left closes an open one. The row of the selected file tab is the selected row. Only the rows in view are drawn, and the focused row stays drawn ([packages/desktop/src/panels/file-tree.tsx](../../packages/desktop/src/panels/file-tree.tsx), [src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx)).
- The tree scrolls both ways. A row's mark is pinned to the visible right edge of the row, and its backing follows the row's hover and selected states ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [packages/desktop/src/panels/file-tree.tsx](../../packages/desktop/src/panels/file-tree.tsx)).

#### Marks

- The view asks every provider of `files.decorations/v1` for the marks of the tree it shows, `observe({ projectId, cwd }, listener)`, and draws their merge. Each answer is `{ marks, error?, fetching }`, a list of `{ path, mark }`. For a path two providers mark, the provider whose bundle id is smaller, by code unit, wins; the first error in bundle-id order is shown, and the tree's own read error wins over it ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/client/hooks/use-decorations.ts](../../bundles/features/files/src/client/hooks/use-decorations.ts), [src/client/tree/decorations.ts](../../bundles/features/files/src/client/tree/decorations.ts), [src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx)).
- A mark (`FileMark`) has a `description`, which the row's accessible label and tooltip append; a `count`, the badge of a folder; and the optional `tone` (class names of the name and badge), `letter` (a file's badge) and `struck` (a file's name struck through). Marks are keyed by path, so a folder never opened carries them too ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [packages/desktop/src/panels/file-tree.tsx](../../packages/desktop/src/panels/file-tree.tsx)). `git` provides the marks of its changes, as [git.md](git.md) describes.

#### Row menus

- A file row's context menu holds Copy relative path, which copies the path relative to the tree's root ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx)).
- A folder row's menu holds New file and New folder. Each opens the folder and shows a name row as its first child. Enter sends the trimmed name to `createFile` or `createDirectory`, and an empty name cancels; Escape or leaving the field cancels, except while the call runs. A created entry closes the row and requests a refresh of the Project; any other answer shows its reason under the row, which keeps the typed name: `<name> already exists.`, `A name cannot contain / or \, cannot be . or .., and has at most 255 bytes.`, `This folder is outside the Project.`, `This folder no longer exists.`, the command's first stderr line, a lease sentence (`The Project is starting. Try again in a moment.`, `The Project is unavailable.`, `The Project's sandbox expired. Reopen the Project.`, `The Project no longer exists.`), or `Could not create <name>.` when the call fails ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [src/client/tree/pending-entry.tsx](../../bundles/features/files/src/client/tree/pending-entry.tsx)).

#### Read failures

- A failed read never replaces what the tree shows: a tree already drawn stays, and the failure is one toast, `Unable to update`, with the message and a `Try again` action that requests a refresh. The toast is shared by the panel's views, shown once per message, held while a read is on its way, and dismissed by the next successful read ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [src/client/reads/state.ts](../../bundles/features/files/src/client/reads/state.ts), [packages/desktop/src/panels/use-read-error.ts](../../packages/desktop/src/panels/use-read-error.ts)).
- A failed read is retried three times, after 2, 4 and 8 seconds. A read that answers `pending` is read again every second; any other answer that is not ready waits for a refresh that is not periodic ([src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts), [packages/desktop/src/reads/read-policy.ts](../../packages/desktop/src/reads/read-policy.ts), [src/client/api/reads.ts](../../bundles/features/files/src/client/api/reads.ts)).
- The panel shows no updating label. A refresh in the background keeps the tree and the reader's position, and a refresh that changes nothing leaves every row as it is ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx), [src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts)).

### Revalidation and `files.refresh/v1`

`files.refresh/v1` 1.0.0 is the window's one Project refresh coordinator, a client contract ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/client/refresh/coordinator.ts](../../bundles/features/files/src/client/refresh/coordinator.ts)).

| Method                               | Behavior                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `register(reads)`                    | Adds a registrant, `{ projectId, active(), refresh({ periodic }) }`: reads of one Project, active while they are shown. Returns a `Disposable`. |
| `request(projectId, { periodic? }?)` | Calls `refresh` of every registrant of that Project, and of no other. A failing `refresh` is ignored.                                           |

- The Files tree and each file tab register while they are mounted; `git` registers its own reads ([src/client/hooks/use-project-reads.ts](../../bundles/features/files/src/client/hooks/use-project-reads.ts), [bundles/features/git/src/client/hooks/use-project-reads.ts](../../bundles/features/git/src/client/hooks/use-project-reads.ts)).
- There is no filesystem watcher. The coordinator requests a refresh of the selected Project, while the window is connected, when any of these changes: the selected Project or its state, the selected Thread or its working directory, a Thread of the Project (its id, its state — the start of a run excepted, its end counted in any state — or its working directory), whether something of the Project is shown, or the connection coming back. A Thread that starts to run is not a change ([src/client/refresh/coordinator.ts](../../bundles/features/files/src/client/refresh/coordinator.ts)).
- While something of the selected Project is shown, the window is connected and the document is visible, window focus and a visibility change request a refresh, and a poll requests a periodic one every 15 seconds ([src/client/refresh/coordinator.ts](../../bundles/features/files/src/client/refresh/coordinator.ts), [src/client/index.ts](../../bundles/features/files/src/client/index.ts)).
- Other bundles request refreshes. A Thread the chat holds is one whose conversation the chat keeps loaded. The chat's `onSandboxActivityHook` requests one when the chat starts to hold a Thread, a held Thread's working directory changes or its run ends; `files` itself requests one after an `edit` or `write` call finishes in a held Thread's conversation (`onThreadUpdateHook`); `git` after a `git` call; and `terminal` when a Project's terminals change ([src/client/index.ts](../../bundles/features/files/src/client/index.ts), [src/client/refresh/tool-refresh.ts](../../bundles/features/files/src/client/refresh/tool-refresh.ts), [bundles/features/git/src/client/index.ts](../../bundles/features/git/src/client/index.ts), [terminal.md](terminal.md)).
- A refresh of the `files` reads rereads the Project's tree and file reads that are observed. Requests within 250 ms share one read, and a request that arrives during a read leaves one more read after it. A read in flight is not cancelled. A periodic refresh skips a read that failed or did not answer ready (a lease state, `not_found` or `invalid_path`): a failed or `pending` read keeps its own retry, and the others wait for a refresh that is not periodic; any other refresh includes them. An unobserved read is only marked stale ([src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts), [packages/desktop/src/reads/refresh.ts](../../packages/desktop/src/reads/refresh.ts)).

### `files.sandbox/v1`

- `files.sandbox/v1` 1.0.0 has one method, `observeTree({ projectId, cwd? }, listener)`, which returns a `Disposable`. It is the window's one tree read per Project and root, shared by every observer, and it reads only while observed ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts)).
- Each observation is `{ read, error?, fetching, loading? }`: `read` is `idle`, `loading`, `ready` with the root's entries (a read directory carrying `children`), or a state (`missing`, `pending`, `unavailable`, `expired`, `invalid_path`, `not_found`, with `retryAfterSeconds`); `loading` names the open folders being read. An observation that changes nothing is not sent ([src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/client/sandbox-store.ts](../../bundles/features/files/src/client/sandbox-store.ts)).

### File tabs and the viewer

- `files.open-file/v1` takes `{ projectId, path }` and opens the file as a tab of the selected Thread through `layout.tabs/v2`: id `file:<path>`, title the file's name, tooltip the whole path, element `files-file-view`, icon `files-file-icon`. Opening a file whose tab that Thread has open selects that tab ([bundles/desktop/layout/src/client/services/layout-tabs.ts](../../bundles/desktop/layout/src/client/services/layout-tabs.ts), [src/contracts/index.ts](../../bundles/features/files/src/contracts/index.ts), [src/client/commands.ts](../../bundles/features/files/src/client/commands.ts)).
- Clicking a file row runs that command, so the file opens beside the conversation and the tree stays as it is ([src/client/tree/files-tree.tsx](../../bundles/features/files/src/client/tree/files-tree.tsx)).
- A file tab's context menu holds Reveal in Files. It opens the file's ancestor folders under the tree's root, selects the Files view with `layout.panel/v3.select('files')` and selects the tab, so the tree selects the file's row. A file outside the root, or of a Project other than the selected one, only selects the Files view and the tab, without opening folders ([src/client/commands.ts](../../bundles/features/files/src/client/commands.ts)).
- File tabs share the viewer with the comparisons of [git.md](git.md), the terminals of [terminal.md](terminal.md) and subthreads. The viewer is a resizable column beside the conversation, present while a tab is open. Each Thread keeps its own tabs and their order. A tab stays mounted while another is selected or the tabs are reordered, so a file keeps its editor and position. Its tabs are 28 px pills that reorder by dragging (from 6 px of movement) or with Alt+Shift+Left/Right, close with a middle click, and drop their transitions under reduced motion; [ui-redesign.md](ui-redesign.md) describes them ([bundles/desktop/layout/src/client/components/templates/workspace-layout.tsx](../../bundles/desktop/layout/src/client/components/templates/workspace-layout.tsx), [packages/desktop/src/panels/tab-strip.tsx](../../packages/desktop/src/panels/tab-strip.tsx), [packages/desktop/src/panels/use-tab-strip.ts](../../packages/desktop/src/panels/use-tab-strip.ts), [bundles/desktop/layout/src/client/services/layout-tabs.ts](../../bundles/desktop/layout/src/client/services/layout-tabs.ts), [bundles/desktop/layout/src/client/components/organisms/workspace-tabs.tsx](../../bundles/desktop/layout/src/client/components/organisms/workspace-tabs.tsx)).
- The tab reads the file on demand through `files/v1.content` as text, and refreshes with the Project. Until the first answer it shows twelve skeleton lines; a later read keeps the text on screen. A failed read is the tab's own toast, with `Try again`; a file the sandbox cannot give shows `This file cannot be shown` with the sentence of `sandboxNotice` ([src/client/file/file-view.tsx](../../bundles/features/files/src/client/file/file-view.tsx), [src/client/reads/state.ts](../../bundles/features/files/src/client/reads/state.ts)).
- The text is drawn by a read-only Monaco editor, with the language its path calls for, no minimap and no word wrap, in the app's theme, which follows the color scheme. Monaco loads once per window, on the first editor, with its editor worker only. A new read of the file keeps the reader's position ([src/client/file/file-view.tsx](../../bundles/features/files/src/client/file/file-view.tsx), [packages/desktop/src/code/code-view.tsx](../../packages/desktop/src/code/code-view.tsx), [packages/desktop/src/code/monaco.ts](../../packages/desktop/src/code/monaco.ts), [packages/desktop/src/code/monaco-runtime.ts](../../packages/desktop/src/code/monaco-runtime.ts)).
- A binary file shows `This is a binary file, so its contents are not shown.` A file past the read limit shows its first part and `This file is larger than the read limit, so only its first part is shown.` ([src/client/file/file-view.tsx](../../bundles/features/files/src/client/file/file-view.tsx), [src/client/reads/state.ts](../../bundles/features/files/src/client/reads/state.ts)).
- The tab has its own footer: the file's workspace-relative path in a monospace font, cut at the end when it is too long, with the whole path as its tooltip, and `Updating…` while a read is on its way ([src/client/file/file-view.tsx](../../bundles/features/files/src/client/file/file-view.tsx)).
- The bundle's style sheet shapes Monaco's scrollbar slider as the app's other scroll areas ([src/client/styles.css](../../bundles/features/files/src/client/styles.css)).
