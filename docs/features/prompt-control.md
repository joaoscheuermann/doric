# Feature: Stop, steering and the queue of inputs

- Status: `implemented`

## Problem

A Thread runs one prompt at a time, while input keeps arriving: the reader writes more, child Threads finish, background terminals end, and bundles have something to tell the agent. The reader needs to stop a run without losing what it already did, to add words to a run without waiting for it to end, and to see what waits, remove it and correct it. Every input must run exactly once, in a known order, across a host restart.

The runtime holds the queue, the dispatch gate and the steering ([`runtime` README](../../bundles/runtime/runtime/README.md)); the `default` executor takes steering in at its safe points ([`default` README](../../bundles/runtime/default/README.md)); the `transport` bundle exposes the operations over REST ([`transport` README](../../bundles/foundation/transport/README.md)); and the `chat` bundle draws the queue and binds the controls and keys ([`chat` README](../../bundles/desktop/chat/README.md)).

## Decisions

- A reader's stop pauses the Thread's dispatch, and only the reader reopens it: the boot (the recovery the host runs when it starts, see [Projects and Threads](projects-and-threads.md)) never does. The stopped prompt itself ends: the history it wrote stays, and it finishes `cancelled` with the reason `interrupted` and is never resumed. Terminating a Thread or a Project, not stopping it, is the terminal act.
- Repeated stops are idempotent, including when the display names a prompt that just finished: a repeated stop answers `interrupted` again and changes nothing.
- The interrupt a parent prompt has over a child targets one `promptId`: it aborts only that running prompt, keeps the child's pending inputs and its own children, and the next input runs only after the aborted run has settled.
- Without `interrupt`, a steer never interrupts a tool: it is taken in at the agent loop's safe points. With `interrupt` it aborts only the current step (the provider call or the tool in flight), and the same prompt continues from the history it wrote, with no pause or resume recorded.
- A bundle's instruction carries the calling bundle's id, which the runtime takes from the call and never from the input. `instruct` is local to bundles and never reachable from a window, and it reaches agent Threads, which the reader's `steer` does not.
- A newer prompt of the reader, accepted outside the queue, supersedes the Thread's older paused prompts: their resume action disappears, the host refuses to resume them, and the boot never schedules them again. Delegated inputs, and any acceptance marked `queued: true`, keep the pause and its resume action.
- While a queued prompt is being edited, Cmd/Ctrl+Enter saves the edit and never resumes the queue.

## Current behavior and contracts

### Inputs and their events

- Every input a Thread receives is accepted with `prompt.accepted`, which carries its text and its source (`user`, `parent`, `result`, `terminal` or `bundle`), and the boolean `queued`. The text is redacted with the runtime's list: the secrets on the `secrets/v1` list and the Git token applied to the Project's sandbox ([bundles/runtime/runtime/src/host/domain/redactor.ts](../../bundles/runtime/runtime/src/host/domain/redactor.ts), [service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). When the input must wait — a prompt runs, other input is pending, the dispatch gate is closed, the Thread is paused because storage is low, or the Project holds no sandbox lease (its claim on a running sandbox, see [Projects and Threads](projects-and-threads.md)) — the acceptance and `prompt.queued` are written in one append ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- The Thread runs its inputs one at a time, first in, first out. The dispatcher starts the next one only after the previous run has settled: it marks the Thread `running` with the prompt's id, records the turn's checkpoint, then writes `prompt.started` under the same prompt id ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Around the executor's events the runtime writes `prompt.accepted`, `prompt.queued`, `prompt.started`, `prompt.paused`, `prompt.resumed`, `prompt.edited`, `prompt.steered`, `prompt.finished`, `agent.failed`, `agent.cancelled`, and the Thread notifications `queue.paused`, `queue.resumed` and `queue.updated` ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/store/progress.ts](../../bundles/runtime/runtime/src/host/store/progress.ts)).
- `prompt.finished` closes a prompt: `{ status, text, source, reason? }`, with `status` `completed`, `failed` or `cancelled`, the response text, the input's source, and `reason` `interrupted` for a prompt the reader stopped or `queue_removed` for a removed input. A run completes only after its history is saved: when the history or an event cannot be saved for a reason other than a full disk, the runtime closes the Thread with `persistence_failed` and finishes the prompt `failed` with `Thread persistence failed.` ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts)). Its qualified type is `runtime.prompt-finished/v1`, whose registered schema admits only `queue_removed` as `reason` ([bundles/runtime/runtime/src/contracts/events.ts](../../bundles/runtime/runtime/src/contracts/events.ts)).
- The window acknowledges a prompt's end by `prompt.finished`, not by the executor's `agent.finished`: it clears the prompt's pending execution, and it replaces the agent's turn with the finished text when the prompt `completed`, or when nothing streamed (it adds a turn then); a failed or cancelled prompt keeps what streamed ([bundles/desktop/chat/src/client/domain/projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts), [bundles/desktop/chat/src/client/domain/projector-execution.ts](../../bundles/desktop/chat/src/client/domain/projector-execution.ts)).
- In the transcript, an input that waits shows a Queued receipt at its `prompt.queued`, and its full text renders at its `prompt.started` ([bundles/desktop/chat/src/client/domain/projector-input.ts](../../bundles/desktop/chat/src/client/domain/projector-input.ts)).

### The reader's stop

- The Stop control of the footer, Escape in the prompt with no words, and Ctrl+C with nothing selected all call one stop, and only while the Thread has an active prompt. It sends `runtime.threads/v1.pause({ id, promptId })` with the displayed active prompt; a refusal shows a toast with the code `stop_failed` ([bundles/desktop/chat/src/client/hooks/use-thread-stop.ts](../../bundles/desktop/chat/src/client/hooks/use-thread-stop.ts), [bundles/desktop/chat/src/client/api/threads-api.ts](../../bundles/desktop/chat/src/client/api/threads-api.ts), [bundles/desktop/chat/src/client/components/organisms/conversation/plugins/send-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/send-prompt.tsx)).
- `pause` ignores `promptId`. It answers `missing` for a missing Thread, and `inactive` for a Thread that is closing or finished. Otherwise it closes the Thread's dispatch gate first — it sets `queuePaused` and writes the durable `queue.paused` — and then aborts the active run; it answers `interrupted`. A Thread whose gate is already closed answers `interrupted` and nothing changes ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The aborted run ends the turn: the history it wrote stays, the runtime writes `agent.cancelled`, then `prompt.finished` with `status: cancelled`, `reason: interrupted` and the text `The prompt was interrupted.` The prompt is never resumed ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- While the gate is closed nothing is dispatched. Inputs accepted meanwhile — the reader's prompts, child results, terminal results, instructions — are accepted and queued, and wait ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The gate is part of the Thread's record, rebuilt from `queue.paused` and `queue.resumed`, so it survives a host restart: the boot schedules no input of a Thread whose gate is closed ([bundles/runtime/runtime/src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The runtime pauses a prompt with `prompt.paused` when the host stops (`host_stopped`), when a restart finds it running (`host_restarted`), or when storage fills (`storage_low`); a log may also hold `reader_stopped`. A prompt paused with `reader_stopped` or `storage_low` is resumable: the host never resumes it on its own, and resuming the queue takes it up before the FIFO ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [bundles/runtime/runtime/src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts), [bundles/runtime/runtime/src/host/domain/prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts)).
- `runtime.threads/v1.resume({ id, promptId })`, reachable from the desktop, takes up one unfinished prompt of the Thread, the one a pause marker names. It answers `missing`, `inactive` for a finished Thread, and `unknown_prompt` for a prompt the Thread does not hold unfinished or that is superseded. While the gate is closed or storage is paused, it resumes the queue with that prompt first, as `resumeQueue` does; otherwise it writes `prompt.resumed` and queues the prompt, and answers `busy` when the prompt already runs or waits, or `storage_low` while storage stays low. The window calls it from a pause marker's resume action ([threads-api.ts](../../bundles/desktop/chat/src/client/api/threads-api.ts), [service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/rpc/threads.ts](../../bundles/runtime/runtime/src/host/rpc/threads.ts)).

### A parent's interrupt

- `runtime.threads/v1.interrupt(threadId, promptId)` belongs to a running parent prompt and reaches only its direct children. It answers `not_running` unless `promptId` is the child's active, unfinished prompt, and `inactive` for a closing child. It aborts that run only: the child's queue and its children stay, the gate stays open, and the prompt finishes `cancelled` with `The prompt was cancelled.`. The child's next input starts after the aborted run has settled ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts)).
- Terminating a Thread closes it and its descendants; that, not a stop, ends a Thread ([service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)). See [Projects and Threads](projects-and-threads.md).

### Steering

- Steering puts input into the running prompt without ending it. Four sources steer: the reader (`steer`), a bundle (`instruct`), and the correlated results of child Threads and of background terminals, which always steer the active prompt when one runs and are queued when none does ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- `runtime.threads/v1.steer({ id, prompt, promptId, interrupt? })`, reachable from the desktop, is the reader's steer of the prompt the reader saw running. It answers `forbidden` for an agent Thread ([service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/runtime/runtime/src/host/rpc/threads.ts](../../bundles/runtime/runtime/src/host/rpc/threads.ts)).
- `runtime.threads/v1.instruct({ id, prompt, reason, promptId?, interrupt?, retain? })` is local to bundles. `prompt` is non-empty and `reason` has 1 to 64 characters. Its source is `{ kind: 'bundle', bundleId, reason, retain? }`, with `bundleId` the calling bundle's id. Without `promptId` it steers whatever prompt runs. `retain` marks a standing instruction, which the executor keeps in the history the model reads, one per bundle and reason, through every compaction ([rpc/threads.ts](../../bundles/runtime/runtime/src/host/rpc/threads.ts), [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts), [model.ts](../../bundles/runtime/runtime/src/contracts/model.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Both answer `{ status: 'steered' | 'queued', promptId }`, or `missing` or `inactive` (and `forbidden` for `steer`). An empty prompt rejects ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- A steer is accepted as an input of its own: `prompt.accepted` with `queued: true` and `steer` naming the running prompt; it then waits on that run, and the queue snapshot does not list it ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts)).
- When the named prompt is not running, or the Thread is stopping, paused or waiting on storage, the steer is queued as an ordinary input and answered `queued`. A run that ends while the steer is accepted puts it at the front of the queue with `prompt.queued` `first: true` ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The executor takes steering in through `PromptSession.steers()` of `executor/v1`, oldest first ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)). The `default` executor's agent loop asks at its safe points: before the run's first turn, after each finished tool batch, and before a final answer would end the turn, in which case the run continues. It does not ask when no turn is left or when a structured run submits its result ([packages/agent/src/lib/agent.ts](../../packages/agent/src/lib/agent.ts), [executor.ts](../../bundles/runtime/default/src/host/executor.ts)).
- Each input reaches the model in its source's envelope; a steer uses one of `<user-request>`, `<child-result thread="" prompt="">`, `<terminal-output terminal="" prompt="">` or `<bundle-instruction bundle="" reason="">`. A parent's input, `<parent-instruction thread="" prompt="">`, is only queued (`runtime.threads/v1.send`) ([bundles/runtime/default/src/host/envelope.ts](../../bundles/runtime/default/src/host/envelope.ts)).
- The executor saves the history holding the steer before it emits `agent.steered`; the runtime then closes the steer under its own id with `prompt.steered { promptId, text, source }`, naming the prompt it steered, so neither replay nor boot runs it again ([executor.ts](../../bundles/runtime/default/src/host/executor.ts), [session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts)).
- With `interrupt`, the runtime also aborts the current step. The same prompt runs again from the history it wrote and takes the steer in before its next turn; no pause or resume is recorded. A reader's stop, a close or a persistence failure that meets the same abort ends the run; a host stop or a full disk pauses it ([bundles/runtime/runtime/src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- A steer the run ends without taking in returns to the front of the queue with `prompt.queued` `first: true`, ahead of inputs queued earlier. A steer a crash left unread is resumed by the boot like any accepted input that never started ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [progress.ts](../../bundles/runtime/runtime/src/host/store/progress.ts), [prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts)).

### The queue

- `runtime.threads/v1.queue(id)` answers the snapshot `{ revision, error?, paused, stopping, current?, resumable?, items }`, or `undefined` for a missing Thread. `revision` is the Thread's last event sequence. `paused` is `true` while the gate is closed or storage is low, with `error` `{ code: 'storage_low', message }` in the second case; `stopping` is `true` while `paused` holds and a prompt still runs. A full disk closes the gate itself, with `queue.paused { reason: 'storage_low' }`. `current` is the active prompt, else the resumable one; `resumable` is the latest prompt paused with `reader_stopped` or `storage_low`. `items` is the FIFO of pending inputs: those marked `first` (a returned steer, or a prompt resumed to the front) come first, the rest follow in the order they were queued. It leaves out the active prompt, the steers still waiting for it, superseded prompts, and prompts paused with `reader_stopped` or `storage_low`. A closing or finished Thread shows nothing pending ([store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts), [progress.ts](../../bundles/runtime/runtime/src/host/store/progress.ts), [service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/runtime/runtime/src/host/domain/storage-pause.ts](../../bundles/runtime/runtime/src/host/domain/storage-pause.ts), [model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).
- Each item is `{ promptId, source, label, preview, acceptedAt, editable, revision }`. `label` is `You`, `Terminal`, `<bundleId> · <reason>`, `Subthread · <name>` or `Parent · <name>`; `preview` is the text, or a terminal result's command, with whitespace collapsed and cut to 240 characters. The accepted event keeps the full text ([store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts)).
- `resumeQueue(id)` answers `missing` or `inactive` for a missing or finished Thread, `busy` while a prompt still runs (the Thread is stopping), and `storage_low` while storage stays low. A Thread whose gate is open and whose storage is not paused is answered `resumed` at once. Otherwise it rebuilds the FIFO from the stored inputs: the resumable prompt first, with `prompt.resumed`, then the queued inputs; then it writes `queue.resumed`, opens the gate and starts dispatch ([service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The Thread watch carries the durable notifications `queue.paused`, `queue.resumed` and `queue.updated`; the runtime writes `queue.updated` whenever the Thread's active prompt changes ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The window reads snapshots through `runtime.threads/v1.queue`. It reads again 100 ms after the last queue-changing event of the Thread's watch (an acceptance, edit, queuing, start, resume, pause, finish or steer of a prompt, `agent.started`, a `queue.*` notification, or `history.truncated`), when the connection returns and when the window regains focus; one read serves every surface that watches the Thread's queue. A snapshot with a lower `revision` than the one held is ignored ([use-thread-queue.ts](../../bundles/desktop/chat/src/client/hooks/use-thread-queue.ts), [domain/queue.ts](../../bundles/desktop/chat/src/client/domain/queue.ts), [threads-api.ts](../../bundles/desktop/chat/src/client/api/threads-api.ts)).

### Removing a pending input

- `removeQueued({ id, promptId })` runs under the Project's lock, the one dispatch takes. It answers `missing`, `forbidden` for an agent Thread, `inactive` for a closing or finished Thread, `busy` for the input that is executing, and `unknown_prompt` for an input the Thread does not hold ([service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- It removes a pending or paused input by writing its `prompt.finished` with `status: cancelled`, empty text and `reason: queue_removed`, so neither replay nor boot runs it; its Queued receipt stays in the transcript. Removing it again answers `removed` ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Removing an input a parent sent returns a cancelled result, `Removed from queue.`, to that parent through the same delivery as any child result ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- In the queue block, Delete or Backspace on the selected row removes it; a refusal shows the Thread's queue toast ([bundles/desktop/chat/src/client/hooks/use-queue-caret.ts](../../bundles/desktop/chat/src/client/hooks/use-queue-caret.ts), [use-thread-queue.ts](../../bundles/desktop/chat/src/client/hooks/use-thread-queue.ts)).

### Reading and editing a queued input

- `queuedPrompt({ id, promptId })` answers `{ promptId, text, revision, editable }` with the full current text, or `undefined` when the input is not pending or the Thread is closing or finished. `revision` is the sequence of the input's acceptance or its last edit ([service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts)).
- An input is editable only when it is the reader's, has never started, is not paused and is not superseded: paused, dispatched, finished and machine inputs are not ([store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts)).
- `editQueued({ id, promptId, text, revision })` runs under the dispatch lock. It answers `missing` for a missing Thread, `forbidden` for an agent Thread, `inactive` for a closing or finished Thread, `not_editable` for the executing or an ineligible input, `invalid_prompt` for empty text or a bad revision, `unknown_prompt`, and `conflict` for a stale revision. It writes `prompt.edited { text }` (redacted) before replacing the waiting input's text in place, keeping its FIFO position, and answers `updated` with the new revision; the same text answers `updated` with nothing written ([runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- Replay and recovery run the latest edited text; the Queued receipt keeps the original text. An edit raises the Thread's sequence, so the snapshot's revision changes ([progress.ts](../../bundles/runtime/runtime/src/host/store/progress.ts), [projector-input.ts](../../bundles/desktop/chat/src/client/domain/projector-input.ts)).

### Superseded pauses

- A prompt accepted with `queued` not `true`, whose source is the reader's, supersedes every paused prompt of its Thread. A superseded prompt is left out of the queue, `resume` answers `unknown_prompt` for it, and the boot does not schedule it. Inputs of other sources and acceptances with `queued: true` supersede nothing ([progress.ts](../../bundles/runtime/runtime/src/host/store/progress.ts), [service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [prompts.ts](../../bundles/runtime/runtime/src/host/domain/prompts.ts)).
- The transcript applies the same rule when it reads the log, live or replayed: a pause marker keeps its resume action until a later non-queued prompt of the reader, a resume or a finish of the same prompt takes it away ([projector.ts](../../bundles/desktop/chat/src/client/domain/projector.ts)).

### Over REST

The `transport` bundle maps the operations onto `/threads`: `POST /:id/interrupt` → `pause`, `POST /:id/steer` → `steer`, `POST /:id/resume` → `resume`, `GET /:id/queue` → `queue`, `POST /:id/queue/resume` → `resumeQueue`, and `GET`, `PATCH` and `DELETE /:id/queue/:promptId` → `queuedPrompt`, `editQueued` and `removeQueued`. Queue reads are not cached. A refused steer answers `409 thread_inactive`, an agent Thread's `forbidden` included. The [`transport` README](../../bundles/foundation/transport/README.md) gives each body, status and error code ([bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts)).

### In the window

- The footer's control is one button that sends (an arrow), resumes queued work (Play), or stops the run (a square, labelled `Stop (Esc)`). It stops while a prompt runs or the Thread is stopping, resumes while the queue holds a resumable or pending item, and sends otherwise; with a queued prompt open for editing it saves (a check). Resume does not consume the draft. The button is disabled while the Thread stops, while a resume is in flight, while an edit saves, and for a resume when the queue failed to load. While an edit is open and a prompt runs, a separate `Stop execution` button sits beside it ([bundles/desktop/chat/src/client/components/organisms/composer-controls.tsx](../../bundles/desktop/chat/src/client/components/organisms/composer-controls.tsx), [bundles/desktop/chat/src/client/components/molecules/composer-button.tsx](../../bundles/desktop/chat/src/client/components/molecules/composer-button.tsx), [domain/queue.ts](../../bundles/desktop/chat/src/client/domain/queue.ts)).
- While a prompt runs, the prompt's keys control it: Cmd/Ctrl+Enter (`chat.send-prompt/v1`) steers it with the draft, Tab queues the draft for after it, Escape with a draft aborts its current step and steers it (`interrupt: true`), and Escape without a draft or Ctrl+C with nothing selected stops it. Tab with nothing to send moves the focus ([send-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/send-prompt.tsx), [bundles/desktop/chat/src/client/hooks/use-thread-chat.ts](../../bundles/desktop/chat/src/client/hooks/use-thread-chat.ts), [bundles/desktop/chat/src/client/services/send-command.ts](../../bundles/desktop/chat/src/client/services/send-command.ts)).
- A send takes one route: a steer of the running prompt when one runs; otherwise, when the queue is paused and holds nothing, it resumes the queue first and then sends; otherwise it only appends a prompt. A refused send gives the reader's words back to the prompt ([bundles/desktop/chat/src/client/domain/send-route.ts](../../bundles/desktop/chat/src/client/domain/send-route.ts), [send-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/send-prompt.tsx)).
- Cmd/Ctrl+Enter with an empty prompt resumes the queue through the same operation as the footer's Play. It does nothing while a prompt runs, the Thread stops or a resume is in flight, when the queue failed to load, or when no item remains. While a queued prompt is being edited, Cmd/Ctrl+Enter saves the edit and does nothing else ([send-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/send-prompt.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/index.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/index.tsx), [bundles/desktop/chat/src/client/components/organisms/conversation/plugins/edit-queue-prompt.tsx](../../bundles/desktop/chat/src/client/components/organisms/conversation/plugins/edit-queue-prompt.tsx)).
- A steer's words stay drawn as a pending turn until the run takes them in. They then render as the reader's turn where `prompt.steered` landed; a steer that returns to the queue renders as a Queued receipt. A bundle's input renders with the bundle and the reason instead of the reader ([projector-input.ts](../../bundles/desktop/chat/src/client/domain/projector-input.ts)).
