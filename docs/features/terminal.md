# Feature: Terminal

- Status: `implemented`

## Problem

The agent needs a shell in its Project's sandbox to run builds, tests and scripts, and it needs the result in a form it can read. A long command must not hold up the agent, and its result must still reach the Thread that started it. The reader needs to see the commands the agent runs while they run, stop them, and open a shell of their own in the same sandbox.

## Decisions

- `terminal/v1.watchProject` is a stream. It sends one snapshot of the Project's sessions on every subscribe, then `updated` and `removed` items, and `output` items only after the snapshot. Output is never buffered for a subscriber: a reader that reconnects reads the terminal's bounded snapshot instead ([src/host/watch.ts](../../bundles/features/terminal/src/host/watch.ts)).
- Every `terminal/v1` method that takes more than one value takes them as a positional tuple (`create(threadId, size)`, `snapshot(terminalId, after)`, `input(terminalId, data)`, `resize(terminalId, cols, rows)`, `rename(terminalId, name)`, `watchProject(projectId, listener)`); `list` and `stop` take one value. `stop` answers whether a session existed ([src/contracts/index.ts](../../bundles/features/terminal/src/contracts/index.ts)).
- `terminal/v1` has two references to the one id `terminal/v1`: `TerminalV1`, typed with `run` only, and `TerminalServiceV1`, the full 1.2.0 service. Both are exported from the bundle's contracts module ([src/contracts/index.ts](../../bundles/features/terminal/src/contracts/index.ts)).
- The registry redacts the terminal stream chunk by chunk with the last list `secrets/v1.watchRedactions` delivered, and reads `secrets/v1.redactions()` again right before each terminal starts ([src/host/redactions.ts](../../bundles/features/terminal/src/host/redactions.ts), [src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).
- `run` throws `Thread is inactive.` when the call's scope has no `threadId` or no `promptId`, when `runtime.workspace/v1.withThread` does not answer `ready`, or when the Thread or its Project is closing. A background command's result goes to `runtime.threads/v1.enqueueTerminalResult`; when the result or its delivery rejects, the provider calls `runtime.threads/v1.failTerminalResult` ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).
- The runtime delivers a background result as a prompt of the input source `terminal`, with its text redacted. A failed delivery logs `Terminal result delivery failed` with the `threadId` and closes the Thread with the failure `terminal_result_failed`, which ends it in the final state `failed`. For a Thread the host does not hold live, `enqueueTerminalResult` does nothing and `failTerminalResult` only logs ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts)).
- The `onThreadsClosingHook` handler of the `terminal` bundle logs `Terminal cleanup failed` with `{ projectId }` and never rejects. The runtime runs the hook and awaits it where Threads close (`close`), where a host stops (`suspend`) and where a Project drains (`drainProject`); a failing handler never fails the close, and the hook does not fire for an empty list of Threads ([src/host/index.ts](../../bundles/features/terminal/src/host/index.ts), [bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)).
- The `terminal` tool runs every command through the bundle's own `terminal/v1`, in the calling prompt's scope. It has no other way to run a command ([src/host/tool.ts](../../bundles/features/terminal/src/host/tool.ts)).
- The desktop reaches every `terminal/v1` method except `run` ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).
- The host part reaches `runtime.workspace/v1`, `runtime.threads/v1` and `runtime.hooks/v1` through local structural copies, each narrowed to what the bundle calls ([src/host/peers.ts](../../bundles/features/terminal/src/host/peers.ts)).
- The client part reaches `files.refresh/v1` through a local structural copy, narrowed to `request`. It builds `ChatViewsV1` from the id `chat.views/v1` and imports the chat's contracts module for types only, since the [`chat`](../../bundles/desktop/chat/README.md) bundle is optional ([src/client/peers.ts](../../bundles/features/terminal/src/client/peers.ts)).
- The "New terminal" button has the order 10 in its region ([src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).
- The sidebar's terminal rows follow each Thread's Project the first time they count that Thread's rows, and sit one level deeper than their Thread, counted through `parentThreadId` ([src/client/index.ts](../../bundles/features/terminal/src/client/index.ts), [src/client/elements.tsx](../../bundles/features/terminal/src/client/elements.tsx)).
- A row's click navigates to `/projects/<projectId>/threads/<threadId>`, when the window's records hold the Thread, before it opens the tab `terminal:<id>` ([src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).
- A change of a Project's terminal activity (id, state, command, working directory) calls `files.refresh/v1.request(projectId)` ([src/client/store.ts](../../bundles/features/terminal/src/client/store.ts), [src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).

## Current behavior and contracts

### The units

The [`terminal`](../../bundles/features/terminal/README.md) bundle, version 1.2.1, provides `terminal/v1@1.2.0` and implements the feature. Its host part holds the session registry, the `terminal/v1` provider and the `terminal` tool; its client part draws the terminals in the window ([manifest.json](../../bundles/features/terminal/manifest.json), [src/host/index.ts](../../bundles/features/terminal/src/host/index.ts), [src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)). Its README holds the full shape of `terminal/v1`, the tool's input and output, the session data, the limits and the errors. The other units, at the grain this feature uses them:

- [`core`](../../bundles/foundation/core/README.md): `tools/v1` registers the `terminal` tool, `secrets/v1` gives the redaction list, `hooks/v1` waits for `runtime.hooks/v1`, `log/v1` takes the two log lines, and in the window `ui/v1` defines the elements, `regions/v1` holds the header button and `navigation/v1` follows a row's click ([manifest.json](../../bundles/features/terminal/manifest.json)).
- [`runtime`](../../bundles/runtime/runtime/README.md): `runtime.workspace/v1` gives the Thread's working directory and runs a task on a live Thread with its sandbox (`withThread`); `runtime.threads/v1` takes a background result; `runtime.hooks/v1` fires when Threads close; `runtime.records/v1` gives the window its Thread records.
- [`default`](../../bundles/runtime/default/README.md): its executor offers the `terminal` tool to the model with every other tool `tools/v1` lists, calls it, and sends its result back to the model ([Tools](../../bundles/runtime/default/README.md#tools)).
- The [`sandbox`](../../packages/sandbox/README.md) package: every session is a process started with the sandbox's optional `start` method, written to with `write`, resized with `resize` and ended with `terminate` ([SandboxSession](../../packages/sandbox/README.md#sandboxsession)).
- [`workspace`](../../bundles/desktop/workspace/README.md): `workspace.sidebar/v1` holds the terminal rows under each Thread and `workspace.selection/v1` gives the selected Thread.
- [`layout`](../../bundles/desktop/layout/README.md): `layout.tabs/v2` opens, retitles and closes the terminal tabs.
- [`chat`](../../bundles/desktop/chat/README.md), optional: `chat.views/v1` draws the tool calls and the background results in the conversation. Without it the bundle draws nothing there.
- [`files`](../../bundles/features/files/README.md), optional: `files.refresh/v1` refreshes the Project's files when its terminals change. Without it nothing is refreshed.
- [`git`](../../bundles/features/git/README.md): lists the sessions for its busy check ([Effects on other units](#effects-on-other-units)).
- The [desktop app](../../app/desktop/doric/README.md): its preload and dispatcher carry the window's `terminal/v1` calls to the host, and `doric.connection/v1` tells the window when the host connection drops ([The window boundary](../../app/desktop/doric/README.md#the-window-boundary)).

### Flow: an agent command

1. The [`default`](../../bundles/runtime/default/README.md) executor calls the tool `terminal`, which the `terminal` bundle registers through `tools/v1` as always available, at the model-visible order 500 ([src/host/index.ts](../../bundles/features/terminal/src/host/index.ts)).
2. The tool reads the Thread's working directory with `runtime.workspace/v1.cwd(call)` and resolves the command's `working_directory` against it; an empty or blank one means the Thread's own. Its timeout is 2 minutes by default and 10 minutes at most; 0 means none ([src/host/tool.ts](../../bundles/features/terminal/src/host/tool.ts)).
3. It calls `terminal/v1.run` in the prompt's scope with the command, the directory, the timeout, `background` and `pty` ([src/host/tool.ts](../../bundles/features/terminal/src/host/tool.ts)).
4. `run` rejects with the call's abort error when the prompt is already cancelled, and with `Thread is inactive.` when the scope has no Thread or prompt. It then runs under `runtime.workspace/v1.withThread(threadId, { exclusive: false })`, which answers only for a Thread the host holds live, with a sandbox, that is neither finished nor closing; any other answer, or a closing Thread or Project inside the task, rejects with `Thread is inactive.` ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts), [runtime.workspace/v1](../../bundles/runtime/runtime/README.md#runtimeworkspacev1)).
5. Inside the task the provider reads `secrets/v1.redactions()` again; a failed read rejects `run` with that error ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts), [src/host/redactions.ts](../../bundles/features/terminal/src/host/redactions.ts)).
6. The registry starts the session. A sandbox object without `start` rejects with `Live terminals are unavailable.` before any session exists. Otherwise the session is published as `starting`, and the registry calls the sandbox's `start` with `sh -lc <command>`, the working directory, `tty` set to `pty`, the environment `TERM=xterm-256color` and `COLORTERM=truecolor` for a PTY, and an abort signal. When `start` fails, the session is removed and `run` rejects with that error. Both shipped sandbox providers, `docker` and `firecracker`, build their sandbox with the `sandbox` package's `createSandbox`, whose session always has `start`; when the provider's runtime has no live processes, that `start` throws `Sandbox provider does not support live processes`, so a shipped sandbox takes this path: the session is published `starting`, then removed, and `run` rejects with that message ([packages/sandbox/src/lib/sandbox.ts](../../packages/sandbox/src/lib/sandbox.ts), [bundles/sandboxes/docker/src/host/sandbox.ts](../../bundles/sandboxes/docker/src/host/sandbox.ts), [bundles/sandboxes/firecracker/src/host/sandbox.ts](../../bundles/sandboxes/firecracker/src/host/sandbox.ts)). Once the process runs, the session is published as `running` ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts)).
7. In the foreground, `run` waits for the result. The prompt's abort signal and the timeout both end the process; the result's reason is `exited`, `timeout`, `terminated` or `failed`, and its exit code is -1 when the process reports none. The tool answers the compact record `terminal.compact.v1`: the exit status, the head and tail of each long stream, and the lines it recognizes as errors, warnings or failed tests ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts), [src/host/tool.ts](../../bundles/features/terminal/src/host/tool.ts), [README's tool](../../bundles/features/terminal/README.md#the-terminal-tool)). With `pty: true` stdout and stderr come combined.
8. With `background: true`, `run` does not take the prompt's abort signal and answers at once; the tool answers `{ terminal_id, background: true }` and the agent keeps working. The command outlives the prompt and stays owned by its Thread, and its result follows [Flow: a background result](#flow-a-background-result) ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).
9. When the command ends, the registry removes its session: a `removed` item reaches every `watchProject` subscriber, and the window drops the row and closes the tab ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).

### Flow: a manual shell

1. The reader clicks "New terminal" in the header region `shell.header.actions`. The button is disabled until `workspace.selection/v1` names a Thread ([src/client/elements.tsx](../../bundles/features/terminal/src/client/elements.tsx), [src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).
2. The window's terminal store calls `terminal/v1.create(threadId, {})` through the desktop bridge: the window sends no size, and the view resizes the PTY once it is drawn ([src/client/store.ts](../../bundles/features/terminal/src/client/store.ts), [src/client/api.ts](../../bundles/features/terminal/src/client/api.ts)).
3. `create` runs under `runtime.workspace/v1.withThread(threadId, { exclusive: true, resume: true })`: it holds the Project lock and brings the Project back when the host does not hold it. It answers `undefined` when there is no such Thread, the Thread is finished or closing, or its Project has no sandbox ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).
4. Inside the task it reads the redaction list again and starts an interactive `bash` in a PTY in the Thread's working directory, with no timeout, as step 6 of the agent's flow starts a command ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts), [src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts)).
5. The answer is the `running` session. The store adds it to its Project's list and opens its tab beside the conversation ([src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).
6. A manual shell never sends anything to its Thread: only `run` with `background` delivers a result ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).

When `create` fails, the reader sees a toast and no tab: `Doric backend is unavailable.` when the bridge answers `unavailable`, `disconnected` or `generation_lost`; `Doric could not complete the terminal request.` for an `undefined` answer or any other error; `Doric returned an invalid terminal.` for a session that fails the window's check ([src/client/api.ts](../../bundles/features/terminal/src/client/api.ts), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).

### Flow: a background result

1. When a background command ends, the provider sends its result once to `runtime.threads/v1.enqueueTerminalResult` with the Thread, the originating prompt, the terminal and a Markdown text headed `# Background terminal result`: the terminal, the prompt, the command, the exit code, the reason and the duration, then the last 12,000 characters of stdout and of stderr ([src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts), [README's background results](../../bundles/features/terminal/README.md#background-results)).
2. For a Thread the host does not hold live, the runtime does nothing. Otherwise, under the Project lock, it drops the result when the Project or the Thread is closing or the Thread is finished, with no delivery and no failure; else it redacts the text and delivers it as a prompt of the source `{ kind: 'terminal', terminalId, promptId }` ([bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue)).
3. A Thread that runs a prompt takes it in as a steer at its next safe point; an idle Thread takes it from its first-in, first-out input queue; a Thread that is stopping or paused queues it. In the queue it shows with the label `Terminal` and its `Command:` line as preview ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/store/queue.ts](../../bundles/runtime/runtime/src/host/store/queue.ts)).
4. When the delivery fails, or the provider's call rejects, the runtime logs `Terminal result delivery failed` and closes the Thread with `terminal_result_failed`: its running prompt is aborted, its other terminals stop, and the Thread ends `failed`, a final state that only `restart` of a direct child reopens ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [Thread](../../bundles/runtime/runtime/README.md#thread)).

A background command that ends because its Thread closes, its Project drains or the host stops delivers no result: each of these marks the Thread closing before the hook stops its sessions, so the agent is not told ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts)). A background command the reader stops does deliver one, with the reason `terminated` ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts), [src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).

### The session lifecycle

The host holds every session in process memory, in one registry; none is stored, so none survives a host restart. A session belongs to one Thread and runs in that Thread's Project sandbox. Its `TerminalSession` record holds its id, `projectId`, `threadId`, origin (`agent` for the tool's commands, `user` for a manual shell), command, working directory, start time, timeout (`null` for none), state, `pty` and an optional name; its full shape is in the [README's types](../../bundles/features/terminal/README.md#types) ([src/contracts/index.ts](../../bundles/features/terminal/src/contracts/index.ts), [src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts)).

| Origin  | `starting`                    | `running`                | Then                                                                       |
| ------- | ----------------------------- | ------------------------ | -------------------------------------------------------------------------- |
| `agent` | Published when it is created. | Once the process starts. | Removed when the command ends, or when it is stopped.                      |
| `user`  | Published when it is created. | Once the process starts. | `exited` when the shell exits, and stays until stopped; removed on `stop`. |

A session whose start fails is removed from `starting`. `stop` aborts the process, waits for it to end and removes the session, whatever its state ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts)). When Threads close, the bundle's `runtime.hooks/v1.onThreadsClosingHook` handler stops the sessions of those Threads only; the runtime fires it when it terminates Threads or their Project, when the host stops, and when a Project drains from the host ([src/host/index.ts](../../bundles/features/terminal/src/host/index.ts), [runtime.hooks/v1](../../bundles/runtime/runtime/README.md#runtimehooksv1)).

A manual shell's command is read from markers the shell prints, never from keystrokes: it reads `bash` while the shell is idle and the running command otherwise. Each session keeps a bounded tail of its output, and a snapshot after an offset older than that tail is marked `truncated` ([README's sessions](../../bundles/features/terminal/README.md#sessions), [src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts)).

Only the `terminal` tool and manual shells create sessions. The filesystem and Git probes of `files` run through the sandbox's `exec` and never appear as terminals ([bundles/features/files/src/host/reads.ts](../../bundles/features/files/src/host/reads.ts), [bundles/features/files/src/host/tools/find.ts](../../bundles/features/files/src/host/tools/find.ts), [bundles/features/files/src/host/tools/grep.ts](../../bundles/features/files/src/host/tools/grep.ts), [bundles/features/files/src/host/tools/visible-files.ts](../../bundles/features/files/src/host/tools/visible-files.ts)).

### Effects on other units

- **The sidebar's busy mark.** An agent session that has not exited (`starting` or `running`) keeps its Thread marked busy in the sidebar; a manual one never does ([src/client/domain/terminals.ts](../../bundles/features/terminal/src/client/domain/terminals.ts), [src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).
- **Git's busy check.** `git` lists the Project's sessions through `terminal/v1.list`. A session that has not exited and is either an agent's or a manual shell whose command is not `bash` counts as running work in its working directory. Running work in the same repository blocks a branch switch with `Wait for active prompts and terminal commands in this worktree to finish before switching branches.`, and a Discard with `Wait for active prompts and terminal commands in this repository to finish before discarding changes.` The shell's markers are what tell an idle manual shell from a busy one ([bundles/features/git/src/host/service.ts](../../bundles/features/git/src/host/service.ts), [git's `switchBranch`](../../bundles/features/git/README.md#branches-and-switchbranch), [git's `discard`](../../bundles/features/git/README.md#discard)).
- **The chat's live output.** A tool call's row watches its terminal's output only while the session is `starting` or `running` ([src/client/chat/live-output.ts](../../bundles/features/terminal/src/client/chat/live-output.ts)).
- **The file refresh.** A change of a Project's terminal activity (id, state, command or working directory) asks `files.refresh/v1` to refresh that Project ([src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).

### Redaction and what the agent sees

- The registry replaces each secret on the `secrets/v1` redaction list with `[REDACTED]` in the session's command, in its live output and in its retained output, so every snapshot and stream item is redacted. It holds back the end of a chunk that could begin a secret until the next chunk arrives. It redacts only that list: a Git token the runtime applies to a sandbox is redacted in the terminal only while the secret store holds it ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts), [src/host/redactions.ts](../../bundles/features/terminal/src/host/redactions.ts)).
- The `stdout` and `stderr` of a foreground `run` result are the process's own output, not redacted by the registry. The `default` executor keeps the run's messages in memory and sends the tool result to the model in the same run as the tool answered it, capped at the tool-result limit and not redacted: the `agent` package caps the answer and pushes it into those messages. What the executor stores is redacted by the runtime on write, so a later run, which reads the stored history, sees the redacted copy ([src/host/registry.ts](../../bundles/features/terminal/src/host/registry.ts), [bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts), [packages/agent/src/lib/agent.ts](../../packages/agent/src/lib/agent.ts), [agent's tool results](../../packages/agent/README.md#tool-results-and-the-ledger), [One prompt run](../../bundles/runtime/default/README.md#one-prompt-run)).
- What the conversation stores is redacted by the runtime with its own list: the secrets on the `secrets/v1` list and the Git token it applied to the Project's sandbox. That covers the background result's text and every recorded event and history part, tool results included. The conversation keeps the tool results and the background results; it keeps no terminal session ([bundles/runtime/runtime/src/host/domain/redactor.ts](../../bundles/runtime/runtime/src/host/domain/redactor.ts), [bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), [bundles/runtime/runtime/src/host/domain/session.ts](../../bundles/runtime/runtime/src/host/domain/session.ts), [Redaction](../../bundles/runtime/runtime/README.md#redaction)).
- The host part writes no terminal command or output to the log. It logs only `Terminal cleanup failed` with the Project's id and `Terminal result delivery failed` with the Thread's id ([src/host/index.ts](../../bundles/features/terminal/src/host/index.ts), [src/host/provider.ts](../../bundles/features/terminal/src/host/provider.ts)).

### The window's path to the host

The window reaches `terminal/v1` only through the Electron preload's `window.doric.desktop`. The main process's dispatcher forwards each call to the host over the main process's own Socket.IO connection on `/doric/bridge`; the window's packaged content security policy is `connect-src 'none'`, and no window policy allows a connection to the host, so the window opens no HTTP or Socket.IO connection to the host of its own ([app/desktop/doric/src/app/api/preload.ts](../../app/desktop/doric/src/app/api/preload.ts), [app/desktop/doric/src/platform/bridge/dispatcher.ts](../../app/desktop/doric/src/platform/bridge/dispatcher.ts), [app/desktop/doric/src/platform/bridge/host-bridge.ts](../../app/desktop/doric/src/platform/bridge/host-bridge.ts), [app/desktop/doric/src/platform/protocol/csp.ts](../../app/desktop/doric/src/platform/protocol/csp.ts)).

Separately, the host's REST routes and its `/projects` Socket.IO namespace, which the [`transport`](../../bundles/foundation/transport/README.md) bundle serves and which are not the window's path, read and drive the same sessions through `terminal/v1` ([bundles/foundation/transport/src/host/routes/terminals.ts](../../bundles/foundation/transport/src/host/routes/terminals.ts), [bundles/foundation/transport/src/host/sockets/terminal-feed.ts](../../bundles/foundation/transport/src/host/sockets/terminal-feed.ts)).

### In the window

The README's [window](../../bundles/features/terminal/README.md#the-window) holds the row labels, the view's settings and the watch limits.

- **One store.** The window keeps one terminal store, which follows each Project's sessions through `watchProject`. When a session leaves its Project's list, its tab closes, so a finished agent command leaves both the sidebar and the open tabs ([src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).
- **Rows.** The sidebar lists a Thread's terminals under it through `workspace.sidebar/v1`: an agent row shows its command, its elapsed time and its timeout; a manual row shows the shell's current command. A name, when set, replaces the command. A row's click selects its Thread, when the window's records hold it, and opens the terminal's tab, or shows it when open ([src/client/index.ts](../../bundles/features/terminal/src/client/index.ts), [src/client/rows/terminal-rows.tsx](../../bundles/features/terminal/src/client/rows/terminal-rows.tsx), [src/client/domain/terminals.ts](../../bundles/features/terminal/src/client/domain/terminals.ts)).
- **Stopping.** A row's stop button ("Stop terminal" for an agent terminal, "Discard terminal" for a manual one), Kill terminal in the row's or the tab's context menu, and the Stop action of a tool call in the conversation all call `stop`. Stopping a background agent command ends it with the reason `terminated`, and its result still goes to the Thread ([Flow: a background result](#flow-a-background-result)). A failed stop is a toast ([src/client/rows/terminal-rows.tsx](../../bundles/features/terminal/src/client/rows/terminal-rows.tsx), [src/client/tab.ts](../../bundles/features/terminal/src/client/tab.ts), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).
- **Rename and Copy command.** Rename, in the row's context menu, turns the row into a name field of at most 80 characters: Enter sends the trimmed text (empty clears the name), Escape or leaving the field cancels, and the field closes whatever the answer. A failed call keeps the old name and shows a toast; an answer of `false`, a session already gone, shows none. Copy command writes the command to the clipboard; a refusal is the toast `Could not copy the command.` ([src/client/rows/terminal-rows.tsx](../../bundles/features/terminal/src/client/rows/terminal-rows.tsx), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts), [src/client/api.ts](../../bundles/features/terminal/src/client/api.ts)).
- **Tabs.** A terminal's tab is titled by its name, else its command, else "Terminal", and follows every rename and command change. Closing the tab only closes the tab: the process keeps running and its row reopens it. The workspace, drawn by `layout`, keeps an open tab's element mounted while another tab is shown, so switching tabs keeps the emulator ([src/client/tab.ts](../../bundles/features/terminal/src/client/tab.ts), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts), [bundles/desktop/layout/src/client/components/organisms/workspace-tabs.tsx](../../bundles/desktop/layout/src/client/components/organisms/workspace-tabs.tsx)).
- **The view.** The tab draws an xterm emulator. An agent terminal's view has a header with its command; a manual shell's has none. The view sends every keystroke to `input` for any session that has not exited, an agent command's included; writes to one terminal reach the host in the order they were typed. It sends a resize only for a PTY session that has not exited, and only when its columns or rows change. A manual shell whose process exited stays open in its tab and takes no input; its tab and row carry no mark of the exit. A failed input or resize, such as one for a session already gone, shows in the view's alert line ([src/client/view/terminal-view.tsx](../../bundles/features/terminal/src/client/view/terminal-view.tsx), [src/client/input-queue.ts](../../bundles/features/terminal/src/client/input-queue.ts), [src/client/api.ts](../../bundles/features/terminal/src/client/api.ts)).
- **Output.** A view reads the terminal's snapshot on every subscribe and then the stream, and draws only the output it has not seen, so a reconnect neither repeats nor loses output; a truncated snapshot first writes `[Earlier output is no longer available]`. All the watchers of one terminal share one stream, which closes when the last one stops ([src/client/output-watch.ts](../../bundles/features/terminal/src/client/output-watch.ts), [src/client/view/terminal-view.tsx](../../bundles/features/terminal/src/client/view/terminal-view.tsx)).
- **Connection loss.** The watches read the connection state from `doric.connection/v1` ([Contexts](../architecture/bundles/contexts.md#shapes-of-the-platform-contracts)). A dropped connection or a lost host generation shows nothing and subscribes again once connected, or after one second. An output watch shows its messages in the view's alert line: `The terminal connection failed.` for any other end of its stream, and `The terminal is no longer available.` for a terminal whose snapshot cannot be read, on the first read or after a resubscribe. A Project watch's messages are toasts: `The terminal connection failed.` for any other end of its stream, and `The terminal list could not be read.` or `The terminal could not be read.` for a list or a session that fails the window's check ([src/client/output-watch.ts](../../bundles/features/terminal/src/client/output-watch.ts), [src/client/view/terminal-view.tsx](../../bundles/features/terminal/src/client/view/terminal-view.tsx), [src/client/store.ts](../../bundles/features/terminal/src/client/store.ts)).

### In the conversation

- While `chat.views/v1` is served, the bundle registers the element `terminal-tool-call` for the `terminal` tool and the element `terminal-result` for the input source `terminal`, each in a registration of its own ([src/client/index.ts](../../bundles/features/terminal/src/client/index.ts)).
- `terminal-tool-call` draws each `terminal` call. A foreground call carries no terminal id while it runs, so the row finds its session in the window's store: the session the call's background answer names, whatever its Thread or state; otherwise, only while the call runs, an agent session of the call's Thread running the call's command (any command when the call names none), the newest that has not exited, else the newest. The [README's chat](../../bundles/features/terminal/README.md#in-the-chat) holds the rule ([src/client/domain/live-terminal.ts](../../bundles/features/terminal/src/client/domain/live-terminal.ts)). While its terminal is `starting` or `running` it shows the live output, the last 32,000 characters drawn at most every 50 ms, and a Stop action, which stops the terminal and disappears at once ([src/client/chat/terminal-call.tsx](../../bundles/features/terminal/src/client/chat/terminal-call.tsx), [src/client/chat/live-output.ts](../../bundles/features/terminal/src/client/chat/live-output.ts), [src/client/domain/live-terminal.ts](../../bundles/features/terminal/src/client/domain/live-terminal.ts)).
- `terminal-result` draws a background result as a block named "Background terminal", or "Background terminal failed" when the reason is not `exited` or the exit code is not 0; a failed result's block is open, any other is folded. A prompt of the source `terminal` without the host's frame is a block labelled "Terminal" holding its text as read-only Markdown ([src/client/chat/terminal-result.tsx](../../bundles/features/terminal/src/client/chat/terminal-result.tsx), [src/client/domain/terminal-result.ts](../../bundles/features/terminal/src/client/domain/terminal-result.ts)).
