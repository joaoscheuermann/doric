# Feature: bundle isolation

- Status: `implemented`

## Problem

Doric is a platform and 33 bundles, and every feature of the app is a bundle or a part of one ([The bundle map](../architecture/bundles/feature-split.md)). A bundle is worth having only when it can change alone: a change to a feature lands in the bundle that owns it, a bundle loads in a composition that lacks the bundles that extend it, and the platform does not change when a bundle does. Nothing in a language or a package manager keeps that true. A bundle can import another bundle's source, name the bundles that fill it, enumerate their tools, hand out another bundle's records through its own contract or give out a live database client, and the code still compiles and runs.

Bundle isolation is the boundary model that keeps the bundles apart: eleven rules, a manifest that lists every contract a bundle provides or uses, the import paths between bundles (`<id>/contracts` and its generated code), the checks CI runs over the whole repository, and one file that lists every violation the checks find and the document that keeps it. A rule a machine can decide is a test; the others are applied in review.

## Decisions

- **One function.** A bundle's manifest `description` states one function, and every contract, slot, route and tool the bundle provides serves it.
- **Contracts only.** A bundle reaches another bundle only through what that bundle publishes: its contracts, imported from `<id>/contracts`, or from `<id>/contracts/gen/<path>` for the code generated from its `.proto` files. A file under the bundle's `tests/` or `stories/` may also import `<id>/testing`, and a file under `tests/` `<id>/package.json`, which locates the other bundle's built parts. No file anywhere imports `<package>/src/…` of a workspace package, and no entry of the exceptions file can excuse such an import.
- **One direction.** Where bundle B contributes into bundle A, A does not name B. The edges between bundles, drawn from every `requires` and `optional` line, form no cycle. For a contract that one bundle declares and other bundles provide, the edge runs from each provider to the declarer: `executor/v1` and `sandbox/v1`, declared by `runtime`; `default.skill-sources/v1`, declared by `default`; `files.decorations/v1`, declared by `files`.
- **Declared extension points.** Every way to add something to a bundle is a contract it provides or a slot it declares. A set other bundles extend (tools with a drawing, icons, tab kinds, provider kinds, input sources, skill sources) is open: its members are registered, not enumerated.
- **Owners announce.** A bundle registers its own tools, commands, routes, slot items and drawings from its own code. No bundle registers, opens or draws on behalf of another.
- **Base capabilities stay generic.** The platform declares the base contracts, in `bundle/contracts`, and one `core` bundle provides them, except the backend and model-provider contracts other bundles provide; the core is not split. Neither the platform nor the core names a feature bundle's concept: no Project, Thread or prompt, and no feature bundle's route. The platform never imports a bundle outside its tests. The recorded exceptions are the core's command, window keys and selection key, the optional `projectId` of `tools/v1`, and the papercraft cache that the Electron main process places by the bundle's id; each is listed below.
- **Data has one owner.** A record is read through a contract of the bundle that owns it. A bundle does not hand out another bundle's record types through its own contract, imported or retyped. It may publish a view of another bundle's data: a read-only type it declares itself, holding what its own function produces from that data and no field it does not use. `settings.models/v1`, the configured models with the labels, groups and icons `settings` computes, is such a view of the configuration [`host-config`](../../bundles/foundation/host-config/README.md) owns.
- **Persistence by operations.** A backend bundle exposes operations. No contract hands out a live client or connection: `postgres` provides `storage.backend/v1` and `secrets.backend/v1`, keeps its Prisma client internal, and exports the client only from `postgres/testing`, for tests.
- **One source for the bundle set.** The bundles of a build are the manifests on disk. Every other list of bundles is derived from them, checked against them, or is a named deployment choice; `enabled` in the host's `composition.json` is the deployment choice, written by hand.
- **Plain data in added contracts.** A contract method a change adds takes and returns plain data. A contribution to another bundle's surface names an element tag and gives props, and the element answers with DOM events; it passes no function, component or live object, except a subscription listener and the `Disposable` that ends a registration or subscription ([`context.ts`](../../packages/bundle/src/contracts/context.ts), [`basic/common.ts`](../../packages/bundle/src/contracts/basic/common.ts), [`basic/regions.ts`](../../packages/bundle/src/contracts/basic/regions.ts)). A contract that moves between bundles is not reshaped for this rule.
- **Enforced or listed.** Each rule a machine can check is a test CI runs. Each standing violation a check finds is one entry of the exceptions file, with the document that keeps it.
- The six checks are one test file, run by `npm run lint:test` beside the Biome tests. The exceptions file holds one list, `violations`, which the checks match to their findings one to one. CI also runs the `test` target of every bundle.
- The runtime owns the records mirror, the client contract `runtime.records/v1` that its client part provides, and `workspace` publishes the selection as ids only, in `workspace.selection/v1`.
- Slots are string names. Each is owned by the bundle that draws its place on the screen and exported from that bundle's contracts module as a constant (`shell.*` by `layout`, `workspace.*` by `workspace`, `account.*` by `account`, `settings.*` by `settings`); `regions/v1` has no declaration of slots. A bundle that fills a slot writes the name as a literal checked against the owner's constant through a type-only import.
- A client part imports a value from another bundle's contracts module only when its manifest lists a contract of that bundle under `requires`. For a contract under `optional`, it imports the types with `import type` and declares the ref by its id.
- The core keeps the command `core.open-settings/v1`, the window keys `settings` and `workspace` with their sizes ([`appearance.ts`](../../bundles/foundation/core/src/desktop/appearance.ts)), and the local-storage key `doric.selection`, and holds no settings route: a caller passes the path to open, as `path` or `defaultPath` ([`commands.ts`](../../bundles/foundation/core/src/desktop/commands.ts), [`index.ts`](../../bundles/foundation/core/src/desktop/index.ts), [`migrations.ts`](../../bundles/foundation/core/src/desktop/migrations.ts)). A tool of `tools/v1` keeps its optional `projectId` ([`tools.ts`](../../packages/bundle/src/contracts/basic/tools.ts)).
- Five placements hold although no check sees them: the comments UI is the chat's, and `chat` requires `comments/v1` ([`chat/manifest.json`](../../bundles/desktop/chat/manifest.json)); `sandbox/v1` and `executor/v1` are declared in `runtime/contracts` ([`declaredContracts`](../../tests/support/boundaries.mjs)); the Electron main process places the cache of [`papercraft`](../../bundles/features/papercraft/README.md) itself, by the bundle's id ([`app.ts`](../../app/desktop/doric/src/platform/app.ts)); [`transport`](../../bundles/foundation/transport/README.md) serves the per-feature REST routes and Socket.IO namespaces, reaching `files/v1`, `git.commands/v1`, `usage/v1`, `resources/v1` and `terminal/v1` under `optional` and the runtime's contracts under `requires` ([`transport/manifest.json`](../../bundles/foundation/transport/manifest.json), [`host.ts`](../../bundles/foundation/transport/src/host/api/operations/host.ts), [`terminals.ts`](../../bundles/foundation/transport/src/host/api/operations/terminals.ts)); and `transport` answers REST errors from the table `runtime` keeps in its contracts module ([`rest-errors.ts`](../../bundles/runtime/runtime/src/contracts/rest-errors.ts), [`threads.ts`](../../bundles/foundation/transport/src/host/api/operations/threads.ts)).

## Current behavior and contracts

The mechanisms below have their full description in three architecture documents: [Bundle boundaries](../architecture/bundles/boundaries.md) for the rules, the checks and the exceptions file; [The bundle manifest](../architecture/bundles/manifest.md) for `provides`, `requires` and `optional`; and [Contracts](../architecture/bundles/contracts.md) for contract ids, the `contracts` entry point and structural copies. The rules are written as instructions for agents in [`bundles/AGENTS.md`](../../bundles/AGENTS.md). Which bundle owns what is in [The bundle map](../architecture/bundles/feature-split.md).

### The platform and the bundles

- The platform is `packages/bundle`, `packages/desktop`, the desktop app (`app/desktop/doric`, `app/desktop/doric-renderer`, `app/desktop/doric-platform`) and the kernel `app/backend/doric-host`. It installs bundles, composes providers, routes calls, and runs processes, windows and IPC; it reaches a bundle only through contract ids, manifests and the data a call carries ([Bundle boundaries](../architecture/bundles/boundaries.md#the-platform-and-what-it-never-knows)).
- The base contracts (`hooks/v1`, `tools/v1`, `storage/v1`, `regions/v1` and the others) are declared in [`packages/bundle/src/contracts/basic/`](../../packages/bundle/src/contracts/basic/index.ts). The [`core`](../../bundles/foundation/core/README.md) bundle provides each of them except `storage.backend/v1` and `secrets.backend/v1`, which [`postgres`](../../bundles/foundation/postgres/README.md) provides, and `models.provider/v1`, which each provider bundle provides ([`core/manifest.json`](../../bundles/foundation/core/manifest.json), [`postgres/manifest.json`](../../bundles/foundation/postgres/manifest.json)). The core's manifest has no `desktopScope`, so a window call to a core contract whose scope carries `projectId`, `threadId` or `promptId` is refused with `invalid_input` ([`dispatcher.ts`](../../app/desktop/doric/src/platform/bridge/dispatcher.ts)), and its sources do not write the route `'/settings'`: `core.open-settings/v1` opens the path its caller passes ([`commands.ts`](../../bundles/foundation/core/src/desktop/commands.ts)).
- The host imports no bundle: it boots the platform over the staged bundles ([`boot.ts`](../../app/backend/doric-host/src/lib/bundles/boot.ts)); its Socket.IO buffer limit went with the bridge in slice S63b.

### Parts per process

A bundle is a folder `bundles/<group>/<id>/` with a `manifest.json`, and it has only the parts it has a source entry for ([`cli.ts`](../../packages/bundle/src/build/cli.ts), [`parts.ts`](../../packages/bundle/src/build/parts.ts)):

| Part        | Entry                  | Runs in                                            |
| ----------- | ---------------------- | -------------------------------------------------- |
| `host`      | `src/host/index.ts`    | The host process                                   |
| `desktop`   | `src/desktop/index.ts` | The desktop app's main process (`desktopMain`)     |
| `client`    | `src/client/index.ts`  | Each app window                                    |
| `contracts` | `src/contracts/`       | Every process that imports it, as `<id>/contracts` |

- Each part exports `activate`, and the bundle build imports each built part, runs `activate` against recording services and fails when what the part provides, defines or registers differs from the manifest's `provides` ([`cli.ts`](../../packages/bundle/src/build/cli.ts), [`record.ts`](../../packages/bundle/src/build/record.ts)).
- The build fails on an import a part may not contain: a desktop part may not import `bundle`, `react`, `react-dom`, `@base-ui/react`, `lexical`, `@lexical/*` or any `desktop` entry point; a client part may not import `bundle`, `bundle/runtime`, `desktop`, `desktop/client` or any `desktop/client/…` subpath ([`parts.ts`](../../packages/bundle/src/build/parts.ts)). A client part's `<id>/contracts` imports stay external and resolve through the window's import map, which holds one entry for each bundle of the window's generation that ships a `contracts` module ([`externals.ts`](../../packages/bundle/src/build/externals.ts), [`import-map.ts`](../../app/desktop/doric/src/platform/protocol/import-map.ts)). The full table is in [Bundle boundaries](../architecture/bundles/boundaries.md#what-a-client-part-may-import-and-slot-names).
- A part in `host` is served by providers in `host`, a part in `desktopMain` by providers in `desktopMain`, and a part in `client` by providers in `client`, `desktopMain` and `host` ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts), [Manifest](../architecture/bundles/manifest.md#requires-activation-dependencies)).

### Manifests: `provides`, `requires` and `optional`

A bundle's manifest says what it provides and every contract it uses that it does not provide ([`manifest.ts`](../../packages/bundle/src/runtime/manifest.ts), [Manifest](../architecture/bundles/manifest.md#provides-requires-and-optional)):

- `provides` lists each contract a part of the bundle provides, defines or registers, with its exact version.
- `requires` lists, with a version range, each contract the bundle cannot run without. The catalog orders activation by it and quarantines the bundle with `missing_dependency` when no enabled bundle provides the contract, with `dependency_quarantined` when every provider is quarantined, and every member of a `requires` cycle with `dependency_cycle` ([`catalog.ts`](../../packages/bundle/src/runtime/catalog.ts)).
- `optional` lists, by bare id, each contract the bundle uses when a provider is there and does without otherwise. The catalog does not read it, so a missing provider neither quarantines the bundle nor orders its activation. A bundle typically reaches such a contract through `whenAvailable` ([`services.ts`](../../packages/bundle/src/runtime/services.ts)).
- `services.use` and `hooks/v1.use` throw `undeclared_requirement` for a contract the manifest lists under neither, the bundle does not provide and that is not a `doric.*` platform contract; the build's dry activation applies the same rule ([`services.ts`](../../packages/bundle/src/runtime/services.ts), [`record.ts`](../../packages/bundle/src/build/record.ts)). `whenAvailable` is not checked at run time; the `declared` check holds it in the repository.

Both `requires` and `optional` lines are edges between bundles for the `cycles` check. `files` lists `files.decorations/v1` under `optional` and `git` provides it, so the edge runs from `git` to `files`; `default` lists `default.skill-sources/v1` under `optional` and `mcp` provides it, so the edge runs from `mcp` to `default` ([`files/manifest.json`](../../bundles/features/files/manifest.json), [`git/manifest.json`](../../bundles/features/git/manifest.json), [`default/manifest.json`](../../bundles/runtime/default/manifest.json), [`mcp/manifest.json`](../../bundles/features/mcp/manifest.json), [`boundaries.mjs`](../../tests/support/boundaries.mjs)). The [`files`](../../bundles/features/files/README.md), [`git`](../../bundles/features/git/README.md), [`default`](../../bundles/runtime/default/README.md) and [`mcp`](../../bundles/features/mcp/README.md) READMEs describe the two contracts.

### Imports between bundles

- A bundle's source names another bundle's package only as exactly `<id>/contracts` or as `<id>/contracts/gen/<path>`, its generated code; its tests and stories may also name `<id>/testing`, and its tests `<id>/package.json`. Any other subpath, `<id>/contracts/<file>` outside `gen/` included, is a finding of the `imports` check ([`boundaries.mjs`](../../tests/support/boundaries.mjs), [Contracts](../architecture/bundles/contracts.md#what-a-bundle-may-import), [gRPC processes](../designs/grpc-processes.md#8-contracts-in-proto)). Until phase 3 a client or desktopMain part imports neither `<id>/contracts/gen/*` nor its own generated code: its build externalizes only `bundle/contracts` and `*/contracts` and turns its own `src/contracts/…` imports into `<id>/contracts` ([`parts.ts`](../../packages/bundle/src/build/parts.ts), [`externals.ts`](../../packages/bundle/src/build/externals.ts)).
- A bundle imports its own contracts by relative path. The build of a desktop or client part turns an import that resolves into its own `src/contracts/` into the external `<id>/contracts`, so each process or window holds one instance of the module; a client frame (`src/client/frames/*.ts`) bundles the contracts it imports, and the host part is compiled by `tsc` ([`terminal/project.json`](../../bundles/features/terminal/project.json), [`cli.ts`](../../packages/bundle/src/build/cli.ts), [`parts.ts`](../../packages/bundle/src/build/parts.ts)).
- For a contract under `requires`, a client part imports the ref from `<id>/contracts` as a value. For a contract under `optional`, it imports the types only and declares the ref by its id, so the part loads in a window without the provider: `terminal` reaches `chat.views/v1` as `ref<ChatViews>('chat.views/v1')` ([`terminal/src/client/peers.ts`](../../bundles/features/terminal/src/client/peers.ts), [`terminal`](../../bundles/features/terminal/README.md)).
- A bundle may keep a structural copy of another bundle's contract, a local interface under the same id, where it must load without the owner; the copy keeps its manifest line. `chat` reads `workspace.selection/v1` through such a copy and lists it under `optional` ([`workspace-selection.ts`](../../bundles/desktop/chat/src/client/api/workspace-selection.ts), [`chat`](../../bundles/desktop/chat/README.md), [Contracts](../architecture/bundles/contracts.md#structural-copies)).
- A bundle's `package.json` lists every package it imports and none it does not use: Biome's rule `noUndeclaredDependencies` reports the first half for `bundles/**`, and the `dependencies` check the second, which counts `@bufbuild/protobuf` as used by a package that exports `./contracts/gen/*`, since its Git-ignored generated code imports it (rule 6 of the `dependencies` finder) ([`biome.json`](../../biome.json), [Bundle boundaries](../architecture/bundles/boundaries.md#what-a-bundles-packagejson-lists)).

### Slots and extension points

- A slot is a region name of `regions/v1`, which holds items under string names and declares none ([`regions.ts`](../../packages/bundle/src/contracts/basic/regions.ts)). The [`layout`](../../bundles/desktop/layout/README.md) bundle, the workspace window's frame, exports the `shell.*` slots as constants (`SHELL_PANEL = 'shell.panel'` and the others) and draws each one ([`layout/src/contracts/index.ts`](../../bundles/desktop/layout/src/contracts/index.ts)); [`workspace`](../../bundles/desktop/workspace/README.md), [`account`](../../bundles/desktop/account/README.md) and [`settings`](../../bundles/desktop/settings/README.md) export their own. A filler writes `region: 'shell.panel' satisfies typeof SHELL_PANEL` with an `import type` of the owner's contracts, so the slot name adds no load dependency on the owner ([`files/src/client/index.ts`](../../bundles/features/files/src/client/index.ts), [UI composition](../architecture/bundles/ui-composition.md)).
- An open set is a registration point of its owner. The chat draws a tool call or an input source with the element its owner registers through `chat.views/v1.registerToolRenderer` and `registerInputRenderer`: `files` registers `edit`, `write` and `view-image`, `terminal` the `terminal` tool and the input source `terminal`, `threads` `thread-spawn`, and `default` `load_skill` ([`files/src/client/chat/views.ts`](../../bundles/features/files/src/client/chat/views.ts), [`terminal/src/client/index.ts`](../../bundles/features/terminal/src/client/index.ts), [`threads/src/client/index.ts`](../../bundles/features/threads/src/client/index.ts), [`default/src/client/index.ts`](../../bundles/runtime/default/src/client/index.ts), [`threads`](../../bundles/features/threads/README.md)). Skill sources register as providers of `default.skill-sources/v1`, and file marks as providers of `files.decorations/v1`.
- Records come from their owner: the [`runtime`](../../bundles/runtime/runtime/README.md)'s client part provides `runtime.records/v1`, the mirror of Projects and Threads that the windows' bundles read, and `runtime/testing` exports an in-memory provider of it for tests and stories ([`records.ts`](../../bundles/runtime/runtime/src/client/records.ts), [`testing.ts`](../../bundles/runtime/runtime/src/testing.ts)). `workspace.selection/v1` carries the selected `projectId` and `threadId` only ([`workspace/src/contracts/index.ts`](../../bundles/desktop/workspace/src/contracts/index.ts)).
- The [`postgres`](../../bundles/foundation/postgres/README.md) bundle exports no `contracts` module; its package exports `./package.json` and `./testing` ([`postgres/package.json`](../../bundles/foundation/postgres/package.json), [`postgres/src/testing.ts`](../../bundles/foundation/postgres/src/testing.ts)).

### The boundary checks and the exceptions file

- `npm run lint:test` runs `tests/lint.test.mjs`, then [`tests/boundaries.test.mjs`](../../tests/boundaries.test.mjs) and then [`tests/contract-inventory.test.mjs`](../../tests/contract-inventory.test.mjs) ([bundle processes](bundle-processes.md)), one after the other, and CI runs it in the step "Test Biome configuration, bundle boundaries and the contract inventory" ([`package.json`](../../package.json), [`ci.yml`](../../.github/workflows/ci.yml)). The test reads the repository once and runs six finders over it ([`tests/support/boundaries.mjs`](../../tests/support/boundaries.mjs)):

  | Check          | Holds                          | Reports                                                                                                                                             |
  | -------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `imports`      | Contracts only                 | An import of `<package>/src/…`; an import of another bundle's package other than the paths above                                                    |
  | `declared`     | One direction                  | A contract id another bundle provides that a bundle uses and does not list; a `requires` or `optional` line no manifest provides                    |
  | `cycles`       | One direction                  | A cycle among the bundles that the listed edges do not break; a listed edge that is not in the graph or breaks no cycle                             |
  | `core`         | Base capabilities stay generic | A core `desktopScope` key `projectId`, `threadId` or `promptId`; a production import of a bundle from a platform package; `'/settings'` in the core |
  | `lists`        | One source for the bundle set  | A host build file that names a bundle; an id in `composition.json` with no manifest on disk                                                         |
  | `dependencies` | The `package.json` rule        | A package a bundle lists and does not use                                                                                                           |

  What each finder reads and how it matches is in [Bundle boundaries](../architecture/bundles/boundaries.md#the-checks).

- [`tests/boundary-exceptions.json`](../../tests/boundary-exceptions.json) is `{ "violations": [ … ] }`, each entry `{ check, bundle, target, decision, until? }`, where `decision` is the path of the document that keeps the violation. The test fails on a finding no entry lists, on an entry that matches no finding, and on an entry whose `decision` file does not exist, so the file always equals the violations the checks find; for `cycles`, an entry names an edge that breaks a cycle ([`boundaries.mjs`](../../tests/support/boundaries.mjs), `diffViolations`; [Bundle boundaries](../architecture/bundles/boundaries.md#the-exceptions-file)). The file holds no entry.
- The host's `build-bundles` target builds every Nx project tagged `type:bundle` and stages every `bundles/<group>/<id>` that holds a `manifest.json` with `stage … --all bundles`; neither the host's `project.json` nor its `.Dockerfile` names a bundle ([`doric-host/project.json`](../../app/backend/doric-host/project.json), [`cli.ts`](../../packages/bundle/src/build/cli.ts)).
- CI runs `npx nx run-many -t test --projects=tag:type:bundle`, every bundle's own tests, with the test database set ([`ci.yml`](../../.github/workflows/ci.yml)).

### What review holds

No boundary check decides one function, declared extension points, owners announce, data has one owner, persistence by operations or plain data in added contracts, nor whether an edge between two bundles that closes no cycle runs the wrong way. They are applied in review, with the rules as [`bundles/AGENTS.md`](../../bundles/AGENTS.md) states them and their reading in [Bundle boundaries](../architecture/bundles/boundaries.md#the-rules) and [Contracts](../architecture/bundles/contracts.md#two-rules-for-the-content-of-a-contract).

- One bundle's own test holds part of data has one owner: `workspace` checks that no source file under its `src` names `runtime/v2` or `runtime.threads/v1`, or their refs, so it reads and writes Projects and Threads through `runtime.records/v1` only ([`records-boundary.test.ts`](../../bundles/desktop/workspace/tests/records-boundary.test.ts)).
- The `description` of [`files`](../../bundles/features/files/manifest.json), "Core capabilities available to the Doric agent.", names no single function.
