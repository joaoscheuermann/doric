- Status: `accepted` (2026-11-17). The user accepted the concept in OD25. Nothing of it is built.
- Brief: this document, the concept of putting every bundle on one model, a microkernel with extension points, and of the first changes that apply it: the layout becomes a shell of slots, the Projects and Threads navigation moves to a new bundle `workspace`, the account menu moves to a new bundle `account`, and chat, settings, runtime, default, files, git, core, postgres, the kernel and the composition give up the knowledge that belongs to another bundle.

It starts once Spec 1 is approved and is designed while Spec 1 is implemented (OD21).
- Decisions: OD1–OD26 below, the user's decisions, all recorded on 2026-11-17. [Decisions](#decisions) states each as the course that was chosen. No question is open ([Open questions](#open-questions)).
- Version 5 (2026-11-17): the concept accepted, with the user's last answers recorded as OD25 ([Evolution](#evolution)).

## Summary

Doric's 31 bundles import one another only through published contracts. That is the only boundary the repository checks. Inside it, several bundles do another bundle's work, and several kinds of contribution are knowledge written into the bundle that receives them: the layout holds the Projects and Threads navigation, the chat draws the terminal's and the files' tool calls by name, the settings window draws the Claude sign-in, the runtime imports the terminal's contracts, the core names Project and Thread ids and the settings route.

The user's target is one model for every bundle: the platform declares the base capabilities and the core provides them; each bundle has one function and announces its own capabilities through extension points; a bundle that is extended never knows who extends it. This concept reduces that model to eleven rules ([The model](#the-model)), says which of them a machine can check and how, says what each bundle is responsible for afterwards ([Shape of the result](#shape-of-the-result)), and sets out fourteen phases, each leaving the product working ([Phases](#phases)).

The scope is the user's choice (OD11, OD17–OD25): one spec. It changes 20 of the 31 bundles (three of them only by manifest lines) and three parts of the platform, adds two bundles, changes public contracts and nine slot names, adds one field to a payload of the host's public REST API, and drops database tables. Its last phase before the close rewrites the architecture documentation, writes a feature doc for every implemented feature and retires `GROUNDING.md`; that phase is designed in the [documentation plan](../designs/bundle-isolation-docs.md). [Size and risk](#size-and-risk) states what the work costs. [Conflicts](#conflicts) lists where the decisions collide with one another, with a rule of this document or with the code: 22 conflicts, of which two are open; neither waits for the user. Seven more, on the documentation, are in the plan.

## Background

What a reader needs to know about Doric to follow the argument.

- **Doric** is a desktop app (Electron) and a host (a Node server) that run coding agents. A **Project** is a workspace with a **sandbox**, a container in which the agent's commands run. A **Thread** is one conversation with an agent inside a Project; Threads can have child Threads. A **prompt** is one input to a Thread; its **input source** says who wrote it (the reader, a parent Thread, a finished background command). The agent answers by calling **tools** (`terminal`, `edit`, `write`, and others). A **skill** is a text of instructions the agent loads on demand with the tool `load_skill`.
- **Bundle.** A folder under `bundles/*/*` with a `manifest.json`: an id, a one-line `description`, the contracts it `provides`, those it `requires`, and those it may use when present (`optional`). There are 31, listed with their functions in [The bundles](#the-bundles); Spec 1 adds two. The user's word "plugin" means a bundle, and "microkernel" means this arrangement: a small platform that loads bundles and connects them, with every feature in a bundle.
- **Parts of a bundle.** A bundle has up to three parts, one per environment (`packages/bundle/src/contracts/basic/index.ts:45`): a **host** part (`src/host`), which runs in the host; a **desktop** part (`src/desktop`, environment `desktopMain`), which runs in a utility process of the Electron main process; and a **client** part (`src/client`), which runs in a window (`packages/bundle/src/build/parts.ts:1-3`). Many bundles have only some of them: `settings` has only a client part, `claude-login` and `default` have no client part, `runtime` has only a host part. Beside its parts a bundle may have a **contracts module** (`src/contracts`), the types and ids other bundles import; it runs nowhere and is not a part.
- **Processes.** In the host, the **kernel** process runs the platform and the host parts of the core, its backends and the bundles the composition names `resident`; one more process, the **generation** process, runs every other host part (`packages/bundle/src/process/partition.ts:3-14`). A generation is one loaded set of bundles; a reload starts a new one. All client parts of a window share that window.
- **Quarantine.** The loader **quarantines** a bundle it cannot run: a requirement no bundle provides, a cycle of requirements, or an activation that throws (`packages/bundle/src/loader/activate.ts:16,375`). The parts of a quarantined bundle do not run, and the other bundles do. A bundle that requires a contract of a quarantined bundle is quarantined with it. The window shows one notice that lists the quarantined bundles, the **quarantined-bundle notice** (`L/src/client/components/molecules/bundle-health-notice.tsx`).
- **Contract.** A versioned service, hook, event or command a bundle publishes, such as `layout.tabs/v1`. Other bundles import its types from `<bundle id>/contracts`. A bundle reaches a contract through its activation services: `use` (the contract must be there) or `whenAvailable` (a callback runs when a provider appears). The loader refuses a `use` of a contract the manifest does not list (`packages/bundle/src/runtime/services.ts:133-152,332`); it does not check `whenAvailable` (`:234`).
- **Platform, base capabilities, core.** The platform is the code that loads bundles and runs processes and windows: `packages/bundle`, `packages/storage`, `packages/desktop`, `app/desktop/*` and the kernel `app/backend/doric-host` (`GROUNDING.md:864-871`). It declares 18 **base contracts** (`packages/bundle/src/contracts/basic/index.ts:48-69`): hooks, log, tools, skills, settings, secrets, storage, events, models, commands, windows, menus, ui, navigation, regions, and three interfaces a **backend bundle** implements (`storage.backend/v1`, `secrets.backend/v1`, `models.provider/v1`). The **core** is the one bundle the composition names to provide the other fifteen (`bundles/foundation/core`, `docs/architecture/bundles/core.md:11`). Every other bundle that is not a backend is a **feature bundle**: the runtime, the chat and the layout are feature bundles.
- **Scope keys and the bridge.** A call may carry a **scope**: a small record that says which Project or Thread the call is about, for example `{ projectId, threadId }`. The **bridge** is the channel between a window and the main process, through which a client part calls contracts that live in the desktop or host parts. A provider's manifest lists, per contract, the scope keys a window may send (`desktopScope`); the bridge refuses any other key with `invalid_input` (`app/desktop/doric/src/platform/bridge/dispatcher.ts:652-662`).
- **Slots.** A slot is a named place in a bundle's UI that other bundles fill. Today a slot is a **region**: a string name that an element draws with `<core-region name="…">`, filled through the base contract `regions/v1` with items `{ id, tag, props?, order? }`, where `tag` is a custom element. An element tag must start with the id of the bundle that defines it (`bundles/foundation/core/src/client/ui.ts:38-46`); a region name has no such rule (`bundles/foundation/core/src/client/regions.ts:83` only records who added an item).
- **Composition.** `app/backend/doric-host/composition.json` is the deployment's choice: `core` (which bundle is the core), `enabled` (the bundles that run), `providers` (which bundle implements each backend interface), `resident` (bundles whose host part runs in the kernel process), `required` (contracts and bundles without which the host refuses to serve) and `alternatives` (a named choice between bundles made by an environment variable: `DORIC_SANDBOX_PROVIDER` picks `docker`, the default, or `firecracker`).
- **Configuration.** The stored configuration (the providers, their models, the default model a new Thread runs on) belongs to the bundle `host-config` (`bundles/foundation/host-config/manifest.json:6-7`). The settings window reads and writes it through `host-config/v1` (`bundles/desktop/settings/src/client/api/settings-api.ts:72-75`). A Thread's **execution** is the provider, model and reasoning effort it runs on.
- **Where Projects and Threads are stored.** The runtime stores them as documents and streams through the base contract `storage/v1`, in the generic tables of the `postgres` bundle (`bundles/foundation/postgres/prisma/schema.prisma:143-187`). Before that they were rows of three tables, `project`, `thread` and `thread_event`. The migration `20261010000000_runtime_documents` ("stage 7" in the repository's documents) copied them in one transaction, verified the copy, wrote a marker document of type `runtime.migration/v1` and deleted the rows (`GROUNDING.md:1743-1749`). The three tables remain, empty, and are called the **legacy tables** here. The operator runs migrations with `prisma migrate deploy`; in the shipped `compose.yaml` a one-shot `migrate` service does it before the host starts (`app/backend/doric-host/compose.yaml:21-32`).
- **The runtime's words.** The runtime runs one prompt of a Thread at a time; further prompts wait in the Thread's **queue**. **Recovery** is what the runtime does, when the host starts, with the prompts that were running when it stopped. A **lease** is the runtime's hold on a Project's sandbox while its prompts use it; `runtime.lease/v1` is the contract through which tools run commands in the leased sandbox (`bundles/runtime/runtime/src/contracts/lease.ts:29-34`).
- **`transport`** is the bundle that serves the host's REST routes and Socket.IO namespaces. The desktop calls them, and so do programs outside the desktop (OD25), which makes them a public API. The API carries no version: its paths have no version segment (`bundles/foundation/transport/src/host/app.ts:23-36`), and `transport` provides no contract (`bundles/foundation/transport/manifest.json:7`).
- **The workspace window.** The window has two strips of tabs. The **Project tabs**, in the title bar, switch between open Projects. The **viewer tabs**, in the conversation column, hold the conversation and whatever other bundles open beside it (a file, a diff, a terminal) through `layout.tabs/v1`. The **history buttons** are the back and forward buttons of the title bar (`L/src/client/components/molecules/history-buttons.tsx`). The **workspace error notice** is what the sidebar shows, with a retry, when a read of Projects or Threads fails (`L/src/client/components/molecules/workspace-error-notice.tsx`). **About** is the app's name and version, which the account menu shows; it is read from `doric.about/v1`, a contract the platform itself provides. Contract ids that start with `doric.` are reserved to the platform (`packages/bundle/src/contracts/define.ts:56-62`) and are not among the 18 base contracts.
- **How the chat draws.** For each Thread the chat keeps a **projection**: what the transcript shows, computed from the Thread's events by a pure function, the **projector**. The transcript is drawn by the **conversation editor**, a read-only editor whose document is a tree of **nodes**: a message, a tool call, the terminal's result block. Through `chat.views/v1` a bundle can already register a projector for its own event types, a **block renderer** (an element that draws one type of block of the projection) and a **fence renderer** (an element that draws a fenced code block of one language inside a message) (`bundles/desktop/chat/src/contracts/index.ts:136-150`).
- **Staging.** The host is built by copying each bundle's built output into the host's `dist/bundles`. The copy is called staging, the `stage` command of the build tool does it, and the build files list the bundles to stage.

| Shell                | The layout bundle after this change: the window's frame and its slots.                                                                                                                                                                                                     |

| Records mirror       | The window's live copy of the runtime's Project and Thread records, kept current by a watch on the host. Today inside the layout; afterwards in the runtime's client part.                                                                                                 |
| Execution picker     | The control in the conversation footer that shows and sets the selected Thread's execution. Today in `settings`; afterwards in `chat`.                                                                                                                                     |
| Knows, `A → B`       | A knows B when A's code, manifest, package dependencies or styles name B's id, a contract of B, or an element tag, tool name, kind id, route, event type or CSS selector that B owns. `A → B` is written for "A knows B".                                                  |
| Right-way, wrong-way | `A → B` is right-way when A is built on B: A needs B's function to do its own (the chat needs Threads: `chat → runtime`). It is wrong-way when A works without B and names B only to give B's contribution a place (the chat names the `terminal` tool to draw its calls). |

## Problem

The repository checks one boundary rule: no import of another package's `src/` (`tests/lint.test.mjs:224-245`). The bundles pass it, and every static cross-bundle import in `bundles/*/*/src` goes through `<id>/contracts`. Nothing checks what a bundle is responsible for or which way knowledge runs, and CI runs no bundle's tests (`.github/workflows/ci.yml:48-70` runs the lint test, the format check, the `doric-host` and `agent` tests, and build and typecheck). The result, in the places this concept covers:

- **The layout is two bundles in one.** Its manifest says "The workspace frame: Projects and Threads, header, side panel, tabs and footers." (`L/manifest.json:8`) and requires `runtime/v1` and `runtime.threads/v1` (`L/manifest.json:23-24`). Its sources are 90 files and 9,733 lines, of which about 6,700 are Projects and Threads code and about 2,900 are frame code (search). It keeps the records mirror and hands the runtime's `Project` and `Thread` records out through `layout.workspace/v1` (`L/src/contracts/index.ts:13,169-197`) to ten other bundles: chat, settings, files, git, mcp, resources, screen, terminal, threads and usage. A change to the sidebar and a change to the frame land in the same bundle and the same tests.
- **The layout knows the bundles that fill it.** It opens the chat's element by tag (`L/src/client/domain/workspace-tabs.ts:45`, `L/src/client/hooks/thread-navigation.ts:25`), sets the chat's CSS variable `--chat-footer-height` (`L/src/client/components/templates/conversation-frame.tsx:16`), styles the terminal's and the Monaco editor's elements (`L/src/client/styles.css:28,37`), depends on the packages `monaco-editor`, `@xterm/*` and `resources` (`L/package.json:21-30`), names the core's command `core.open-settings/v1` (`L/src/client/views/workspace-view.tsx:74`), holds tab kinds `diff`, `file` and `terminal` (`L/src/client/domain/workspace-tabs.ts:5-23`), defaults the side panel to `files` (`L/src/client/stores/panel.ts:15`), and closes two sets other bundles extend: `TabIcon` (`L/src/contracts/index.ts:57`) and the panel icons (`L/src/client/components/organisms/project-panel.tsx:27-40`).
- **The layout holds the account menu.** `L/src/client/components/organisms/account-status.tsx` (82 lines) draws the reader's avatar, a menu with one "Settings" entry and the app's version, and the slot `layout.account.status`. The dashboard's sidebar has a second way into the settings window, the button "All settings" (`L/src/client/components/organisms/dashboard-sidebar.tsx:150`).
- **The chat names seven tools of other bundles, in four places.** (1) The drawing: `C/components/molecules/tool-item.tsx:44,57,71` picks a dedicated component for `terminal`, `edit`, `write` and `load_skill`, and `C/components/organisms/conversation/plugins/insert-thread-turn-nodes.tsx:221` a dedicated block for `thread-spawn`. (2) Open by default: `C/domain/collapsible.ts:69` lists `edit`, `write` and `view-image`. (3) Outside the activity group (the collapsed run of an agent's steps): `C/domain/projector.ts:450-456` lists `edit`, `write`, `thread-spawn` and `load_skill`. (4) Writes the sandbox, which tells the files views to refresh: `C/domain/projector.ts:1241` lists `write`, `edit`, `terminal` and `git`. The tools are registered by `terminal` (`terminal`), `files` (`edit`, `write`, `view-image`), `threads` (`thread-spawn`), `git` (`git`) and `default` (`load_skill`). The terminal has two more things in the chat: the live output of a running command (`C/stores/live-terminals.ts`, through `terminal/v1` and `runtime.terminals/v1`) and the block of a finished background command, which is a prompt whose input source is `terminal` (`C/domain/terminal-result.ts:6-7`). Thirteen chat files named after these tools hold 2,362 lines.
- **The settings bundle draws one provider's sign-in, holds one provider's link and owns a control of the conversation.** `bundles/desktop/settings/src/client/components/organisms/settings-provider.tsx:201` tests `kind?.id === 'claude'`; the sign-in hook and its page logic live in settings (`bundles/desktop/settings/src/client/hooks/use-provider-page.ts:91-110`), while the `claude-login` bundle has no client part. A fixed map gives the kind `openrouter` its site link (`bundles/desktop/settings/src/client/domain/provider-icon.ts:1-11`). Its manifest states two functions, "The settings window and the footer execution picker." (`bundles/desktop/settings/manifest.json:8`); the picker is an item it adds to the conversation footer (`bundles/desktop/settings/src/client/index.ts:72-76`).
- **The runtime knows bundles built on it.** It imports `terminal/contracts` in three files (`bundles/runtime/runtime/src/host/index.ts:10`, `bundles/runtime/runtime/src/host/services/terminal-sessions.ts:2`, `bundles/runtime/runtime/src/contracts/tool-host/terminals.ts:5`) and uses `terminal/v1` and `resources/v1` through `whenAvailable` without listing them in its manifest (`bundles/runtime/runtime/src/host/index.ts:170-186`). The terminal sessions already belong to the `terminal` bundle; the runtime still provides `runtime.terminals/v1`, a contract that only forwards to it "for the desktop windows that still read this contract" (`bundles/runtime/runtime/src/host/services/terminal-sessions.ts:10-17`). Its contract `runtime.lease/v1` still carries nine reads of files, Git state and container resources (`bundles/runtime/runtime/src/contracts/lease.ts:110-132`), implemented in `bundles/runtime/runtime/src/host/provisional/` (4 files, 852 lines); the `git` bundle already has its own copies of the Git ones (`bundles/features/git/src/host/status.ts:1-3`), and the `files` bundle still calls six of them through the lease (`bundles/features/files/src/host/reads.ts:144-187`). Because the runtime imports the terminal, the terminal cannot import the runtime's or the layout's contracts without a dependency cycle, and keeps structural copies (`docs/architecture/bundles/implementation-decisions.md:948`).
- **The default agent enumerates its skill sources.** A skill comes from a bundle, from the Thread's working directory or from an MCP server, and `default` holds all three cases as a closed type (`bundles/runtime/default/src/host/skills/sources.ts:25-36`). For the third it imports `mcp/contracts` (`bundles/runtime/default/src/host/skills/sources.ts:9`, `bundles/runtime/default/src/host/skills/load-skill.ts:5`), lists the servers' skills (`sources.ts:131-151`), reads one (`load-skill.ts:32-40`) and names it `mcp/<server>/<name>` (`bundles/runtime/default/src/host/skills/catalog.ts:125-138`). The chat reads that name back to label the call "MCP · server" (`C/domain/skill-load.ts:24,62-66`).
- **`files` and `git` know each other.** The files tree reads `git.changes/v1` to mark changed files (`bundles/features/files/src/client/api/peers.ts:44-53`, `bundles/features/files/src/client/tree/files-tree.tsx:91`). The `git` bundle reads `files.sandbox/v1`, calls `files.refresh/v1` and runs `files.open-file/v1` (`bundles/features/git/src/client/api/peers.ts:10-46`, `bundles/features/git/src/client/index.ts:103`). Neither manifest lists the other's contracts; both sides use structural copies.
- **The core names other bundles' concepts in five places.** (1) Its manifest lists `projectId`, `threadId` and `promptId` as the scope keys of six contracts it provides: the base contracts `windows/v1`, `menus/v1`, `secrets/v1`, `models/v1` and `tools/v1`, and its own `core.commands/v1` (`bundles/foundation/core/manifest.json:34-39`). (2) Its command `core.open-settings/v1` opens the window key `'settings'` with the settings window's sizes and falls back to the route `/settings`, which the settings bundle registers (`bundles/foundation/core/src/desktop/commands.ts:26-39`). (3) Its desktop part opens the first window under the key `'workspace'` at `/` with the workspace's sizes (`bundles/foundation/core/src/desktop/index.ts:62-75`, `bundles/foundation/core/src/desktop/appearance.ts:3-7`). (4) It names the layout's localStorage key `doric.selection` for a one-time origin migration (`bundles/foundation/core/src/desktop/migrations.ts:4-13`). (5) The base contract `tools/v1` has a `projectId` field ([X1](#conflicts)).
- **The kernel imports a bundle.** `app/backend/doric-host/src/index.ts:9,90` imports `ATTACHMENT_MAX_BYTES` from `runtime/contracts` to size its Socket.IO buffer, against the platform boundary of `GROUNDING.md:864-871`.
- **Postgres hands out its client and keeps the legacy tables.** `postgres.database/v1` has `client(): Database`, the Prisma client (`bundles/foundation/postgres/src/contracts/index.ts:20-21`). No non-test code outside `postgres` uses the contract or the `postgres/prisma` export; eleven test files under `app/backend/doric-host/tests` and one in the runtime do. ## The model

Eleven rules. A bundle follows each one or breaks it.

| Rule                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **M1 One function.** A bundle's manifest `description` states one function, and every contract, slot, route and tool it provides serves it.                                                                                                                                                                                                     |
| **M2 Contracts only.** A bundle reaches another bundle only through a contract that bundle publishes, imported from `<id>/contracts`, in sources and in tests.                                                                                                                                                                                  |
| **M3 One direction.** Every `A → B` is right-way. Where B contributes into A, A does not know B. The `→` edges between bundles form no cycle.                                                                                                                                                                                                   |
| **M4 Declared extension points.** Every way to add something to a bundle is a contract it provides or a slot it declares. A set other bundles extend (tools with a drawing, icons, tab kinds, provider kinds, input sources, skill sources) is open: its members are registered, not enumerated.                                                |
| **M5 Owners announce.** A bundle registers its own tools, commands, routes, slot items and drawings from its own code. No bundle registers, opens or draws on behalf of another. Broken today where the layout opens the chat's Thread tab and the core registers the command that opens the settings window.                                   |
| **M6 Base capabilities stay generic.** The platform declares the base contracts and the core provides them. Neither names a feature bundle's concept: no Project, Thread or prompt, no feature bundle's route.                                                                                                                                  |
| **M7 Data has one owner.** A record is read through a contract of the bundle that owns it. A bundle does not hand out another bundle's record types through its own contract. It may publish a view of another bundle's data: a type it declares itself, holding what its own function produces from that data (OD23).                          |
| **M8 Persistence by operations.** A backend bundle exposes operations. No contract hands out a live client or connection.                                                                                                                                                                                                                       |
| **M9 One source for the bundle set.** The bundles of a build are the manifests on disk. Every other list of bundles is derived from them, checked against them, or is a named deployment choice.                                                                                                                                                |
| **M10 Plain data in new contracts.** A contract method Spec 1 adds takes and returns plain data. A contribution names an element tag and gives props, and the element answers with DOM events; it passes no function, component or live object, except a subscription listener. The rule is not a reason to reshape a contract that only moves. |
| **M11 Enforced or listed.** Each rule a machine can check is a test CI runs. Each standing violation a check finds is one entry in an exceptions file, with the decision that keeps it.                                                                                                                                                         |

- **M1, M5, M8, M10: review.** No scan decides them.
- **M4: review, plus one acceptance test per extension point** ([G3](#goals-and-success-measures)). A scan for tool names or kind ids as literals was considered and rejected: `terminal`, `edit`, `write` and `git` are ordinary strings, and the chat legitimately reads the stored input source `terminal`.
- **The manifest lines the M3 test asks for.** Phase 0 adds one manifest line for each of the twenty uses, and every one goes under `optional`, never `requires`. Each use is reached through `whenAvailable` or an observation, so the bundle already runs without the provider. And the resolver reads only `requires`: it orders activation by it and quarantines every member of a `requires` cycle (`packages/bundle/src/runtime/catalog.ts:590-655,751-781`), while the word `optional` does not occur in that file. A line under `requires` could close such a cycle and quarantine the seven bundles named above; a line under `optional` cannot.
- **Why the M3 check is a test and not a check in the loader.** Version 3 had the loader refuse a `whenAvailable` of a contract the manifest does not list, as it refuses a `use`. That check runs in the product, so a use the scans missed would stop a bundle in the field. It also sees less than the test: `services.whenAvailable` only (`packages/bundle/src/runtime/services.ts:233-241`), and not a hook, a command or an event reached by its id, which are eleven of the twenty uses. The test covers M11 without the failure in the field (review finding S6).
- **M7: review.** An import scan of contracts modules lists candidates (17 imports of another bundle's contracts, in 10 contracts files of 8 bundles, today), but naming an owner's type in a method signature is often legitimate, and the scan cannot see structural copies. Two modules get an exact assertion instead ([G11](#goals-and-success-measures)).
- **M7 after OD23: what a view is, and what stays forbidden.** OD23 reads M7 so that `settings` may publish the configured models in `settings.models/v1`, although the configuration is the record of `host-config`. The view is allowed because `settings` declares its type and adds its own work to it: the labels, the groups and the icons. Four things stay forbidden. (1) A contract whose types are another bundle's record types, imported from its contracts module or retyped as a structural copy. `layout.workspace/v1` hands out the runtime's `Project` and `Thread` (`L/src/contracts/index.ts:13,169-197`) and stays a violation, which OD20 removes. (2) A view that passes the record through under a new name: a field the publisher's own function does not use does not belong in it. `settings.models/v1` carries no provider configuration value and no credential. (3) A write through the view. A view is read; a change to the record goes through its owner's contract, as the picker writes a Thread's execution through `runtime.threads/v1` and the settings window writes the configuration through `host-config/v1`. (4) Reading the view in place of the record. A bundle that needs the record itself, and not the publisher's presentation of it, reads the owner.
- **M3's direction.** A scan for element tags that start with another bundle's id was considered and rejected. It flags right-way uses (`threads` creates the chat's `<chat-readonly-markdown>`, `bundles/features/threads/src/client/delegated-turn.tsx:42`), it flags strings that are not tags (the toast id `layout-panel-read` in `files` and `git`), and M10 makes naming a tag the sanctioned form. Whether a lone edge is wrong-way is decided in review, with the definition in [Terms](#terms-this-document-adds).

**The exceptions file.** One JSON file beside the checks, `tests/boundary-exceptions.json`: a list of `{ check, bundle, target, decision }`, where `decision` is the path of the document that keeps the violation. The checks fail on a violation that is not listed, on an entry that no longer matches a violation, and on an entry whose `decision` file does not exist. The file therefore always equals the current violations; adding one is a visible line in a reviewed change, with a reference. A comparison with the base branch, which would make "only shrinks" mechanical, is not proposed: it needs the CI checkout to carry history. The states the phases create on purpose add no entry: a second bundle providing `layout.*` contract ids breaks no check, and no check covers the chat's built-in drawings (M4 is review), so they need no entry while their owners have not replaced them. Nothing checks that the file an entry names records a decision of the user; that is review, in the change that adds the entry.

### Records mirror (the runtime's client part)

Six of the consumers of `layout.workspace/v1` read record fields, synchronously, while they draw: the chat and the terminal read a Thread by id (`C/hooks/use-workspace.ts:107,114`, `bundles/features/terminal/src/client/elements.tsx:44-46`), `files` reads a Project's state and its Threads' working directories (`bundles/features/files/src/client/refresh/coordinator.ts:27-40`), and `git`, `screen` and `threads` read records too. Three need ids only (`mcp`, `usage`, and `resources`, which also reads the connection state). The tenth, `settings`, reads the selected Thread only for the execution picker (`bundles/desktop/settings/src/client/hooks/use-selected-thread.ts`); once the picker is the chat's, `settings` needs neither.

One live copy of the records per window is needed, and the runtime owns it (OD20). The runtime gains a client part that keeps the mirror: the Projects, a Project's Threads when a bundle asks for them, one Thread by id, the connection state, and change notifications. It is built from what the layout has today: its watch on the host, its host adapters and the record half of its workspace state.

Cost for the consumers: each call that reads a record through the selection splits in two, the id from `workspace` and the record from the runtime; about 30 call sites. `threads` stops depending on the navigation at all. The shape changes, so the contract gets new ids, and `layout.workspace/v1` survives only as the transition of phase 4.

**One copy is one point of failure.** Seven bundles read records from this part: `workspace`, `chat`, `terminal`, `files`, `git`, `screen` and `threads`. Today the same seven depend on the layout for them, and a layout that fails leaves no window at all. Afterwards the frame survives, and the records can still be missing. Three cases, each with a stated behavior:

- _The runtime's client part is quarantined or absent._ A bundle that cannot draw without records lists the mirror contract under `requires` and is quarantined with it, by the cascade the resolver already applies ([Background](#background)); a bundle that only adds to another's view lists it under `optional` and draws nothing. The shell draws its empty states, and the quarantined-bundle notice names the runtime and every bundle that fell with it ([R3](#risks)).
- _The part runs and the host cannot be reached._ The mirror keeps the last records it read and publishes the connection state, as the layout does today, and `workspace` draws the workspace error notice with its retry.
- _One read fails._ The mirror publishes the failure of that read, and the bundle that asked draws it.

The mirror contract therefore carries, beside the records, the connection state and a state per read (loading, ready, failed). The spec's test plan has one test per case.

### Default and MCP

- **`default` declares `default.skill-sources/v1`** (OD19): the contract a bundle provides to offer skills to the agent. It has two methods, and both take and return plain data: list the skills available to a call (name, description, and a reference only the source reads), and read one skill's text by that reference. `default` keeps its own two sources, the bundle skills of `skills/v1` and the files of the working directory, and builds the catalog over its own and every provider's.
- **`mcp` provides it** and takes what is its own: the listing of the connected servers' skills (`sources.ts:131-151`), the read of one (`load-skill.ts:32-40`), the sentence that introduces a skill "From the MCP server …", and the server slug. `default` drops `mcp/v1` from its manifest (`bundles/runtime/default/manifest.json:20`) and lists its own contract as optional; `mcp` lists it under `provides`. Where OD19 says `mcp` "registers its source", it registers by providing the contract.
- **Names.** `default` forms a skill's name from the source's id and the name the source gives, so `mcp/<server>/<name>` stays what the agent types, with no line of `default` naming a server.
- **The shape: a contract that others provide.** `default` declares the contract in `default/contracts` and does not provide it. Each source bundle does, the way the four provider bundles provide `models.provider/v1` and `docker` and `firecracker` provide the `sandbox/v1` that `runtime` declares. `default` learns of every provider through `whenAvailable`, which is how a contract with many providers is read (`packages/bundle/src/runtime/services.ts:252-256,326`), and calls them itself. That adds no method that takes a function (M10) and changes nothing in the core. Version 3 declared the point as hooks. Hooks do not fit: the handlers of a hook run one after another, in catalog order, each with a deadline of ten seconds that is set for the whole hooks service (`bundles/foundation/core/src/shared/hooks.ts:24,126-129`), while `default` reads its sources in parallel today (`bundles/runtime/default/src/host/skills/sources.ts:170-174`); and a read addressed to one source fits no hook kind (review finding C4, [X14](#conflicts)).
- **Deadline and failure.** `default` calls its providers in parallel and waits for each at most five seconds, the limit its scan of the working directory has today (`sources.ts:21-22`). A source that is late or fails yields no skills for that prompt, and one diagnostic that names the bundle. Today the MCP listing has no deadline (`sources.ts:160-163`): a slow MCP server delays the prompt. After the change it costs that prompt its MCP skills instead. That is a change the reader can meet, and G9 lists it.
- **`default` gains a client part** (OD20) that registers the `load_skill` drawing at the chat's tool point: the component that draws the call and the reading of the skill's name, which the chat holds today. The label of an MCP skill is [X15](#conflicts).

## Security and performance

**Security.** Every bundle of a composition is code the operator chose, and any client part can already add an item to any slot and call any contract exposed to windows. The new extension points add no trust boundary, but they add places where one bundle's output is shown as another's, or reaches the agent:

- _The provider-page slot_ lets any bundle draw inside the page of the kind `claude`, including a sign-in. The slot's items are drawn with the owner's bundle id available to the settings page (`regions/v1` records it); the spec says whether the page shows it.
- _The chat's two points_ let any bundle draw another bundle's tool calls or prompts. The chat cannot verify ownership today: the tool catalog a window can read carries no bundle id (`packages/bundle/src/contracts/basic/tools.ts:67-71`). The conflict rule stops two bundles from registering the same key; it does not stop the wrong one from being first.
- _Skill sources_ put text into the agent's context. Any bundle that provides the contract can offer the agent instructions under any name. The base contract `skills/v1` already lets any bundle do that. The new contract adds reads that run when a prompt starts; `default` bounds each at five seconds and goes on without a source that is late or fails ([Default and MCP](#default-and-mcp)).
- _The provider link_ is a URL a bundle supplies and the settings window opens in the reader's browser. Settings accepts only `https:` URLs and shows the label beside the host name.
- _The models contract_ is readable by every client part of the window. It carries labels, model names and icons, and no endpoint, credential or other provider value.
- _File marks_ can be given by any bundle that provides the contract, for any path. They are drawn, never acted on.
- _Secrets in output that leaves the runtime._ The runtime redacts with its own list, and secrets it registers only there (the Git token it applies to a sandbox) do not reach other bundles' redaction (`docs/architecture/bundles/implementation-decisions.md:949`). The six file reads move to `files`: before they do, the spec confirms that every such secret is also registered through `secrets/v1`. The author did not check whether that was already done.
- _Scope keys._ Removing the three keys from the core narrows what a window may send; it grants nothing.

**Performance.**

- _Tool drawings and prompt blocks._ Each call of a tool with a registered drawing becomes one custom element of another bundle, with its own rendering root, where today it is a component inside the chat's tree. A transcript can hold hundreds of them. No number exists today, so the measure and the budget are stated here and the baseline is taken in phase 5, before any built-in is removed. The measure: the time from selecting a Thread to the last row of its transcript being drawn, for one fixed transcript of 500 tool calls that is committed with the phase, as the median of ten runs in the desktop end-to-end harness. It is taken twice, with the built-in drawings and with the registered elements. The budget, which is the author's figure and was accepted with the concept: the registered version is at most 10% slower than the built-in one. A drawing that misses the budget stays built in, and the phase's report gives both numbers.
- _Records._ With the mirror in the runtime's client part, consumers read as they do today: synchronously, from one copy per window, fed by one watch.
- _The picker._ One read of the configuration per window, as today; the read moves behind a contract and does not multiply.
- _File marks._ `git` reads only for the Project and directory `files` asks about, as today.
- _The boundary tests_ run in CI and cost the product nothing. _CI time_ is not known: the bundles hold 424 test files that have never run in CI (A5). Phase 1 records the run time of the job before and after it adds the bundle targets; if the job takes more than twice as long, the targets are split over parallel jobs in that phase ([R6](#risks)).

## Alternatives considered

- **Keep the navigation in the layout and narrow its contracts.** Cost: none of the move. It leaves the layout requiring the runtime, holding the records mirror and changing with every sidebar change, which is the cost [Problem](#problem) starts from; and OD3 excludes it.
- **Put the frame in the core.** The core would draw the window and every feature bundle would fill it. One bundle fewer, and no question of who opens the first window. It makes the frame impossible to replace without replacing the core, and puts UI that changes with the product in the bundle every other bundle depends on. OD3 excludes it.
- **Keep `layout.workspace/v1` alive from the layout**, forwarding to the new bundle. No consumer changes. The layout would have to know the new bundle, which breaks M3 in the bundle this work exists to clean.
- **The navigation bundle hands out the records**, as the layout does now. The move would be a move, and three consumers would change only a manifest line. Seven bundles would then depend on the navigation to read a Thread. Rejected by OD20.
- **Selection as ids, each consumer reading the host for records.** No mirror to own. Six consumers would each keep a watch and a cache, and their reads are synchronous during drawing. Rejected by OD20.
- **Account status in `settings`, or kept in the shell.** The first adds a function to a bundle that already stated two; the second leaves the version read and the menu in the shell. Rejected by OD20.
- **A slot declaration in `regions/v1`**, with a warning for an item in an undeclared slot. It changes a base declaration, its only effect is a warning, and a filler that activates before the slot's owner would be warned about wrongly. Rejected by OD18.
- **Draw both slot names during the rename.** Rejected: `order` holds within one region, not across two ([Slot names](#slot-names)).
- **The tool facts on the tool's registration in `tools/v1`** instead of on the chat's point. They would be known even when the owner's client part is absent. It adds fields to a base declaration, puts facts of presentation ("outside the activity group", "open by default") in a host contract, and makes the chat's projection wait for a catalog read. Not proposed; OD11 names a renderer keyed by tool name.
- **"Writes the sandbox" as a third fact of the chat's tool point**, with the chat still counting the writes and telling `files`. One boolean on a registration that exists anyway, and no new observer. It leaves the chat coordinating the refresh of another bundle's views beside `files.refresh/v1`, the contract that exists for it. Version 3 proposed it; rejected in version 4 ([Chat](#chat)).
- **Skill sources as hooks of `default`.** No new kind of contract. Hook handlers run in sequence under one deadline, and a read addressed to one source fits no hook kind. Version 3 proposed it; rejected in version 4 ([Default and MCP](#default-and-mcp)).
- **`git` pushes its marks into `files.decorations/v1`.** A plain registration. `files` would have to publish which Project and directory its tree shows. Version 3 proposed it; rejected in version 4 ([Files and Git](#files-and-git)).
- **The effort rule of the picker in `runtime/contracts`.** One copy of a ten-line wrapper. The wrapper is shaped around the configuration of settings. Version 3 proposed it; rejected in version 4 ([Settings](#settings)).
- **The M3 check in the loader.** It would also catch a bundle that is not in the repository. It runs in the product and sees only service references. Version 3 proposed it; rejected in version 4 ([What a machine can check](#what-a-machine-can-check)).
- **Passing `/settings` as the existing `path` of `core.open-settings/v1`.** No change to the contract. A settings window that is open would jump to its first page each time the reader uses an entry. Rejected by OD25, with two other courses: entries that pass `path` only when no window is open, which need a read that `windows/v1` does not have (`packages/bundle/src/contracts/basic/windows.ts:117`) and whose answer can be stale; and the route left as a literal in the core, which reverses that part of OD17.
- **No provider-page slot: `claude-login` adds its own settings section**, through the section slot and child route settings already has (`git` uses them). No new slot. The sign-in would move from the Claude provider's page to a page of its own, a change the reader sees (G9).
- **The execution picker stays in `settings`**, recorded as an exception. This was the author's recommendation: no code moves and no contract is added. It leaves `settings` with two functions and a control of the conversation outside the chat. Rejected by OD19.
- **The chat reads the configuration from `host-config/v1`** for the picker, and `settings` publishes nothing. It keeps M7 as written and adds no contract. The chat then holds the rules that label and group models, which the settings window also needs, so they exist twice or move to a third place. Rejected by OD23.
- **`mcp` registers its skills in `skills/v1`**, the base contract, instead of a new point of `default`. No new contract. `skills/v1` holds a skill's text at registration; an MCP skill is listed per call, by connected server, and read on demand, so the base contract would have to change. Not proposed.

- **Keep the legacy tables:** empty as they are, renamed, or dropped by Spec 2. Nothing irreversible happens in Spec 1. Rejected by OD14, which has Spec 1 drop them. ## Riskiest assumptions

- **A1.** No bundle outside this repository consumes `layout.*`, `runtime.terminals/v1` or `postgres.database/v1`, fills a renamed slot, or observes `onSandboxActivityHook` for finished tool calls. Not verified, and the repository cannot verify it: the host loads whatever is under `DORIC_BUNDLES_PATH` (`app/backend/doric-host/src/lib/bundles/boot.ts:76-85`). What such a bundle meets, by kind of change:
  - _A removed contract it lists under `requires`:_ the resolver quarantines it, and the quarantined-bundle notice names it.
  - _A removed contract it reaches through `whenAvailable`, a renamed slot, or the narrowed hook:_ nothing happens and nothing is reported (SR13, [R4](#risks)).
  - _The `site` field:_ a bundle built against the older, strict schema of the kind descriptor rejects a descriptor that has it ([X16](#conflicts)).
  - _A call of `core.open-settings/v1` with no `path` while no settings window is open:_ it fails with `invalid_input` where it opened the window at `/settings` ([Core](#core)).
  - _What the spec carries for them:_ the removals and renames are listed in the release notes of the phase that makes them. Each bundle whose contract changes gets the version the repository's rules ask for (`docs/architecture/bundles/versioning.md`). The platform version rises by a minor in phase 6(b), which adds `site` to a base contract, as `packages/bundle/src/runtime/version.ts:1-11` prescribes for a phase that adds to the platform; a bundle that fills `site` requires that version through `engines.doric`.
  - _No deprecation window is proposed._ A window in which the old and the new contract ids both work needs the layout to forward to `workspace`, which M3 excludes, and two names for one slot break `order` ([Alternatives considered](#alternatives-considered), [Slot names](#slot-names)).
  - _A desktop and a host of different versions._ The desktop resolves its bundles against the platform version built into it (`app/desktop/doric/src/platform/catalog/resolve.ts:89`), and the host against its own. Spec 1 does not change that. It adds one case: a desktop older than phase 6(b), connected to a newer host, reads kind descriptors with a field its schema rejects. ## Risks

- **R1 — Phase 4 regresses the sidebar, the selection or the dashboard.** About 6,700 lines leave the layout, and the workspace state is split in phase 3, not only moved. Mitigation: phase 3 changes no consumer and is checked by the layout's existing tests; step 4(c) is then a move; the other steps are separate changes.
- **R2 — The exceptions file becomes permanent.** Mitigation: an entry needs a decision file that exists; a stale entry fails the check; phase 13 does not close while an entry lacks a decision of the user. Whether the file an entry names records such a decision is checked by review, not by the test.
- **R3 — An empty frame.** The shell's body is filled by another bundle. If the client part of `workspace` is quarantined or absent, the window shows a frame with nothing in it. The composition's `required` list cannot guard this: it is a host check over which bundles are active (`app/backend/doric-host/src/lib/bundles/boot.ts:119-143`), it does not see a client part failing in a window, and listing a UI contract there would make a UI failure stop the whole host. The same frame shows when the runtime's client part fails, since `workspace` requires its records ([Records mirror](#records-mirror-the-runtimes-client-part)). Mitigation: the shell draws a stated empty state in its sidebar and page slots, and keeps the quarantined-bundle notice (OD18), which names the bundle that failed first and those that fell with it.
- **R4 — A consumer left on a removed contract id or slot name fails silently.** `chat`, `settings` and `threads` read `layout.workspace/v1` through `whenAvailable` (`C/api/workspace-contract.ts:1-19`, `bundles/desktop/settings/manifest.json:10`, `bundles/features/threads/src/client/source.ts:24-30`); after the id is gone they receive nothing and degrade without an error. An item added to an old slot name is drawn nowhere. Mitigation: step 4(e) is accepted only when a search finds no removed id or slot name under `bundles/`. Outside the repository, A1.
- **R5 — The drop migration meets rows.** After stage 7 the legacy tables are empty; migrations run in order, so a database restored from an older backup runs stage 7 before the drop. Rows can exist at the drop only if an old host binary wrote them after the migration. The drop then raises, the tables stay, the `migrate` step fails and the host does not start. The operator's path, to be written in the host's README: read the error, which names the table and the row count; either restore the backup taken before the deploy, or export and delete the stray rows; then mark the failed migration as rolled back (`prisma migrate resolve --rolled-back`) and run the deploy again. Operators back up first, as for stage 7.
- **R6 — CI time and flakiness** when the 31 bundle test targets, with 424 test files, are added. Their run time on the CI runner is not known (A5). Mitigation: phase 1 is separate from the checks, so a slow or flaky target delays only that phase; it records the time of the job before and after, and splits the targets over parallel jobs if the job takes more than twice as long.
- **R7 — Parallel work.** Changes on `main` to the layout's sidebar, to the chat's tool rows or to the picker conflict with phases 4, 5 and 6. Mitigation: phases merge one at a time (OD17); steps 4(c) and 6(c) are announced and kept short.
- **R8 — One spec over fourteen phases** is long to write and to review, and a late finding in one area holds back the others. Mitigation: the spec is organised by phase, each with its own files, tests and acceptance.
- **R9 — The M3 test misses a use.** It does not see a contract id built at run time or one reached through a re-export. Such a use stays undeclared, as it is today, and nothing fails in the product. Mitigation: review, and the import half of the test.
- **R10 — Spec 2.** Every contract Spec 1 adds is plain data (M10, G10). Spec 1 adds no host contract that returns a live object.
- **R11 — The picker regresses in the move.** It has rules for a Thread whose stored model is no longer offered, for a write in flight and for a refused write. Mitigation: its 1,247-line test moves with it and changes only in what supplies the models.
- **R12 — A slow or failing skill source.** Mitigation: `default` calls its sources in parallel, waits five seconds for each and goes on without one that is late or fails ([Default and MCP](#default-and-mcp)). The cost is on the other side: a slow MCP server now costs a prompt its MCP skills.
- **R13 — The chat depends on `settings` for the picker.** Without `settings` in a composition, a Thread's model can no longer be changed from the conversation. The contract is optional, so the chat still works.
- **R15 — Spec 2 is designed while Spec 1 moves.** Its design reads contracts that phases 2–11 are still changing, and it revises documents phase 12 has just written. Mitigation: Spec 2 takes the approved Spec 1, not the code of the day, as its starting state; the documents Spec 2 will revise say so ([documentation plan](../designs/bundle-isolation-docs.md#how-the-rewrite-treats-each-kind)). The user accepted the second cost in OD21.
- **R23 — The files views refresh at other moments once the owners ask.** `files` and `git` request the refresh from an observation of live events, where the chat requested it from a change of its store. The coordinator coalesces requests over 250 ms (`bundles/features/files/src/client/refresh/coordinator.ts:3-4`), so the difference should not show. Mitigation: the chat's test of this behavior (`bundles/desktop/chat/tests/sandbox-activity.test.ts`) is rewritten as a test of the two observers before the chat's list is removed.
- **R25 — A consumer of the REST API outside the desktop rejects the `site` field** (A6). It fails to read the provider kinds from the first host that carries step 6(b). Mitigation: the field and the rule that an answer may gain optional fields are written in the host README in that step, and the release notes name the route. No later step reads `site`, so step 6(b) can be reverted alone. R24, the risk of a late answer to Q30, is withdrawn: OD25 answered it.
