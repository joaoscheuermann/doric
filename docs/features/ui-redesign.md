## Summary

The Figma file redraws Doric's desktop UI: a warm beige and brown palette instead of the neutral grey and blue one, a three-column window without a window-wide footer (sidebar, conversation card, Files column), borderless content on inset cards, and features the code does not have: an Appearance setting, an account avatar with an account menu and a resources popover, Back and Forward, ⌘F sidebar search, 14 new context-menu actions and a two-pane splash. Archived Threads, which the design also draws, are deferred ([UR9](#deferred)).

"1:1" in this document means: every screen the Figma prototype draws, and every component its component pages draw, renders with the file's colors, sizes, spacing, radii, typography and icons, within the checks of [How 1:1 is verified](#how-11-is-verified).

This concept fixes the scope, the four phases and what each must leave behind, and the contracts and persisted data each new feature implies. The [spec](../designs/ui-redesign.md) settles the per-file work.

## Problem

The Figma file is the design the user wants shipped, and the code differs from it in three ways:

1. **Visual language.** Every color token changes (Light `11:6`, Dark `11:311` against `packages/desktop/src/tokens/tokens.ts:51-208`): for example `--background` becomes `#fbf8f2` / `#1c1a17` (code `#ffffff` at `tokens.ts:52`, `#222222` at `:132`) and `--primary` becomes `#3b352e` / `#ede4d3` (code `oklch(0.55 0.145 258)` at `:58`). Figma puts Noto Sans first; the code puts the system sans first (`tokens.ts:213`). Most component frames remove borders and dividers and place content on inset cards. There is no Doric logo component in the code.
2. **Shell structure.** The prototype has three full-height columns and no window-wide footer. The code renders a window-wide footer with the connection label, the `layout.global-footer` region (resources) and the only Settings button (`bundles/desktop/layout/src/client/components/organisms/workspace-footer.tsx:35-44`, mounted at `bundles/desktop/layout/src/client/views/workspace-view.tsx:195` and `:312`); a full-width Project tab bar holding the Dashboard tab and, on its right, the `layout.header` region and the Files/Changes toggles (`bundles/desktop/layout/src/client/components/organisms/project-tabs.tsx:282-294`, `workspace-view.tsx:231-240`); and the working directory and branch in the conversation footer (`bundles/features/git/src/client/index.ts:58`). The breadcrumb header and sidebar header in `bundles/desktop/layout/src/client/components/organisms/workspace-header.tsx:40-58` are mounted only by their stories, so the app shows neither today.
3. **Missing features.** The design draws a theme setting, an account menu, Back and Forward, sidebar search for Threads, archived Threads (deferred, UR9), ◆ context-menu actions and a two-pane splash. None exists in the code ([New features](#new-features)).

## Goals and success measures

- **G1 — 1:1 with the design**, as defined in the [Summary](#summary).
- **G2 — No behavior lost.** Every behavior `GROUNDING.md` and the code have today stays reachable, except those this concept removes by name (the window-wide footer, the visible separators, and hiding or collapsing the Files column — UR26). Settings stays reachable in two clicks (avatar, then Settings); the connection state stays visible without a click (the status dot); the resource readings are one click away; every keyboard path (tab sorting, inline rename, ⌘F on the Dashboard at `bundles/desktop/layout/src/client/components/organisms/dashboard.tsx:199-211`) keeps working.
- **G3 — The new features.** The feature groups of UR2 except Archive (UR9) — Appearance, the account status, Back/Forward with ⌘F search, the ◆ actions and the splash — work end to end, with their persisted data, contracts and tests. [New features](#new-features) splits them into table rows.
- **G4 — Phased delivery.** Each phase, and each feature inside phase 4, lands on its own with the code building, its tests passing and `GROUNDING.md` describing the shipped state.

### Proposals

The author's proposals, each with its evidence. UR10 accepts them as written, except P4, P5 and P7 (UR7–UR9); [Answered questions](#answered-questions) maps each question to its answer.

- **P1 — The theme is applied by the platform alone.** Main sets Electron's `nativeTheme.themeSource` to `dark`, `light` or `system` from the reader's preference before the splash opens (today it sets `'system'` at `app/desktop/doric/src/main.ts:30`). Electron documents that `themeSource` decides what the `prefers-color-scheme` media query matches in every renderer ([nativeTheme.themeSource](https://www.electronjs.org/docs/latest/api/native-theme#nativethemethemesource)). Every theme consumer follows that query, directly or through one step:
  - **The media query itself**: the generated token sheet's dark block (`packages/desktop/src/tokens/css.ts:25`), Monaco (`packages/desktop/src/code/code-view.tsx:119`, `packages/desktop/src/code/diff-editor.tsx:154`) and the splash page (`app/desktop/doric/src/splash-page/index.html:5-7`).
  - **The `.dark` class**, which each window's bootstrap toggles from the query (`app/desktop/doric-renderer/src/bootstrap.ts:3-7`): the token sheet's `.dark` block (`css.ts:26`), Monaco's theme builder (`packages/desktop/src/code/code-view-theme.ts:221`) and papercraft's preview surface, which watches the class with a `MutationObserver` and passes the mode into its frames, whose shell sets its own `.dark` (`bundles/features/papercraft/src/client/surface/preview-surface.tsx:61-83`, `bundles/features/papercraft/src/client/frames/preview/shell.ts`).
  - **Native window backgrounds**, through `nativeTheme.shouldUseDarkColors` (`main.ts:48-55`).
  - **Exception: open terminals.** xterm reads its colors once with `getComputedStyle` when the view mounts and never listens again (`bundles/features/terminal/src/client/view/terminal-view.tsx:43-75`); the Appearance feature includes making it follow a scheme change.

  No bundle applies the theme; the `settings` bundle shows and changes the preference. `doric.tokens/v1` is not a theme consumer and does not change: it returns a fixed snapshot of the shared tokens and the light palette, answered inside the window (`app/desktop/doric/src/platform/tokens.ts:25-30`, `packages/desktop/src/client/platform.ts:97-108`), and does not report the reader's mode. The token module's `defaultVariant` (`tokens.ts:49`) stays `light`, since it feeds only that snapshot (`css.ts:31-39`).

## Deferred

Archive (UR9). Not shipped in this change: no Archive button in the sidebar header (`256:20963`), no ◆ Archive entry in the Thread menu (`364:23820`), no archive field or method, no Archive view. 1:1 deliberately excludes the Archive button, so the shell captures of phase 2 differ from the prototype there. The user will mature the concept later; this model, withdrawn as P7, is its starting point:

- Archiving a root Thread hides it and its subtree from the sidebar tree; an Archive view, opened from the sidebar header's Archive button, lists the selected Project's archived Threads with Unarchive and Delete.
- Archiving is refused while the Thread or any descendant is running or has queued prompts, so no hidden work spends tokens or sends notifications.
- Data: the Thread document gains an optional archive timestamp. No storage migration is needed: Thread documents already gained optional fields without one (`agent`, `model`, `effort`, `bundles/runtime/runtime/src/contracts/storage.ts:122-139`). The document schema is `.strict()` (`storage.ts:141`), so a build older than the change would reject an archived Thread document; a rollback rule is needed.
- Filtering happens in the desktop: the storage indexes (`byProject`, `byParent`, `storage.ts:192-200`) cannot exclude archived documents, and `projectThreads` returns them all. Agents' Thread listing keeps returning archived Threads.
- Alternatives already weighed: archive kept only in the desktop (lost across machines and windows, invisible to the host's Delete) and archive as soft delete (Delete already exists with its own lifecycle, `GROUNDING.md:208-209`; archiving must be reversible and keep the Thread's history).

## How 1:1 is verified

- **Tokens (phase 1).** The Figma variables of `11:6` and `11:311` are captured once with `get_variable_defs` into a committed fixture with node ids and date, and a test compares the token module with it. The token module stays the hand-edited source; the test catches a later edit of the module that departs from the design, and turns a later Figma change into a reviewed fixture diff instead of a silent drift.
- **Light while the app is fixed to Dark (phases 1–3, UR8).** The light palette ships and is checked without a reader-facing switch: stories render in both themes in papercraft's preview, whose frame takes the light or dark mode it is given (`GROUNDING.md:1359-1361`); doric-e2e sets `nativeTheme.themeSource` itself in its test process; and a development run reads a `DORIC_THEME` environment variable that a packaged build ignores. The spec defines both paths.
- **Components (phases 1 and 3).** The spec lists, per component, its Figma node, its code file and its story. The implementer reads `get_design_context` for sizes, spacing, radii, colors and typography and checks them against the classes, then compares the story, rendered in papercraft's preview (`GROUNDING.md:1425-1436`), with `get_screenshot` of the node, side by side, in both themes.
- **Shell (phase 2).** doric-e2e opens the app on fixture data that matches the prototype's content and captures the window through `doric.windows/v1.capture` (`GROUNDING.md:1772-1773`); the captures are compared with the prototype frames at 1920×1080 in both themes. The deferred Archive button is the one expected difference (UR9).
- **Splash (phase 4).** The splash is not a path window, so `doric.windows/v1.capture` cannot take it (`GROUNDING.md:872-874`); doric-e2e captures the splash window's own contents instead, as the spec states, and compares each state with `71:7407`–`71:7412`.
- **Acceptance.** The user accepts each phase on those side-by-side images. No automated pixel-diff gate: Figma's renderer and Chromium rasterize fonts differently, so a numeric threshold would fail on matching designs or pass on wrong ones.

## Alternatives considered

- **One change for everything.** Rejected by UR5.
- **Restyle the bundles before the shell.** Rejected: the restyles assume the inset cards and transparent panels the shell provides, so they would be drawn twice.
- **Theme in the host configuration** (`settings.config/v1`). Rejected: main needs it before the host answers, the host can be remote and shared, and a theme is a per-machine choice (P2).
- **Theme in `state.json`.** Rejected: a schema failure there drops migration markers, and older builds strip the key (P2).
- **Theme as a method of `doric.tokens/v1`.** Rejected: that contract is a snapshot answered inside the window and cannot reach main to apply or store a choice (P1).
- **Theme by toggling `.dark` from a bundle.** Rejected: the media query consumers (the token sheet's dark block, Monaco, the splash) and native backgrounds would not follow; `themeSource` reaches the query, and the bootstrap already derives `.dark` from it (P1).
- **A reader-facing theme switch before phase 4.** Rejected by UR8: light is reached only through development and test paths until the Appearance selector ships.
- **Back/Forward state from the Navigation API** (`window.navigation.canGoBack`). Rejected: absent from the DOM the tests run in and from the minimal test core. **From main's `webContents.navigationHistory`.** Rejected: one main round trip per render for a state the window can keep itself (P6).
- **A new Files column footer region instead of `layout.panel.footer`.** Rejected: the documented name already describes this place (P16).
- **`layout` depends on `chat` for the reader's name and avatar.** Rejected: `chat` registers into `layout`; the dependency would run against that direction (P11).
- **File creation through a terminal or the agent.** Rejected: the design asks for direct menu actions; the agent's `write` tool overwrites and has no inline-name flow.
- **Deprecate `layout.global-footer` instead of removing it.** Rejected: its one item moves in the same change (P15), and a region with no host would draw nothing.
- **Keep the window-wide footer.** Rejected by UR1. **Keep "follow the OS" as the default.** Rejected by UR4.
- **An automated pixel-diff gate.** Rejected under [How 1:1 is verified](#how-11-is-verified).

## Riskiest assumptions

- **A1 — The component pages describe today's code except where a note says otherwise.** Their descriptions cite `file:line`, but the survey compared pixels for only a few components. If false, phase 3 finds unannounced differences; each is raised as a finding, not adopted silently.
- **A2 — The theme chain holds in every window.** `themeSource` changes what `prefers-color-scheme` matches, each window's bootstrap turns that into `.dark`, and papercraft's preview surface passes `.dark` into its frames (P1). Phase 1 already relies on it for the fixed Dark; phase 1's doric-e2e checks prove it, including a preview frame, and phase 4 adds an open terminal.
- **A3 — The prototype covers the states the shell needs.** It draws no empty Project and no narrow window. P13 keeps the sidebar non-collapsible, and the Files column is always shown (UR26); a zoomed narrow window draws the columns below their minimums, a risk UR27 accepts.

## Risks

- **R1 — Provenance.** Edits to vendored files fail `verify-provenance` unless recorded (HC-008). Mitigation: phase 1 records each patch and adds ButtonGroup from the CLI; brand components live outside the vendored folder.
- **R2 — Behavior regressions in the shell.** `bundles/desktop/layout/AGENTS.md` and the layout tests pin today's structure. Mitigation: the behavior inventory and exit criteria of phase 2; tests changed deliberately and reviewed.
- **R3 — Destructive operations (HC-007, HC-009).** Discard deletes untracked files and cannot be undone; file creation writes into the repository. Mitigation: P22's rules, confirmations and the user's explicit approval before implementation.
- **R4 — ⌘F conflicts.** Monaco's find and xterm also use ⌘F. Mitigation: the sidebar binding acts only when focus is outside an editor or terminal.
- **R5 — Theme flash.** A theme decided after the first window paints shows the wrong one. Mitigation: main sets `themeSource` before creating the splash — to `dark` from phase 1, and from the preference in `appearance.json` from phase 4.
- **R6 — Light-mode readers switch to dark, without a way back until phase 4.** From phase 1 the app is fixed to Dark (UR8), so a reader whose OS is light sees dark after updating and cannot choose Light or System until phase 4 ships the selector. Accepted by UR8; the release notes of phase 1 say so, and those of phase 4 say where the setting is.
- **R7 — Interim inconsistency between phases.** After phase 1 the palette is new and the layout old. Accepted: each phase is coherent on its own, and the user accepts it before the next.
- **R8 — Search scale.** Filtering covers only the Threads the renderer has loaded for the Project (`GROUNDING.md:180-181`); a match in an unloaded subtree is not found. Accepted for this version.
- **R9 — Readings behind a popover.** Resource values are no longer on screen. Mitigation: the dot takes the warning tone when a threshold is crossed (P19).
- **R10 — Glyph fallback.** Text outside Latin and Latin Extended renders in the system sans, not Noto Sans (P12).

## Current behavior and contracts

Phases 1 to 4 and part 2i are built ([spec](../designs/ui-redesign.md) header). Since 2i the Files column is always shown, with no FilesToggle: it is 328 px wide by default, resizes between 14rem and 30rem and cannot be hidden or collapsed; the account status is drawn once, in its header. The layout (2.0.0) provides `layout.panel/v2@2.0.0`, whose one method is `select(id)`, and the panel draws no view while the selected one is not registered (UR28). Today's behavior is the one `GROUNDING.md` and the code describe. This section lists what phase 1 added; the spec records phases 2 to 4 as built. Phase 1 adds:

- The app is Dark: `resolveThemeSource` (`app/desktop/doric/src/platform/appearance.ts`) returns `'dark'` unless an unpackaged run sets `DORIC_THEME` to `light`, `dark` or `system`; windows follow `prefers-color-scheme`.
- Tokens: the Figma Light and Dark palettes; shadows are black in both themes; the native window backgrounds are `#fbf8f2` (light) and `#1c1a17` (dark).
- The filled (default) button hovers by mixing in oklch: `--primary` with 60% `--foreground` in light, with 8% `--primary-foreground` in dark.
- Dialog and alert-dialog footers draw no top rule.
- The window bootstrap and the doric-e2e fixture shell share `followScheme` (`app/desktop/doric-renderer/src/scheme.ts`), which keeps `.dark` equal to `prefers-color-scheme`.
- Fonts: Noto Sans first, the system sans as fallback, Latin and Latin Extended subsets only.
- The reader's identity lives in `packages/desktop/src/identity/`, exported as `desktop/ui/identity` (`initials`, `identityTone`, `identityRing`, `READER_NAME`) and `desktop/ui/reader-avatar` (`ReaderAvatar`). `PLATFORM_VERSION` is 1.6.0 (1.6.0 adds `ScrollArea`'s `scrollbars` prop, which lets the Files column trees scroll sideways); `PLATFORM_ASSETS_VERSION` stays 1.0.0. Chat 1.6.1 requires `engines.doric` `^1.1.0`.
- The tree row has a 28 px height, a 16 px lead slot and 20 px indent steps. Hover or focus never swaps the lead icon for a chevron; the trees draw no chevron. A Thread row with children carries `aria-expanded`. An Untitled Thread's icon is `message-circle-dashed`.

The [sidebar alignment](../designs/sidebar-alignment.md) adds:

- Activity: a Thread row shimmers and shows the elapsed badge while the Thread or any descendant runs, or while an agent terminal under it is busy (`layout.sidebar/v1` 1.1.0 `ThreadRows.busy`, answered by the terminal bundle). The time counts from the Thread's own last start; with none, the row shimmers with no time and keeps a hidden "Agent running" status. The badge reads `mm:ss`, `h:mm:ss` up to 99 h, `{d}d {h}h` up to 99 days, then `99d+`. Thread rows draw no repository mark.
- Sidebar column: no Threads pane or header; an icon-only New Thread button sits under the tree. The Screens and MCP panes (`layout.stack/v2`, layout 3.0.0) are pinned to the column's bottom with 28 px headers, with no divider and no resizing; an open pane is as tall as its content, at most 40 % of the column, and scrolls past that.
- Files column: the Files and Changes trees scroll sideways; the status marks stay pinned to the visible right edge, and a selected or hovered row's background ends where its mark begins.
