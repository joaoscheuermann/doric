# Feature: per-thread model

- Status: `implemented`

## Problem

A conversation runs on a provider, a model and a reasoning effort. The reader needs to change that execution for one conversation without changing it for any other, and a child Thread spawned on a model needs that model checked against the provider its parent runs on. So each Thread needs its own execution, chosen from the conversation, with a workspace setting only as the starting point of a new Thread.

## Decisions

- Each Thread stores its own `providerId`, `model` and `effort`. The workspace default (`models.execution` of the [`host-config`](../../bundles/foundation/host-config/README.md#the-configuration) configuration, chosen in Settings) is only what a new top-level Thread copies when it is created.
- A child inherits its parent's execution. A spawn may override `model` and `effort`, always on the parent's provider. A spawn that names only a model other than the parent's takes that model's start effort; one that names the parent's own model keeps the parent's effort.
- A Thread whose record has no `providerId` runs on the workspace default's provider, with its own stored `model` and `effort` over the default's when it has them, until its execution is first set. The record is not rewritten to add a provider.
- The runtime validates the execution a caller chooses, at spawn (the parts the spawn names, below) and through `setThreadExecution`: first against the configuration (the provider must be configured; a provider that lists models accepts only those, and one that lists none accepts any), then through `models/v1.resolve` ([`core`](../../bundles/foundation/core/README.md#modelsv1)). The `thread-spawn` tool reads neither the configuration nor `models/v1`.
- Validation and `models/v1.resolve` run outside the Project's lock, because they may wait on the network; only the write of the Thread runs inside it.
- Creating a Thread fails, creating nothing, when the configuration cannot be read.
- A change of execution applies from the Thread's next run and next manual compaction. A running prompt keeps the execution it resolved at its start.
- The footer picker edits only the selected Thread and never writes `models.execution`; the default changes only in Settings.
- The [`chat`](../../bundles/desktop/chat/README.md) draws the footer picker from `settings.models/v1`, which it reaches only through `whenAvailable` ([`bundle`](../../packages/bundle/README.md#services-and-the-part-contexts)) and by id, taking the contract's types from `settings/contracts` by `import type` only ([bundles/desktop/chat/src/client/api/settings-models.ts](../../bundles/desktop/chat/src/client/api/settings-models.ts)). It adds the footer item only while that contract is available, so without [`settings`](../../bundles/desktop/settings/README.md) the footer has no `execution` item. It lists `workspace.selection/v1` under `optional` and reads it through its own copy of the contract's types, importing nothing from [`workspace`](../../bundles/desktop/workspace/README.md); without it the picker shows the default, locked.

## Current behavior and contracts

### Stored execution and its resolution

- A Thread record carries optional `providerId`, `model` and `effort` (`runtime.thread/v1` 1.3.0, [bundles/runtime/runtime/src/contracts/storage.ts](../../bundles/runtime/runtime/src/contracts/storage.ts); the public `Thread` of `runtime.threads/v1` 1.8.0, [bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)). Every write the runtime makes stores `providerId` and `model` together, and with `providerId` present an absent `effort` means no effort. The schema does not require `model` beside `providerId`; a record with a provider and no model resolves as unavailable (below), and a child opened from it, or spawned from it without naming a model, stores that provider with `model: ''` ([Creation and spawn](#creation-and-spawn)). The record and the public `Thread` are in the [`runtime`](../../bundles/runtime/runtime/README.md) README's [`runtime.thread/v1`](../../bundles/runtime/runtime/README.md#runtimethreadv1) and [Thread](../../bundles/runtime/runtime/README.md#thread).
- `resolveThreadExecution` ([bundles/runtime/runtime/src/contracts/execution.ts](../../bundles/runtime/runtime/src/contracts/execution.ts)) answers what a Thread runs on under the configuration in force, and never throws:
  - no `providerId`: `resolved` with `source: 'default'`, the default's provider, the Thread's `model` and `effort` when set and the default's otherwise; nothing is checked;
  - `providerId` without `model`: `unavailable` with `issue: 'model'`;
  - a provider the configuration lacks, or a model a listing provider does not list: `unavailable` with that issue and the stored values;
  - otherwise `resolved` with `source: 'thread'` and the stored values. The default's effort is never used for such a Thread, and a stored effort the model does not list does not make the execution unavailable.
- `checkThreadExecution` ([bundles/runtime/runtime/src/contracts/execution.ts](../../bundles/runtime/runtime/src/contracts/execution.ts)) names the first issue that refuses an execution, in the order `provider`, `model`, `effort`. An effort is refused when the model's entry lists efforts (`reasonings`) and not that one; an empty list refuses every effort. `resolveThreadExecution` calls it; apart from that, only the runtime host imports it, and the contracts index does not export it. On a provider that lists no models it passes any model and any effort. These rules are in the runtime README's [Execution](../../bundles/runtime/runtime/README.md#execution-provider-model-and-effort).
- `modelStartEffort` ([bundles/runtime/runtime/src/contracts/execution.ts](../../bundles/runtime/runtime/src/contracts/execution.ts)) is the effort a model starts at: none when the model lists no effort; else the `defaultEffort` of the model's entry in the configuration, when it is one of the model's listed efforts and is not `none` (`modelDefaultEffort`); else the first listed effort other than `none`; else the first. A model that lists no effort carries no effort, and a run with no effort requests no reasoning.
- The settings window keeps reasoning on: when it loads a configuration whose default has no effort or `none` on a model that offers an effort other than `none`, its draft starts at that model's start effort ([bundles/desktop/settings/src/client/domain/config.ts](../../bundles/desktop/settings/src/client/domain/config.ts), `enableExecutionReasoning`). The runtime accepts `none` as an effort (`reasoningEfforts`, [bundles/runtime/runtime/src/contracts/model.ts](../../bundles/runtime/runtime/src/contracts/model.ts)).

### Creation and spawn

- A new top-level Thread stores `models.execution`, its effort kept only when it is one of `reasoningEfforts`. A child the reader opens stores its parent's stored execution, available or not, or a parent without `providerId` its resolved one ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), `create`, `parentExecution`). A parent stored with `providerId` and no `model` gives its child that provider and `model: ''`; on a provider that lists no models the child then resolves as `resolved` with an empty model, while its parent is `unavailable`.
- `createThread` (`runtime.threads/v1` 1.8.0) and `POST /projects/:id/threads`, which the [`transport`](../../bundles/foundation/transport/README.md#routers) bundle serves ([bundles/foundation/transport/src/host/routes/projects.ts](../../bundles/foundation/transport/src/host/routes/projects.ts)), reject, creating nothing, when the configuration cannot be read; the route then answers `500 internal_error` (`handleHttpError`, [bundles/foundation/transport/src/host/errors.ts](../../bundles/foundation/transport/src/host/errors.ts)).
- A spawn (`RuntimeThreadControls.spawn`, `SpawnOptions`, [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts)) starts from the parent's execution and completes it with the `model` and `effort` it names ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts), `spawnExecution`). `SpawnOptions.model` sets no minimum length, so `''` passes on a provider that lists no models and is stored. When the spawn names a model or an effort, the runtime validates the result before any child is created ([bundles/runtime/runtime/src/host/domain/execution.ts](../../bundles/runtime/runtime/src/host/domain/execution.ts)). It takes the first issue `checkThreadExecution` finds and refuses only when that issue is `provider`, or is `model` or `effort` and the spawn named that key; an issue that does not count ends the check, so a named effort is not checked when the parent's own model fails the model check. Then `models/v1.resolve` must accept the provider and model. A failed validation rejects the spawn:
  - a refused execution rejects with a `ContractError` ([`bundle`](../../packages/bundle/README.md#errors)) coded `invalid_execution`, `details.issue` `provider`, `model` or `effort`, and the message `Provider "<provider>" is not configured.`, `Model "<model>" is not available on provider "<provider>". Available models: <models>.` or `Effort "<effort>" is not supported by model "<model>". Supported efforts: <efforts>.`;
  - a provider `models/v1.resolve` cannot resolve rejects with `models/v1`'s own error.
- The `thread-spawn` tool ([`threads`](../../bundles/features/threads/README.md#thread-spawn) 2.1.0, [bundles/features/threads/src/host/tools/thread-spawn.ts](../../bundles/features/threads/src/host/tools/thread-spawn.ts)) passes to the spawn, field by field, the input's `model` or else the agent definition's, and the input's `effort` or else the agent definition's, so an input model can travel with the agent's effort. Its own input leaves `model` optional and, when given, requires at least one character. When the model comes from the agent definition and the runtime refuses it with `details.issue` `model`, the tool fails with `Agent "<name>" names model "<model>", which its parent thread's provider does not list.` followed by the runtime's message; every other refusal is the runtime's error unchanged. Its manifest requires `runtime.threads/v1@^1.7.0` and neither `models/v1` nor `host-config/v1`.

### Changing a Thread's execution

- `setThreadExecution` (`runtime.threads/v1` 1.8.0, [bundles/runtime/runtime/src/contracts/threads.ts](../../bundles/runtime/runtime/src/contracts/threads.ts)) sets a Thread's provider, model and optional effort. Its input trims `providerId` and `model`, which take 1 to 128 and 1 to 512 characters. The method is exposed to windows only (`expose: 'desktop'`, [bundles/runtime/runtime/src/host/services/threads.ts](../../bundles/runtime/runtime/src/host/services/threads.ts); exposure in the `bundle` README's [`defineMethod`](../../packages/bundle/README.md#definemethod-and-defineservice)). It answers `updated` with the Thread, `missing`, `invalid` with the refused part, or `unresolvable` with `models/v1`'s message, and, for a well-formed input, rejects only when the configuration cannot be read or the storage read or write of the Thread fails. Its input and result are in the runtime README's [`runtime.threads/v1`](../../bundles/runtime/runtime/README.md#runtimethreadsv1).
- The runtime validates the execution against the configuration and `models/v1.resolve` outside the Project's lock, then writes the three values in one document write under the lock (an absent `effort` removes the stored one), which also sets the Thread's `updatedAt` to the time of the write, and publishes a Thread update ([bundles/runtime/runtime/src/host/store/threads.ts](../../bundles/runtime/runtime/src/host/store/threads.ts), [bundles/runtime/runtime/src/host/domain/service.ts](../../bundles/runtime/runtime/src/host/domain/service.ts), [bundles/runtime/runtime/src/host/domain/execution.ts](../../bundles/runtime/runtime/src/host/domain/execution.ts)). It updates a Thread of an inactive Project as well. Because `updatedAt` moves, a change of execution moves the Project's `activityAt`, the latest `updatedAt` of the Project and its Threads, and, for a Thread that is not in a terminal state, makes it the Project's `latestActiveThreadId`, the non-terminal Thread with the latest `updatedAt` ([bundles/runtime/runtime/src/host/domain/activity.ts](../../bundles/runtime/runtime/src/host/domain/activity.ts); the runtime README's [`runtime/v2`](../../bundles/runtime/runtime/README.md#runtimev2)).
- `PATCH /threads/:id` ([bundles/foundation/transport/src/host/routes/threads.ts](../../bundles/foundation/transport/src/host/routes/threads.ts)) accepts an execution beside `name` and `cwd`, with the same trims and bounds; `providerId` and `model` come together, `effort` only with them, and a body that breaks this rule or names nothing answers `422 invalid_thread`. The name and the working directory are applied first and are kept when the execution is refused; a missing Thread (`404`), a refused working directory (`400 invalid_cwd`) or a Thread whose Project is inactive when `cwd` is given (`409`) ends the request before the execution is written. A refused or unresolvable execution answers `422 invalid_execution` and a missing Thread `404 thread_not_found` (`restErrors.setThreadExecution`, [bundles/runtime/runtime/src/contracts/rest-errors.ts](../../bundles/runtime/runtime/src/contracts/rest-errors.ts)). When the configuration cannot be read, or a storage read or write fails, the route answers `500 internal_error`; a failure in the execution step leaves the name and the working directory already applied, and a failed write of the name or the working directory ends the request with that step not applied. The body and its answers are in the transport README's [Routers](../../bundles/foundation/transport/README.md#routers), and the messages in the runtime README's [`restErrors`](../../bundles/runtime/runtime/README.md#other-exports-of-runtimecontracts).

### Runs and compaction

- The executor (`executor/v1` 1.5.0, provided by [`default`](../../bundles/runtime/default/README.md) 2.8.0) receives the Thread, with its stored execution, as an `ExecutorThread`, whose shape is in the default README's [`executor/v1`](../../bundles/runtime/default/README.md#executorv1-150) ([bundles/runtime/runtime/src/contracts/executor.ts](../../bundles/runtime/runtime/src/contracts/executor.ts)). Each run resolves the Thread's execution once with `resolveThreadExecution` and uses it for the agent loop, its input modalities, its `response.started` events and its automatic compaction ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts)). A change made while a prompt runs applies from the next run; a manual compaction resolves the execution when it starts. `runtime` 3.0.0 requires `executor/v1@^1.4.0`, the executor version that runs on the Thread's own provider ([bundles/runtime/runtime/manifest.json](../../bundles/runtime/runtime/manifest.json)).
- A Thread whose stored provider or model is unavailable fails each run before any model request, after logging one `LogV1` warning for that run, with the code `thread_execution_unavailable` and the message `The model "<model>" on provider "<provider>" is not available for this thread. Choose another model in the conversation footer.` ([bundles/runtime/default/src/host/executor.ts](../../bundles/runtime/default/src/host/executor.ts); the default README's [Model](../../bundles/runtime/default/README.md#model); `LogV1` is `log/v1` of the `bundle` README's [Basic contracts](../../packages/bundle/README.md#basic-contracts)). The runtime handles the rejection as any failed run: it publishes `agent.failed` carrying the error, finishes the prompt as `failed` with the text `The prompt failed.`, and returns the Thread to `ready`; the Thread itself does not fail. The next queued prompt then runs and fails the same way, until the Thread's execution is changed ([bundles/runtime/runtime/src/host/domain/runner.ts](../../bundles/runtime/runtime/src/host/domain/runner.ts); the runtime README's [Prompts and the queue](../../bundles/runtime/runtime/README.md#prompts-and-the-queue)).
- A manual compaction summarizes on the Thread's own provider and model, with no effort, and fails as `summarizer_failed` when the Thread's execution is unavailable or `models/v1.resolve` rejects ([bundles/runtime/default/src/host/compact.ts](../../bundles/runtime/default/src/host/compact.ts); the default README's [Compaction](../../bundles/runtime/default/README.md#compaction)). The chat titles these failures `Model unavailable` and `Compaction failed` ([bundles/desktop/chat/src/client/domain/error-catalog.ts](../../bundles/desktop/chat/src/client/domain/error-catalog.ts); see [error messages](error-messages.md)).

### The footer picker

- `<chat-execution-picker>` (`chat` 2.0.0) is the footer item `execution`, order 20, of the slot `shell.conversation.footer`, which [`layout`](../../bundles/desktop/layout/README.md#slots) declares and draws as the band over the conversation's bottom ([bundles/desktop/layout/src/contracts/index.ts](../../bundles/desktop/layout/src/contracts/index.ts)); the `usage` item sits after it, at order 30 ([bundles/features/usage/src/client/index.ts](../../bundles/features/usage/src/client/index.ts)). The chat adds the item only while `settings.models/v1` is available; the item is in the chat README's [Elements, route, slot items](../../bundles/desktop/chat/README.md#elements-route-slot-items) and the picker in its [execution picker](../../bundles/desktop/chat/README.md#the-execution-picker) ([bundles/desktop/chat/src/client/index.ts](../../bundles/desktop/chat/src/client/index.ts), [bundles/desktop/chat/src/client/elements/chat-elements.tsx](../../bundles/desktop/chat/src/client/elements/chat-elements.tsx)). The chat's manifest lists `settings.models/v1` and `workspace.selection/v1` under `optional` and requires `runtime.threads/v1@^1.8.0` ([bundles/desktop/chat/manifest.json](../../bundles/desktop/chat/manifest.json)).
- Everything the picker shows, and the execution each pick yields, comes from `settings.models/v1` 1.0.0 (`view(stored?)`, `subscribe`, `reload`, provided by [`settings`](../../bundles/desktop/settings/README.md#settingsmodelsv1-100) 1.12.2, [bundles/desktop/settings/src/contracts/models.ts](../../bundles/desktop/settings/src/contracts/models.ts)): picking another model yields that model's start effort, and the chat applies no rule of its own. Picking a model in another provider's group yields that provider as well, so the footer, like any other `setThreadExecution` call, can move a Thread to another provider, which a spawn never does ([bundles/desktop/settings/src/client/domain/config.ts](../../bundles/desktop/settings/src/client/domain/config.ts), `selectModelChoice`, `updateModel`). A pick writes the selected Thread's execution through `setThreadExecution`; picking what is already shown writes nothing ([bundles/desktop/chat/src/client/components/organisms/execution-picker.tsx](../../bundles/desktop/chat/src/client/components/organisms/execution-picker.tsx)).
- `settings.models/v1` reads the workspace configuration through the settings' `configSnapshot` query, which it observes only while it has a subscriber; while it has one, it also reads the configuration again every time the window gains focus ([bundles/desktop/settings/src/client/services/settings-models.ts](../../bundles/desktop/settings/src/client/services/settings-models.ts), [bundles/desktop/settings/src/client/index.ts](../../bundles/desktop/settings/src/client/index.ts)). A save through the settings' `useConfig`, in the settings view or on the dashboard's providers page ([bundles/desktop/settings/src/client/views/dashboard-providers.tsx](../../bundles/desktop/settings/src/client/views/dashboard-providers.tsx)), invalidates that query in its own window ([bundles/desktop/settings/src/client/hooks/use-config.ts](../../bundles/desktop/settings/src/client/hooks/use-config.ts)), so a footer in that window shows the new configuration at once; a footer in another window shows it when that window gains focus. A new default or a removed model therefore reaches an open footer at the next read, and each read re-renders the picker.
- Until the first read answers, `view` is `status: 'loading'` and the picker draws nothing. When the first read fails, the picker draws only an announced inline `ErrorNotice`, and no triggers. The notice takes its title from the first code, in the error and then its causes, that the chat's catalog or the shared catalog has an entry for, skipping `internal` (an `auth_*` code, for one), and `Settings not loaded` (`config_read_failed`, the fallback) when none has; its Retry calls `reload` and is hidden when the matched level is not retryable (the full rule is in the `desktop` README's [How a notice words an error](../../packages/desktop/README.md#how-a-notice-words-an-error), [packages/desktop/src/error-copy.ts](../../packages/desktop/src/error-copy.ts)). When a later read fails, the same notice stands beside the triggers ([bundles/desktop/chat/src/client/domain/error-catalog.ts](../../bundles/desktop/chat/src/client/domain/error-catalog.ts); the notice in the `desktop` README's [error notice](../../packages/desktop/README.md#the-error-notice-desktopuierror-notice)).
- The picker shows the execution being written while a write is pending, and otherwise the selected Thread's stored execution resolved with `resolveThreadExecution`: for a Thread without `providerId`, the default's provider with the Thread's own `model` and `effort` when it has them and the default's otherwise ([bundles/desktop/settings/src/client/services/settings-models.ts](../../bundles/desktop/settings/src/client/services/settings-models.ts)). A Thread whose stored provider or model the configuration lacks shows its stored model: a model its provider does not list is added as the first choice of that provider's group, or, when the configuration lacks the provider, as an unlabeled first group of its own ([bundles/desktop/settings/src/client/domain/config.ts](../../bundles/desktop/settings/src/client/domain/config.ts)). An empty model adds no choice; the model trigger then reads `Choose model`, and in text-field mode (below) the field is empty with its placeholder `Model id`.
- The picker reads the selected Thread from the window's [`runtime.records/v1`](../../bundles/runtime/runtime/README.md#runtimerecordsv1) mirror of the host's Projects and Threads; each update of the mirror re-renders the picker. An `updated` answer is shown while its `updatedAt` is later than the mirror's record, and dropped once the mirror's record is as late, so a pick shows at once and the mirror's record takes over when it catches up.
- With no Thread selected, without [`workspace.selection/v1`](../../bundles/desktop/workspace/README.md#workspaceselectionv1-100), or while the selected Thread's record is not in the mirror, it shows the workspace default with both triggers disabled and titled `New threads start on the workspace default. Change it in Settings.` While a write is pending both triggers are disabled.
- When a provider lists models, the model trigger opens a popover with a search field over the models grouped by provider, and a shaded footer that always holds the Reasoning effort button ([bundles/desktop/chat/src/client/components/molecules/model-picker.tsx](../../bundles/desktop/chat/src/client/components/molecules/model-picker.tsx)). The popover has the same bordered surface as the conversation's usage popover of the [`usage`](../../bundles/features/usage/README.md) bundle ([bundles/features/usage/src/client/components/thread-usage.tsx](../../bundles/features/usage/src/client/components/thread-usage.tsx)). Beside the model trigger, the effort trigger lists the efforts the model accepts, without `none` ([bundles/desktop/chat/src/client/components/molecules/effort-picker.tsx](../../bundles/desktop/chat/src/client/components/molecules/effort-picker.tsx)). For a model with no effort, both the footer's Reasoning button and the effort trigger are disabled and show `Unavailable`. Both effort menus have the same bordered surface and draw the platform's `ChoiceList` (`desktop/ui/choice-list`, [packages/desktop/src/choice-list.tsx](../../packages/desktop/src/choice-list.tsx); the `desktop` README's [`ChoiceList`](../../packages/desktop/README.md#choicelist)) in its compact form: compact rows, with a subtle highlight on the selected level.
- When no provider lists models, the model is a text field (`Model id`) that commits on blur or Enter, never per keystroke; a blank or unchanged value writes nothing. The typed model is written with no effort, which removes the Thread's stored effort, on the view's typed provider: the shown execution's provider when the configuration has it, else the default's provider (`typedProviderId`, [bundles/desktop/settings/src/client/services/settings-models.ts](../../bundles/desktop/settings/src/client/services/settings-models.ts)).
- A refused write shows an announced inline `ErrorNotice` on its own Thread only, in place of a failed-read notice. Its text is the REST error `restErrors.setThreadExecution` gives the answer, not the spawn's messages: for `invalid`, `Model not accepted` with `The provider is not configured.`, `The model is not available on this provider.` or `This model does not support that effort.`; for `unresolvable`, `Model not accepted` with `models/v1`'s message; for `missing`, `Thread not found` with `The thread was not found.` These carry no Retry ([bundles/runtime/runtime/src/contracts/rest-errors.ts](../../bundles/runtime/runtime/src/contracts/rest-errors.ts), [bundles/desktop/chat/src/client/domain/error-catalog.ts](../../bundles/desktop/chat/src/client/domain/error-catalog.ts)). When the call itself rejects, the notice is worded by the same rule, with `Model not accepted` (`invalid_execution`) as the fallback, and its Retry, unless hidden by that rule, writes the same execution again. A new write clears the Thread's notice.
