# Feature: papercraft

- Status: `implemented`

## Problem

An agent that changes a user interface can only describe the change in words, and the reader has to picture it. The reader needs to see the change drawn with the Project's own components, point at the element they mean, and steer the agent from there. The Project's components are code the app does not trust, so drawing them must not give that code the app's powers, and showing an idea must not write files into the Project. So the agent writes a short OpenUI Lang program in its answer, the conversation draws it live in an isolated frame with the Project's components and exports, and the reader pins comments on it that go back to the agent.

## Decisions

- The agent writes a papercraft program in a ` ```papercraft ` fence of its answer. The fence's info string names the program's identity. A later fence with the same identity is a patch, merged into that program by statement name; a fence with a new identity, or with none, starts a new program, and a fence without an identity never patches the Thread's last program.
- Only papercraft fences are drawn in the isolated frame, because they run repository code; every other OpenUI fence is drawn in the app's own DOM. The built-in library is react-ui's, extended with the repository's components and `Export`.
- No artifact is stored: the program lives in the assistant's answer in the Thread log, and each fence of an identity is one revision of the program.
- Every program is drawn in an `<iframe sandbox="allow-scripts">` without `allow-same-origin`: an opaque origin, its own realm, no preload, no persistent storage and no access to the app's DOM. The frame's `localStorage` and `sessionStorage` live in memory and nothing persists. A window keeps at most three live frames, and the others show a snapshot. Cross-origin access is granted by path prefix, not per module. The frame runtime is an asset of the `papercraft` bundle, not a platform package. Each frame evaluates its own React.
- A papercraft fence has no actions. Inside the frame a program changes only its local state (`$variables`, tabs, forms); an action step (`@ToAssistant`, `@OpenUrl`, `@Run`), `Query` or `Mutation` is an error reported to the agent, with a hint that actions belong in conversation fences. The reader answers a program with pinned comments.
- Form values and `$variables` are not stored: they reset when a fence's frame mounts again.
- A fence's errors reach the agent only when a window drew the fence, from the renderer's errors; no host reads or parses fences. Errors of a drawn fence are delivered in the same turn: as a steer while the prompt that wrote it runs, as a new prompt once it has finished. A fence whose repository library answers `failed` is drawn with the built-ins and reports no errors to the agent; a fence with no library still reports.
- The reader sees a program's errors in one card under the canvas: a header with "1 error" or "N errors", one line per error with its statement name before it and no code, and the footer "Sent to the agent." once the report is sent. Library and `Export` notes join the card. A complete program whose errors leave it blank says "Nothing to draw: this program has errors."
- `Export(path, name?, props?)` draws any export or story of a workspace file. Its props are not validated by a schema, so registering a component in a repository library adds typed props and signatures the agent reads, and is not needed to preview it.
- A repository registers its components in library files under `.doric/papercraft/schemas/`, one `defineComponent` with a zod schema per entry file, written by the agent or a developer and versioned in Git. Each bundle that keeps app state under `.doric/` ignores it with a `.gitignore` in its own folder; papercraft's ignores everything in `.doric/papercraft/` but itself and `schemas/`.
- A library is evaluated in the Project's sandbox under Node, built when a window draws a fence and at prompt start in a Thread that has loaded the `papercraft` skill. Its harness wraps the whole program. When a Git rule hides the schema files, the library instruct names the rule and tells the agent to tell the reader.
- A repository component named like a built-in, or named `AskForm`, `Action`, `Query` or `Mutation`, is a compile error of the library.
- The harness search stops at the repository root, for libraries and `Export`. A harness may live in `.storybook/preview.<ext>` or `.papercraft/preview.<ext>`.
- Repository components keep the repository's own CSS; react-ui components take Doric's tokens.
- Showing or revising a program changes no Project file. The writes are `.doric/papercraft/.gitignore`, the runner copy under `.doric/papercraft/` and temporary job folders. Once per Project per host session, a `.doric/.gitignore` whose whole content is `*` is deleted, after writing `.doric/artifacts/.gitignore` (`*`) when `.doric/artifacts/` exists without one.
- Limits: at most 100 schema entry files, 16 KiB each and 1 MiB in all; a host memo of 64 MiB; a desktop cache cut back from above 256 MiB to 128 MiB at the first `ensure` of each app session, before any frame of that session loads a module; two runner jobs per Project at once; a 10-second evaluation timeout; a 5-minute hold of a `cwd` after the runner reports it could not run the job, for any reason (a crash, a timeout, an output the host could not read) except a missing sandbox lease and the lasting reasons no retry within minutes changes: the sandbox has no `node`, the sandbox's esbuild version differs from the host's, esbuild could not be loaded, or this host was built without the sandbox runner; during the hold `library` answers that job's `failed` answer without running another; a library instruct of at most 16,000 characters.
- The OpenUI packages are used directly, with no reimplementation: `@openuidev/lang-core` 1.0.2, `@openuidev/react-lang` 1.0.2 and `@openuidev/react-ui` 0.18.1, each pinned to an exact version. react-ui's `zustand` peer resolves to zustand 4.5.7 in `bundles/features/papercraft/node_modules` ([package-lock.json](../../package-lock.json)), not to the zustand 5 that the root `overrides` entries of [package.json](../../package.json) name for react-ui and react-headless. zustand is not a frame import-map specifier ([externals.ts](../../packages/bundle/src/build/externals.ts)), so the frame build bundles that copy, imported through `@openuidev/react-ui/genui-lib`, into the frame runtime ([runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts)). `@openuidev/react-headless` is an installed peer that no Doric module imports.
- OpenUI's runtime telemetry is opt-in through `OPENUI_RUNTIME_TELEMETRY_ENABLED`, and Doric never sets it.
- Instructions come in two skills. `openui` holds the language and the built-in components. `papercraft`, at most 8,000 characters, holds the papercraft fence, `Export`, repository libraries and how to answer comments, and tells the agent to load `openui` first. Both state the patch rule: a fence with an earlier identity is a patch; a new program is written whole, starting with `root`; a fragment is never sent as a new program. The repository's signatures reach the agent as a retained instruct, at a prompt's start or a move.
- The canvas is kept: pins, pan, zoom, gestures and the element tree. The canvas window is keyed by the program's identity. A comment targets kind `papercraft-program` with the identity as its id. An element's anchor uses the `selector` form, with the statement name as `selector` and the component as `label`; a click on no statement records a point. The agent answers comments with `comment_reply`.

### The fence and its program

- The agent writes ` ```papercraft <identity> `. A written identity is lowercase letters, digits and hyphens, starting with a letter, at most 64 characters; a fence without one gets an anonymous identity of the form `_<n>` ([bundles/features/openui/src/contracts/identity.ts](../../bundles/features/openui/src/contracts/identity.ts)).
- The client registers `<papercraft-fence>` as chat's renderer of the `papercraft` tag through `chat.views/v1.registerFenceRenderer`, and claims the `papercraft.cwd/v1` events so the conversation draws no block for them ([bundles/features/papercraft/src/client/index.ts](../../bundles/features/papercraft/src/client/index.ts), [cwd-projector.ts](../../bundles/features/papercraft/src/client/cwd-projector.ts)). Each window keeps one fold per Thread of the Thread's papercraft fences, merged by statement name with lang-core's merge; each fence is one revision, `streaming`, `closed` or `unterminated` ([bundles/features/papercraft/src/client/folds.ts](../../bundles/features/papercraft/src/client/folds.ts), [openui-adapter.ts](../../bundles/features/papercraft/src/client/openui-adapter.ts)).
- `<papercraft-fence>` draws the fence's revision as a canvas node: the library bound at the fence's turn, its `Export`s, a frame, the errors and the program's comments ([bundles/features/papercraft/src/client/fence.tsx](../../bundles/features/papercraft/src/client/fence.tsx)). The frame gets no program until the library answer is known; then it receives `init` with the library, and a `program` message (the text, whether it streams, and the built exports) each time one of them changes, without resetting the program's local state ([bundles/features/papercraft/src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts), [frame-protocol.ts](../../bundles/features/papercraft/src/client/frame-protocol.ts)).
- Each window boots one warm frame at activation, handshaken up to `ready`, which the first papercraft fence takes ([bundles/features/papercraft/src/client/surface/live-frames.ts](../../bundles/features/papercraft/src/client/surface/live-frames.ts)).
- In the frame, OpenUI's `Renderer` draws the program with react-ui's library, `Export` and the repository's components, each named statement wrapped in a `display: contents` span that names its statement and component. Actions reach nothing outside the frame ([bundles/features/papercraft/src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts)).

### Repository libraries and the working directory

- The host appends `papercraft.cwd/v1` (`{ cwd }`) to the Thread at a prompt's start, and at a move of the working directory during a prompt, whenever the directory differs from the last one appended. A fence binds to the `cwd` of the last such event below its `turnSequence`; without one its library is `none` ([bundles/features/papercraft/src/host/library.ts](../../bundles/features/papercraft/src/host/library.ts), [src/contracts/cwd.ts](../../bundles/features/papercraft/src/contracts/cwd.ts)).
- `papercraft.programs/v1` 1.0.0 (host, exposed to the desktop with the scope `projectId`, `threadId`) builds a fence's library, builds an export and reads a built module's bytes; its methods and answers are in the [README](../../bundles/features/papercraft/README.md#papercraftprogramsv1-100--libraries-exports-and-module-bytes) ([src/contracts/programs.ts](../../bundles/features/papercraft/src/contracts/programs.ts), [src/host/programs.ts](../../bundles/features/papercraft/src/host/programs.ts)):
  - `library` answers `none`, `ready` or `failed`, and never rejects for a library problem. When the Project has no sandbox lease, `library` answers `ready` from the previous build of the same library root while the host memo still holds it, and otherwise `failed` with "The Project's sandbox is not running; repository components need it"; neither case is held ([src/host/programs.ts](../../bundles/features/papercraft/src/host/programs.ts)).
  - `export` answers `ready` with the built module, or `failed` with why; a path that leaves the Project or a source that does not build answers `failed`.
  - `read` answers the bytes of a module the host memo holds; it fails `not_found` when the memo holds none, and the window then asks `library` or `export` again, once.
- A module is named by a hash of its files, so equal files give the same module; it holds `index.js`, `index.css` when the module has a sheet, and its `url()` assets ([src/contracts/programs.ts](../../bundles/features/papercraft/src/contracts/programs.ts)).
- The library root is the first directory, walking up from the `cwd`, whose `.doric/papercraft/schemas/` holds entry files; the walk stops after the nearest repository root (a directory with `.git`), else at the workspace root, and finding none answers `none`. The library job walks up to that root, answers from the previous build when its manifest still holds, and otherwise evaluates the schema files for their signatures and bundles the library module, in the Project's sandbox ([bundles/features/papercraft/src/sandbox/library.ts](../../bundles/features/papercraft/src/sandbox/library.ts)). The limits are those of the Decisions ([src/sandbox/library.ts](../../bundles/features/papercraft/src/sandbox/library.ts), [src/host/programs.ts](../../bundles/features/papercraft/src/host/programs.ts), [src/host/library.ts](../../bundles/features/papercraft/src/host/library.ts)).
- Once the Thread has loaded the `papercraft` skill, each prompt start and each move gives the library instruct, through `runtime.threads/v1` `instruct` with the reason `library` and `retain: true`, built from the directory's last library answer and given only when its text changed; at a prompt start a library job for the directory then runs without being awaited ([src/host/library.ts](../../bundles/features/papercraft/src/host/library.ts)).
- The library job checks the schema files with `git check-ignore -v` (5-second timeout). When a Git rule hides them, the instruct gains the line "Git ignores these schema files (`<source>:<line>`), so they are not versioned. Tell the reader. Removing that rule keeps Doric's app state out of Git, because each Doric folder under `.doric/` has its own `.gitignore`." ([src/sandbox/library.ts](../../bundles/features/papercraft/src/sandbox/library.ts), [src/host/library.ts](../../bundles/features/papercraft/src/host/library.ts)).
- The frame loads the library module and its sheet. A module built against other OpenUI packages than the frame's, or one that does not load, is left out with an error, and the program draws with the built-ins. A library that answers `failed` draws the program with the built-ins, adds "Drawn without the repository library: <reason>" to the error card, and sends no errors to the agent ([src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts), [src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts)).

### `Export`: previewing the Project's code

- `Export(path, name?, props?)` mounts one export or story of a workspace file. Only calls whose `path` (and `name`, when given) are string literals are built, at most 8 distinct exports per program, each keyed `<path>#<name>`; an export not built yet shows a placeholder. Each distinct export past the eighth gives `runtime-error` "Too many exports in one program: at most 8.", and an export whose build failed gives `render-error` with the failure; both join the program's errors ([src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts), [src/client/program-errors.ts](../../bundles/features/papercraft/src/client/program-errors.ts), [src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts)).
- The built module exports `mount(root, { theme, args })`. It wraps the chosen export (`entry`, else `default`, else the single PascalCase export) in the Project's harness decorators; a CSF stories file mounts one story (`entry`, else the first in source order) with Storybook's decorator order and `args` merge, and `props` are spread over the story's args; a plain component (not CSF) takes `props` as its props ([src/host/entry.ts](../../bundles/features/papercraft/src/host/entry.ts), [src/host/bundle.ts](../../bundles/features/papercraft/src/host/bundle.ts)).
- The bundle is built in the Project's sandbox when the sandbox image installs esbuild under `/opt/doric/bundler`, as the image `app/backend/doric-host/.sandbox.Dockerfile` builds does: through `runtime.lease/v1.withLease`, the host copies its runner script into `.doric/papercraft/` of the workspace, writes the job's input JSON there, runs `node` on it with a 120-second timeout and reads the output back, so esbuild reads the Project's files from the sandbox's disk. A sandbox without a lease, `node` or that esbuild, or a runner that breaks, falls back to the host bundling the entry and reading each file through `files/v1`, under a budget of 1,500 reads and 8 MiB; past it the build fails, telling the agent to stub large dependencies. Only this host build has a read budget; the sandbox build has none ([src/sandbox/run.ts](../../bundles/features/papercraft/src/sandbox/run.ts), [src/host/sandbox.ts](../../bundles/features/papercraft/src/host/sandbox.ts), [src/host/compile.ts](../../bundles/features/papercraft/src/host/compile.ts), [src/host/bundle.ts](../../bundles/features/papercraft/src/host/bundle.ts)).
- Resolution is the same for every Project ([src/host/bundle.ts](../../bundles/features/papercraft/src/host/bundle.ts)):
  - `react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `react-dom`, `react-dom/client` and each `@base-ui/react` specifier the frame's import map serves stay external; the host checks once per specifier that its own copy builds with React external.
  - `lucide-react` is bundled from the host's own `node_modules`.
  - Relative imports and `tsconfig.json` `paths` aliases are read from the Project; any other package from the Project's `node_modules`, by the nearest tsconfig's `customConditions` and honouring a subpath folder's own `package.json`, and bundled as the preview's own copy.
  - No import is refused for what it names, because the frame is the boundary. A build fails, naming the import, only for a Node built-in, a package missing from the Project, or a host build past the read budget. A source that does not build answers `failed`.
- The harness is the nearest `.storybook/preview.*`, else `.papercraft/preview.*` (`.tsx`, `.ts`, `.jsx`, `.js`), walking up from the previewed file and stopping at the repository root (a directory whose `.git` is a file or a directory), skipping `.doric/` and `node_modules/`. It is in Storybook's `Preview` shape (`decorators`, `parameters`, `args`); a harness that does not compile is left out with a warning. `@storybook/addon-themes` is a built-in stand-in whose decorators set their class or attribute on `parentSelector` (`html` by default) ([src/host/harness.ts](../../bundles/features/papercraft/src/host/harness.ts), [src/host/files.ts](../../bundles/features/papercraft/src/host/files.ts)).
- Decorators and stories receive `context.papercraft` (also `context.parameters.papercraft`) with `theme`, `root` and a `portalContainer` that is `undefined`; overlays portal into the frame's `document.body`, Base UI's and Radix's default ([src/host/entry.ts](../../bundles/features/papercraft/src/host/entry.ts)).

### Styles and theme

- The program frame loads three sheets before anything renders: Doric's tokens, react-ui's layered sheet and Doric's `--openui-*` tokens ([src/client/frames/openui/sheets.ts](../../bundles/features/papercraft/src/client/frames/openui/sheets.ts)).
- An export's sheet compiles on the host with Tailwind v4. Its base is a generic theme (Tailwind's theme variables, preflight and utilities, and a neutral shadcn token set in light and dark); the CSS the harness imports replaces it, and the components' CSS is appended. A `.css` import always compiles into the sheet. A relative `url()` is rebased: its bytes are read and stored with the module as `assets/<sha256>.<ext>`; one that cannot be read, or is larger than 4 MiB (16 MiB a sheet), stays as written with a warning. Tailwind v3, or a sheet that does not compile, falls back to the generic theme with a warning ([src/host/css.ts](../../bundles/features/papercraft/src/host/css.ts), [src/host/theme.ts](../../bundles/features/papercraft/src/host/theme.ts)).
- Sheets are linked in the frame's own document, so `:root` is the frame's `<html>`, which carries `class="dark"` in dark mode. Only the reader's light or dark mode reaches the frame, at `init` and on each change; the frame waits at most 3 seconds for a linked sheet to load ([src/client/frames/preview/shell.ts](../../bundles/features/papercraft/src/client/frames/preview/shell.ts), [src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts), [src/client/surface/preview-surface.tsx](../../bundles/features/papercraft/src/client/surface/preview-surface.tsx)).

### Errors

- The app checks each program itself. Each call of `@ToAssistant`, `@OpenUrl` or `@Run` gives `unknown-function` with "@<step> is not available in papercraft fences. Actions belong in openui-lang fences; a preview changes only local state ($variables, forms, @Set, @Reset), and the reader answers with pinned comments."; `Query` and `Mutation` give `tool-not-found` with "Query and Mutation are not available; write the data as literals."; a statement holding `AskForm` gives `unknown-component` with "Questions go in openui-lang fences." ([src/client/program-errors.ts](../../bundles/features/papercraft/src/client/program-errors.ts)). The `Export` errors of the previous section join these.
- The frame posts the renderer's errors, at most 50, each message cut to 1,024 characters ([src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts)). The conversation node, not the canvas window, reports a revision's errors with the tag `papercraft` through `openui.programs/v1.reportErrors`, sending only each error's code and statement, never the frame's text ([src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts)); how a report reaches the agent is in [generative-ui.md](generative-ui.md#errors).
- The card is drawn by [program-errors-card.tsx](../../bundles/features/papercraft/src/client/surface/program-errors-card.tsx), and the "Nothing to draw" notice by [preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx).

### The frame

- Each frame is an `<iframe sandbox="allow-scripts">` ([src/client/surface/live-frame.tsx](../../bundles/features/papercraft/src/client/surface/live-frame.tsx)) that loads `doric://app/frame/index.html?entry=` naming papercraft's frame entry, `client/frames/openui.js` ([src/client/frame-url.ts](../../bundles/features/papercraft/src/client/frame-url.ts), [src/client/frames/openui.ts](../../bundles/features/papercraft/src/client/frames/openui.ts)).
- The desktop serves the frame document with an import map of its own, holding only React, ReactDOM and the platform's Base UI specifiers as absolute `doric://app/platform/…` URLs, so a frame loads the platform's files and evaluates its own instance. Its `boot.js` imports the entry only when it is a `doric://app/bundles/<id>@<version>/client/frames/<name>.js` module. Its policy lets the frame run scripts only from `doric://app` and its inline import map (allowed by its hash), take sheets from `doric://app` or inline `<style>`, fonts only from `doric://app` and images from `doric://app`, `data:` and `blob:`; it connects nowhere and only `doric://app` may frame it, and the shell's policy frames only `doric://app/frame/` ([the policies](../architecture/bundles/doric-protocol.md#content-security-policies); [app/desktop/doric/src/platform/protocol/frame.ts](../../app/desktop/doric/src/platform/protocol/frame.ts), [csp.ts](../../app/desktop/doric/src/platform/protocol/csp.ts)). Only the paths a frame loads answer cross-origin requests: the frame document, the platform's files, the module files and the bundles' frame entries ([cross-origin access](../architecture/bundles/doric-protocol.md#cross-origin-access); [handler.ts](../../app/desktop/doric/src/platform/protocol/handler.ts)). A subframe of an app window may navigate only to the frame document ([navigation-guard.ts](../../app/desktop/doric/src/platform/windows/navigation-guard.ts)).
- A client's `src/client/frames/*.ts` build to `dist/client/frames/<name>.js`. Only the frame import map's specifiers stay external; `bundle/*` and `desktop/*` are refused, and so is every other specifier of the window's map except `zod`, which a frame bundles. The build's dry activation never loads a frame, and frames ship with the client's files ([packages/bundle/src/build/parts.ts](../../packages/bundle/src/build/parts.ts), [externals.ts](../../packages/bundle/src/build/externals.ts)).
- The app and the frame speak over one `MessageChannel` per frame, protocol 2. Once its runtime listens, the frame posts a window message `hello` to its parent; the app, taking it only from that iframe's `contentWindow`, answers `connect` with the channel's second port, and from then on each side speaks only through the port, the frame first with `ready`. The app parses every frame message as untrusted data with a strict schema and drops what does not parse ([src/client/frame-protocol.ts](../../bundles/features/papercraft/src/client/frame-protocol.ts)). The app sends the frame its program, theme, input capture and layers; the frame reports its readiness, size, scene, errors and input. There is no action message; the messages and their fields are in the [README](../../bundles/features/papercraft/README.md#the-program-frame).
- The frame runtime installs in-memory `localStorage` and `sessionStorage`, puts a `#root` in its `<body>`, sets the theme on `<html>`, reports the scene, the size, `mounted` and errors, and applies the hidden layers, the cursor lock and the input capture the app asks for ([src/client/frames/preview/shell.ts](../../bundles/features/papercraft/src/client/frames/preview/shell.ts), [storage.ts](../../bundles/features/papercraft/src/client/frames/preview/storage.ts), [input.ts](../../bundles/features/papercraft/src/client/frames/preview/input.ts)).
- The frame derives the scene from its own DOM, with bounds in CSS px of its document; the canvas scales the iframe by `transform`, so no measure depends on the zoom. Each element is measured only by the part its clipping ancestors leave visible, and a `display: contents` wrapper gives its children's boxes, so fitting the view centres what is shown and does not drift ([src/client/frames/preview/scene.ts](../../bundles/features/papercraft/src/client/frames/preview/scene.ts), [src/client/surface/fit.ts](../../bundles/features/papercraft/src/client/surface/fit.ts)).
- A program frame reports the layout `padded`, so the surface lays it out at the canvas's width; a frame that falls back hugs what it shows. The height is always the content's ([src/client/frames/openui/runtime.ts](../../bundles/features/papercraft/src/client/frames/openui/runtime.ts), [src/client/surface/preview-surface.tsx](../../bundles/features/papercraft/src/client/surface/preview-surface.tsx)).

### Live frames and snapshots

- A window keeps at most three live frames, those used last. A preview is used when its revision first appears in the window, when the reader's pointer moves over it or presses on it, and for as long as a live frame of it is on screen. A dead preview scrolled into view is not promoted; a pointer or press on it mounts a live frame again, under its stand-in until the frame reports `mounted`. The canvas window's open revision always stays live, outside the count ([src/client/surface/live-frames.ts](../../bundles/features/papercraft/src/client/surface/live-frames.ts), [preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx)).
- A dead preview shows its snapshot at the same size, else a placeholder with its size and title, with the last scene its frame reported, so pins, outlines and comments still draw. A snapshot is taken once a live frame has mounted and stays settled, wholly on screen, with nothing over it; it is kept in memory by program, revision, theme and width. A frame that does not report `mounted` within ten seconds shows the stand-in with the fallback notice ([src/client/surface/snapshots.ts](../../bundles/features/papercraft/src/client/surface/snapshots.ts), [stand-in.tsx](../../bundles/features/papercraft/src/client/surface/stand-in.tsx), [preview-surface.tsx](../../bundles/features/papercraft/src/client/surface/preview-surface.tsx)).
- `papercraft.snapshot/v1` 1.0.0 (desktop main) captures a rectangle of the calling window as a PNG. The window is the call's own, never an input, and the capture goes through `doric.windows/v1.capture`; its input, answer and errors are in the [README](../../bundles/features/papercraft/README.md#papercraftsnapshotv1-100--a-windows-capture-of-itself) ([src/contracts/index.ts](../../bundles/features/papercraft/src/contracts/index.ts), [src/desktop/snapshot.ts](../../bundles/features/papercraft/src/desktop/snapshot.ts)).

### Module cache and serving

- Before a library or an export loads, the window reads the module's bytes through `papercraft.programs/v1.read` and hands them to `papercraft.cache/v1.ensure` ([src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts)).
- `papercraft.cache/v1` 1.0.0 (desktop main; [README](../../bundles/features/papercraft/README.md#papercraftcachev1-100--the-verified-module-cache)) writes each entry only once its SHA-256 matches, staged and moved into place, and answers which entries were `written`, `kept` or `failed`; it rejects only an input that does not parse. Its directory is `userData/papercraft/`, and the first call of each app session cuts it back from above 256 MiB to at most 128 MiB, oldest directories first ([src/contracts/cache.ts](../../bundles/features/papercraft/src/contracts/cache.ts), [src/desktop/cache.ts](../../bundles/features/papercraft/src/desktop/cache.ts), [app/desktop/doric/src/platform/app.ts](../../app/desktop/doric/src/platform/app.ts)).
- The frame imports the files from `doric://app/papercraft-modules/<dir>/<file>` ([app/desktop/doric/src/platform/protocol/handler.ts](../../app/desktop/doric/src/platform/protocol/handler.ts)).

### The canvas window and its commands

- `papercraft.open-canvas/v2` 2.0.0 ([README](../../bundles/features/papercraft/README.md#papercraftopen-canvasv2-200--the-canvas-window)) takes the Project, the Thread and the program's identity, and opens or focuses the window at `/papercraft/:projectId/:threadId/:identity`, a path window with the integrated title bar ([src/desktop/commands.ts](../../bundles/features/papercraft/src/desktop/commands.ts)). The route stands alone, outside the workspace ([src/client/index.ts](../../bundles/features/papercraft/src/client/index.ts)).
- The window reads the Thread's fences through `chat.views/v1.watchFences` and shows any revision of the program ([src/client/surface/program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts)).
- Its command bar runs the canvas commands: the select, comment and pan tools, isolate and show all, the zoom commands, the revision choice and `papercraft.send/v1` (`CmdOrCtrl+Enter`); the keybindings apply only on the canvas route, and the commands and their keys are in the [README](../../bundles/features/papercraft/README.md#the-canvas-commands) ([src/contracts/index.ts](../../bundles/features/papercraft/src/contracts/index.ts), [src/client/commands.ts](../../bundles/features/papercraft/src/client/commands.ts)).
- Every call of the node and the window carries the Project scope, and the Thread when the scope has one ([src/contracts/index.ts](../../bundles/features/papercraft/src/contracts/index.ts), `callScopeOf`).
- The node and the window draw the same header over the canvas: the title and the revision on the left, and icon buttons on the right: open in the canvas window (the node only), the comment tool, pressed in comment mode and showing the count of what is pending and drafted, and, once a thread of the revision is resolved, the control that shows or hides resolved pins. The window adds a send button while there are drafts, since it has no prompt of its own. The node shows the buttons only while it is focused ([src/client/surface/preview-header.tsx](../../bundles/features/papercraft/src/client/surface/preview-header.tsx)).
- The node's focus stays with it: confirming or cancelling the open input, and cancelling or closing the open thread (`Esc` or its close button), hand focus to the canvas first. Once focus has left the node, the next press on it only focuses it, and the click is consumed. The window is always focused ([src/client/surface/frame-focus.ts](../../bundles/features/papercraft/src/client/surface/frame-focus.ts)).
- A dashed outline follows the pointer in any mode, focused or not: to the element a comment would land on while the comment tool is armed (`Alt` forces a free point), else to the element under the pointer. Its label names the target, and its pseudo-element when there is one, and shows only while no input or thread is open. Nothing is outlined while the canvas pans, and the outline goes when the pointer leaves the canvas ([src/client/surface/gestures.ts](../../bundles/features/papercraft/src/client/surface/gestures.ts), [overlays.tsx](../../bundles/features/papercraft/src/client/surface/overlays.tsx)).

### Comments

- A comment is written in an inline input at its pin, in a popover with the thread popover's surface; the send button sits inside the popover, beside the field and outside it. `Enter` confirms, `Shift+Enter` breaks the line and `Esc` cancels ([src/client/surface/comment-field.tsx](../../bundles/features/papercraft/src/client/surface/comment-field.tsx)). Only a confirmed note joins the Thread's composer stack (`chat.composer/v1`). The stack item, of kind `papercraft-program`, carries the target, the pin, the point, the identity as its title and, for a reply, the root it answers ([its shape](../../bundles/features/papercraft/README.md#other-exports-of-papercraftcontracts)), and draws as chat's comment line. It stays a draft until a prompt is sent: the desktop part's flush, registered with `chat.composer/v1.registerFlush`, turns each item into one `comments/v1.add` ([src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts), [src/desktop/comment-flush.ts](../../bundles/features/papercraft/src/desktop/comment-flush.ts), [src/contracts/index.ts](../../bundles/features/papercraft/src/contracts/index.ts)).
- In the conversation `Cmd/Ctrl+Enter` is chat's send, before which the open note joins the stack (`doric:prompt-send`); neither the canvas nor its fields answer the chord. In the canvas window it is `papercraft.send/v1`, which, like the window's send button, confirms the open note and sends the stack through `chat.send/v1`; without `chat.send/v1` the drafts stay ([src/client/surface/comment-flow.ts](../../bundles/features/papercraft/src/client/surface/comment-flow.ts), [src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts)).
- A target is `{ kind: 'papercraft-program', id: <identity>, revision, anchor }`. A click on a statement records `{ form: 'selector', selector: <statement>, label: <component, else tag>, x, y }`; a click on no statement, such as a portal, records a point. A program anchor records no `text` and no `index` ([src/client/anchor.ts](../../bundles/features/papercraft/src/client/anchor.ts)). A new comment targets the revision on screen; a reply targets its root's target.
- Comments are grouped into threads from the Thread log, through one shared `runtime.threads/v1.watchThread` per Thread per window, with `comments/v1.list` by kind as the fallback ([src/client/surface/thread-log.ts](../../bundles/features/papercraft/src/client/surface/thread-log.ts), [program-data.ts](../../bundles/features/papercraft/src/client/surface/program-data.ts)). Threads and drafts carry over revisions: every revision on screen shows every thread of the program, numbered by the root's place among all its roots ([src/client/surface/threads-view.ts](../../bundles/features/papercraft/src/client/surface/threads-view.ts)).
- A pin re-places itself through its anchor on the revision on screen: to the first node of the statement its selector names. When no node has that statement, it picks among the elements whose label equals the selector: the one whose text excerpt matches the anchor's `text`, then the one at the anchor's `index`, then the only candidate, then the one under or nearest the recorded point, else the first; never an element of another selector. A program anchor has no `text` or `index`, so for it only the last three steps apply ([src/client/surface/pin-geometry.ts](../../bundles/features/papercraft/src/client/surface/pin-geometry.ts)).
- When no element resolves, the pin sits at the point the anchor recorded, else at the draft's own point. A pin with neither is `detached`: stacked down the content's left edge, 28 units apart, still counted and openable, its tooltip saying why it sits apart ([src/client/surface/threads-view.ts](../../bundles/features/papercraft/src/client/surface/threads-view.ts), [pins-layer.tsx](../../bundles/features/papercraft/src/client/surface/pins-layer.tsx)).
- The canvas draws pins at the middle of the three sizes of `desktop/ui/comment-pin` ([packages/desktop/src/comment-pin.tsx](../../packages/desktop/src/comment-pin.tsx)). A pin shows its thread's state by its fill: a draft is dashed, an open thread primary with its reply count, a thread awaiting the reader orange with `?`, a resolved one muted with a green check, shown only while the reader shows resolved threads ([src/client/surface/pins-layer.tsx](../../bundles/features/papercraft/src/client/surface/pins-layer.tsx)).
- A pin that holds its first comment opens a thread popover: a header naming the pin and its anchor, a menu, resolve or reopen on a sent root, and close; the messages; and a reply field. A reply joins the stack with `inReplyTo`; drafts stay editable and removable. Resolving calls `comments/v1.resolve` on the root under the root's own `promptId` ([src/client/surface/thread-popover.tsx](../../bundles/features/papercraft/src/client/surface/thread-popover.tsx), [src/client/comment.ts](../../bundles/features/papercraft/src/client/comment.ts)).
- When the conversation asks to show a comment thread (`doric:comment-thread-open`), a canvas answers only when the target's kind and id are its own. A fence node opens the thread only when the target's `revision` is its own revision, or, when the target names none, when it draws the program's newest revision; the canvas window opens it on the revision on screen ([src/client/surface/preview-container.tsx](../../bundles/features/papercraft/src/client/surface/preview-container.tsx)).
- The agent receives the comments in `<comments>` under the target and answers each with `comment_reply`, as the `papercraft` skill tells it ([src/host/skills/papercraft.md](../../bundles/features/papercraft/src/host/skills/papercraft.md); the delivery is in [comments.md](comments.md#how-comments-reach-the-agent)).

### Files papercraft writes in the workspace

- Before any runner job, the host writes `.doric/papercraft/.gitignore` when it is absent, ignoring everything there but itself and `schemas/`; it never rewrites an existing one. Once per Project per host session, when `.doric/.gitignore` holds exactly `*`, it writes `.doric/artifacts/.gitignore` (`*`) if `.doric/artifacts/` exists and has none, then deletes `.doric/.gitignore`. A failed step is left for the next job ([src/host/ignore.ts](../../bundles/features/papercraft/src/host/ignore.ts)).
- The runner copy and each job's temporary folder live under `.doric/papercraft/`; the job folder is removed when the job ends ([src/host/sandbox.ts](../../bundles/features/papercraft/src/host/sandbox.ts)).

### `artifacts.*` rows and the desktop's `artifacts` folder

- A Thread's log may hold rows of the event types `artifacts.created/v1`, `artifacts.revised/v1`, `artifacts.applied/v1` and `artifacts.approved/v1`, which no installed bundle writes. The client claims them and gives no block for them, so they replay as nothing ([src/client/old-artifacts.ts](../../bundles/features/papercraft/src/client/old-artifacts.ts), [src/client/index.ts](../../bundles/features/papercraft/src/client/index.ts)).
- `userData/artifacts/` is a directory no part of Doric reads or writes. At every start, before any window opens, the desktop deletes it when it exists, removing a symlink there without following it ([app/desktop/doric/src/platform/artifacts-cleanup.ts](../../app/desktop/doric/src/platform/artifacts-cleanup.ts), [app.ts](../../app/desktop/doric/src/platform/app.ts)).

### Doric's own components

- A Doric bundle or package with a `.storybook/preview.tsx` harness at its root, for example [packages/desktop/.storybook/preview.tsx](../../packages/desktop/.storybook/preview.tsx), previews its CSF stories through `Export` like any Project's, under the same resolution rules; the read budget applies only when the host builds them ([src/host/harness.ts](../../bundles/features/papercraft/src/host/harness.ts), [src/sandbox/run.ts](../../bundles/features/papercraft/src/sandbox/run.ts)).
