## Summary

Spec 1 changes 24 of the 31 bundles, by the spec's count, and adds two. The user decided that the same spec also brings the documentation in line with the result (OD21, OD22, OD24): the architecture documents are rewritten in English, every implemented feature gets a feature doc, every bundle gets an `AGENTS.md`, and `GROUNDING.md` is retired. By the user's later decisions, the file is deleted with no pointer (OD56), every living document describes only the present and can be read on its own (OD57), and every `AGENTS.md` instructs (OD58). That is phase 12. It writes or rewrites about 106 files, with one agent per file and one review per file, after the code phases are committed on `feat/bundle-isolation` (decision 34: the branch merges to `main` once, at the end).

This document says what is written, from which sources, by whom, in which order, and how the result is accepted. It designs no code.

## How to read this document

- **People.** "The user" is the product owner who made the decisions. "The author" wrote this document. "An agent" is a coding agent that works on this repository.
- **What the concept defines.** Bundle, contract, slot, the shell, Spec 1 and Spec 2 are defined in the concept's [Background](../features/bundle-isolation.md#background), which also lists the 31 bundles.
- **`GROUNDING.md`.** A file of 3,430 lines at the repository root that calls itself "the repository validity contract" and that an agent must read before any work (`AGENTS.md:3-8`). It holds a description of the whole system and three things that are not description:
  - the _order of authority_: the list that says which source wins when two disagree (`GROUNDING.md:9-27`);
  - ten _hard constraints_, HC-001 to HC-010: gates at which an agent stops and asks the user (`GROUNDING.md:3319-3416`). HC-001 makes reading the file itself a gate. HC-002 says that the current code, manifests and tests win over stale documentation;
  - nine _convention parameters_, CP-001 to CP-009: defaults an agent follows unless the task gives a reason not to (`GROUNDING.md:3418-3430`).
- **The kinds of document.** A _feature doc_ (`docs/features/<feature>.md`) is the living description of one feature. A _spec_ (`docs/designs/<topic>.md`) is the dated document of one change and is not rewritten afterwards. An _architecture document_ (`docs/architecture/`) describes a mechanism of the platform. An `AGENTS.md` holds instructions for agents that change the code under its directory.
- **Stage N** names a step of the migration that moved the application into bundles; the steps are recorded in `docs/architecture/bundles/migration.md`.

## Problem

- **Two descriptions of one system, neither current.** `GROUNDING.md` describes the system, and so do the 35 documents under `docs/architecture/`. 28 of the 35 open with a status line that calls them proposals and names `GROUNDING.md` as the contract of the implementation. The architecture documents are in Portuguese; every other document and the code are in English. Spec 1 makes statements false in about twenty of the 35 and in about 54 lines of `GROUNDING.md`.
- **Most features have no document.** `docs/features/` holds ten feature docs. The inventory below lists 36 features; for 26 of them the description exists only as paragraphs of `GROUNDING.md` and as READMEs.
- **Rules for changing a bundle are written for three bundles.** Seven `AGENTS.md` files exist, three of them in bundles (`layout`, `chat`, `settings`), and those three repeat one another: nine of their sentences of twelve words or more appear in two or three of them.
- **The gate file is a description.** The hard constraints an agent must obey are at the end of a 3,430-line description that goes stale with every change.

## Goals

- **G15.** Every living document under `docs/architecture/` describes the state after Spec 1. None says it is a proposal, and a search of them finds no removed contract id and no old slot name. They describe only what is implemented: no earlier name, no removed feature, no migration and no link to a dated record (OD57). They are in English. By OD24, 25 documents are rewritten in place and one is new, `docs/architecture/bundles/boundaries.md`; the records, the retired designs, the proposal and the four folded documents are not living ([How the rewrite treats each kind](#how-the-rewrite-treats-each-kind)).
- **G16.** Every feature of the [Feature inventory](#feature-inventory) has a feature doc in the format that section gives, with the status `implemented` and no Evolution section (OD57), and every one of the 33 bundles is named by at least one of them.
- **G17.** `GROUNDING.md` is deleted, with no pointer left (OD56): every row of the retirement ledger is closed by a reviewer; the hard constraints and the convention parameters are in the root `AGENTS.md` under their ids; and no tracked file outside `docs/designs/` mentions the file, which a search of the whole repository confirms ([criterion 5](#acceptance-of-the-documentation-phase)). Its last full text is reachable only through Git history, at `ebbf8f94`, and through the ledger ([Retiring the grounding file](#retiring-the-grounding-file)).
- **G18.** Every bundle has an `AGENTS.md` that instructs (OD58): it tells an agent what to do and what not to do in the bundle (its function, its conventions and invariants, the commands that verify a change, and the files not edited by hand), and it links `bundles/AGENTS.md`, where the rules common to every bundle are. Two measures, because one test cannot decide both. A test decides that the file exists, has its four headings and links the common file. The review of step 12(c) decides that every sentence is a rule and that no common rule is restated in it ([Agent instruction files](#agent-instruction-files)).

- **The design of the code phases.** It is in the concept and in the spec.

## How the documentation agents work

The procedure the spec prescribes for steps 12(b) and 12(c). OD22 has sub-agents conduct the work; the rules below are what makes a hundred documents written in parallel agree with the code and with one another.

- **Who runs it.** The work is run with the coding workflow that the `default` bundle ships as a skill (`bundles/runtime/default/src/skills/coding-workflow/SKILL.md`). A coordinator, a Thread the user starts, creates one child Thread per unit of work and gives it its instruction; the user sees every child and can stop it. The writers are the workflow's `docs` agent (`bundles/runtime/default/src/host/agents/docs.md`) and the reviewers its `review` agent (`bundles/runtime/default/src/host/agents/review.md`). A reviewer never sees the writer's conversation: it is given the repository, the document's path and its lens.
- **Review, lens, severity.** A review reads one document from one fixed point of view, called a lens, each with its own list of checks (`review.md:28-36`). The Docs lens assumes that the documentation is stale until the code shows otherwise: it compares each statement with the changed files and reports a divergence between the code and the document as drift (`review.md:36`). A finding has one of three severities: Blocker (the work cannot proceed, or would be wrong), Major (a gap to close before proceeding) and Nit (minor) (`review.md:27`).
- **One document per agent.** The unit of work is one file: one feature doc, one architecture document, or one `AGENTS.md`. An agent writes that file and no other. The spec carries the assignment table: every file of phase 12 has exactly one writer.
- **Files with many contributors have one writer too.** The overview `bundles.md`, the map `feature-split.md`, the root `AGENTS.md`, the root `README.md` and the ledger are each written by one agent in step 12(d) or 12(e), after the others, and one agent deletes `GROUNDING.md` in step 12(e). An agent that needs a change in a file it does not own (a link from a README, a row in the map, a sentence in another feature doc) returns it as a requested edit, and the owner of that file applies it. The READMEs of a bundle are edited by one agent per bundle folder, in step 12(c).
- **One commit to read.** Every agent of a step reads the code at the same commit, the tip of `feat/bundle-isolation` after the last code phase of Spec 1 is committed. In the spec's order that is phase 10: phase 11 is committed earlier, as steps 11(a) and 11(b). By decision 34 the branch merges to `main` only once, at the end, so phase 12 does not wait for a merge. The commit is named in the phase's report; a living document does not name it (OD57).
- **What a feature-doc agent is given:** the template; its row of the [Feature inventory](#feature-inventory); the manifests, the contracts modules, the READMEs and the tests of the bundles in that row; the specs and architecture documents the row names; the ledger rows assigned to the feature, as line ranges of the frozen `GROUNDING.md`; the entries of `implementation-decisions.md` that name the feature; and the existing feature doc, if there is one. It does not read `GROUNDING.md` whole.
- **What an architecture-document agent is given:** the current document, the spec of Spec 1, the code of the mechanism the document describes, and its ledger rows.
- **What an `AGENTS.md` agent is given:** the directory's code layout, the root `AGENTS.md`, the document of the boundary rules (`docs/architecture/bundles/boundaries.md`), the lint and test configuration, the existing file where there is one, the ledger rows assigned to the file, where there are any, and the `project.json` of each Nx project under the directory, for the Verify section (OD58). For a bundle's file it is also given the common `bundles/AGENTS.md`, the required form, the bundle's manifest and its folders.
- **The template** is the format of [Feature inventory](#feature-inventory). Two parts have a fixed rule. _Status_ is `implemented`. _Decisions_ states only decisions that are recorded somewhere, each in full and as the rule it sets, so that the reader needs no other document; it links no spec, no entry of `implementation-decisions.md` and no pull request (OD57). The agent returns the record of each decision with its result, and the reviewer checks the decision against it; where none is recorded the section says "None recorded.", and the agent does not infer a decision from the code. The document has no Evolution section (OD57); up to version 7 it had one, with a dated entry per change and the entry of this phase.
- **Every statement of current behavior is tied to the code.** In the document, a statement names the file that implements it, as a link, and the contract id and version where it describes a contract, as `docs/features/cwd-tool.md` does. Line numbers stay out of a living document, because they go stale with the next edit. With its result, the agent returns an evidence table: each statement of "Current behavior and contracts", its `file:line` at the commit, and whether the agent read the code or ran a test. A statement with no row is removed.
- **Disagreements between sources are reported, not resolved in silence.** The order of evidence is: the code and its tests at the commit; the manifests and contracts modules; the latest spec; an existing feature doc; a README; an architecture document; `GROUNDING.md`. The document says what the code does. Each disagreement the agent meets goes into a conflicts list returned with the result: the two sources, what each says, what the code does, and the `file:line`. Three cases have a rule. (1) A document is stale against the code: the new document follows the code. (2) The code contradicts a decision the user made, recorded in a spec, a feature doc or `implementation-decisions.md`: the document states the behavior, with no mark and no link to the decision (OD57), and the case goes to the user in the phase's report, since it may be a defect. (3) `GROUNDING.md` states something for which the agent finds no code: the ledger row stays open, and only the reviewer may mark it obsolete, with evidence.
- **Each document gets one review through the Docs lens**, by an agent that did not write it. The reviewer checks every row of the evidence table against the code, the links, the format, the rule for Decisions, the ledger rows assigned to the document, and that the text is plain. It also checks the rules of OD57: no sentence describes the past, names an earlier name or a removed feature, or needs another document to be understood, and no link sends the reader to a dated record. For an `AGENTS.md` it checks OD58: every sentence is a rule, the Verify commands run at the commit, and every file a command writes is under Generated files. The searches of criteria [5, 11 and 12](#acceptance-of-the-documentation-phase), run on the one document, are part of the review. Findings come by severity; the writer answers each with a fix or with the evidence that it is wrong. A document is accepted when no Blocker and no Major finding is open.
- **One review of the set**, in step 12(d), reads the feature docs and the architecture documents together for the same fact stated twice or stated differently, and for a bundle, a contract or a slot that no document describes. One home per fact: a contract is described in full in the feature doc of the bundle that provides it, a mechanism in its architecture document; another document that needs the fact states it in its own words at the grain it needs and links the home (OD57), and this review checks that the two agree. Up to version 7 every other document only linked.

## Steps of phase 12, and when it runs

The phase has five steps.

- **(a) The retirement ledger.** `GROUNDING.md` is cut into blocks, each with its destination ([Retiring the grounding file](#retiring-the-grounding-file)). It reads only the frozen file, so it may start before the code phases end.
- **(b) One document per agent, in parallel:** the feature docs of the inventory and the living documents of `docs/architecture/`, in English, written to the state the code phases left, present only and readable on their own (OD57). The step starts with the pilot of [Size](#size) and with the move of the concept's text to `docs/designs/bundle-isolation-concept.md`, in the same change as the fix of every link that refers to the concept (OD62, [How the rewrite treats each kind](#how-the-rewrite-treats-each-kind)); the records of `docs/architecture/` have their mentions of `GROUNDING.md` replaced in this step.
- **(c) Agent instruction files and READMEs:** the common `bundles/AGENTS.md` first, then the `AGENTS.md` of each of the 33 bundles and the other nested files, each in the form of OD58; and the READMEs, one agent per folder, each brought to the present only (OD57).
- **(d) The files with many contributors,** each by one writer: the overview `bundles.md`, the bundle map `feature-split.md` and the root `AGENTS.md`. The review of the whole set runs here.
- **(e) Deletion** (OD56): every mention of `GROUNDING.md` outside `docs/designs/` is removed, the ledger's owner closes its last rows, `GROUNDING.md` is deleted, and the checks of [Acceptance](#acceptance-of-the-documentation-phase) are run.

From phase 0 of Spec 1, `GROUNDING.md` is frozen: phase 0 puts a notice at its top that names the spec and HC-002, and no later phase edits its body. The repository's rule that each step updates `GROUNDING.md` (`docs/architecture/bundles/migration.md:112`, `AGENTS.md:45-48`) ends there, and so do the clauses of `docs/architecture/bundles/implementation-decisions.md:3` and `docs/architecture/bundles.md:3` that have it updated phase by phase.

- Phase 12 is a phase of its own and the last before Close. It is last because the documents describe the result, and every code phase changes the result: a document written earlier is written twice. It is separate from Close because of its size and because each of its documents needs a review against the committed code at that tip.
- **Whether documentation can run per phase instead.** Three courses were weighed, and OD24 takes the first.
  - _(a) After the code phases, as one phase._ Every agent reads the code once, at one commit. The cost: from phase 0 to phase 12 `GROUNDING.md` is frozen and wrong wherever a code phase changed the system. The author's search finds 54 such lines; the notice of phase 0 says so and names HC-002, by which the code wins.
  - _(b) Per phase._ Each code phase writes the feature docs of the bundles it changes. Seventeen bundles change in code in ten phases, and `chat` is edited by four of them; its feature docs would be written four times, by agents whose task is the code.
  - _(c) Two waves._ The features Spec 1 leaves alone are documented while the code phases run, and the rest afterwards. It shortens the calendar. It rests on "expected not to change", which is not verified for six bundles ([Size and risk](../features/bundle-isolation.md#size-and-risk)), and it puts documentation agents and code agents in the same bundle folders at the same time.
  - **Decided: (a)** (OD24), with one part that may start early: step 12(a), the ledger, reads only the frozen `GROUNDING.md`.
