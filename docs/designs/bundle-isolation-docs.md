## Summary

Spec 1 changes 24 of the 31 bundles, by the spec's count, and adds two. The user decided that the same spec also brings the documentation in line with the result (OD21, OD22, OD24): the architecture documents are rewritten in English, every implemented feature gets a feature doc, every bundle gets an `AGENTS.md`, and `GROUNDING.md` is retired. That is phase 12. It writes or rewrites about 106 files, with one agent per file and one review per file, after the code phases are committed on `feat/bundle-isolation` (decision 34: the branch merges to `main` once, at the end).

This document says what is written, from which sources, by whom, in which order, and how the result is accepted. It designs no code.

## How to read this document

- **People.** "The user" is the product owner who made the decisions. "The author" wrote this document. "An agent" is a coding agent that works on this repository.
- **What the concept defines.** Bundle, contract, slot, the shell, Spec 1 and Spec 2 are defined in the concept's [Background](../features/bundle-isolation.md#background), which also lists the 31 bundles.
- **`GROUNDING.md`.** A file of 3,430 lines at the repository root that calls itself "the repository validity contract" and that an agent must read before any work (`AGENTS.md:3-8`). It holds a description of the whole system and three things that are not description:
  - the _order of authority_: the list that says which source wins when two disagree (`GROUNDING.md:9-27`);
  - ten _hard constraints_, HC-001 to HC-010: gates at which an agent stops and asks the user (`GROUNDING.md:3319-3416`). HC-001 makes reading the file itself a gate. HC-002 says that the current code, manifests and tests win over stale documentation;
  - nine _convention parameters_, CP-001 to CP-009: defaults an agent follows unless the task gives a reason not to (`GROUNDING.md:3418-3430`).
- **The kinds of document.** A _feature doc_ (`docs/features/<feature>.md`) is the living description of one feature. A _spec_ (`docs/designs/<topic>.md`) is the dated document of one change and is not rewritten afterwards. An _architecture document_ (`docs/architecture/`) describes a mechanism of the platform. An `AGENTS.md` holds instructions for agents that change the code under its directory.
- **Stage N** names a step of the migration that moved the application into bundles; the steps are recorded in `docs/architecture/bundles/migration.md`.

## Problem

- **Two descriptions of one system, neither current.** `GROUNDING.md` describes the system, and so do the 35 documents under `docs/architecture/`. 28 of the 35 open with a status line that calls them proposals and names `GROUNDING.md` as the contract of the implementation. The architecture documents are in Portuguese; every other document and the code are in English. Spec 1 makes statements false in about twenty of the 35 and in about 54 lines of `GROUNDING.md`.
- **Most features have no document.** `docs/features/` holds ten feature docs. The inventory below lists 36 features; for 26 of them the description exists only as paragraphs of `GROUNDING.md` and as READMEs.
- **Rules for changing a bundle are written for three bundles.** Seven `AGENTS.md` files exist, three of them in bundles (`layout`, `chat`, `settings`), and those three repeat one another: nine of their sentences of twelve words or more appear in two or three of them.
- **The gate file is a description.** The hard constraints an agent must obey are at the end of a 3,430-line description that goes stale with every change.

## Goals

- **G15.** Every living document under `docs/architecture/` describes the state after Spec 1. None says it is a proposal, and a search of them finds no removed contract id and no old slot name. They are in English. By OD24, 25 documents are rewritten in place and one is new; the records, the retired designs, the proposal and the four folded documents are not living ([How the rewrite treats each kind](#how-the-rewrite-treats-each-kind)).
- **G16.** Every feature of the [Feature inventory](#feature-inventory) has a feature doc in the repository's format, with the status `implemented`, and every one of the 33 bundles is named by at least one of them.
- **G17.** `GROUNDING.md` is retired: every block of the retirement ledger has a destination that a reviewer confirmed, or is marked obsolete with its evidence; the hard constraints and the convention parameters are in the root `AGENTS.md` under their ids; no file cites `GROUNDING.md` except the dated specs, the documents of `docs/architecture/` that are not rewritten (the three records, the retired designs, the proposal and the four folded documents), the pointer itself, the concept and this plan, whose evidence is pinned to a commit, and Evolution entries ([Retiring the grounding file](#retiring-the-grounding-file)).
- **G18.** Every bundle has an `AGENTS.md` that states the bundle's function and the rules only that bundle has, and that links `bundles/AGENTS.md`, where the rules common to every bundle are. Two measures, because one test cannot decide both. A test decides that the file exists, has its Function heading and links the common file. The review of step 12(c) decides that no common rule is restated in it ([Agent instruction files](#agent-instruction-files)).

## Non-goals

- **Changing what a hard constraint says.** The documentation work moves the hard constraints and the convention parameters to the root `AGENTS.md` with their ids and their text. Only HC-001, which names `GROUNDING.md`, must change; the others move word for word (OD24).
- **Rewriting dated specs.** The specs under `docs/designs/` keep their text, including their citations of `GROUNDING.md` (OD24).
- **Any change to code.** Phase 12 touches Markdown files, three story fixtures and one test ([Acceptance of the documentation phase](#acceptance-of-the-documentation-phase)).
- **The design of the code phases.** It is in the concept and in the spec.

  - _Feature docs:_ ten exist. One is this concept; the other nine hold 1,694 lines. The [Feature inventory](#feature-inventory) proposes 36: the ten, revised, and 26 new ones.
  - _`AGENTS.md`:_ seven files, 461 lines; three belong to bundles. By OD24 every bundle gets one: 30 new files, 28 for the existing bundles that have none and two for `workspace` and `account`. The author adds one common file, `bundles/AGENTS.md`, so that a rule common to every bundle has one home: 38 files after Spec 1, 31 of them new. The author expects 10 to 20 lines for a bundle with no layering rules of its own, about 500 new lines in all; no such file was drafted ([A12](#riskiest-assumptions)). The copying the owner asked to prevent exists today: the seven files hold 81 sentences of twelve words or more, and nine of them appear in two or three of the bundle files ([Agent instruction files](#agent-instruction-files)).
  - _`GROUNDING.md`:_ 3,430 lines to distribute. 2,950 of them are one section, "Product Direction", with three sub-headings; it is cut into about forty blocks ([Retiring the grounding file](#retiring-the-grounding-file)).
  - _References to `GROUNDING.md`:_ 34 architecture documents (54 lines), two living feature docs (57 lines), the root and the host `AGENTS.md` (8 lines), the root `README.md` (1), two bundle READMEs (3) and three story fixtures (3) are updated. Fourteen of the fifteen specs under `docs/designs/` cite it in 89 lines and are not rewritten (OD24).
  - _Work units:_ about 106 files, each written by one agent and reviewed by another: 36 feature docs; 26 architecture documents (25 rewritten in place, and the new document of the boundary rules); 38 `AGENTS.md` files (30 new for bundles, the common file and the seven existing); the banners of the four folded documents; the ledger and the pointer. The 52 READMEs are edited by one agent per folder and are not counted. Version 3 counted about eighty before OD24: the per-bundle files add 29, and the folding removes four rewrites and the question of a second new document.
- **Cost.** No estimate of time or of model usage exists. Each file is at least one writing thread and one review thread, so the phase is at least 212 agent threads, plus the answers to findings and the review of the set. Step 12(b) therefore starts with a pilot: five documents, one of each kind (a new feature doc, a revised one, a rewritten architecture document, a bundle `AGENTS.md`, the common file), written and reviewed before the rest start. The pilot records the time and the model usage per document, and the phase's report multiplies them. If the pilot shows that the template or the minimum is wrong, it is corrected before 100 more files use it.

- **New documents.** The boundary rules (M1–M11, the checks, the exceptions file) have no document and get one. ## How the documentation agents work

The procedure the spec prescribes for steps 12(b) and 12(c). OD22 has sub-agents conduct the work; the rules below are what makes a hundred documents written in parallel agree with the code and with one another.

- **Who runs it.** The work is run with the coding workflow that the `default` bundle ships as a skill (`bundles/runtime/default/src/skills/coding-workflow/SKILL.md`). A coordinator, a Thread the user starts, creates one child Thread per unit of work and gives it its instruction; the user sees every child and can stop it. The writers are the workflow's `docs` agent (`bundles/runtime/default/src/host/agents/docs.md`) and the reviewers its `review` agent (`bundles/runtime/default/src/host/agents/review.md`). A reviewer never sees the writer's conversation: it is given the repository, the document's path and its lens.
- **Review, lens, severity.** A review reads one document from one fixed point of view, called a lens, each with its own list of checks (`review.md:28-36`). The Docs lens assumes that the documentation is stale until the code shows otherwise: it compares each statement with the changed files and reports a divergence between the code and the document as drift (`review.md:36`). A finding has one of three severities: Blocker (the work cannot proceed, or would be wrong), Major (a gap to close before proceeding) and Nit (minor) (`review.md:27`).
- **One document per agent.** The unit of work is one file: one feature doc, one architecture document, or one `AGENTS.md`. An agent writes that file and no other. The spec carries the assignment table: every file of phase 12 has exactly one writer.
- **Files with many contributors have one writer too.** The overview `bundles.md`, the map `feature-split.md`, the root `AGENTS.md`, the root `README.md`, the ledger and the pointer are each written by one agent in step 12(d) or 12(e), after the others. An agent that needs a change in a file it does not own (a link from a README, a row in the map, a sentence in another feature doc) returns it as a requested edit, and the owner of that file applies it. The READMEs of a bundle are edited by one agent per bundle folder, in step 12(c).
- **One commit to read.** Every agent of a step reads the code at the same commit, the tip of `feat/bundle-isolation` after the last code phase of Spec 1 is committed. In the spec's order that is phase 10: phase 11 is committed earlier, as steps 11(a) and 11(b). By decision 34 the branch merges to `main` only once, at the end, so phase 12 does not wait for a merge. The commit is named in the Evolution entry the agent writes.
- **What a feature-doc agent is given:** the template; its row of the [Feature inventory](#feature-inventory); the manifests, the contracts modules, the READMEs and the tests of the bundles in that row; the specs and architecture documents the row names; the ledger rows assigned to the feature, as line ranges of the frozen `GROUNDING.md`; the entries of `implementation-decisions.md` that name the feature; and the existing feature doc, if there is one. It does not read `GROUNDING.md` whole.
- **What an architecture-document agent is given:** the current document, the spec of Spec 1, the code of the mechanism the document describes, and its ledger rows.
- **What an `AGENTS.md` agent is given:** the directory's code layout, the root `AGENTS.md`, the document of the boundary rules, the lint and test configuration, and the existing file where there is one. For a bundle's file it is also given the common `bundles/AGENTS.md`, the required form, the bundle's manifest and its folders.
- **The template** is the format of [Feature inventory](#feature-inventory). Three fields have a fixed rule. _Status_ is `implemented`. _Decisions_ lists only decisions that are recorded somewhere, each with a link to the spec, the entry of `implementation-decisions.md` or the pull request that records it; where none is recorded it says "none recorded", and the agent does not infer a decision from the code. _Evolution_ has one dated entry per change the agent can source from a spec or a pull request, and ends with the entry of this phase, which names the commit the document was checked against.
- **Every statement of current behavior is tied to the code.** In the document, a statement names the file that implements it, as a link, and the contract id and version where it describes a contract, as `docs/features/cwd-tool.md` does. Line numbers stay out of a living document, because they go stale with the next edit. With its result, the agent returns an evidence table: each statement of "Current behavior and contracts", its `file:line` at the commit, and whether the agent read the code or ran a test. A statement with no row is removed.
- **Disagreements between sources are reported, not resolved in silence.** The order of evidence is: the code and its tests at the commit; the manifests and contracts modules; the latest spec; an existing feature doc; a README; an architecture document; `GROUNDING.md`. The document says what the code does. Each disagreement the agent meets goes into a conflicts list returned with the result: the two sources, what each says, what the code does, and the `file:line`. Three cases have a rule. (1) A document is stale against the code: the new document follows the code. (2) The code contradicts a decision the user made, recorded in a spec, a feature doc or `implementation-decisions.md`: the document states the behavior and marks it as differing from that decision, and the case goes to the user, since it may be a defect. (3) `GROUNDING.md` states something for which the agent finds no code: the ledger row stays open, and only the reviewer may mark it obsolete, with evidence.
- **Each document gets one review through the Docs lens**, by an agent that did not write it. The reviewer checks every row of the evidence table against the code, the links, the format, the rule for Decisions, the ledger rows assigned to the document, and that the text is plain. Findings come by severity; the writer answers each with a fix or with the evidence that it is wrong. A document is accepted when no Blocker and no Major finding is open.
- **One review of the set**, in step 12(d), reads the feature docs and the architecture documents together for the same fact stated twice or stated differently, and for a bundle, a contract or a slot that no document describes. One home per fact: a contract is described in the feature doc of the bundle that provides it, a mechanism in its architecture document, and every other document links.

## Steps of phase 12, and when it runs

The phase has five steps.

- **(a) The retirement ledger.** `GROUNDING.md` is cut into blocks, each with its destination ([Retiring the grounding file](#retiring-the-grounding-file)). It reads only the frozen file, so it may start before the code phases end.
- **(b) One document per agent, in parallel:** the feature docs of the inventory and the living documents of `docs/architecture/`, in English, written to the state the code phases left. The step starts with the pilot of [Size](#size).
- **(c) Agent instruction files and README links:** the common `bundles/AGENTS.md` first, then the `AGENTS.md` of each of the 33 bundles.
- **(d) The files with many contributors,** each by one writer: the overview `bundles.md`, the bundle map `feature-split.md` and the root `AGENTS.md`. The review of the whole set runs here.
- **(e) Retirement:** every reference to `GROUNDING.md` is updated, and the file is reduced to a pointer.

From phase 0 of Spec 1, `GROUNDING.md` is frozen: phase 0 puts a notice at its top that names the spec and HC-002, and no later phase edits its body. The repository's rule that each step updates `GROUNDING.md` (`docs/architecture/bundles/migration.md:112`, `AGENTS.md:45-48`) ends there, and so do the clauses of `docs/architecture/bundles/implementation-decisions.md:3` and `docs/architecture/bundles.md:3` that have it updated phase by phase.

- Phase 12 is a phase of its own and the last before Close. It is last because the documents describe the result, and every code phase changes the result: a document written earlier is written twice. It is separate from Close because of its size and because each of its documents needs a review against the committed code at that tip.
- **Whether documentation can run per phase instead.** Three courses were weighed, and OD24 takes the first.
  - _(a) After the code phases, as one phase._ Every agent reads the code once, at one commit. The cost: from phase 0 to phase 12 `GROUNDING.md` is frozen and wrong wherever a code phase changed the system. The author's search finds 54 such lines; the notice of phase 0 says so and names HC-002, by which the code wins.
  - _(b) Per phase._ Each code phase writes the feature docs of the bundles it changes. Seventeen bundles change in code in ten phases, and `chat` is edited by four of them; its feature docs would be written four times, by agents whose task is the code.
  - _(c) Two waves._ The features Spec 1 leaves alone are documented while the code phases run, and the rest afterwards. It shortens the calendar. It rests on "expected not to change", which is not verified for six bundles ([Size and risk](../features/bundle-isolation.md#size-and-risk)), and it puts documentation agents and code agents in the same bundle folders at the same time.
  - **Decided: (a)** (OD24), with one part that may start early: step 12(a), the ledger, reads only the frozen `GROUNDING.md`.

## Risks

- **R14 — The rewritten documents describe the spec and not the code.** Phase 12 writes about a hundred documents after ten phases of code changes, and its sources include documents that are already wrong. Mitigation: it runs after the code phases have merged, and every statement of current behavior carries its file, the agent returns the line for each, and a second agent checks them against the code ([How the documentation agents work](#how-the-documentation-agents-work)).
- **R16 — Something true in `GROUNDING.md` is lost in the retirement.** It is the only place where some behavior is written down. Mitigation: the ledger covers every line of the file; a block is closed only when a reviewer finds its content in the destination, or when it is marked obsolete with the evidence; the last full text stays reachable at the commit the pointer names.
- **R17 — Two documents state one fact differently.** About a hundred documents are written in parallel, and a contract or a slot is relevant to several of them. Mitigation: one home per fact (a contract is described in the feature doc of the bundle that provides it, a mechanism in its architecture document, and the others link); one review of the whole set in step 12(d), for duplicates and contradictions.
- **R18 — Decisions are invented.** An agent asked to fill a Decisions section for a feature that never had a concept can infer "decisions" from what the code does. Mitigation: the section lists only decisions that are recorded somewhere, each with its link; otherwise it says "none recorded".
- **R19 — The frozen `GROUNDING.md` misleads during the code phases.** For the length of the code phases, 2 to 11, the first document an agent is told to read is wrong in about 54 lines. Mitigation: the notice of phase 0 names the spec and HC-002, by which the code wins; the alternatives were weighed under [Steps of phase 12, and when it runs](#steps-of-phase-12-and-when-it-runs), and OD24 keeps this course.
- **R20 — The hard constraints lose force in the move.** A gate that was a document of its own becomes a section of `AGENTS.md`. Mitigation: the ids and the text are kept (OD24), HC-001 is reworded to name the root `AGENTS.md`, and the phase's acceptance checks for the nineteen ids.
- **R21 — Thirty-three instruction files repeat one another, or say nothing, or go stale.** The three bundle files that exist already repeat nine sentences. Mitigation: the file holds only what no other file states (the function and the bundle's own rules) and links the manifest, the exceptions file and the tests in place of restating them; every common rule is in `bundles/AGENTS.md`; a test in CI decides presence, the Function heading and the link; review decides the rest ([Agent instruction files](#agent-instruction-files)). - **R22 — A folded document is read as current.** The four files keep their text ([X28](#conflicts)), and `chat.md` keeps 304 lines of which Spec 1 makes many false. Mitigation: the banner is the file's first line and names the feature doc and the date; the index of `bundles.md` lists the four under records; the root `AGENTS.md` names the feature docs as required context, and no living document links a folded one.
