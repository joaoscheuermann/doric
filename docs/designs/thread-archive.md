## Problem

Every Thread of the selected Project is drawn in the sidebar tree, recursively (`bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx:284-298`, `bundles/desktop/layout/src/client/domain/thread-tree.ts:58-69`). Agents spawn many agent threads; each stays in the tree after its work ends, under its parent, for as long as the Project exists. The reader cannot hide one: the only way to remove a Thread is to delete it, and deleting an agent thread is refused (`bundles/runtime/runtime/src/host/domain/service.ts:1386`; the layout offers no Delete on such a row, `bundles/desktop/layout/src/client/domain/thread-kind.ts:97-105`). Main threads stay in the tree however long they go unused.

Deleting is not an answer: the parent's conversation links to its children through the spawn card, which opens a child only while the child is in the layout's tree (`bundles/desktop/chat/src/client/hooks/use-delegated-source.ts:13-25`). The UI redesign deferred archiving for this reason (UR9, `docs/features/ui-redesign.md:135`, `docs/designs/ui-redesign.md:80`).

The tree has no notion of "done": there is no finished state, and none is to be added (U2). The runtime knows when a turn ends, but it has no timer, no sweep and no record of what a window shows.

## Goals

- **G1.** The Thread record and its stored document carry an archive time and a pin flag; existing documents stay valid with neither (U7, U9).
- **G2.** The runtime archives an agent thread 30 s to 40 s after its turn ends (D13), and un-archives it on any new activity, under the exceptions of U3 (U2, U3, U13, U14).
- **G3.** The runtime archives a main thread and its subtree after the configured inactivity, when nothing in the subtree is pending (U4, U5).
- **G4.** Windows report the Threads they show; the runtime never auto-archives a Thread while a view of it is held, across generation handovers (U3).
- **G5.** `runtime.threads/v1` 1.8.0 adds `archiveThread`, `restoreThread`, `setThreadPinned` and `viewThread`, desktop-exposed; an archived agent thread can be deleted (U8, U9, U11).
- **G6.** The sidebar draws a Chat tab and an Archived tab, with the filtering, dimmed context rows, date sections, hover actions, context-menu entries, toast and delete warning of U1, U6, U8–U10, U16.
- **G7.** The host configuration carries `threads.autoArchive`, edited in a new Settings section (U12).
- **G8.** The spawn card keeps opening every child that exists, archived or not (U7).

## Non-goals

- No new Thread state and no "finished" event (U2).
- No change to how a Thread runs, queues or is delivered to its parent; archiving never stops, pauses or cancels work.
- No counter badge on the Archived tab (U1).
- No unread indicator on rows. Unread results only block the main-thread rule (U4, U5).
- No pinning to the top: a pinned Thread keeps its place in the tree.
- No presence from REST or Socket.IO clients: only desktop windows report views (U3 names the desktop app). A REST client's reads hold no view.
- No REST routes for archive, restore or pin. U8–U11 are sidebar actions; the four methods are desktop-exposed only. REST clients see `archivedAt` and `pinned` on the records they already read whole (`GET /threads/:id`, `bundles/foundation/transport/src/host/routes/threads.ts:290-296`), and `DELETE /threads/:id` deletes an archived agent thread through the same `deleteThread` (D16).
- No change to `DELETE /threads/:id` answering `204` when the host refuses with `forbidden` (`bundles/foundation/transport/src/host/routes/threads.ts:590-601`). That bug exists today, independent of archiving, and is left to a separate fix.
- No auto-archive in a terminated Project. The host never makes a terminated Project live again (`bundles/runtime/runtime/src/host/domain/service.ts:461-468`), and the sweep reads live Projects only; every Project that is not terminated is live after boot (`bundles/runtime/runtime/src/host/lifecycle.ts:55-70`), so U4's N-day rule covers every Project still in use. A terminated Project's tree is final; its Threads can be archived by hand.
- No failed marker on rows. The Figma Chat column draws a red "Falhou" label on a failed row (`473:15631`); it is not among U1–U16 and is out of scope (Q3, decided).
- No terminal rows in the Archived tab.
- No translation layer: the app has no i18n library and its UI text is English (D21).

## Requirements

The user's decisions, restated. U3, U5 and U11 carry the second round's decisions U13–U16 where they apply.

- **U1.** The sidebar gets two icon-only tabs above the Thread tree: Chat (lucide `message-circle`) and Archived (lucide `archive`), with tooltips. Thread search (⌘F) applies to both tabs. No counter badge on the Archived icon.
- **U2.** An agent thread is archived automatically 30 s after a turn ends (the Thread back to `ready`, `prompt.finished` written; no finished state exists and none is added). Any new activity — a parent's send or new task, Continue/Resume, Retry/restart — un-archives it automatically, back in its place under its parent; it is archived again 30 s after its next turn ends.
- **U3.** A Thread is never auto-archived while busy, failed, cancelled by the reader's stop (U13), waiting for action or input (an open question form included, U14), open on screen in any client (the desktop app reports open Threads to the host; archiving waits until the reader leaves), or pinned. The sub-agent rule never archives a main thread.
- **U4.** A main thread is archived manually, or automatically after N days without activity (a user message, an agent response, or any descendant running), only when nothing is pending: no failure, no waiting, no unread result, not pinned. N is 1 day, 7 days (default), 30 days or never.
- **U5.** An unread result is a last turn that ended after the last time a user opened that Thread. A result that arrives while the reader has the Thread open counts as read (U15).
- **U6.** A non-archived descendant keeps its ancestor chain visible in the Chat tab; archived ancestors render dimmed with an archive icon.
- **U7.** The spawn card in the parent's conversation always opens the child, archived or not. Archived Threads therefore stay in the client's workspace store (`threadsByProject`); "archived" is a field on the Thread, and each tab filters on it.
- **U8.** Manual archive is a hover action on a row (an archive icon next to the existing plus). Archiving a parent archives its descendants. The standard sonner toast "Thread archived" with an Undo action confirms it; there is no confirmation dialog.
- **U9.** Pin is new in this change: a hover and context-menu action, and a pin icon on pinned rows. A pinned Thread is never auto-archived.
- **U10.** The Archived tab draws the real tree, grouped by archive date into Today / Last 7 days / Older. Only archived rows are interactive; non-archived ancestors drawn for context are dimmed and inert. Hovering an archived row offers Restore (back to its place, un-archived) and Delete.
- **U11.** Delete is permanent and deletes the whole subtree through the existing delete path. Today that path refuses an agent thread (`forbidden`) and a subtree that is not terminal; this change must allow deleting archived agent threads. The confirmation warns about descendants still shown in Chat (U16).
- **U12.** Settings gets an "Auto-archive" group with a toggle "Archive finished sub-agents" (on by default) and a choice "Archive inactive main threads after": 1 day / 7 days (default) / 30 days / Never, persisted in the host configuration as an optional strict sub-object, since the host archives.
- **U13.** (2026-11-17) "Cancelled" in U3 means the reader stopped the turn. A `cancelled` result written by removing a queued prompt, by closing a Thread or Project, or by any other abort does not block auto-archiving; neither does the Thread state `cancelled` of a closed Thread.
- **U14.** (2026-11-17) A turn that ends with an open question form counts as "waiting for action" until the reader answers it: never auto-archived meanwhile, by either rule.
- **U15.** (2026-11-17) A result that arrives while the reader has the Thread open counts as read: the viewed time is the last time a view started or ended.
- **U16.** (2026-11-17) Deleting from the Archived tab warns, in the confirmation dialog, with the number of descendants that are busy or pinned — still shown in Chat — that the delete removes too. The spec counts every non-archived descendant: busy and pinned ones are the descendants a manual archive leaves in Chat (D8), and a descendant new activity un-archived is in Chat too.
- **U17.** (2026-11-17, with the approval) Any activity brings an archived Thread back. A parent archived by hand while an agent child keeps running is un-archived, back in Chat, when the child's result is delivered to it.

## Design

### 1. Data model

#### 1.1 The public record (`runtime.threads/v1` 1.8.0)

`bundles/runtime/runtime/src/contracts/model.ts`, after `Thread.providerId` (`bundles/runtime/runtime/src/contracts/model.ts:207`):

```ts
export interface Thread {
  // … unchanged fields …
  /** 1.8.0: when the Thread was archived (ISO 8601); absent while not archived. */
  readonly archivedAt?: string;
  /** 1.8.0: true while the reader has it pinned; absent when not pinned. */
  readonly pinned?: boolean;
}
```

`threadSchema` (`bundles/runtime/runtime/src/contracts/model.ts:672-704`) gains, after `providerId`:

```ts
archivedAt: z.string().optional(),
pinned: z.boolean().optional(),
```

`ThreadOutcome` and `threadOutcomeSchema` (`bundles/runtime/runtime/src/contracts/model.ts:82-87,664-670`) do not change (D1).

#### 1.2 The stored document (`runtime.thread/v1` 1.3.0)

`threadDocumentSchema` (`bundles/runtime/runtime/src/contracts/storage.ts:78-144`, strict) gains `reason: z.literal('interrupted').optional()` in its strict `result` object (`bundles/runtime/runtime/src/contracts/storage.ts:103-111`) and, after `providerId` (`bundles/runtime/runtime/src/contracts/storage.ts:141`) and before `createdKey`:

```ts
/** runtime.thread/v1 1.3.0: present while archived. */
archive: z
  .object({
    at: iso,
    /** The archive batch; Undo and Restore act on it. */
    batch: z.uuid(),
  })
  .strict()
  .optional(),
/** 1.3.0: the last time an archive of this Thread was undone. */
restoredAt: iso.optional(),
/** 1.3.0: present (true) while pinned; removed on unpin. */
pinned: z.literal(true).optional(),
/** 1.3.0: the last time a view of it started or ended. */
viewedAt: iso.optional(),
```

`toThread` (`bundles/runtime/runtime/src/host/store/threads.ts:104-156`) maps `archive.at` to `archivedAt` and `pinned` as given; `restoredAt`, `viewedAt`, `archive.batch` and `result.reason` stay in the document, since `toThread` copies the result's four fields one by one (`bundles/runtime/runtime/src/host/store/threads.ts:122-131`). Existing documents carry none of the new fields and stay valid (D1).

#### 1.3 The reader's stop on the result (D23)

`ThreadStore.setResult` (`bundles/runtime/runtime/src/host/store/types.ts:237`) gains an optional third parameter: `setResult(id: string, result: ThreadOutcome, reason?: 'interrupted'): Promise<void>`. Its implementation (`bundles/runtime/runtime/src/host/store/threads.ts:939-948`) writes `result.reason` when `reason` is given. `finishJob` (`bundles/runtime/runtime/src/host/domain/runner.ts:369-394`) passes its own `reason` parameter as that argument. No other caller of `setResult` changes, so only the reader's stop writes the reason.

### 2. The rules (`bundles/runtime/runtime/src/host/domain/archive.ts`, new)

Pure, no I/O, times in epoch milliseconds.

```ts
import type { ConfigurationValue } from '../../contracts/configuration.js';
import type { Thread } from '../../contracts/model.js';

export const finishedDelayMs = 30_000;
export const dayMs = 86_400_000;

/** The configuration's `threads.autoArchive`, defaults applied. */
export interface AutoArchiveSettings {
  readonly agentThreads: boolean;
  /** Undefined: never. */
  readonly mainThreadsAfterMs?: number;
}

/** `agentThreads` absent → true; `mainThreadsAfter` absent → '7d'; '1d' | '7d' | '30d' → 1, 7, 30 × dayMs; 'never' → undefined. */
export const autoArchiveSettings = (
  configuration: ConfigurationValue,
): AutoArchiveSettings;

/** What a rule reads about one Thread. */
export interface ArchiveFacts {
  readonly thread: Thread;
  readonly batch?: string;
  readonly restoredAt?: string;
  readonly viewedAt?: string;
  /** The stored result carries reason 'interrupted' (D23). */
  readonly interrupted: boolean;
  /** Busy: state queued, running or cancelling, or live jobs, an active prompt or a storage pause. */
  readonly busy: boolean;
  /** At least one view is held. */
  readonly viewing: boolean;
  /** hasQuestionForm(thread.result.text), from runtime/contracts (§2.1). */
  readonly question: boolean;
}

/** Whether a result blocks both rules (U3, U13): status 'failed', or 'cancelled' and interrupted. */
export const blockingResult = (facts: ArchiveFacts): boolean;

/**
 * The time the agent-thread rule archives `facts.thread`, or undefined when
 * it does not under these facts. Defined only when every one holds:
 * 1. settings.agentThreads;
 * 2. origin 'agent' with a parent;
 * 3. not archived, not pinned;
 * 4. state 'ready' or 'cancelled';
 * 5. queuePaused not true, no question, not busy, not viewing;
 * 6. a result whose status is 'completed', or 'cancelled' and not interrupted;
 * 7. no restoredAt, or result.at > restoredAt.
 * Value: max(result.at, viewedAt ?? result.at) + finishedDelayMs.
 */
export const finishedDue = (
  facts: ArchiveFacts,
  settings: AutoArchiveSettings,
): number | undefined;

/**
 * Whether a non-archived Thread is pending for the main-thread rule: state
 * queued, running, cancelling or failed; queuePaused true; a question; busy;
 * viewing; pinned; a blocking result; or an unread result (viewedAt defined
 * and result.at > viewedAt). An archived Thread is never pending.
 */
export const pending = (facts: ArchiveFacts): boolean;

/**
 * The time the main-thread rule archives `root` and its non-archived
 * descendants, or undefined. `descendants` is every descendant of `root`.
 * Defined only when settings.mainThreadsAfterMs is defined, root has no
 * parent and is not archived, and no Thread of [root, ...descendants] is
 * pending. Value: the latest of every createdAt and result.at in [root,
 * ...descendants] and root's restoredAt, plus settings.mainThreadsAfterMs.
 */
export const inactiveDue = (
  root: ArchiveFacts,
  descendants: readonly ArchiveFacts[],
  settings: AutoArchiveSettings,
): number | undefined;

/**
 * A manual archive of `target`: 'already_archived' when it is archived,
 * 'busy' when it is busy; else its id first, then, in the order of
 * `descendants`, the ids of every descendant that is not archived, not busy
 * and not pinned.
 */
export const manualArchiveSet = (
  target: ArchiveFacts,
  descendants: readonly ArchiveFacts[],
): readonly string[] | 'busy' | 'already_archived';

/**
 * The ids a restore of `target` un-archives. The batch is `batch` when given,
 * else the target's own batch; with neither, the answer is empty. The answer
 * is the target, when it carries that batch, then every descendant carrying
 * it, in the order of `descendants`.
 */
export const restoreSet = (
  target: ArchiveFacts,
  descendants: readonly ArchiveFacts[],
  batch?: string,
): readonly string[];
```

Every caller builds the facts from `archiveStates` (§3), the live runtime and the archiver's view counts, and builds `descendants` with the existing `subtreeIds(threads, rootId)` (`bundles/runtime/runtime/src/host/domain/runtime.ts:94-116`), which the service's stored terminate and its delete already use (`bundles/runtime/runtime/src/host/domain/service.ts:518,1389`): it answers the root and its descendants in one set, the root first, and the caller drops the root and maps the rest to their facts. The rules walk no tree themselves.

The Thread state `cancelled` blocks neither rule (U13): a closed agent thread whose last result completed is archived like a `ready` one. The state `failed` blocks both. A `cancelled` result without a reason counts as `completed` for both rules; a reader-stopped result blocks both until a later turn replaces it.

#### 2.1 Question forms (`bundles/runtime/runtime/src/contracts/fences.ts`, new)

Today the rules that decide whether a window draws a question form live in three places: the chat bundle finds fences (`fenceOf` and `closesFence`, `bundles/desktop/chat/src/client/domain/markdown.ts:129-142`; `blockFence`, `bundles/desktop/chat/src/client/domain/fences.ts:18-41`), the openui contracts take a fence's completed statements and their first line (`completedStatements` and `firstCompletedLine`, `bundles/features/openui/src/contracts/fold.ts:57-76`), and the openui client tests that line (`isQuestionLine`, `bundles/features/openui/src/client/folds.ts:57-59`). This change moves those line rules into the runtime's contracts module, which is browser-safe (`bundles/runtime/runtime/src/contracts/index.ts:1`), already holds pure text helpers such as `attachmentLine` (`bundles/runtime/runtime/src/contracts/attachments.ts:107-117`) and is imported by chat and openui, and builds the host's test from them. `bundles/runtime/runtime/src/contracts/index.ts` exports the module.

```ts
/** The marker a line opens a fence with: optional whitespace, then three or more backticks or tildes; undefined when it opens none. */
export const fenceMarker = (line: string): string | undefined;
/** Whether `line` closes a fence `marker` opened: optional whitespace, at least as many of the marker's character, then only whitespace. */
export const closesFence = (line: string, marker: string): boolean;
/** An opener's info (the line after its marker, trimmed) and tag (the info's first whitespace-separated word, '' when none). */
export const fenceInfo = (opener: string): { readonly info: string; readonly tag: string };
/** D21 of docs/designs/conversation-openui.md: /^root\s*=\s*AskForm\(/. */
export const isQuestionLine = (line: string): boolean;
/**
 * A fence body's completed statements: the whole body when `closed` or when it
 * ends with '\n'; otherwise every line but the last, '' when there is one line.
 */
export const completedStatements = (body: string, closed: boolean): string;
/** The first non-blank line of completedStatements(body, closed); undefined when there is none. */
export const firstCompletedLine = (body: string, closed: boolean): string | undefined;
/** The fence tag of a question form. */
export const questionFenceTag = 'openui-lang';
/**
 * Whether `text`, trimmed, holds a question form. Walking its lines, a line
 * with a fenceMarker opens a fence; the fence's body is every following line
 * up to the first that closesFence(line, marker), or to the end (then it is
 * not closed); the body's lines join with '\n'. A fence whose tag is
 * questionFenceTag and whose firstCompletedLine(body, closed) passes
 * isQuestionLine is a question form.
 */
export const hasQuestionForm = (text: string): boolean;
```

The three places then call these functions:

- `bundles/desktop/chat/src/client/domain/markdown.ts`: `fenceOf` and `closesFence` (`:129-142`) are removed; `opensBlock` (`:215-224`) and `markdownBlocks` (`:406-420`) call `fenceMarker` and `closesFence`.
- `bundles/desktop/chat/src/client/domain/fences.ts`: `blockFence` reads its opener with `fenceMarker` and `fenceInfo` and its last line with `closesFence`, in place of the `OPENER` and `CLOSER` patterns (`:18-19`). Their rules are the same: `CLOSER` with the same-character and length check (`:30-34`) is `closesFence`.
- `bundles/features/openui/src/contracts/fold.ts`: `completedStatements(fence)` and `firstCompletedLine(fence)` stay, with their signatures, and answer the runtime's `completedStatements(fence.body, fence.state === 'closed')` and `firstCompletedLine(fence.body, fence.state === 'closed')`. The fold keeps calling them (`bundles/features/openui/src/contracts/fold.ts:122,127`), and their tests (`bundles/features/openui/tests/fold.test.ts:10-72`) pass unchanged.

#### 5.1 Views

- `view(threadId, end)` increments the Thread's count and keeps `end` with the view. On 0 → 1 it calls `markViewed(threadId, new Date().toISOString())` without waiting for it.
- The answer's `dispose` runs once and decrements the count. On 1 → 0 it calls `markViewed` the same way and the Thread still counts as viewed until that write settles, so no sweep reads the older stored time between the view's end and its write (D5).
- A `markViewed` failure logs `warn` with the Thread id; the stored time stays older ([Edge cases](#edge-cases)).
- A view never triggers a sweep: the next sweep sees the count.

#### 5.2 The sweep

A sweep runs these steps in order:

1. If the archiver is draining or disposed, stop.
2. Read the settings. A rejection logs `warn` and goes to step 5.
3. Take `now = Date.now()`.
4. For each live runtime, in map order:
   1. Skip it while it is closing, while it has been live in this process for less than `projectGraceMs` (D29), or while this archiver's previous write for it has not finished (D26). A Project counts as live from the first sweep that sees it in `runtimes`; one that leaves `runtimes` and comes back starts its grace again.
   2. Read `threads.archiveStates(projectId)` without the Project lock. A rejection logs `warn` and skips the Project for this sweep.
   3. Build each Thread's facts from its `ArchiveState`, the busy state of its `ThreadRuntime`, `viewing(threadId)` and `hasQuestionForm(result.text)`.
   4. Collect the due groups: for each main thread, its descendants through `subtreeIds` and `inactiveDue`; when due, the main thread and its non-archived descendants form one group. Then, for each agent thread not in a group, `finishedDue`; when due, it forms a group of its own.
   5. With no group, go on with the next runtime. Otherwise start the Project's write task and go on without waiting for it.
   6. The write task runs under `exclusive(projectId)`. It reads `archiveStates` again, builds the facts and collects the due groups again, and writes each group with `writeArchive(…).catch(oversized({ projectId, threadId: root }))`. A rejection ends the task: `oversized` has logged a `limit_exceeded`, and any other rejection is logged as `error` with the Project id. Groups written before it stay written; the next sweep tries again.
5. Arm the next sweep `sweepIntervalMs` later with `schedule`.

A sweep awaits the settings read and one storage read per live Project, never a Project lock (D26). A due Thread is archived by the first sweep at or after its due time, then after its write takes the Project lock (D13).

### 6. Presence views

`runtime.threads/v1.viewThread({ threadId }, listener)` returns a `Disposable` at once and registers asynchronously:

1. It reads `threads.record(threadId)`.
2. When the `Disposable` was disposed meanwhile, it does nothing more.
3. A missing Thread ends the stream with `new ContractError('not_found', 'Thread not found.')` and holds no view.
4. Otherwise it holds a view through `archiver.view(threadId, end)`, where `end` calls the listener's `end` (a bare-function listener is treated as `{ next }` and has none), and emits one item `{ kind: 'viewing', threadId }`. It emits nothing else.

The stream ends when disposed, when the host link closes (D12), on drain with `unavailable` (D29), or with `not_found`. Several windows, or two views in one window, each hold their own stream; the count keeps a Thread viewed until the last ends. The layout reports views ([§10.8](#108-presence-reporting)).

## Flows

1. **Agent thread finishes.** The parent spawns a child; the child runs; `finishJob` writes `prompt.finished` and the result; the runner sets `ready` and publishes. The first sweep at or after `result.at + 30 s` reads the Project's Threads, finds the child due, takes the Project lock, reads them again, finds it still due and archives it in a batch of its own. The publish reaches every window; the Chat tab drops the row, the Archived tab shows it under Today.
2. **Parent sends again.** The parent's send reaches `enqueue` under the lock; `wake` restores the child (`restoredAt` = now) and publishes; the row is back under its parent in Chat; the turn runs and ends; 30 s to 40 s later it is archived again (`result.at > restoredAt`).
3. **Reader watches the child.** The window's route or Thread tab names the child; `viewThread` holds a view and `viewedAt` is written; every sweep skips the child while the view is held. The reader leaves; the stream is disposed and `viewedAt` is written again; the first sweep at or after `viewedAt + 30 s` archives it.
4. **Agent asks a question.** A turn's answer ends with a question form. The Thread is waiting (U14): neither rule archives it or its main thread. The reader answers; the answers go in as the next message, the Thread is woken if archived, and the next turn's result replaces the one with the form.
5. **Main thread goes quiet.** N days (7 by default) after the last `createdAt` or `result.at` in its subtree, with nothing pending, the next sweep archives it and every non-archived descendant in one batch.
6. **Manual archive and Undo.** Hover → Archive; `archiveThread` answers the batch and the records; the toast offers Undo; Undo calls `restoreThread({ id, batch })`; the records come back without `archivedAt`.
7. **Restore and Delete from the Archived tab.** Restore → `restoreThread({ id })` with the Thread's own batch. Delete → the dialog, with the count of descendants still in Chat → terminate → delete; an archived agent thread is no longer refused.
8. **Host restart.** The schedule and the view counts are in memory and start empty. Documents keep `archive`, `restoredAt`, `viewedAt`; the Projects become live at boot; windows open their view streams again when their host link returns; each Project is swept from 30 s after it became live.
9. **Generation handover.** The old generation starts draining: its archiver stops and ends every view stream with `unavailable`; each window opens the stream again within about 1 s and reaches the new generation, which counts the view. The new generation adopts each Project once the old one lets it go and sweeps it from 30 s after the adoption.

## Persisted data

- Thread documents (`runtime.thread/v1` 1.3.0): five optional fields. Documents without them stay valid and are not rewritten. Archive, restore, pin and view writes keep `updatedAt` (D2).
- Host configuration: optional `threads.autoArchive`; a configuration without it is unchanged byte for byte.
- No new storage type, index, stream or migration. The layout persists nothing new.

### Rollback

- `runtime` 2.8.0 cannot go back to 2.7.x once it wrote a Thread with any new field: the 2.7.x document schema is strict (`bundles/runtime/runtime/src/contracts/storage.ts:78-144`) and its updates write the whole document, so 2.7.x fails to write that Thread (R2).
- `host-config` 0.2.0 can go back to 0.1.0 only after `threads` is removed from the stored configuration. 0.1.0's settings definition parses the stored value with its strict `ConfigInputSchema` (`bundles/foundation/host-config/src/host/configuration.ts:55,74`, `bundles/foundation/host-config/src/host/config/schema.ts:419-431`), and the settings facade answers `invalid_output` on every read that fails it (`bundles/foundation/core/src/host/settings/facade.ts:112-120`), so with `threads` stored the host cannot read its configuration at all. The procedure, with 0.2.0 still running: `GET /config`, remove `threads` from the answered `configuration`, `PUT /config` with the rest (`app/backend/doric-host/README.md:376-382`); then install 0.1.0. The runtime then applies the defaults (R16).
- `chat` 1.8.0 and `openui` 2.3.0 can go back to 1.7.0 and 2.2.0 on their own: their behavior does not change, and the older versions need no 2.8.0 export.
- `layout` 3.2.0 can go back to 3.1.0 on its own: 3.1.0 ignores `archivedAt` and `pinned`, draws every Thread again and reports no views, so no view blocks the rules.
- `settings` 1.8.0 can go back to 1.7.0 on its own: the Threads section disappears and the stored values stay in force.

## Acceptance criteria

Times are measured with `Date` mocked and the sweep scheduler driven by the test (D28).

- **AC1.** An agent thread whose turn completes is not archived before `result.at + 30 s` and is archived by `result.at + 40 s`, once its Project has been live for 30 s (U2, D13).
- **AC2.** A parent's send, a retry, a restart, a Continue and a queue resume each publish the agent thread without `archivedAt` before its run starts; it is archived again 30 s to 40 s after that turn completes (U2, D13).
- **AC3.** An agent thread that is busy, waiting (paused queue or open question), in state `failed`, pinned, viewed, or whose last result is `failed` or reader-stopped is not auto-archived (U3, U13, U14).
- **AC4.** A view held in any window delays the agent-thread rule until 30 s after the last view ends (U3, D5).
- **AC5.** A main thread is never archived by the agent-thread rule (U3).
- **AC6.** A main thread whose subtree has had no `createdAt` or `result.at` for the configured days, with nothing pending, is archived with its non-archived descendants in one batch; `never` archives none (U4).
- **AC7.** A main thread with an unread result, as U5 defines it, is not archived until a view ends after that result; a result that arrived while a view was held is read (U4, U5, U15).
- **AC8.** `archiveThread` archives the target and its idle, unpinned descendants in one batch, answers `busy` for a busy target and `already_archived` for an archived one; over the storage batch limit it rejects with `limit_exceeded` and writes nothing (U8, D27).
- **AC9.** `restoreThread` with the archive's batch restores every Thread of the subtree still carrying it; without a batch it uses the target's (U8, U10).
- **AC10.** A restored Thread is not auto-archived until a turn ends after the restore (D6).
- **AC11.** `deleteThread` deletes a terminal subtree whose target is an archived agent thread and still answers `forbidden` for a non-archived one (U11).
- **AC12.** Archive, restore, pin and view writes leave `updatedAt` and the dashboard's Project order unchanged (D2).
- **AC13.** Settings writes `threads.autoArchive`; the runtime applies the toggle and the days at its next sweep (U12, D14).
- **AC14.** The sidebar shows the two icon-only sidebar tabs with tooltips "Chat" and "Archived", no counter, and the search filters the open sidebar tab (U1).
- **AC15.** The Chat tab hides archived Threads, except archived ancestors of a non-archived Thread, drawn dimmed with the archive mark (U6).
- **AC16.** The Archived tab groups archived Threads into Today / Last 7 days / Older by local archive date, in tree form, with inert dimmed context rows (U10).
- **AC17.** Hover on a Chat row shows Archive next to the plus; archiving shows "Thread archived" with Undo, and Undo restores the batch (U8).
- **AC18.** A pinned row shows the pin mark; Pin and Unpin are in the context menu; Unpin is on hover (U9, D20).
- **AC19.** Hover on an archived row shows Restore and Delete; Restore returns it to its place; Delete deletes the subtree after the dialog, for an agent thread too (U10, U11).
- **AC20.** The spawn card opens an archived child (U7).
- **AC21.** A reader-stopped result blocks both rules; a `cancelled` result from a parent's stop, a removed queued input or a close does not, and neither does the state `cancelled` (U13).
- **AC22.** A Thread whose last result holds a question form is not archived by either rule, nor is its main thread; the next turn's result without one lifts it. `hasQuestionForm` is true for every text in which chat draws a question form (U14, §2.1).
- **AC23.** The Archived tab's delete dialog names the number of non-archived descendants when there is at least one (U16).
- **AC24.** A draining generation sweeps no more and ends every view stream with `unavailable`; a Project newly live in a process is not swept for 30 s (D29).
- **AC25.** A Project whose lock is held does not delay another Project's archive and gets no second write while its first waits (D26).
- **AC26.** A sweep write over the storage batch limit writes nothing and logs `Auto-archive exceeds the storage batch limit`; the next sweep tries again (D27).
- **AC27.** A parent archived by hand while an agent child runs is published without `archivedAt` when the child's result is delivered to it, before the parent's run starts (U17). A save from any Settings section keeps the stored `threads.autoArchive` (§12).
