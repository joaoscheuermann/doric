# Spec: the coding workflow as an on-demand skill, with a repository-root flag in the `cwd` result

- Ticket: [DORIC-91](https://linear.app/doric/issue/DORIC-91).
- Status: approved by the user, version 5 (2026-10-28), revised after the stage 4 Readiness and Codebase reviews; see [Revisions](#revisions). Line references are checked against commit `61c4e7b6`.
- Bundles touched: `runtime` (`runtime.workspace/v1` 1.1.0 → 1.2.0), `files` (the `cwd` tool), `default` (executor, skills, compaction, system prompt).
- Feature docs: [docs/features/coding-workflow.md](../features/coding-workflow.md) and [docs/features/cwd-tool.md](../features/cwd-tool.md), both new; this change creates them, in the feature-doc format of [docs/designs/living-docs.md](living-docs.md) (DORIC-92), and they are the source of truth for the behavior this change documents (see [Docs to update](#docs-to-update)).
- Paths are written from the repository root. A line reference names the file as it is before this change.

## Problem

Today the `default` bundle pushes the coding workflow into a Thread through a dedicated hook:

- `createWorkflow` (`bundles/runtime/default/src/host/repository.ts:46-107`) calls `runtime.threads/v1.instruct` with the text of `bundles/runtime/default/src/host/prompts/repository.md` (`bundles/runtime/default/src/host/repository.ts:12-15`), `reason: 'coding-workflow'` and `retain: true` (`bundles/runtime/default/src/host/repository.ts:54-63`).
- The executor calls `workflow.start` before a run's first model request (`bundles/runtime/default/src/host/executor.ts:453-470`) and `workflow.end` when the run ends (`bundles/runtime/default/src/host/executor.ts:561`). `start` gives the instruction when the Thread has a repository hint and the input is a `user` or `parent` input (`bundles/runtime/default/src/host/repository.ts:85-88`).
- `bundles/runtime/default/src/host/index.ts:117-120` registers `workflow.onCwdChanged` on `runtime.hooks/v1.onThreadCwdChangedHook`, which gives the instruction when a running prompt moves into a repository root (`bundles/runtime/default/src/host/repository.ts:96-105`).
- A Thread running as an agent never receives it (`bundles/runtime/default/src/host/repository.ts:85`).

The push does two things at once: it delivers the workflow's text, and it tells the model "you are at a repository root" at the moment that becomes true. Every other guidance text reaches the model through the skill mechanism instead: the `# Skills` section lists skills, `load_skill` loads one (`bundles/runtime/default/src/host/skills/load-skill.ts:85-132`), and a "Skills changed" message reports changes (`bundles/runtime/default/src/host/skills/live.ts:62-82`). The push is a separate path next to that mechanism, with its own hook consumer, retention key and bundle-instruction reason.

Moving the text into a skill removes the push, and with it the signal. This change therefore also needs a replacement signal: a flag and a reminder in the `cwd` tool result, and an instruction in the system prompt to check the directory and load the matching skills.

## Decisions already made

Ticket decisions, from [DORIC-91](https://linear.app/doric/issue/DORIC-91):

- **T1.** Remove the `default` bundle's coding-workflow hook: `createWorkflow`, its `onThreadCwdChangedHook` handler, the `workflow.start` call in the executor, the `coding-workflow` reason and the `default:coding-workflow` retention key.
- **T2.** The content of `prompts/repository.md` becomes a built-in skill of the `default` bundle, loaded on demand (not always-available). Its description says when to load it; there is no other routing logic.
- **T3.** The `cwd` tool result, not the system prompt's `# Environment`, reports whether the working directory is a repository and, when it is, a short reminder to load the matching skills. The system prompt stays the same across moves, so the provider's prompt cache stays valid.
- **T4.** The system prompt's `# Instructions` tell the model to load the matching skills when working on code in a repository. The host does not verify that it did. The sentence "moving your working directory into it is what gives you the repository's working rules" (`bundles/runtime/default/src/host/prompts/system.md:11`) is reworded.
- **T5.** A move into a repository during a run is covered by the same `cwd` result, replacing the `onThreadCwdChangedHook` trigger.

User decisions made while refining DORIC-91:

- **U1.** A Thread whose run starts in a repository sees no `cwd` result until it calls the tool; the system prompt tells it to check its directory with `cwd` before working on code.
- **U2.** Threads running as an agent do not get the skill: it is not listed for them, and `load_skill` refuses it.
- **U3.** Histories that already hold a retained `default:coding-workflow` instruction are left as they are; no migration.
- **U4.** The repository fact comes from the runtime through a new `runtime.workspace/v1` method, `location()`, not from a check in the `files` bundle.
- **U5.** The `cwd` result keeps the reminder (`note`), with the exact text `Remember to load the skills that match your task when working in a repository.`
- **U6.** The skill has `order: 50`.
- **U7.** Delivery relies on the model following the instruction, without host verification; the user accepts the risks listed under [Risks](#risks), including the extra round trips and the rewind case.
- **U8.** The `coding-workflow` entry is pinned in the "Loaded skills" message, so the size cap never omits it after a compaction.
- **U9.** Two feature docs are created: `docs/features/coding-workflow.md` and `docs/features/cwd-tool.md`.

## Goals

- **G1.** No hook, retention key or `coding-workflow` bundle-instruction reason remains in the `default` bundle (T1).
- **G2.** The workflow is the built-in skill `coding-workflow` of the `default` bundle, listed under "Skills to load" and loadable with `load_skill` (T2).
- **G3.** Every `cwd` result reports whether the working directory is a Git repository's root and, when it is, carries the reminder (T3, T5, U5).
- **G4.** The system prompt tells the model to check its directory with `cwd` before working on code and to load the matching skills at a repository root (T4, U1).
- **G5.** For a Thread with `agent`, `coding-workflow` is absent from the `# Skills` section and `load_skill({ name: 'coding-workflow' })` fails (U2).
- **G6.** A loaded `coding-workflow` is in the "Loaded skills" message after every compaction whose summarized span holds it (U8).
- **G7.** Every sandbox request of a hint probe is bounded by 5000 ms (one request on firecracker, three on docker), and a probe that does not finish never replaces a stored hint with "no repository"; a move, through the `cwd` tool or `PATCH /threads/:id`, answers as today for every probe that exits or throws, and rejects instead of hanging when the probe times out (D8).

## Constraints

- **C1.** The system prompt holds no repository facts, so a move does not change it. It holds none today (`bundles/runtime/default/src/host/prompts/system.md:20-28`), and this change adds none (T3).

## Non-goals

- The per-agent `# Agent` sections (`bundles/runtime/default/src/host/agents/*.md`) stay as they are.
- No host-side check that the skill was loaded, no reminder when the model skips it, no pre-loading (T4, U7).
- No migration of histories that hold a retained `default:coding-workflow` instruction (U3).
- `runtime.hooks/v1.onThreadCwdChangedHook` and the `retain` option of `runtime.threads/v1.instruct` stay in their contracts (`bundles/runtime/runtime/src/contracts/hooks.ts:60`, `bundles/runtime/runtime/src/contracts/threads.ts:391-407`); only the `default` bundle stops using them.
- The `# Skills` section keeps listing the workspace skills of the run's starting directory (`bundles/runtime/default/src/host/executor.ts:293-298`).
- No new trust policy for workspace skills: they are listed and loadable today, and the catalog already tells the model to load the skills that match its task (`bundles/runtime/default/src/host/prompts/skills-catalog.md:23`). See [Risks](#risks).
- No repository fact other than "this directory is a repository root" reaches the model (no branch, dirty state or GitHub origin).

```ts
/** How long the hint probe may run. */
const HINT_TIMEOUT_MS = 5000;

/** The hint probe ran but did not finish: it exited non-zero, was killed or timed out. */
export class HintProbeIncompleteError extends Error {
  constructor(readonly exitCode: number | null) {
    super(`The repository hint probe exited with ${String(exitCode)}.`);
    this.name = 'HintProbeIncompleteError';
  }
}

/**
 * The repository hint of one working directory, or nothing when it holds none.
 * Rejects with HintProbeIncompleteError when the probe did not finish: the
 * script exits 0 on every path it completes, so any other exit code, `null`
 * included, is a failure. An exec that rejects passes its error through.
 */
export const cwdRepoHint = async (
  sandbox: Sandbox,
  cwd: string,
): Promise<CwdRepo | undefined> => {
  const result = await sandbox.exec({
    cmd: ['sh', '-c', HINT_SCRIPT, 'git-hint', cwd],
    timeoutMs: HINT_TIMEOUT_MS,
  });

  if (result.exitCode !== 0)
    throw new HintProbeIncompleteError(result.exitCode);

  const [marker, ...origin] = result.stdout.split('\n');
  if (marker !== 'present') return undefined;

  return isGithub(origin.join('\n').trim()) ? 'github' : 'git';
};
```

```ts
const execute = async (
  workspace: RuntimeWorkspace,
  call: Call,
  input: Input,
): Promise<CwdOutput> => {
  const path = input.path?.trim();
  const change =
    path === undefined || path === ''
      ? undefined
      : await workspace.setCwd(path, call);
  // One read after every outcome: the directory the Thread is in now, and
  // whether it is a repository root.
  const { cwd, repo } = await workspace.location(call);
  const repository =
    repo === undefined
      ? { repositoryRoot: false }
      : { repositoryRoot: true, note: repositoryNote };

};
```

## Flows

**Move into a repository during a run.** The model calls `cwd({ path: 'doric' })`. `RuntimeWorkspaceV1.setCwd` → `runner.setCwd` probes the hint in the lock and stores it (`bundles/runtime/runtime/src/host/domain/runner.ts:1348-1349`) → `{ status: 'set', cwd }`. `location()` probes again → `{ cwd, repo: 'github' }`. The tool answers `repositoryRoot: true` and the note. The model loads `coding-workflow` with `load_skill` if its task matches the description. Before the next model request, the live catalog lists the new directory's workspace skills in a "Skills changed" message (`bundles/runtime/default/src/host/skills/live.ts:62-81`).

**Run that starts in a repository.** The system prompt bullet tells the model to call `cwd` before working on code → `location()` probes → `repositoryRoot: true` and the note.

**Agent Thread.** The executor drops `coding-workflow` from the run's skills (§5); the `# Skills` section does not list it; `load_skill` refuses it. The `cwd` result still carries the note, and the agent can load the other skills that match its step, such as the Git skills or the repository's workspace skills.

**Compaction.** The "Loaded skills" message keeps the pinned `coding-workflow` entry (§6).

**Rewind.** A rewind that removes the `load_skill` result removes the skill from the history, and no host code gives it again (U7). The model reloads it only if it follows the instruction again; the next `cwd` result at a root repeats the note.

## Compatibility

- **Existing histories.** A history that holds a `<bundle-instruction bundle="default" reason="coding-workflow">` message and a `default:coding-workflow` entry in `meta.retained` keeps both: compaction keeps the message verbatim, and rewind drops it past its boundary (`bundles/runtime/default/src/host/compaction/rewrite.ts:9-14,42-50`, `bundles/runtime/default/src/host/history.ts:109,139-140`). If the model also loads the skill, the workflow text appears twice; the two texts differ only in their first sentence (U3).
- **Desktop.** The chat labels a bundle instruction by `bundleId · reason` (`bundles/desktop/chat/src/client/domain/projector-input.ts:109-115`), so old messages render as before. The route `PATCH /threads/:id` keeps its code and its outcomes for every probe that exits or throws; a move whose probe hangs now rejects when the exec times out instead of holding the project lock (§2, G7, R8). The chat has no special case for the `cwd` output.
- **Contract consumers.** `runtime.workspace/v1` 1.2.0 adds one method. The terminal bundle's local copy of `RuntimeWorkspace` (`bundles/features/terminal/src/host/peers.ts:30-43`) lists only `cwd` and `withThread` and does not change.
- **Rollback.** The phases revert in reverse order: phase 3 (the `default` bundle) can revert alone, because it uses no new runtime method; phase 2 (`files` 1.4.0, which requires `runtime.workspace/v1@^1.2.0`) reverts before or together with phase 1, because `files` 1.4.0 does not activate against `runtime.workspace/v1` 1.1.0; phase 1 reverts last. After phase 3 is reverted, the old hook gives the workflow again to any task at a repository root whose history holds no `default:coding-workflow` key (`bundles/runtime/default/src/host/repository.ts:52,85-88`), including histories that loaded the `coding-workflow` skill, so the model reads the workflow twice, the two texts differing only in their first sentence. This is the same duplication U3 accepts in the forward direction, and the user accepted it on the same terms while approving version 5; no migration runs either way.
- **Skill name.** `coding-workflow` is taken by the `default` bundle; another bundle registering the same name fails activation with `duplicate_skill` (`packages/bundle/src/contracts/basic/skills.ts:34-38`). No bundle in the repository uses the name.
