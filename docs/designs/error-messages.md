## Problem

The three desktop UI bundles show failures in 33 places — 17 in `chat`, 11 in `settings`, 5 in `layout` (§5) — with five styles and no shared component:

- **Five styles.** A `Marker` row for a failed prompt (`bundles/desktop/chat/src/client/components/molecules/failure-notice.tsx:28-47`); shadcn `Alert` banners (`bundles/desktop/chat/src/client/components/organisms/thread-queue.tsx:214-219`, `bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx:356-362`); bare red spans and paragraphs (`bundles/desktop/chat/src/client/components/molecules/tool-item.tsx:101-105`, `bundles/desktop/settings/src/client/components/organisms/settings-tools.tsx:55-57`, `bundles/desktop/layout/src/client/components/organisms/dashboard.tsx:405-409`); Sonner toasts (`bundles/desktop/chat/src/client/hooks/use-thread-queue.ts:100,107`); and the OpenUI errors card, which stays out of scope (U5).
- **Raw text with visible chains.** A tool error is flattened into one string of `Caused by:` lines (`bundles/desktop/chat/src/client/domain/errors.ts:23-45`, called at `bundles/desktop/chat/src/client/domain/projector.ts:817`) and drawn red in the row. A failed prompt shows the same chain text (`bundles/desktop/chat/src/client/domain/prompt-lifecycle.ts:140-155`).
- **Codes dropped.** Every client adapter replaces a contract error by fixed text and drops its code and cause: `bundles/desktop/chat/src/client/api/threads-api.ts:158-171,180-198`, `bundles/desktop/settings/src/client/api/settings-api.ts:80-117`, `bundles/desktop/layout/src/client/api/workspace-api.ts:51-73`. A failed prompt reads `code` only at the top level (`bundles/desktop/chat/src/client/domain/prompt-lifecycle.ts:140-155`), but the package errors keep their code under `data` (`packages/llms/src/lib/classes/provider-error.ts:4-15`, `packages/agent/src/lib/classes/agent-error.ts:4-13`, `packages/tool/src/lib/classes/tool-error.ts:4-13`), so most failed prompts show no code. A compaction failure shows only its code (`bundles/desktop/chat/src/client/components/organisms/conversation/nodes/compaction-turn-node.tsx:52`), and the executor does not record the error behind it (`bundles/runtime/default/src/host/compact.ts:204-209,329-336`).
- **Almost no actions.** Only the dashboard's project list offers Retry (`bundles/desktop/layout/src/client/components/organisms/dashboard.tsx:315-326`); the provider model catalog offers Reload (`bundles/desktop/settings/src/client/components/organisms/provider-model-picker.tsx:78-91`). Nothing copies the details of a failure.
- **Mixed languages.** The compaction row, its copy toasts and its number format are Portuguese (`bundles/desktop/chat/src/client/components/organisms/conversation/nodes/compaction-turn-node.tsx:52-57,91,96,102-103,108`), and so is the host's exhausted-resume failure (`bundles/runtime/runtime/src/host/domain/prompts.ts:54-61`).
- **Stacking toasts.** Several toasts have no id, so repeated failures stack (`bundles/desktop/chat/src/client/hooks/use-thread-stop.ts:22`, `bundles/desktop/chat/src/client/hooks/use-thread-queue.ts:100,107`, `bundles/desktop/chat/src/client/components/organisms/intent-dispatcher.tsx:45,48`, `bundles/desktop/chat/src/client/components/organisms/conversation/plugins/edit-queue-prompt.tsx:102,113,142`, `bundles/desktop/chat/src/client/components/organisms/conversation/plugins/attach-images.tsx:92-94`, `bundles/desktop/settings/src/client/components/organisms/dashboard-provider-page.tsx:56`).
- **Shown twice.** A failed rename is toasted by the name field (`bundles/desktop/layout/src/client/components/molecules/editable-name.tsx:110-115`) and also stored as the sidebar's error, because the workspace's `rename` both calls `store.fail` and rethrows (`bundles/desktop/layout/src/client/hooks/use-workspace.ts:442-467`).
- **Silent failures.** The startup splash lists the bundles quarantined when the catalog is resolved, with their reasons, and offers "Continue without them" and "Disable" (`app/desktop/doric/src/platform/catalog/resolve.ts:97-121`, `app/desktop/doric/src/platform/catalog/distribution.ts:231-232`, `app/desktop/doric/src/splash-page/view.ts:72-94`). After "Continue without them", nothing in the window says which bundles are off, and a client part quarantined when the window activates it (`activate_failed`, `registration_failed`, `packages/bundle/src/contracts/platform.ts:169-170`) is reported nowhere: such a bundle's view is replaced by a hidden, empty `<core-unavailable>` (`bundles/foundation/core/src/client/ui.ts:63-69`, `bundles/foundation/core/src/client/elements/unavailable.ts:1-15`), and an element whose creation throws is only logged (`bundles/desktop/layout/src/client/components/molecules/element-host.tsx:30-35`). The settings window reads provider kinds and credentials but never shows those read failures (`bundles/desktop/settings/src/client/hooks/use-provider-kinds.ts:46`, `bundles/desktop/settings/src/client/hooks/use-credentials.ts:58`; no component reads either `error`).

## Goals

- **G1.** Every surface §5 marks as a notice is drawn by `ErrorNotice`, in the `chat`, `settings` and `layout` bundles (U1). Three failure texts are not notices, by design: form validation (U1), the settings save status word (§5.2) and the name field's validation line (§5.3).
- **G2.** A notice's title is its headline level's error catalog title, and its explanation follows §2.3: the entry's explanation, else the error's message cut to its first line and 200 characters. The cause chain is in the collapsed details (U2).
- **G3.** A notice's only actions are Retry, on the surfaces §5 names and under the rules of D5, and Copy details, on every notice (U3).
- **G4.** Every failure toast goes through `toastError` with an id, and failure toasts appear only on the surfaces §5 marks "Toast" (U1).
- **G5.** Every string this change adds or edits is English, and the strings §6.3 lists become English; stored events keep the language they were written in ([Persisted data](#persisted-data)) (U4).
- **G6.** Tool, prompt, compaction and settings failures show their code and cause chain in the notice's details (AC6–AC9) (U7).
- **G7.** The workspace window names every bundle its own bundle catalog lists as quarantined, in one notice (AC11; R11 lists the cases it cannot cover) (U6).

- No quarantine reported by the host only: the window lists only the bundles its own bundle catalog reports as quarantined, and the host's bundle catalog is not forwarded to windows (R7, Q2).

- No change to `useReadError` and `ReadFeedback` (`packages/desktop/src/panels/use-read-error.ts:10-51`, `packages/desktop/src/panels/read-feedback.tsx:4-17`), exported as `desktop/ui/panels` (`packages/desktop/package.json:98-103`). They toast a feature bundle's read failure with the title "Unable to update", the raw message as description, a lifetime of 8 000 ms and a "Try again" action (`packages/desktop/src/panels/use-read-error.ts:31-41`) — the opposite of `toastError` (§4: the error catalog title, Sonner's 4 000 ms, no Retry). The two policies coexist until the follow-up spec of Q1 decides whether `toastError` replaces them: the feature bundles' read failures keep "Unable to update" with "Try again", and the chat, settings and layout failures use `ErrorNotice` and `toastError`.

## Requirements

The user's decisions, restated:

- **U1.** Model A, a single contextual notice: each failure stays where it happens today, but all use one shared component, `ErrorNotice`, in `packages/desktop`, with an icon, a clear title, an explanation, actions and collapsed details holding the technical cause chain. Toasts only for background actions, always with an id, so they do not stack. Form validation stays inline under the field.
- **U2.** Tone: a clear title derived from the error code; the technical detail collapsed.
- **U3.** Actions: Retry and Copy details only.
- **U4.** English everywhere: the compaction strings, the compaction copy toasts and their number format, and the host's exhausted-resume message.
- **U5.** Out of scope: the OpenUI errors card and the splash failure screens.
- **U6.** In scope and new: a notice for a quarantined bundle.
- **U7.** Tool errors and compaction failures carry their code and structured cause chain to the UI; settings keeps the contract error's code and cause.
- **U8** (2026-11-16). The notice looks as the user approved it in a papercraft review on 2026-11-16. §3.3 records that look and is its only description.

## Design

### 1. The error value (`desktop/reads`)

The module is `packages/desktop/src/reads/errors.ts`; `packages/desktop/src/reads/index.ts` gains `export * from './errors.js';` beside `messageFrom` (`:5`). `desktop/reads` holds the window-free helpers every client part shares and is not in the import map: each client part compiles its own copy (`docs/architecture/bundles/implementation-decisions.md:842`, `app/desktop/doric-platform/tests/import-map.test.mjs:93-102`). The chat, settings and layout bundles already depend on the `desktop` package (`bundles/desktop/chat/package.json:29`, `bundles/desktop/settings/package.json:14`, `bundles/desktop/layout/package.json:24`), and `packages/desktop/src/error-notice.tsx` imports `./reads/errors.js` and `./error-copy.js` (§2.1) into the platform's `error-notice.js`. The copies exchange only plain data: `ErrorInfo` is JSON, `ErrorCatalog` a record of strings and flags, and `errorInfo` reads fields, never `instanceof`, so a `ClientError` built by a bundle's copy reads the same in the platform's copy. R10 bounds the drift between copies.

`messageFrom` (`packages/desktop/src/reads/messages.ts:2-5`) does not change; the feature bundles keep calling it (Q1). `describeError`'s last fallback is `messageFrom(undefined)`, so the sentence "The operation could not be completed." is written once (§2.3).

#### 1.1 Types

```ts
/** One level of a cause chain, as the details show it. */
export interface ErrorCause {
  readonly code?: string;
  /** A provider id, from a provider error (`ProviderError.provider`). */
  readonly provider?: string;
  /** An HTTP status, from a provider error. */
  readonly status?: number;
  /** The level's own `retryable` flag, when it states one. */
  readonly retryable?: boolean;
  readonly message: string;
}

/** The value every surface renders: plain JSON, safe to keep in a store. */
export interface ErrorInfo {
  /** The outermost code; '' when the error names none. */
  readonly code: string;
  readonly provider?: string;
  readonly status?: number;
  /** The outermost message, trimmed; '' when there is none. */
  readonly message: string;
  /** The outermost level's own `retryable` flag, when it states one. */
  readonly retryable?: boolean;
  /** The causes below the outermost level, outermost first; at most 7. */
  readonly causes: readonly ErrorCause[];
  /** When the failure happened, ISO 8601; absent only where nothing records it (§1.2). */
  readonly at?: string;
}

/** A rejection the desktop adapters throw: a code, their message, the original error as `cause`. */
export class ClientError extends Error {
  override readonly name: string = 'ClientError';
  readonly code: string;
  /** Set only when the thrower knows a repeat fails the same way (§6.4). */
  readonly retryable?: boolean;
  constructor(
    code: string,
    message: string,
    options?: { readonly cause?: unknown; readonly retryable?: boolean },
  );
}
```

`ClientError` passes `{ cause: options.cause }` to `super(message, …)` when `options.cause` is given, so `cause` is the standard ES2022 property. It sets `retryable` only when `options.retryable` is given; `errorInfo` reads it as the level's own flag (§1.2).

#### 1.2 `errorInfo(value, options?)`

```ts
export const errorInfo = (
  value: unknown,
  options?: { readonly at?: string | null },
): ErrorInfo;

/** An `ErrorInfo` with a given outer code and message whose causes are `cause`'s chain. */
export const errorFrom = (
  code: string,
  message: string,
  cause?: unknown,
  options?: { readonly at?: string | null },
): ErrorInfo;

/** Whether two values carry the same code, message, fields and causes (`at` ignored). */
export const sameErrorInfo = (
  left: ErrorInfo | undefined,
  right: ErrorInfo | undefined,
): boolean;
```

`errorInfo` reads a level as follows; it works the same on a live `Error`, on a `ClientError`, on a `ContractError` (`packages/bundle/src/contracts/error.ts:59-76`) and on the JSON of a stored event:

- A string is a level with that message and no code.
- An object is read field by field: `code` is the string `code`, else the string `data.code`; `provider` is the string `provider`, else `data.provider`; `status` the number `status`, else `data.status`; `retryable` the boolean `retryable`, else `data.retryable`; `message` the string `message`, trimmed, else the string `data.message`, else `''`. No other field is read: not `stack`, `details`, `diagnostic` or `name` (D17). `diagnostic` is an excerpt of a provider's response body or of a tool call's arguments (`packages/llms/src/lib/providers/common.ts:174`, `packages/tool/src/lib/tools.ts:321`), that is, payload.
- Each read is guarded: a property whose getter throws reads as absent.
- Anything else (`undefined`, a number, `null`) is a level with no code and the message `''`.
- The next level is the object's `cause`.

The walk:

1. If the outermost value has the code `handler_failed` (at `code` or `data.code`) and a `cause`, the walk starts at that cause. The tool registry's wrapper only names the tool that threw, which the row already shows; chat's `failureText` dropped it for the same reason (`bundles/desktop/chat/src/client/domain/errors.ts:15-30`). This is the only rule for `handler_failed`; `describeError` has none (§2.3).
2. It reads at most 8 levels, as `MAX_CAUSES` does today (`bundles/desktop/chat/src/client/domain/errors.ts:8`), and stops at the first level that has no `cause`. The cap also ends a cyclic chain.
3. A cause level is left out when its message is `''` or is contained in an outer level's message, and its code is absent or equal to an outer level's code. A level with a new code is always kept.
4. `at` is `options.at` when it is a string; absent when it is `null`, for a failure whose time nothing records; else `new Date().toISOString()`.

`errorFrom(code, message, cause, options)` returns `{ code, message, causes, at }` where `causes` is the chain `errorInfo(cause)` would read, outermost level included, with the same omission rule (step 3) applied against the new outer level. With `cause === undefined`, `causes` is empty.

`sameErrorInfo` compares `code`, `provider`, `status`, `message`, `retryable` and every cause field by value, and ignores `at`.

**Where `at` comes from.** `at` is the time of the failure, so each caller converts where it learns of the failure:

- The chat projection passes the stored event's `createdAt` (§6.1).
- A `catch` of the failing call converts there, without `options.at`, so the current time is the failure time (stores, mutations, `toastError` callers).
- A hook that reads a React Query result converts inside `useMemo` keyed on the query's `errorUpdatedAt`, passing `{ at: new Date(query.errorUpdatedAt).toISOString() }`, so a remount shows the time of the failed read, not of the render.
- The queue-paused notice passes `{ at: null }`: `ThreadQueue.error` is `{ code, message }` with no time (`bundles/runtime/runtime/src/contracts/model.ts:504`), and the current time would change on each remount, giving a new `Time:` line and a new announcement key (§3.6). It builds the value in `useMemo` keyed on the code and the message (§5.1).
- The quarantine notice has no time to give and sets none (§7.2).
- A notice with no `at` has no `Time:` line in its details.

#### 2.3 `describeError`

The levels are `[info, ...info.causes]`, outermost first. With `merged = { ...sharedErrorCatalog, ...options.catalog }` and the pass-through code `internal` — the adapters' outer code when a contract error names none (§6.4):

1. The headline level is the first level, outermost first, whose code is in `merged` and is not `internal`. This is the one rule for every surface; a deeper level wins only when every level above it has no entry or is `internal`.
2. Else, when `options.fallbackCode` is in `merged`, the fallback code's entry gives the title and flags, and the outermost level is the headline level.
3. Else the first level whose code is `internal` is the headline level.
4. Else the `unknown` entry gives the title and flags, and the outermost level is the headline level.

Then:

- `title` is the entry's title.
- `explanation` is the entry's `explanation`, else the first line of the headline level's message, else the first line of `info.message`, else `messageFrom(undefined)` (§1). A first line longer than 200 characters is cut to 199 and ends with `…`.
- `{provider}` in the explanation becomes the headline level's `provider`, else `info.provider`, else `the provider`.
- `retryable` is the entry's flag and the headline level's own flag: `entry.retryable && headline.retryable !== false`. For the `unknown` entry (step 4) it is `headline.retryable ?? true`.
- `tone` is the entry's tone, default `error`.

A surface whose context has a code of its own — the compaction row — builds the outer level with `errorFrom` (§6.1), so the context code is the outermost level and step 1 picks it.

#### 3.4 Details and copy text

`packages/desktop/src/error-notice.tsx` builds two texts in module-private functions; neither is exported. The details text, shown in the open `<pre>`, has these lines, in order, leaving out a line whose value is absent or, for a message, the empty string:

```text
Code: <info.code, or "none">
Provider: <info.provider>
Status: <info.status>
Message: <info.message>
Caused by: [<cause.code>] <cause.message> (<cause.provider>, <cause.status>)
<context key>: <context value>
Time: <info.at>
```

One `Caused by:` line per cause, in chain order; its `[code]` part only when the cause has a code, its parenthesis only when it has a provider or a status, listing those present. The context lines follow the order of `props.context`'s keys. A message's or a context value's further lines are indented by two spaces under their line.

The copy text is the title, a newline, the explanation, an empty line, then the details text. An `inline` notice copies the same text, although it shows only row 1.

#### 3.5 Copy details and the clipboard

Copy details calls `navigator.clipboard.writeText` with the copy text, the mechanism the desktop window already uses (`bundles/desktop/layout/src/client/hooks/use-workspace.ts:526-530`, `bundles/desktop/chat/src/client/components/organisms/conversation/nodes/compaction-turn-node.tsx:101-104`). When the promise resolves, the button's icon becomes `CheckIcon` and its `aria-label` and `title` "Copied"; when it rejects or `navigator.clipboard` is absent, the icon stays `CopyIcon` and the words become "Copy failed". After 1 500 ms the button returns to "Copy details". The same word is written into a visually hidden status `<span>` inside the notice (§3.6). When the copy fails, the details stay selectable in the open `<pre>` of a `block` or `compact` notice (R2).

#### 3.6 Accessibility

- **Announcement.** With `announce`, the notice decides its role when it mounts and when its key changes, and keeps it until then. The key is the code, the message, `at` (absent counts as empty) and the context. The role is `role="alert"` when the window's module-level set of keys in `packages/desktop/src/error-notice.tsx` (one per window, at most 200, the oldest leaves first) does not hold the key, else `role="group"` with `aria-labelledby` naming the title. The decision is made in a lazy `useState` initializer with no side effect (and, for a new key on a mounted notice, in a state update during render), so the two renders of `StrictMode`, which the windows use, give the same answer. The key is added to the set in a `useEffect` after commit; `StrictMode`'s repeated effect adds it again, which changes nothing. A mounted notice therefore keeps `role="alert"` across re-renders, and a later mount with the same key — a frame switch, a navigation, a Thread reopened — finds it and has `role="group"`. Every notice without `announce` has `role="group"`.
- **Who announces.** Surfaces set `announce` for a failure of the reader's own action or of live work (§5 lists each). Transcript blocks rebuilt from the log and the quarantine notice do not.
- **Description.** `aria-describedby` names the explanation's `<span>` when it renders (not the Details link). The title's `title` attribute shows the full title on hover when the ellipsis cuts it.
- **Controls.** Retry and Copy details are native icon-only `<button>`s with an `aria-label` and a `title` of the same words. The Details link is a native `<button>` whose visible text is its name and which exposes `aria-expanded` and `aria-controls` through the collapsible. Retry, while `retrying`, is `disabled` with `aria-busy="true"`.
- **Status.** The notice knows it is in a toast from the module-private toast context of §4. Outside a toast, the copy feedback goes to a visually hidden `<span role="status" aria-live="polite">`. Inside a toast, that `<span>` has no role or `aria-live` of its own: the toaster's region already reads added text (`aria-live="polite"`, `aria-relevant="additions text"`, `node_modules/sonner/dist/index.mjs:1145-1147`), so the word is read once.
- **Details in a toast.** Inside a toast, `CollapsibleContent` has `aria-live="off"`, so opening the details does not make the toaster's region read the whole `<pre>`; the reader reaches it with Tab (`tabIndex={0}`).
- **Focus.** The notice never moves focus.

### 4. Toasts

`desktop/ui/error-notice` also exports:

```ts
export interface ToastErrorInput {
  /** Required: a later failure with the same id replaces this toast; no other toast uses it (§4). */
  readonly id: string;
  readonly error: ErrorInfo;
  readonly catalog?: ErrorCatalog;
  readonly fallbackCode?: string;
  readonly context?: Readonly<Record<string, string>>;
}

export const toastError = (input: ToastErrorInput): void;
```

`toastError` calls Sonner's `toast.custom` (`node_modules/sonner/dist/index.mjs:410-416`, sonner 2.0.8) with `{ id, duration: 4000 }` and a render function that returns the toast surface of §3.3 holding a `compact`, unannounced `ErrorNotice` with the input's `error`, `catalog`, `fallbackCode` and `context`. A custom toast is drawn unstyled (`data-styled` is false for a toast with `jsx`, `node_modules/sonner/dist/index.mjs:712`), so that `div` is the whole surface, and the Toaster's type icons (`packages/desktop/src/components/sonner.tsx:18-24`) do not apply; the notice's own tone icon does.

- **Toast context.** `packages/desktop/src/error-notice.tsx` has a module-private React context, `undefined` by default, of `{ onDetailsChange(open: boolean): void }`. Only the render function of `toastError` provides it, and it is not exported, so no bundle can. `ErrorNotice` reads it: when it is set, the status `<span>` has no role and no `aria-live`, `CollapsibleContent` has `aria-live="off"` (§3.6), and the details' `onOpenChange` also calls `onDetailsChange(open)`. `ErrorNoticeProps` does not change.
- **Replacement.** Sonner keeps one `Toast` component per id (`key: toast.id`, `node_modules/sonner/dist/index.mjs:1208`) and merges a later call with that id into it (`:195-218`), so nothing stacks. Each `toastError` call takes the next number of a module counter and draws its toast surface with that number as React `key`, so a later failure with the same id mounts a new notice, with its details closed.
- **Lifetime.** 4 000 ms, Sonner's default (`:470`), paused while the pointer is over the toaster or the window is hidden (`:667-668`). Every `toast.custom` call passes `duration` explicitly, because a merged call keeps the previous call's `duration` (`:199-213`). `toastError` passes `duration: 4000`. While the reader has the details open, the toast does not expire: `onDetailsChange(true)` calls `toast.custom` with the same id, the same render function (so the same `key`, and the details stay open) and `duration: Infinity`, which starts no timer (`:644`); `onDetailsChange(false)` calls it with `duration: 4000`, which resets the remaining time (`:563-567`) and starts a new 4 000 ms. A later `toastError` with the same id while the details are open passes `duration: 4000` and a new `key`, so its notice starts closed and expires 4 000 ms later. A module-private `Map` from id to the current render function holds what these calls reuse; Sonner's `onDismiss` and `onAutoClose` callbacks (`:663,684`) delete the entry.
- **Ids.** A failure toast's id is used by no other toast. Sonner merges any call into the toast with the same id, `toast.success`, `toast.error` and `toast.message` never clear the `jsx` a custom toast set (`:199-213,252-274`), and a toast draws its `jsx` before its title (`:860`); a success toast on a failure's id would keep drawing the failure's notice, with its `duration`. The three settings actions that toast both outcomes therefore use two ids: the failures `config-save-failed`, `claude-login-failed` and `credentials-write-failed`; the successes keep `config-save` (`bundles/desktop/settings/src/client/hooks/use-config-autosave.ts:56`), `claude-login` (`bundles/desktop/settings/src/client/hooks/use-claude-login.ts:111`) and `credentials-write` (`bundles/desktop/settings/src/client/components/organisms/settings-credentials.tsx:691-694,703`). Before its success toast, each of these actions calls `toast.dismiss` with its failure id, so a failure that a later success superseded does not stay on screen. The chat and layout failure toasts have no success toast on any id.
- **Announcement.** The notice inside a toast is not announced on its own (§3.6): the toaster's region reads the added toast once.
- **Copy.** Copy details is the notice's own button (§3.5). No follow-up toast is shown, so `toast.success` and `toast.error` are not called.
- **Retry.** A toast has no Retry (D5): `toastError` never passes `onRetry`, because the surfaces that toast have no retry target that stays on screen. `useReadError` in `desktop/ui/panels` keeps its own toast with "Try again" for the feature bundles' reads; this change does not touch it ([Non-goals](#non-goals)).

#### 7.2 The window notice

New `bundles/desktop/layout/src/client/domain/bundle-health.ts`:

```ts
/** What the window notice hands to `ErrorNotice`. */
export interface QuarantineNotice {
  readonly error: ErrorInfo;
  readonly catalog: ErrorCatalog;
  readonly context: Readonly<Record<string, string>>;
}

/**
 * One notice for every bundle the snapshot lists as `quarantined`, in its
 * order; undefined when it lists none.
 */
export const quarantineNotice = (
  snapshot: CatalogSnapshot,
): QuarantineNotice | undefined;
```

`quarantineNotice` fills only props every notice has:

- `error`: `{ code: 'bundle_quarantined', message, causes: [] }`, with no `at`: the snapshot does not say when a bundle was quarantined (`CatalogBundle`, `packages/bundle/src/contracts/platform.ts:247-255`). `message`, which is the explanation, is `Turned off: <ids>.`, the bundle ids joined by `, ` in the snapshot's order — for `files` and `terminal`, "Turned off: files, terminal." The manifest has no display name (`CatalogManifest`, `packages/bundle/src/contracts/platform.ts:199-209`), so the id is the name. The sentence names no remedy, because the remedy depends on the reason: an update for `engines_unsatisfied`, a composition choice for `unchosen_provider`, another bundle's fix for `dependency_quarantined` (`packages/bundle/src/contracts/platform.ts:156-174`); the reasons are in the details.
- `catalog`: `{ bundle_quarantined: entry }`, where `entry` is `{ title, retryable: false, tone: 'warning' }` and `title` is `1 extension couldn't start` or `<n> extensions couldn't start`, `n` the number of bundles. The notice shows no other code, so `layoutErrorCatalog` is not merged in, and `ErrorCatalogEntry.title` stays a string.
- `context`: one entry per bundle, in the snapshot's order: the key `<id>@<version>`, the value each reason's message, followed by ` (<contract>)` when it names one, joined by `; `, or `no reason given` when the bundle lists no reason (`CatalogBundle.reasons` may be empty, `packages/bundle/src/contracts/platform.ts:254`). The details read `Code: bundle_quarantined`, the `Message:` line, then one `<id>@<version>: <reasons>` line per bundle, such as `files@1.4.0: requires runtime.threads/v1@^1.8.0; active 1.7.0 (runtime 2.7.0) (runtime.threads/v1)`, the loader's `incompatible_version` message (`packages/bundle/src/runtime/catalog.ts:623-627`) followed by its contract. The bundles are not `causes`: they are separate failures, not a chain.


`Sidebar.error` (`bundles/desktop/layout/src/client/domain/sidebar.ts:69`) and `Workspace.error` (`bundles/desktop/layout/src/client/hooks/use-workspace.ts:51,57`) become `WorkspaceError | undefined`. The rules:

- A failed Projects load stores the target `{ kind: 'projects' }`; a failed Threads load stores `{ kind: 'threads', projectId }`.
- A failed create, rename, color change or delete stores no target: running it again could repeat a write that reached the host.
- A failed project stream reports `errorFrom('project_stream_failed', <today's text>, <the stream's error>)`; the stream's error reaches the hook as `ErrorInfo` instead of a string (`bundles/desktop/layout/src/client/domain/workspace.ts:71`).
- A parent Thread that cannot be found (`bundles/desktop/layout/src/client/hooks/thread-navigation.ts:64`) reports `errorFrom('not_found', 'The parent thread was not found.')`, with no target.
- A failed thread-id copy reports `errorFrom('clipboard_failed', 'Unable to copy the thread ID.', <the rejection>)`.
- `WorkspaceActions` (`bundles/desktop/layout/src/client/hooks/use-workspace.ts:27`) and `SidebarActions` (`bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx:80`) gain `retryError()`: it clears the error, then loads the stored target again. The notice's Retry calls it.
- The error clears when the reader starts a create, rename, color change, delete or thread-id copy, and after a successful load of the stored target.

How `bundles/desktop/layout/src/client/hooks/use-workspace.ts` makes the Projects load callable again, and which store functions carry the target, is the plan's.

New `bundles/desktop/layout/src/client/components/molecules/workspace-error-notice.tsx` renders `<ErrorNotice announce error={value.error} catalog={layoutErrorCatalog} fallbackCode={fallbackFor(value.retry)} onRetry={value.retry === undefined ? undefined : retryError} className={className} />`, where `fallbackFor` answers `projects_load_failed` for `{ kind: 'projects' }`, `threads_load_failed` for `{ kind: 'threads' }` and `workspace_action_failed` without a target. A fixed `workspace_action_failed` would title a failed load with an uncatalogued code "Change not saved" and, that entry being not retryable, hide its Retry (§2.3). `ProjectSidebar` (`bundles/desktop/layout/src/client/components/organisms/project-sidebar.tsx:356-362`) and the dashboard (`bundles/desktop/layout/src/client/components/organisms/dashboard.tsx:405-409,450-457`) render it. A frame switch remounts it without a second announcement (§3.6).

A failed rename or name creation is shown once: `rename` and `createProject` keep calling `store.fail` and rethrowing (`bundles/desktop/layout/src/client/hooks/use-workspace.ts:409-412,463-466`), and `EditableName` keeps only the mark (§5.3). Name validation never reaches the store: `nameError` refuses before `onSubmit` (`bundles/desktop/layout/src/client/components/molecules/editable-name.tsx:99-104`).

## Flows

**Tool failure.** Tool throws → `run-tools` emits `tool.failed` with the error (`packages/agent/src/lib/utils/run-tools.ts:42,67`) → the runtime stores it as redacted JSON → the chat projects `ToolTurn.error = errorInfo(event.error)`, dropping an outermost `handler_failed` wrapper (§1.2) → the row draws a compact notice whose title comes from the first level, outermost first, with an error catalog entry (§2.3); for a provider rate limit inside a tool: "Rate limit reached" → explanation, Copy details, collapsed details with the chain.

**Failed prompt, then Retry.** `agent.failed` → `FailureTurn` → block notice; it is the last prompt's failure and `canRetry` holds, so Retry shows → Retry → `chat.retry()` → `threads.retry(threadId)` (`bundles/desktop/chat/src/client/stores/thread-chats.ts:426-438`); Retry spins and is disabled while `chat.sending`. A new prompt's turns follow; the old block is no longer the last failure and its Retry disappears.

**Compaction failure.** Summarizer throws a provider error → `compaction.failed { code: 'summarizer_failed', error }` (§6.2) → `CompactionTurn.error = errorFrom('summarizer_failed', 'The summarizer failed.', error)` → compact notice titled "Compaction failed", with "Earlier messages could not be summarized." on row 2 and the provider error in the details.

**Settings write refused.** The picker writes → `setThreadExecution` answers `invalid` → `errorFrom('invalid_execution', message)` → inline notice "Model not accepted" (row 1 only; the runtime's message "The model is not available on this provider." is in the copy text) with no Retry. The bridge rejects with `unavailable` instead → `SettingsApiError` keeps that code → "Doric host unavailable" with Retry → `write(next)`.

**Quarantine.** Window boot quarantines `chat`'s client part → the layout mounts → `doric.catalog/v1.get()` lists `chat` as `quarantined` → the left sidebar's bottom shows one warning notice titled "1 extension couldn't start" with "Turned off: chat." on row 2, whose details list `chat@<version>` with its reasons on one line; the regions `chat` fills stay empty.

## Persisted data

- `tool.failed` and `agent.failed` events already hold the full error JSON with `code` or `data.code`, `provider`, `status` and `cause` (`bundles/runtime/runtime/src/host/domain/serialization.ts:121-158`). - No store, setting or configuration schema changes. Client state that held strings (`sendError`, the queue edit `error`, the sidebar error, the settings hooks' errors) is in-memory only.

## Phases

Each phase builds and passes its tests on its own.

1. **Platform.** `packages/desktop/src/reads/errors.ts` and its `desktop/reads` export, `packages/desktop/src/error-copy.ts`, `packages/desktop/src/error-notice.tsx`, the `./ui/error-notice` `exports` entry, the theme `@source`, the story and tests; `PLATFORM_VERSION` 1.7.0 and its test; the import-map test. No bundle uses them yet.
2. **Runtime data.** `compaction.failed` gains `error` (`default` 2.6.0, `executor/v1` 1.5.0); the English `resume_exhausted` message (`runtime` 2.7.1). The chat does not read `error` yet. One visible change: the current failure block shows the stored message of a `resume_exhausted` failure (`bundles/desktop/chat/src/client/domain/prompt-lifecycle.ts:140-153`), which is English for prompts that fail after this phase.
3. **Chat.** Adapter `ClientError`s, the projection of §6.1, every chat surface of §5.1, the English compaction text; `chat` 1.7.0 with `engines.doric` `^1.7.0`.
4. **Settings.** `SettingsApiError` codes, the hooks' `ErrorInfo`, every settings surface of §5.2; `settings` 1.7.0.
5. **Layout.** Adapter `ClientError`s, the workspace error (§8), `EditableName`, `ElementHost`, the quarantine notice (§7); `layout` 3.1.0.

Phases 3–5 depend on phase 1 only and may land in any order after it. Chat 1.7.0 may ship before phase 2: a `compaction.failed` event without `error` shows the code alone (AC8).

### Rollback

No phase changes stored data or configuration ([Persisted data](#persisted-data)), so each rolls back by shipping the previous version:

- **Chat, settings, layout (phases 3–5).** Their previous versions require `engines.doric` `^1.1.0`, `^1.0.0` and `^1.1.0` ([Contracts and versions](#contracts-and-versions)), which platform 1.7.0 satisfies, so each rolls back alone. They read stored events as they did before; a `compaction.failed` event with `error` carries one more field, which they do not read.
- **Default (phase 2).** Going back from 2.6.0 to 2.5.0 provides `executor/v1@1.4.0` again; the runtime requires `^1.4.0` (`bundles/runtime/runtime/manifest.json:34`), and no bundle requires 1.5.0. Events already written keep `error`; chat 1.7.0 still shows their chains, and shows the code alone for events written after the rollback.
- **Runtime 2.7.1 (phase 2).** Going back restores the Portuguese `resume_exhausted` message for prompts that fail afterwards; chat 1.7.0 still shows the English title and explanation, and the message only in the details.
- **Platform (phase 1).** Roll back chat, settings and layout first: an app on platform 1.6.0 quarantines a bundle that requires `^1.7.0` (`engines_unsatisfied`, R1). With them back, nothing imports `desktop/ui/error-notice`, and the platform rolls back.
