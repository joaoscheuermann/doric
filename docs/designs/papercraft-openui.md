## Problem

Papercraft lets the agent show a visual change of the Project instead of describing it: a canvas node in the conversation that the reader can pan and zoom, pin comments on, and send back (concept [Summary](../features/papercraft.md#summary)). Today each preview is an artifact revision built from a Project file the agent wrote, rendered once in an isolated frame (concept [How papercraft works today](../features/papercraft.md#how-papercraft-works-today)).

After U18, papercraft is the one exception to OpenUI's model: its fences render in the isolated frame, because they run untrusted repository code (U15 libraries, `Export`) and the canvas is built on the frame. Generative UI that runs no repository code renders in the app ([conversation-openui.md](conversation-openui.md)). This document decides:

- how a papercraft fence is drawn in the frame, with its protocol (D6);
- how a repository declares, compiles and serves its library, with several repositories in one Project (U15, D8, D10–D14);
- how harness and theme apply (D15) and how `Export` previews any export (U14, D16);
- how comments, pins and the canvas window work on programs (U6, P6, D19, D26);
- how artifacts and the old preview path are removed, and what persisted data stays (D25, P8);
- how the agent learns the library (D28).

## Non-goals

- No conversation UI, questions or actions in a papercraft fence ([D7](openui.md#d7-render-hosts-and-routing), D6).
- One fence never mixes components of two repositories (D10).
- No namespacing of repository components; a name that collides with a built-in is a compile error (D11).
- Doric never edits a repository's own `.gitignore` (D8).
- No `Query` or `Mutation` in a papercraft fence: a preview has no tools to call, and the app's check reports each one (D6).

## Design

### Overview

One papercraft fence, from the model's text to the agent's next prompt:

1. The model writes ` ```papercraft <identity> ` in its answer. The chat finds the fence and gives it a key and a state ([D1](openui.md#d1-the-fence-in-the-chat-a-new-chat-contract), [D2](openui.md#d2-fence-key-states-and-the-end-of-answer-signal)).
2. The chat mounts the `papercraft-fence` element for that key, which papercraft's client registered for the tag ([D1](openui.md#d1-the-fence-in-the-chat-a-new-chat-contract), [D24](openui.md#d24-the-setting-and-rollback)).
3. The element reads its revision from papercraft's fold of the Thread's papercraft fences: the merged program, its base and whether it is complete ([D4](openui.md#d4-the-program-reducer), [D5](openui.md#d5-progressive-merge-of-patches-p4)).
4. It asks the host for the library bound at the fence's turn, `papercraft.programs/v1.library({ turnSequence })`. The host finds the working directory recorded before that turn (D10), the library root above it, and the compiled module, building it when its inputs changed (D11–D14).
5. It collects the program's literal `Export` calls and asks `export` for each (D16).
6. For each module file the window has not stored yet, it `read`s the bytes from the host and `ensure`s them into the desktop cache, which serves them at `doric://app/papercraft-modules/` (D14).
7. Once the library has answered, it boots or reuses a frame and sends `init` (theme, input capture, the library's URLs), then a `program` message for each change of the merged program (D6).
8. The frame renders the program and sends back `scene` (with each node's statement and component) and `errors`.
9. When the fence is `closed` or `unterminated`, the element reports the frame's error codes and its own checks through `openui.programs/v1.reportErrors` with the tag `papercraft` (D6, [D18](openui.md#d18-validation-feedback-u19)).
10. At the Thread's next prompt start, papercraft's host gives the errors as a `validation` instruct ([D18](openui.md#d18-validation-feedback-u19)) and, when the library changed, the library instruct (D28).

The canvas node draws pins and comments over the frame or its snapshot (D19, D26). Papercraft requires the `openui` bundle's setting and imports the identity rule, the fold and the error format from `openui/contracts` ([D27](openui.md#d27-the-openui-bundle)). A papercraft fence's identities and revisions never meet a conversation program of the same name ([D3](openui.md#d3-identity-and-revision)).

### D6. The frame entry and protocol 2

#### Frame entry

`bundles/features/papercraft/src/client/frames/openui.ts`, built as a bundle frame (`packages/bundle/src/build/parts.ts:392-419`) beside today's `frames/preview.ts`, which serves the old path until stage 4 ([Protocol 2](#protocol-2)). It is the frame realm's only importer of `@openuidev/*` (concept R12). It:

- renders OpenUI's `Renderer` with `response`, `library`, `isStreaming`, `onAction`, `onError` (react-lang 1.0.2 `dist/index.d.mts:38-79`) and `publishObservability={false}` ([D23](openui.md#d23-telemetry-u8)); it passes no `toolProvider` (`:61-65`);
- is a browser build, so it takes D23's `define` of `process.env.NODE_ENV` as `"production"`: the bundled react-lang neither imports `@openuidev/devtools` nor mounts OpenUI's Inspect widget into the frame's `document.body`, and does not publish the library to `globalThis` (react-lang 1.0.2 `dist/index.mjs:19-44,47-87`). PC32 tests the built frame;
- uses `openuiLibrary` extended with `Export` (D16) and, when bound, the repository library (D10), the papercraft library of [D7](openui.md#d7-render-hosts-and-routing); the question built-ins are not in it;
- wraps the component of every named statement with `library.extend({ components: { override } })` (lang-core 1.0.2 `dist/index.d.mts:624-640`) in a statement wrapper `<span data-papercraft-statement="<statementId>" data-papercraft-component="<name>" style="display: contents">`; inline components have no `statementId` and get none (`dist/index.d.mts:549-554`);
- loads three sheets as `<style>` elements, which the frame CSP allows (`style-src doric://app 'unsafe-inline'`, `app/desktop/doric/src/platform/protocol/csp.ts:47-58`): Doric's `packages/desktop/src/styles/tokens.css`, react-ui's `@openuidev/react-ui/layered/styles/index.css` and `bundles/features/openui/src/client/tokens.css` ([D31](openui.md#d31-the-built-in-library-and-dorics-tokens)). It imports each as text, `import sheet from '<path>' with { type: 'text' }`, which esbuild maps to its `text` loader with no build option (https://esbuild.github.io/content-types/); the two Doric sheets by relative path, since a frame may not import `desktop/*` or another bundle's specifiers (`parts.ts:94-101`). The three imports are the only content of `src/client/frames/openui/sheets.ts`, which exports `sheets: readonly string[]`; `src/client/frames/openui/css-text.d.ts` declares `declare module '*.css' { const text: string; export default text; }`, which `tsconfig.client.json` includes through `src/client/**/*.ts`. The entry `frames/openui.ts` is `startProgramFrame(window, { sheets })`, with `startProgramFrame` in `src/client/frames/openui/runtime.ts`. tsc 5.9.3 accepts the import with that declaration, but Node 22 refuses a `.css` import (`ERR_UNKNOWN_FILE_EXTENSION`; checked on 2026-11-04 with v22.23.4), so no test imports `sheets.ts` or the entry: PC24 calls `startProgramFrame` with sheets of its own, and PC32 reads the built frame;
- sets the `dark` class on its `<html>` from the `theme` message, as today's runtime does (`bundles/features/papercraft/src/client/frames/preview/runtime.ts:294-296`); it sets no `data-openui-theme` (D31);
- publishes the namespaces `reactLang`, `langCore`, `zod` and `zodCore`, which compiled libraries read, with the shim ABI (D13), before it imports a library module;
- for an `Export`, imports the module and calls its `mount(root, { theme, args })` (D16);
- shares with `preview.ts` the frame modules that already stand alone, `frames/preview/storage.ts`, `input.ts` and `scene.ts`, and one module extracted from `frames/preview/runtime.ts`, `frames/preview/shell.ts`. The shell holds what both entries do apart from drawing: the handshake (`isConnect` and `onConnect`, `runtime.ts:157-158,716-738`), `send`, the error reporting (`:160-182,228-292`), the theme (`:294-303`), the cursor lock (`:305-330`), the hidden set (`:332-361`), size, measure and scene posting (`:363-460`) and the shared app messages `theme`, `capture`, `hidden`, `cursor`, `measure` and `dispose` (`:672-714`):

#### Local state only (U22)

- `$variables`, tabs, toggles and form fields work, since the renderer runs them by itself (https://www.openui.com/docs/openui-lang/actions). The steps `@Set` and `@Reset` change only local state (`ACTION_STEPS` `set` and `reset`, lang-core 1.0.2 `dist/index.mjs:591-597`) and stay allowed.
- The frame's `onAction` ignores every event and posts nothing. Protocol 2 has no message that carries text toward the conversation.
- With no `toolProvider`, a `Query` or `Mutation` statement does nothing and raises nothing: react-lang creates its query manager with `toolProvider ?? null` (react-lang 1.0.2 `dist/index.mjs:630`), lang-core's fetch returns at once without a provider (`if (!toolProvider) return;`, lang-core 1.0.2 `dist/index.mjs:4897`), and a mutation gives `false` silently (`:5075`). `tool-not-found` (`:4930-4939`) is raised only when a provider exists and throws. So the app's check reports them (below).

#### The app's check of a papercraft program

A pure function `programErrors(program: string): ReportedError[]` (`ReportedError` from [D18](openui.md#d18-validation-feedback-u19)) in `bundles/features/papercraft/src/client/program-errors.ts` walks the program with lang-core's parser parts, through the client's adapter: `split(tokenize(program))`, then `parseExpression` on each statement's tokens, then `walkAST` (lang-core 1.0.2 `dist/index.d.mts:93,866,875,878-883,903`).

- An action call `@ToAssistant(…)` parses to a node `{ k: 'Comp', name: 'ToAssistant' }`: the tokenizer drops the `@` (`dist/index.mjs:2700-2707`), and a call of a built-in step gets no `fn` flag (`:2189-2194`; `ASTNode`, `dist/index.d.mts:30-35`). Without the `@`, a PascalCase name of a built-in call followed by `(` parses as a reference, not a component: the parser builds a component only when `!isBuiltin(name) || name === "Action"` (`:2180-2187`), and `isBuiltin` covers `BUILTIN_CALLS`, the built-in functions (`Count`, `Filter`, `Sort`, `Each` and the others), the steps and `Action` (`:710-729`). The author ran the parser on 2026-11-04: `a = Filter("x")` and `a = ToAssistant("x")` give `{ k: 'Ref' }`, while `@ToAssistant("y")` inside a `Button` and `a = Query("t")` give `Comp`. So a repository component named like a built-in call would never render, and D11 refuses those names; a plain `ToAssistant(…)` is an unresolved reference that runs nothing, so the check need not report it.
- Each statement that holds a `Comp` named `ToAssistant`, `OpenUrl` or `Run` gives `{ code: 'unknown-function', statementId, message: '@<Step> is not available in papercraft fences. Actions belong in openui-lang fences; a preview changes only local state ($variables, forms, @Set, @Reset), and the reader answers with pinned comments.' }`.
- Each statement whose expression, as `parseExpression` gives it, is a `Comp` named `Query` or `Mutation` (lang-core's reserved statement calls, `dist/index.mjs:734-741`) gives `{ code: 'tool-not-found', statementId, message: 'Query and Mutation are not available; write the data as literals.' }`, the code and hint the conversation's check gives ([D7](openui.md#d7-render-hosts-and-routing)). The frame reports nothing for these statements (above), so no other line covers them. `Query` and `Mutation` are lang-core's reserved calls (`RESERVED_CALLS`, `:735-741`), not built-ins, so they parse as `Comp`; D11 refuses repository components of those names (U35), so the name always means the reserved call.
- Each statement that holds a `Comp` named `AskForm` gives `{ code: 'unknown-component', statementId, message: 'Questions go in openui-lang fences.' }`, the hint of [D7](openui.md#d7-render-hosts-and-routing). The frame reports the same statement as a bare `unknown-component`; the reporter sends the check's results first and the host keeps the first of two lines with the same tag, key, code and statement ([D18](openui.md#d18-validation-feedback-u19)), so the hint wins. D11 refuses a repository component named `AskForm` ([open question 10](#open-questions)), so the hint is never wrong.
- The element runs it on the merged program when the fence is `closed` or `unterminated`, shows the errors under the canvas node, and reports them with the frame's (step 9 of the [Overview](#overview)). The messages are computed by papercraft's client from the model's program, so they keep their text under D18.
- **Errors, not warnings.** D18 drops warnings, as OpenUI advises, so a warning would never reach the agent. A control that does nothing is a defect the agent fixes by changing the program, which is what an `OpenUIError` error is for (`dist/index.d.mts:212-238`).
- **The code `unknown-function`** is OpenUI's code for an `@Name(…)` call the library does not provide (`dist/index.d.mts:34-35,180`), and the papercraft library provides none of these steps. A code from OpenUI's union fits `ReportedError` unchanged.

#### Frame cap

The window keeps at most three live frames (`GROUNDING.md:1402-1407`); after U18 only papercraft fences use them. One warm frame, a protocol 2 frame booted with no program, counts as one of the three and becomes the next fence's live frame (PC24).

#### Boot and memory

Boot time, memory per frame and re-parse cost (concept R3) are not measured before shipping (U48). If a cold boot is slow in use, one warm frame per window can be kept at all times, outside the cap of three; if memory per live frame grows, the cap can be lowered to two. The user decides.

#### Alternatives

- _Send papercraft actions on click through `chat.send/v1.sendAction`_, as conversation fences do ([D20](conversation-openui.md#d20-actions-back-to-the-agent-p1)). Rejected by U22. Repository code in the frame can call `onAction` without a click, so a message could be sent as the reader without the reader acting.
- _A reviewed proposal: the action becomes a draft on the composer's stack, sent with the composer's send._ Rejected by U22: it adds a stack kind and a second action route beside D20's, used only by previews, whose channel back is already the pinned comment.
- _Report the action at run time, from the frame's `onAction`._ Rejected: the agent would learn of it only when a reader clicked, while the app's check reports it from the program alone.
- _Leave `Query` and `Mutation` to the frame_ (version 9). Rejected: without a `toolProvider` the frame raises nothing for them (`dist/index.mjs:4897,5075`), so the fence would draw nothing and the agent would learn nothing.
- _Raise protocol 1 to 2 for both entries, with `init.content` optional_. Rejected: `preview.ts` would accept messages it cannot draw, and every protocol 2 change would have to keep the old entry working; two numbers keep each entry's messages exact.
- _A `toolProvider` for `Query` and `Mutation`._ Rejected: a preview would call tools on the reader's behalf from inside the frame, which U22 rules out for actions for the same reason.

### D8. `.doric/` layout and versioning

#### Today

`.doric/` is app state. The artifacts store writes `.doric/.gitignore` with `*` before its first write when the file is absent (`bundles/features/artifacts/src/host/store.ts:40-44,293-304`), and papercraft keeps its runner and jobs in `.doric/papercraft/` of the workspace root (`sandbox.ts:61-62,92-93`). Nobody owns the `.doric/` layout: these two are the only writers under `.doric/` in the bundles' sources, each picked its folder itself, and the artifacts design leaves open what else lives in `.doric/` (`docs/architecture/bundles/artifacts.md:220`). This repository also ignores `.doric` as a whole (`.gitignore:9`). So files under `.doric/papercraft/schemas/` would not be versioned today.

#### Decision (U15: the schemas are versioned): each owner ignores its own folder

- `.doric/` has no Doric-wide ignore file. A bundle that keeps app state under `.doric/<folder>/` ignores it with a `.gitignore` inside that folder, written by that bundle before its first write there, when the file is absent. Everything else under `.doric/` is versioned like any repository file. No bundle writes another bundle's folder, except in the one migration below.
- papercraft writes `.doric/papercraft/.gitignore` in the workspace root, before the runner's first write there:

  ```gitignore
  # Written by papercraft: the runner and its jobs stay out of Git; schemas/ is versioned.
  /*
  !/.gitignore
  !/schemas/
  ```

  It names only papercraft's paths. A library root inside a nested repository gets no file, because papercraft writes nothing there; its `schemas/` files are ordinary repository files.

- The artifacts store, in stage 2, writes `.doric/artifacts/.gitignore` with `*` instead of `.doric/.gitignore` (the change is in its ignore step, `store.ts:293-304`). The file goes with the bundle in stage 4.
- The author checked the layout with Git on 2026-11-03, in a scratch repository: with `.doric/papercraft/.gitignore` above and `.doric/artifacts/.gitignore` holding `*`, `git add -A` adds `.doric/papercraft/.gitignore`, `.doric/papercraft/schemas/Button.tsx` and a nested `apps/web/.doric/papercraft/schemas/Card.tsx`, and not `.doric/papercraft/runner-1.mjs`, `.doric/papercraft/jobs/…` or `.doric/artifacts/…`. With a `.doric/.gitignore` holding `*` added, nothing under the root's `.doric/` is added.

#### The migration

Decided by U31.

A `.doric/.gitignore` whose content is exactly `*` plus an optional newline is the file the artifacts store wrote (`store.ts:43-44`). Before papercraft's first runner job in a Project in each host session, papercraft writes `.doric/artifacts/.gitignore` with `*` when `.doric/artifacts/` exists and has none, then deletes that `.doric/.gitignore`. When `.doric/artifacts/` does not exist, it only deletes the file. A per-Project flag in memory makes it run once per host session. Any other content of `.doric/.gitignore` is the repository's and is left alone.

**How and when.** `src/host/ignore.ts` runs both steps through the job's `RunnerSandbox`, which offers `exec`, `putFile` and `getFile` (`sandbox.ts:30-33`), in `bundleInSandbox` before the runner copy (`sandbox.ts:97-98`). Every path is under the sandbox's `root`, as the runner copy's is (`sandbox.ts:91-93`), and every `exec` runs with `cwd: root`:

1. `exec({ cmd: ['test', '-e', '.doric/papercraft/.gitignore'], cwd: root })`; on a non-zero exit, `putFile` writes D8's content.
2. `exec({ cmd: ['test', '-f', '.doric/.gitignore'], cwd: root })`; when it exists, `getFile` reads it, and only when its content is exactly `*` plus an optional newline: `exec({ cmd: ['test', '-d', '.doric/artifacts'], cwd: root })`, and when that succeeds and `test -e .doric/artifacts/.gitignore` fails, `putFile` writes `*\n` there; then `exec({ cmd: ['rm', '-f', '--', '.doric/.gitignore'] })`.

- **Every job, whatever the setting.** Both run before the first runner job of any kind in a Project in each host session: a library or `Export` job, and an old-path job of `papercraft_preview`, which writes the same `.doric/papercraft/` folder. They do not depend on the setting: from stage 2 the artifacts store no longer writes `.doric/.gitignore` (below), so without papercraft's own file an old-path job in a new workspace would leave the runner copy visible to Git. With the setting off, the migration's effect is the one U31 and U40 decide: once per workspace, only when the old file exists.
- **Failures.** A step that fails, a non-zero exit of `rm` or a rejected `putFile` or `getFile` included, ends the steps and leaves the flag unset, so the next job of that Project tries again. The job itself still runs, and nothing is reported: the steps change only ignore files.
- **A downgrade.** An artifacts store older than stage 2 writes `.doric/.gitignore` with `*` again when it is absent and it writes an artifact (`store.ts:40-44,293-304`). That hides the schemas from Git until a stage 2 or later host runs a papercraft job there, which migrates the file again. Accepted: a downgrade loses no file, and `git status` shows the schemas again after the next job.

The first runner job can be the library job a window starts to draw a fence (D14), so showing a UI can run the migration. It is the one exception to G4's target, confirmed by the user (U40): it runs only when the old file exists, writes `.doric/artifacts/.gitignore` and deletes `.doric/.gitignore`, once per workspace, since a later run finds no file holding exactly `*`. PC4 tests it; PC17 runs on a workspace without that file.

papercraft does it, not artifacts, because:

- the file hides papercraft's schemas;
- artifacts writes under `.doric/` only when the old `papercraft_preview` tool creates or revises an artifact, through `writeRevision` (`store.ts:345-349`), or when the reader approves a revision (`bundles/features/artifacts/src/host/artifacts.ts:771`, `store.ts:375`); stage 3 withholds the tool, and from stage 2 those writes go to `.doric/artifacts/.gitignore`;
- old workspaces keep the file after artifacts is removed in stage 4.

#### A repository rule that hides the schemas

Decided by U31.

A repository that ignores `.doric` itself (this repository's `.gitignore:9`) hides the schemas before any of these files is read. Doric does not edit the repository's `.gitignore`. The library job checks it (D14): when it builds a library whose root contains `.git`, it runs `git check-ignore -v -- .doric/papercraft/schemas/<first entry file>` in the root, with a 5 s timeout, where the first entry file is the first in D11's file-name order. Exit status 0 means the file is ignored; the job keeps the `<source>:<line>` part of the output (the rule's file and line, not its pattern) as `ignoredBy`. Any other status, or no `git`, gives no `ignoredBy`.

The library instruct then adds one line (D28): "Git ignores these schema files (`<source>:<line>`), so they are not versioned. Tell the reader. Removing that rule keeps Doric's app state out of Git, because each Doric folder under `.doric/` has its own `.gitignore`." The last sentence holds because papercraft and artifacts are the only writers under `.doric/` and each ignores its own folder (above).

This repository gets no library in this change, so `.gitignore:9` does not change.

#### Alternatives

- _papercraft owns `.doric/.gitignore`_: one file with `/*` and re-includes for `papercraft/` and `papercraft/schemas/`, rewritten on each library compile. Rejected: papercraft's paths would sit in a Doric-wide file that the artifacts store also writes, and a later bundle that needs a versioned file under `.doric/` would have to edit papercraft's template.
- _A shared helper that composes `.doric/.gitignore` from each bundle's declared versioned paths._ Rejected: after stage 4 papercraft is its only user, and it would still need one Doric-wide file and a merge rule for content a repository edited.
- _A skill rule: the agent runs `git check-ignore` after writing a schema file_ (the earlier draft). Rejected: an agent that skips the rule leaves the files untracked, and `git status` does not list ignored files, so the reader learns it only on a clone. The check in the library job costs one `git` process per build, and builds run only when the inputs change (D14).
- _Local, not versioned._ Keep `.doric/` ignored as a whole, so the schemas stay local to one checkout, like app state. Rejected by the user's decision in U15, for these reasons:
  - Nothing is shared through Git: each developer's agent writes its own library, the libraries drift apart, and the same request draws different components on two machines.
  - A clone, a new worktree or a CI checkout starts without a library, so the agent falls back to built-ins or `Export` (U14) until someone writes the files again.
  - Schema changes get no review: a component's description and props schema are what the model reads, and they would change outside pull requests.
  - G5 measures components against the product; a library that is not versioned cannot follow the components it describes from one commit to the next.

### D10. Discovery and binding (several repositories)

A Project's `/workspace` can hold several repositories, and each Thread's working directory moves inside it (`GROUNDING.md:625-632`).

#### Discovery

Walking up from a working directory, the first directory that contains `.doric/papercraft/schemas/` with at least one entry file (D11) is the library root. The walk stops after the nearest repository root, a directory that contains `.git` (a directory, or a file in a worktree); when no repository encloses the working directory, it stops at `/workspace`. So a repository is never served another repository's library, nor a library above it in the workspace. The library job does the walk in the sandbox, where the files are (D14).

- A working directory that no longer exists gives `failed` with "The working directory <cwd> no longer exists".
- A walk that ends without a root gives `none`.

#### Binding

Papercraft's host appends the event `papercraft.cwd/v1@1.0.0`, payload `{ cwd: string }` (the Thread's working directory, as the hooks give it), to the Thread:

- at `onPromptStartedHook`, with the hook's `cwd`, and at `onThreadCwdChangedHook`, with the new `cwd`, only when that hook carries a `promptId` (`bundles/runtime/runtime/src/contracts/hooks.ts:35-72`), while the setting is on;
- only when the value differs from the entry's `lastCwd`, the `cwd` of the last binding the entry holds (after a restart it appends once more; a repeated value binds the same way). The hook first reads the events after the entry's cursor (D28), so a rewind read there has already updated `lastCwd`.

**The scoped call.** The runtime's Thread sink takes a row only with `projectId`, `threadId` and `promptId` in the call's scope (`bundles/runtime/runtime/src/contracts/events.ts:28-32`) and refuses any other with `invalid_scope` (`bundles/foundation/core/src/host/events/facade.ts:111-120`). The runtime runs both hooks with no parent call (`bundles/runtime/runtime/src/host/ports.ts:152-159`), and `CallOptions` carries no scope (`packages/bundle/src/contracts/call.ts:54-58`), so the host binds the scope itself: `services.use(EventsV1, { projectId, threadId, promptId }).append(cwdEvent, { cwd })`, with the hook's own ids (`packages/bundle/src/contracts/context.ts:24`). A move while no prompt runs has no `promptId`, so it appends nothing; the next prompt start appends, because its `cwd` then differs from `lastCwd`. A fence is written only by a prompt, after that prompt's start hook, so every fence is still bound to the working directory it was written in.

**Failures.** The runtime drops a hook's rejection (`ports.ts:152-159`), so the hook catches its own steps: a failed read of the events ends the hook; a failed append leaves `lastCwd` as it was, since `lastCwd` changes only through events read, so the next hook appends again; the steps after it still run.

Both hooks are awaited before the prompt's first model request or before the move answers its caller, so the event's `sequence` is lower than that of any turn written after it.

A papercraft fence is bound to the `cwd` of the last `papercraft.cwd/v1` event whose `sequence` is lower than the fence's `turnSequence` (the middle part of its key). Without one, its library answer is `none`. The event is durable, so replay binds each fence to the same working directory, and a rewind that removes the event rebinds the fences after it to the previous one. The host compiles the root's current content, so an old fence is drawn with the library as it is now (R23).

The binding does not depend on the skill or on a compile: the event is written in every Thread, including the prompt that first loads the `papercraft` skill, before the model writes anything. Papercraft's client registers a projector that claims `papercraft.cwd/v1` and returns no blocks (`chat.views/v1.registerProjector`, `bundles/desktop/chat/src/contracts/index.ts:48-56,69`); without a claim each event would become a generic block (`bundles/desktop/chat/src/client/domain/external-blocks.ts:1-7`). The claim is registered whatever the setting, so the events stay hidden after a rollback.

**How the host finds the event.** `events/v1.append` returns nothing (`packages/bundle/src/contracts/basic/events.ts:68-72`), so the host learns sequences by reading. Its per-Thread entry (D28) keeps a cursor and the `(sequence, cwd)` pairs read so far; a `library` call whose `turnSequence` is above the cursor reads the events after it with `runtime.threads/v1.threadEvents` (`bundles/runtime/runtime/src/contracts/threads.ts:437-441`) and advances it. Each event is read once per host session.

**Rewinds.** A rewind removes every row from the rewound prompt's first row on, sequence numbers are never reused, and it writes a marker row `{ type: 'history.truncated', afterSequence }`, where `afterSequence` is the last sequence it kept (`bundles/runtime/runtime/src/host/store/threads.ts:830-864`; `GROUNDING.md:2291-2296`). The marker's sequence is above every earlier one, so the entry reads it past its cursor like any event, and applies D28's rewind rule: the pairs above `afterSequence` are dropped and `lastCwd` becomes the `cwd` of the last pair left. So a live host binds a fence written after a rewind as a restarted host does, and the next hook appends the working directory again when the removed event was the last one (PC14).

#### Two repositories in one Thread

- One fence uses one library. A component that only another repository declares is unknown in that fence: OpenUI reports `unknown-component` and drops it (concept R6), the node shows the error, and [D18](openui.md#d18-validation-feedback-u19) reports it.
- A Thread that moves from repository A to repository B gets a new `papercraft.cwd/v1` event at the move, so fences written before the move use A and fences after it use B, and a new library instruct (D28).
- A patch whose base was written against A and that is written against B is drawn with B; A's components in the base become unknown. The skill tells the agent to start a new identity after moving to another repository.
- Mixing repositories in one fence is a non-goal. Namespacing components by repository would need no change to the binding, which is per fence.

#### Alternatives

- _One library for the whole Project_, merging every repository's components. Rejected: names collide across repositories, and a Thread working in one repository would be offered another's components.
- _A per-fence library named in the info string_ (` ```papercraft settings lib=apps/web `). Rejected: it adds a second word of custom protocol to every fence, and the binding already follows the working directory.
- _A `papercraft.library/v1` event written after each compile, with the root and hash_ (the earlier draft). Rejected: in the prompt that first loads the skill no compile had run, so its fences bound to no library permanently; and a fence written while a compile ran bound to the previous library.
- _Bind by the Thread's working directory when the fence is drawn._ Rejected: the Thread record holds only the current working directory (`bundles/runtime/runtime/src/contracts/model.ts:160-171`), so replay would bind old fences to wherever the Thread is now.

### D11. `schemas/` layout and the library module

#### Layout

- An entry file is a `*.ts`, `*.tsx`, `*.js` or `*.jsx` file directly in `.doric/papercraft/schemas/`. Files in subdirectories of `schemas/` are helpers that entry files may import; they are not entry files.
- **File-name order** is ascending by the UTF-16 code units of the file name, JavaScript's default string sort, which `entriesOf` already uses for bundle parts (`packages/bundle/src/build/parts.ts:280-289`). It orders the module's `components`, the instruct's lines (D28) and the file the ignore check tests (D8).
- An entry file declares one component: exactly one of its exports is a `defineComponent` result, and that component's `name` equals the file's base name (`AppButton.tsx` declares `AppButton`; `Button.tsx` declaring `Button` would fail, because `Button` is a react-ui built-in and reserved below). A file with none, with two, or with another name fails the compile with an error naming the file.
- A component name that a second file also declares, or that is reserved, fails the compile with an error naming both places, the reserved name's place being "a built-in of papercraft fences". The reserved names, which the runner checks after evaluation (D12):
  - every component of react-ui's library and papercraft's `Export`: `BUILTIN_COMPONENT_NAMES` in `src/sandbox/shim-names.ts`, which `scripts/shim-names.mjs` writes from `Object.keys(openuiLibrary.components)` of the installed `@openuidev/react-ui/genui-lib`, sorted, plus `Export`. PC28 fails when the committed file differs from what the script writes, so a react-ui version change fails the tests until the file is written again (D13);
  - every built-in call of lang-core, found with the runner's bundled lang-core, the frame's version (D13): a name for which `parseExpression` of the one statement in `split(tokenize('a = <name>()'))` gives a `Ref`, not a `Comp`. That covers the built-in functions (`Count`, `Filter`, `Sort`, `Each` and the others), the steps `Run`, `ToAssistant`, `OpenUrl`, `Set` and `Reset` (`dist/index.mjs:591-597,710-729`), which would parse as references and never render (D6);
  - `Action`, which the parser takes as a component call (`:2180`); `Query` and `Mutation`, the reserved calls (`:735-741`); and the conversation's `AskForm`, which D6's check names (U44). Overriding built-ins is not offered: a react-ui parent that refers to the overridden component would take a component with another schema ("Every parent points at the new one", lang-core 1.0.2 `dist/index.d.mts:624-633`).

#### Limits

Decided by U35.

At most 100 entry files, each at most 16 KiB, and at most 1 MiB for all of `schemas/`. A library over a limit fails the compile with an error naming the limit. The limits bound what the agent reads in the prompt that loads the skill (D28) and the size of the library instruct.

#### One module

The library job writes a generated entry that imports each entry file and exports `components`, the `defineComponent` results in file-name order; `papercraftAbi` (D13); and, when the library root has a harness, `Harness`, a component that applies the harness's decorators once around its `children` for the `theme` it is given (D15). esbuild bundles it into one ES module with today's Project resolution (`bundles/features/papercraft/src/host/bundle.ts:1-58`), whose rules stay as they are:

- React and ReactDOM, and each `@base-ui/react` specifier the window serves, stay external to the frame import map (`bundle.ts:31-38,155-162`; `packages/bundle/src/build/externals.ts:32-40`);
- `lucide-react` is left external by the runner and bundled by the host's second pass (`bundle.ts:46-49`, `compile.ts:211-216`);
- relative imports, `paths` aliases and the Project's packages resolve as today.

One rule comes before them, through a new option `BundleInput.shims` that only the library job sets: `@openuidev/react-lang`, `@openuidev/lang-core`, `zod`, `zod/v4` and `zod/v4/core` resolve to D13's shim modules, and any other `zod/*` entry fails with D13's error. `RunnerInput` (`src/sandbox/protocol.ts:13`) gains `kind?: 'bundle' | 'library'`, absent for today's jobs; `src/sandbox/main.ts`, which calls `runBundle` unconditionally today (`main.ts:18`), calls `runLibrary` from `src/sandbox/library.ts` when `kind` is `'library'` and `runBundle` (`run.ts:41`) otherwise. The host then compiles the CSS with today's Tailwind step (`bundles/features/papercraft/src/host/css.ts:1-35`) from the harness's global CSS (D15), and adds the paths that step read to the manifest (D14).

#### Without a Project sandbox

The library needs a lease: both the build and the evaluation run in the sandbox (D12). Without one, the library answer is `failed` with "The Project's sandbox is not running; repository components need it" (unless the host memo holds a result, D14), and the fence is drawn with built-ins.

### D12. Evaluation for signatures

#### Decision: under Node, in the same library job

Decided by U30.

After the module build, the runner bundles the generated entry a second time for `platform: 'node'` with these substitutions:

- `@openuidev/react-lang` → a shim exporting lang-core's `defineComponent` and `createLibrary`, and inert values for react-lang's React-only exports (lang-core's `defineComponent` stores `component` and never inspects it, lang-core 1.0.2 `dist/index.d.mts:556-578`);
- `zod`, `zod/v4` and `zod/v4/core` → the runner's own zod, the version the frame bundles (D13);
- every import that resolves outside `.doric/papercraft/schemas/` → a stub module (below), so component implementations, CSS and browser globals never run.

It then evaluates the bundle in a `node:worker_threads` worker, terminated after 10 s. The runner ships lang-core and zod bundled into `runner.mjs`, which the host copies into the sandbox once per version (`sandbox.ts:1-8`), and the sandbox has no Doric `node_modules`, so the worker gets them from the runner itself:

- **One file, two modes.** The runner writes the Node bundle to `<job>/evaluate.mjs`, inside the job folder the host removes, and starts `new Worker(new URL(import.meta.url), { workerData: { evaluate: '<job>/evaluate.mjs' } })`, so the worker runs `runner.mjs` again. `main.ts` first tests `isMainThread` from `node:worker_threads`; when it is false, it runs `evaluateInWorker(workerData)` from `src/sandbox/library.ts` and reads no `argv`.
- **One realm.** In the worker, `evaluateInWorker` sets `globalThis[Symbol.for('doric.papercraft.evaluate')]` to `{ langCore, zod, zodCore, reactLang, stub }`: the runner's own bundled lang-core, `zod` and `zod/v4/core`, the react-lang shim of the first substitution above, and the stub factory (below). The Node bundle's substitutions are generated modules that read that namespace, as D13's shims read the frame's, with the same name lists; each stub module calls `stub(origin)`. Then it imports `evaluate.mjs`, builds `createLibrary({ components })`, walks the props schemas, and takes each component's `signature` and `description` from `library.toSpec().components[name]` (lang-core 1.0.2 `dist/index.mjs:1800-1808`), which builds them with `buildSignature` from the schemas; the runner calls `buildSignature` with no `FieldInfo` of its own. So the evaluated code, `createLibrary`, the signatures, zod and the stubs' `WeakSet` are all in the worker's realm. It posts `{ components: { name, description, signature }[] }` or `{ error }` to the main thread, which writes the job's output.
- It then checks the reserved names of D11 with the same lang-core.

The host needs no JSON Schema: no host parses programs ([D18](openui.md#d18-validation-feedback-u19)).

#### Stubs

The runner generates one stub module per importer and specifier, so each stub knows its origin: the importing file and the import. Every export of a stub module, default included, is a stub value: a `Proxy` over a function that

- may be called or constructed, and returns a new stub value with the same origin and the call appended to its path;
- returns a new stub value for any property read, except `then` (undefined, so it is never a thenable) and `$$typeof` (undefined);
- throws `StubReadError` naming its origin when it is turned into a primitive (`Symbol.toPrimitive`, `valueOf`, `toString`), iterated (`Symbol.iterator`), or enumerated (the `ownKeys`, `has` and `getOwnPropertyDescriptor` traps).

So module-scope calls such as `forwardRef(…)`, `cva(…)` or `styled.div` evaluate without error, and `z.enum(variants)` with `variants` imported from `src/` throws, because zod enumerates the values. A stub that reaches a schema without being read, such as `z.string().max(LIMIT)` with a stubbed `LIMIT`, is found after evaluation: the runner walks each component's props schema (zod's `_zod.def`, recursively, with a visited set) and fails on any stub value it finds, checked through a `WeakSet` of every stub it created. The `component` field is not walked; a stub there is the intended case.

Either failure gives ``<entry file>: the schema reads `<import>` from `<specifier>`, which is outside schemas/. Schema values must come from schemas/ or from zod.``. A worker that does not finish in 10 s gives "Evaluating the schemas did not finish in 10 s".

#### The rule this imposes

Stated in the skill and in the error: a schema's values must come from `schemas/` or from zod.

#### Alternatives

- _Evaluate in the frame._ Rejected: the host needs the signatures with no window open (it runs Threads with no window, in `app/backend/doric-host`), and the frame realm cannot answer the host.
- _Evaluate with the real imports under Node._ Rejected: component modules import CSS, assets and browser globals at module scope; running them in Node is the failure mode the stubs avoid.
- _Stubs that throw on any use._ Rejected: harmless module-scope calls (`forwardRef`, `cva`, `styled`) would fail the whole library.
- _Static extraction without evaluation._ Rejected: zod schemas are values; their signatures exist only after evaluation.

#### If evaluation with stubs fails

Riskiest assumption 5 is not tested before shipping (U48). If the stub rule fails on real repositories, the option is to evaluate with real imports under Node, with CSS and assets mapped to empty modules, and report modules that throw. The user decides.

### D13. The version contract (R17)

#### Decision

- The frame's pinned versions are the contract: `@openuidev/react-lang` 1.0.2, `@openuidev/lang-core` 1.0.2, `@openuidev/react-ui` 0.18.1 (U9), and zod as installed for Doric (4.4.3, `node_modules/zod/package.json`; the root asks `^4.4.3`, `package.json:27`).
- A compiled library never carries its own copy. Its imports resolve to generated shims over the frame entry's namespaces:

  | Import                                        | Namespace                                                                                             |
  | --------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
  | `@openuidev/react-lang`                       | `reactLang`                                                                                           |
  | `@openuidev/lang-core`                        | `langCore`                                                                                            |
  | `zod`, `zod/v4`                               | `zod`: both are zod 4's classic API (`node_modules/zod/index.js:1-3`, `node_modules/zod/v4/index.js`) |
  | `zod/v4/core`                                 | `zodCore`, which lang-core imports separately from `zod/v4` (lang-core 1.0.2 `dist/index.d.mts:1-2`)  |
  | any other zod entry (`zod/mini`, `zod/v3`, …) | none: a compile error "This zod entry is not served in papercraft libraries; import from 'zod'."      |

  Each shim reads a namespace that the frame entry publishes before it imports a library module (D6): `const ns = globalThis[Symbol.for('doric.papercraft.openui')].<namespace>;`, then `export const <name> = ns.<name>;` for each name of the namespace's list and `export default ns.default;` when the list has `default`. So the library and the frame share one module instance, and a module names no URL. A URL would tie it to one papercraft version: the frame entry is served at `doric://app/bundles/papercraft@<version>/client/frames/openui.js`, which only the client resolves, at run time (`bundles/features/papercraft/src/client/frame-url.ts:1-20`).

- **The name lists.** `bundles/features/papercraft/src/sandbox/shim-names.ts` holds the four lists and `SHIM_ABI`, the SHA-256 of the lists as JSON. `bundles/features/papercraft/scripts/shim-names.mjs` writes it from `Object.keys` of each installed namespace, and the file is committed; PC28 fails when it differs from what the script writes, so a version change of the four packages fails the tests until the file is written again. The runner and the frame entry import the file; the runner already bundles every import, lang-core and zod included (`project.json:17`, `--bundle`).
- **The ABI check.** The library module exports `papercraftAbi`, the runner's `SHIM_ABI`. The frame entry compares it with its own before it builds the library. On a mismatch, which happens only when a window that loaded an older papercraft draws a library a newer host built, it draws the fence with built-ins and posts `error` with "The repository library was built for another version of Doric. Open this canvas in a new window."

- The repository's own versions of these packages are not checked. Its `package.json` has no effect at run time, because the shims replace every import of them. A schema that needs an API the frame's zod lacks fails D12's evaluation, which runs against the same zod, with an error naming the file; a repository on zod 3 whose schemas also work under zod 4 is accepted. Doric does not check or supply the repository's editor types.

#### Alternative

_Refuse a repository whose `package.json` asks for an incompatible range._ Rejected: it guards no failure that D12 does not already report, it refuses repositories whose schemas work, and it would make `semver` a new direct dependency (no `package.json` of this repository lists it).

### D14. Caching and serving (P7)

#### The library job

Decided by U30, with the limits of U35.

The window's `library` call starts it; so does papercraft's prompt-start hook, only while the setting is on and only in a Thread whose skill load the entry has found (U30, D28). The move hook starts none, so a Thread that never loaded the skill costs no job at its prompt starts. Its input is the bound `cwd` and, when the host memo has one for the root last found from that `cwd` in the same Project, the previous manifest. The runner:

1. walks up from `cwd` (D10) and answers `none`, or `failed` for a missing `cwd`;
2. when the root equals the previous one and every manifest path has the same SHA-256 (or is still absent), answers `unchanged` without building;
3. otherwise builds the module (D11), evaluates the signatures (D12) and runs the ignore check (D8). It answers `built`, with the module, the stylesheets it read, the signatures, the manifest and `ignoredBy`; or `failed`, with the error (at most 4,096 characters) and the manifest of what it read before failing.

The manifest lists every path the runner's reader looked up, found or not, and every Project path the host's CSS step then read: each stylesheet read through `files/v1` and each `url()` asset read through `readBytes` (`bundles/features/papercraft/src/host/css.ts:17-30,162-240`, `compile.ts:218-226`), each with the SHA-256 of the bytes read, or `null`. So a fix that creates a missing file changes it, and so does a changed nested `@import` sheet, font or image. Stylesheets the CSS step reads from Doric's own `node_modules` (`tailwindcss`, and a stylesheet package the Project lacks, `css.ts:17-22`) are not listed: they change only with papercraft's version, and a new version starts with an empty memo (below). Hashing runs in the sandbox: the runner hashes every listed path, its own and the host's, on local files; the host reads no Project file for the check.

#### Freshness

Each `library` call is answered by a job that started after the call arrived. Calls for the same Project and `cwd` share jobs: a call that arrives while a job runs waits for the next one, which starts when the current one ends and answers every call that waited. So twenty fences mounting at once cost at most two jobs. The check runs while the model writes the fence's first statement, since the element calls `library` when the fence opens.

#### Failures

- A `failed` answer is kept in the memo with its manifest, like a built one: an unchanged failing root costs one check per call, never a rebuild.
- A job that crashes or reaches the 120 s timeout answers `unavailable` (`sandbox.ts:118-123,175-179`). For a library job the host keeps that answer per Project and `cwd` for 5 minutes, and calls in that time answer `failed` with its reason without a job.
- A sandbox with no `node`, or whose runner reports another esbuild, answers `unavailable` too, and `bundleInSandbox` keeps that answer for the sandbox for the host session, with no job (`sandbox.ts:73-74,88-89,111-115,147-151`). A library call then answers `failed` with that reason, without the 5-minute hold, since the sandbox's image does not change; an `export` call builds through `files/v1` (D16).
- With no lease, no job runs (`sandbox.ts:201-229`): the host answers from the memo when it holds a result for the root last found from that `cwd` in that Project, else `failed` (D11). That answer is not kept under a root key or as a hold, since checking the lease costs no job; it is recorded as the `cwd`'s last answer (below), which the instruct reads.

#### Host memo

The memo is module state of papercraft's host, so a new papercraft version starts with an empty one. Its keys carry the Project, because every Project's workspace is `/workspace` (`GROUNDING.md:625-628`) and two Projects can have the same root path:

- `(projectId, 'library', root)` and `(projectId, 'export', '<path>#<name>')`, with `<path>#` when `name` is absent (D16), each holding the last answer, its manifest (none for a `files/v1` build, D16), its module bytes and, for a library, its signatures;
- per Project too, keyed by `(projectId, cwd)`: the 5-minute hold, and the `cwd`'s last answer, `{ root: string } | { none: true } | { failed: string }`. It is set by every `library` answer for that `cwd`, from a job, the memo, the hold or a missing lease: `root` when the answer names one (`ready`, or `failed` with a `root`), `none` for `none`, and `failed` with the error for a `failed` answer without a root (a missing `cwd`, a crashed or timed-out job, the hold, a sandbox with no `node` or another esbuild, no lease). "The root last found from that `cwd`" is its `root`. The instruct reads it (D28), so every failure reaches the agent, with or without a root.

The module bytes of all keys of all Projects together are capped at 64 MiB per host (U35); above it, the keys used least recently (by `library`, `export` or `read`) are dropped with their manifests until the total is under the cap, and their next call rebuilds. Nothing is written to the workspace except, in `.doric/papercraft/`, the runner copy (`sandbox.ts:4-8,92`), the job folders, which each job removes, and `.gitignore`, plus D8's one-time migration (G4, U40).

#### Jobs per Project

A Project runs at most two runner jobs at once; later jobs wait in a first-in, first-out queue, with library jobs ahead of export jobs.

#### Desktop cache

The verified cache (`bundles/features/artifacts/src/desktop/cache.ts`, 240 lines) is copied to papercraft's desktop part as `papercraft.cache/v1` (desktopMain), with one method, `ensure({ entries: { path: '<dir>/<file>', sha256, base64 }[] })`, which writes a file only after its SHA-256 matches, staged and renamed into place as today (`cache.ts:150-169`). The artifacts bundle keeps its own until stage 4, for the old path. `ensure` sets the modification time of each `<dir>/` directory it writes or keeps.

- **Root.** A desktop part learns its directory only through `doric.cache/v1`, which the kernel resolves to `join(root, bundleId)` (`app/desktop/doric/src/platform/native/cache.ts:12-27`), with `root` `userData/bundle-cache/` except for `artifacts`, which the kernel puts under `userData` so that the protocol can serve it (`app/desktop/doric/src/platform/app.ts:310-319`). The kernel treats `papercraft` the same way: its directory is `userData/papercraft/`, a new `DesktopPaths.papercraftModules` (`app/desktop/doric/src/platform/paths.ts:4-31`), and the protocol is given that root beside `artifacts` (`app.ts:516-524`).
- **When it is read.** `doric.*` services answer nothing during the build's dry activation, so the part asks for its directory at the first `ensure`, as the artifacts cache does (`bundles/features/artifacts/src/desktop/index.ts:11-13`).
- **Cut-back.** Once per desktop app session, the first `ensure` cuts the cache back before it writes, and every `ensure` awaits that cut-back: when the root holds more than 256 MiB, whole `<dir>/` directories are deleted, oldest modification time first, until it holds at most 128 MiB (U35, U45). A frame loads a module only after its window's `ensure` for it has resolved ([The window's steps](#the-windows-steps)), so no module a frame is loading disappears.

#### Route

The protocol serves the cache at `doric://app/papercraft-modules/<dir>/<file>` with `Access-Control-Allow-Origin: *` for frames, beside `/artifacts/*` until stage 4 (`app/desktop/doric/src/platform/protocol/handler.ts:118,134,215-232,393`; `GROUNDING.md:1669-1680`). `ServedModules { root }` is added beside `ServedArtifacts`, which stage 4 removes. The CSP does not change: `script-src doric://app` already covers it (`csp.ts:47-58`).

#### Host contract

`papercraft.programs/v1@1.0.0`, its three methods `expose: 'desktop'`; the manifest's `desktopScope` gains `"papercraft.programs/v1": ["projectId", "threadId"]` and `"papercraft.cache/v1": ["projectId", "threadId"]` beside today's `papercraft.previews/v1` entry (`bundles/features/papercraft/manifest.json:40-42`). A key a manifest does not list for a contract is refused at the IPC (`packages/bundle/src/runtime/manifest.ts:111-114`); the window calls `services.use(PapercraftCacheV1, { projectId, threadId }).ensure(…)` with its fence's Project and Thread, as the artifacts window calls its cache with a scoped call (`bundles/features/artifacts/manifest.json:27-30`, `bundles/features/papercraft/src/client/surface/preview-data.ts:181-183`). The cache ignores the scope: its paths are content-addressed. It holds the module methods only; a papercraft fence's errors go to `openui.programs/v1` ([D18](openui.md#d18-validation-feedback-u19)):

```ts
interface ModuleRef {
  /** The cache directory: the SHA-256 of the files' `<path>:<sha256>` lines, sorted by path and joined by `\n`. */
  readonly dir: string;
  /**
   * `index.js`; `index.css` when the module has a sheet; and `assets/<sha256>.<ext>`
   * for each `url()` asset the sheet names (`css.ts:24-29,162-240`; `compile.ts:228-236`).
   */
  readonly files: readonly {
    readonly path: string;
    readonly sha256: string;
  }[];
}

type LibraryAnswer =
  | { readonly status: 'none' }
  | {
      readonly status: 'ready';
      readonly root: string;
      readonly module: ModuleRef;
    }
  | {
      readonly status: 'failed';
      readonly root?: string;
      readonly error: string; // at most 4,096 characters
    };

type ExportAnswer =
  | { readonly status: 'ready'; readonly module: ModuleRef }
  | { readonly status: 'failed'; readonly error: string };

interface Programs {
  /** The library bound at `turnSequence` (D10), checked and built as above. */
  library(
    input: { readonly turnSequence: number },
    call?: CallArg,
  ): Promise<LibraryAnswer>;
  /** One export or story of a workspace file (D16). */
  export(
    input: { readonly path: string; readonly name?: string },
    call?: CallArg,
  ): Promise<ExportAnswer>;
  /**
   * The bytes of a module the memo holds, each entry's `path` `<dir>/<file>`
   * as `ensure` takes it. Throws ContractError `not_found` when no memo key
   * holds a module with that `dir`; the caller asks `library` or `export`
   * again, once, and when the new answer's `read` also throws `not_found`, it
   * takes the answer as `failed` with "The module could not be read from the host".
   */
  read(
    input: { readonly dir: string },
    call?: CallArg,
  ): Promise<{
    readonly entries: readonly {
      readonly path: string;
      readonly sha256: string;
      readonly base64: string;
    }[];
  }>;
}
```

#### The window's steps

The window keeps, for its life, the set of module `dir`s it has ensured. For each answer it `read`s and `ensure`s only modules not in that set, then hands the URLs to the frame: `module` is `doric://app/papercraft-modules/<dir>/index.js`, and `styles` is `doric://app/papercraft-modules/<dir>/index.css` when `files` lists `index.css`. The sheet names its assets as `assets/<sha256>.<ext>`, relative to itself, so they load from the same directory.

#### What the fence shows while the library is not ready

- **Pending.** The element sends no `init` until `library` answers. The canvas node shows the program source and "Loading the repository library…".
- **`failed`.** The fence is drawn with built-ins only, under a line "Drawn without the repository library: <error>". Its errors are not reported (U23; step 9 of the [Overview](#overview)), because every repository component would be a false `unknown-component`; the agent learns of the failure from the library instruct (D28), which reads the `cwd`'s last answer, with or without a root (D14).
- **`none` or `ready`.** Drawn, and its errors reported.

### D15. Harness and theme for library components (concept Q1 rest, Q5)

- **Harness.** The nearest harness of the library root is compiled into the library module. The search starts at the library root (the walk skips any directory inside `.doric/`, `harness.ts:35-36`) and goes up as today (`harness.ts:39-74`), except that it stops after the nearest repository root, as D10's walk does. The stop applies to `Export` builds too, so a file in a nested repository never takes an outer repository's providers or CSS. A preview of a nested repository that relied on an outer harness loses it (U32).
- **The stop's mechanism.** `findHarness(read, sourcePath)` (`bundles/features/papercraft/src/host/harness.ts:64-74`) gains a third parameter, `isRepositoryRoot: (dir: string) => Promise<boolean>`; after it checks a directory's candidates, the walk stops when that directory answers `true`. `bundleComponent` takes the probe beside `read` and passes it (`bundle.ts:1017`). Its two readers each get one:
  - the runner's disk reader (`src/sandbox/run.ts:20-35`): `fs.stat(join(root, dir, '.git'))` resolves, for a directory or a file;
  - the host's `files/v1` reader, for the fallback (D16): `files/v1.content({ path: '<dir>/.git' })` answers `read` (a `.git` file) or `not_file` (a `.git` directory); `not_found`, any other answer and a Project with no lease are `false`. `content` stats the path with `workspacePathKind`, which hides nothing (`packages/sandbox/src/lib/files.ts:313-324`, `bundles/features/files/src/host/reads.ts:69-78`), while `directory` cannot serve: its listing prunes `.git` and hides every dot entry but `.agents` (`files.ts:23-24,50-53,660-664`). A `.git` file is a few bytes, so the read stays under `content`'s limit.
- **One wrap (U30).** The frame renders the library's `Harness` around `Renderer`, so the harness's decorators wrap the whole output once, in one React root, so providers such as router, query client, store, i18n and theme reach every repository component. Its global CSS import is the input of the library's Tailwind sheet, as for previews today (`harness.ts:4-8`).
- **Theme (U34).** Repository components keep the repository's own CSS. react-ui components take Doric's tokens through `--openui-*` variables, from Doric's hand-written token sheet ([D31](openui.md#d31-the-built-in-library-and-dorics-tokens)), for the light and dark themes. Two design systems share one frame (concept R11); whether repository components look as in the product (G5) is not measured before shipping (U48).
- **If the wrap changes layout.** If the harness wrap changes a repository component's layout in use, the option is to wrap each repository component separately. The user decides.

### D16. The export component

- `Export(path: string, name?: string, props?: Record<string, unknown>)` is a papercraft built-in with an unvalidated `props` (U14). `path` is workspace-relative, as `papercraft_preview` takes it today (`bundles/features/papercraft/src/contracts/index.ts:43-46`).
- The app parses the revision's `program` with lang-core and collects `Export` calls whose `path` and `name` are string literals. While the fence streams, that program holds only completed statements ([D4](openui.md#d4-the-program-reducer)), so a half-written path is never collected. Each distinct `<path>#<name>` (`<path>#` when `name` is absent) is built once through `papercraft.programs/v1.export`, which runs today's pipeline: the export choice (`pickExport`, `bundles/features/papercraft/src/host/bundle.ts:338-368`), the story mount and the harness (D15). It runs in the sandbox first and through `files/v1` when the sandbox cannot (`compile.ts:3-7`); the manifest check of D14 applies to sandbox builds. A `files/v1` build rebuilds on each call under that reader's budget (`bundle.ts:136-139`); its answer is kept under its memo key with no manifest, so `read` serves its bytes, and the next `export` call for the key builds again.
- `export` checks `path` with today's `projectPath(from, specifier)` (`bundles/features/papercraft/src/host/paths.ts:41-55`), called as `projectPath('.', path)`: `posix.dirname('.')` is `.`, so a workspace-relative path resolves from the workspace root, and a leading `/` is the root too. A path that leaves the Project answers `failed` with "The path leaves the Project".
- In the frame, `Export` renders a `<div>` and calls the module's `mount(root, { theme, args: props })`. Today's `mount(root, { theme })` (`runtime.ts:542`) gains `args`, which are spread over the story args, or become the component's props for a plain component, which today renders with none (`entry.ts:28-29`).
- An `Export` whose `path` is not a literal, or that is not built yet, shows a placeholder. A build failure shows its error in the node and is reported as `{ code: 'render-error', statementId, message: 'Export <path>#<name> did not build: <error>' }`, cut to 300 characters. Props errors appear only when the component throws, as `render-error` (concept R18).
- At most 8 distinct exports per program: the first 8 keys in the order of their first call in the current revision's program are built, and a key that a later revision no longer calls stops counting. Each call of a ninth or later key shows "Too many exports in one program" and is reported as `{ code: 'runtime-error', statementId, message: 'Too many exports in one program: at most 8.' }`. Builds go through D14's queue, so a program's exports build at most two at a time, each within the 120 s job timeout.
- Because the app, not the frame, finds the calls, the frame never asks the host for anything.

### D19. Comments and pins (P6, U6, U11)

The target kind and the anchor follow U33.

- **Target.** `{ kind: 'papercraft-program', id: <identity>, revision }`. `comments/v1` never interprets a target (`bundles/features/comments/src/host/comments.ts:1-12`) and folds only the call's Thread log, so an identity needs no Thread prefix. Comments on artifacts carry the target kind `artifact` (`ARTIFACT_TARGET_KIND`, `bundles/features/papercraft/src/contracts/index.ts:457`; `docs/architecture/bundles/comments.md:24`), so they never match a program.
- **Stack kind.** A draft on the composer stack has today's item kind `papercraft-preview` (`PAPERCRAFT_COMMENT_KIND`, `contracts/index.ts:612`), flushed by `papercraftFlush` (`bundles/features/papercraft/src/desktop/comment-flush.ts:1-45`, registered at `src/desktop/index.ts:29-36`). A program's drafts get the kind `papercraft-program` (U33), flushed by a second function, `programFlush`, in the same file: the same rules, with the program target the item's data records. Its data has today's shape, `PreviewItemData` (`contracts/index.ts:620-630`), so chat's line, which reads `target` and `refs` (`:613-618`), and `previewItemTargetOf` (`:642-660`) read it unchanged: `target` is `{ kind: 'papercraft-program', id: <identity>, revision, anchor }`; `pin` numbers the pins `1`, `2`, … per identity and revision; `inReplyTo` and `point` are as today; `refs` is `{ title: <identity> }`, with no `source`, since a program has no source file. Both kinds and both flushes are registered from stage 2 on, in stage 4 too, so a draft of either kind left in a stack still sends.
- **Existing comments.** No stored comment changes. Comments with the kind `artifact` stay in the log, chat keeps drawing them in the turns that sent them, and from stage 4 no canvas lists them. This keeps U33's list of persisted data as it is.
- **Anchor.** `{ form: 'selector', selector: <statement name>, label: <component name> }`, from the scene node's `statement` and `component` (D6). A click inside a portal, or with no named statement above it, falls back to `{ form: 'point', x, y, label }` with the nearest component's name (concept R14). A click on an inline component anchors to its nearest named ancestor.
- **Pins.** A pin is placed on the scene node whose `statement` equals the anchor's `selector`. When the shown revision has no such statement, the pin is detached and drawn in the node's margin, as today's detached pins.
- **Revisions.** Every revision shows every comment thread of its identity (as today, `bundles/features/papercraft/src/client/surface/thread-open.ts:3-4`). The lists and the thread-open check compare the target's kind and id with `targetKeyOf` (D26) instead of `ARTIFACT_TARGET_KIND` and the artifact id (`thread-open.ts:34-42`, `threads-view.ts:170-182`, `preview-data.ts:308-325`, `anchor.ts:134-143`). The envelope reads `<target kind="papercraft-program" id="settings" revision="2">` (`bundles/desktop/chat/src/client/domain/prompt-envelope.ts:1-13`).
- `comment_reply` stays.
- **If wrappers change layout** (riskiest assumption 3, R14). If statement wrappers change layout in use, the option is to put the data attributes on the element of components whose renderer returns a single element, with no wrapper; all others anchor by `point`.

### D26. The canvas and its window

The route keyed by identity is U33's.

- **Keys.** Frame memory, snapshots, live frames, controllers and the canvas registry are keyed by the canvas id (Terms) instead of the artifact id: their `artifactId` parameters become `canvasId` (`bundles/features/papercraft/src/client/surface/frame-memory.ts:45-60`, `snapshots.ts:32,56`, `controller.ts:32-174`, `bundles/features/papercraft/src/client/canvas-registry.ts:13-70`), and the old path passes the artifact id, so its keys do not change. Live frames already take the `frameKeyOf` string (`live-frames.ts:109-122`) and do not change. A closed revision is immutable, so its snapshot key adds the theme and width, as today. A streaming or unterminated revision is never snapshotted.
- **The source.** `bundles/features/papercraft/src/client/surface/canvas-source.ts` (new):

- **Route.** `CANVAS_ROUTE` becomes `/papercraft/:projectId/:threadId/:identity` (concept Q8), one route for both kinds, since an artifact id and an identity both fill the last segment (`bundles/features/papercraft/src/contracts/index.ts:555-563`, `src/client/elements.tsx:11`). ### D28. The papercraft skill and the library instruct

#### The skill

The `papercraft` skill ([D17](openui.md#d17-instructions-the-skills-u13-concept-q3)) is a committed text, `bundles/features/papercraft/src/host/skills/papercraft.md`, at most 8,000 characters. The host registers it through `skills/v1.register` while the setting is on ([D24](openui.md#d24-the-setting-and-rollback)), with:

- `order: 3410`, its position in `skills/v1.list()`, ascending (`packages/bundle/src/contracts/basic/skills.ts:26-29`): after `openui`'s 3400 and, in stages 2–3, `papercraft-preview`'s 3400 (`src/skills/papercraft-preview/SKILL.md:9`), which `skills/v1` orders between themselves by registration (`bundles/foundation/core/src/host/skills.ts:19-22`);
- `allowedTools: ['comment_reply']`, the tools the skill uses; registration fails with `unavailable_tool` when one is not registered (`skills.ts:33-39`; `bundles/foundation/core/src/host/skills.ts:61-67`). `comment_reply` is registered by `comments` at its activation (`bundles/features/comments/src/host/index.ts:1-3`), and papercraft requires `comments/v1` (`manifest.json`), so `comments` activates first and the registration finds the tool. A registration that still throws is caught: the skill stays unregistered until the setting next turns on, and fences draw as before, since they do not depend on the skill.

Its rules:

- first: "Load the `openui` skill first if it is not loaded; it teaches the language and the built-in components.";
- the fence tag and identity (` ```papercraft <identity> `), with an example of a new preview and a patch; use it to preview repository components or exports, and ` ```openui-lang ` for any other UI ([D7](openui.md#d7-render-hosts-and-routing));
- `Export(path, name?, props?)` (D16);
- `Query` and `Mutation` do not exist in papercraft fences; write data as literals (D6);
- after moving to another repository, start a new identity (D10);
- after editing files under `.doric/papercraft/schemas/`, the new signatures arrive at the next prompt; a fence draws the files as they are when it is drawn;
- in the prompt that loads the skill (below): "If no repository library instruction is in your context and `.doric/papercraft/schemas/` exists in this repository, list it and read the file of each component you use before you write a fence that uses it.";
- the authoring rules of D11 and D12 for schema files;
- comments arrive in `<comments>` under a `papercraft-program` target and are answered with `comment_reply` (D19); a papercraft fence has local state only, and the reader answers a preview with pinned comments (D6).

#### Knowing that the skill was loaded

papercraft reads it from the Thread log: a `tool.started` event whose `call.name` is `load_skill` and whose `call.payload.name` is `papercraft`, followed by its `tool.finished` (the shapes the chat reads, `bundles/desktop/chat/src/client/domain/projector.ts:754-773`). The host's per-Thread entry keeps a cursor: at each hook in a Thread not yet marked, it reads only the events after the cursor (`threadEvents`, `threads.ts:437-441`) and advances it; once the load is found, the entry records its sequence as `skillLoadedAt`. Every hook still reads the events after the cursor, for the cwd events and for rewinds (D10). Each event is read once per host session. No new hook is added. The scan depends on `default`'s tool name and input, which R36 names.

#### The per-Thread entry

`{ cursor, skillLoadedAt?: number, bindings: (sequence, cwd)[], lastCwd?: string, lastInstruct?: { root: string | null, digest?: string } }` (`root` is `null` for the `none` text and for a failure without a root), in memory, one per Thread that had a prompt start, a move or a `library` call in this host session, kept until the host stops. The skill is loaded when `skillLoadedAt` is set. `bindings` gains one pair per `papercraft.cwd/v1` event, which is written only when the working directory changes (D10), so an entry grows with a Thread's moves, as its log does. There is no cap: no measure supports one, and U35's limits do not include one.

**The rewind rule.** When the entry reads a `history.truncated` row with `afterSequence` a (D10):

- `bindings` drops every pair whose sequence is above a, and `lastCwd` becomes the `cwd` of the last pair left, or none;
- `skillLoadedAt` is cleared when it is above a, since the `load_skill` call it found was removed; the events read after the marker can set it again;
- `lastInstruct` keeps its `root` and loses its `digest`. A rewind forgets the retained messages past its boundary (`GROUNDING.md:759-762`), and the entry cannot tell whether its last instruct was among them, so the next hook with the skill loaded gives the current text again, the "No repository library here" text included when `root` was set. At worst the context holds the same instruct once, since one retained instruct per bundle and reason replaces the other (R35).

#### The library instruct

`reason: 'library'`, `retain: true`, through `runtime.threads/v1.instruct` (`threads.ts:391-409`). The executor keeps one per bundle and reason through every compaction (`bundles/runtime/runtime/src/contracts/model.ts:214-219`), so the newest replaces the older one.

- **When.** Only inside the two awaited hooks, while the setting is on and the Thread's skill is loaded:
  - at `onPromptStartedHook`, with the starting prompt's `promptId`, so it steers that prompt before its first model request and never starts one: the runner marks the prompt active before it awaits the hook (`bundles/runtime/runtime/src/host/domain/runner.ts:493,510`), and an instruct for the active prompt is not queued (`:944-957`);
  - at `onThreadCwdChangedHook`, only when the hook carries a `promptId` (a prompt is running), so it steers that prompt at its next safe point, after the tool batch that moved it. A move while nothing runs gives no instruct; the next prompt start does.
- **What the hook does.** In this order, each step after a failed one still running except where stated (D10's failure rule):
  1. It reads the events after the cursor and applies them (cwd pairs, the skill load, rewinds). A failed read ends the hook.
  2. It appends the `papercraft.cwd/v1` event when the working directory differs from `lastCwd` and the hook has a `promptId` (D10).
  3. It reads the `cwd`'s last answer in this Project (D14) and, for a `root`, that root's memo entry. When the skill is loaded and that gives a text whose SHA-256 differs from `lastInstruct.digest` (a missing digest differs from every text), it gives the instruct with the hook's `promptId` and records `{ root, digest }`, `root` being `null` for `none` and for a failure without a root. A rejected `instruct` records nothing, so the next hook tries again.
  4. At `onPromptStartedHook` only, with the skill loaded and the setting on, it starts a library job for the working directory without awaiting it, so the next hook has a fresh answer, also in a Thread no window shows (D14). The move hook starts no job.

  It awaits no job. With the setting off, the hook does nothing at all: it reads no events, appends nothing, gives no instruct and starts no job.

- **Text.** One of:
  - for a `ready` root: `Repository library at <root>: <n> components.`, then one line per component in file-name order (D11), `<signature> — <description>`, then the `ignoredBy` line of D8 when there is one. The whole text, the last line included, is at most 16,000 characters: when the next component's line would make the text plus a final line `Also: <names, joined by ", ">; read their schema files for their props.` and the `ignoredBy` line longer than that, the remaining components go into that final line instead, which counts toward the limit. 100 names of at most 64 characters each fit in about 6,600 characters, so the final line always fits;
  - for `none`: "No repository library here; use built-in components only.", given only when `lastInstruct.root` was a root;
  - for a root whose answer is `failed`: `The repository library at <root> did not compile: <error>`;
  - for a failure without a root: `The repository library could not be checked: <error>`, for example "The repository library could not be checked: The Project's sandbox is not running; repository components need it".
- **Cost.** A library compile that finishes after the hook is used at the next hook; it never starts a prompt or adds a model request. After a move during a prompt, the move hook finds the new working directory's last answer only when a window or an earlier prompt start built it, so the new library's instruct can arrive one prompt start later. After a host restart a Thread may get the same instruct once more, because `lastInstruct` is empty.

#### The prompt that loads the skill

Its hooks ran before the load, so it has no library instruct. Its fences are still bound (D10) and drawn with the library once it is built (D14). For writing them, the skill's rule has the agent list `schemas/` and read the file of each component it uses: one file per component, each at most 16 KiB (D11).

#### Alternatives

- _A new hook `onSkillLoadedHook` in `default.hooks/v1`_, fired by `load_skill`, so the instruct arrives within the loading prompt. Rejected: it adds a public contract to `default` for one consumer, and the instruct would still need a compile; when the compile outlasts the `load_skill` batch, the model has already written its fence. Reading the files covers that prompt without a contract.
- _Give the instruct when a compile finishes_ (the earlier draft). Rejected: an instruct while nothing runs is queued and starts a prompt (`threads.ts:391-409`, `bundles/runtime/runtime/src/host/domain/runner.ts:944-957`), and one taken before the final answer adds a model request.
- _Await the compile in the hook._ Rejected: a cold compile can take up to the 120 s job timeout, before the prompt's first model request.
- _A read-only query owned by `default`_, such as `default.skills/v1.loaded({ threadId })`, answered from `default`'s own reading of loaded skills (`bundles/runtime/default/src/host/skills/loaded.ts:139-239`), read inside the two hooks. Rejected: `default` reads a Thread's history only through the reader the runtime passes into `run`, `checkpoint`, `rewind` and compaction (`HistoryReader`, `bundles/runtime/runtime/src/contracts/executor.ts:42-56,126-150`), and a running prompt's history is in the executor's memory until it is saved (`bundles/runtime/default/src/host/executor.ts:367-375`). So the query needs a runtime contract for reading a history on demand plus a new `default` contract, for one consumer. The log scan's coupling is R36.
- _Watch the Thread log during each prompt for the `load_skill` call._ Rejected: it needs a log subscription per running prompt and its teardown when the prompt ends; no host bundle watches a Thread log today.
- _Give the library instruct in every Thread whose working directory has a library_, loaded skill or not. Rejected by U13: the signatures reach the model once papercraft's skill is loaded.

## Risks

The concept's risks stand with the mitigations here and in [openui.md](openui.md#risks). Risk numbers do not repeat across the three documents: the concept has R1–R19, [openui.md](openui.md#risks) uses R25 and R28–R31, [conversation-openui.md](conversation-openui.md#risks) R24, R26, R27, R32 and R33, and this document R20–R23 and R34–R37. Papercraft's:

- **R14 Statement wrappers change layout.** Mitigated by `display: contents` wrappers, with D19's option if they change layout in use.
- **R17 Version coupling.** Mitigated by D13.
- **R20 Long first compile.** A first library build can take up to the 120 s job timeout (`RUNNER_TIMEOUT_MS`, `sandbox.ts:64-65`). Mitigation: the fence shows its source and a loading line until the library is built (D14); no prompt waits for it, and the instruct arrives at the next hook (D28).
- **R21 Ignored schemas.** A repository that ignores `.doric` loses its library on clone. Mitigation: the library job's ignore check and the instruct's line (D8).
- **R22 Schema evaluation rule.** Schemas that compute values from repository code fail D12. Mitigation: the rule is in the skill and in the error; D12 names the option of real imports.
- **R23 Stale library for old fences.** An old fence is drawn with the current library (D10), so it can differ from what the reader saw then. Accepted: artifacts' immutable bytes are gone by U4.
- **R34 No sandbox when a Thread is read.** A reader who opens an old Thread with no lease sees its fences drawn with built-ins, unless the host memo of this host session holds the library. Accepted: the source and the error line are shown, and no false error reaches the agent (D14).
- **R35 Instruct repeated after a restart.** A Thread may get the same library instruct once more after a host restart (D28). Accepted: one retained instruct replaces the other, so the context holds one.
- **R36 The skill load read from the log.** papercraft finds the load in `tool.started` events by `default`'s tool name `load_skill` (`bundles/runtime/default/src/host/skills/load-skill.ts:44`) and its input `name`, neither of which is a contract. If `default` renames or reshapes the tool, the library instruct stops arriving and nothing reports it. Mitigation: PC23 runs both real bundles and fails on such a change. And papercraft's mark never clears, while `default` can cut skill texts from its loaded-skills message (`LOADED_SKILLS_MAX_CHARS`, `loaded.ts:14,27`), so the signatures can stay in a context that no longer holds the skill's full text. Accepted: the instruct is at most 16,000 characters, it states what it is, and the `openui` skill still teaches the language.
- **R37 Reserved names in a shadcn repository.** A shadcn/ui repository names its components Button, Card, Input, Select, Table and Tabs, which are react-ui 0.18.1 built-ins that D11 reserves, so a library that keeps those names fails the compile. Mitigation: the compile error names the reserved name's place, "a built-in of papercraft fences" (D11), and a library declares other names, for example with a prefix such as `App` (D11's example, `AppButton`).
- **Security.** The frame stays an opaque origin under the unchanged frame CSP (U3). The frame sends only data (`errors`, scene, input events); the app validates every message's schema and size; frame errors reach the host as a code and a checked statement name only ([D18](openui.md#d18-validation-feedback-u19)); the frame never triggers a build (D16) and sends nothing toward the conversation (D6). Compile, evaluation and build errors are toolchain output over repository files, the same kind of text today's `papercraft_preview` returns to the agent as a tool error (`sandbox.ts:13-14`); they are capped at 4,096 characters in the instruct and 300 in a report. `Export` paths are checked by `projectPath` (D16).
- **Scale.** Per Project: at most two runner jobs at once (D14). Per host: module bytes in the memo at most 64 MiB, for all Projects together (D14); one per-Thread entry for each Thread active in the host session, growing by one binding per working-directory change (D28). Per instruct: at most 16,000 characters (D28). Per library: at most 100 entry files, 16 KiB each, 1 MiB in all (D11). Per program: at most 8 exports (D16). Per frame message: at most 50 errors (D6). Per window: at most 3 live frames (D6). On disk: the desktop cache is cut to 128 MiB at the first `ensure` of each app session when above 256 MiB; during one app session it only grows (D14).
