# Doric renderer shell

`doric-renderer` (Nx project `doric-renderer`) builds the shell: the one page every Doric desktop window loads from `doric://app`. The shell holds no product UI. It keeps the `dark` class in step with the page's `prefers-color-scheme`, which follows the theme main shows: the saved preference, `dark` when nothing is saved ([`src/scheme.ts`](src/scheme.ts), [`appearance.ts`](../doric/src/platform/appearance.ts)). It boots the window through `desktop/client`'s `bootstrapWindow`, and carries the window-wide stylesheet; the workspace, the conversation and the settings are drawn by client bundles. The Electron main process serves the build and renders its HTML template per request, adding the import map, the platform theme and the content security policy.

The feature doc is [the workspace window](../../../docs/features/ui-redesign.md), which covers the window's frame, its 40 px bars and the footer weight; the theme preference and the `dark` class are in [window appearance](../../../docs/architecture/bundles/window-appearance.md#theme). The main process that serves the shell is described in the [desktop README](../doric/README.md); the protocol that serves it, in [the `doric://app` protocol](../../../docs/architecture/bundles/doric-protocol.md); how a window boots from it, in [windows](../../../docs/architecture/bundles/windows.md); the shared packages and the theme tokens, in [platform packages](../../../docs/architecture/bundles/platform-packages.md). `bootstrapWindow`, the window–main protocol, `insertBundleStyles` and `theme.css` belong to the `desktop` package and are described in full in the [`packages/desktop` README](../../../packages/desktop/README.md).

## What a window loads

The shell's files live under the URL prefix `/platform/shell@<v>/`, where `<v>` is `PLATFORM_ASSETS_VERSION`, `1.0.0` ([`version.ts`](../../../packages/bundle/src/runtime/version.ts), [`resources.ts`](../doric/src/platform/protocol/resources.ts)). The build writes the prefix as a literal instead: `shellPath` in [`webpack.config.js`](webpack.config.js) and the favicon link in [`src/shell.html`](src/shell.html) both say `/platform/shell@1.0.0/`, and nothing ties that literal to `PLATFORM_ASSETS_VERSION`. When the two differ, packaged, the protocol's `route()` takes `/platform/shell@1.0.0/…` for an ordinary platform file and looks for it in the platform assets, so every shell file the template names is a `404` ([`handler.ts`](../doric/src/platform/protocol/handler.ts)); in development main fetches `/platform/shell@<v>/shell.html` from the dev server, which serves only `/platform/shell@1.0.0/`, so rendering the shell fails ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)).

A window loads `doric://app/<path>`. For any path outside the asset prefixes (`/platform/`, `/bundles/`, `/schemas/`, `/frame/`, `/papercraft-modules/`), main's protocol handler answers a navigation with the rendered shell and a `content-security-policy` header. A request is a navigation when its `Sec-Fetch-Dest` header, if present, is `document`; without that header, when its `Accept` header names `text/html` or `application/xhtml+xml`, or when it has no `Accept` header. Any other request, and any path whose last segment carries a file extension, is a `404` ([`handler.ts`](../doric/src/platform/protocol/handler.ts)). A request under `/platform/shell@<v>/<file…>` is a file of this build: read from `doric-renderer/` beside the built main process (`dist/app/desktop/doric-renderer` in the workspace) when packaged, forwarded to the dev server otherwise ([`handler.ts`](../doric/src/platform/protocol/handler.ts), [`resources.ts`](../doric/src/platform/protocol/resources.ts)). The full routing table is in [the `doric://app` protocol](../../../docs/architecture/bundles/doric-protocol.md#what-the-handler-serves).

### The rendered template

Main renders the shell for each request from the built `shell.html` ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`app.ts`](../doric/src/platform/app.ts)):

1. It takes the template. Packaged, it reads `shell.html` from the shell root once and caches it; a failed read clears the cache, so the next request reads again. In development it fetches `<dev-server>/platform/shell@<v>/shell.html` on every request, and a status other than 2xx is an error ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)).
2. It inserts, right after the opening `<head>` tag and before everything the template holds:
   1. `<meta name="doric-generation" content="<n>">`, the newest client generation, only when there is one;
   2. `<script type="importmap">` holding `{"imports": {…}}`, with every `<` written as `\u003c`;
   3. `<link rel="stylesheet" href="/platform/desktop@<v>/theme.css">`, the theme of `desktop/ui`.
3. It answers with `content-type: text/html` and the policy of its mode.

A template without a `<head>` element makes `renderShell` throw `The shell template has no <head> element.`; that error, like a failed template read or a dev server answer other than 2xx (`The renderer dev server answered <status> for shell.html.`), rejects the protocol handler's answer, so the navigation fails ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`handler.ts`](../doric/src/platform/protocol/handler.ts), [`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)). Main's `loadURL` of the window then rejects, and the call that opened or navigated the window fails with `ContractError('unavailable', 'The window could not load: <message>')`. The window it created is not closed; it stays open without the shell ([`native-windows.ts`](../doric/src/platform/windows/native-windows.ts)).

### The import map

The platform map is read from `importmap.platform.json` in the platform assets once, when main constructs `DesktopPlatform`; a missing or unreadable file, or one without an `imports` object (`importmap.platform.json has no "imports" object.`), throws there, inside main's `app.whenReady()` handler. The handler's promise then rejects with nothing to handle the rejection (`main.ts` discards it with `void`), the rest of the startup does not run, no window opens, and the Electron process keeps running with no window, since `window-all-closed`, which quits outside macOS, fires only when windows close ([`main.ts`](../doric/src/main.ts), [`app.ts`](../doric/src/platform/app.ts), [`import-map.ts`](../doric/src/platform/protocol/import-map.ts)). The import map is that platform map plus, for each retained bundle of the generation that ships a `contracts` part, the entry `"<id>/contracts"` → `doric://app/bundles/<id>@<version>/<entry>`. Without a generation it is the platform map alone. It is computed once per generation and kept for the life of the process ([`import-map.ts`](../doric/src/platform/protocol/import-map.ts), [`app.ts`](../doric/src/platform/app.ts), [`shell.ts`](../doric/src/platform/protocol/shell.ts)). What the platform map holds is in [platform packages](../../../docs/architecture/bundles/platform-packages.md).

### The content security policy

`<hash>` is the base64 SHA-256 of the exact text between the import map's `<script>` tags ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`csp.ts`](../doric/src/platform/protocol/csp.ts)).

Packaged:

```text
default-src 'none'; script-src 'self' 'sha256-<hash>'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; frame-src doric://app/frame/; connect-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

Development, where `<ws-origin>` is the dev server origin with its leading `http` turned into `ws`:

```text
default-src 'self'; script-src 'self' 'unsafe-eval' 'sha256-<hash>'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; frame-src doric://app/frame/; connect-src 'self' <ws-origin>; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

The packaged policy gives the page no network access (`connect-src 'none'`), and the only document it may frame is the preview frame under `doric://app/frame/`. Whether the app is packaged comes from Electron's `app.isPackaged` ([`main.ts`](../doric/src/main.ts), [`app.ts`](../doric/src/platform/app.ts)).

## What the bootstrap does

The build's `main` script runs [`src/bootstrap.ts`](src/bootstrap.ts):

1. `followScheme()` ([`src/scheme.ts`](src/scheme.ts)) sets the `dark` class on `document.documentElement` when `matchMedia('(prefers-color-scheme: dark)')` matches, and again on every change of that query, for the page's lifetime. It touches no other class, and throws where `matchMedia` is missing. The query follows Electron's `nativeTheme.themeSource`, which main sets from the saved appearance and which is `dark` when nothing is saved ([`appearance.ts`](../doric/src/platform/appearance.ts), [`app.ts`](../doric/src/platform/app.ts)). Tailwind's `dark` variant, `&:is(.dark *)`, matches the descendants of the element that carries that class ([`tailwind.css`](../../../packages/desktop/src/styles/tailwind.css)). When `followScheme()` throws, `src/bootstrap.ts` stops there: `bootstrapWindow` never runs, so the window reports neither ready nor a failure. The doric-e2e fixture shell calls the same function ([`shell-bootstrap.mjs`](../doric-e2e/tests/fixtures/shell-bootstrap.mjs)).
2. `bootstrapWindow({})` ([`bootstrap.ts`](../../../packages/desktop/src/client/bootstrap.ts); its full sequence is in [the `packages/desktop` README](../../../packages/desktop/README.md#bootstrapwindow)) asks main for the window's description, applies its chrome, reads the catalog and activates the generation's client bundles; activation's `insertBundleStyles` appends one `<link rel="stylesheet" data-bundle="<id>">` per bundle part that ships styles to `<head>`, in activation order ([`styles.ts`](../../../packages/desktop/src/client/styles.ts)). It installs, for the page's lifetime: a listener that applies the chrome again on each `onChromeChanged`; `wireClose`, which answers main's close requests through `doric.window.hooks/v1` ([`close.ts`](../../../packages/desktop/src/client/close.ts)); `installKeybindings`, one capture-phase `keydown` listener on `window` that follows the `doric.shell/v1` keybinding table and sends main a matching key ([`keybindings.ts`](../../../packages/desktop/src/client/keybindings.ts)); and `serveShellCommands`, which runs the client commands of the `doric.shell/v1` `commands` stream and answers each with `commandResult` ([`commands.ts`](../../../packages/desktop/src/client/commands.ts)). What each does with these contracts is under [Platform contracts it uses](#platform-contracts-it-uses). It then mounts the outlet `<<core>-outlet>`, where `<core>` is the composition's core bundle id, by replacing the body's children, `<div id="root">` included, and reports the window ready.

   It reports a failure to main instead, and does not report ready:
   - any error thrown while booting: kind `bootstrap`, with the error's message;
   - in the primary window only, a quarantined core: kind `core`, `bundleId` the core's id, with the quarantine reasons joined by `; `, or `Core bundle "<core>" is quarantined.` when there are none;
   - in any window, an outlet element the core did not define: kind `core`, `bundleId` the core's id, with the quarantine message when the core is quarantined, else `Core bundle "<core>" did not define <<core>-outlet>.`

   In a window other than the primary, a quarantined core whose outlet is defined mounts. How main answers a failure is in [windows](../../../docs/architecture/bundles/windows.md).

   Some failures are never reported ([`bootstrap.ts`](../../../packages/desktop/src/client/bootstrap.ts), [`src/bootstrap.ts`](src/bootstrap.ts)):
   - When `window.doric` is missing, reading `window.doric.desktop` throws before the error handling starts, so `bootstrapWindow` rejects without a report.
   - `ready()` and `reportFailure()` are awaited without a guard, so when one rejects, `bootstrapWindow` rejects with that error.
   - `src/bootstrap.ts` discards the promise of `bootstrapWindow` (`void`), so each of these rejections goes unhandled.

The outlet, the `core` bundle's `<core-outlet>`, shows what the active route renders ([`outlet.ts`](../../../bundles/foundation/core/src/client/elements/outlet.ts)); routing is the core's ([navigation](../../../docs/architecture/bundles/navigation.md)). `/` is the `layout` bundle's workspace frame, `<layout-workspace>` ([`layout/src/client/index.ts`](../../../bundles/desktop/layout/src/client/index.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). Its child routes (`/projects` and `/projects/:projectId`, registered by the `workspace` bundle, and the Thread route `/projects/:projectId/threads/:threadId`, registered by the `chat` bundle) are drawn inside it; in its conversation form the frame shows the child route in a nested `<core-outlet>` ([`workspace/src/client/index.ts`](../../../bundles/desktop/workspace/src/client/index.ts), [`chat/src/client/index.ts`](../../../bundles/desktop/chat/src/client/index.ts), [`thread-route.ts`](../../../bundles/desktop/chat/src/client/domain/thread-route.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). The `workspace` bundle fills the frame's slots: the sidebar and the Project tabs whatever the route, and, while the route is `/` or `/projects`, the Dashboard in `shell.page`, which puts the frame in its page form, and its footer in `shell.sidebar.footer` ([`workspace/src/client/index.ts`](../../../bundles/desktop/workspace/src/client/index.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). `/settings` is a top-level route, the `settings` bundle's page, so the frame is not drawn there ([`settings/src/client/index.ts`](../../../bundles/desktop/settings/src/client/index.ts)). The full detail of these elements, routes and slots is in each bundle's README: [`core`](../../../bundles/foundation/core/README.md#structural-elements), [`layout`](../../../bundles/desktop/layout/README.md#the-frame), [`workspace`](../../../bundles/desktop/workspace/README.md#elements-routes-and-slot-items), [`chat`](../../../bundles/desktop/chat/README.md#elements-route-slot-items) and [`settings`](../../../bundles/desktop/settings/README.md#routes).

### Platform contracts it uses

The page reaches main only through `window.doric.desktop`, the one object the preload exposes, of type `DoricDesktopApi` ([`preload.ts`](../doric/src/app/api/preload.ts), [`desktop.ts`](../doric/src/app/api/desktop.ts), [`protocol.ts`](../../../packages/desktop/src/client/protocol.ts); its full shape is in [the `packages/desktop` README](../../../packages/desktop/README.md#doricdesktopapi)). Its requests travel on the IPC channel `doric:desktop` as the operations `describeWindow`, `ready`, `reportFailure`, `catalog`, `call`, `cancel`, `subscribe`, `unsubscribe` (sent when a subscription's returned function runs while the stream is open) and `closeAnswer` (the answer to a close request). Main pushes on `doric:desktop:push`: `chrome`, `close-requested`, and `event` and `end` for an open subscription. Only `call` and `subscribe` carry a contract call envelope, which main's dispatcher routes ([services and channels](../../../docs/architecture/bundles/services-and-channels.md#the-dispatcher-in-the-desktop-process)); the other operations belong to the window protocol itself.

Through `call` and `subscribe`, the bootstrap uses two platform contracts:

- **`doric.shell/v1`**, platform-internal, always with `bundleId: null` ([`bridge.ts`](../../../packages/desktop/src/client/bridge.ts)). `installKeybindings` subscribes to the `keybindings` stream, a `{ key, command }[]` table, and on a matching key calls `preventDefault()` on the event and calls `keybinding({ key })`, fire-and-forget ([`keybindings.ts`](../../../packages/desktop/src/client/keybindings.ts)). `serveShellCommands` subscribes to the `commands` stream; for each `{ id, command, input }` it runs `commands/v1.execute(command, input ?? {})` and calls `commandResult` with `{ id, ok: true }` or `{ id, ok: false, error: { code, message, details? } }`, fire-and-forget ([`commands.ts`](../../../packages/desktop/src/client/commands.ts)). The window platform that activation registers ([`activate.ts`](../../../packages/desktop/src/client/activate.ts)) also sends `log` and `diagnostic`, fire-and-forget ([`platform.ts`](../../../packages/desktop/src/client/platform.ts)), follows the `connection` stream ([`connection.ts`](../../../packages/desktop/src/client/connection.ts)), and calls `openExternal` ([`browser.ts`](../../../packages/desktop/src/client/browser.ts)) and `appearanceGet` and `appearanceSet` ([`appearance.ts`](../../../packages/desktop/src/client/appearance.ts)). The method table is in [the `packages/desktop` README](../../../packages/desktop/README.md#doricshellv1); how main serves it, in [services and channels](../../../docs/architecture/bundles/services-and-channels.md#the-dispatcher-in-the-desktop-process).
- **`doric.window.hooks/v1`**, which activation defines in the window's `hooks/v1` provider ([`activate.ts`](../../../packages/desktop/src/client/activate.ts)). On a `close-requested` push in phase `close`, `wireClose` answers `{ allow: true }` when the request is forced or the window has no hooks, and otherwise the decision of `onCloseHook`, with no deadline: `{ allow: true }`, or `{ allow: false, reason }` when the hook refuses; in phase `flush` it runs `onFlushHook` with the request's deadline when it is not `0`, ignores its outcome and answers `{ allow: true }` ([`close.ts`](../../../packages/desktop/src/client/close.ts)). The preload sends the answer as `closeAnswer`. In phase `close`, a handler that rejects (as `onCloseHook` throwing does) or answers nothing is sent as `{ allow: true }`, so a failing veto never keeps the window open; in phase `flush` the preload waits for the handler to settle and sends `{ allow: true }` ([`desktop.ts`](../doric/src/app/api/desktop.ts)). The hooks' full shape is in [hooks](../../../docs/architecture/bundles/hooks.md#doricwindowhooksv1).

## Styles and their cascade

A window's stylesheets apply in this order:

1. `desktop/ui`'s `theme.css` (`/platform/desktop@<v>/theme.css`), inserted first in `<head>` by main: the preflight, the font faces, the tokens and the theme mapping ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`theme.css`](../../../packages/desktop/src/styles/theme.css); described in [the `packages/desktop` README](../../../packages/desktop/README.md#stylesheets)).
2. This project's sheet, linked by the build from the template's `<head>` ([`webpack.config.js`](webpack.config.js)).
3. Each UI bundle's `client/styles.css`, appended at activation by `insertBundleStyles` ([`styles.ts`](../../../packages/desktop/src/client/styles.ts); described in [the `packages/desktop` README](../../../packages/desktop/README.md#close-commands-keybindings-and-styles)).

[`src/styles.css`](src/styles.css) holds:

- **The utility set.** `@import 'tailwindcss/utilities.css' layer(utilities) source(none)` with `@reference 'desktop/ui/tailwind.css'`, scanning only the named sources: this project's `src/`, `packages/desktop/src`, and every bundle's `bundles/*/*/src/client/**/*`. The sources are listed, not detected from the working directory, so the set does not depend on where the build runs. Because the sheet emits every utility the theme and the bundle sheets emit, in the order one compiled sheet gives them, a class that two sheets emit keeps that order whichever sheet comes later.
- **The base layer.** A pointer cursor on every enabled clickable surface (links, buttons, `summary`, `select`, button-like and check inputs, labels holding a checkbox or radio, and the roles `button`, `checkbox`, `link`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, `option`, `radio`, `switch`, `tab` and `treeitem` unless `aria-disabled='true'`); `body` with the background and foreground colors, `margin: 0`, `var(--font-sans)` and no text selection; text selection back on `input`, `textarea` and `[contenteditable='true']`; the `data-placeholder` text of an empty content-editable element, muted at 0.6 opacity; and `height: 100%` on `html`, `body` and `#root`.
- **`.chrome-bar`**, unlayered: `height: 40px`, the one height of the window chrome bars ([window appearance](../../../docs/architecture/bundles/window-appearance.md)).
- **The footer weight**, unlayered: `font-weight: 400 !important` on `footer`, on any element whose `data-slot` ends in `-footer`, and on everything inside them, so it overrides utilities and inline weights.

The sheet sets no weight on `body` or on the headings; running text at 300 and headings at 400 come from the theme. Fonts, tokens and the preflight are defined only by the theme. Rules of one surface are in the sheets of the bundles that draw it: the conversation's in [`chat`](../../../bundles/desktop/chat/src/client/styles.css), the Monaco scrollbar slider in both [`files`](../../../bundles/features/files/src/client/styles.css) and [`git`](../../../bundles/features/git/src/client/styles.css), and the xterm slider in [`terminal`](../../../bundles/features/terminal/src/client/styles.css).

## Build

```console
npx nx run doric-renderer:build
```

The build target is inferred by `@nx/webpack/plugin` from [`webpack.config.js`](webpack.config.js): it runs `webpack-cli build --node-env=production` with the project folder `app/desktop/doric-renderer` as its working directory ([`nx.json`](../../../nx.json)). `webpack-cli` sets `process.env.NODE_ENV` from `--node-env` before it loads the config, so a build always sees `production`, whatever `NODE_ENV` the shell exports, and always hashes names and optimizes. [`project.json`](project.json) makes the target depend on the dependencies' builds and `desktop:build`, and adds every bundle's client sources to its inputs, since the utility set scans them. The config uses two Nx plugins: `NxAppWebpackPlugin`, with `tsConfig: './tsconfig.app.json'` and `compiler: 'babel'`, and `NxReactWebpackPlugin` with its default options. It compiles [`src/bootstrap.ts`](src/bootstrap.ts) with Babel (React preset, [`.babelrc`](.babelrc)) and bundles it with the workspace packages it imports, from source (resolve conditions `@org/source`, `import`, `module`, `browser`, `default`), into the `main` script. It writes to `dist/app/desktop/doric-renderer/`, cleaned on each build:

- `shell.html`, the template with the build's stylesheet link added to `<head>` and the three scripts `runtime`, `styles` and `main` added to `<body>` in that order as `<script type="module">`, all as absolute URLs under `/platform/shell@1.0.0/` and with no `<base>` element;
- the `runtime`, `styles` and `main` scripts and the `styles` sheet, with content hashes in their names (for example `main.<hash>.js` and `styles.<hash>.css`) and optimized, because `NODE_ENV` is `production` (`outputHashing: 'all'`, `optimization: true`); with any other `NODE_ENV`, as under `serve`, names carry no hash and nothing is optimized;
- `favicon.ico`.

The public path is the literal `output.publicPath`, `/platform/shell@1.0.0/`. `output.scriptType: 'text/javascript'` makes any chunk script webpack loads at run time a classic script; the build has no async chunks, so the `runtime` script holds no chunk loading and no public-path code. Source-map warnings from `rehype-harden` are ignored. The `doric-app` build does not build this project. The `package` and `make` targets of `doric-app` name it as their frontend project with `sourcePath: dist/app`, and do not build it first; the packager copies the frontend from `<sourcePath>/doric-renderer`, that is `dist/app/doric-renderer`, while this build writes `dist/app/desktop/doric-renderer` ([`project.json`](../doric/project.json)).

## Run

From the repository root:

```console
npm run doric:dev
```

The script builds the desktop generation runner (`nx run doric-app:build-runner`), then runs two processes under `concurrently --kill-others --success first`: `nx serve doric-renderer`, and `wait-on tcp:127.0.0.1:4200 && nx serve doric-app`, which starts the app once the dev server's port accepts connections. When either process exits, `concurrently` kills the other, and the script exits with the status of the first to exit ([`package.json`](../../../package.json)). The `serve` target depends on `desktop:build` ([`project.json`](project.json)).

The dev server ([`webpack.config.js`](webpack.config.js)) listens on `http://localhost:4200`, serves the build under `/platform/shell@1.0.0/`, and answers any HTML request with `/platform/shell@1.0.0/shell.html`. In development the windows open `doric://app` too; main fetches the template from the dev server and forwards every `/platform/shell@<v>/` file request to it, copying the status and `content-type`, and a forward that fails is a `404` ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts), [`handler.ts`](../doric/src/platform/protocol/handler.ts)). Since those requests carry the `doric://app` host, the dev server accepts every host, and its hot-reload client connects to the fixed `ws://localhost:4200/ws`. The error overlay shows a runtime error unless [`showsInOverlay`](overlay-errors.js) finds, in the error or in one of its first seven `cause`s, a message starting with `ResizeObserver loop` or a stack containing `doric://app/artifacts/`.

- [`tests/stylesheet.test.ts`](tests/stylesheet.test.ts) compiles the theme, the shell sheet and the `chat` and `layout` bundle sheets with Tailwind's PostCSS plugin and asserts: the shell emits every utility of the theme and of the chat sheet in their order; fonts, tokens and the preflight come only from the theme, which defines 12 font faces, sets `:root` to 300 and every heading to 400; the shell sets no body or heading weight; `.chrome-bar` and the footer rule are unlayered with their values; the shell carries the important `sm:max-w-3xl!` max width inside its `40rem` media query; the shell holds none of the editor, queue, conversation-highlight, Monaco slider and xterm slider selectors, the chat sheet holds the editor, queue and conversation-highlight rules, and the `layout` sheet holds the Monaco slider as an unlayered rule and the xterm slider; and the `layout` sheet emits no utilities.
