# Doric renderer shell

`doric-renderer` (Nx project `doric-renderer`) builds the shell: the one page every Doric desktop window loads from `doric://app`. The shell holds no product UI. It follows the system color scheme, boots the window through `desktop/client`'s `bootstrapWindow`, and carries the window-wide stylesheet; the workspace, the conversation and the settings are drawn by client bundles. The Electron main process serves the build and renders its HTML template per request, adding the import map, the platform theme and the content security policy.

The feature doc is [the workspace window](../../../docs/features/ui-redesign.md), which covers the window's frame, its 40 px bars and the footer weight; the theme preference and the `dark` class are in [window appearance](../../../docs/architecture/bundles/window-appearance.md#theme). The main process that serves the shell is described in the [desktop README](../doric/README.md); the protocol that serves it, in [the `doric://app` protocol](../../../docs/architecture/bundles/doric-protocol.md); how a window boots from it, in [windows](../../../docs/architecture/bundles/windows.md); the shared packages and the theme tokens, in [platform packages](../../../docs/architecture/bundles/platform-packages.md).

## What a window loads

The shell's files live under the URL prefix `/platform/shell@<v>/`, where `<v>` is `PLATFORM_ASSETS_VERSION`, `1.0.0` ([`version.ts`](../../../packages/bundle/src/runtime/version.ts), [`resources.ts`](../doric/src/platform/protocol/resources.ts)). The build writes the prefix as a literal instead: `shellPath` in [`webpack.config.js`](webpack.config.js) and the favicon link in [`src/shell.html`](src/shell.html) both say `/platform/shell@1.0.0/`, and nothing ties that literal to `PLATFORM_ASSETS_VERSION`. When the two differ, packaged, the protocol's `route()` takes `/platform/shell@1.0.0/…` for an ordinary platform file and looks for it in the platform assets, so every shell file the template names is a `404` ([`handler.ts`](../doric/src/platform/protocol/handler.ts)); in development main fetches `/platform/shell@<v>/shell.html` from the dev server, which serves only `/platform/shell@1.0.0/`, so rendering the shell fails ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)).

A window loads `doric://app/<path>`. For any path outside the asset prefixes (`/platform/`, `/bundles/`, `/schemas/`, `/frame/`, `/papercraft-modules/`), main's protocol handler answers a navigation with the rendered shell and a `content-security-policy` header. A request is a navigation when its `Sec-Fetch-Dest` header, if present, is `document`; without that header, when its `Accept` header names `text/html` or `application/xhtml+xml`, or when it has no `Accept` header. Any other request, and any path whose last segment carries a file extension, is a `404` ([`handler.ts`](../doric/src/platform/protocol/handler.ts)). A request under `/platform/shell@<v>/<file…>` is a file of this build: read from `doric-renderer/` beside the built main process (`dist/app/desktop/doric-renderer` in the workspace) when packaged, forwarded to the dev server otherwise ([`handler.ts`](../doric/src/platform/protocol/handler.ts), [`resources.ts`](../doric/src/platform/protocol/resources.ts)). The full routing table is in [the `doric://app` protocol](../../../docs/architecture/bundles/doric-protocol.md#what-the-handler-serves).

### The rendered template

Main renders the shell for each request from the built `shell.html` ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`app.ts`](../doric/src/platform/app.ts)):

1. It takes the template. Packaged, it reads `shell.html` from the shell root once and caches it; a failed read clears the cache, so the next request reads again. In development it fetches `<dev-server>/platform/shell@<v>/shell.html` on every request, and a status other than 2xx is an error ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)).
2. It inserts, right after the opening `<head>` tag and before everything the template holds:
   1. `<meta name="doric-generation" content="<n>">`, the newest client generation, only when there is one;
   2. `<script type="importmap">` holding `{"imports": {…}}`, with every `<` written as `\u003c`;
   3. `<link rel="stylesheet" href="/platform/desktop@<v>/theme.css">`, the theme of `desktop/ui`.
3. It answers with `content-type: text/html` and the policy of its mode.

A template without a `<head>` element makes `renderShell` throw `The shell template has no <head> element.`; that error, like a failed template read or a dev server answer other than 2xx (`The renderer dev server answered <status> for shell.html.`), rejects the protocol handler's answer, so the navigation fails ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`handler.ts`](../doric/src/platform/protocol/handler.ts), [`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)). Main's `loadURL` of the window then rejects, and the call that opened or navigated the window fails with `ContractError('unavailable', 'The window could not load: <message>')`. The window it created is not closed; it stays open without the shell ([`native-windows.ts`](../doric/src/platform/windows/native-windows.ts)).

### The import map

The platform map is read from `importmap.platform.json` in the platform assets once, when main constructs `DesktopPlatform`; a missing or unreadable file, or one without an `imports` object (`importmap.platform.json has no "imports" object.`), throws there, inside main's `app.whenReady()` handler, so the rest of the startup does not run and no window opens ([`main.ts`](../doric/src/main.ts), [`app.ts`](../doric/src/platform/app.ts), [`import-map.ts`](../doric/src/platform/protocol/import-map.ts)). The import map is that platform map plus, for each retained bundle of the generation that ships a `contracts` part, the entry `"<id>/contracts"` → `doric://app/bundles/<id>@<version>/<entry>`. Without a generation it is the platform map alone. It is computed once per generation and kept for the life of the process ([`import-map.ts`](../doric/src/platform/protocol/import-map.ts), [`app.ts`](../doric/src/platform/app.ts), [`shell.ts`](../doric/src/platform/protocol/shell.ts)). What the platform map holds is in [platform packages](../../../docs/architecture/bundles/platform-packages.md).

### The content security policy

`<hash>` is the base64 SHA-256 of the exact text between the import map's `<script>` tags ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`csp.ts`](../doric/src/platform/protocol/csp.ts)).

Packaged:

```text
default-src 'none'; script-src 'self' 'sha256-<hash>'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; frame-src doric://app/frame/; connect-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

Development, where `<ws-origin>` is the dev server origin with its leading `http` turned into `ws`:

```text
default-src 'self'; script-src 'self' 'unsafe-eval' 'sha256-<hash>'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; frame-src doric://app/frame/; connect-src 'self' <ws-origin>; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

The packaged policy gives the page no network access (`connect-src 'none'`), and the only document it may frame is the preview frame under `doric://app/frame/`. Whether the app is packaged comes from Electron's `app.isPackaged` ([`main.ts`](../doric/src/main.ts), [`app.ts`](../doric/src/platform/app.ts)).

## What the bootstrap does

The build's `main` script runs [`src/bootstrap.ts`](src/bootstrap.ts):

1. `followScheme()` ([`src/scheme.ts`](src/scheme.ts)) sets the `dark` class on `document.documentElement` when `matchMedia('(prefers-color-scheme: dark)')` matches, and again on every change of that query, for the page's lifetime. It touches no other class, and throws where `matchMedia` is missing. The query follows Electron's `nativeTheme.themeSource`, which main sets from the saved appearance and which is `dark` when nothing is saved ([`appearance.ts`](../doric/src/platform/appearance.ts), [`app.ts`](../doric/src/platform/app.ts)). Tailwind's `dark` variant reads that class. The doric-e2e fixture shell calls the same function ([`shell-bootstrap.mjs`](../doric-e2e/tests/fixtures/shell-bootstrap.mjs)).
2. `bootstrapWindow({})` ([`bootstrap.ts`](../../../packages/desktop/src/client/bootstrap.ts)) asks main for the window's description, applies its chrome, reads the catalog and activates the generation's client bundles, which appends one `<link rel="stylesheet">` per bundle part that ships styles to `<head>`, in activation order ([`styles.ts`](../../../packages/desktop/src/client/styles.ts)). It installs, for the page's lifetime: a listener that applies the chrome again on each `onChromeChanged`; `wireClose`, which answers main's close requests through the window hooks ([`close.ts`](../../../packages/desktop/src/client/close.ts)); `installKeybindings`, one `keydown` listener on `window` that asks main to dispatch a matching keybinding ([`keybindings.ts`](../../../packages/desktop/src/client/keybindings.ts)); and `serveShellCommands`, which runs the client commands main sends and answers each with its result ([`commands.ts`](../../../packages/desktop/src/client/commands.ts)). It then mounts the outlet `<<core>-outlet>`, where `<core>` is the composition's core bundle id, by replacing the body's children, `<div id="root">` included, and reports the window ready.

   It reports a failure to main instead, and does not report ready:
   - any error thrown while booting: kind `bootstrap`, with the error's message;
   - in the primary window only, a quarantined core: kind `core`, with the quarantine reasons joined by `; `, or `Core bundle "<core>" is quarantined.` when there are none;
   - in any window, an outlet element the core did not define: kind `core`, with the quarantine message when the core is quarantined, else `Core bundle "<core>" did not define <<core>-outlet>.`

   In a window other than the primary, a quarantined core whose outlet is defined still mounts. How main answers a failure is in [windows](../../../docs/architecture/bundles/windows.md).

The outlet, the `core` bundle's `<core-outlet>`, shows what the active route renders ([`outlet.ts`](../../../bundles/foundation/core/src/client/elements/outlet.ts)); routing is the core's ([navigation](../../../docs/architecture/bundles/navigation.md)). `/` is the `layout` bundle's workspace frame, `<layout-workspace>` ([`layout/src/client/index.ts`](../../../bundles/desktop/layout/src/client/index.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). Its child routes (`/projects` and `/projects/:projectId`, registered by the `workspace` bundle, and the Thread route `/projects/:projectId/threads/:threadId`, registered by the `chat` bundle) are drawn inside it; in its conversation form the frame shows the child route in a nested `<core-outlet>` ([`workspace/src/client/index.ts`](../../../bundles/desktop/workspace/src/client/index.ts), [`chat/src/client/index.ts`](../../../bundles/desktop/chat/src/client/index.ts), [`thread-route.ts`](../../../bundles/desktop/chat/src/client/domain/thread-route.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). The `workspace` bundle fills the frame's slots: the sidebar and the Project tabs whatever the route, and, while the route is `/` or `/projects`, the Dashboard in `shell.page`, which puts the frame in its page form, and its footer in `shell.sidebar.footer` ([`workspace/src/client/index.ts`](../../../bundles/desktop/workspace/src/client/index.ts), [`workspace-view.tsx`](../../../bundles/desktop/layout/src/client/views/workspace-view.tsx)). `/settings` is a top-level route, the `settings` bundle's page, so the frame is not drawn there ([`settings/src/client/index.ts`](../../../bundles/desktop/settings/src/client/index.ts)).

The page reaches main only through `window.doric.desktop`, the one object the preload exposes ([`preload.ts`](../doric/src/app/api/preload.ts)); every call is a contract call that main's dispatcher routes ([services and channels](../../../docs/architecture/bundles/services-and-channels.md)).

## Styles and their cascade

A window's stylesheets apply in this order:

1. `desktop/ui`'s `theme.css` (`/platform/desktop@<v>/theme.css`), inserted first in `<head>` by main: the preflight, the font faces, the tokens and the theme mapping ([`shell.ts`](../doric/src/platform/protocol/shell.ts), [`theme.css`](../../../packages/desktop/src/styles/theme.css)).
2. This project's sheet, linked by the build from the template's `<head>` ([`webpack.config.js`](webpack.config.js)).
3. Each UI bundle's `client/styles.css`, appended at activation ([`styles.ts`](../../../packages/desktop/src/client/styles.ts)).

[`src/styles.css`](src/styles.css) holds:

- **The utility set.** `@import 'tailwindcss/utilities.css' layer(utilities) source(none)` with `@reference 'desktop/ui/tailwind.css'`, scanning only the named sources: this project's `src/`, `packages/desktop/src`, and every bundle's `bundles/*/*/src/client/**/*`. The sources are listed, not detected from the working directory, so the set does not depend on where the build runs. Because the sheet emits every utility the theme and the bundle sheets emit, in the order one compiled sheet gives them, a class that two sheets emit keeps that order whichever sheet comes later.
- **The base layer.** A pointer cursor on every enabled clickable surface (links, buttons, `summary`, `select`, button-like and check inputs, labels holding a checkbox or radio, and the roles `button`, `checkbox`, `link`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, `option`, `radio`, `switch`, `tab` and `treeitem` unless `aria-disabled='true'`); `body` with the background and foreground colors, `margin: 0`, `var(--font-sans)` and no text selection; text selection back on `input`, `textarea` and `[contenteditable='true']`; the `data-placeholder` text of an empty content-editable element, muted at 0.6 opacity; and `height: 100%` on `html`, `body` and `#root`.
- **`.chrome-bar`**, unlayered: `height: 40px`, the one height of the window chrome bars ([window appearance](../../../docs/architecture/bundles/window-appearance.md)).
- **The footer weight**, unlayered: `font-weight: 400 !important` on `footer`, on any element whose `data-slot` ends in `-footer`, and on everything inside them, so it overrides utilities and inline weights.

The sheet sets no weight on `body` or on the headings; running text at 300 and headings at 400 come from the theme. Fonts, tokens and the preflight are defined only by the theme. Rules of one surface are in the sheets of the bundles that draw it: the conversation's in [`chat`](../../../bundles/desktop/chat/src/client/styles.css), the Monaco scrollbar slider in both [`files`](../../../bundles/features/files/src/client/styles.css) and [`git`](../../../bundles/features/git/src/client/styles.css), and the xterm slider in [`terminal`](../../../bundles/features/terminal/src/client/styles.css).

## Build

```console
npx nx run doric-renderer:build
```

The build target is inferred by `@nx/webpack/plugin` from [`webpack.config.js`](webpack.config.js); [`project.json`](project.json) makes it depend on the dependencies' builds and `desktop:build`, and adds every bundle's client sources to its inputs, since the utility set scans them. It compiles [`src/bootstrap.ts`](src/bootstrap.ts) with Babel (React preset, [`.babelrc`](.babelrc)) and bundles it with the workspace packages it imports, from source (resolve conditions `@org/source`, `import`, `module`, `browser`, `default`), into the `main` script. It writes to `dist/app/desktop/doric-renderer/`, cleaned on each build:

- `shell.html`, the template with the build's stylesheet link added to `<head>` and the three scripts `runtime`, `styles` and `main` added to `<body>` in that order as `<script type="module">`, all as absolute URLs under `/platform/shell@1.0.0/` and with no `<base>` element;
- the `runtime`, `styles` and `main` scripts and the `styles` sheet, with content hashes in their names when `NODE_ENV=production`, which also turns on optimization;
- `favicon.ico`.

Chunks use `scriptType: 'text/javascript'`, so their public path comes from `self.location`. Source-map warnings from `rehype-harden` are ignored. The `doric-app` build does not build this project. The `package` and `make` targets of `doric-app` name it as their frontend project with `sourcePath: dist/app`, and do not build it first; the packager copies the frontend from `<sourcePath>/doric-renderer`, that is `dist/app/doric-renderer`, while this build writes `dist/app/desktop/doric-renderer` ([`project.json`](../doric/project.json)).

## Run

From the repository root:

```console
npm run doric:dev
```

The script builds the desktop generation runner, starts `nx serve doric-renderer`, waits for port 4200, then starts `nx serve doric-app` ([`package.json`](../../../package.json)). The `serve` target depends on `desktop:build` ([`project.json`](project.json)).

The dev server ([`webpack.config.js`](webpack.config.js)) listens on `http://localhost:4200`, serves the build under `/platform/shell@1.0.0/`, and answers any HTML request with `/platform/shell@1.0.0/shell.html`. The windows still open `doric://app`; main fetches the template from the dev server and forwards every `/platform/shell@<v>/` file request to it, copying the status and `content-type`, and a forward that fails is a `404` ([`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts), [`handler.ts`](../doric/src/platform/protocol/handler.ts)). Since those requests carry the `doric://app` host, the dev server accepts every host, and its hot-reload client connects to the fixed `ws://localhost:4200/ws`. The error overlay shows a runtime error unless [`showsInOverlay`](overlay-errors.js) finds, in the error or in one of its first seven `cause`s, a message starting with `ResizeObserver loop` or a stack containing `doric://app/artifacts/`.

| Setting                  | Default                 | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------ | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DORIC_RENDERER_DEV_URL` | `http://localhost:4200` | Used only when the app is not packaged. The dev server main fetches the template from and forwards shell files to, with trailing slashes removed ([`main.ts`](../doric/src/main.ts), [`dev-proxy.ts`](../doric/src/platform/protocol/dev-proxy.ts)); a template answer other than 2xx fails with `The renderer dev server answered <status> for shell.html.` The development policy's `connect-src` takes the value as given, with `http` turned into `ws` ([`app.ts`](../doric/src/platform/app.ts), [`csp.ts`](../doric/src/platform/protocol/csp.ts)). The dev server's own port and its hot-reload URL stay `4200`, so with another origin the hot-reload client's connection to `ws://localhost:4200/ws` is blocked by that policy. |
| `NODE_ENV`               | unset                   | `production` turns on content hashes and optimization in the build                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `DORIC_THEME`            | unset                   | Unpackaged only: `light`, `dark` or `system` overrides the saved theme that `followScheme` follows ([`appearance.ts`](../doric/src/platform/appearance.ts))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
